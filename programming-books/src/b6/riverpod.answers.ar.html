1. أول لمسة ترمي خطأً: فـ build تعيد const {}، والخريطة الثابتة لا تتغير، فتفشل state[item] = … بـ UnsupportedError، ويفشل معها كل اختبار يضيف إلى السلة. واجعل الحالة الأولى {} عادية فيختفي الخطأ، وهذا أسوأ: فالخريطة تتغير الآن، لكن state هو الكائن نفسه، فلا يُبلَّغ أحد، وتبقى الدوائر على الشاشة تعرض 0، ويعدّ اختبار select مرة بناء واحدة لكل منهما. والحالات الأولى الثابتة حارس رخيص من هذا الخطأ.
  2. يُرسل الطلب وتُفرَّغ السلة، لكن «طلباتك» تبقى تقول «لم تطلب شيئاً بعد»: فالسجل حُمِّل مرة ولم يخبره شيء أنه صار قديماً. ولا يلحق إلا حين يعيد بناءه شيء من الصفر: زر «أعد المحاولة»، أو مغادرة شاشة رُمي الـ provider الخاص بها ثم فتحها، أو إعادة تشغيل التطبيق. والإبطال في المكان الذي تتغير فيه البيانات هو ما يُبقي كل شاشة صحيحة دون أن تعرف الشاشات بعضها.
  3. ref.listen(placeControllerProvider, (previous, next) { if (next.value case Ok(:final value)) { ScaffoldMessenger.of(context).showSnackBar(SnackBar(content: Text('… ${value.id}'))); } }); في بداية build. فـ listen تشغّل دالة مرة واحدة لكل تغيير، وهذا ما يحتاجه الأثر الجانبي: شريط سفلي، أو انتقال، أو صوت. أما watch فتعيد البناء فقط، وعرض الشريط من build سيعرضه من جديد مع كل إعادة بناء، حتى حين لا يحدث جديد.
  4. FutureProvider(…, retry: (count, error) => null). فتعرض شاشة انقطاع الاتصال الخطأ فوراً بدل قيمة تبقى في التحميل أثناء إعادة المحاولة؛ ويبقى زر «أعد المحاولة» يعمل لأنه يُبطل. واختر ذلك حين لا تفيد إعادة المحاولة (403، أو خطأ تحقق، أو سجل غير موجود)، أو حين يجب أن يقرر الشخص، مثلاً على باقة بيانات محدودة؛ وأبقِ إعادة المحاولة التلقائية للأخطاء العابرة مثل انتهاء المهلة.
  5. historyProvider.overrideWith((ref) async => [order1, order2, order3]). وهذا يتخطى المصدر والـ DTO وتحويل المستودع: جيد لصور الشاشات ولاختبار كيف ترسم الصفحة قائمة معروفة، لكنه لم يعد يختبر أن طبقة البيانات تنتج هذه القائمة، ولا تظهر الطلبات الجديدة أبداً، لأن إبطال السجل يشغّل الاستبدال من جديد فيعيد الثلاثة نفسها. أما استبدال المصدر فيُبقي كل الطبقات تعمل.
