Capstone: A Production App

In this chapter you will

  • see one app built with the architecture, state, navigation and data layers of this book
  • follow a customer from the menu to an order that is ready, in tests at every level
  • check the whole app for accessibility, dark mode and large text
  • run the release pipeline: format, analysis, tests with coverage, and a production build
  • extend the app the way a team would: favorites, robustness checks, an offline outbox

Each chapter so far built one part, on its own, so that it could be seen clearly. A real app is all of them at once, and most of the skill of a senior engineer is in how they fit: which layer knows what, where a rule lives, what a test proves. This chapter builds Bit Café, a small ordering app, from the parts of the book, and runs everything a team would run before shipping it.

Everything in this chapter ran on the book’s machine: seven test files, the Linux integration test, the CI script and the web build behind the screenshots. And, fittingly for a last chapter, the screenshots caught a bug that every test had passed. Section {{n}}.5 shows it.

The rule that holds it together is the one from Chapter 2: dependencies point inward. Pages know providers; providers know the data layer’s interfaces; nothing in data/ knows about widgets. That is what lets every layer be tested without the ones above it.

Watch out
All of those tests passed on the first run, and the first screenshot of the menu still showed a bug: the plus on each “Add” button was drawn dark grey on brown, barely visible. A ListTile gives its trailing widget the tile’s icon colour, and that won over the filled button’s own. No test looked at that colour: the contrast guideline checks text, not icons. Giving the icon onPrimary explicitly fixed it. Tests prove what you thought to check; looking at the real screen, in both themes and both languages, catches what you did not.

Before a release, the same script CI runs on every push: formatting, analysis, every test with coverage, and the production build.






From here, Chapter 15’s flavors and signing turn the build into store packages, Chapter 12’s push source replaces the demo’s, and Chapter 14’s token store holds the session. Each is a file added to the map above, not a change to what is already there. That is the payoff of the structure: a feature is a new folder; a new service is a new implementation of an interface.



Professional habit
Write down the decisions that shaped the app, in a short file next to the code: why Riverpod, why this folder structure, why the menu is cached, why notifications ask after the first order. A new team member reads the code to learn what it does and the decision record to learn why, and the why is what stops the next refactor from undoing a choice that was made for a reason.

Where to go from here


You have built every part of a production Flutter app and put them together. The next step is not another book: it is a real app, with real users, shipped and then improved, release after release. Keep the habits of these chapters (pass in what you depend on, measure before you optimize, test what matters, look at the real screen) and the code will stay something a team is glad to work on.
