CI/CD, Flavors and Signing

In this chapter you will learn to

  • build one app for several environments from configuration files, not from edits to the code
  • give each environment its own installable Android app with product flavors
  • sign release builds with a key whose password never touches a file
  • write a release script that refuses to build from an unsafe state
  • run the same checks on every push with a CI workflow, and on your own machine before pushing

Book 5 ended with one app, signed once, by hand. A team needs more: a build that talks to the test server and one that talks to the real one, both installed on the same phone; a release that cannot be made from a forgotten change; and a machine that checks every push before a person reviews it. None of it is hard. All of it is easy to get subtly wrong, which is why it belongs in scripts.

Every build in this chapter really ran: three flavors of the Android app, a signed release, two refusals by the release script, the CI script from start to finish, and the web app built twice from two configuration files.

{{n}}.2 Flavors: installable side by side



Testers want the development app and the store app on the same phone. Android tells apps apart by their application id, so each flavor gets its own id suffix and its own name:






The manifest’s label becomes @string/app_name, so each flavor’s name appears under its icon. A build names the flavor and its configuration file together:






com.example.bit_app.dev, “Bit Café Dev”, version 0.1.0-dev: a different app as far as the phone is concerned, with its own data, installable next to the real one. iOS does the same with schemes and build configurations in Xcode; the Dart side, --flavor and the configuration file, stays the same.



{{n}}.3 Signing, without a password in any file



The release key is made once (Book 5, Chapter 15) and kept off the repository. The password is never written down in the project: it is taken from the environment when the build runs.










On a CI machine, the keystore and its password come from the CI system’s secret store, written to the machine for the length of the job and gone when it ends. (keytool’s note about JKS is real advice: PKCS12 is the standard format, and the same steps work with -storetype PKCS12.)

{{n}}.5 CI: the same checks, on every push



Continuous integration runs the project’s checks on a clean machine for every push and pull request, so a mistake is found minutes after it is made, by a machine, not days later by a colleague. The checks live in a script in the repository, so they are the same everywhere:

Professional habit
Make the main branch protected: no merge without a green CI run and one review. Keep the pipeline fast (under ten minutes) so that people wait for it instead of working around it, and treat a red build on the main branch as the team’s first job of the day. A pipeline that is often red teaches everyone to ignore it.

Summary



    

  • Each environment is a configuration file; the app reads compile-time constants from one place, with safe defaults.
    • 

  • Product flavors give each environment its own application id and name, installable side by side.
    • 

  • Release builds are signed with a key whose password comes from the environment, never from a file.
    • 

  • A release script checks the state before building, and refuses clearly.
    • 

  • CI runs a script from the repository on every push; the same script runs on your machine.
    • 




Quick check answers: 1. So that a build made without a configuration file, by a new team member or a forgotten flag, talks to the development server and shows the DEV ribbon, never to production by accident. 2. Each flavor has a different application id (com.example.bit_app.dev and com.example.bit_app), and Android treats different ids as different apps, with their own data and icons. 3. From the environment variable STORE_PASSWORD: on your machine you set it in the shell for the build; on CI it comes from the CI system’s secret store, for the length of the job.
