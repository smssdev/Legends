Accessibility on Mobile

In this chapter you will learn to

  • read your app the way a screen reader does, through Flutter’s semantics tree
  • name every control, merge what belongs together, and hide what is decoration
  • turn Flutter’s accessibility guidelines into tests, and know what they cannot see
  • make the reading order of an Arabic screen run right to left, not only its layout
  • survive text at twice its size, and announce changes that cannot be seen

About one person in six lives with some disability, and almost everyone has a bad day: a cracked screen, bright sun, a broken arm, a phone held in one hand on a crowded bus. People use screen readers (TalkBack on Android, VoiceOver on iOS), larger text, a keyboard or a single switch, and higher contrast. An accessible app is not a separate app for them. It is the same app, built so that what the screen shows is also available as names, roles and actions.

Two results in this chapter surprised the author, and both are kept: a guideline that passed a grey that fails, and an Arabic screen that looked right to left but was read left to right. Sections {{n}}.3 and {{n}}.4 show the tests that found them.

{{n}}.1 The semantics tree

Flutter draws every pixel itself, so the operating system cannot look inside the picture to find buttons and text. Next to the widget tree and the render tree, Flutter builds a third tree, the semantics tree: nodes with a label (“Add Latte”), a role (button, heading, text field), a state (selected, checked) and actions (tap, scroll). The platform hands this tree to TalkBack or VoiceOver; on the web, Flutter turns it into HTML elements with ARIA roles that the browser’s accessibility tree reads.

Most widgets fill the tree well by themselves: Text gives its words, ElevatedButton says it is a button, TextField gives its label. The trouble starts with what we build ourselves from GestureDetectors, icons and containers.

{{n}}.3 Guidelines as tests



Flutter’s test package includes accessibility guidelines that check a pumped screen: every tappable node has a label, every tap target is at least 48 × 48 (Android) or 44 × 44 (iOS), and text has enough contrast. A test runs all four on both menus:








The hurried menu fails three: its 20-pixel heart has no label, and it is too small to hit reliably. The careful menu passes all four. But look at the last line of the hurried menu: text contrast passes, for a description drawn in a light grey that is plainly hard to read. Checked on its own, the same grey fails clearly:






Why did it pass in the menu? The contrast guideline looks for each semantics node’s label among the Text widgets on screen, and measures that text. In the menu, Flutter had combined each row’s name, description and price into one node, so its label was all three lines together, no single Text matched it, and nothing was measured. The guideline did not lie; it checked nothing and reported no failure.



Watch out
A passing accessibility guideline means “no problem found”, not “no problem”. Use the guidelines to catch missing labels and small targets, which they do reliably, and check colour contrast where it can be computed for certain: on the design tokens themselves, as the contrast test of Chapter 7 does for every pair of the theme. The careful menu’s description uses onSurfaceVariant on the surface, a pair Material’s colour scheme is built to keep readable, and one a token test like Chapter 7’s can check for every theme.



{{n}}.4 Reading order, right to left



A screen reader moves through the semantics tree in its traversal order: top to bottom, and within a line, in the reading direction. In an Arabic app, the drink’s name is on the right and its buttons on the left, so the name should be read first. A test prints the first row as a screen reader would visit it, for the careful menu set up two ways:








With only a Directionality widget, the screen looks right to left, but it is read left to right: “Add Latte” before the user has heard what Latte is. The direction of the semantics tree comes from higher up, from the app’s locale. With the Arabic locale and its localizations, both the layout and the reading order run right to left. The Arabic edition of this chapter’s apps uses that setup, the same one Chapter 13 of Book 5 used.

{{n}}.5 Large text



Both Android and iOS let people make text larger, up to twice its size and more, and Flutter honours it through MediaQuery.textScalerOf. Layouts written for the default size break: rows run out of width, fixed heights cut words in half. The book’s demo apps take a text scale so that a test and a screenshot can try 200%:













Two changes made the careful menu fit. The total bar is a Wrap with no fixed height, so the button moves to a second line when the line is full:






And the price moved from beside the name to under it. The first careful version kept it beside the name; in English it fitted, but in Arabic, whose words are wider at this size, the test reported “A RenderFlex overflowed by 6.5 pixels on the right”. Test large text in every language you ship.



Professional habit
Once per feature, use it as your users would: with TalkBack or VoiceOver on and your eyes closed, with the largest text size, and with a keyboard only. Ten minutes finds what no guideline can: a screen that makes sense to the eye but not to the ear, a button that can be reached but not understood, an order that only works with a finger.

Summary



    

  • Flutter builds a semantics tree of labels, roles, states and actions; screen readers and the browser read it.
    • 

  • Name every control (tooltip, labels), merge what is one idea, hide what is decoration.
    • 

  • The accessibility guidelines catch missing labels and small targets; contrast is checked for certain on the tokens.
    • 

  • Right-to-left reading order comes from the locale, not from a Directionality widget.
    • 

  • Test at 200% text in every language, and let layouts wrap instead of fixing sizes.
    • 




Quick check answers: 1. It combines its whole subtree into one semantics node, read in one go, like a menu item’s photo, name and price. Do not use it around things that are separate actions, such as two buttons: merged, they would become one node and the user could not reach them separately. 2. Because the guideline measures the Text widget whose words match a node’s label, and Flutter had merged each row’s texts into one node whose label matched no single Text; nothing was measured, so nothing failed. 3. The app’s locale: with the Arabic locale and its localizations, the semantics tree reads right to left. A Directionality widget alone mirrors the layout but leaves the reading order left to right.
