Four attempts have three waits between them, with limits of 200, 400 and 800 milliseconds: at most 1.4 seconds of waiting, and usually about half of that, since full jitter picks a random value below each limit. The cap of 5 seconds is never reached with these numbers; it matters with more attempts. A Retry-After from the server replaces the computed wait, and can make it longer.
  2. get returns null: the client treats an empty successful body as “no content”, which is what 204 No Content and many DELETE answers send. It is not a BadResponse because nothing failed to parse. The repository that expected a list must decide what null means for it, an empty list or an error, and that decision belongs there, not in the client.
  3. Give requests an optional cancel token (an object with a cancelled flag, or a Future that completes on cancel), created by the screen and cancelled in dispose. The client checks it in two places: before each attempt, and after each wait, throwing Cancelled. Screens ignore Cancelled: nobody is there to see it. Without it, a person who left the screen still causes four requests and four waits.
  4. Wrap the client (an http.BaseClient like Project {{n}}.3) or log in _send: '$method $path -> $status in ${watch.elapsedMilliseconds} ms'. Never the Authorization header: logs are copied to crash reporters, support tickets and screenshots, and a token in a log lets anyone who reads it act as the person. Never the body: it holds personal data (names, addresses, messages), and collecting it in logs is both a privacy risk and, in many countries, against the law.
  5. Without jitter, the counts arrive in tall spikes: all one hundred clients at 0, at 200, at 600 and at 1400 milliseconds, and nothing in between, so the server that is just recovering meets a wall of requests at each spike and may fall over again. With full jitter the same requests spread across every bucket, a few per 100 milliseconds, and the recovering server sees a steady trickle. The total number of requests is the same; only their shape in time changes, and that shape decides whether the server recovers.
