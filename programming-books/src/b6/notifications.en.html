Push Notifications and Background Work

In this chapter you will learn to

  • explain how a push reaches a phone: tokens, FCM and APNs, and the three moments a message can arrive
  • treat messages as data that is checked, not trusted, and turn them into routes
  • keep Firebase behind an interface, so the app and its tests never depend on it
  • ask for permission at the right moment, and know what the plugins add to your app
  • write background work that the system can stop at any time, and test it

A café app is used for a minute, then closed. Its most useful moment comes later: “your latte is ready”. That moment belongs to the operating system, not to the app. The system decides whether a message is shown, when background work runs, and whether the app may run at all. This chapter builds the parts of that story an app controls, and is honest about the parts it does not.

This book’s machine has no phone and no Firebase project, so no real push is sent in this chapter. What runs here, runs for real: the messages, the routing, the permission flow and the background job are tested with fakes, and the Firebase, notification and WorkManager code is compiled into a real Android app, whose first build failed. Section {{n}}.5 shows why.

{{n}}.1 How a push arrives

A phone keeps one connection open to its platform’s push service: Firebase Cloud Messaging (FCM) on Android, the Apple Push Notification service (APNs) on iOS. When the app starts, it asks for a token, an address for this app on this phone, and sends it to your server. To notify the user, the server sends a message for that token to FCM (which also forwards to APNs for iOS apps that use it), and the service delivers it when the phone is reachable.

A message can carry a notification (a title and body that the system shows by itself when the app is not on screen) and data (key–value strings for the app). When it arrives, the app is in one of three situations, and each one reaches your code differently:

The app is…What the system doesWhat your code receives
On screen (foreground)Nothing visibleThe message, at once: show your own banner
In the backgroundShows the notification in the trayThe message, when the user taps it
Not runningShows the notification in the trayThe message that started the app, once, at launch

{{n}}.2 Messages are data

A push message is input from outside, like a form or an HTTP response: checked, never trusted. The app reads only the kinds it knows, and only with valid fields:






An order message without an order is ignored, and so is one whose id is a path: a message that sends the app to /orders/../admin is exactly what checking is for. Unknown types are ignored too, so an old version of the app is not confused by a kind of message added next year.

Watch out
Firebase.initializeApp() needs the project’s configuration: google-services.json on Android, GoogleService-Info.plist on iOS, or a firebase_options.dart generated by flutterfire configure. Those files identify your Firebase project; this book has none, so lib/main_firebase.dart is compiled but not run here. The server key that sends pushes is a different thing, and it never goes into the app.

{{n}}.5 Permission, and what the plugins bring



iOS has always asked the user before an app may show notifications, and asks once: an app that asks at its first launch, before the user knows why, is usually refused for good. Android asks too, since Android 13, through the POST_NOTIFICATIONS permission. So the café asks after the first order, when the reason is obvious, and explains it in its own card first:












The plugins, for their part, change the app more than their Dart code suggests. The first Android build of this chapter’s app, exactly as Flutter created it, failed:






The notifications plugin needs the Android 37 SDK to compile against, and core library desugaring, which lets code written for newer Java APIs run on older Android versions. Both are settings of the app’s Gradle build:










Then the finished APK can be asked what it will request on the phone. The app’s own manifests ask for one thing, INTERNET, and only in debug builds, for hot reload; every other line below was merged in from a plugin:






Together they cover showing notifications (POST_NOTIFICATIONS, VIBRATE), receiving FCM messages (c2dm.permission.RECEIVE), keeping the phone awake for a moment of work (WAKE_LOCK), and scheduling work again after the phone restarts (RECEIVE_BOOT_COMPLETED). Read this list before every release: it is what the store shows, what reviewers ask about, and what the privacy policy must explain.

{{n}}.6 Background work



Sometimes the app must check for itself, for example when a push was lost. Both platforms allow background work, on their terms. Android’s WorkManager runs periodic work at most every 15 minutes, only when its constraints (a network, say) are met, and delays it further to save battery. iOS runs background tasks when it decides the user will benefit, which may be rarely, or never for an app the user does not open. Either may stop the work at any moment.



So the work itself is plain Dart, quick, and safe to run twice:








Run twice, it notifies orders 41 and 42 once each: the second run finds them in seen. The plugin code only connects that function to the system:






The dispatcher runs in a fresh isolate, with none of the app’s state: no providers, no open database, no logged-in session in memory. It must build what it needs from storage, which is another reason to keep the job a function of its inputs.



Professional habit
Send few notifications, and only ones the user would thank you for. Every push competes with messages from friends; an app that sends promotions at night is muted, and a muted app cannot even say “your order is ready”. Make the kinds of messages visible in settings (Android notification channels do this for you), and let people turn off promotions without losing order updates.

Summary



    

  • A push goes from your server to FCM or APNs to the phone, addressed by a token; it arrives in the foreground, from a tap, or as the launch message.
    • 

  • Messages are data: parse them, check them, ignore what you do not know.
    • 

  • Firebase stays behind a small interface; tests and demos use a fake.
    • 

  • Ask for permission when the reason is clear; know the permissions the plugins add.
    • 

  • Background work runs when the system allows, may be stopped at any time, and must be safe to repeat.
    • 




Quick check answers: 1. When the app is in the foreground; the app should show its own banner (here a SnackBar with a “View” action) so that the user still learns about the message. 2. Because message data comes from outside and is not trusted: the id becomes part of a route, and an id like ../admin could send the app somewhere it should not go. A number is all an order id can be. 3. Because the system asks only once (on iOS, and in practice on Android too), and a user who does not yet know why the app wants to notify them usually refuses; after the first order, “know when it is ready” is an obvious reason.
