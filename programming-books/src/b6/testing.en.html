Testing: Unit, Widget, Golden and Integration

In this chapter you will learn to

  • choose the right kind of test: unit, widget, golden or integration, and how many of each
  • make code testable by passing in what it depends on: a repository, an HTTP client, a clock
  • replace the network with fakes that behave like the real thing, under the test’s control
  • protect the look of a widget with golden images, and read a golden failure
  • run the real app end to end with integration_test, and measure coverage

Every chapter of this book has proved its claims with tests. This one is about the tests themselves: which kinds exist, what each one is good at, and how to write code that is easy to test in the first place. The app is small, a menu that may fail to load and an order with a happy hour, but it has the parts of every real app: logic, a server, a screen, and a look that should not change by accident.

The integration test in this chapter found a real bug on its first run, one that the screenshots of the same app did not show. Section {{n}}.6 tells the story.

{{n}}.1 Four kinds of test

KindWhat it runsSpeedGood for
UnitA function or a class, in plain DartMillisecondsRules: prices, dates, parsing
WidgetWidgets in a test environment, without a deviceTens of millisecondsScreens: states, taps, text
GoldenA widget, compared pixel by pixel with an approved imageTens of millisecondsThe look of components
IntegrationThe real app, built and launched on a deviceSeconds to minutesWhole journeys, platform code

A healthy suite is shaped like a pyramid: many unit tests, a good number of widget tests, a few goldens for the components that matter, and a handful of integration tests for the journeys that pay the bills. Each kind catches what the cheaper ones cannot, and costs more to run and to keep.

This is the whole secret of testable code: pass in what you depend on. A function that reads the clock, the network or a file by itself can only be tested by controlling the clock, the network or the file. A function that is given them can be tested with anything.



{{n}}.3 Fakes at the edge



The screen needs a menu. It should not care where the menu comes from, so it depends on a small interface, and the real implementation talks HTTP:






The API class is tested with a fake HTTP client. package:http ships one, MockClient: it receives each request, so the test can check it, and returns whatever response the test chooses:








Two words are often mixed up. A fake is a working implementation that takes a shortcut: an in-memory repository, a client that answers from a function. A mock is an object that records calls so the test can verify them, usually made with a package such as mocktail. Fakes test behaviour (“the screen shows the menu”), mocks test interaction (“the screen called menu() once”). Prefer fakes; reach for a mock when the interaction itself is the point, and even then a fake with a counter often does the job, as Project {{n}}.2 shows.



{{n}}.4 Widget tests



The screen takes its repository and its clock as parameters, for the same reason as total:






The test gives it a fake whose menu arrives only when the test says so, through a Completer. That makes the loading state testable: it lasts exactly as long as the test wants.








The second test taps two lattes and a cake and expects 145 EGP. Its clock says 10:00, so happy hour never makes the test pass in the morning and fail in the afternoon. A test that depends on when it runs is the most common kind of flaky test: green on your machine, red in CI at 15:05.










{{n}}.5 Golden tests



A widget test checks what a screen says. A golden test checks how it looks: it draws a widget, and compares the pixels with an approved image, the golden, kept in the repository.






The first time, there is no golden to compare with, so you create it, look at it, and commit it:








Then a teammate changes the theme’s seed colour from brown to teal, for an unrelated screen, and the golden test fails:








Two things in those pictures surprise everyone the first time. The text is drawn as boxes: Flutter tests use a test font in which every letter is a square, so that goldens are identical on every machine, whatever fonts it has installed. And the icons are squares too, for the same reason. Goldens protect layout, colour and spacing; the words are checked by widget tests.



Watch out
Goldens are sensitive to everything that draws: the Flutter version, the operating system’s image libraries, even the GPU on some setups. Generate and compare them in one place, usually the CI machine, and update them with --update-goldens only after looking at the difference. A golden updated without looking protects nothing.

{{n}}.6 Integration tests



Everything so far ran in a test environment: no real window, no real engine, no platform. An integration test builds the real app and runs it on a device, here a Linux desktop, the device this book’s machine has, on a virtual screen. The same test runs unchanged on an Android emulator or a phone with -d and the device’s id.








The package is part of the Flutter SDK, added as a development dependency:






On its first run, this test failed. The “Try again” button was written as onPressed: () => setState(() => drinks = widget.repository.menu()). The inner arrow returns the value of the assignment, a Future, and setState asserts that its callback returns nothing, because an async callback would update the state too late. The integration test runs a debug build, where assertions are on, and stopped with “setState() callback argument returned a Future”. The screenshots of the same app came from a release build, where assertions are removed, so the button seemed to work there. The fix is a block body: setState(() { drinks = widget.repository.menu(); }).



That is the value of running the real thing: it found a mistake in a path no widget test had walked yet.



{{n}}.7 Coverage



flutter test --coverage records which lines the tests ran, in coverage/lcov.info. A short script in the project, tool/coverage.dart, prints it per file:






Read coverage as a map of what no test has touched, not as a score. The missing lines here are MenuException.toString and the error branch of the screen, with its “Try again” button: exactly the path where section {{n}}.6 found its bug. (Project {{n}}.2 covers it; this run did not include it.) And notice what is not in the list at all: the demo repository. A file that no test imports does not appear in the report, so it cannot even lower the percentage. 100% coverage does not mean the code is right; 40% means that most of it has never run in a test at all.



Professional habit
When a bug is reported, write the test that shows it before fixing it, and watch it fail. Then fix the code and watch it pass. The test proves you understood the bug, proves the fix, and guards against its return, and over the years such tests become the most valuable part of the suite: each one stands for something that really went wrong.

Summary



    

  • Unit tests for rules, widget tests for screens, goldens for looks, integration tests for journeys, in that proportion.
    • 

  • Code is testable when it is given what it depends on: a repository, an HTTP client, a clock.
    • 

  • Fakes behave like the real thing without the network; a Completer controls when they answer.
    • 

  • Goldens compare pixels with an approved image; text is drawn as boxes so that they match everywhere.
    • 

  • Integration tests run the real app on a device, with assertions on, and find what the others cannot.
    • 

  • Coverage shows what has never run in a test; it is a map, not a score.
    • 




Quick check answers: 1. So that a test can choose the time: a function that called DateTime.now() itself would give different answers depending on when the test ran, and happy hour could only be tested between 15:00 and 17:00. 2. A fake is a simpler working implementation (an in-memory repository, a client that answers from a function); a mock records the calls made to it so the test can verify them. Fakes test behaviour, mocks test interaction. 3. Flutter tests draw text with a test font in which every letter is a box, so that goldens are identical on every machine regardless of the fonts installed; the words themselves are checked by widget tests.
