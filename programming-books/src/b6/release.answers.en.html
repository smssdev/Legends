  2. Because the flavor sets versionNameSuffix = "-staging", which Gradle appends to the version name from pubspec.yaml (0.1.0). It shows in Settings and in crash reports, so nobody mistakes a staging build for a release.
  3. Put each flavor’s icons in its own source set, android/app/src/dev/res/mipmap-* and android/app/src/staging/res/mipmap-*, with the same file names as in src/main/res. Gradle merges the source sets and the flavor’s resources win over main’s; the prod flavor uses main’s icons. flutter_launcher_icons can generate them per flavor from a configuration file for each one.
  4. Add a second job, or a workflow, with on: push: tags: ['v*'], that runs tool/release.sh. The CI system must hold the keystore (base64-encoded) and its password as encrypted secrets; the job decodes the keystore to a temporary file, writes key.properties pointing to it, sets STORE_PASSWORD from the secret for that step only, and uses the run number as the build number. Nothing is committed, and everything disappears with the machine.
  5. Cache the pub and Gradle downloads between runs; run the analyzer and tests, which take a minute, on every pull request, and build the Android app only on the main branch and on tags (or only when android/ or the dependencies change); and split the work into parallel jobs (checks, web build, Android build) so the total time is the longest job, not the sum. None of these checks less: the Android build still runs before every release.
