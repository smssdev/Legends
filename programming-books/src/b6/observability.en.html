Chapter {{n}}

Crash Reporting and Analytics

In this chapter you will learn to

  • catch every error an app can raise, from build methods to forgotten futures
  • send useful crash reports: what, where, which version, and what came before, without user data
  • show people a calm screen instead of a broken one
  • turn an obfuscated release stack trace back into file names and line numbers
  • collect analytics only with consent, in batches, and measure crash-free sessions

Before the release, you see every error in your terminal. After it, errors happen on thousands of phones you will never hold, and the only report you get, unless you build one, is a one-star review that says “it crashes”. This chapter builds the reporting itself, without an outside service, so that every part is visible. Services such as Sentry and Firebase Crashlytics do the same things at scale, and the ideas carry over unchanged.

Two things in this chapter went wrong the first time, and both are kept: the friendly error screen came out in red, underlined text, and Flutter’s own symbolizer could not read a Linux crash that a newer tool decoded at once. Sections {{n}}.2 and {{n}}.4 show both.

{{n}}.1 Every error, in one place

Errors reach a Flutter app by two doors. Errors in building, laying out and painting widgets go to FlutterError.onError. Everything else that nobody caught, in a Future, a timer, or platform code, goes to PlatformDispatcher.instance.onError. A small class sends both to one method:




A test raises one error through each door, after recording two steps the user took:






A build error is non-fatal: Flutter replaces the broken widget and the app goes on. An uncaught error in async code has left something unfinished, so it is reported as fatal. The breadcrumbs, the last few things the user did, travel with every report; they are often the quickest way from “a StateError in the specials page” to “it happens when the specials list is empty”.



{{n}}.2 A calm screen instead of a broken one



In debug builds, a broken widget shows the famous red screen. In release builds, it shows a grey box, which looks like the app froze. ErrorWidget.builder replaces it with something a customer can understand:













Watch out
The first version of this screen drew its second line in large red letters with two yellow underlines. That is Flutter’s style for text with no Material above it, and an error widget has none: it replaces the entire broken page, Scaffold included. Wrapping it in its own Material fixed it. Test your error screen in a release build, the only place customers see it.



{{n}}.3 Sending a report



A report is a small JSON document. It says what happened and where, the app version and platform, and the breadcrumbs, and nothing about the person: no name, no email, no order contents. The error message itself can contain user data, so in a real app it goes through the redactor of Chapter 14 first.






A test starts a real HTTP server, causes a real error, records it, and prints what the server received:






In production, the server stores reports, groups them by error type and top stack frame, and counts how many users each group affects, which is what tells you which crash to fix first.

Professional habit
Keep the symbols of every release you ship, labelled with its version and build id, for as long as that version is in use. A crash report from an old version without its symbols is a list of numbers forever. Crash services take care of this when you upload the symbols as part of the release script.

{{n}}.5 Analytics, with consent



Crash reports tell you what broke; analytics tell you what people do: which screens they open, where they give up, which features nobody finds. They are also the part of an app most likely to break the trust of the people using it. Three rules keep them honest: ask before collecting anything, collect events and not people, and send them in batches so that measuring does not cost the user battery and data. The projects build all three, and use the reports to measure the number that matters most after a release: the share of sessions without a crash.

Summary



    

  • Two handlers catch everything: FlutterError.onError for widget errors, PlatformDispatcher.instance.onError for the rest.
    • 

  • Reports carry the error, the version, the platform and breadcrumbs, never user data.
    • 

  • A custom ErrorWidget.builder replaces the release grey box with a calm screen.
    • 

  • Obfuscated traces are translated with the symbols kept from the build.
    • 

  • Analytics wait for consent, travel in batches, and the crash-free rate per version decides when a release is healthy.
    •

Because the error widget replaces the whole broken page, so there was no Material above its text to give it a style, and Flutter draws unstyled text in red with yellow underlines to make the mistake visible. 3. The symbols file saved by --split-debug-info for that exact build (matched by its build id), and a tool to translate the addresses: flutter symbolize or the native_stack_traces decoder.

Hint: 95% sounds good and is not: one session in twenty ends in a crash. Teams commonly aim for 99.5% or better, and stop a staged rollout when a new version falls clearly below the previous one. Look at sessions, not users: one unlucky user with many crashes and many happy users can hide each other in a per-user number.
