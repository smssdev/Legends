Chapter {{n}}

Security on the Device

In this chapter you will learn to

  • think like an attacker who holds your app, and sometimes the phone
  • see where an app’s data really ends up, and read it back as an attacker would
  • keep tokens in the platform’s secure storage, short-lived ones only in memory
  • accept that nothing compiled into an app is secret, and design for it
  • pin the server’s certificate, rotate pins safely, and keep secrets out of logs

A server sits in a locked room. An app sits in a stranger’s pocket. Anyone can download it, unpack it, read its strings, run it on a rooted phone and watch every file it writes. Security on the device starts by accepting that, and then deciding what the app may keep, where, and for how long.

Every attack in this chapter was carried out on the book’s own apps: a token read from a file, a “secure” value decrypted, a secret pulled out of an obfuscated release build. One of them failed the first time, for an interesting reason. Section {{n}}.3 tells it.

{{n}}.1 The attacker holds the app

Three kinds of attacker matter for a café app. The curious user unpacks the app to see how it works, or to find a discount code. The thief has the phone, perhaps unlocked, perhaps with a debugging tool. The network, at a café’s free Wi-Fi, watches or changes traffic. From these follow four rules:

  • Everything in the app is public: code, strings, assets, keys.
  • Files the app writes can be read, on a rooted phone, a backup or a shared computer, unless the platform encrypts them with keys the app does not hold.
  • Traffic is only as safe as the app’s idea of whom to trust.
  • The server decides. A check in the app is a convenience for honest users, never a protection.

On the web, the book’s screenshot tool signed in, then read the browser’s localStorage, as any script on the page, or anyone at the computer, can:












The access token is in plain text. The refresh token is encrypted with AES-GCM, but look at the last line: the key is stored right beside it, because a web page has nowhere else to put one. A dozen lines of Python, an attacker’s tool, read both:








That is not a bug in the plugin; it is the web. A browser gives a page no hardware-backed key store that survives a reload. On the web, the safest session is a cookie the page cannot read at all (HttpOnly), set by your server.

Watch out
The first version of this app only displayed the key’s length, and grep found nothing in the web build:




That was not protection. The compiler saw that only the length, 23, was ever used, and kept the number instead of the string. The moment the app uses the key, to call the maps service, the key is in the build. Never mistake “I could not find it” for “it is not there”.



So: a key that must stay secret belongs on your server, which calls the service on the app’s behalf. Keys that are meant to be public (a maps key restricted to your app’s package name, a payment provider’s publishable key) may ship, as long as the provider lets you restrict what they can do.



{{n}}.4 Tokens on the phone



On Android and iOS, flutter_secure_storage is a different thing from the web: values are encrypted with keys kept by the operating system, in the iOS Keychain or the Android Keystore, often in dedicated hardware, and those keys cannot be copied out of the phone. A copied file or a backup is useless without them. The café keeps the long-lived refresh token there, and the short-lived access token only in memory:






An access token that leaks is useful for minutes; a refresh token is guarded by the platform; signing out deletes both. Project {{n}}.2 tests that, with a fake store and a fake clock. (This book’s machine has no phone, so the Keychain and Keystore themselves are not exercised here; the plugin is compiled into the Android build above.)

{{n}}.5 Trust on the wire



HTTPS encrypts traffic and checks that the server’s certificate was issued by an authority the phone trusts. On a phone where the user (or an attacker, or a company) has installed an extra authority, a proxy can present its own certificate and read everything. Certificate pinning narrows the trust: the app accepts only the certificate it expects, whatever authorities the phone has.






To test it for real, a script makes throwaway certificates for localhost on every run (they are never committed), and the test starts real HTTPS servers with them:










The pinned client talks to its server and refuses the other one, although both are equally valid HTTPS servers. The ordinary client refuses the pinned server too, because its certificate is self-signed: that row shows the normal check at work.



Professional habit
Pin only with a plan for renewal. Certificates expire; a pin that is not updated in time turns into an app that cannot reach its own server, for every user, until they update. Ship the next certificate’s pin before you need it (Project {{n}}.3), pin a key you control rather than a provider’s rotating certificate, and keep a way to turn pinning off from the server for emergencies.

Summary



    

  • The attacker holds the app and sometimes the phone; the server is the only place a rule is enforced.
    • 

  • Files and localStorage are readable; on the web, even “secure” storage keeps its key beside the value.
    • 

  • Anything compiled into the app, obfuscated or not, can be extracted.
    • 

  • On phones, keep refresh tokens in the Keychain or Keystore and access tokens in memory; sign-out deletes both.
    • 

  • Pin certificates to narrow trust, with the next pin shipped in advance; keep secrets out of logs.
    • 




Quick check answers: 1. Because the encryption key is stored in the same localStorage, next to the encrypted value: whoever can read one can read the other, and decrypt. 2. No: obfuscation renames symbols, and the key stays a plain string in libapp.so, found with strings. 3. So that it is never written anywhere: it disappears when the app closes, and if it leaks while the app runs, it expires within minutes.
