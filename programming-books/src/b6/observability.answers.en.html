1. A NavigatorObserver: give MaterialApp (or the router) an observer whose didPush, didPop and didReplace add route.settings.name to the breadcrumbs. With go_router, pass it in the router’s observers, and name your routes so the breadcrumbs read as words, not as anonymous routes.
  2. One line is usually the framework method that threw (List.first), which says nothing about your code; the useful frames are a few lines below. The whole stack of a Flutter error can be a hundred framework frames, most of them identical between reports, which costs data and storage for nothing. Eight lines usually reach the app’s own frames; a crash service keeps the whole stack because it stores it compactly and groups by it.
  3. Write the report to a file before anything else, synchronously if the error is fatal, and send queued files on the next launch, deleting each one when the server accepts it. The sending is the same ReportSink, reading from a small queue on disk, as the offline outbox of Chapter 6.
  4. By the error type and the top frames of the stack that belong to the app (here Order.fromJson, total), not by the message. Messages contain data that changes between occurrences; the place in the code does not. That grouping is also why reports keep the stack in a stable form.
  5. One event per step of the funnel, with the same names on every platform: menu_opened, item_added (with the item’s category and the cart size, not the customer), checkout_started, payment_failed (with the error code), order_placed (with the number of items and a price bucket). The drop between two steps shows where people give up. Avoid anything that identifies a person: names, emails, phone numbers, exact addresses or locations, free-text notes, and order or payment ids that can be joined with other data.
