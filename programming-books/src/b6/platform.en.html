Platform Channels and Native Code

In this chapter you will learn to

  • explain how Dart and the platform talk: channels, codecs and the platform thread
  • write a method channel by hand, on both sides, and handle every way it can fail
  • replace hand-written channels with Pigeon, which generates typed code for every platform
  • stream values from native code with an event channel
  • test the Dart side with mocks, and the native side on a real platform

Flutter draws everything itself, but it cannot read the battery, open the camera or talk to a payment terminal by itself. Those belong to the platform: Kotlin and Java on Android, Swift and Objective-C on iOS, C and C++ on Linux. Every plugin you have used so far crosses that border through a platform channel. This chapter crosses it with our own code.

The native code in this chapter really runs: this book’s machine builds and runs Flutter apps on Linux, so the C++ side is compiled, run and tested there, and the Kotlin side is compiled into a real Android app. Swift needs a Mac; it is generated here but not compiled.

{{n}}.1 How a channel works

A channel is a name, both sides agree on it, and a codec that turns values into bytes and back. Dart sends a message on the channel; the engine hands the bytes to the platform side registered under the same name; that side answers, and the answer comes back to Dart as a Future. The standard codec carries null, booleans, numbers, strings, byte arrays, lists and maps of those: a small, common language that Kotlin, Swift and C all understand.

Three kinds of channel cover everything:

  • a MethodChannel for calls: a method name and arguments, a result or an error;
  • an EventChannel for streams: native code sends values for as long as Dart listens;
  • a BasicMessageChannel for plain messages, which is what Pigeon builds on.

On the native side, handlers run on the platform’s main thread, the same thread that draws the platform’s own windows. A handler that blocks that thread freezes the app.

Watch out
The first Arabic run of this app showed the kernel version as fc-v726-6.18.44. The string was right; its display was not: in a right-to-left line, the Unicode bidirectional algorithm moved the pieces around the hyphens. The first fix, textDirection: TextDirection.ltr on that Text, put the pieces in order but moved the whole line to the left edge, away from its label. The right tool is an isolate: wrapping the version in the characters U+2066 and U+2069 keeps the line right to left and reads only the version left to right. Use it for versions, codes, emails and file names inside any text that may be Arabic.

{{n}}.4 Threads and costs



A channel call is cheap but not free: the arguments are encoded, copied across, decoded, and the answer makes the same trip back. It is fine for a call per tap; it is wrong for sixty calls per second carrying images. For large data, pass a file path or a texture, not the bytes.



The native handler runs on the platform thread. Reading uname takes microseconds, but reading a large file, querying a database or calling a slow system service there freezes the app’s window. Do that work on a background thread (a GTask on Linux, a coroutine on Android, a dispatch queue on iOS) and answer when it finishes: the Dart side is already waiting on a Future, so nothing else has to change.



Professional habit
Before writing native code, look for a plugin; before writing a plugin, look again. When you do write native code, keep it thin: gather the data, translate it, answer. Every decision that can live in Dart should, where it is tested once for every platform, instead of three times in three languages.

Summary



    

  • Channels carry messages between Dart and the platform by name, through a codec; handlers run on the platform thread.
    • 

  • A method channel by hand needs matching names on both sides and care with every failure.
    • 

  • Pigeon generates typed Dart, Kotlin, Swift and GObject code from one definition.
    • 

  • Native errors travel as codes and arrive as PlatformException; no native side at all is MissingPluginException or channel-error.
    • 

  • Test the Dart side with mocks and fakes, and the native side with integration tests on the platform.
    • 




Quick check answers: 1. null, booleans, integers, doubles, strings, byte arrays (and typed lists of numbers), and lists and maps of those values; Pigeon adds its own classes on top of it. 2. A mismatch between the two sides, such as a field or method named differently in Dart and in Kotlin, which compiles everywhere and fails only at run time; with Pigeon both sides are generated from one definition and checked by each compiler. 3. The C++ handler returns cafe_device_api_battery_level_response_new_error("UNAVAILABLE", …); the generated code sends it as an error, and Dart’s batteryLevel() throws a PlatformException whose code is UNAVAILABLE.
