Chapter {{n}}

Performance: Jank, Memory and Startup

In this chapter you will learn to

  • think in frames: 16 milliseconds at 60 Hz, 8 at 120, and what happens when a frame is late
  • rebuild only what changed, and prove it by counting rebuilds in a test
  • decode images at the size they are shown, and measure the memory you save
  • start an app faster by running independent work together and showing something at once
  • keep heavy work off the main isolate, and keep repaints in their own layer

People rarely say an app is slow. They say it “feels cheap”, “stutters”, “heats my phone”, “takes forever to open”. Each of those has a cause that can be measured: a frame that took too long, a picture that filled the memory, a startup that waited for things one by one. This chapter measures each cause with a test that prints numbers, fixes it, and measures again.

The tests in this chapter count things: rebuilds, paints, bytes, frames. Counts are the same on every machine, so they make good tests. Milliseconds depend on the phone: section {{n}}.5 shows how to measure those on a real device, where they mean something.

{{n}}.1 The frame budget

A screen at 60 Hz shows a new picture every 16.7 milliseconds; at 120 Hz, every 8.3. For each picture, Flutter does its work in two places. On the UI thread, the main isolate where your Dart code runs, it builds widgets, lays them out and records what to paint. On the raster thread, the engine turns those records into pixels on the GPU. If either side misses the deadline, the screen shows the previous picture again, and the eye sees a stutter: jank.

Three rules follow from this:

  • Do less per frame. Every widget rebuilt, every row built, every layer painted costs time in the frame that needs it.
  • Do heavy work elsewhere. While your Dart code parses a large JSON on the UI thread, no frame can be built at all.
  • Measure in profile mode. Debug builds are many times slower than release builds, on purpose, to support hot reload and assertions. Never judge speed in debug; use flutter run --profile on a real phone.

{{n}}.2 Rebuild less

The order page has thirty drinks and a badge with the number of items. The first version keeps the number in the page’s state:




It looks harmless. But setState rebuilds the whole build method, and the rows are new objects each time, so each one is built again. Each row counts its builds, and a test taps the button once:








Thirty rows rebuilt to change one number. The fast version makes two changes:








    

  • The count is a ValueNotifier, and only a ValueListenableBuilder around the badge listens to it. The page itself never rebuilds. (A Riverpod provider watched only by the badge, as in Chapter 3, does the same.)
    • 

  • The rows live in their own widget, created with const. A const widget is the same object every time, and Flutter skips rebuilding a widget that has not changed.
    • 




Zero rows rebuilt. Thirty rows are nothing for a phone; but the same mistake at the top of a large screen, with images, charts and text, is how apps start to stutter. The habit is cheap: keep state as low in the tree as the widgets that use it, and make what does not depend on it const.



{{n}}.3 Images and memory



A phone camera takes photos of 4032 by 3024 pixels. The menu shows them at 56 by 56. The file is small because JPEG compresses well, but to draw it, Flutter must decode it into raw pixels, four bytes each, and those bytes stay in memory while the image is cached. A test decodes the menu’s photo both ways:








A file of a third of a megabyte becomes 46.5 MB of memory when decoded at full size: more than many phones will give an app for all its images. Decoded at the size it is shown, it takes 0.08 MB, almost six hundred times less. In a widget, cacheWidth does this, computed from the size on screen and the phone’s pixel density:












On this phone the density is 3, so 56 logical pixels are 168 real ones: the picture is as sharp as it can be on that screen, and no sharper. Too much memory does not show up as jank at first; it shows up as the app being killed in the background, or the phone getting hot and slow after a few minutes of scrolling.



Watch out
cacheWidth is in real pixels, not logical ones. Writing cacheWidth: 56 would decode a picture of 56 pixels and stretch it over 168: blurry on every modern phone. Always multiply by MediaQuery.devicePixelRatioOf(context).



{{n}}.4 Starting fast



An app is judged in its first second. A common main reads the settings, then opens the database, then fetches the menu, then shows something. The three steps here are stand-ins that wait as long as the real ones might:








One by one, the waits add up: 300 + 200 + 400, about 900 ms. The steps do not need each other, so Future.wait starts them together, and the app is ready when the slowest is: about 400 ms. And runApp is not kept waiting at all: a splash screen (or, better, the menu from the last visit, as in Chapter 6) appears on the first frame, and the real screen replaces it when the work is done.

{{n}}.5 Measuring on a real phone



Counts tell you that a change does less work. How long that work takes depends on the phone, so the milliseconds must be measured on one, ideally a mid-range Android phone a few years old, because that is the phone many of your users have:



    

  • flutter run --profile builds the app almost like a release, but keeps the hooks that tools need. Open DevTools from the link it prints.
    • 

  • The Performance page draws every frame as two bars, UI and raster, against the frame budget. Slow frames are red; selecting one shows which builds, layouts and paints filled it. Turn on “Track widget builds” to see the rebuilds of section {{n}}.2 by name.
    • 

  • The Memory page shows the app’s memory over time; scrolling the menu with full-size photos makes the line climb in steps of tens of megabytes.
    • 

  • flutter run --profile --trace-startup writes the time to the first frame into build/start_up_info.json.
    • 

  • showPerformanceOverlay: true on MaterialApp draws the two frame graphs on the phone’s screen itself, which is useful when testing in someone else’s hands.
    • 




Professional habit
Turn each performance fix into a test that counts, as this chapter does: rows rebuilt by a tap, rows created by a list, bytes per thumbnail. Counts never flake, so they can run on every pull request and catch the regression on the day it is written. Keep the millisecond measurements for the phone, before each release, with the same phone each time so that the numbers can be compared.

Summary



    

  • Each frame has 16 ms at 60 Hz, 8 at 120; work on the UI thread or the raster thread that misses it is jank.
    • 

  • Keep state low and the rest const: a tap that rebuilt 30 rows rebuilds none.
    • 

  • Decode images at their size on screen: 46.5 MB becomes 0.08 MB.
    • 

  • Run independent startup work together and show a first frame at once: 900 ms becomes 400.
    • 

  • Count work in tests; measure time in profile mode on a real phone, with DevTools.
    • 




Quick check answers: 1. setState runs the page’s whole build, which creates new row widgets, and Flutter rebuilds every widget that is a new object. A const widget is created once by the compiler and is the same object every time, so Flutter sees that it has not changed and skips it. 2. 4032 × 3024 × 4 bytes, about 46.5 MB, because a decoded image keeps four bytes (red, green, blue, alpha) for every pixel, whatever the size of the compressed file. 3. When none of them needs the result of another; a step that needs another’s result must wait for it, though it can still run alongside the steps that do not.

Hint: on the main isolate not a single tick fires: for 400 ms the app could not have drawn anything, animated anything or answered a tap. Hint: shouldRepaint: false is not enough, and that is the lesson.
