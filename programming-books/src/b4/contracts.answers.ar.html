  2. لأن كل خطأ يطلب رد فعل مختلفاً، والعميل لا يستطيع الرد الصحيح إلا على ما يعرفه. 409 تعني «اختر وقتاً آخر»: يجب أن تحتفظ الصفحة بالنموذج، وتشرح أن الموعد حُجز للتو، وتعرض غيره. و422 تعني «أصلح هذا الحقل»: يجب أن تعرض الصفحة الرسالة بجانب الحقل. والأخطاء الموثَّقة تأخذ أنواعاً أيضاً، فيقرأ العميل error.title بأمان، ويفحص اختبار العقد أن الخادم يرسلها بالشكل الموعود.
  3. يفشل التحقق، لأن المخطط يقول إن للكائن الحقول المسرودة بالضبط، فيصير اختبار العقد أحمر، وعلى المطوّر إما أن يحذف الحقل أو يضيفه إلى العقد. وهذا ما تريده عادة للإجابات أثناء التطوير: كل حقل يراه العملاء موثَّق ومراجَع، ولا يتسرب شيء داخلي (بصمة كلمة مرور، أو سعر التكلفة) بالصدفة. أما العملاء فيجب أن يتجاهلوا الحقول المجهولة، فتكون الإضافة الموثَّقة آمنة لهم.
  4. داخل الحلقة على oldOut.properties، قارن schema.type بـ newOut.properties?.[field]?.type وبلّغ عن "field" type changed: integer → string حين يوجد الاثنان ويختلفان (وافعل الشيء نفسه لحقول الطلب). وما زال يفوته: التغييرات في المعاملات (معامل استعلام جديد مطلوب، أو محذوف)؛ والصيغ والحدود والأطوال المتغيرة (maxLength تقلّص)؛ والكائنات والمصفوفات المتداخلة، لأنه لا ينظر إلا في المستوى الأعلى؛ وسلاسل $ref الأعمق من خطوة واحدة؛ وأنواع المحتوى وترويسات الإجابة المتغيرة؛ وحالات الخطأ المحذوفة. ولهذا تستعمل المشاريع الحقيقية أداة كاملة مثل oasdiff، وتُبقي اختبار العقد الفحصَ الأخير.
  5. function statusLabel(status: string) {
  switch (status) {
    case "confirmed":
      return t("status.confirmed");
    case "cancelled":
      return t("status.cancelled");
    default:
      reportUnknown("booking.status", status); // to the error tracker
      return status; // shown as it came, never a crash
  }
}
