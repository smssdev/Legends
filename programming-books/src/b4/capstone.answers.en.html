If reviews link to bookings, also make sure a salon cannot attach a review to another salon’s booking (a foreign key that includes salon_id, or a check in the insert).
  2. Counting by created_at measures the product’s use this month, which is what the plan sells, and it cannot be gamed by moving appointments. Counting by appointment date would let a free salon take a hundred bookings this month for next month, and then be blocked next month by bookings made long ago. But created_at is unfair to a salon whose customers all book at the start of the month for the whole month: it reaches the limit on the 2nd. Whichever you choose, write it in the plan’s description, show it in the usage screen, and keep it the same everywhere.
  3. Connected as the owner, the job bypasses RLS: one bug in a query (a missing condition, a join on the wrong key) can put salon A’s customers into salon B’s email, with nothing to stop it. Make it as safe as the API: run it as app_user, and loop over salons, opening one transaction per salon with withSalon, so each summary is computed under that salon’s policy. Add a test that a summary never contains another salon’s data, and send the emails from an outbox so a crash does not send them twice.

In order: (1) measure what is slow: the queries of that salon, the locks it holds, the share of connections it takes (Chapter {{n-4}}’s per-salon views); (2) fix the cheap things: an index for its access patterns, caching its public free slots (Chapter {{n-8}}), moving its reports to a read replica; (3) limit its share: a per-salon rate limit and a per-salon cap on connections, so one tenant cannot starve the others; (4) if it still dominates, move it to its own database or its own shard (a single-tenant deployment), which the salon_id on every row makes possible without changing the code that runs inside one salon. Each step is more expensive than the one before; take the next one only when the numbers show the previous one is not enough.
  5. The record: Context: the chain must keep its customers’ data in its own country by contract; we run one database in one region. Options: (a) a separate deployment of the whole product in that country for this chain; (b) a regional database for all salons of that country, with routing by salon; (c) decline. Decision, for example (a) at first, because it changes no code: the infrastructure code of Chapter {{n-5}} creates the same environment in another region, and the pipeline deploys the same image to both. Consequences: two environments to run, monitor and upgrade; migrations applied to both, in step; backups and the restore test kept in the country; support staff need access rules for that region; reports across all salons now need two sources. Revisit when a second customer needs the same country, which would favour (b). Price: the running cost of the second environment plus the time to operate it (for example, a fixed monthly fee several times Pro, with a minimum contract length), because the cost does not depend on the number of bookings.
