1. “Refunds of 10% if availability falls below 99.5% in a month” is an SLA: a promise to customers with a consequence, and looser than the internal objective. “The share of searches answered within 300 ms” is an SLI: a measurement, good events over all events, with no target. “99.9% of payments succeed over 28 days” is an SLO: a target for an SLI over a period.
  2. Into the time between the click and the moment the API received the request, and the time for the answer to travel back: opening the connection, and in a real browser also DNS, TLS, the network, and the browser’s own queue of requests. No server log can show it because the server only knows about a request once it has arrived; from its side, that time does not exist. A trace that starts in the browser measures it as the gap before the server’s span begins.
  3. It fires when the failure rate is above 14.4 times the budget rate, in both windows. For 99.9% the budget rate is 0.1%, so the page fires above 1.44% failures. For 99.5% the budget rate is 0.5%, so it fires above 7.2%. A stricter objective makes every rule more sensitive: with an objective stricter than customers need, small, harmless problems page people, the budget is always spent, and the team either ignores the alerts or stops releasing. Choose the objective customers actually notice, not the highest number that sounds good.
  4. The commander keeps the priority on mitigation: if a safe action exists that stops the harm now (roll back, switch off the feature flag), it happens now, while that engineer keeps investigating in parallel. Ten minutes of a SEV-1 is a lot of failed customers, “I think I see the bug” is a guess, and a fix written under pressure and deployed without review is a common way to make an incident worse. Once customers are fine, the fix goes through the normal pipeline. If no mitigation exists, the commander gives the ten minutes, with a clear time to check in and a second person watching.
  5. “A query on bookings without an index reached production; review and tests did not show its cost, because test tables are small.” Action: run the slow-query check of Book 3’s performance chapter against a copy of production-sized data in the pipeline, and alert on queries over 100 ms. “A migration ran against production from a laptop, because production credentials were available there and the command looked the same for every environment.” Action: only the pipeline can reach the production database; remove production credentials from laptops, and make the target environment visible in the prompt. “The disk filled up without warning, because there was no alert on disk usage and the log volume had grown with traffic.” Action: alert when a disk is 80% full and on the rate it fills, and rotate and limit the logs.
