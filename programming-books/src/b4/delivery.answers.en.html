1. Lint (10 s), type check (20 s), unit tests (40 s), integration tests (3 min), build the image (2 min). The fast, cheap checks come first, so most mistakes fail within a minute instead of after five; the image is built last because it is only worth building for a change that passed everything, and on a pull request it can be skipped entirely. Lint and type check can also run in parallel with the unit tests, since none depends on another.
  2. The gap between stopping the old process and the new one being able to answer: the new server’s start-up time (one second here, for opening connections and warming caches) plus the time to stop the old one and bind the port, while the load balancer kept sending requests to a port with nothing ready behind it. An application that needs 30 seconds to start (large frameworks, cache warming) would fail every request for 30 seconds on every deploy, which is exactly why the rolling update waits for readiness before sending any traffic.
  3. For each server in turn: (1) pull the image …:$SHA; (2) start a container from it on a free port; (3) poll its /ready until it answers 200, with a time limit, and abort the deploy (removing the new container) if it never does; (4) add it to the load balancer’s pool and check the load balancer reports it healthy; (5) remove the old container from the pool; (6) send the old container SIGTERM and wait for it to exit, with a time limit after which it is killed; (7) watch the error rate for a minute and stop the rollout if it rises. Each step checks its own result, so a failure stops the deploy with the old version still serving.
  4. During the rolling deploy the old version is still running and inserting rows without the new column: if the column is NOT NULL without a default, every insert from the old version fails, for as long as the deploy takes (and the migration itself may fail on existing rows). Split it: release 1 adds the column as nullable (or with a default) and deploys code that fills it; then backfill existing rows; release 2 adds the NOT NULL constraint once every running version fills it.
  5. You can simply redeploy the previous image when the migration was backward compatible, as in expand and contract: an added column, table or index that the old code ignores. The old code runs fine on the new schema, so rolling back the code is safe and the migration can stay. You cannot when the migration removed or changed something the old code needs: a dropped or renamed column, a changed type, a tightened constraint. Then you need a down-migration, which may lose data written since (rows in the new shape), or a forward fix. That is the strongest reason to make every migration additive, and to drop old columns only in a later release, once the code that used them is long gone.
