1. Public free slots: cache, up to 30 seconds (the booking itself is checked by the database). The owner’s list right after a cancellation: primary, for the few seconds after their write (read your own writes), then the replica, a second or two stale at most. A payment’s status before refunding it: primary, in the transaction that records the refund, never stale, because it decides a write involving money. The count of bookings this month on the dashboard: replica or a cache of a few minutes; nobody is harmed if it lags a little, and it can be expensive to compute.
  2. A DELETE works row by row: it finds each of the 521,279 rows, marks each as dead, writes each change to the write-ahead log (and so to every replica), and updates every index; the space is only reclaimed later by VACUUM. Dropping a partition removes whole files: the work is the same whatever the number of rows, a catalog change and a few file deletions, logged as one small record.
  3. Every cached answer is gone, so every read of free slots misses and goes to the database until the cache fills again, a stampede of misses that the database must absorb for a minute. That is acceptable if the database can serve the full read load on its own, which it must, because a cache can always be empty (restart, eviction, a new key). It would be worse if the system had been sized assuming the cache absorbs most reads: then the database is overloaded exactly while the cache refills, and slow queries delay the refill further. Never size the database on the cache’s hit rate; size it to survive without the cache, and use the cache for speed.
  4. The table is partitioned by month, and the query does not filter by time, so the planner cannot prune: it must search all 24 partitions, each with its own index, and combine the results. One table would need one index search. Options: add a time range to the query when the screen allows it (the owner usually wants the next weeks, not all time); keep an index on (staff_id, starts_at) in every partition so each search is short; or, for frequent “all time” questions, keep a small summary table maintained alongside the bookings.
  5. The report: each shard computes its own daily counts for the last 30 days (a small query, run in parallel on the four shards), and a coordinator adds the four results. Better, each shard writes its daily counts into a central analytics store every night, and the report reads only that store, never the shards. Moving a business: copy its rows to the new shard while it keeps running on the old one; keep copying the changes (logical replication filtered by business, or the outbox); when the new shard has caught up, block writes for that business for a few seconds, copy the last changes, switch the routing table that maps business id to shard, unblock; then delete the old rows after a safety period. The routing table must be the single source the application consults on every request.
