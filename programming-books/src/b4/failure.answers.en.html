Three in sequence then cost at most 900 ms, leaving 600 ms for the page’s own work and for one retry of one call. If a retry of every call must fit, the budget does not add up (3 × 2 × 300 = 1.8 s), which tells you to make the calls in parallel where they are independent, or to give the whole page an overall deadline that stops further retries when it runs out.
  2. Because failures are usually shared: when the provider has a hiccup, many clients fail at the same moment. With fixed delays they all retry together after exactly 100 ms, hit the provider at the same instant, and fail together again, in waves. A random wait spreads the retries over the whole interval, so the provider sees a smooth trickle it can handle, and most retries succeed.
  3. The first request reaches the provider and creates a charge, but the answer is slow and the client’s 500 ms deadline passes first. The client sees a timeout and retries; the provider receives a second, identical request and charges again. What prevents it is an idempotency key: the client generates one key per deposit (for example the payment row’s id) and sends it on every attempt; the provider recognises the second request as a repeat and returns the first result instead of charging again. The webhook handling of Chapter {{n-2}} is the same idea on the way back.
  4. With a threshold of 1, a single momentary failure (one timeout among thousands of successes) opens the breaker, and for the next 2 seconds every customer gets the fallback although the provider is healthy: the breaker causes outages. With a cool-down of 10 minutes, the breaker reacts well when the provider goes down, but after it recovers customers keep getting the fallback for up to 10 more minutes, because no trial call happens until then. Thresholds and cool-downs are tuned from the provider’s normal error rate and its typical recovery time, and watched on a dashboard.
  5. Every request now holds a database connection for 4 seconds instead of 4 ms, a thousand times longer, so the pool of each copy is used up almost at once. New requests queue for a connection, the copies’ memory and open requests grow, and their readiness checks (which also query the database) start failing; the load balancer may then remove every copy, turning a slow database into a complete outage. Customers first see very slow pages, then errors. Defences: a short query timeout (statement_timeout) and a timeout on waiting for a pool connection, so requests fail fast instead of piling up; a readiness check that does not mark every copy dead because a shared dependency is slow; a fallback for read pages (cached slot lists, marked as possibly stale); load shedding when the pool is exhausted; and, separately, finding why the database is slow (the next chapter).
