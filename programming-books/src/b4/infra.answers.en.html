1. The number of app copies: in the code, as a variable with a default per environment (it is configuration, reviewed like any change). The database password: a sensitive variable from the secret store, never in a file. The region: in the code (often a variable per environment); it is not secret and changing it is a major, reviewed decision. A customer’s email address: in neither; customer data lives in the database, never in infrastructure code or its state. The image tag of the release: a variable set by the pipeline at deploy time (the commit), not written in the files, so that a release does not need an infrastructure commit.
  2. Because a container’s environment variables are fixed when it is created; the only way to give a running container a new VERSION is to create a new one, so the provider marks the change as forcing replacement. If both copies were destroyed and recreated at the same moment, there would be a window with no copy able to serve: every request in that window fails, exactly like the naive deploy of Chapter {{n-1}}. Replacing one at a time, with the new one created and ready before the old one is removed, avoids it.
  3. Both read the same state, compute plans from it, and start changing resources: they may both create the same resource (two databases, or a name conflict that fails half way), or one may delete what the other just created. Then both write the state back, and the second write overwrites the first, so the state no longer records resources that exist: the next plan wants to create them again, or loses track of them until someone imports them by hand. Locking makes the second apply wait (or fail) until the first finishes.
  4. Stop: replacing the database container means destroying it and creating a new one, and if the data were not on a separate volume it would be gone. Before approving, confirm where the data lives (here, the named volume, which survives), take a backup and test that it restores, plan the downtime, and consider whether the upgrade should rather happen through the managed service’s own upgrade process. In the code, add lifecycle { prevent_destroy = true } to the database, so that any plan that would destroy it fails until someone removes that line on purpose, in a reviewed change.
  5. The infrastructure code covers the network, the platform for the application, the database server and its settings, storage buckets, the load balancer and the permissions between them. It does not cover the data (the database’s contents and the uploaded files), the secrets’ values, DNS records if they are managed elsewhere, or anything changed by hand. Recovery in order: (1) apply the code with the new region’s variables, creating an empty environment; (2) restore the database from the latest backup copied to another region, and the files from replicated storage; (3) load the secrets into the new environment’s secret store from their backup; (4) deploy the last released image; (5) run the smoke tests and the contract tests; (6) switch DNS to the new load balancer; (7) watch the metrics. Practise it, on a schedule, with a timer.
