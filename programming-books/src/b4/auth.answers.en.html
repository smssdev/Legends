1. See today’s bookings: owners and staff of that business; nobody gets 401, a user of another business sees only their own business’s list (never this one). Cancel a booking: owners of that business; nobody 401, staff 403, an owner of another business 404. Book a slot: anyone, without signing in (the customer); the database constraint and validation are the checks. Change a staff member’s name: owners of that business; nobody 401, staff 403, another business’s owner 404.
  2. localStorage is readable by every script that runs on the page, so a single cross-site scripting bug, or a compromised third-party script, can copy the token and use it from anywhere until it expires. Keep the token in an httpOnly, sameSite, secure cookie, which the browser sends on its own and no script can read; a mobile web app is just a website and uses the cookie too. Only native apps, which have no browser cookies, keep a bearer token, in the platform’s secure storage (Keychain, Keystore).
  3. curl -s localhost:3000/owner -H 'cookie: session=anything'. The proxy sees a cookie with the right name and lets the request through. The page then calls requireUser, which hashes anything, finds no session with that hash, and gets no user; the page redirects to the login page without reading any data. The proxy was never the check, so passing it gains nothing.

    The checks: signed in (401), owner only, since it exports personal data (403 for staff); scoped to the user’s business in the query; and beyond permissions, personal-data rules: export only customers who agreed to marketing (a column the spec must add first), log every export with who and when, and rate-limit it. The privacy policy must mention the export before it ships.
  5. Replace users.business_id and role with a membership table: memberships (user_id, business_id, role, PRIMARY KEY (user_id, business_id)). A request must now say which business it is for: in the web app the business is part of the address (/b/12/owner), in the API a path segment or header. requireUser(roles, businessId, request) looks up the session and then the membership for that business, and returns { user, businessId, role }; no membership means 404, a membership with the wrong role means 403. The queries keep filtering by a business id, now taken from that result rather than from the user row, so the rule “the condition is the permission” stays the same.
