A key chosen by the server, with the business id as prefix and a random UUID, is unique, unguessable and always inside the business’s own folder; the presigned URL is valid only for that key.
  3. The row still has sent_at empty, so the next run sends the email again: delivery is at least once, and the customer receives two. To make them receive one, give the email service an idempotency key, which many services accept (the outbox id is the natural one; our mailer already sends it as the X-Outbox-Id header), so the service drops the second send. Without such support, keep the window small: mark the row as sending with a time before sending, and only resend rows whose attempt is old. A rare duplicate remains possible, which is why at-least-once is the honest promise for email.
  4. At the deposit step, fetch fails or times out: today startDeposit throws, the customer sees an error, and the pending payment row stays behind with no checkout. Better: give the call a short timeout and a retry; if it still fails, keep the booking in awaiting_deposit, roll back or mark the payment failed, and show the customer “Payments are unavailable right now; your time is held for 30 minutes, try again from the link in your email”, with the outbox sending that link. Webhooks during the outage are not lost: the provider retries them when it is back, and the idempotent handler applies them once.
  5. Do not trust arrival order; decide by the state the event can apply to, and by the provider’s own time. Each update names the state it moves from: paid only from pending, refunded only from paid. If checkout.refunded arrives first, there is no paid payment to refund: store the event (it is already in webhook_events with its payload) as deferred rather than dropping it, and when checkout.paid is applied, look for deferred events for the same checkout and apply them in the order of the provider’s created time. The simpler alternative, which most providers recommend: on any event, fetch the checkout’s current state from the provider’s API and set the payment to match it, so the order of webhooks stops mattering.
