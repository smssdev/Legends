A 422 means “fix this field”: the page should show the message next to the field. Documented errors also get types, so the client reads error.title safely, and the contract test checks that the server sends them in the promised shape.
  3. The validation fails, because the schema says the object has exactly the listed fields, so the contract test turns red and the developer must either remove the field or add it to the contract. That is usually what you want for responses during development: every field clients can see is documented and reviewed, and nothing internal (a password hash, a cost price) leaks by accident. Clients, on the other hand, should ignore unknown fields, so that a documented addition is safe for them.

It still misses: changes to parameters (a new required query parameter, a removed one); changed formats, ranges and lengths (a maxLength that shrank); nested objects and arrays, since it looks only at the top level; $ref chains deeper than one step; changed content types and response headers; and removed error statuses. That is why real projects use a full tool such as oasdiff, and keep the contract test as the final check.
  5. function statusLabel(status: string) {
  switch (status) {
    case "confirmed":
      return t("status.confirmed");
    case "cancelled":
      return t("status.cancelled");
    default:
      reportUnknown("booking.status", status); // to the error tracker
      return status; // shown as it came, never a crash
  }
}
    The parameter is typed as string (or the generated union plus string), so a new value is expected rather than impossible. The page keeps working and shows the raw value, and the error tracker tells the team that the server started sending something the client does not know, so they can add the case in the next release. With every client written this way, adding an enum value becomes a safe change in practice, though the contract check should still flag it so someone decides consciously.
