1. Renaming a function in one module: easy to undo, local; the person doing the work decides, in a normal pull request. Moving all dates to UTC: hard to undo (stored data changes) and wide (every module, the API and the clients); a design doc, a review with a named approver, a decision record, and a careful migration. Adding a column to one module’s table: hard-ish to undo once data is in it, but local; a short review in the pull request, and a record only if it changes how the module models its data. Choosing a company error tracker: wide, and moderately hard to undo (every service is wired to it, and its history is lost on a switch); a short design doc with a matrix and a trial, an approver, and a record.

For example: “We chose PostgreSQL for jobs because a load test on production-sized hardware ran 200 jobs a second with the job query under 20 ms, and we run 9,000 jobs a day (at most 2 a second at peak). Revisit above 100 jobs a second or if the job query exceeds 50 ms.” The numbers and the condition make it checkable; “scales well enough” cannot be proved wrong.
  3. It is a disagreement of facts, because the cost can be calculated. Settle it by measuring instead of arguing: take this month’s real job count and peak rate, price them with the cloud provider’s calculator, and add what each option costs the team to run (hours per month for upgrades, backups and monitoring, at a known rate). Put the calculation in the design doc, so both people can check it. If they still disagree afterwards, it is usually because they value something differently (time of people against money), and that the approver decides.
  4. Today: fix the customer problem in the smallest way that respects the rule if at all possible (often it is a matter of exporting one function through index.ts). If it truly is not possible today, merge with an explicit, visible exception (an allow-list entry with the reason, a ticket number and the approver’s name), never by switching the check off. Next week: remove the exception through a proper change, and ask why the rule was in the way: if it is often in the way of real needs, the rule or the module boundary may be wrong, and that deserves a review and possibly a new decision record.
  5. Seam: one function, enqueue(job), through which all code creates jobs; first change every caller to use it, with the Redis queue behind it. Flag: a setting with the share of jobs that go to the PostgreSQL queue, by job type (start with receipts, the least risky). Compare: for two weeks write each job to both queues but let only one run it, and compare daily counts of created, run and failed jobs, and their delay; any difference is investigated before the next step. SLIs: jobs run within a minute of being due, jobs lost (created but never run), and the database’s query time. Roll back: at every step, set the flag back to 0% for that type; the Redis path still works. Then move 10%, 50%, 100% of each type, waiting a few days each time. Delete the old path only after a full week at 100% with no differences, and when the Redis queue is empty; then supersede the decision record and remove Redis’s job settings.
