Chapter {{n}}

Forms and Validation

In this chapter you will learn to

  • choose between controlled inputs and letting the form keep its values
  • describe the rules of your data once, in a Zod schema, and get the TypeScript type from it
  • build forms with React Hook Form that validate at the right moment
  • show errors that everyone can see and hear
  • handle errors that only the server can know, such as an email that is already taken
  • split a long form into steps without losing the user’s data

Forms are where users give your app something: their name, their address, their money. They are also where most frustration happens: rules that are not explained, errors that appear too early or too late, data that disappears after a mistake. Good forms are a large part of what makes an app feel professional. This chapter shows the approach most React teams use today: a schema that describes the data once, and a form library that connects it to the inputs.

Validation in the browser is for the user’s comfort: quick, friendly feedback. It is never security. Anyone can send anything to your server, so the server must check everything again. The nice part: with a schema, both sides can use the same rules.

{{n}}.1 Controlled and uncontrolled inputs

An input can keep its value in two places. A controlled input takes its value from React state, value={text}, and reports every change with onChange; React is the single source of truth. You used this for the task list and the search box. An uncontrolled input keeps its own value in the DOM, like a plain HTML form, and your code reads it when needed, for example on submit with new FormData(form).

Controlled inputs are simple and are right when the screen must react to every keystroke: a live search, a character counter. For big forms, re-rendering the whole form on every key becomes slow and verbose. Form libraries such as React Hook Form use uncontrolled inputs under the hood, and give you the convenience of controlled ones.

{{n}}.2 One schema for the rules

Zod lets you describe the shape and rules of data as a schema, an object you can both read and run. Each rule carries its own error message:




    

  • z.string().trim().min(3, …) removes spaces at the ends, then requires at least three characters.
    • 

  • z.email() checks the format of an email address.
    • 

  • z.coerce.number() turns the text from the input into a number first, because every input value is a string.
    • 

  • z.infer<typeof contactSchema> produces the TypeScript type. You never write the type by hand, so it can never disagree with the rules.
    • 




The schema is plain TypeScript, so the same file can run on the server. safeParse never throws: it returns either the clean data or a list of issues:








Notice what came out of the valid case: the name lost its extra spaces, and the age became the number 27. A schema both checks and cleans the data. This is the type guard of Chapter {{n-5}}, written for you.



{{n}}.3 React Hook Form

When to show errors



Showing “invalid email” after the first letter is rude: the user has not finished. Waiting until submit is late: the user fills ten fields and then finds five errors. mode: "onTouched" is a good compromise: a field is checked when the user leaves it for the first time, and after that on every change, so the error disappears the moment it is fixed.



Tip: help the browser help the user
The right type, inputMode and autoComplete cost nothing and save users a lot of typing: type="email" brings the @ key on phones, inputMode="numeric" the number pad, and autoComplete="name", "email", "street-address" or "new-password" let the browser fill in or suggest values. Email, password and phone inputs also get dir="ltr" in Arabic pages.

{{n}}.4 Errors only the server knows



Some rules cannot be checked in the browser: whether an email is already registered, whether a coupon is still valid, whether the item is still in stock. The server answers with an error, and the form must show it next to the right field, just like its own errors. React Hook Form’s setError("email", { message }) does exactly that, and shouldFocus moves the user there. Project {{n}}.2 builds a sign-up form with this pattern.



While the request is on its way, isSubmitting is true. Use it to disable the button and change its text, so impatient users do not send the form twice.



Watch out: never lose what the user typed
After a failed submit, keep every value in the form. The only exceptions are passwords and card numbers, which many sites clear for safety. Nothing makes users leave faster than typing a long message twice.



{{n}}.5 Forms in several steps



A long form, such as a checkout, is easier as a few short steps. The data should still be one form, so nothing is lost when the user goes back, and the rules should still be one schema. Each step lists the fields it is responsible for, and the “Next” button validates only those, with trigger(fields). Project {{n}}.3 builds this, and shows a subtle React bug that multi-step forms are famous for.



Professional habit: write the error messages with the design
Every rule needs a message that says what is wrong and how to fix it, in the user’s language: “Please enter an 11-digit Egyptian mobile number”, not “Invalid input”. Write them in the schema, review them like any other text in the product, and test the form by making every mistake on purpose.

Summary



    

  • Controlled inputs keep their value in state; uncontrolled inputs keep it in the DOM. Form libraries combine the speed of the second with the convenience of the first.
    • 

  • A Zod schema describes the rules and messages once; z.infer gives the type, and safeParse checks and cleans data anywhere, including the server.
    • 

  • React Hook Form connects the schema to inputs with register, and calls your submit function only with valid, typed data.
    • 

  • Show errors at the right moment (onTouched), next to the field, linked with aria-describedby, with a message that says how to fix it.
    • 

  • Put server errors on their fields with setError; disable the button while submitting; never lose the user’s input.
    • 

  • Split long forms into steps of one form and one schema, validating each step with trigger.
    • 




Quick check answers: 1. Because anyone can send any data to the server without using your form; browser validation is for comfort, not security. 2. The TypeScript type of the valid data, derived from the schema. 3. parse throws an error for invalid data; safeParse returns an object with success and either the data or the issues.




Practice projects



For each form, write the schema first, with every error message, and test it with safeParse in Node before you build any screen. When the rules are right, the form is mostly wiring.

    3. 

  3. Write a pretend createAccount that answers with { ok: false, field, message } for one particular email.

  4. In onSubmit, call it, and on failure call setError(result.field, { message }, { shouldFocus: true }).

Project {{n}}.3 · Challenge


A checkout in three steps


Delivery, payment and review as three steps of one form, validated step by step, with a review screen before the order is placed.


You will practise: composing schemas with extend, z.enum, trigger for partial validation, getValues, aria-current="step", and keys that force a new element.


    

  1. Write one schema per step and join them: delivery.extend(payment.shape). Keep a STEPS list with each step’s title and fields.
    2. 

  2. Show only the current step’s inputs. “Next” calls await trigger(fields) and moves on only if it returns true.
    3. 

  3. On the last step, show a summary from getValues() and a “Place order” submit button.
    4. 

  4. Show the progress as a list, with aria-current="step" on the current one, and a hidden “Step 2 of 3” for screen readers.
    5. 

  5. Give “Next” and “Place order” different keys. Without them, React reuses the same <button> and only changes its type, and the click on “Next” can finish as a submit of the new type, placing the order one step early. This book’s own screenshots caught that bug.
    6. 



Hint: because all steps are one form, “Back” is free: the values are still there. Never create a separate form per step unless the steps are saved separately on the server.
