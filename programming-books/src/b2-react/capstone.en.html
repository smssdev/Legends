Capstone: A Production Dashboard

In this chapter you will

  • turn a short brief into user stories and the quality goals a release must meet
  • organise a real codebase in layers, with one place that talks to the server
  • build five screens with routing, server data, URL state, an optimistic update and a validated form
  • support two languages, right to left, and a dark theme from the first line
  • prove the app works with unit tests, end-to-end tests and an accessibility audit
  • find out why the app was too big, and fix it until it fits the budget

Every chapter of this book taught one skill on a small example. Real work is different: all the skills are needed at once, they pull in different directions, and nobody tells you which chapter applies. In this last chapter we build one complete app, the admin dashboard of Bit’s shop, from a brief to a release. Every file is shown, every test is run, and every number is measured. When something goes wrong, as it will, you will see how it was found and fixed.

Read this chapter twice: once for the app, and once for the decisions. Each section says which chapter a decision comes from, so you can go back whenever something feels new.

{{n}}.1 The brief

The shop owner writes: “I want to see how the shop is doing, find orders and mark them as shipped, and fix product prices, from my laptop or my phone, in Arabic or English.” A brief like this is not yet something you can build. The first job is to turn it into user stories, each with a test for “done”:

As the owner, I want to…Done when…
see revenue, orders and what is waiting to shipThe overview shows four numbers and the last seven days of revenue
find an order by status or by customerThe list filters and pages, and a filtered list can be bookmarked
mark an order as shippedThe change shows at once, and is undone clearly if the server refuses
fix a product’s name, price and stockWrong values are explained under each field; the server’s own errors too
use it in Arabic or English, in light or darkEvery text is translated, the layout mirrors, and the choice is remembered

And the qualities that every story must also meet, which a team writes down before the first line of code:

  • Accessible: no violations in an automatic audit, and everything works with the keyboard (Chapter {{n-8}}).
  • Tested: the logic by unit tests, the main journeys by end-to-end tests (Chapter {{n-7}}).
  • Fast: the first load under 150 KB of compressed JavaScript (Chapter {{n-6}}).
  • Safe: every answer from the server is checked before use (Chapter {{n-5}}).

{{n}}.3 Talking to the server



First, what the server sends, as zod schemas. Each schema is also a TypeScript type, so the rest of the app never writes these shapes twice. Money is a whole number of piastres:






Then the client. It is the only file in the app that calls fetch. It parses every answer with its schema, so a server that changes a field breaks here, loudly, instead of in a random screen, and it turns failures into an ApiError that the screens can understand:






And the TanStack Query hooks that the screens use. Notice the keys: ["orders"] and ["orders", 1036] share a prefix, so invalidating keys.orders refreshes the list and every order. Changing a status is optimistic, as in Chapter {{n-12}}: the screen shows the new status before the server answers, and puts the old one back if it fails.






During development, and for this book’s screenshots and end-to-end tests, a small pretend server answers the same addresses with the same shapes. A test page puts it in place of fetch, and nothing else in the app knows. Real projects do the same with the library Mock Service Worker, which intercepts requests in the browser.






{{n}}.4 Two languages from the first line



Adding a second language to a finished app means finding every text in every file. Starting with two costs almost nothing. All texts live in one file, src/i18n/messages.ts, as an English object and an Arabic one typed Record<Key, string>: if a key is missing in Arabic, the build fails. Money, dates and weekdays come from Intl, which writes “EGP 250” in English and “‏٢٥٠ ج.م.‏” in Arabic without a single rule of ours (Chapter {{n-4}}):

{{n}}.5 The frame: routes and layout






A few details in this file come straight from earlier chapters. The layout sets lang, dir and the dark class on <html>, so the whole page mirrors and changes colour together; all colours are CSS variables, and the dark theme only redefines them (Chapter {{n-9}}). A “skip to content” link is the first thing a keyboard user reaches. The language button is marked with the language it switches to, so screen readers pronounce “English” and “العربية” correctly. And the two product routes are lazy: we will see why in section {{n}}.9.



{{n}}.6 The overview



The numbers on the overview are pure functions of the orders. Keeping them in lib/, away from React and fetch, means they can be tested in milliseconds, and the screens stay short:









The chart is plain HTML: a list of seven bars whose height is a percentage. Each bar carries its value as visually hidden text, so a screen reader reads “Tue: EGP 1,350” instead of nothing. A chart library would be heavier and, by default, silent.





{{n}}.7 The orders






The status, the search text and the page number are all in the address, as in Chapter {{n-12}}. The page reads them with readFilters, which also protects against nonsense such as ?page=-4 or ?status=lost. The status links are real links, so they can be opened in a new tab, and the current one is marked with aria-current, which both the CSS and screen readers understand. Typing in the search box uses replace, so the back button does not step back one letter at a time.





{{n}}.8 One order






The buttons offer every status except the current one, and are disabled while a change is on its way, so a double click cannot send two. The status sits in an aria-live region, so a screen reader announces the change. If the server refuses, the optimistic status is put back by useSetStatus, and an alert says so: the user is never left believing something that is not true.





{{n}}.9 The product editor



The form is React Hook Form with a zod schema, as in Chapter {{n-11}}, with two details that real forms need. The schema is built with the current language, so its messages are translated. And the inputs are text, so z.coerce.number turns them into numbers; .int() then refuses “85.5” instead of quietly saving it. The form takes the product and an onSave function, and knows nothing about the server, which makes it easy to test:

The size budget



The last quality goal was a first load under 150 KB of compressed JavaScript. This script bundles the app as production would, and checks:






The first time it ran, it failed. The story of how it was fixed is the most realistic part of this chapter, so here it is, with the numbers it printed each time:





StepFirst load (gzip)What we learned



First version221.7 KBThe script listed every package: zod alone was 444 KB before compression, more than React


import * as z from "zod"156.2 KBWe had written import { z } from "zod". That imports one object that holds all of zod, so the bundler cannot leave anything out. Importing the module itself lets it keep only what we use


Lazy product routes142.6 KBThe form library is only needed on the product pages. Loading them on demand takes it out of the first download









Two lessons here go far beyond this app. Measure before you optimise: nobody would have guessed that one import line cost a third of the app. And a budget only works if it runs automatically: in a real project this script runs in CI on every pull request, and a red check stops the next 70 KB from arriving unnoticed.



Professional habit: a release checklist
Before every release, a short list that anyone on the team can run: all checks green in CI; the main journeys clicked by hand in both languages and both themes, on a phone and with the keyboard; the size budget met; no errors in the browser console; and a plan to undo the release if something goes wrong. Five minutes of checking is cheaper than one evening of fixing in production.



{{n}}.11 What you built



Look back at the list of files in section {{n}}.2. In about 800 lines of TypeScript, not counting the tests, there is a typed, validated data layer with caching and optimistic updates; five screens with URL state, loading and error states; a validated form that merges the server’s errors; two languages with mirrored layout and real number and date formats; a dark theme; and tests, an accessibility audit and a size budget that prove it. That is not a toy. With a real server behind /api, it is a product.



And more important than the app is the order in which it was made: the brief and the quality goals first, the layers next, the pure logic tested on its own, the screens kept thin, and measurement before any optimisation. That order works for apps a hundred times bigger.



Summary



    

  • Turn a brief into user stories with a test for “done”, and write the quality goals (accessible, tested, fast, safe) before the code.
    • 

  • Organise the code in layers: one place talks to the server, pure logic is separate, screens stay thin.
    • 

  • Validate every answer from the server with a schema, and give the screens errors they understand.
    • 

  • Keep server data in TanStack Query, filters in the address, and app-wide settings in a small store.
    • 

  • Start with two languages and Intl, and define colours as variables, so a theme is a few lines.
    • 

  • Prove it with unit tests, end-to-end tests and an accessibility audit, all automatic.
    • 

  • Measure the bundle against a budget, find the real cause, and load what is not needed at first lazily.
    • 





Practice projects



These projects grow the dashboard the way a real one grows: one feature at a time, each meeting the same quality goals. For every project, write the user story first, put the logic in lib/ with a test, keep the screen thin, and run the three checks (unit tests, end-to-end tests, size) before you call it done.

Project {{n}}.3 · Challenge


From laptop to production


Turn the dashboard into a Vite project with a real CI pipeline, and serve it from a container, ready for a real /api.


You will practise: Vite, GitHub Actions, required checks, Docker, Nginx, and single-page app routing on a server.


    

  1. Create a Vite React project (Chapter 3) and move src/ into it. In development, run the pretend server only when import.meta.env.DEV is true.
    2. 

  2. Write a workflow that, on every pull request, installs with npm ci, then runs the type checker, the unit tests, the end-to-end tests and the size script, and make all four required.
    3. 

  3. Write a two-stage Dockerfile: the first stage builds with Node, the second copies dist/ into an Nginx image.
    4. 

  4. Configure Nginx to send every unknown path to index.html, so /orders/1036 works after a reload, and to forward /api/ to the real server.
    5. 

  5. Add long cache headers for the hashed files in assets/, and none for index.html.
    6. 



Hint: the cache rule in the last step is what makes releases safe. Hashed files never change, so they can be cached for a year; index.html must always be fresh, because it is the file that points to the new hashes.
