Chapter {{n}}

Server Rendering with Next.js

In this chapter you will learn to

  • tell apart the ways a page can be made: in the browser, on the server per request, or ahead of time at build
  • create a Next.js app and build its routes from folders and files
  • write Server Components that read data directly, and Client Components that react to the user
  • cache pages, prerender them at build time, and stream the slow parts
  • handle forms with Server Actions, and answer API requests with route handlers
  • read the build’s route table and run the app in production

Every React app in this book so far started as an almost empty HTML page. The browser downloaded JavaScript, ran it, fetched the data, and only then drew something. That works well for apps behind a login, but the user waits for a blank page, slow phones wait longest, and a search engine or a link preview may see nothing at all. Next.js is a framework around React that can make the HTML on the server instead, and send a page that is complete before any JavaScript runs. It is the most widely used way to build React sites that must be fast and found.

Next.js does not replace what you learned. Components, props, state, hooks and forms all work the same. What changes is where each component runs, and that one question is the whole chapter.

{{n}}.1 Four ways to make a page

WayWhen the HTML is madeGood forPrice
Client-side rendering (CSR)In the browser, after the JavaScript runsDashboards and apps behind a loginA blank page at first, weak for search engines
Server-side rendering (SSR)On the server, for every requestPages that differ per user or per minuteServer work on every visit
Static generation (SSG)Once, when the app is builtPages that are the same for everyone: articles, docs, product pagesStale until the next build
Incremental revalidation (ISR)At build, then again in the background after a set timeMostly-static pages whose data changes sometimesVisitors may see data a little old

In all three server ways, the browser still downloads the React code afterwards, and React attaches event handlers to the HTML that is already there. This step is called hydration: the page appears first and becomes interactive a moment later. Next.js lets you choose the way per page, and even per part of a page, which is why it suits real sites where the home page, the product pages and the account page need different things.

{{n}}.4 Client Components



Server Components cannot do what happens after the page arrives: they have no state, no effects and no event handlers, because they are not in the browser. A component that needs any of these starts its file with the directive "use client":






A Client Component is the kind of component you have written all book long. It is still rendered to HTML on the server for the first visit, so the button appears at once, and then it is hydrated in the browser, where it reacts to clicks. "use client" marks a boundary: this file and everything it imports goes to the browser.





Four rules keep the two kinds working together:


    

  • Server Components can render Client Components, and pass them props. The props cross from the server to the browser, so they must be data that can be serialised: strings, numbers, plain objects and arrays, not functions or class instances.
    • 

  • Client Components cannot import Server Components. They can still show one if it is passed to them as children.
    • 

  • Push "use client" down to the leaves. Make the button a Client Component, not the whole page. Everything above the boundary stays on the server and costs the browser nothing.
    • 

  • Keep server-only code out of client files. The package server-only, imported at the top of a file, makes the build fail if that file is ever imported into the browser by mistake.
    • 




Watch out: hydration mismatches
During hydration, React expects the browser’s first render to produce exactly the HTML that the server sent. A Client Component that renders new Date(), Math.random() or window.innerWidth directly gives different results in the two places, and React warns about a hydration mismatch. Read such values in an effect, after hydration, or compute them on the server and pass them as props.



{{n}}.5 Dynamic routes



The folder [id] matches any value in that part of the address, and the page receives it in params:






Three functions do a lot of work here:


    

  • generateStaticParams lists the ids known at build time. Next.js builds a page for each of them ahead of time, the way static generation works, and still handles other ids when they are requested.
    • 

  • generateMetadata gives each product its own title and description, which is what appears in search results and link previews.
    • 

  • notFound() stops rendering and shows the nearest not-found.tsx, with the correct status code 404. It throws, so TypeScript knows that product is defined in the lines after it.
    • 




params is a promise: Next.js starts rendering before it has decided everything about the request, and the component waits only when it really needs the value.





{{n}}.6 Caching, prerendering and streaming



Now we can read the route table from the build in section {{n}}.2. Each symbol tells you how that address will be served:



    

  • ○ Static. / and /contact depend on nothing that changes, so they were made once, at build time, and are served as ready files. This is the fastest a page can be.
    • 

  • ◐ Partial prerender. The product pages were prerendered at build time for ids 1, 2 and 3, and the route also has a part that is made per request (the params of an id nobody listed). The static shell is sent at once and the rest is streamed into it.
    • 

  • ƒ Dynamic. /api/products runs on every request.
    • 

  • /products is static with Revalidate 1m and Expire 1h. That is our "use cache" at work.
    • 




By default, Next.js does not cache data: anything that reads data runs again for each request, so pages are never stale by accident. You opt in with the directive "use cache" at the top of a component or an async function. Its result is stored and reused, and cacheLife says for how long. With "minutes", the cached page is considered fresh for about a minute; after that, the next visitor still gets the stored page at once, while a fresh one is made in the background. That is incremental revalidation, written in one line. Other profiles include "seconds", "hours", "days" and "max".



When data changes because of something your own app did, such as an admin editing a price, you do not need to wait. Give the cached function a name with cacheTag("products"). Then, in the Server Action that made the change, call updateTag("products"): the stored result is thrown away, and the next request, including the admin’s own, makes the page again. (revalidateTag("products", "max") is the gentler version for other places: visitors keep getting the old page while a new one is made.)



Streaming the slow parts



Our pretend database takes 300 ms. When a page has to wait for data, the file loading.tsx next to it is shown immediately in its place:






Behind the scenes, Next.js wraps the page in React’s <Suspense> component, with loading.tsx as its fallback: while anything inside is still waiting, the fallback is shown instead. The server sends the layout and the grey bars first, keeps the connection open, and sends the real content when it is ready, in the same response. You can also place your own <Suspense> around a single slow part of a page, so that everything else appears without waiting for it.



Professional habit: read the route table after every build
The table is a summary of every caching decision in the app. A page you expected to be ○ that shows as ƒ means something in it reads data per request, and every visitor now pays for server work. Catching that in the build output takes a second; finding it later in a slow production site takes much longer.



{{n}}.7 Route handlers



A route.ts file answers HTTP requests with any response you like, usually JSON. Export a function named after the HTTP method:






The second command in the curl transcript above called it. Route handlers are for clients that are not your pages: a mobile app, a webhook from a payment service, another company’s system. {{n}}.8 Forms with Server Actions



A Server Action is an async function that runs on the server and can be called from the browser, usually by a form. A file that starts with "use server" makes every function it exports a Server Action:






The form uses React’s useActionState, which keeps the last value the action returned, and tells you when it is running:








When the form is submitted, React sends its fields to the server, runs sendMessage there with the previous state and a FormData, and puts the returned value in state. The validation is the zod schema from Chapter {{n-9}}, running on the server, where no user can switch it off. Because the form uses a plain action, it even works before the JavaScript has loaded: the browser posts it like a classic HTML form.





Watch out: every Server Action is a public endpoint
An action feels like a function call, but anyone can call it with any data, just like an API. Validate every field on the server, check that the user is signed in and allowed to do this, and never trust a hidden field for the user’s id or a price. Everything from Chapter {{n-3}} applies here.



{{n}}.9 Running in production



npm run build makes the optimised app, and npm start runs it as a Node.js server on port 3000. That is all a server needs: Node.js, the built .next folder, and node_modules. Two more facts complete the picture:


    

  • Environment variables stay on the server, unless their name starts with NEXT_PUBLIC_. Those are written into the browser’s JavaScript at build time, where anyone can read them. Database passwords and API keys must never have that prefix.
    • 

  • For containers, set output: "standalone" in next.config.ts. The build then copies only the files the server really needs into .next/standalone, which makes a much smaller image.
    • 




Put a reverse proxy such as Nginx in front of it for HTTPS and compression, and the shop is ready for visitors. Hosting platforms that specialise in Next.js do all of this for you, but nothing in this chapter needs one.

MistakeWhat happensFix

useState or onClick in a Server ComponentA build errorMove that part into a Client Component


Passing a function as a prop from server to clientAn error: functions cannot be serialisedPass data, or a Server Action

Trusting a Server Action’s inputAnyone can call it with forged dataValidate and check permissions inside the action

Summary



    

  • A page can be made in the browser, on the server per request, at build time, or at build time and revalidated later. Next.js lets you choose per page. Hydration makes server HTML interactive.
    • 

  • Folders in app/ are addresses; page, layout, loading, error, not-found and route files give each one its parts.
    • 

  • Components are Server Components by default: async, reading data directly, never sent to the browser. "use client" marks Client Components, which have state and events. Keep the boundary at the leaves.
    • 

  • generateStaticParams, generateMetadata and notFound() make dynamic routes fast, findable and correct.
    • 

  • Data is not cached unless you ask: "use cache" with cacheLife, and updateTag after changes. loading.tsx and <Suspense> stream slow parts.
    • 

  • Server Actions handle forms on the server, and are public endpoints to validate and protect. Route handlers serve other clients.
    • 

  • Production is npm run build and npm start. Only NEXT_PUBLIC_ variables reach the browser.
    • 




Quick check answers: 1. Only on the server: it is a Server Component. 2. Because the server already rendered the components into HTML, with the data inside, before sending the page. 3. React runs in the browser, matches the HTML that is already on the page, and attaches the event handlers, so the page becomes interactive.
