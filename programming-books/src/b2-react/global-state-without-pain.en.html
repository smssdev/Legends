Chapter {{n}}

Global State without Pain

In this chapter you will learn to

  • sort every piece of state into the right home: component, address, server cache or global store
  • share values with distant components through Context, without passing props through every level
  • keep Context fast, and know when it is not enough
  • build a small global store with Zustand, and read it with selectors
  • save a store between visits, and test it without React

Some data is needed everywhere: who is signed in, the chosen language and theme, the number of items in the cart. Passing it as props from the top of the app through every component in between is called prop drilling, and it makes every component in the path depend on data it never uses. React’s answer is Context. For state that changes often and is read in many places, a small store is usually better. But first, the most important skill of this chapter: knowing that most state is not global.

Many apps have a giant global store full of data that one screen uses, or that really belongs to the server. Every time I am tempted to make something global, I first ask: who actually reads this?

{{n}}.2 Context

Context lets a component provide a value to everything below it in the tree, at any depth, without passing props. It has three parts: createContext makes the context, a provider component puts a value into it, and useContext reads the nearest value from any component below:








Three habits make Context pleasant to use:


    

  • Hide the context behind a hook. Components call useAuth(), never useContext(AuthContext). The hook also throws a clear error if someone forgets the provider, instead of a mysterious null later.
    • 

  • Provide data and the functions that change it together, so readers do not need to know how it is stored.
    • 

  • Keep the value stable. Every component that reads a context re-renders when its value changes. useMemo creates a new value object only when user changes, not on every render of the provider.
    • 




When Context is not enough



Context is perfect for values that change rarely: the user, the theme, the language. It becomes slow for values that change often and are read in many places, because every reader re-renders on every change, even readers that only care about one small part. A cart is the classic example: the badge needs the count, the summary needs the lines, the product list only needs the add function. That is the job of a store.

  1. Where should the text of a search box live if users want to share the results?
  2. What happens to a component that calls useAuth() outside any AuthProvider?
  3. Why can a frequently changing value in Context make an app slow?

{{n}}.3 A store with Zustand



A store is an object that lives outside the component tree, holds state and the functions that change it, and tells interested components when something changes. Zustand (German for “state”) is a tiny store library: one function, no provider, and almost no rules to learn. Under the hood it is the event emitter you built in Chapter {{n-7}}, with state:








That ran in Node, with no React at all: set merges a change into the state and notifies the subscribers, and subscribe returns its own “stop” function. In React, create turns the same idea into a hook:










    

  • useCart(selector) reads part of the store. The selector is a function from the whole state to what this component needs. The component re-renders only when that result changes, so ProductList, which selects only add, never re-renders when the cart changes.
    • 

  • Selectors such as selectCount and selectTotal are plain functions next to the store. They derive values, as in Chapter {{n-3}}, so the store keeps only the lines.
    • 

  • The updates are immutable, exactly as with useState: set receives the old state and returns the parts that change.
    • 

  • The persist middleware saves the store in localStorage under the name "cart" and loads it on the next visit, with one line.
    • 




Watch out: a selector must not build a new object
useCart((s) => ({ count: …, total: … })) returns a new object on every call, so the component re-renders on every change in the store, or even loops. Select single values, or several separate selectors, or use Zustand’s useShallow helper.



Professional habit: keep server data out of global stores
Copying products or orders into a global store means writing your own cache, by hand, without refetching, deduplication or invalidation. Let TanStack Query own server data, and keep the store for what the app itself owns. Most “global state” problems disappear with this one rule.

Summary



    

  • State has four homes: the component, the address, the query cache and, for the few values the app owns and many places read, Context or a store.
    • 

  • Context passes a value down to any depth: createContext, a provider, and a useX() hook. Keep the value stable with useMemo.
    • 

  • Context suits values that change rarely. For frequent changes read in many places, use a store.
    • 

  • Zustand creates a store as a hook; components read it with selectors and re-render only when their selection changes.
    • 

  • Stores update immutably, can be saved with persist, and, being plain code, can run and be tested without React.
    • 




Quick check answers: 1. In the address, as a search parameter. 2. It throws the error “useAuth must be used inside <AuthProvider>”, which points straight at the problem. 3. Because every component that reads the context re-renders on every change, even if it uses only a small part of the value.

Project {{n}}.1 · Easy


A theme that follows the user


A light and a dark theme, starting from the system setting, switchable from anywhere, and remembered on the next visit.


You will practise: a context with a provider and a hook, lazy initial state, matchMedia, and an effect that updates the page.


    

  1. Write the colours as CSS custom properties on :root, and the dark ones on body.dark. Components never mention colours by name.
    2. 

  2. In ThemeProvider, start from the saved choice, or else from matchMedia("(prefers-color-scheme: dark)").
    3. 

  3. In an effect, toggle the dark class on body and save the choice.
    4. 

  4. Expose { theme, toggle } through useTheme(), which throws a clear error outside the provider.
    5. 

  5. Make the switch a button with aria-pressed, and a label that says what is on now.
    6. 



Hint: the theme changes rarely and is read in few places, which is exactly what Context is good at. All the real work is done by CSS variables: React only switches one class.

Project {{n}}.3 · Challenge


Notifications with undo


A notification system that any component can use with one call, that shows at most three messages, disappears by itself, can offer an “Undo” button, and is announced by screen readers.


You will practise: a context that provides a function, useCallback, portals, timers, and live regions.


    

  1. Provide a single function, notify(text, action?), through Context. Wrap it in useCallback so that it never changes, and readers never re-render because of it.
    2. 

  2. Keep the list of messages in the provider. Add new ones with [...all.slice(-2), next], so at most three stay on screen.
    3. 

  3. Remove each message after five seconds with setTimeout, and also with a close button labelled for screen readers.
    4. 

  4. Render the list with createPortal into document.body, so it is never hidden or clipped by the component that called it.
    5. 

  5. Give the list role="status" and aria-live="polite", so screen readers announce new messages without interrupting the user.
    6. 



Hint: “Undo” is friendlier than “Are you sure?”. Do the action at once, and offer to reverse it for a few seconds. Users make fewer mistakes, and the rest of the time they are not slowed down.
