Chapter {{n}}

Claude Code for Teams and CI

In this chapter you will learn to

  • layer team settings and personal settings, and know which one wins
  • run Claude Code in continuous integration, with no person at the keyboard
  • get a verdict as structured data a script can act on
  • keep CI runs small, bounded and cheap
  • keep people in charge of the decisions an automatic review informs

A team using Claude Code needs two things that a single developer does not. The first is shared rules that a person cannot loosen by accident: what every session may do, and what none may. The second is automation: Claude Code running on every pull request, in the same pipeline as the tests, without anyone typing. This chapter builds both, and shows what each one costs.

The settings, the denial, the CI script, its exit codes and its costs are real Claude Code behaviour. The verdicts come from the practice server, scripted to depend on the diff it received: blocking the unrounded total, passing the rounded one.

{{n}}.1 Team settings and personal settings

The team commits .claude/settings.json; each developer may add .claude/settings.local.json, which git ignores. Here the team allows the tests and denies pushing, and one developer has allowed pushing for themselves:






The push was denied. When rules conflict, a deny wins over an allow, wherever each is written, so a personal file cannot undo a team’s refusal. That is the property a team needs: allows can be added where people need them; the few things nobody may do stay refused. Organisations that need more can install managed settings on every machine, which take precedence over both and cannot be changed by users.



Tip
Write the team’s denies first, then its allows. The denies are short (push to the main branch, read the secrets folder, delete data) and almost never change; the allows grow with the work, and can live closer to the people who need them.



{{n}}.2 A review in CI



In continuous integration nobody can approve a tool call, so the safest run has no tools at all: Claude Code reads the diff from standard input, answers, and stops. Three flags make it fit for a pipeline: --tools "" so it can only read what it is given, --max-budget-usd so a run cannot overspend, and --json-schema so the verdict comes back as data:








The branch adds VAT to receipts, the change of Chapter 7, with the rounding problem its review found. The CI step:






The verdict is an object, not a paragraph: ok is false and the blocker names the file and the problem, so the script exits with 1 and the pipeline fails. With --json-schema, Claude Code gives the model a tool to report its answer in that shape and returns it in structured_output; a script never has to parse prose.



Look at the cost, too: a cent and a half. The runs of the earlier chapters cost about twelve cents a turn, mostly for Claude Code’s own instructions and tool descriptions; with no tools, there is little to send but the diff and the request. In a pipeline that runs on every push, that difference is the budget.

Watch out
The diff is input from whoever opened the pull request, and a pull request from outside the team can contain text written to steer a reviewer. A review with no tools can only answer; it cannot run anything. Never give a CI run tools that write, or secrets it does not need, on code nobody on the team has looked at.



{{n}}.3 In the pipeline



The workflow runs the same script on every pull request, with the API key from the repository’s secrets, read-only access to its contents and a time limit (Project {{n}}.3 checks the file). Anthropic also publishes a GitHub Action for Claude Code, which can review pull requests and answer comments that mention it; the principles are the same: the fewest tools that do the job, a limit on spending, and output a script can read.



What the automatic review produces is information for a person, not a decision. A failing review should block a merge the way a failing test does; a passing one should not approve anything. The pull request still needs a human reviewer, who now starts with the mechanical problems already found.

Professional habit
Track what the automatic review finds and what people find after it, for a month. If people keep finding what it misses, improve its instructions; if it keeps blocking what people approve, loosen them. An automatic reviewer that nobody measures turns into noise that everyone ignores.

Summary



    

  • Team settings are committed, personal ones are not, and a deny wins over an allow wherever each is written.
    • 

  • In CI, run Claude Code in print mode with no tools, a spending limit and a JSON schema for the verdict.
    • 

  • A script reads structured_output and fails the build on a blocker; the same step passes once the problem is fixed.
    • 

  • Fewer tools means a smaller request on every turn: the CI review cost about a tenth of a run with Claude Code’s full tool set.
    • 

  • Automatic reviews inform people; they do not approve.
    • 




Quick check answers: 1. Because the team’s settings deny Bash(git push:*), and a deny wins over an allow, even an allow in a personal file. 2. --tools "" removes every tool, so untrusted input cannot make it act; --max-budget-usd stops a run that would spend too much; --json-schema returns the verdict as data a script can check. 3. Because with no tools, the request carries no tool descriptions and much less of Claude Code’s own instructions: mostly just the diff and the request.
