Chapter {{n}}

From Issue to Pull Request

In this chapter you will learn to

  • write an issue that an agent, or a colleague, can fix without asking
  • let Claude Code take an issue to a branch, a fix, a test and a commit
  • keep the repository’s rules in force with git’s own hooks, whoever commits
  • get a pull request description that a reviewer can use
  • check the branch, the commits and the description before anyone reviews them

Most work in a software team travels the same road: an issue describes a problem, a branch holds the fix, commits record it, and a pull request asks a colleague to accept it. Claude Code can walk that road for you, from reading the issue to writing the description. This chapter follows it all the way, in a local repository, and shows where the team’s rules stop a mistake that the agent made on the way.

Every step in this chapter ran for real: the branch, the edits, the two tests, git refusing a commit message, the second commit, and the description written from the repository’s template. The practice server chose the steps; git, Node and Claude Code carried them out.

{{n}}.2 From issue to commit



The task names the issue, the branch policy, the need for a test, and where the description goes. The run allows file edits and four commands: reading the issue, creating the branch, running the tests, and committing, the last allowed by prefix, Bash(git commit:*), because the message is not known in advance:



claude -p "Fix issue 42 ..." --permission-mode acceptEdits \
  --allowedTools "Bash(cat issues/42.md)" "Bash(git switch -c fix/42-piastres)" \
                 "Bash(node --test)" "Bash(git commit:*)"





Follow the road. It read the issue before anything else, created a branch named for it, read the code, and saw the cause: parseInt, the bug from Chapter 4. It fixed the code and added a test built from the issue’s own numbers, ran the tests (two, both passing), and committed. Then the repository said no.



{{n}}.3 Rules that hold for everyone



The first commit message was “fixed stuff”. The repository has a commit-msg hook, a script git itself runs before accepting a commit:






The message did not match, the hook exited with 1, and git refused the commit; its message went back to the model, which committed again with a message that follows the convention, naming the issue. This is a different kind of hook from Chapter 8’s: it belongs to git, not to Claude Code, so it applies to every commit in the repository, by a person, by Claude Code, or by any other tool. Rules that matter to the team belong where they hold for everyone: git hooks locally, and on the server, branch protection and required checks (Chapter 10).



Tip
Keep git hooks in the repository (here in githooks/) and point git at them with git config core.hooksPath githooks, as the chapter’s setup does. Hooks in .git/hooks are not versioned, so each developer, and each agent’s machine, would have a different set.



{{n}}.4 The pull request



The description came from the repository’s template, section by section: what changed and why, how it was tested, and the issue it closes. Project {{n}}.3 gathers it with the branch’s commits and the size of the change, which is what a reviewer reads first. On a hosting service such as GitHub, “Closes #42” in a pull request closes the issue when the pull request is merged, and Claude Code can open the pull request itself through the service’s command-line tool, if you allow it.



Twelve turns and about seventy cents, by the practice server’s count: a real task of this size usually costs less than an hour of anyone’s time, and the review it needs still costs a person’s attention. That attention is better spent on a small, well-described pull request than on a large one.



Watch out
Do not let an agent merge its own pull request, or push to the main branch. Opening a pull request is a proposal; merging is a decision. Keep decisions with people, and make the server enforce it with branch protection, so that no permission set by mistake can bypass it.
