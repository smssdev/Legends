Projects and Knowledge

In this chapter you will learn to

  • set up a project: instructions once, knowledge once, and every chat starts with both
  • write project instructions that hold up across hundreds of chats
  • organise knowledge so Claude finds the right document and you can keep it current
  • see a project underneath: a system prompt, documents, and the prompt cache
  • share a project with a team without sharing what should stay private

Chapter 2 ended with a chore: attaching the same menu, the same policies and the same instructions to every new chat. A project ends it. You put the instructions and the documents in one place, and every conversation inside the project begins with them. For a team, a project becomes something more: the shared memory of how the team works, which a new colleague can use on their first day.

The answers in this chapter come from the practice server. The projects, their documents, the token counts and the cache are real parts of the code; and the English edition ran into a limit of the cache that this chapter turns into a lesson.

{{n}}.1 What a project is

In the Claude apps, a project has three parts:

  • Instructions, written once, that apply to every chat in the project: who Claude is helping, which sources to use, how to answer.
  • Knowledge: files you add (documents, PDFs, code, data) that Claude can read in every chat.
  • Chats, each a normal conversation that starts with the instructions and the knowledge already in place.

On team plans, a project can be shared with colleagues, who then chat with the same instructions and knowledge. When the knowledge grows larger than Claude can read at once, the app searches it for the passages that matter to each question, instead of reading everything: the retrieval that Book 7’s Chapter 14 built by hand.

{{n}}.2 Instructions that hold up



Project instructions are read at the start of every chat, by every member of the team, for months. They deserve the care of code:






Three sentences, and each one earns its place. The first says who Claude is helping, which decides the tone and the level of detail. The second limits the sources, so the answer about prices comes from the menu and not from what cafés usually charge. The third says what to do when the documents are silent, which is the case instructions most often forget, and the one that produces confident inventions when they do.



Tip
Keep instructions short and about behaviour; put facts in the knowledge. “Our latte costs 45” in the instructions goes out of date unseen; in menu.md it sits with the other prices, where the person who changes prices will find it.



{{n}}.3 Knowledge you can keep current



A project is only as good as its documents, and documents rot. A few rules keep them useful:


    

  • One topic per file, named for the topic: menu.md, policies.md. Clear names help Claude and the people who maintain them.
    • 

  • The current version only. Two menus, one from last year, give Claude two prices to choose from. Replace files; do not add new versions next to old ones.
    • 

  • Text over scans. A Markdown or text file is read exactly; a scanned PDF must be read from page images, which is slower and less reliable.
    • 

  • An owner and a date. Somebody updates the menu when prices change, and the file says when it was last checked.
    • 




{{n}}.4 A project underneath



Built with the API, a project is a few lines: the instructions become the system prompt, the part of the request that sets Claude’s role before any message, and the knowledge follows as documents in it. The last document carries a cache_control marker, which asks the API to keep everything up to that point in the prompt cache, so the next request that starts with the same text reads it back for a fraction of the price:








Three chats in the support project:






The answers follow the instructions: prices from the menu, the nut warning from the policies, and an honest “I will ask a colleague” about parking, which no document mentions. But look at the cache: nothing was written and nothing read. Every chat paid for all 900 tokens of knowledge. The reason is a rule of prompt caching that the API applies without an error or a warning: a prefix shorter than a minimum is not cached. The minimum depends on the model, from 512 to 4,096 tokens; the practice server uses 1,024, and the English knowledge is 913 tokens long.



In the Arabic edition, the same four documents take 1,379 tokens, because Arabic text uses more tokens for the same content, and there the cache works as intended: the first chat writes 1,379 tokens to the cache, and the next two read them back. On Claude Opus 5.5, reading from the cache costs a twentieth of the normal input price, so from the second chat on, the knowledge is almost free.



Watch out
Caching fails silently: a request that misses the cache still works, it just costs the full price. Check cache_read_input_tokens in the usage of the second request. If it is zero, either the prefix is too short, or something in it changed between requests: a date in the instructions, documents in a different order, a tool list that varies. Chapter 15 lists the usual culprits.



Without the project, the same question gets a general answer, and an honest one: it does not know the café’s price.






Quick check
  1. Why did the English chats write nothing to the cache?
  2. Which instruction produced “I will ask a colleague”, and what might happen without it?
  3. Why should a price live in menu.md and not in the instructions?

{{n}}.5 Projects for a team



A shared project gives a team one place for its working knowledge: the support team’s answers, the engineering team’s conventions, the sales team’s product sheets. Before sharing, settle three things. Who can change the instructions and the knowledge: a project anyone can edit drifts. What is in the knowledge: everyone with access can ask Claude about every document in it, so a salary sheet does not belong in a project the whole company uses. And how chats are shared: check what your plan shows to other members, and tell the team, so nobody types into a shared space what they meant to keep private.



Professional habit
Give every shared project an owner and a monthly check: are the documents current, are the instructions still right, and what did people ask that the documents could not answer? Those questions are the next documents to write.

Summary



    

  • A project holds instructions and knowledge once, and every chat in it starts with both.
    • 

  • Instructions say whom Claude helps, which sources to use, and what to do when they are silent; facts belong in the knowledge.
    • 

  • Keep knowledge one topic per file, current, in text, with an owner.
    • 

  • Underneath, a project is a system prompt with documents, cached after the first chat; caching is silent, has a minimum length, and must be checked.
    • 

  • Shared projects need an owner, a policy on what they contain, and a team that knows what is visible to whom.
    • 




Quick check answers: 1. Because the English knowledge, 913 tokens, is shorter than the practice server’s minimum for caching, 1,024 tokens, and a prefix below the minimum is simply not cached, with no error. 2. “If the documents do not answer, say you will ask a colleague.” Without it, Claude might answer from general knowledge, for example by guessing that there is street parking, and a customer would take the guess as the café’s word. 3. Because prices change, and a price in the instructions is easy to forget when the menu is updated; in menu.md it is where the person changing prices will look, next to the other prices.
