1. Record Date.now() before the call, at the first text event and after finalMessage(). Users notice the first: an answer that starts in half a second feels fast even if it takes ten to finish. With the practice server both are almost instant; with the real API, the gap between them is the reason to stream.
  2. Add a rule with "error": {"status": 400, "type": "invalid_request_error", "message": "..."} for the question. The SDK makes one attempt: a 400 means the request itself is wrong, so retrying would only fail again. The fetch wrapper shows a single 400.
  3. Wrap the call: record the start time, call with .withResponse(), then append JSON.stringify({model, requestId, stop: data.stop_reason, tokens: data.usage, ms}) to a log file; in the catch, write the same fields with the error’s status and requestID. One line per call makes the log easy to search and to load into any tool.
  4. Create a server with http.createServer; for a request, write the header content-type: text/event-stream, start client.messages.stream(...), and on each text event write data: ${JSON.stringify(piece)}\n\n; when finalMessage() resolves, write an end event and close. In the page, read it with EventSource. Handle the client disconnecting by aborting the stream, so you stop paying for an answer nobody reads.
  5. Keep a queue of the 20 requests and start a new one whenever fewer than 4 are running (a small pool of “workers” that each take the next request until the queue is empty). Leave the SDK’s retries on; count results by outcome and by error class. With the practice server, add a 429 rule with "times" for some questions: you will see them succeed after retries, and the others unaffected. A pool limits how hard you hit the rate limit in the first place, which is better than retrying after hitting it.
