Chapter {{n}}

The Claude API

In this chapter you will learn to

  • stream an answer, so users see it as it is written
  • let the SDK retry what can be retried, and know what it does
  • set timeouts, and choose them for the request rather than the program
  • handle an answer cut off at max_tokens, without losing what came
  • keep a feature working when a model is overloaded

Chapter 1 sent one message and read one answer. A product sends thousands, from users who are waiting, through networks that fail, to a service that sometimes says “not now”. This chapter covers what every production program needs around the call itself: streaming, retries, timeouts, answers that do not fit, and what to do when the model you wanted is busy.

The errors, retries, timeouts and streaming events in this chapter are real behaviours of the SDK against the practice server, which can be made slow, busy or overloaded on purpose. The words of the answers are the practice server’s.

{{n}}.1 Streaming

A long answer can take many seconds to write. Without streaming, the user stares at nothing until it is complete; with it, the first words appear almost at once. The SDK’s stream gives you the text as it arrives, and the complete message at the end:






Each bar marks where every fourth piece began: the answer arrived in 23 pieces, and the program printed each one immediately. finalMessage() then gives the same message a non-streaming call would have returned, with its stop reason and usage, so the rest of the program does not care how it arrived. Stream whenever a person is waiting, and whenever max_tokens is large: long requests that do not stream can hit HTTP timeouts before the answer is finished.



{{n}}.2 Retries



Some failures are worth trying again: 429 (too many requests), 529 (overloaded), other 5xx errors, and broken connections. Others are not: a 400 will fail the same way every time. The SDK knows the difference, and retries the first kind by itself, twice by default, waiting longer each time and respecting the retry-after header when the API sends one. A wrapper around fetch makes it visible:








With the default, the request failed twice with 429, waited as the server asked, and succeeded on the third attempt; the program saw only the answer. With maxRetries: 0, the first 429 became a RateLimitError. Leave the retries on for interactive requests, set them higher for background jobs that can wait, and never write a second retry loop around the SDK’s own: the waits multiply.



Watch out
Retries make failures slower, not rarer. If your requests are rate-limited regularly, the fix is fewer or smaller requests (caching, batching, a smaller model for simple tasks, Chapter 15) or a higher limit, not more retries.



{{n}}.3 Timeouts



The SDK waits up to ten minutes by default, which suits long answers and not much else. Set the timeout for the request in front of you:








The practice server took three seconds on purpose. With a one-second timeout, the SDK gave up and raised APIConnectionTimeoutError; with ten seconds, the answer arrived. In the JavaScript SDK the timeout is in milliseconds; other SDKs use their own units (seconds in Python, for example). Timeouts are retried like other connection errors, so the longest wait is the timeout times the number of attempts: set both with that sum in mind.

{{n}}.4 Answers that do not fit



When an answer reaches max_tokens, it stops, mid-sentence if need be, and stop_reason says max_tokens. A program must not show it as complete. To continue, keep the cut answer in the history and ask for the rest in a new user message:








The first answer stopped at “and”; the second began with “today”, because the model could read exactly where its first answer ended. The simpler fix is often the better one: a larger max_tokens, or a request for a shorter answer.



An older trick no longer works here: writing the start of Claude’s answer yourself, as a last assistant message, for Claude to continue. Current models refuse it:






To control the form of an answer, say it in the instructions, or ask for structured output (Chapter 12); to continue an answer, use a user message as above.



{{n}}.5 When a model is busy



An overloaded model returns 529, and after the SDK’s retries the error reaches your code. For a feature that must answer, fall back to another model that can do the job, and say so in your logs (Project {{n}}.3). Every response also carries a request id, on success and on error: log it with your own request, and when something goes wrong, it is the first thing Anthropic’s support asks for (Project {{n}}.2).



Professional habit
For every call to the API, log the model, the request id, the stop reason, the tokens and the time taken. When a user reports a strange answer, those five fields are the difference between finding the cause in a minute and guessing for a day.

Summary



    

  • Stream when a person is waiting or the answer is long; finalMessage() gives the complete message.
    • 

  • The SDK retries 429, 5xx and connection errors by itself, respecting retry-after; configure it, do not wrap it.
    • 

  • Set a timeout per request; remember it is retried too.
    • 

  • A max_tokens stop is not an answer: continue with the cut text in the history, or ask for less; prefill is refused by current models.
    • 

  • Fall back to another model on overload, and log the request id of every call.
    • 




Quick check answers: 1. It retries 429, 408, 409, 5xx (529 included) and connection errors, including timeouts; it does not retry other 4xx errors, such as 400, 401 and 404, which would fail again the same way. 2. Up to about 30 seconds of waiting for responses (three attempts of 10 seconds), plus the pauses between attempts. 3. The complete message, as a non-streaming call would have returned it, with its content, stop reason and usage.
