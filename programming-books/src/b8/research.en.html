Chapter {{n}}

Research, Connectors and Tools

In this chapter you will learn to

  • tell apart the ways Claude reaches beyond its training: search, research, connectors and tools
  • turn on web search from the API and read every block that comes back
  • judge a cited answer by its sources, not by its citations
  • handle a search that fails inside a successful response
  • connect Claude to your team’s tools without handing it more than it needs

Chapter 1 ended with Claude saying, correctly, that it could not know today’s news. This chapter removes that limit, carefully. Claude can search the web, run a longer research process that reads dozens of pages, and, through connectors, read your team’s documents, email and code. Each of these makes Claude more useful and adds a new question: where did this answer come from, and should I believe it?

Every search, result and answer in this chapter is the practice server’s, and every website ends in .example, a domain reserved so that it can never belong to anyone. The blocks, the citations and the error are shaped exactly as the API returns them.

{{n}}.1 Four ways beyond the training

WayWhat it doesWhere
Web searchClaude searches when a question needs current or specific facts, and cites what it usedThe apps, and the API as a server tool
ResearchA longer process: many searches, many pages, a report with sources; takes minutes, not secondsThe apps
ConnectorsClaude reads, and sometimes acts in, your own tools: documents, email, calendars, code, ticketsThe apps; the API through MCP (Chapter 13)
Your own toolsFunctions you write that Claude can call: your database, your pricing rulesThe API (Chapter 12)

All four work the same way underneath: Claude decides it needs something, asks for it, reads the result, and continues. What differs is who runs the step. Web search is a server tool: Anthropic runs the search and returns the results inside the same response. Your own tools are run by your code (Part III).

{{n}}.3 Reading a cited answer



A program shows the answer the way the app does: a number after each cited claim, and the sources at the end:








Every sentence but the last has a source, and that is exactly where the reading starts, not where it ends. Look at what each claim rests on. The 8% comes from the association that set the prices, three days ago: the best source there is. The cause comes from a news report, two days old, which is reasonable. The doubling comes from a blog post five weeks old, whose title states a prediction as a fact: a citation, but not evidence. And the last sentence has no source because it is Claude’s own reasoning, which may be right but should be read as an opinion.



A citation answers one question: where did this sentence come from? It does not answer whether the source is right, current, or relevant to you. Each citation carries the cited_text from the page, so you can check that the source says what the sentence claims; the source itself, you judge as you would any web page.



Watch out
Search results are text written by strangers, and Claude reads them. A page can contain instructions aimed at AI models, as Book 7’s Chapter 15 showed with a café review. Never give a model with web search access to secrets or to tools that act, without checks outside the model on what it does.



{{n}}.4 When a search fails



A search can fail while the request succeeds. The response is a normal 200 with a normal stop reason, and the failure sits inside a result block, where the list of results would be:








The question asked for more than two searches could cover, and the third search came back as max_uses_exceeded. A program that assumed content is always a list would crash here, or worse, report zero results as if the web had nothing. Check the type of content before reading it, and treat an answer built on failed searches as incomplete, whether or not the answer says so.



Quick check
  1. The blog sentence has a citation. Why is it still the weakest claim in the answer?
  2. How does a program know that a search failed, when the request succeeded?
  3. What does cited_text let you check?

{{n}}.5 Research in the apps



For a broad question (“what are our options for accepting payments in Egypt?”), the apps can run a research process: Claude plans, searches many times, reads the pages it finds, and writes a report with sources. It takes minutes rather than seconds, and it is good at covering ground you would not have thought of. Read its report the way Section {{n}}.3 read the short answer: by its sources. Open the three or four citations that carry the conclusions, check their dates and their authors, and treat the report as a well-organised first draft of your own research, not as the research.



{{n}}.6 Connectors



A connector lets Claude reach into a tool your team uses: shared documents, email, a calendar, a code repository, an issue tracker. Most are built on MCP, the open protocol of Chapter 13, and you can add your own. Once connected, Claude can search your documents to answer a question, summarise a thread, or, if the connector allows it, create a ticket or draft a reply.



Three questions decide whether a connector is safe to turn on:


    

  • What can it read? Everything Claude reads through it becomes part of the conversation. Connect the folder the task needs, not the whole drive.
    • 

  • What can it do? Reading is one level of trust; sending, deleting and paying are another. Prefer connectors that ask you before each action, and read the action before you approve it.
    • 

  • Who wrote what it reads? An email from outside your company is untrusted text, like a web page. A connector that reads email and can also send it is exactly the combination an attacker would want.
    • 




Professional habit
For every connector your team enables, write one line: what it can read, what it can do, and who approved it. Review the list when people change roles, and remove what nobody uses: an idle connector is access nobody is watching.



Common mistakes





MistakeWhat happensFix



Treating a citation as proofWeak sources passed off as factsJudge each source: who, when, and does it say that


Ignoring uncited sentencesThe model’s opinion read as a findingMark them, and check them first


Assuming search results are a listCrashes, or failures reported as “nothing found”Check the type of content


No limit on searchesSlow, costly answersSet max_uses; read the usage


Connecting everythingClaude reads far more than the task needsThe smallest scope; review it regularly


Reading and sending in one connector, uncheckedAn injected instruction becomes an actionApprove every action; separate read from act






Summary



    

  • Claude reaches beyond its training through search, research, connectors and tools; all of them follow the same pattern of asking, reading and continuing.
    • 

  • Web search from the API is one tool entry; the response shows the searches, the results, and text split by citation.
    • 

  • A citation says where a sentence came from, not whether it is true: judge the sources, and check uncited sentences first.
    • 

  • Search failures arrive inside successful responses; check the type before reading the results.
    • 

  • Connectors should read and do as little as the task needs, with every action approved.
    • 




Quick check answers: 1. Because its source is the weakest: a five-week-old blog post stating a prediction as a fact, while the 8% comes from the association itself. A citation shows where the claim came from, not that it is right. 2. The web_search_tool_result block’s content is an error object with an error_code instead of a list of results. 3. That the source really says what the sentence claims: you can compare the sentence with the exact text it was based on.
