Chapter {{n}}

Working on a Real Codebase

In this chapter you will learn to

  • prepare a repository so that every change Claude Code makes is easy to see and to undo
  • let Claude Code find its way around before it changes anything
  • follow a change across several files, from search to passing tests
  • review the result the way a reviewer would: from the diff, not from the summary
  • get a second opinion on a diff, and check it too

A real codebase has more files than anyone remembers, conventions nobody wrote down, and tests that pass for reasons nobody checked. That is where Claude Code earns its place, and where it needs the most care: the change it makes may touch files you did not think of, and its summary of what it did is only as good as its attention. This chapter makes a small change across a small project, end to end, and reviews it properly.

Claude Code in this chapter is real, and so are its searches, its edits and the test run: the files changed on disk, and git diff shows exactly how. The practice server plays the model, and its replies were checked against what really happened, which is how this chapter found one claim in its own script that was false.

{{n}}.1 Before Claude Code touches anything

Start every task from a clean working tree: everything committed, the tests passing. Then whatever the agent changes is exactly what git diff shows, and undoing it is one command. The chapter’s project is three files and a test, in a new repository:




Tip
Give each task its own branch, or its own worktree (a second checkout of the same repository in another folder), so two tasks never mix their changes. Claude Code can create worktrees for you; plain git worktree add works too.



{{n}}.2 A change across files



The task: add 14% VAT to receipts, with a subtotal, the VAT and the total. It touches the code that totals a receipt, the place where rates belong, and the test that checks the total. The run allows file edits for the session (acceptEdits) and exactly two commands, a search and the tests:



claude -p "Add 14% VAT to receipts: ..." --permission-mode acceptEdits \
  --allowedTools "Bash(grep -rln total src)" "Bash(node --test)"





Read it as you would watch a colleague. It searched before guessing where totals live. It read the two files before changing them, in one turn, because the two reads did not depend on each other. It edited both, then the test, which still expected the old total. It ran the tests, and the real result came back: one test, passing. Only then did it report. Eight turns, about forty cents with the practice server’s token counts; a real model on a real task may take more turns or fewer.



One detail is worth noticing for what it says about tools. Claude Code’s set of built-in tools varies by version and settings, and the build used here had no separate search tool enabled, so the search went through grep, allowed as an exact command. Check what your installation offers (/permissions, and the documentation for your version) before you write rules that depend on it.



Watch out
The practice server’s first script for this task ended with “both tests pass”. The project has one test. The run showed one, and the script was corrected. A real model can make the same slip: a summary is written after the work, from memory of it, and memory is where errors hide. Read the tool results, not just the last message.

{{n}}.4 Habits for real repositories



    

  • Small tasks. “Add VAT to receipts” is a task; “clean up the billing code” is a week. Small tasks give small diffs, and small diffs get real reviews.
    • 

  • Questions before changes. In an unfamiliar codebase, ask first (“where is the total computed?”, Project {{n}}.1), or start in plan mode, and correct the plan before any file changes.
    • 

  • Tests as the contract. If the tests are weak, the agent’s “they pass” means little. Ask for the tests first, read them, then ask for the change.
    • 

  • Undo without fear. git checkout -- . throws away a change you do not like; a fresh attempt with a better prompt is often faster than repairing a bad one.
    • 

  • You commit. Read every line, run the tests yourself, and make the commit with your name on it. The agent wrote the change; you are the one who says it is right.
    • 




Professional habit
Hold changes made with Claude Code to the same review as changes from a colleague: the same tests, the same reviewer, the same standards. A team that reviews agent changes more lightly will soon have a codebase nobody understands.

Summary



    

  • Start from a clean, committed tree, so the diff is exactly the agent’s change and undoing it is one command.
    • 

  • A good agent run searches, reads, edits, tests and only then reports; you can see every step.
    • 

  • Tools vary by version and settings; allow exactly the commands a task needs.
    • 

  • The summary is a claim and the diff is the fact; check one against the other.
    • 

  • Small tasks, tests first, easy reverts, and the same review as any colleague’s change.
    • 




Quick check answers: 1. So that git diff shows exactly what the agent changed, nothing of yours mixed in, and so that undoing it is a single command. 2. Because the two reads did not depend on each other, so both could be requested at once; it saves a turn, and every turn re-sends the context. 3. The summary is what the agent says it did, written after the work; the diff is what actually changed on disk. When they disagree, the diff is right.

Hint: the second point is the one that matters, and it is true: in JavaScript, 16 + 2.24 is 18.240000000000002, and 158 of the integer subtotals up to 2,000 give such a tail. The script’s first draft of this review gave an example that does not happen (136.80000000000001); a reviewer’s example deserves the same check as the code.
