Chapter {{n}}

CLAUDE.md, Skills and Hooks

In this chapter you will learn to

  • write a CLAUDE.md that gives every session what it needs to know about your project
  • put permissions in settings files, and understand why a new folder must be trusted first
  • enforce a rule with a hook, instead of hoping the model follows it
  • package a repeated task as a skill that loads only when needed
  • test a hook on its own, without any model

In Chapter 7 every run carried its rules on the command line: which commands were allowed, how to run the tests, what not to touch. A team cannot work like that. Claude Code reads its configuration from files in the repository, so the rules are written once, reviewed like code, and shared by everyone. Four files do most of the work: CLAUDE.md for knowledge, settings.json for permissions, hooks for rules that must hold, and skills for tasks you do again and again.

Everything Claude Code did in this chapter is real: it sent CLAUDE.md to the model, ignored the project’s permissions until the folder was trusted, ran the hook that blocked a push, and loaded a skill by name. The practice server played the model, and its reply about CLAUDE.md was set to appear only if CLAUDE.md’s words really arrived.

{{n}}.1 CLAUDE.md

A file named CLAUDE.md at the root of a project is read at the start of every session and sent with every request. It is the briefing a new colleague would need: how to run things, the conventions, and what never to do. The chapter’s project configures all four pieces:

Keep CLAUDE.md short and specific. Commands, conventions, the layout of the code, and the mistakes people make here; not a tutorial, not the whole architecture, not facts that change weekly. Every line is sent with every request, so every line costs tokens and attention. /init in an interactive session drafts one from your codebase; edit it down. You can also keep a personal CLAUDE.md in ~/.claude/ for your own habits across projects, and add files in subfolders for the parts of a large repository that need their own notes.



Tip
When Claude Code makes the same mistake twice, the fix is usually a line in CLAUDE.md, not a longer prompt. Write it as a rule with its reason (“money is in piastres, as integers: floats round wrongly”), commit it, and the whole team’s sessions improve at once.



{{n}}.2 Settings, and trust



Permissions live in settings files, in three places: .claude/settings.json in the project, committed, for the team; .claude/settings.local.json, not committed, for your own additions; and ~/.claude/settings.json for all your projects. The project allows exactly one command:

Claude Code ignored the project’s allow rule, and said why: the folder has not been trusted. This is deliberate. A repository you clone from the internet could otherwise allow itself any command, and an agent opening it would obey. Trust is given once, by a person, interactively, the first time Claude Code opens a folder; until then, a project’s settings cannot widen what Claude Code may do. Project {{n}}.3 trusts the folder and shows the same rule working.



Watch out
Read .claude/ before you trust a repository you did not write, as you would read a build script before running it: its settings can allow commands, and its hooks run programs on your machine.



{{n}}.3 Hooks: rules that hold



CLAUDE.md says “never push”. That is advice: the model reads it and usually follows it. Usually is not enough for some rules. A hook is a command Claude Code runs itself at a moment in the loop (before a tool runs, after it runs, when a prompt is submitted, when the session stops), whatever the model thinks. The project’s hook runs before every shell command:








The scripted model tried to push, despite CLAUDE.md, exactly the kind of slip a hook exists for. Claude Code ran the hook, the hook saw git push and exited with code 2, and the command never ran; the hook’s message went back to the model, which reported the block. A model can ignore advice; it cannot ignore a hook.



Hooks are ordinary programs, so they can do far more than block: format a file after every edit, run the tests when the session ends, add today’s on-call name to every prompt, write an audit log. Keep them fast, since they run on every matching event, and remember that they run with your permissions.

{{n}}.4 Skills



A skill is a folder with a SKILL.md: a name, a one-line description, and instructions, plus any scripts or templates the task needs. Claude Code sees only the descriptions until a task calls for a skill; then it loads the instructions. Unlike CLAUDE.md, which is sent with every request, a skill costs nothing until it is used, so a team can keep dozens.






Project {{n}}.2 runs it. The description matters more than it looks: it is what Claude reads to decide whether the skill fits the task, so write it as the situation it is for (“write release notes for the café app”), not as a title (“release helper”).



Professional habit
Review changes to CLAUDE.md, settings, hooks and skills like code, in pull requests, with someone who understands what they allow. They decide what an agent knows, may do and must not do, for everyone on the team.
