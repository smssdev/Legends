1. Most people settle on /clear (a fresh context for each task), /compact (a long session summarised so it can continue) and /model (a faster or a stronger model for the task at hand), with /permissions close behind. The list changes between versions; /help is always the current one.
  2. In plan mode Claude Code does not run commands that change or execute anything: the Bash call is denied, and the run’s summary shows one denial. The exact message depends on your version and settings. A good reply then proposes a plan (“run node --test, read the failure, fix total”) for you to approve, instead of claiming results it does not have; with the practice server, the scripted reply for this task assumes the tests ran, so its answer here describes a failure nobody saw: a reminder to read what any model says against what actually happened in the run.
  3. For example --allowedTools "Bash(npm test)" "Bash(npm run lint)": two exact commands. If your test script takes arguments you need, allow those forms explicitly too. Keep the list in the team’s settings file (Chapter 8) so everyone gets the same rules.
  4. Record Date.now() as each line arrives and print the difference from the previous one. With a real model, most of the time is usually in the model’s turns (thinking and writing); with a slow test suite or a large build, the tools dominate. Either answer tells you where to look when a task is slow: a smaller model or lower effort, or faster tests.
  5. Run claude -p "$TASK" --output-format json > runs/$(date +%Y%m%d-%H%M%S).json, then read the file with a few lines of Node and append date,task,subtype,num_turns,total_cost_usd to runs.csv. After a week you would see what typical tasks cost, which tasks take many turns, and how often runs end in something other than success: the numbers to bring to a conversation about budgets, and the tasks to give clearer instructions.
