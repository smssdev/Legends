Chapter {{n}}

Claude Code in the Terminal

In this chapter you will learn to

  • install Claude Code, sign in, and choose between the interactive and the print mode
  • watch the agent loop: what Claude says, which tools it calls, what comes back
  • control what Claude Code may do, with permissions and allowed tools
  • read Claude Code’s JSON output: the result, the turns and the cost
  • put a hard limit on what a run may spend

Part I used Claude in a window, and you carried the code to and from it. Claude Code works where the code is: in your terminal, inside your repository. It reads files, searches them, runs commands, edits code and checks its own work, in a loop, until the task is done or it needs you. That makes it the most powerful way to use Claude for software, and the one where permissions matter most.

The Claude Code in this chapter is real, version 2.1.331, running on the book’s machine. Only its model is the practice server: the replies are scripted, but the file it reads, the tests it runs, the command it is refused, its cost accounting and its spending limit are all Claude Code’s own behaviour.

{{n}}.1 Install and sign in

Claude Code is a command-line program. Anthropic’s documentation lists the ways to install it (a native installer, a package for your system, or npm); with Node.js already on your machine, npm is the shortest:

npm install -g @anthropic-ai/claude-code
claude --version



The first time you run claude, it asks you to sign in, with a Claude subscription or with a Claude Console account that pays per token through an API key. It also runs in editors such as VS Code and JetBrains, in the desktop app and on the web; it is the same agent in each, and this part of the book uses the terminal because there everything is visible.



Did you know?
Claude Code reads the same ANTHROPIC_BASE_URL and ANTHROPIC_API_KEY variables as the SDK. That is how this chapter points it at the practice server, and how companies route it through their own gateway or a cloud provider.



{{n}}.2 Two ways to run it



Run claude in a project folder and you get an interactive session: you type, Claude works, and you can steer it, approve its actions and type commands that start with a slash: /help for the list, /model to change the model, /clear to start fresh, /compact to summarise a long session and continue, /permissions to see what is allowed. This is how you will use it most of the time.



Run claude -p with a prompt and you get the print mode: one task, no questions, the answer on standard output. It is how scripts, CI jobs and this book use Claude Code:

{{n}}.4 Permissions



Claude Code’s tools fall into two groups. Reading (files, searches, the list of files) is allowed by default. Anything that changes something or runs something (editing files, running commands, fetching from the web) needs permission, given once, for a session, or by rule. A rule names a tool and, for commands, the command:






--allowedTools "Bash(node --test)" allows exactly that command, and nothing else: not node --test --watch, not rm. This time the tests ran, for real, and their real result went back to the model: the round bill passes, the bill with piastres fails, the same parseInt bug as Chapter 4. The same rules can live in a settings file, for you or for the whole team (Chapter 8).



Permission modes change the default for a whole session: default asks for each action; acceptEdits lets Claude edit files without asking but still asks before commands; plan lets it read and plan but not change anything, which is the right start for a large task. And there is a mode that skips all permission checks: it exists for throwaway sandboxes, and has no place on a machine with your keys, your email and your company’s code.



Watch out
Allow commands by name, not by pattern you have not thought through. Bash(npm test) is a decision; Bash(*) is giving away the decision. A repository can contain instructions in a README or an issue, written for AI agents to find, and the commands you allowed are what such instructions can reach.

{{n}}.5 What a run costs



With --output-format json, print mode returns one JSON object at the end: the result, the number of turns, the token usage and the cost. A script keeps what it needs:








Two turns (reading the file, then answering), about seven cents. Look at the tokens: twelve thousand written to the cache, twelve thousand read from it, and almost nothing else. Before your prompt says a word, Claude Code sends its own instructions and the descriptions of its tools, and that is most of every request. Caching makes the second turn cheap; the first still pays to write the cache. The practice server counts tokens approximately, so the real figures will differ, but the shape does not: an agent’s fixed context is a large part of its cost, and the cost is per turn.



Tip
On a subscription, Claude Code’s usage counts against your plan’s limits rather than a bill; with an API key, every turn is billed. Either way, /cost in an interactive session and the JSON output in print mode tell you what a task used. Look after a few tasks, and you will know what your work costs.

Summary



    

  • Claude Code is an agent in your terminal: it reads, searches, runs and edits, in a loop, inside your project.
    • 

  • Interactive sessions are for working with it; print mode (-p) is for scripts, with text, JSON or a stream of events.
    • 

  • Reading is allowed by default; changing and running need permission, given exactly, by rule or by mode.
    • 

  • Every run reports its turns, tokens and cost; an agent’s own instructions are a large, cached part of every turn.
    • 

  • A spending limit stops a runaway loop, after the turn that crosses it.
    •
