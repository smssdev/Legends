Chapter 16

Accessible Pages for Everyone

In this chapter you will learn to

  • explain what accessibility is and who it helps
  • use the right HTML element, the single most important accessibility skill
  • make pages that work with a keyboard, with visible focus and a skip link
  • write accessible forms, images and colours, and measure contrast yourself
  • check a page with the browser’s own tools

More than a billion people live with some form of disability. Some cannot see the screen and listen to a screen reader. Some cannot use a mouse and move through pages with a keyboard or a switch. Some need large text, strong colours, or pages that do not move. And all of us are “temporarily disabled” sometimes: with a broken arm, in bright sunlight, holding a baby in one hand. Accessibility, often written a11y, means building pages that work for all of them.

Here’s the good news: if you use HTML the way Chapter 5 taught you, most of the work is already done! Accessibility is not an extra feature you add at the end; it’s a habit you build into every page from the start.

The international standard is the Web Content Accessibility Guidelines (WCAG). Many countries require it by law for government sites and large companies, so accessible code is also a professional requirement. But the best reason is simpler: it is the right thing to do, and it makes pages better for everyone.

16.2 The right element for the job

Look at these two buttons:





The <div> works with a mouse, and nothing else. You cannot reach it with the Tab key, Enter does nothing, and a screen reader announces it as plain text, so a blind user never learns that there is something to press. The <button> gets all of that for free: it can be focused, it responds to Enter and Space, and it is announced as “button”.



Professional habit: HTML first
If something navigates to another page, use <a href>. If it does something on this page, use <button>. Use headings in order, lists for lists, <nav>, <main> and <footer> for the parts of the page. Every semantic element brings built-in behaviour that you would otherwise have to rebuild by hand, and would probably get wrong.



When HTML alone is not enough, ARIA attributes add information for assistive technology, such as aria-label to name a button that only shows an icon. But the first rule of ARIA is: do not use ARIA if a native HTML element does the job. A wrong ARIA attribute is worse than none.



16.3 The keyboard test



Put your mouse away and try to use your page with the keyboard only. Tab moves forward through links, buttons and fields, Shift + Tab moves back, Enter follows links and presses buttons, and Space presses buttons and ticks boxes. Two things must be true:



    

  1. You can reach and use everything.
    2. 

  2. You can always see where you are. The element that has the keyboard focus must be clearly visible.
    3. 









    

  • :focus-visible styles the focus when the user is using the keyboard. Never remove the outline with outline: none unless you replace it with something at least as visible.
    • 

  • The skip link is the first thing on the page. It stays hidden until it is focused, and lets keyboard and screen reader users jump past the menu straight to the content, instead of tabbing through every link on every page.
    • 

  • prefers-reduced-motion is a media query that is true when the user has asked their system for less motion. Use it to turn off animations.
    • 




16.4 Text for images



You met alt in Chapter 5. Here is how to write it well:





ImageGood alt



A photo in a news storyWhat it shows and why it matters: “Fans celebrating in Tahrir Square after the final”


A logo that links to the home pageWhere it goes: “Bit’s Shop, home page”


An icon on a button with no textWhat the button does: “Search”


A purely decorative patternEmpty: alt=""






Do not start with “image of”; screen readers already say it is an image. Describe the purpose, not every pixel.



16.5 Accessible forms







    

  • Every field has a visible <label>. A placeholder is not a label: it disappears when you type.
    • 

  • aria-describedby connects the hint and the error to the field, so screen readers read them when the field gets focus.
    • 

  • aria-invalid="true" tells assistive technology the value is wrong, and role="alert" makes screen readers announce the error at once.
    • 

  • The error is shown in text, not only by turning the border red. People who cannot see red would never notice.
    • 

  • autocomplete lets browsers fill in known values, a big help for people who find typing hard.
    • 




16.6 Colour and contrast



WCAG asks for a contrast ratio of at least 4.5 to 1 between normal text and its background, and 3 to 1 for large text. The ratio goes from 1 (the same colour) to 21 (black on white). Our dark ink and our brand indigo pass easily on white. The light grey, often used for “elegant” small print, fails, and white text on bright yellow is almost unreadable. You do not need to remember the formula; the point is that contrast is a number you can check, not a matter of taste.



Watch out: never rely on colour alone
About one man in twelve has some form of colour blindness. A form that shows errors only in red, or a chart that tells lines apart only by colour, leaves them guessing. Always add text, an icon, or a pattern as well.



16.7 Checking your pages



Automatic tools find many problems quickly:


    

  • In Chrome or Edge, open DevTools, choose the Lighthouse panel, tick Accessibility and click Analyze. You get a score and a list of problems with explanations.
    • 

  • The Elements panel has an Accessibility pane that shows how a screen reader understands any element: its role and its name.
    • 




But automatic tools find only part of the problems. Always add two manual tests: use the page with the keyboard only, and turn on your system’s screen reader for a few minutes (VoiceOver on Mac and iPhone, Narrator on Windows, TalkBack on Android). Hearing your own page read aloud is an unforgettable lesson.

Summary



    

  • Accessibility makes pages work for people with all kinds of abilities, and better for everyone.
    • 

  • Use the right HTML element: <button> for actions, <a> for links, headings and landmarks for structure. ARIA only when HTML is not enough.
    • 

  • Everything must work with the keyboard, with a clearly visible focus. Add a skip link.
    • 

  • Write alt for purpose; use alt="" for decoration.
    • 

  • Forms need visible labels, connected hints and errors in text.
    • 

  • Normal text needs a contrast ratio of at least 4.5:1. Never use colour alone.
    • 

  • Test with Lighthouse, the keyboard, and a real screen reader.
    • 




Quick check answers: 1. It can be reached with Tab, works with Enter and Space, and screen readers announce it as a button; a <div> does none of this. 2. At least 4.5 to 1 (3 to 1 for large text). 3. It lets keyboard and screen reader users jump past the navigation straight to the main content.




Practice projects



For each project, do the keyboard test from section 16.3 before you call it finished: put the mouse away and use only Tab, Shift+Tab, Enter and Space. If you can do everything, and always see where you are, you are on the right track.

Rescue a recipe card

Project 16.2 · Medium


A form that explains its errors


When the visitor makes a mistake, tell them what went wrong, where, and how to fix it, in a way that both eyes and screen readers notice.


You will practise: label, autocomplete, aria-describedby, aria-invalid, role="alert", and moving the focus with JavaScript.


    

  1. Build the form with a label for every field, and add novalidate so your script, not the browser, shows the messages.
    2. 

  2. Under each input, add an empty <p class="error">, and link it to the input with aria-describedby. The screen reader will read it with the field.
    3. 

  3. Keep the rules as data: an array of { id, message, ok }, where ok is a small function that tests the value.
    4. 

  4. On submit, check every rule. Write the message, and set aria-invalid="true" on each field that fails.
    5. 

  5. Fill a summary box at the top with a link to each problem, show it, and call summary.focus(). Because it has role="alert", it is announced at once.
    6. 

  6. When everything is correct, hide the summary and show a success message in a role="status" element.
    7. 



Hint: never use colour alone for errors. Here the message has words, the border changes, and the summary repeats it, so people who cannot see red still know what to do.








Project 16.3 · Challenge


An accessible FAQ


Build questions that open and close their answers, and that tell assistive technology whether each one is open.


You will practise: buttons inside headings, aria-expanded, aria-controls, the hidden attribute, and querySelectorAll.


    

  1. For each question write an h2 containing a <button type="button" aria-expanded="false" aria-controls="answer-1">.
    2. 

  2. Below it, put the answer in <div id="answer-1" hidden>. hidden hides it from everyone, screen readers included.
    3. 

  3. Find all the buttons with querySelectorAll and give each a click listener.
    4. 

  4. On click, read aria-expanded, flip it, and set the answer’s hidden to match.
    5. 

  5. Draw the + and − with CSS from the attribute itself: button[aria-expanded="true"]::after. Now the look can never disagree with what the screen reader says.
    6. 

  6. Test it with only the keyboard: Tab to a question, press Enter or Space, and Tab into the open answer.
    7. 



Hint: because you used real buttons, Enter and Space work with no extra code. A div with a click listener would need a dozen lines to copy what <button> gives you free.
