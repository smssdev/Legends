Chapter 14

Reading Errors and Debugging

In this chapter you will learn to

  • read an error message and find exactly where the problem is
  • recognise the three most common kinds of error
  • follow a stack trace back to the real cause
  • find bugs that give no error at all, with console.log and the debugger
  • use a calm, step-by-step method that works for any bug

Every programmer, from the first day to the fortieth year, spends a large part of their time fixing things that do not work. The difference between a beginner and a professional is not that the professional makes fewer mistakes. It is that the professional is not afraid of them, reads what the computer is saying, and follows a method. By the end of this chapter, red text in the terminal will feel like a helpful note, not a disaster.

Here is the most important sentence in this chapter: the error message is trying to help you. It usually says what went wrong and exactly where. Most beginners panic and stop reading after the first word. Let’s read the whole thing together!

14.1 Anatomy of an error message

Here is a small program with a typo, and what Node.js says when you run it:








Node.js told us: in the file reference.js, on line 2, at the place marked by the ^, there is a ReferenceError: scor is not defined. That is everything you need. You look at line 2, see scor, and realise you meant score. The browser console shows the same information, with the file name and line number as a link you can click.



14.2 The three errors you will meet most



ReferenceError: something does not exist



You used a name that JavaScript does not know, as above. The cause is almost always a typo, a variable used outside its scope (Chapter 10), or something used before it was created.



TypeError: the right name, the wrong kind of value








This is the most common error in all of JavaScript. You tried to read name from undefined, which has no properties. In real programs, user is undefined because a find found nothing, a server returned no data, or a property name was misspelled. The question to ask is: “why is this value undefined, when I expected an object?”



SyntaxError: the code is not valid JavaScript








A SyntaxError happens before anything runs: JavaScript cannot even understand the code. Here, the array opened with [ was never closed with ]. With syntax errors, the real mistake is often a little before the place marked: a missing bracket, quote or comma. VS Code underlines most of them in red as you type, before you even run the code.

14.3 Stack traces: how did we get here?



In bigger programs, functions call functions that call other functions. When an error happens deep inside, Node.js prints a stack trace: the path of calls that led to the error.








Read the lines starting with at from top to bottom: the error happened in getCity (line 2), which was called by welcome (line 6), which was called from the main code (line 9). The error is in getCity, but the cause is where the data came from: the user object on line 9 has no address. Stack traces let you walk backwards from the symptom to the cause.



Tip
In real projects, stack traces also contain many lines from libraries and from Node.js itself. Look for the first lines that point to your files; that is almost always where to start.

The hardest bugs do not produce any error. The program runs and gives the wrong answer:








No red text, but 16.67 is not 20. When nothing tells you where the problem is, you make the program tell you. The simplest tool is console.log: print the values you are unsure about, at the moments you are unsure about them.

Better console tools








Give every log a label, so you know which line printed what. Use console.table for arrays of objects, and console.error for problems; in the browser it is shown in red with a stack trace. And remember to remove your debugging logs when the bug is fixed.



14.5 The debugger: pausing time



console.log shows a few values at a few moments. The debugger lets you pause the program at any line and look at everything. In the browser, open DevTools, go to the Sources panel, open your file and click a line number. A blue marker appears: a breakpoint. The next time that line runs, the page freezes there.





While paused, you can hover over any variable to see its value, look at all of them in the Scope pane, and press Step to run one line at a time and watch the values change. You can also write the word debugger; in your code; when DevTools is open, the program pauses there. VS Code has the same tools for Node.js programs, in its Run and Debug view.



14.6 A method for any bug



When something is wrong, resist the urge to change things at random. Follow these steps instead:



    

  1. Reproduce it. Find the exact steps that make the bug happen every time.
    2. 

  2. Read the error, all of it, from the bottom: what happened, and where.
    3. 

  3. Form a guess. “I think user is undefined because find found nothing.”
    4. 

  4. Test the guess with a console.log or a breakpoint, not by changing code blindly.
    5. 

  5. Fix the cause, not the symptom, then run the program again, with unusual cases too.
    6. 




Professional habit: rubber duck debugging
Many programmers keep a small toy, often a rubber duck, on their desk. When they are stuck, they explain the code to it, line by line, out loud. Very often, halfway through the explanation, they hear themselves say the mistake. It sounds silly and works astonishingly well. (Bit is also happy to listen.)

Summary



    

  • Error messages say what went wrong and where: the file, the line and the position. Read all of it.
    • 

  • ReferenceError: the name does not exist. TypeError: the value is the wrong kind, often undefined. SyntaxError: the code is not valid.
    • 

  • A stack trace lists the calls that led to the error; walk back from the symptom to the cause.
    • 

  • For bugs without errors, make the program show its values with labelled console.log, console.table and console.error.
    • 

  • The debugger pauses at breakpoints so you can inspect and step through code.
    • 

  • Method: reproduce, read, guess, test the guess, fix the cause.
    • 




Quick check answers: 1. Some code tried to read .price from a value that is undefined; find out why that value is missing. 2. The first line that points to one of your own files. 3. console.log with labels (or a breakpoint) to see the values step by step.




Practice projects: bug hunts



In this chapter the projects are reversed: the code is already written, and it is broken. Type each program as it is, run it, and see the bug for yourself. Then use the method from section 14.6 (read, reproduce, narrow down, fix, test) until your output matches the fixed one. Professionals spend more time doing this than writing new code.

The greeting that will not start

You will practise: reading an error message from top to bottom: the line, the caret, the type and the description.






    

  1. Find the type of error. A ReferenceError means “I do not know this name”.
    2. 

  2. Find the line and the caret ^: they point at the exact name JavaScript could not find.
    3. 

  3. Compare that name, letter by letter, with the variable you created at the top. JavaScript is case-sensitive.
    4. 

  4. Fix it, run the program again, and make sure the output below appears.
    5. 



Hint: most errors you will ever meet are typos. Your editor can help: when you click on a variable, it highlights every place with the same name. A name that does not light up is a typo.

Project 14.3 · Challenge


The order that breaks the list


The first order prints, then the program dies. Follow the stack trace back to the cause, and fix it so every order prints.


You will practise: reading a stack trace, finding bad data rather than bad code, and guarding against missing values.






    

  1. Read the stack from the top: the crash is in label, which was called by printAll, which was called from line 17.
    2. 

  2. The message says it could not read name of undefined. So in order.customer.name, the undefined is order.customer.
    3. 

  3. One order printed before the crash, so the problem is the second order. Look at the data: order 2 has no customer.
    4. 

  4. Decide what should happen. Here a missing customer is a guest, so add an if (!order.customer) at the start of label and return a “guest” line.
    5. 

  5. Run again. All three orders should print, and the program should finish normally.
    6. 



Hint: the line that crashes is often not the line that is wrong. The code in label was fine; the data was not what it expected. Real data from users and servers is always missing something, so professionals check before they read deep inside an object.
