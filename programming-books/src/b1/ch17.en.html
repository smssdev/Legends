Project: Build and Publish a Web App

This is the chapter where everything comes together. You will build a real app that you can use every day: a list of daily tasks that you can add, tick off, filter and delete, and that remembers everything when you close the browser. This is my favourite chapter! At the end of it, you won’t just have learned to code. You’ll have shipped something: a real app, live on the web, built by you from nothing. Let’s go!

17.1 Plan first

Chapter 2 taught you to think before you type. Professionals start every project the same way: they write down what the app must do, sketch how it will look, and decide what data it needs.

What the app does

  1. Add a task by typing it and pressing Enter or the Add button.
  2. Tick a task to mark it as done, and untick it again.
  3. Delete a task.
  4. Show all tasks, only the tasks still to do, or only the finished ones.
  5. Show how many tasks are left, and clear all finished tasks at once.
  6. Remember everything after the browser is closed.
  7. Work with a keyboard, on a phone, and in English or Arabic.

A sketch

The data

Each task needs a unique id, its text, and whether it is done. The whole app’s data is an array of these objects, plus the current filter:

[
  { id: 1741766400000, text: "Read chapter 17", done: true },
  { id: 1741766460000, text: "Practise Flexbox", done: false }
]

Everything else on the screen, the list, the counter and the highlighted filter, can be calculated from this data. That decision will make the code simple.

17.3 The CSS



The stylesheet uses custom properties, Flexbox, rounded corners and visible focus, all from Chapters 6 and 7. It uses no physical directions, so the same file styles the Arabic version. It is in the book’s code repository as style.css; here are the most interesting parts:



form {
  display: flex;
  gap: 8px;
}
form input {
  flex: 1;                /* the input takes all the free space */
}
.filters button[aria-pressed="true"] {
  color: white;           /* the active filter is styled from */
  background: var(--brand); /* the same attribute screen readers use */
}
li.done label {
  color: var(--muted);
  text-decoration: line-through;
}



Styling the active filter with [aria-pressed="true"] is a neat professional trick: the look and the accessibility information can never disagree, because they are the same attribute.



17.4 The JavaScript



The program follows the pattern from Chapter 12: data, changes, display, and events. Read it section by section:






Remembering data: localStorage



Variables disappear when the page is closed. localStorage is a small storage space that each website gets in the browser, and it survives reloads and restarts. It stores only strings, so we use JSON from Chapter 11:


    

  • save() turns the tasks into JSON and stores them under the key "my-tasks".
    • 

  • load() reads them back when the page opens, or starts with an empty array the very first time.
    • 

  • Every change goes through update(), which saves and then redraws. Because there is only one path, the screen and the storage can never get out of step.
    • 




Watch out
localStorage belongs to one browser on one device. Tasks added on your phone will not appear on your laptop, and clearing the browser’s data deletes them. Syncing between devices needs a server and a database, which is exactly what the backend books in this series teach.



Other details worth noticing


    

  • Date.now() returns the number of milliseconds since 1970, a simple way to get a unique id.
    • 

  • tasks.filter(…) creates new arrays for deleting and clearing, which is simpler and safer than removing items from the middle of an array.
    • 

  • replaceChildren(...visibleTasks().map(taskItem)) redraws the whole list in one line: the spread syntax from Chapter 11 passes every new <li> at once.
    • 

  • Every task has a real checkbox with a <label>, so clicking the text ticks the box, and the delete button has an aria-label that says which task it deletes.
    •

17.6 Publish it with GitHub Pages



GitHub Pages is a free service that turns a GitHub repository into a website. Because your app is just HTML, CSS and JavaScript, with no server code, it can be hosted there in a few minutes:



    

  1. Put the my-tasks folder under Git and commit, as in Chapter 15.
    2. 

  2. Create a public repository called my-tasks on GitHub and push to it.
    3. 

  3. On the repository page, open Settings, then Pages.
    4. 

  4. Under Build and deployment, choose Deploy from a branch, select the branch main and the folder / (root), and click Save.
    5. 

  5. Wait a minute and reload. GitHub shows your address: https://your-username.github.io/my-tasks/.
    6. 




Open that address on your phone. That is your app, on the internet, served over HTTPS, built by you. From now on, every time you push a new commit to main, GitHub updates the site automatically.



Tip
The main page of a site must be called index.html; that is the file a web server sends when the address ends with a folder name. That is why we named our file that way from the start.



Send the link to a friend and ask them to add a task. Watching someone else use something you made is one of the best feelings in programming. You did it!



17.7 Ideas to keep going



The best way to keep learning is to keep building. Here are improvements, roughly from easy to hard:


    

  • Edit a task by double-clicking its text.
    • 

  • Add a due date to each task, and sort by it.
    • 

  • Add a dark theme that follows the system setting with prefers-color-scheme.
    • 

  • Drag tasks to reorder them.
    • 

  • Add a language switch that changes all the app’s texts between English and Arabic, and sets lang and dir.
    • 




Summary



    

  • Plan before coding: list the features, draw a sketch, and design the data.
    • 

  • Calculate everything on the screen from the data, and send every change through one function that saves and redraws.
    • 

  • localStorage keeps strings in the browser across reloads; store objects as JSON.
    • 

  • Build accessibility in from the start: real forms, buttons, labels and visible focus.
    • 

  • Test the empty state, unusual input, persistence, keyboard, phone width and the Console before publishing.
    • 

  • GitHub Pages publishes a static site from a repository for free.
    •
