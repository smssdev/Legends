Chapter 15

Git and GitHub

In this chapter you will learn to

  • explain what version control is and why every developer uses it
  • save snapshots of your project with git add and git commit
  • look at the history, see what changed and undo mistakes
  • work on new features safely in branches
  • put your project on GitHub and understand how teams work together

Have you ever saved files called profile-final.html, profile-final-2.html and profile-REALLY-final.html? Professional developers had the same problem, and they solved it with a tool called Git. Git remembers every version of every file in your project, lets you go back to any of them, and lets many people work on the same code at the same time. It is used by almost every software team in the world.

Git is like the save points in a video game. Before trying something risky, you save. If it goes wrong, you load the last save and try again. Except with Git, you keep every save, forever, with a note about what you did!

15.1 What is version control?

A version control system records changes to files over time. With it you can:

  • see exactly what changed, when, and why;
  • go back to any earlier version when something breaks;
  • try new ideas without risking the working version;
  • combine the work of several people without overwriting each other.

Git is the version control system that almost everyone uses today. It is free, it runs on your own computer, and it works even without the internet. GitHub is a website that stores Git projects online, so you can back them up, share them and work on them with others. Git is the tool; GitHub is one of the places to keep what Git records.

15.3 Your first commit



A Git project is called a repository, or repo. A snapshot of the project is called a commit. Making a commit takes two steps: first you choose which changes go into it, then you save them with a message.





Here is the whole process for the profile site from Chapter 7, run in its folder:






    

  • git init turns the folder into a repository. It creates a hidden .git folder where the history lives; never edit it by hand.
    • 

  • git status is the command you will type most. --short gives a compact view: ?? means a new file Git does not track yet, A means added to the staging area.
    • 

  • git add puts changes into the staging area. git add . adds everything in the folder.
    • 

  • git commit -m "…" saves the snapshot. Git gives it an id, here 96c0a17, which you can use to find it later.
    •

Now edit index.html, add a line, and ask Git what changed:






git diff shows the changes you have not committed yet: lines starting with + were added, lines with - were removed. git commit -am adds all changed tracked files and commits in one step. git log --oneline shows the history, one commit per line.

Watch out
git restore on a file throws away your uncommitted changes to it, and Git cannot bring them back, because they were never saved. Commit often, and these accidents become impossible to lose.



15.5 Branches



A branch is a separate line of work. The main branch, main, holds the version that works. When you start a new feature, you create a branch for it, work and commit there freely, and when it is ready you merge it back into main:








git switch -c contact creates a branch called contact and moves to it. Commits made there do not touch main: when you switch back, contact.html disappears from your folder, and reappears when you switch to contact again. git merge contact brings the branch’s commits into main. Because main had not changed in the meantime, Git simply moved it forward, which it calls a fast-forward.



Tip: merge conflicts
If two branches change the same line differently, Git cannot guess which version you want and reports a conflict. It marks the place in the file with <<<<<<<, ======= and >>>>>>>. Don’t panic: edit the file to keep the right version, delete the markers, then git add and git commit. VS Code shows conflicts with buttons that make this easy.



15.6 GitHub: your code online



Create a free account on github.com, click New repository, give it a name, and leave it empty. GitHub then shows you its address. Connect your local repository to it and send your commits:






    

  • A remote is a copy of the repository somewhere else. By tradition the main one is called origin.
    • 

  • git push sends your commits to the remote. The first time, -u origin main remembers where to push, so afterwards plain git push is enough.
    • 

  • git clone downloads a whole repository, with its history, onto another computer.
    • 

  • git pull brings down commits that others (or you, on another computer) have pushed.
    • 




The first time you push, Git asks you to sign in to GitHub. Follow the instructions in the browser window it opens; GitHub no longer accepts your account password directly in the terminal.



Files that should not be in Git



Some files do not belong in a repository: downloaded packages that can be reinstalled, system files, logs, and above all secrets such as passwords and API keys. List them in a file called .gitignore and Git will never track them:






Watch out: never commit secrets
Anything you push to a public repository can be read by anyone, and automated bots scan GitHub for keys within minutes. Deleting the file in a later commit is not enough: it stays in the history. If you ever push a secret by mistake, change that password or key immediately.



15.7 How teams work together



On a team, nobody commits straight to main. Instead, each change follows the same path:



    

  1. Create a branch for the change, and commit there.
    2. 

  2. Push the branch to GitHub.
    3. 

  3. Open a pull request (PR): a page on GitHub that shows the changes and asks for them to be merged.
    4. 

  4. Teammates review the code, comment, and ask for improvements. Automatic checks run the tests.
    5. 

  5. When everyone is happy, the PR is merged into main.
    6. 




This way, every line in main has been seen by at least two people. Code review is one of the best ways to learn: you will learn as much from reading others’ pull requests as from writing your own.



Professional habit: good commit messages
Write commit messages for the person who will read the history in a year. Start with a short summary in the imperative, as if giving an order: “Add contact section”, “Fix price for children”, not “stuff” or “changes”. Make each commit one logical change. Small, well-described commits make bugs easy to find and easy to undo.

Practice projects



Git is learned with your fingers, not your eyes. Open a terminal and type every command yourself. The sessions below are real: Git printed exactly this. Your commit ids will be different, because they depend on your name and the time; everything else should match.





Project 15.1 · Easy


A learning journal under version control


Start a repository for a journal of what you learn, and save one commit per day.


You will practise: git init, add, commit, commit -am, log --oneline and show.


    

  1. Make a new folder called journal, open it in VS Code, and run git init in its terminal.
    2. 

  2. Create journal.md with a heading. Add it and make your first commit.
    3. 

  3. Each day, add one line about what you learned and commit it with a short message. -am adds and commits in one step, but only for files Git already tracks.
    4. 

  4. Read your history with git log --oneline.
    5. 

  5. Look inside the last commit with git show --stat. Then try plain git show to see the exact line you added.
    6. 



Hint: keep this journal for the rest of the book. In a few weeks, git log will be a diary of your progress, and the habit of small, frequent commits is exactly what teams expect.









Project 15.2 · Medium


Two ways to undo


Make two mistakes on purpose, one not yet committed and one already committed, and undo each with the right tool.


You will practise: git status --short, git restore for uncommitted changes, and git revert for commits.


    

  1. Replace the whole contents of journal.md with one silly line, and save. git status --short shows M: modified.
    2. 

  2. Run git restore journal.md. The file goes back to the last commit, and the status is clean again.
    3. 

  3. Write Day 3 properly and commit it.
    4. 

  4. Now create quote.md, add it and commit it. Pretend you regret this commit.
    5. 

  5. Run git revert --no-edit HEAD. Git makes a new commit that does the opposite, and the file disappears.
    6. 

  6. Read git log --oneline: the mistake and its undo are both in the history, so nobody is surprised.
    7. 



Hint: restore throws away work that was never saved, so there is no way back; use it with care. revert is always safe, even after you have pushed, because it adds history instead of erasing it.









Project 15.3 · Challenge


Create a merge conflict, then solve it


Conflicts frighten beginners only until they have solved one. Create one on purpose, read it, and resolve it calmly.


You will practise: branches, git switch -c, fast-forward and real merges, conflict markers, and finishing a merge.


    

  1. On main, add a title line at the top of the journal and commit it.
    2. 

  2. Create a branch personal, change the title, and commit. Go back to main.
    3. 

  3. Create a second branch ambitious from main, change the same title line differently, and commit. Go back to main.
    4. 

  4. Merge personal: it is a fast-forward, because main had not moved. Then merge ambitious: Git cannot choose between two changes to the same line, so it stops.
    5. 

  5. Open the file. Between <<<<<<< and ======= is your version (HEAD); between ======= and >>>>>>> is the incoming one.
    6. 

  6. Write the line you really want, delete all three marker lines, then git add and git commit. The graph shows the two branches joining.
    7. 



Hint: a conflict is not an error. It is Git politely asking a human to decide. VS Code shows buttons above each conflict (“Accept Current”, “Accept Incoming”, “Accept Both”), but always read the result before you commit.
