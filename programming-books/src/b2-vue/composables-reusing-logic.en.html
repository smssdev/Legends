Chapter {{n}}

Composables: Reusing Logic

In this chapter you will learn to

  • move stateful logic out of components into composables, and give it a name
  • decide whether each caller gets its own state or everyone shares one
  • accept values, refs and getters as inputs, with toValue
  • write async composables that cancel stale work, and composables that clean up after themselves
  • use VueUse instead of writing common composables yourself
  • test composables without any component

Components are good at reusing pieces of the screen. But much of the code in a component is not about the screen: a timer, a search that cancels old requests, the state of the network, a value saved in the browser. When two components need the same behaviour, copying it means fixing every bug twice. Vue’s answer is the composable: a plain function that uses the Composition API, keeps its own reactive state, and returns it. It is the main way Vue apps share logic, and the idea behind most of the Vue ecosystem.

The rule of thumb I use: when a <script setup> needs a comment to explain what a group of refs and watchers are doing together, that group wants to be a composable with a name.

Watch out: a computed sees only reactive reads
The first version of this composable had const running = computed(() => timer !== undefined && …), where timer was a plain let. Vue cannot track a plain variable, so the computed sometimes kept an old answer, and the screen showed “Start” on a running stopwatch. Anything a computed or a template depends on must be reactive. A plain let is fine only for values the screen never shows, like the interval’s id here.



{{n}}.2 Own state or shared state?



Because a composable is just a function, where you create the refs decides who shares them:












Refs created inside the function are new for every call: the usual case. Refs created outside, at the top of the module, exist once, so every caller shares them. That is a quick way to share state, but use it with care: it is shared by the whole app, it is hard to reset in tests, and in server rendering (Chapter {{n+11}}) it would even be shared between different users’ requests. For real app-wide state, Chapter {{n+3}} introduces Pinia.



{{n}}.3 Inputs: values, refs or getters



A useful composable accepts its inputs in whatever form the caller has them. MaybeRefOrGetter<T> means “a plain value, a ref, or a function that returns the value”, and toValue reads any of them. Watching () => toValue(source) then reacts to changes, whichever form was passed:






useDebounced returns a copy of a value that changes only after the original has stopped changing for a while. It is what you want between a search box and a server: the user types “bit”, and the server is asked once, not three times. The cleanup cancels the waiting timer each time a new letter arrives.



{{n}}.4 An async composable



Composables shine for asynchronous work, because all the hard parts can be solved once: loading and error states, and above all, ignoring answers to questions nobody is asking any more:








The third argument of a watch callback, onCleanup, works like onWatcherCleanup: before the watcher runs for a new query, the old request is aborted. An aborted request is not an error, so the catch checks for that and stays quiet. Composables also compose: the page passes the debounced query to the search, and neither composable knows about the other.

{{n}}.5 Composables that clean up after themselves



Listening to the browser is a classic source of leaks: a listener added in a component and never removed keeps running, and keeps the component in memory, long after the user has left the screen. A small composable makes the mistake impossible:












Notice that useOnline is built on useEventListener. Small composables become the building blocks of bigger ones, the same way small components do.



Watch out: call composables at the top of <script setup>
A composable registers its watchers and cleanup with the component that is being set up right now. Called later, inside a click handler or after an await, there is no such component: the watchers are never stopped and onScopeDispose warns. Call composables at the top level, synchronously, and use the functions they return later.



{{n}}.6 VueUse

VueUse is a free library of more than two hundred of them, well tested, typed, and with the cleanup already done. {{n}}.7 Testing composables



Because composables are functions, they can be tested without rendering anything. Two tools make it easy: Vitest’s fake timers, which move time forward instantly, and effectScope, which plays the role of a component, so cleanup runs when the test calls scope.stop():










Five seconds of stopwatch and a third of a second of typing, tested in a few milliseconds. Logic that lived in a component could only be tested by rendering the component and clicking it; as a composable, it is tested directly.



Professional habit: a composable has one job
Name each composable after the one thing it does: useStopwatch, useSearch, useOnline. When a name needs “and”, split it. Return only what callers need, as readonly where they should not write, and document what it cleans up.

Summary



    

  • A composable is a use… function that uses the Composition API and returns reactive state and functions.
    • 

  • Refs created inside are per call; refs at module level are shared by the whole app.
    • 

  • Accept inputs as MaybeRefOrGetter and read them with toValue. Return readonly refs where callers should not write.
    • 

  • Async composables handle loading, errors and cancel stale work in their cleanup.
    • 

  • Register cleanup with onScopeDispose, and call composables synchronously in <script setup>.
    • 

  • Use VueUse for general needs, and test composables directly, with fake timers and effectScope.
    • 




Quick check answers: 1. No: seconds is created inside the function, so each call makes its own ref. 2. A plain string, a ref containing a string, and a function that returns a string. 3. Because the user did nothing wrong: the request was cancelled on purpose, because a newer one replaced it.




Practice projects



For each composable, write its signature and a test before its body: what it takes, what it returns, and what it cleans up. If the test is hard to write, the design is usually wrong.

Project {{n}}.3 · Challenge


An endless list


A product list that loads the next page by itself when the user scrolls near the end, with a button as a fallback, and without loading the same page twice.


You will practise: IntersectionObserver, template refs passed to composables, async state, and accessible loading.


    

  1. Write useIntersection(target, callback), where target is a template ref. Create the observer when the element exists, and disconnect it in the cleanup.
    2. 

  2. Write useInfiniteList(loadPage), returning items, loading, done and loadMore(). loadMore does nothing while a page is loading or when the last page has arrived.
    3. 

  3. Put an empty element after the list with ref="end", and call loadMore when it becomes visible.
    4. 

  4. Also show a “Load more” button: keyboard users and screen readers may never trigger the observer.
    5. 

  5. Announce “Loaded 10 more products” in a role="status" element after each page.
    6. 



Hint: the most common bug is two pages loading at once, because the end marker stays visible while the first request is running. The loading check at the top of loadMore is the whole fix; write a test for it.
