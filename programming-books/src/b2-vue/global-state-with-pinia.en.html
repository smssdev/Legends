Chapter {{n}}

Global State with Pinia

In this chapter you will learn to

  • sort every piece of state into the right home: component, address, server cache or global store
  • share values with distant components through provide and inject, with typed keys
  • build a global store with Pinia, and read it without losing reactivity
  • save a store between visits
  • use a store outside components, watch its actions, and test it without any screen

Some data is needed everywhere: who is signed in, the chosen language and theme, the number of items in the cart. Passing it as props from the top of the app through every component in between is called prop drilling, and it makes every component in the path depend on data it never uses. Vue offers two answers: provide and inject, built into Vue, and Pinia, Vue’s official store. But first, the most important skill of this chapter: knowing that most state is not global.

Many apps have a giant global store full of data that one screen uses, or that really belongs to the server. Every time I am tempted to make something global, I first ask: who actually reads this?

{{n}}.1 Four homes for state

Kind of stateExamplesIts home
Belongs to one part of the screenAn open menu, a form’s values, the current tabA ref in the lowest common component (Chapter {{n-4}})

Go down the table in order and stop at the first home that fits. In a typical app, only a handful of values reach the last row.

{{n}}.2 provide and inject

A component can provide a value to everything below it in the tree, at any depth, and any of those components can inject it, without props in between. Wrapped in two small functions, it looks like this:










Three habits make provide and inject pleasant to use:


    

  • Use a typed InjectionKey, a Symbol that carries the type. inject(AuthKey) then knows exactly what it returns, and two libraries can never clash over a name.
    • 

  • Hide the key behind composables. Components call provideAuth() and useAuth(), never inject directly, and useAuth throws a clear error if someone forgets the provider, instead of a mysterious undefined later.
    • 

  • Provide data read-only, with the functions that change it. readonly(user) means components cannot assign to it; the only way to change the user is signIn and signOut, so it is always clear who changed what.
    • 




provide works best for values that belong to a part of the tree: a theme for one area, a form’s context for its fields, the settings of a library component. For state that the whole app shares, a store is clearer.

  3. Why is the user provided as readonly?

{{n}}.3 A store with Pinia



A store holds state that lives outside any one component, together with the values derived from it and the functions that change it. In Pinia, a store is defined with defineStore and, in the setup store style, written exactly like a composable: refs are the state, computed values are the getters, and functions are the actions:

Watch out: destructuring a store
A store is a reactive object, so const { count } = useCart() copies the current number and never updates, exactly the trap of Chapter {{n-4}}. Use storeToRefs(store) for state and getters, which gives refs linked to the store. Actions are plain functions and can be destructured directly, as ProductList does with add.



{{n}}.4 Saving a store between visits



The cart above keeps its lines in useLocalStorage from VueUse (Chapter {{n-3}}), so they are saved in the browser on every change and loaded on the next visit, and even kept in step between open tabs. Because a setup store is just a function, any composable works inside it. Larger apps sometimes use a Pinia plugin, such as pinia-plugin-persistedstate, to save several stores the same way with one line each.



Tip: save only what you must
Save the cart, the theme, a draft. Never save server data, which goes stale, nor anything secret: localStorage is readable by any script on the page (Chapter {{n+5}}). And if you change the shape of saved data later, old visitors still have the old shape, so read it carefully.



{{n}}.5 Stores outside components



A store does not need a screen. With an active Pinia, it runs anywhere, which is how you test it, and how a router guard or a plain module reads it. Pinia also lets you watch a store from outside: $onAction sees every action call, and $subscribe sees every change of state:








That is the same mechanism the devtools use to show a history of changes, and the one a logging or analytics plugin would use: one place that sees every change, without touching the components. After $dispose(), the hooks are gone: the last call changed the count but printed nothing.



Professional habit: keep server data out of global stores
Copying products or orders into a store means writing your own cache, by hand, without refetching, deduplication or invalidation. Let TanStack Query own server data, and keep stores for what the app itself owns. Most “global state” problems disappear with this one rule.

Summary



    

  • State has four homes: the component, the address, the query cache and, for the few values the app owns and many places read, provide/inject or a store.
    • 

  • provide and inject pass values down any depth. Use a typed InjectionKey, composables around it, and readonly state.
    • 

  • A Pinia setup store is written like a composable: refs are state, computed are getters, functions are actions.
    • 

  • Read stores with storeToRefs; destructure actions directly.
    • 

  • Composables such as useLocalStorage work inside stores, for example to save them.
    • 

  • Stores run without components; $onAction and $subscribe watch them from outside, and tests use them directly.
    •

Project {{n}}.1 · Easy


A theme that follows the user


A light and a dark theme, starting from the system setting, switchable from anywhere, and remembered on the next visit.


You will practise: provide and inject with a typed key, VueUse’s usePreferredDark and useLocalStorage, a computed choice, and watchEffect.


    

  1. Write the colours as CSS custom properties on :root, and the dark ones on html.dark. Components never mention colours by name.
    2. 

  2. In provideTheme, keep the user’s saved choice, or null if they never chose, and fall back to the system setting with usePreferredDark().
    3. 

  3. In a watchEffect, toggle the dark class on <html>.
    4. 

  4. Provide { dark, toggle } with a typed key, and read it with useTheme(), which throws a clear error outside the provider.
    5. 

  5. Make the switch a button with aria-pressed.
    6. 



Hint: saving null until the user chooses means the app keeps following the system setting, and starts following the user only once they express a wish. That small detail is what users notice when they switch their phone to dark mode at night.

Project {{n}}.3 · Challenge


Notifications with undo


A notification system that any component can use with one call, that shows at most three messages, disappears by itself, can offer an “Undo” button, and is announced by screen readers.


You will practise: a store used from many components, Teleport, timers, and live regions.


    

  1. Write a useToasts store with the list of messages and two actions, notify(text, action?) and dismiss(id).
    2. 

  2. Add new messages with [...toasts.slice(-2), next], so at most three stay on screen.
    3. 

  3. Remove each message after five seconds with setTimeout, and also with a close button labelled for screen readers.
    4. 

  4. Render the list with <Teleport to="body">, so it is never hidden or clipped by the component that placed it.
    5. 

  5. Give the list role="status" and aria-live="polite", so screen readers announce new messages without interrupting the user.
    6. 



Hint: “Undo” is friendlier than “Are you sure?”. Do the action at once, and offer to reverse it for a few seconds. Users make fewer mistakes, and the rest of the time they are not slowed down.
