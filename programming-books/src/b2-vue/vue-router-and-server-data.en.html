Chapter {{n}}

Vue Router and Server Data

In this chapter you will learn to

  • give every screen of an app its own address with Vue Router
  • share a layout between pages with nested routes and RouterView
  • read route parameters as typed props, and keep filters in the address so they can be shared
  • load server data with TanStack Query: caching, loading and error states, retries
  • change server data with mutations, including optimistic updates that roll back on failure
  • protect pages with navigation guards, and load each page only when it is needed

A real app is many screens: a list, a details page, a basket, a profile. Users expect each one to have an address they can bookmark, share and reach with the back button. And almost every screen shows data that lives on a server, which arrives late, sometimes fails, and changes while the user looks at it. This chapter adds the two libraries that most Vue teams use for these jobs: Vue Router, Vue’s official router, and TanStack Query for server data.

In the last chapter you wrote useSearch, with cancellation and loading and error states. TanStack Query is a set of composables that does that work, and much more, for every request in the app. Now you know what it does inside.

{{n}}.1 Routes

An app with a router is still one HTML page, a single-page application. The router reads the address, decides which components to show, and, when the user clicks a link, changes the address without reloading the page. The routes are plain data: a tree of objects, each with a path and a component:




    

  • The route / shows Layout. Its children are drawn inside it, where Layout places <RouterView />. The navigation bar is written once and every page gets it. These are nested routes. A child with an empty path is shown at exactly its parent’s address.
    • 

  • :id(\d+) is a route parameter that matches digits only, so /products/2 matches and /products/abc does not. Parameters are strings, so the props function turns the id into a number and passes it as a normal prop. The component never touches the router, which makes it easy to reuse and to test.
    • 

  • :path(.*)* matches anything the other routes did not, so mistyped addresses get a friendly page instead of an empty screen.
    • 







The app starts in main.ts, which installs the router and TanStack Query as plugins, so every component can use them:






About the screenshots
createWebHistory reads the real address of the page. The screenshots in this chapter are taken from files, not from a site, so they start the same routes with createMemoryHistory, which keeps its address in memory, and then click the links exactly as a user would.



{{n}}.2 Links and navigation



Inside the app, never write <a href> for your own pages: it would reload the whole page and lose all state. Use <RouterLink to="/products">, which changes the address and redraws only what changed. A RouterLink also knows whether it points to the current page: it adds the class router-link-active when its route is part of the current one, and router-link-exact-active when it is exactly the current one, so the navigation bar can highlight it. In code, after saving a form for example, const router = useRouter() and then router.push("/products") move the user.





The address is state too



Look at how the product list filters by category. It has no ref for the filter: the category lives in the address, as a query parameter, /products?category=gifts, read from useRoute().query. The filter links point to { query: { category: "gifts" } }. This costs nothing and gives users three things for free: they can share the filtered list, bookmark it, and use the back button to undo a filter. Search text, sorting, the current page of results and the selected tab are all good candidates for the address.








{{n}}.3 Server data with TanStack Query



Data from a server is not like state that your app owns. Someone else can change it at any time, you only ever have a copy, and getting that copy takes time and can fail. A composable like useSearch works for one screen, but a real app soon needs much more:


    

  • A cache, so going back to a page shows it instantly instead of loading again.
    • 

  • Deduplication, so two components asking for the same data make one request.
    • 

  • Retries when the network fails for a moment.
    • 

  • Refreshing stale data when the user comes back to the tab.
    • 

  • Protection from the race between old and new requests.
    • 




TanStack Query provides all of these through one composable. You give useQuery a query key, an array that names the data, and a query function that returns a promise:



    

  • The key is a name in a cache: ["products", "gifts"] and ["products", null] are cached separately. In Vue, the key can contain refs and computed values; ["products", category] is reactive. When the address changes, category changes, the key changes, and the right data is loaded, or shown at once if it is already cached.
    • 

  • The result holds refs: isPending, isError with error, and data, which TypeScript knows is a Product[]. These are the four states of Chapter {{n-3}}, ready-made. Templates only unwrap refs at the top level, which is why Products.vue writes query.isPending.value, while Product.vue destructures the result and writes isPending.
    • 

  • staleTime: 30_000 in main.ts says data stays fresh for 30 seconds; inside that time, visiting the page again makes no request at all.
    • 







The details page receives id as a prop and puts a getter, () => props.id, in its key, so moving from one product to another refetches. It uses retry to try twice on network errors, but never on NotFoundError: retrying a product that does not exist is pointless.





Tip: skeletons instead of spinners
A skeleton that has roughly the shape of the coming content feels faster than a spinner, and stops the layout from jumping. Mark it with aria-busy="true" and a label, so screen readers know that content is on its way.

{{n}}.4 Changing server data



Reading uses queries; writing uses mutations. useMutation wraps a function that changes data on the server, and gives you mutate to call it, plus isPending and isError for the screen. After a successful change, the cached copies are out of date, so you invalidate them: queryClient.invalidateQueries({ queryKey: ["products"] }) marks every query whose key starts with "products" as stale, and the ones on screen reload.



Waiting for the server makes small actions, like a heart or a tick, feel slow. An optimistic update changes the screen at once, assuming the server will agree, and puts the old value back if it does not. Project {{n}}.3 builds one, in three short steps: change the cache and remember the old value; restore it on error; reload the truth from the server either way.



{{n}}.5 Guards and lazy routes



Some pages are only for signed-in users. A navigation guard runs before every navigation and can let it pass, cancel it, or send the user elsewhere. Routes carry the information in meta:



router.ts
{ path: "account", component: Account, meta: { requiresAuth: true } }

router.beforeEach((to) => {
  if (to.meta.requiresAuth && !session.signedIn) {
    return { path: "/sign-in", query: { next: to.fullPath } };
  }
});



After signing in, the sign-in page sends the user to route.query.next, back where they wanted to go. Remember that a guard only protects the screen: the server must still check every request, because anyone can call an API without your app (Chapter {{n+7}}).



Each route is also a natural place to split the code (Chapter {{n+6}}): users who never open the admin pages should never download them. Give a route a function that imports its component, instead of the component itself:



routes.ts
{ path: "admin", component: () => import("./views/Admin.vue") }



The build puts the admin page in its own file, and the router loads it the first time someone visits the route.



Professional habit: every page needs four states and a way out
For each route, ask: what does the user see while it loads, when it is empty, when it fails, and when the address is wrong? Each answer should offer a way forward: a retry button, a link to the list, a link home. Nobody should ever reach a blank screen.

Summary



    

  • Vue Router maps addresses to components. Routes are data; nested routes share a layout through <RouterView />.
    • 

  • Pass route parameters to components as typed props; keep filters and other shareable state in the query of the address.
    • 

  • Navigate with RouterLink and router.push; style the current link with router-link-active.
    • 

  • TanStack Query caches server data by query key, which can be reactive; it removes duplicate requests, retries and refreshes, and reports pending, error and success.
    • 

  • Mutations change server data; invalidate the affected queries afterwards. Optimistic updates change the screen first and roll back on failure.
    • 

  • Guards redirect before navigation; lazy routes load each page on its first visit.
    • 




Quick check answers: 1. A plain link reloads the whole page and loses the app’s state; RouterLink only changes the address and the parts of the screen that differ. 2. :id(\d+) does not match letters, so the catch-all route shows the “Page not found” message, and no request is made. 3. One: queries with the same key share a single request and a single cache entry.

Project {{n}}.1 · Easy


A small blog with pretty addresses


A list of posts and a page for each post, at addresses like /posts/rules-for-state, with a kind message for posts that do not exist.


You will practise: nested routes, named routes, route parameters as props, RouterLink, and not-found handling.


    

  1. Give each post a slug: a short, readable id made from the title, such as keys-explained. Readable addresses are better for users and for search engines.
    2. 

  2. Write a layout with the blog’s name, a RouterLink to the list, and a RouterView.
    3. 

  3. Give the routes names, posts and post, and link with { name: "post", params: { slug } }: if an address changes later, no link has to.
    4. 

  4. Pass the slug as a prop with props: true, and find the post in a computed. If it does not exist, say so and link back home.
    5. 

  5. Try a wrong address by hand, such as /posts/nothing, and check the message.
    6. 



Hint: the data here is a constant, so no query is needed. Not every page needs TanStack Query; use it when the data comes from a server.










Project {{n}}.2 · Medium


A product list you can share


Extend the shop from this chapter so that the category and a search text live in the address, and every combination can be shared as a link.


You will practise: reading and writing the route’s query, query keys with several reactive parts, and keeping the address in step with an input.


    

  1. Make category and q computed values from route.query. Both may be missing.
    2. 

  2. Put both in the query key: ["products", category, q], and pass both to the API function.
    3. 

  3. Make the search input follow the address: a writable computed whose get reads q, and whose set calls router.replace with the new text, keeping the category.
    4. 

  4. Use replace, not push, while typing, so every letter does not become a new entry in the back button’s history.
    5. 

  5. Open the same address in a new tab and check that you see exactly the same list.
    6. 



Hint: to change one query parameter and keep the others, spread them: router.replace({ query: { ...route.query, q: text || undefined } }). A value of undefined removes the parameter.







Project {{n}}.3 · Challenge


An optimistic favourite button


A heart that fills the moment it is pressed, saves in the background, and quietly puts things back if the server refuses.


You will practise: useMutation, reading and writing the query cache, rolling back with a context value, and invalidating.


    

  1. Load the product with useQuery under the key ["product", id].
    2. 

  2. Create a mutation whose mutationFn calls setFavourite(id, value).
    3. 

  3. In onMutate, cancel queries for the key (so an old answer cannot overwrite you), save the current value with getQueryData, write the new value with setQueryData, and return { previous }.
    4. 

  4. In onError, write context.previous back. In onSettled, invalidate the key, so the screen ends with the server’s truth.
    5. 

  5. Test the failure: the pretend API has a server.failNextSave switch. Watch the heart fill, then empty, with a message.
    6. 



Hint: use optimistic updates for small, frequent, reversible actions, such as likes, ticks and reordering. For payments and anything hard to undo, show a clear “Saving…” state and wait for the server instead.
