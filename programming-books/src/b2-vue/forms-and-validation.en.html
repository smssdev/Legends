Chapter {{n}}

Forms and Validation

In this chapter you will learn to

  • bind every kind of input with v-model and its modifiers
  • describe a form’s rules once, in a zod schema that also gives you the TypeScript type
  • build a small form composable: values, errors, touched fields and submitting
  • show errors at the right moment, accessibly, and move the focus to them
  • show errors that only the server can find, under the right field
  • split long forms into steps that check only their own fields

Forms are where users give your app their data: a name, an address, a password, money. They are also where most frustration on the web happens: rules that are not explained, errors that appear too early or too late, typed text that vanishes after a failed submit. A good form is mostly a list of small decisions made well. This chapter makes them once, in a schema and a composable that every form can reuse.

The browser checks nothing that matters on its own, and the server must check everything again anyway. So why validate in the form at all? Because it is the only place where you can help the user fix the mistake while they are still typing.

{{n}}.1 v-model on every kind of input

In Vue, the value of a field lives in your state, and v-model keeps the two in step. It adapts to the kind of input:

  • A text input or <textarea> binds a string. v-model.trim removes spaces at the ends, v-model.number converts to a number, and v-model.lazy updates only when the field is left.
  • A checkbox binds a boolean, or, with an array, the list of checked values.
  • Radio buttons with the same v-model bind the value of the chosen one.
  • A <select> binds the value of the chosen option.

Because the values are in state, everything else is ordinary Vue: a computed can check them, a watcher can save a draft, and the template can show anything derived from them.

{{n}}.2 One schema for the rules

Every form has rules: required fields, formats, limits. Written by hand, they end up in three places: the form, the TypeScript type, and the server. zod, which you met in Chapter 2, describes them once:




    

  • Each field has its rules and its own message, written for the user: what is wrong and how to fix it.
    • 

  • z.coerce.number() turns the text of the age field into a number before checking it. Inputs always give text; the schema decides what it becomes.
    • 

  • z.infer gives the type of the result, with age as a number and the name trimmed, so the code after validation is fully typed.
    • 




The same schema runs anywhere, including on the server, where it must run again, because anyone can send data without your form:








{{n}}.3 A form composable



A real form needs more than a schema: it must know which fields the user has visited, whether a submit was tried, whether it is sending, and where to put errors that come back from the server. This is the same work for every form, so it belongs in a composable, as in Chapter {{n-2}}:






The composable keeps the values in a reactive object, checks them with the schema whenever they change, and exposes only the errors the user should see now. handleSubmit wraps the code that sends the data: it marks the form as submitted, stops and moves the focus if anything is wrong, and passes the parsed data, typed and converted, to your function.



Each field also needs the same markup around it: a label, the input, and an error linked to the input. A component with a scoped slot writes it once:






The slot hands its attributes to the input, so the label’s for, the input’s aria-invalid and aria-describedby, and the error’s id always match. A screen reader reading the field also reads its error. And the form itself becomes a short list of fields:








When to show errors



Errors shown while the user is still typing the first letters are noise: “invalid email” after one letter is not helpful, it is rude. Errors shown only after submit are too late. The composable follows the rule that most good forms use: a field’s error appears when the user leaves the field (@blur), or tries to submit. After that, it updates as the user types, so it disappears the moment the value is fixed.



Tip: help the browser help the user
The right type, inputmode and autocomplete cost nothing and save users a lot of typing: type="email" shows the @ key on phones, inputmode="numeric" shows digits, and autocomplete="email" lets the browser fill in a saved address. Emails, phone numbers and passwords also get dir="ltr", so they read correctly in Arabic pages.

{{n}}.4 Errors only the server knows



Some rules cannot be checked in the browser: is this email already registered? Is this coupon still valid? The server answers with errors per field, and they should appear exactly like the form’s own errors, under the field, with the focus moved there. In useForm, the function passed to handleSubmit can return such errors; Project {{n}}.2 uses it for an email that already has an account.



Watch out: never lose what the user typed
After a failed submit, keep every value in the form. The only exceptions are passwords and card numbers, which many sites clear on purpose. Nothing makes users leave faster than retyping a long form because one field was wrong.



{{n}}.5 Forms in several steps



A long form, such as a checkout, is easier in steps. The data is still one object with one schema; each step lists the fields it is responsible for, and “Next” checks only those, with checkFields. The last step shows a summary and submits the whole form, checked against the whole schema. Project {{n}}.3 builds one.



{{n}}.6 Form libraries



The composable in this chapter is about seventy lines, and it is enough for many apps. Large apps with many complex forms often use a library, which adds features such as field arrays, async rules and fine-grained performance:


    

  • VeeValidate is the most used in Vue. At the time of writing, its stable version 4.15 accepts zod 3 schemas through @vee-validate/zod, and version 5, still in beta, adds support for zod 4 and other schema libraries directly.
    • 

  • TanStack Form, from the authors of TanStack Query, accepts zod 4 schemas directly.
    • 



All of them do what you just built: values, errors, touched fields, submitting and server errors, around a schema. Knowing how it works inside lets you choose one with open eyes, or decide you do not need one.



Professional habit: write the error messages with the design
Every rule needs a message that says what is wrong and how to fix it, in the user’s language: not “Invalid input” but “Please enter an 11-digit Egyptian mobile number.” Write the messages when the form is designed, review them like any other text, and keep them next to the rules, in the schema.

Summary



    

  • v-model binds every kind of input to state; .trim, .number and .lazy adjust it.
    • 

  • A zod schema holds the rules and the messages once, converts the values, and gives the type with z.infer. The server checks it again.
    • 

  • A form composable keeps values, errors, touched fields and the submitting state, and passes parsed data to your submit function.
    • 

  • Show errors after a field is left or a submit is tried, linked with aria-describedby, and move the focus to the first one.
    • 

  • Server errors go under the right field; never clear what the user typed.
    • 

  • Steps check only their own fields; the last step checks the whole schema.
    • 




Quick check answers: 1. Because anyone can send data to the server without the form, for example with a script, so the form’s checks protect nothing. 2. The TypeScript type of the data after validation, with conversions applied, such as age as a number. 3. Because errors on the first letters only scold the user for an answer they have not finished writing.




Practice projects



For each form, write the schema first, with every error message, and test it with safeParse in Node before you build any screen. When the rules are right, the form is mostly wiring.





Project {{n}}.1 · Easy


An accessible contact form


Finish the contact form from this chapter, and make sure every field is labelled, linked to its error, and receives the focus when it is wrong.


You will practise: useForm, a field component with a scoped slot, @blur, and accessibility attributes.


    

  1. Write the schema and infer the type. Give every rule a message that explains the fix.
    2. 

  2. Write FormField: a label, a scoped slot for the input, and the error paragraph with an id. Pass id, aria-invalid and aria-describedby through the slot.
    3. 

  3. Bind each input with v-model and v-bind="attrs", and call blur("name") on @blur.
    4. 

  4. Try every mistake: leave fields empty, type a short name, a broken email, an age of 9. Check that errors appear only after leaving a field, and disappear as soon as the value is fixed.
    5. 

  5. Test with a screen reader (VoiceOver, NVDA or TalkBack): submit an empty form and listen. The focus should land on the first field, and its error should be read with its label.
    6. 



Hint: the focus moves to the first [aria-invalid='true'] element after nextTick, because the attribute only appears once Vue has updated the page. Without the await nextTick(), there would be nothing to focus yet.







Project {{n}}.2 · Medium


Sign up, with an answer from the server


A sign-up form with a password, its confirmation and a terms box, which also shows the server’s “email already used” message on the email field.


You will practise: rules that compare two fields with refine, z.literal(true) for a required checkbox, server errors returned from the submit function, and the submitting state.


    

  1. Write the schema: an email, a password of at least 8 characters with a digit, a confirmation, and terms: z.literal(true, "…").
    2. 

  2. Compare the passwords with .refine(…, { path: ["confirm"] }), so the error appears under the confirmation field.
    3. 

  3. In the submit function, check the full schema, then call a pretend server that answers { email: "…" } for one particular email. Return that object, and useForm shows it under the email field.
    4. 

  4. Disable the button while submitting is true, so a double click cannot create two accounts.
    5. 

  5. Give each password input autocomplete="new-password", so password managers offer to create a strong one.
    6. 



Hint: design your API so that its errors name the field they belong to, as the pretend server does here. Then the frontend can put every server error in the right place with one line of code.










Project {{n}}.3 · Challenge


A checkout in three steps


Delivery, payment and review as three steps of one form, checked step by step, with a review screen before the order is placed.


You will practise: z.enum, checking some fields only, <select> and radio buttons with v-model, aria-current="step", and keyed buttons.


    

  1. Write one schema for the whole order, and a STEPS list with each step’s title and fields.
    2. 

  2. Show only the current step’s inputs. “Next” calls checkFields(STEPS[step].fields) and moves on only if it returns true.
    3. 

  3. On the last step, show a summary from values and a “Place order” submit button.
    4. 

  4. Show the progress as a list, with aria-current="step" on the current one.
    5. 

  5. Give “Next” and “Place order” different keys. Without them, Vue may reuse the same <button> and only change its type, and a click on “Next” could end as a submit of the new type, placing the order one step early.
    6. 



Hint: because all steps are one form, “Back” is free: the values are still there. Never create a separate form per step unless the steps are saved separately on the server.
