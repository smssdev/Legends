Chapter {{n}}

Reactivity and the Composition API

In this chapter you will learn to

  • explain how Vue knows what to update: tracking what code reads, and triggering what depends on it
  • choose between ref and reactive, and avoid the ways reactivity is lost
  • keep state minimal and compute everything else
  • react to changes with watchers, and clean up after them
  • use the life of a component, and two-way binding with v-model on your own components

In the last chapter you changed likes.value and the button updated, as if by magic. It is not magic, and knowing how it works is the difference between a developer who uses Vue and one who can explain why a screen did not update. This chapter opens the box: how Vue tracks data, the few rules that follow from it, and the tools of the Composition API, the functions such as ref, computed and watch that you call inside <script setup>.

Most bugs about “Vue did not update” come from two or three rules. Learn the rules in section {{n}}.2 once, and those bugs disappear from your life.

{{n}}.1 Track and trigger

Vue’s reactivity works in two steps. When code reads a reactive value, Vue notes who read it: this is tracking. When the value is changed, Vue reruns everything that read it: this is triggering. A component’s template is such code: it is tracked while it renders, and rerun when anything it read changes. You can see the mechanism without any component:






Four lines printed, for three changes plus the first run. The last change printed nothing: total never read coupon, so changing the coupon cannot change the total, and Vue does not waste time recomputing it. This is why Vue updates so precisely: every piece of the screen depends on exactly the data it read.



How does Vue see a read? reactive() wraps an object in a JavaScript Proxy, which can intercept every property read and write. ref() does the same with a small object whose only property is value. That is why refs need .value in the script: it is the property Vue watches.

The official recommendation, which this book follows, is simple: use ref for all state. It works for every kind of value, it can be replaced, and the .value reminds you that the value is reactive. The second rule is about a trap that looks innocent:








Destructuring reads product.stock once and copies the number into a plain variable, which knows nothing about later changes. The same happens when you pass product.stock to a function that keeps it. When you need a separate variable that stays linked, toRefs turns each property into a ref connected to the object.



Updates are batched



Changing reactive data does not update the screen immediately. Vue collects all the changes made in the same moment and applies them together, once:








Three changes, one run of the watcher, with the first and last values. The page works the same way: after you change data, the DOM is updated a moment later, all at once. If code must see the updated page, for example to measure an element or to move the focus into a field that just appeared, await nextTick() first.



{{n}}.3 Minimal state, computed values



The most important design skill for state is to keep as little of it as possible. Everything that can be calculated from other state should be a computed, never a second copy that must be kept in step by hand:










The only state is lines. If the count were stored separately, every function that changes the lines would also have to remember to update the count, and one day one would forget. Computed values cannot be forgotten: they are always calculated from the truth.



Notice also line.quantity++ in add. Unlike some frameworks, Vue lets you change objects and arrays in place: the proxy sees the write, and everything that read quantity updates. Replacing a whole array, as remove does with filter, works too, because lines is a ref.



{{n}}.4 Where should state live?



Each piece of state should live in the lowest component that contains every component that needs it. If only the cart uses the lines, they live in the cart. If the header also needs the number of items, the lines move up to the component that contains both, and travel down as props, with events coming back up. If many distant parts of the app need it, Chapter {{n+4}} gives it a store of its own.

{{n}}.5 Watchers: reacting to changes



A computed calculates a value. Sometimes a change must instead do something outside Vue’s world: start a timer, save to storage, call a server, change the page’s title. That is the job of a watcher:








watch(running, callback) calls the callback every time running changes. The important line is onWatcherCleanup. It registers a function that Vue calls before the next run of the watcher, and when the component is removed from the page. Without it, pressing “Stop” would leave the interval running forever, and pressing “Start” again would start a second one, so the seconds would count twice as fast.



Vue has two kinds of watcher:


    

  • watch(source, callback) watches what you name, and gives you the new and old values. It does not run at first unless you pass { immediate: true }. To notice changes deep inside objects and arrays, pass { deep: true }.
    • 

  • watchEffect(fn) runs fn at once, tracks everything it reads, and runs again when any of it changes, like the effect of section {{n}}.1.
    • 




Watch out: you might not need a watcher
A watcher that copies data into another ref, such as watch(lines, () => { count.value = … }), is a computed value written the hard way, and it is briefly wrong between the change and the watcher. If you are calculating, use computed. Use a watcher only when a change must cause something outside the data.



The life of a component



A component is created, put into the page (mounted), updated as its data changes, and finally removed (unmounted). Functions such as onMounted and onUnmounted run code at those moments: onMounted is the first moment the component’s elements exist in the page, so it is where you measure them, focus a field, or start a library that needs a real element. Clean up in onUnmounted anything you started in onMounted. And to reach an element itself, give it ref="name" in the template and read it with useTemplateRef("name"), as the tabs project of Chapter {{n-1}} did.



{{n}}.6 v-model on your own components



On an input, v-model="text" keeps a ref and the field in step, in both directions. Your own components can support v-model too. defineModel creates a ref that reads the prop the parent passed and, when you change it, emits the event that updates the parent:










This does not break the rule “data flows down, events flow up”: v-model="mugs" is short for :modelValue="mugs" @update:modelValue="mugs = $event". The parent still owns the number; it just lets the child ask for changes with one short attribute.



Professional habit: name what a watcher is for
Every watcher is a small piece of behaviour that runs at times you do not see. Keep each one short, put a comment above it that says why it exists, and clean up whatever it starts. When a component has more than two or three, the next chapter shows how to move them into composables with names.

Summary



    

  • Vue tracks which code reads which data, and triggers exactly that code when the data changes.
    • 

  • reactive wraps objects in a proxy; ref wraps any value in an object with .value. Prefer ref.
    • 

  • Destructuring copies values and loses reactivity; toRefs keeps the link. Updates are batched; nextTick waits for the page.
    • 

  • Keep state minimal; calculate the rest with computed. Put state in the lowest component that contains all its users.
    • 

  • Watchers are for effects outside the data. Clean up with onWatcherCleanup; use onMounted and onUnmounted for the life of the component.
    • 

  • defineModel gives your components v-model, without breaking one-way data flow.
    •

Practice projects



Before each project, write down every piece of state you plan to keep, then cross out each one that can be calculated from the others. What remains goes in refs; the rest becomes computed.

Project {{n}}.2 · Medium


A task list that remembers


A task list that saves itself in the browser, and comes back after a reload, safely.


You will practise: v-model on text and checkboxes, a deep watcher, localStorage, and defensive loading.


    

  1. Load the tasks once, when the component starts, inside a try: saved data can be missing, broken or from an older version.
    2. 

  2. Bind the new task’s text with v-model, and add it on @submit.prevent, so Enter works and the page does not reload.
    3. 

  3. Bind each checkbox straight to task.done with v-model: Vue changes the object in place.
    4. 

  4. Save with watch(tasks, save, { deep: true }). Without deep, ticking a box would not be noticed, because the array itself did not change.
    5. 

  5. Show how many tasks are left with a computed, and add a button that removes the done ones.
    6. 



Hint: deep: true walks the whole structure on every change. That is fine for a task list; for thousands of items, save less often, or watch a smaller part.

Search as you type, without races


Search products while the user types, and never show the results of an old query, even when a slow answer arrives after a fast one.


You will practise: watchers with async work, onWatcherCleanup, AbortController, and loading states announced to screen readers.

    2. 

  2. Watch the query. For an empty query, clear the results and stop.
    3. 

  3. For each search, create an AbortController, and register controller.abort() with onWatcherCleanup. The next keystroke cancels the previous request.
    4.

    5.
