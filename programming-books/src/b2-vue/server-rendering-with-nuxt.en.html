Chapter {{n}}

Server Rendering with Nuxt

In this chapter you will learn to

  • tell apart the ways a page can be made: in the browser, on the server per request, or ahead of time at build
  • create a Nuxt app and build its pages, layouts and server routes from folders and files
  • load data on the server with useFetch, and carry it to the browser without asking twice
  • choose, per address, whether a page is prerendered, cached or made on every request
  • handle forms and errors on the server, and show a real 404
  • read the build’s output and run the app in production

Every Vue app in this book so far started as an almost empty HTML page. The browser downloaded JavaScript, ran it, fetched the data, and only then drew something. That works well for apps behind a login, but the user waits for a blank page, slow phones wait longest, and a search engine or a link preview may see nothing at all. Nuxt is the framework around Vue that can make the HTML on the server instead, and send a page that is complete before any JavaScript runs. It also gives your app a server of its own, so pages and the API that feeds them live in one project.

Nuxt does not replace what you learned. Components, props, refs, composables and forms all work the same. What changes is where each piece runs, and that one question is the whole chapter.

{{n}}.1 Four ways to make a page

WayWhen the HTML is madeGood forPrice
Client-side rendering (CSR)In the browser, after the JavaScript runsDashboards and apps behind a loginA blank page at first, weak for search engines
Server-side rendering (SSR)On the server, for every requestPages that differ per user or per minuteServer work on every visit
Static generation (SSG)Once, when the app is builtPages that are the same for everyone: articles, docs, landing pagesStale until the next build
Stale-while-revalidate (SWR, also called ISR)On the first request, then again in the background after a set timeMostly-static pages whose data changes sometimesVisitors may see data a little old

In all three server ways, the browser still downloads the Vue code afterwards, and Vue attaches event handlers to the HTML that is already there. This step is called hydration: the page appears first and becomes interactive a moment later. Nuxt lets you choose the way per address, which is why it suits real sites where the home page, the product pages and the account page need different things.

{{n}}.3 Data on the server



Nuxt has two halves that run in different places. The server/ folder is a small server, called Nitro, that runs only on the server: it can read a database or use secrets. The app/ folder is your Vue app, which runs on the server for the first visit and in the browser after that. First, a pretend database and an API route that serves it:








The file name says the method and the address: products.get.ts answers GET /api/products. Now the page:






useFetch is the key. During server rendering, it calls the API route directly, without a network request, waits for the data, and puts it into the HTML. It also writes the data into the page as a payload, so when the browser hydrates, it reuses the same data instead of asking for it again. Later navigations in the browser call the API like any request. And because the setup is async, the page is not sent until its data is ready.



What does the browser receive? curl downloads a page without running any JavaScript:






The product names are already inside the HTML. A search engine, a link preview on a phone, or a user on a slow network gets the content immediately.





Watch out: one value, two places
The page runs twice: once on the server, once in the browser to hydrate. new Date() in the setup would give two different times, and Vue would warn about a hydration mismatch. useState solves it: the server computes the value, puts it in the payload, and the browser reads it instead of computing its own. Use it for any value that must be the same on both sides; read things like window.innerWidth only in onMounted.

{{n}}.4 Components on both sides






Unlike React Server Components, every Nuxt component runs in both places by default: it is rendered to HTML on the server, so the button appears at once, and hydrated in the browser, where it reacts to clicks. You do not mark components as “client” or “server”. When something truly cannot run on the server, such as a map library that needs window, wrap it in <ClientOnly>, which renders it only in the browser.

{{n}}.6 Choosing how each page is made



By default, Nuxt renders every page on the server for every request. Route rules in nuxt.config.ts change that per address, which is called hybrid rendering:






    

  • prerender: true: the page is made once, at build time, and served as a file. The build transcript in section {{n}}.2 showed it: / and /contact were prerendered, each with its _payload.json.
    • 

  • swr: 60: the page is made on the first request, then served from a cache; after 60 seconds, the next visitor still gets the cached page at once while a fresh one is made in the background. The curl transcript showed the header it sends: cache-control: s-maxage=60, stale-while-revalidate, which CDNs understand too.
    • 

  • No rule: rendered on the server for every request. Other rules include ssr: false, which turns a section into a classic browser-only app, ideal for an admin area.
    • 




Choosing per address is the whole skill: static for what is the same for everyone, cached for what changes slowly, and per request only for what is personal or live.



Professional habit: decide rendering per route, on purpose
Write the route rules when you add a page, and review them like code. A personal page accidentally cached with swr can show one user’s data to another; a static page accidentally rendered per request costs server time on every visit. Both are one line in nuxt.config.ts, so that line deserves attention.



{{n}}.7 Forms and server routes



The contact form posts to a server route, which validates the fields with the same kind of zod schema as in Chapter {{n-9}}, and answers 422 with an error per field:








$fetch is Nuxt’s fetch: it calls the route, parses JSON, throws on error statuses, and, because the route lives in the same project, it even knows the type of the answer. Use useFetch to load data for a page, and $fetch in event handlers to send data.





Watch out: every server route is public
A route in server/api/ feels like part of your app, but anyone can call it with any data, without your pages. Validate every field on the server, check that the user is signed in and allowed to do this, and never trust a value from the browser for a price or a user id. Everything from Chapter {{n-3}} applies here.



{{n}}.8 Running in production



npm run build makes .output/, a self-contained folder: node .output/server/index.mjs starts the server on port 3000, with no node_modules to copy, which makes small container images. Two more facts complete the picture:


    

  • Configuration and secrets go in runtimeConfig in nuxt.config.ts, and are read with useRuntimeConfig(). Values are private, server-only, unless they are under runtimeConfig.public, which is sent to the browser. They can be set at start time with environment variables such as NUXT_API_SECRET or NUXT_PUBLIC_SITE_URL.
    • 

  • Presets: Nitro can build the same app for other targets, such as serverless platforms or a fully static site with nuxt generate, by changing one setting.
    • 




Put a reverse proxy such as Nginx in front of the Node server for HTTPS and compression, and the shop is ready for visitors.

Summary



    

  • A page can be made in the browser, on the server per request, at build time, or cached and revalidated. Hydration makes server HTML interactive.
    • 

  • In Nuxt, folders are the app: pages, layouts, components, error.vue, and server/api for the app’s own API. Common names are auto-imported.
    • 

  • useFetch loads data on the server and passes it to the browser in the payload; $fetch sends data from event handlers. useState keeps values equal on both sides.
    • 

  • Every component renders on the server and hydrates in the browser; <ClientOnly> is for code that cannot run on the server.
    • 

  • createError makes real error statuses; error.vue shows them. useHead and useSeoMeta set the head on the server.
    • 

  • Route rules choose per address: prerender, swr, or per request. Server routes are public endpoints to validate and protect.
    • 

  • Production is .output/server/index.mjs; secrets live in the private runtimeConfig.
    • 




Quick check answers: 1. server/api/ runs only on the server; a page runs on the server for the first visit, and in the browser after that. 2. Because the server already rendered the page to HTML, with the data inside, before sending it. 3. Because useFetch wrote the data into the page’s payload during server rendering, and the browser reuses it.
