Capstone: A Production Dashboard

In this chapter you will

  • turn a short brief into user stories and the quality goals a release must meet
  • organise a real codebase in layers, with one place that talks to the server
  • build five screens with routing, server data, URL state, an optimistic update and a validated form
  • support two languages, right to left, and a dark theme from the first line
  • prove the app works with unit tests, end-to-end tests and an accessibility audit
  • measure the app against a size budget, and learn which advice applies to your own setup

Every chapter of this book taught one skill on a small example. Real work is different: all the skills are needed at once, they pull in different directions, and nobody tells you which chapter applies. In this last chapter we build one complete app, the admin dashboard of Bit’s shop, from a brief to a release. Every file is shown, every test is run, and every number is measured.

Read this chapter twice: once for the app, and once for the decisions. Each section says which chapter a decision comes from, so you can go back whenever something feels new.

{{n}}.1 The brief

The shop owner writes: “I want to see how the shop is doing, find orders and mark them as shipped, and fix product prices, from my laptop or my phone, in Arabic or English.” A brief like this is not yet something you can build. The first job is to turn it into user stories, each with a test for “done”:

As the owner, I want to…Done when…
see revenue, orders and what is waiting to shipThe overview shows four numbers and the last seven days of revenue
find an order by status or by customerThe list filters and pages, and a filtered list can be bookmarked
mark an order as shippedThe change shows at once, and is undone clearly if the server refuses
fix a product’s name, price and stockWrong values are explained under each field; the server’s own errors too
use it in Arabic or English, in light or darkEvery text is translated, the layout mirrors, and the choice is remembered

And the qualities that every story must also meet, which a team writes down before the first line of code:

  • Accessible: no violations in an automatic audit, and everything works with the keyboard (Chapter {{n-8}}).
  • Tested: the logic by unit tests, the main journeys by end-to-end tests (Chapter {{n-7}}).
  • Fast: the first load under 150 KB of compressed JavaScript (Chapter {{n-6}}).
  • Safe: every answer from the server is checked before use (Chapter {{n-5}}).

{{n}}.3 Talking to the server

Then the client, the only file in the app that calls fetch. It parses every answer with its schema, so a server that changes a field breaks here, loudly, instead of in a random screen, and it turns failures into an ApiError that the screens can understand:






And the TanStack Query composables that the screens use. Their ids accept a getter, as in Chapter {{n-13}}, so a page passes () => props.id and refetches when the id changes. Changing a status is optimistic, as in Chapter {{n-12}}: the screen shows the new status before the server answers, and puts the old one back if it fails.






During development, and for this book’s screenshots and end-to-end tests, a small pretend server answers the same addresses with the same shapes. A test page puts it in place of fetch, and nothing else in the app knows. Real projects do the same with the library Mock Service Worker.

{{n}}.5 The frame: routes and layout








A few details come straight from earlier chapters. The order and product pages are children of their lists, so the side menu stays highlighted on them (Chapter {{n-12}}), and the ids are digits only, passed as typed props. The layout sets lang, dir and the dark class on <html> in a watchEffect, so the whole page mirrors and changes colour together. And the product routes are lazy: section {{n}}.10 measures what that is worth.

The numbers on the overview are pure functions of the orders, in lib/, away from Vue and fetch, so they are tested in milliseconds and the screen stays short:








The chart is plain HTML: a list of seven bars whose height is a percentage. Each bar carries its value as visually hidden text, so a screen reader reads “Tue: EGP 1,350” instead of nothing.





{{n}}.7 The orders






The status, the search text and the page number all live in the address. readFilters, the same pure function as in the React edition, protects against nonsense such as ?page=-4. The status links are real links, marked with aria-current. The search box is bound to a writable computed whose setter calls router.replace, so typing updates the address without filling the back button’s history.

The buttons offer every status except the current one, and are disabled while a change is on its way. The status sits in an aria-live region, so a screen reader announces the change. If the server refuses, the optimistic status is put back and an alert says so.

The size budget



The last quality goal was a first load under 150 KB of compressed JavaScript. A Vue project measures what its own build tool produces, so this script runs vite build in memory and checks the result:








77 KB, about half of the React version of the same app. The React edition of this chapter tells how its bundle shrank from 222 KB with two fixes: importing zod with import * as z, and loading the product pages lazily. We measured both mistakes here too, on purpose: with import { z } the Vue build stays at 77.3 KB, because Vite’s bundler can remove the unused parts of zod anyway; and without the lazy routes it grows by only 0.2 KB, because this form is our own small composable, not a library. Neither fix matters in this setup.



That is the real lesson of budgets: measure your own app, with your own tools. Advice from another project, even a correct one, may cost you work for nothing, or miss what is actually heavy in yours. And keep the script in CI, so the next 70 KB cannot arrive unnoticed.



Professional habit: a release checklist
Before every release, a short list that anyone on the team can run: all checks green in CI; the main journeys clicked by hand in both languages and both themes, on a phone and with the keyboard; the size budget met; no errors in the browser console; and a plan to undo the release if something goes wrong. Five minutes of checking is cheaper than one evening of fixing in production.



{{n}}.11 What you built



In about 900 lines of TypeScript and Vue: a typed, validated data layer with caching and optimistic updates; five screens with URL state, loading and error states; a validated form that merges the server’s errors; two languages with mirrored layout and real number and date formats; a dark theme; and tests, an accessibility audit and a size budget that prove it. With a real server behind /api, it is a product.



And more important than the app is the order in which it was made: the brief and the quality goals first, the layers next, the pure logic tested on its own, the screens kept thin, and measurement before any optimisation. That order works for apps a hundred times bigger.



Summary



    

  • Turn a brief into user stories with a test for “done”, and write the quality goals before the code.
    • 

  • Organise the code in layers: one place talks to the server, pure logic is separate, screens stay thin. Framework-free layers can be shared even between a React and a Vue app.
    • 

  • Validate every answer from the server with a schema, and give the screens errors they understand.
    • 

  • Keep server data in TanStack Query, filters in the address, and app-wide settings in a Pinia store.
    • 

  • Start with two languages and Intl, and define colours as variables, so a theme is a few lines.
    • 

  • Prove it with unit tests, end-to-end tests and an accessibility audit, all automatic.
    • 

  • Measure the bundle with your own build against a budget; apply advice only when your numbers say it helps.

Practice projects



These projects grow the dashboard the way a real one grows: one feature at a time, each meeting the same quality goals. For every project, write the user story first, put the logic in lib/ with a test, keep the screen thin, and run the three checks (unit tests, end-to-end tests, size) before you call it done.

A customers page

You will practise: deriving data with pure functions, a new route and a nav link, Intl formats, and URL state.

    2. 

  2. Add /customers to the routes and to the side navigation, with texts in both languages in messages.ts.
    3. 

  3. Make each customer’s name a link to /orders?q=<name>, so the existing search does the rest.
    4. 

  4. Add the page to the axe test in e2e/admin.spec.ts.
    5. 



Hint: there is no new request here. The orders are already in the query cache, so useOrders() returns them at once, and the new page costs the server nothing.







Project {{n}}.2 · Medium


Date ranges and a CSV export


Filter the orders by a date range kept in the address, and download exactly the filtered orders as a CSV file that opens correctly in Excel, in Arabic too.


You will practise: extending readFilters safely, date inputs, building files in the browser, and testing pure output.

    2. 

  2. Add two <input type="date"> fields with labels, updating the address with replace.
    3.

    4.

Project {{n}}.3 · Challenge


From laptop to production


Turn the dashboard into a Vite project with a real CI pipeline, and serve it from a container, ready for a real /api.


You will practise: Vite, GitHub Actions, required checks, Docker, Nginx, and single-page app routing on a server.


    

  1. Create a Vite Vue project (Chapter 3) and move src/ into it. In development, run the pretend server only when import.meta.env.DEV is true.
    2. 

  2. Write a workflow that, on every pull request, installs with npm ci, then runs the type checker, the unit tests, the end-to-end tests and the size script, and make all four required.
    3. 

  3. Write a two-stage Dockerfile: the first stage builds with Node, the second copies dist/ into an Nginx image.
    4. 

  4. Configure Nginx to send every unknown path to index.html, so /orders/1036 works after a reload, and to forward /api/ to the real server.
    5. 

  5. Add long cache headers for the hashed files in assets/, and none for index.html.
    6. 



Hint: the cache rule in the last step is what makes releases safe. Hashed files never change, so they can be cached for a year; index.html must always be fresh, because it is the file that points to the new hashes.
