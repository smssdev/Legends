1. With innerHTML, <svg onload="window.hacked=true"> runs, and so does <iframe src="javascript:…"> in many browsers; any element with an event-handler attribute is a door. With textContent, none of them runs. The lesson: there are far too many tricks to block one by one.
  2. Session cookies of well-run sites are usually HttpOnly, Secure and SameSite=Lax or Strict. Analytics and preference cookies are often readable by JavaScript, which is fine as long as they carry no secrets.
  3. In report-only mode, the console still reports the violation, but the inline script runs: “script ran?” becomes yes. That is why the mode exists: you can see everything a policy would block on a live site, fix it, and only then enforce it.
  4. function safeUrl(input: string): string { try { const url = new URL(input); return url.protocol === "https:" || url.protocol === "http:" ? url.href : "#"; } catch { return "#"; } }. Test a normal https link, an http link, javascript:alert(1), JavaScript:alert(1) (upper case), and a string that is not a URL at all.
  5. An advisory names the package, the affected and fixed versions, a severity, and how the bug can be exploited. Often the vulnerable function is in a build tool that never reaches users, or in code you never call; the right response may be an upgrade, or a note explaining why it does not apply.
