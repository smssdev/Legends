1. The three dataset rows fail and the two other tests pass (the failure is shown in section {{n}}.7). The rows are exactly the cases where VAT is charged on a positive amount; the fixed-discount case has nothing left to tax, and the unknown code throws before VAT is computed. So the bug is in the VAT step, not in the discounts or the codes, and the difference (8550 instead of 7980, which is 15% instead of 14% of 57000) points at the rate. Good tests narrow a bug down by which of them fail.
  2. After php artisan config:cache, env() outside config/ returns null, so a switch read with env() in application code would silently stop working in production. getenv() reads the process environment directly. The real lesson is that such a switch has no place in production code at all; it exists here only for the exercise. A real feature flag would be a configuration value, read with config().
  3. (1) Shared data: the test is not in a folder that uses RefreshDatabase, or it uses a connection outside the test transaction, so rows from other tests survive; check tests/Pest.php and the connections used. (2) Parallel runs sharing one database: with --parallel each process needs its own database; check the test database names. (3) Work outside the transaction: a queued job or a DB::afterCommit callback that really runs (because a fake is missing) creates the third order; look for jobs and events not faked. Running the test alone with --filter many times, then with the whole suite, then with --parallel, shows which it is.
  4. The test “refuses an order larger than the stock, and changes nothing” already proves it: after the 409 it calls Queue::assertNothingPushed(). The care is about timing: RefreshDatabase wraps the whole test in a transaction that never commits, so a naive implementation of afterCommit would never dispatch anything and the success test would wrongly pass the “nothing pushed” check too. Laravel handles this: in tests it treats the test’s own transaction as the base level, so an afterCommit job is dispatched when the controller’s transaction commits. That is why the success test also asserts that exactly one job was pushed; a test that only checks the refusal would not notice if dispatching stopped working altogether.
  5. Unit level: a pure method isUnpaidTooLong($order, $now) tested with a dataset of times on both sides of 15 minutes. Feature level: the scheduled command or job that cancels orders, run with $this->artisan() against the PostgreSQL test database, with orders created by factories with created_at in the past, or with $this->travel(16)->minutes() after creating them; assert that only the unpaid old orders are cancelled and their stock returned, and fake the notifications sent to customers with Notification::fake(). The scheduler itself needs no test of its timing beyond checking that the command is scheduled (schedule:list in a test, or trust the framework); no test ever waits 15 real minutes.
