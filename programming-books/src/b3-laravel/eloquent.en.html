Eloquent, Relationships and Migrations

In this chapter you will learn to

  • connect Laravel to PostgreSQL and change the schema with migrations you can undo
  • change a live schema without downtime, with expand and contract
  • model a domain with Eloquent: relationships, pivot data, enum casts, scopes and computed attributes
  • see the SQL Eloquent sends, and count it
  • find the N+1 problem, fix it with eager loading, and make Laravel refuse it in development
  • protect models from mass assignment

Chapter {{n-2}} used Eloquent for a few minutes, and Chapter {{n-1}} showed the SQL underneath. Eloquent is Laravel’s ORM (object-relational mapper): every table is a class, every row an object, and relationships are methods. It is pleasant to use and easy to misuse, because a single innocent line can send hundreds of queries. This chapter uses it properly, on PostgreSQL, and keeps an eye on the SQL the whole time.

The slowest page I ever shipped had twelve lines of Blade and sent 1,400 queries. Every line looked harmless: $order->customer->name, $item->product->price. Nothing was wrong with Eloquent; I simply never looked at what it sent. Now I count queries before I trust a page.

{{n}}.1 PostgreSQL and migrations

A new Laravel project uses SQLite. Pointing it at PostgreSQL is a matter of settings in .env:




A migration is one change to the schema, written as code, with an up that makes it and a down that undoes it. Every machine runs the migrations it has not run yet, in order, and Laravel records which ran in a migrations table. Here is the shop:






Laravel’s schema builder hides SQL details. id() is a bigint primary key, and foreignId('customer_id')->constrained() adds the foreign key. On PostgreSQL a foreign key gets no index by itself (MySQL adds one), so ->index() adds it: every “orders of this customer” query needs it. One default needs correcting: timestamps() creates columns without a time zone, the type Chapter {{n-1}} warned against. timestampsTz() creates timestamptz.









Every migration can be undone, and you should try it once for every new migration on your machine, because a down that has never run is a down that does not work:






Professional habit: never edit a migration that has run elsewhere
Once a migration is merged, other machines have run it, and changing its file changes nothing there: their database and yours now differ, silently. Fix mistakes with a new migration. In CI, run php artisan migrate, migrate:rollback to the start, and migrate again on an empty database; it takes seconds and catches broken down methods.



{{n}}.2 Changing a live schema: expand and contract



Every product needs a SKU, a stock code, required and unique. Adding a required column in one step fails on a live system: existing rows have no value, and the code still running in production does not send one. The safe pattern is expand and contract:


    

  1. Expand: add the column as nullable. The running code ignores it.
    2. 

  2. Deploy code that writes it, and fill it for the existing rows.
    3. 

  3. Contract: make it required and unique.
    4. 










chunkById fills the rows 500 at a time, so a large table is never loaded into memory at once. On a table of millions of rows, run the backfill as a separate command or job rather than inside a migration. The same pattern renames a column (add the new one, write both, backfill, read the new one, drop the old one) without the shop ever stopping.



{{n}}.3 Models and relationships



Each table gets a model. Relationships are methods that return relationship objects:






    

  • belongsTo on the side with the foreign key (an order belongs to a customer), and hasMany on the other (a customer has many orders).
    • 

  • belongsToMany for many-to-many, through order_items. withPivot brings the joining table’s own facts, the quantity and the price at the time, onto each product as $product->pivot.
    • 

  • A cast converts a column when it is read and written. The status column holds text; the model gives you the OrderStatus enum from Chapter 2, with its labels.
    • 

  • A scope is a named, reusable condition, marked with #[Scope]: Order::shipped().
    • 

  • An attribute such as total is computed from the items when read: $order->total. It is not stored, so it cannot disagree with them.
    • 




{{n}}.4 Seeing the SQL



Every query Laravel sends passes through the database layer, and DB::listen can watch them. The book’s Artisan commands collect the SQL of each piece of work:









Order::with(['customer', 'products']) asks for the relationships up front: one query for the order, one for its customer, one for its products with the pivot columns. Three queries, whatever the number of products. Read the SQL Eloquent writes now and then: it is the best way to understand what your code costs.



{{n}}.5 The N+1 problem



A report lists every shipped order with its products. Written the natural way, it loads the orders, then touches $order->products for each one, and Eloquent loads them lazily, one order at a time:









Lazy: one query for the orders and one more for each of the 200 orders, 201 queries. Eager, with with('products'): two queries, the orders and then all their products with WHERE order_id IN (…). Several times faster on a database on the same machine; across a network, the difference grows to seconds. This is the N+1 problem, the most common performance bug in Laravel applications, because every line looks innocent.



Laravel can turn it into an error. In the service provider:









In development and tests, the lazy version now fails at once, naming the relationship and the model, so the N+1 is fixed before it ships. In production the setting is off, so a missed case slows a page down instead of breaking it.

{{n}}.6 Mass assignment



Product::create($request->all()) would let a client set any column it names, including ones it must never touch. $fillable lists the attributes that may be set from an array; everything else is ignored, or, with preventSilentlyDiscardingAttributes, refused loudly:






The first line shows the fillable attributes being set. The second call tried to set id, and in development Laravel refused instead of silently dropping it, so a typo or a forgotten field in $fillable is noticed at once. Combine it with Chapter {{n-3}}’s rule: pass $request->validated(), never $request->all().



Tip: Model::shouldBeStrict()
One call, Model::shouldBeStrict(! app()->isProduction()), turns on three protections together: no lazy loading, no silently discarded attributes, and an error when you read an attribute that was not selected. Put it in a service provider of every new project.

Summary



    

  • Laravel talks to PostgreSQL through .env settings; migrations are ordered, recorded, reversible schema changes. Never edit one that ran.
    • 

  • Expand and contract changes a live schema in compatible steps; chunkById backfills safely.
    • 

  • Models declare relationships: belongsTo, hasMany, belongsToMany with withPivot.
    • 

  • Casts, scopes and computed attributes keep domain rules on the model.
    • 

  • DB::listen shows the SQL; count queries before you trust a page.
    • 

  • N+1: one query per row. with() loads relationships together; preventLazyLoading makes the mistake an error in development.
    • 

  • $fillable and preventSilentlyDiscardingAttributes stop mass assignment.
    • 




Quick check answers: 1. $order->products is the loaded collection of products (loaded now, lazily, if it was not eager loaded); $order->products() is the relationship object, a query builder you can add conditions to, such as $order->products()->where('price', '>', 10000)->get(). 2. Without eager loading, 1 + 50 = 51; with with('customer'), 2. 3. timestamps() creates timestamp columns without a time zone, which store a clock reading without saying where; timestampsTz() creates timestamptz, an exact instant.

Project {{n}}.3 · Challenge


A rename without downtime


Rename customers.name to full_name while a script reads and writes customers in a loop, without a single error.


You will practise: expand and contract, accessors for dual reading, backfilling in chunks, and verifying compatibility.


    

  1. Write a command that creates and reads customers in an endless loop and reports any exception.
    2. 

  2. Expand: add full_name. Change the model so it writes both columns (a model event in booted()) and still reads name.
    3. 

  3. Backfill full_name with chunkById in a separate command.
    4. 

  4. Switch reading to full_name; then contract: make it required and drop name.
    5. 

  5. Keep the loop running through every step, and check it never reported an error.
    6. 



Hint: at each step, ask: “if the previous version of the code were still running, would it work?” A step that fails that question needs to be split.
