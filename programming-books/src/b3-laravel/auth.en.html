Chapter {{n}}

Authentication and Authorization with Sanctum

In this chapter you will learn to

  • tell authentication (who are you?) from authorization (may you do this?)
  • store passwords so that a stolen database does not reveal them
  • register and sign users in with Sanctum’s API tokens, without telling attackers which emails exist
  • revoke tokens, and understand when a JWT is the better choice
  • protect routes with gates and policies, by role and by ownership
  • slow down password guessing, and test all of it automatically

Until now, anyone could call every route of the shop’s API. A real shop needs to know who is calling: a customer sees their own orders and no one else’s, and only staff may see the list of customers. Getting this right is not hard, but almost every mistake in it is a security incident, and the mistakes are invisible until someone exploits them. Laravel gives you most of the pieces; this chapter puts them together with Sanctum, PostgreSQL and a fresh project, and runs every request against the real server.

Years ago a site I used was breached, and the attackers published its user table. My password was right there, in plain text, next to my email. It was the same password I used on two other sites. That afternoon I changed seven passwords, and I promised myself that no table I build would ever hold one.

{{n}}.1 Two questions

Every protected request answers two separate questions, in order:

  • Authentication: who is calling? The client proves an identity, with a password once and then with a token on every request. If it cannot, the answer is 401 Unauthorized (a confusing name: it means “not authenticated”).
  • Authorization: may this user do this? The identity is known; the rules decide. If they say no, the answer is 403 Forbidden, or 404 Not Found when even the existence of the thing is private.

Laravel keeps them apart too: guards and the auth middleware answer the first question; gates and policies answer the second.

{{n}}.2 Storing passwords

A password must never be stored as it is, and never with an ordinary hash such as SHA-256 either. A fast hash is the problem: a graphics card computes billions of SHA-256 hashes a second, so an attacker with a stolen table tries every common password against every row in minutes. Password storage needs a hash that is slow on purpose: bcrypt, Argon2 or scrypt. Laravel’s Hash facade uses bcrypt by default, and the User model hashes automatically, because its password attribute has the hashed cast. A small Artisan command shows what it produces:







    

  • $2y$ names the algorithm (bcrypt), 12 is the cost (212 rounds), and the next 22 characters are the salt: random, different for every hash. Two users with the same password get different hashes, so an attacker must attack each row separately, and precomputed tables of hashes are useless.
    • 

  • Because the cost is inside the string, raising it later (BCRYPT_ROUNDS in .env) does not break old hashes; they can be upgraded when their owner next signs in (exercise 3).
    • 

  • One hash took about a quarter of a second: nothing for a user signing in, a great deal for an attacker trying a billion guesses. Hash::check compares in constant time, so the time taken reveals nothing about the stored value.
    • 




Watch out: never write your own crypto
Hash, Str::random() and hash_hmac are written and reviewed by specialists. Combining well-known pieces in the standard way is fine; inventing your own hashing scheme, your own encryption or your own token generator is not. rand() and mt_rand() are never acceptable for anything secret: they are predictable. Use random_bytes() or Str::random().

{{n}}.4 Registering and signing in



Registration validates the body, and User::create hashes the password through the cast. Emails are stored in lower case so that Lina@Example.com and lina@example.com are one account. The unique rule gives a friendly message, but it checks and then inserts, a race from Chapter {{n-2}}: the unique index on the column is what really decides, and the exception it throws becomes a 409:









Signing in is where attackers probe. Two details stop the login route from telling them which emails have accounts:






    

  • The same answer for an unknown email and a wrong password: “email or password is wrong”, never “no such user”.
    • 

  • The same time. Without a dummy hash, an unknown email would answer at once and a known one after a quarter of a second, and the time alone would reveal which emails exist. Checking against a dummy hash, made once per process, makes both cost one hash.
    • 







The token has two parts: the id of its row, and a secret of 40 random characters followed by an 8-character checksum (which lets secret scanners recognise a leaked token). Sanctum stores only the SHA-256 hash of the secret, so someone who reads the table cannot use what they read. A fast hash is right here, unlike for passwords: the token is random, not a word a person chose, so there is nothing to guess. The token was created with an expiry of 30 days.






Signing out deletes the token’s row, and it stops working at once. The database keeps only hashes, of passwords and of tokens:









What about JWTs?



A JSON Web Token takes the opposite approach: instead of a random key into a table, the token contains the data (the user id, the role, the expiry), signed with the server’s secret so that it cannot be changed. Here is one made by hand, to see what is inside:









Changing the role to admin broke the signature, so a JWT cannot be forged. But anyone can read it, and the server checks it without looking anything up, which is both its strength and its weakness: it cannot be revoked. A user who signs out, changes their password or loses their role keeps a valid token until it expires. JWTs fit messages between your own services and short-lived tokens (minutes); for users of your own apps, Sanctum’s revocable tokens are simpler and safer. Never put a secret in a JWT payload.



Note: Sanctum for your own website
A mobile app keeps the token in the phone’s secure storage and sends it in the Authorization header, as curl does here. A website should not keep a token where scripts can read it. For a single-page app on your own domain, Sanctum has a second mode: the app signs in through Laravel’s ordinary session, held in an HttpOnly, Secure, SameSite=Lax cookie, and auth:sanctum accepts either the cookie or a token. You list the website’s domain in SANCTUM_STATEFUL_DOMAINS. Cookies bring a risk of their own, cross-site request forgery, which Chapter {{n+1}} deals with.



{{n}}.5 Authorization: gates and policies



Authentication found the user; now the rules decide what that user may do. A gate is one named yes-or-no rule, good for whole areas such as an admin section; it is defined once, in a service provider, and the can:admin middleware in the routes applies it:






A policy groups the rules for one model. Laravel finds OrderPolicy for the Order model by its name, and Gate::authorize('view', $order) in the controller calls its view method:












    

  • The list of orders goes through the relationship, $request->user()->orders(), so the query itself is limited to the user’s rows. Loading every order and filtering in code risks returning too much the day someone changes it.
    • 

  • Omar asking for Sara’s order gets 404, exactly as for an order that does not exist: Response::denyAsNotFound(). A 403 would confirm that order 1 exists, and ids that count up would let him learn how many orders the shop has.
    • 

  • The admin list returns 403: Omar knows the route exists, and he is told he lacks the role.
    • 

  • These are Laravel’s default JSON errors, {"message": …}; with Chapter {{n-5}}’s exception renderer they become Problem Details like every other error.
    •

{{n}}.6 Slowing down guessing



A slow hash protects a stolen table; the running server needs protection too, against a script that tries passwords one after another. The login rate limiter (Chapter {{n-6}} introduced rate limiters) is keyed on the client’s address and the email, so one attacker cannot try thousands of passwords on one account:









The sixth attempt was refused before its password was even checked. The limiter counts in the cache store, so with Redis (Chapter {{n-1}}) every server shares the count. Locking the account after a few failures is tempting but lets anyone lock out any user by typing wrong passwords for them; rate limits slow the attacker without punishing the owner. Adding a second factor (a code from an app) is the strongest protection of all.



{{n}}.7 Testing it



Security rules are exactly the kind of code that breaks silently, so each rule gets a test. The tests sign in through the real login route and use the token, as a client would:









Note what is tested: not only that the right user gets in, but that the wrong ones are kept out. A test suite that checks only the happy path would pass for an API with no security at all. (For tests that do not care how the user signed in, Sanctum::actingAs($user) skips the login.)



Professional habit: test the “no” for every route
For every protected route, write at least two tests: one without a token (401) and one as a user who must not have access (403 or 404). Add them in the same pull request as the route. The day someone removes a middleware or changes a query, these tests fail, which is far cheaper than finding out from a customer who saw someone else’s order.

Summary



    

  • Authentication finds out who is calling (401 if unknown); authorization decides what they may do (403, or 404 to hide existence).
    • 

  • Passwords are stored with a slow, salted hash: bcrypt through Hash and the hashed cast.
    • 

  • Sign-in gives the same answer and the same time for a wrong email and a wrong password.
    • 

  • Sanctum tokens are random, stored only as a SHA-256 hash, given an expiry, and revoked by deleting the row.
    • 

  • A JWT carries signed data that anyone can read and nobody can revoke: good between services and for minutes, not for user sessions.
    • 

  • Gates for areas, policies for records; rate-limit login, and test every “no”.
    • 




Quick check answers: 1. A token’s random part is 40 random characters: there are far too many possibilities to try, so the hash only needs to stop someone who reads the table from using the values directly, and a fast hash does that. A password is chosen by a person from a small set of likely words, so an attacker can try the likely ones quickly unless each try is made deliberately slow. 2. 403 Forbidden: the server knows exactly who is calling (the token is valid), so the problem is not authentication; the user lacks the admin role. 3. So that the response takes the same time whether or not the email exists; otherwise an unknown email would be answered much faster, and the time would reveal which emails have accounts.
