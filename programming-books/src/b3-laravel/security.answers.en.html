1. A binding can only stand for a value; ORDER BY ? would sort by a constant string, the same for every row, and column names are part of the SQL itself. Validate the input against a fixed list, 'sort' => ['nullable', Rule::in(['name', 'price'])], and pass only the validated value to orderBy() (not orderByRaw), which also quotes it as an identifier. Anything else is refused with 422.
  2. CORS is enforced by browsers, and only for reading responses. Anyone can call the route with curl, a script or another server, none of which care about CORS; and even a browser on another site can still send many requests. Protection of data and actions comes from authentication and authorization on the server. CORS only decides which websites’ scripts may read the answers in a user’s browser.
  3. The browser first sends OPTIONS with the origin, the method it wants and the headers it wants to send; only if the answer allows all three does it send the real PATCH: 
    
204: no body, only permission. Access-Control-Allow-Origin names the shop’s site, so this origin may read the answers. Access-Control-Allow-Methods lists GET and PATCH, from config/cors.php. Access-Control-Allow-Headers allows content-type, which a JSON body needs. Access-Control-Max-Age: 0 tells the browser not to remember the answer; raising max_age in the configuration lets it skip the preflight for a while.

  4. {!! !!} inserts the name as HTML, so the browser creates an image with an invalid source, its onerror handler runs in the admin’s session, and any cookie that scripts can read goes to the attacker; a script could also act as the admin directly. Each defence stops part of it: {{ $product->name }} shows the name as text (the real fix); a Content Security Policy without 'unsafe-inline' refuses inline handlers, and connect-src refuses the request to another site; Laravel’s session cookie is HttpOnly, so scripts cannot read it; and validation could refuse < and > in product names. Layers, because any one of them might be missing one day.

(1) An internal address (http://localhost:6379, http://10.0.0.5/admin, the cloud metadata address http://169.254.169.254/) makes the server reach services that are not public, and may return their answers or secrets: allow only https, resolve the host name yourself and refuse private, loopback and link-local addresses, and turn off redirects (Http::withoutRedirecting()) or check every hop the same way. (2) A huge or endless file ties up the server and fills the disk: Http::timeout(), a maximum size, and a check that the content really is an image. (3) A URL to a slow server keeps workers busy: short timeouts, and the download done in a queued job (Chapter {{n+1}}) rather than inside the request. Better still, have admins upload the file instead of giving a URL.
