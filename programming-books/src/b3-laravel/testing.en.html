Chapter {{n}}

Testing with Pest

In this chapter you will learn to

  • decide what to test with unit, feature and end-to-end tests
  • write expressive tests with Pest, including datasets for many cases
  • test routes against a real PostgreSQL test database
  • replace queues, mail and other edges with Laravel’s fakes, and control time
  • check rules about the code itself with architecture tests
  • read a failing test, and keep a suite fast, reliable and worth trusting

Every chapter so far ended with a few tests. This one is about the craft itself. A good test suite is what lets you change code on a Friday afternoon without fear: it tells you within a minute whether the shop still takes orders, still charges the right amount and still refuses what it must refuse. A bad one is slow, fails at random, and is ignored. Laravel comes with excellent testing tools; Pest, a test framework built on PHPUnit, makes them read almost like sentences.

I once worked on a project with two thousand tests that took forty minutes and failed at random about once a day. Nobody believed a red build any more, so real bugs went out with the noise. We deleted a third of the tests, made the rest use a real database properly, and got the suite under three minutes. It caught more bugs with fewer tests.

{{n}}.1 What to test, and at which level

  • Unit tests call one class or function directly, with no database, HTTP or clock. They are fast and point straight at the broken line. They suit logic with many cases: prices, discounts, rules, state changes.
  • Feature tests send a request through the whole Laravel stack (routing, middleware, validation, controller, database) and check the response and its effects. This is where most of a Laravel application’s tests belong, because most of its bugs live in queries, validation rules and authorization.
  • End-to-end tests drive the real application from the outside, often through a browser (Laravel Dusk, or Playwright from Book 2). Keep them for the few journeys that must never break.

Test each behaviour at the lowest level where a bug in it would actually show. A unit test with a mocked database cannot catch a wrong where; a feature test can.

{{n}}.2 Pest

Laravel’s skeleton ships with PHPUnit test classes. Pest runs the same tests, written as functions:




tests/Pest.php says which base class each folder uses; feature tests get Laravel’s TestCase and the RefreshDatabase trait. A test is it('does something', function () { … }) (or test(…)), and checks are written with expect($value)->toBe(…), in a chain that reads left to right. Everything from PHPUnit, including Laravel’s assertStatus and friends, keeps working.

{{n}}.4 Feature tests with a real database



The order route decrements stock and inserts the order in a transaction, then dispatches a confirmation job after the commit (Chapter {{n-2}}):






Laravel’s skeleton runs tests on an in-memory SQLite database. It is fast, but it is not the database the shop runs on: PostgreSQL behaves differently in types, locking, case sensitivity and many functions. In phpunit.xml, the tests point at a separate PostgreSQL database, shop_test, so that they never touch development data. RefreshDatabase migrates it once and wraps every test in a transaction that is rolled back afterwards, so each test starts clean and fast:






    

  • Checking the effects, not just the response. The first test checks the status and body, the stock left in the database and the job queued; the second checks that a refused order left the stock and the orders untouched, which is the transaction of Chapter {{n-6}} doing its job.
    • 

  • Fakes at the edges. Queue::fake() records jobs instead of pushing them to Redis, and Queue::assertPushed checks them, with a closure for the details. Laravel has the same for Mail, Notification, Event, Bus, Storage and Http (which fakes calls to other services). Each fake replaces something slow or with effects outside the system.
    • 

  • Refusals are tested too. A 409, a 422 with the field named, and in a real suite the 401 and 403 of Chapter {{n-4}}.
    • 




Watch out: fake the edges, not the middle
Fake what is slow, outside your control or has effects in the world: email, queues, payment providers, other companies’ APIs, the clock. Do not mock your own models, the database or Eloquent itself: tests full of mocks pass while the real thing is broken, and break whenever the code is reorganised even when nothing is wrong. If a test needs ten mocks, the code under test probably does too much.



{{n}}.5 Controlling time



A basket left alone for 30 minutes is released. Testing that by waiting is absurd, and testing it with the real clock is fragile. Laravel’s tests can move the application’s clock:






$this->travel(30)->minutes() moves now() forward, and the clock returns to normal after each test; $this->freezeTime() stops it. The two tests check both sides of the boundary, 29 and 30 minutes, which is where off-by-one bugs live. This works because the code asks now() for the time instead of PHP’s time().

{{n}}.8 A suite worth trusting



    

  • Fast. A suite that runs in seconds is run before every commit. RefreshDatabase’s transactions keep feature tests fast; pest --parallel runs files in several processes, each with its own copy of the test database.
    • 

  • Deterministic. The same code gives the same result every time. Flaky tests usually come from shared data, the real clock, random values, results without orderBy, or work left running. Fix them at once, or delete them: a flaky test teaches the team to ignore red.
    • 

  • Testing behaviour. Assert what the caller sees (responses, rows, jobs, emails), not how the code is arranged inside. Then the code can be improved without rewriting the tests.
    • 

  • Measured. pest --coverage (with the PCOV or Xdebug extension) shows untested code; use it as a flashlight to find gaps, never as a number to chase. A test with no expectations reaches 100% too.
    • 

  • Run on every change. In CI, on every pull request, against a real PostgreSQL started as a service, and the merge blocked while it is red.
    • 




Professional habit: a failing test first, for every bug
Before fixing a bug, reproduce it with a test and watch the test fail for the right reason. Only then fix the code and watch it pass. It takes a few minutes, it often reveals that the bug is not where you thought, and it adds to the suite exactly the case that real life proved you had missed.

Summary



    

  • Unit tests for logic with many cases, feature tests for routes, validation and queries, a few end-to-end tests for the main journeys.
    • 

  • Pest writes tests as functions with expect() chains, and datasets run one test per case.
    • 

  • Feature tests run on a real PostgreSQL test database; RefreshDatabase keeps every test independent.
    • 

  • Fakes replace the edges (queues, mail, HTTP, events); travel() controls time.
    • 

  • Architecture tests enforce rules about the code; failures name the behaviour and show the difference.
    • 

  • A fast, deterministic suite, run on every change, is what makes the tests trustworthy.
    • 




Quick check answers: 1. The shop runs on PostgreSQL, which differs from SQLite in column types, case-sensitive comparisons, locking, JSON and date functions; a query or migration can pass on SQLite and fail in production. Testing on the same database removes that whole class of surprise. 2. Dispatched jobs are recorded in memory instead of being pushed to Redis and run, so the test can assert which jobs were dispatched without a queue or a worker. The queue is an edge with effects elsewhere; the database is where the bugs worth catching live, so it stays real. 3. It runs the migrations once for the whole run, then starts a transaction before each test and rolls it back afterwards, so every test sees the same empty, migrated database.
