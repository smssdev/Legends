Chapter {{n}}

Designing REST APIs with API Resources

In this chapter you will learn to

  • name resources and URLs so that an API can be guessed instead of memorised
  • control the JSON your API sends with API Resources, separate from how data is stored
  • page through lists with cursors that never repeat or skip a row
  • return every error in one standard format, Problem Details
  • make retries safe with idempotency keys, and stop lost updates with If-Match
  • generate the API’s documentation from its code, and test it all

An API is a product, and its users are developers. They judge it the way you judge a library: can I guess how it works, does it tell me clearly what I did wrong, and will it break my app next month? Chapter {{n-3}} taught you the protocol, and Chapter {{n-1}} the framework. This chapter is about the decisions on top of them, which are cheap to get right at the start and very expensive to change once other teams depend on them. We build version 1 of Bit’s shop API properly, with products and orders in a real database.

The first public API I designed had /getProducts, /product_list and /Products/All, written by three people in three weeks. Every client needed our help to use it, and we could never remove anything. Consistency is not about taste: it is what lets strangers use your work without asking you.

{{n}}.1 Resources and URLs

REST organises an API around resources: the nouns of your domain, such as products and orders. URLs name the resources; methods say what to do with them. The rules that make an API guessable are few:

  • Nouns, plural, lower case: /products, /orders. The method is the verb: GET /products, not /getProducts.
  • One resource: the collection plus an id, /products/2.
  • Nesting for ownership, one level deep: /orders/7/items is fine; /customers/3/orders/7/items/2 is not.
  • Actions that are not create, read, update or delete become a sub-resource with POST: POST /orders/7/cancel. Do not hide them in a PATCH that sets status: cancelling has rules (restore the stock, refund the payment) that a generic update would skip.
  • A version in the path: /api/v1/.... Make every change additive if you can; when a breaking change cannot be avoided, publish /v2 beside /v1 and announce the end of /v1 with the Deprecation and Sunset headers.



Products are read and updated through a resource controller. Orders have their own controller; Route::controller groups its routes, and the cancel action is a sub-resource. Creating an order goes through an extra middleware, Idempotent, which we write in {{n}}.5.

{{n}}.4 Lists: filters, sorting and cursor pages



Everything a client may send to the list is in a form request, with limits on every value:






Only four sort orders exist. An API that sorts by any field the client names can be asked to sort by a column without an index, which makes a slow query one attacker can repeat a thousand times a minute.



The obvious way to page is an offset, ?page=2, meaning “skip the first 20”. It has two problems: the database must still walk past every skipped row, so deep pages are slow; and the pages drift when rows are added or removed between two requests, so a user sees one product twice, or never. A cursor says “continue after this row” instead, so new rows before it change nothing. Laravel builds cursors with cursorPaginate:






The second orderBy matters. A cursor needs a complete order: two products with the same price must still have a fixed place, or a row could move from one page to the next between requests. Ordering by price and then by id makes every position unique, and the migration’s index on (price, id) lets the database find it directly. Here is the client’s side:






The first page carries the link to the next one, so clients never build URLs themselves; they follow links.next until it is null. With a filter and a sort, the cursor carries the price as well as the id, and withQueryString keeps the filter in the link. The cursor is base64-encoded JSON: anyone can decode it, so it is not a secret. Document it as an opaque token that clients must send back unchanged, so that the server stays free to change what is inside.

{{n}}.5 Errors: Problem Details



Laravel’s default error answers, which you saw in Chapter {{n-1}}, have a shape of their own. Every API with its own shape forces every client to learn it. Problem Details (RFC 9457) is the standard shape for HTTP API errors, sent with the content type application/problem+json: a type URL that identifies the kind of problem and leads to its documentation, a short title, the status, a detail for this case, and the instance, the request that failed. Extra members are allowed, such as a list of errors.



A problem is an exception that knows how to render itself:






One class decides how every other exception becomes a problem: validation errors, models that were not found, rate limits, other HTTP errors, and anything unexpected as a plain 500. It also makes the problems the API throws on purpose, so no controller invents a new status code or a new shape:






match (true) takes the first arm whose condition holds, a common PHP idiom for a list of type checks. The texts come from a language file, lang/en/problems.php, read by __('problems.stale') in the app’s language. And one line in bootstrap/app.php sends every exception in the API through it:









Every error, from validation to a missing model, now has the same shape. Laravel answers 422 for every validation failure, of the query or of the body; some APIs prefer 400 for a malformed query, but what matters most is that your API always does the same thing.



{{n}}.6 Safe retries: idempotency keys



Chapter {{n-3}} warned that a retried POST can create an order twice. The standard answer, used by payment providers such as Stripe, is an idempotency key: the client creates a unique value (a UUID) for each intended operation and sends it in an Idempotency-Key header. If the same key arrives again, the server does not do the work again; it replays the answer it gave the first time. This is a job for middleware, because it wraps the controller without the controller knowing:






    

  • A lock on the key makes a second request that arrives while the first is still running get a 409, instead of doing the work twice. Cache::lock works across all the PHP processes of a server, because the lock lives in the cache store (here the database; Redis in Chapter {{n+4}}).
    • 

  • A fingerprint of the body is kept with the answer. The same key with a different body is a bug in the client, and gets a 422, never a silent replay of a different order.
    • 

  • Only successful answers are kept, for a day. A request that failed may be tried again with the same key.
    • 




The controller creates the order inside a database transaction: either every change happens, or none does:






The stock is taken with one conditional statement, “decrease the stock by 2 where the stock is at least 2”, and the number of changed rows says whether it worked. Reading the stock first and writing it afterwards would let two orders both see the last kit and both take it; Chapter {{n+3}} explains why, and the other tools for it. If anything throws, the transaction is rolled back, so an order that fails on its third item gives back the stock of the first two. And the prices come from the database: a client never tells the server what something costs.






The second request got the same order, with the same id and time, and a header saying it was replayed. The stock went down by 2, not by 4. The other business rules return problems too:






{{n}}.7 Lost updates: ETag and If-Match



Two administrators open product 2 at the same time. Sara changes the price to 65.00 and saves; a minute later Omar, whose screen still shows the old product, changes it to 70.00 and saves. Sara’s change is gone, and nobody was told. This is the lost update problem. HTTP solves it with the ETag from Chapter {{n-3}}: the product’s version is its ETag, and a change must send back, in If-Match, the version it was based on:






show sets the ETag, and Symfony’s isNotModified turns the answer into an empty 304 when the client already has this version. update refuses a request without If-Match, and then changes the row only if its version is still the one the client read, raising it by one in the same statement. If no row changed, someone else got there first:






This is optimistic concurrency: nothing is locked while people look at a screen, and the rare conflicts are detected when they happen. The client that gets 412 reloads the product and shows the user what changed.



{{n}}.8 Documentation from the code



Documentation written by hand drifts away from the code within weeks. Scramble reads the routes, the form requests and the resources, and writes an OpenAPI document from them, a standard, machine-readable description of the API:









On a developer’s machine, Scramble also serves a documentation page at /docs/api. From the same document, tools can generate typed clients in many languages, and a check in CI can refuse a pull request that removes something clients depend on. (Scramble lists the update route as PUT; Laravel accepts PATCH on the same route.)



Professional habit: design the API before you build it
Write the request and response examples for a new endpoint first, in the pull request, and get a review from someone who will use the endpoint, such as a front-end or mobile developer. Changing an example takes minutes; changing a published API takes months of versions and deprecation emails.

Summary



    

  • Resources are plural nouns, methods the verbs, special actions sub-resources with POST. Version in the path; prefer additive changes.
    • 

  • Migrations describe tables, models read and write them, seeders fill them.
    • 

  • API Resources separate the representation from storage: UTC times, money as amount and currency, internal columns hidden.
    • 

  • Cursors page without drift over a complete order (sort field plus id), with links clients follow.
    • 

  • Every error is Problem Details, from one renderer and one set of factory methods.
    • 

  • An idempotency middleware with a lock and a fingerprint makes retries safe; transactions and conditional updates keep stock correct.
    • 

  • ETag and If-Match with an atomic version check prevent lost updates.
    • 

  • Scramble generates OpenAPI from the code; feature tests with RefreshDatabase pin the behaviour.
    • 




Quick check answers: 1. POST /orders/7/cancel: cancelling is an action with its own rules (restore the stock, refund, check that the order can still be cancelled), and a dedicated endpoint can enforce them and be documented and permitted separately; a generic PATCH would let a client set any status. 2. Products with the same price would otherwise have no fixed order, so a row could move between pages and the cursor could not say exactly where to continue. 3. The version is an internal detail of how the server detects conflicts; clients see it only as the ETag, so the server can change how versions work without changing the JSON.
