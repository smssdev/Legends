Chapter {{n}}

Laravel Essentials: Routes, Controllers and Requests

In this chapter you will learn to

  • create a Laravel project and find your way around its folders
  • follow a request through Laravel, from the front door to your controller and back
  • write routes and resource controllers, and see them with Artisan
  • validate input with form requests, with messages written for your users
  • use the service container to give classes what they need, and swap it in tests
  • write middleware, limit request rates, keep configuration in one place, and test the API

In Chapter {{n-2}} we built the shop’s API in one PHP file, and every line was ours: reading the method and path, checking the body, sending the status and headers, catching errors. Laravel does all of that, and does it consistently for every route you will ever add. This chapter rebuilds the same API in Laravel, so you can see exactly which of our hand-written parts each Laravel feature replaces, and where your own code now lives.

My first Laravel project felt like magic: a controller method returned an array, and JSON came out. Magic is pleasant until it breaks. The day I followed one request through the framework, from public/index.php to my controller, Laravel stopped being magic and started being a tool I understood.

{{n}}.1 A new project

Composer creates a Laravel project from the official starter, downloads the framework and its packages into vendor/, writes a .env file with a fresh secret key, and prepares a small SQLite database:




The folders you will work in:


    

  • app/: your code. Controllers, models, middleware and your own classes, under the namespace App\.
    • 

  • routes/: which URL goes to which code. web.php for pages, api.php for the API.
    • 

  • config/: one PHP file per subject (database, cache, mail…), each returning an array of settings.
    • 

  • bootstrap/app.php: how the application is put together: routes, middleware, error handling.
    • 

  • public/: the only folder a web server shows. Its index.php is the front door for every request.
    • 

  • database/, resources/, storage/, tests/: migrations, views and translations, files the app writes, and tests.
    • 




A new project has no API routes yet. One Artisan command adds routes/api.php, and also installs Sanctum, the token authentication we use in Chapter {{n+6}}:






Artisan is Laravel’s command line, the php artisan you will type all day: it creates files, runs migrations and tests, and shows what the app knows about itself.



{{n}}.2 The life of a request



Every request enters through public/index.php, which loads Composer’s autoloader and the application defined in bootstrap/app.php:






Read it as a description, not as code that does work: the app has web and API routes, a health check at /up, two pieces of middleware we added for the API, and a rule that API errors are answered as JSON. From there, a request goes through a pipeline of middleware, then the router finds the route, then the controller runs, and the response travels back out through the same middleware.



You can see that pipeline for real. When debugging is on, Laravel’s error answers include a stack trace, the list of functions that were running. Read from the bottom, it is the path of the request. This little jq filter keeps only the middleware and controllers:






Every class on that list is something our Chapter {{n-2}} server did by hand, or did not do at all: proxies and CORS, maintenance mode, a body size limit, trimming spaces from input and turning empty strings into null, the rate limit, route parameters, our own timing middleware, and finally our controller. Each is a small class with one job, and you can add, remove or reorder them in bootstrap/app.php.



{{n}}.3 Routes and controllers



The routes file says which code answers which method and path:






Everything in api.php gets the prefix /api and the API middleware group. Route::apiResource registers the five standard routes of a resource at once, following the conventions of Chapter {{n-2}}, and where limits {product} to digits. Artisan shows what Laravel made of it:






Artisan also writes the empty classes, in the right folders and namespaces:






The controller holds one method per route. It stays thin: it reads the request, asks someone else to do the work, and builds the response.






    

  • The route parameter {product} arrives as the argument $product, by name.
    • 

  • $request->integer('max_price', PHP_INT_MAX) reads a query value as an int, with a default: no $_GET, no casting by hand.
    • 

  • abort(404, …) stops the request with that status from anywhere, and the exception handler turns it into a JSON answer.
    • 

  • route('products.show', 4) builds the URL from the route’s name, so URLs are never written twice.
    • 

  • $this->json is a small helper of ours. By default, Laravel writes JSON with every non-English letter escaped as ك: valid, but unreadable for people. The flag JSON_UNESCAPED_UNICODE keeps Arabic as Arabic, as in Chapter {{n-2}}.
    • 




{{n}}.4 The service container



The controller’s constructor asks for a ProductCatalog, and nobody calls new ProductController. Laravel’s service container builds the controller: it reads the constructor’s types, builds what each parameter needs (and what those need, all the way down), and passes them in. This is dependency injection: a class says what it needs, and does not go looking for it.



ProductCatalog is an interface, a contract that says what a catalog can do, not how:






The container cannot build an interface, so we tell it which class to use, in a service provider, a class Laravel runs at start-up to register things:






The real catalog keeps products in a JSON file, under a lock, exactly like Chapter {{n-2}}’s server. Because PHP forgets everything between requests, storage must live outside the process:






Every change goes through this one method: it opens the file, waits for the lock, lets the caller edit the data, and writes it back. create, update and delete only describe the edit.



Why the interface? Because the controller does not care where products are kept. In Chapter {{n+3}} we write a catalog backed by the database and change one line in the provider; no controller changes. And in tests, we can give the controller a different catalog, as you will see in {{n}}.8.

{{n}}.5 Requests and validation



Start the server in its own terminal. php artisan serve runs PHP’s development server from Chapter {{n-2}}, pointed at public/index.php:






Reading works as before:






Input is checked by a form request, a class that holds the rules for one kind of request. When a controller method asks for it, Laravel validates the request before the method runs; if anything is wrong, the method never runs, and the client gets a 422 with every error:






The rules read almost like English: required, a string, at most 80 characters; an integer of at least 1. sometimes means “check it only if it was sent”. authorize answers whether this user may make this request; Chapter {{n+6}} fills it in. And messages replaces Laravel’s generic texts with ones written for your users:






In the controller, $request->validated() returns only the fields that have rules. If a client sends "id": 1 or "is_admin": true as well, it is simply not there. Never pass $request->all() to storage: that is how attackers set fields you never meant to accept.



The update request allows every field to be missing, but not all of them at once. An after hook runs once the rules have passed, for checks that involve the whole request:









And because of the where on the route, a product id that is not a number does not even match the route, so the controller’s int parameter is always safe:

A middleware wraps every request in a group. It can look at the request, refuse it, change it, and look at the response on the way back. Ours measures how long the application took and reports it in a Server-Timing header, which browsers’ developer tools display:

{{n}}.7 Configuration and the environment



Settings that change between machines live in .env. But application code never reads .env directly: it reads config/ files, and only those read the environment, once:









The reason is speed. In production, php artisan config:cache combines every config file into one cached array, and from then on .env is not even loaded: an env() call in a controller would quietly return null. Code that reads config('shop.requests_per_minute') works the same with and without the cache.



One setting deserves special care. With APP_DEBUG=true, as on your machine, every error answer includes the exception class, the file, the line and the whole stack trace:






That is a gift to an attacker: file paths, versions and the internal structure of your code. With APP_DEBUG=false, as production must have, the same request answers only this:






Watch out: APP_DEBUG in production
A production server with APP_DEBUG=true shows its stack traces to everyone, and on error pages can even show environment values such as database passwords. Make it part of your deployment checklist, and check it from outside after every deployment: request an address that does not exist and read the answer.



{{n}}.8 Testing the API



Laravel’s feature tests send requests through the whole application, middleware and all, without starting a server. Each test gets a fresh application, and our setUp uses the container to give every test its own empty catalog file, so tests never share data:









$this->app->instance(...) replaces what the container gives for ProductCatalog, for this test only. That is the second reason for the interface: the controller under test does not know, and does not care, which catalog it got. Chapter {{n+10}} covers testing in depth, with Pest.



Professional habit: thin controllers
A controller method should fit on a screen: read the validated input, call one service, return a response. Rules about products (stock, prices, who may do what) belong in classes the controller calls, where every route, job and command can use them and tests can reach them directly. When a controller method grows past twenty lines, the extra lines are usually a service waiting to be extracted. Chapter {{n+12}} turns this habit into an architecture.

Summary



    

  • composer create-project laravel/laravel makes a project; Artisan creates files and shows routes, config and more.
    • 

  • A request enters public/index.php, passes through a pipeline of middleware, reaches the router and the controller, and returns the same way. bootstrap/app.php describes it all.
    • 

  • Routes map method and path to code; apiResource registers a resource’s five routes; where constrains parameters.
    • 

  • Controllers stay thin. Form requests validate before the controller runs, with your own messages; validated() returns only checked fields.
    • 

  • The service container builds classes from their constructors; providers bind interfaces to classes; tests swap them with instance.
    • 

  • Middleware wraps requests; throttleApi limits rates with a limiter defined in a provider.
    • 

  • Code reads config, config reads .env. APP_DEBUG is false in production.
    • 

  • Feature tests send requests through the whole app without a server.
    •
