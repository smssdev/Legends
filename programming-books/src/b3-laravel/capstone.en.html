Chapter {{n}}

Capstone: A Production API

In this chapter you will

  • turn a short brief into the endpoints, tables and quality goals of a real API
  • build accounts, products and orders in one Laravel project, each with the techniques of its chapter
  • make an order happen exactly once, even when the client sends it twice
  • send the order’s email through a job that commits with the order, never before it
  • prove it with Pest against a real database, then run the whole system in containers
  • check the result against a production checklist, and know what is still missing

Each chapter of this book solved one problem on a small example: a route, a transaction, a lock, a token, a job, a metric. A real service needs all of them at once, and the hard part is not any single technique but how they fit together. In this last chapter we build Bit’s shop API in a new Laravel project and run it as a system of four containers: about 500 lines of PHP of our own, each line run, each test passed, and each answer below printed by the real server.

Every section says which chapter a decision comes from. When something feels new, that is your cue to go back and read that chapter again: you will understand it better now that you see where it fits.

{{n}}.1 The brief

The shop owner writes: “Customers should create an account, browse the products, and order. An order must never be charged twice, and they should get an email when it is placed. It has to stay up when we are busy.” As in every real project, the first job is to turn that into something testable:

As a customer, I want to…Done when…
create an account and sign inPOST /api/auth/register and POST /api/auth/login return a user and a token; a stolen database opens no account
browse the products, cheapest firstGET /api/products returns pages with a cursor; no product is skipped or repeated, however large the table
place an orderPOST /api/orders takes the stock and saves the order together, or does neither; the same request sent twice makes one order
get an email when I orderExactly one email per order, even if the email service or the worker is down for a while

And the qualities that every endpoint must also meet:

  • Safe: passwords hashed, tokens stored only as hashes, login attempts limited (Chapters {{n-9}} and {{n-8}}).
  • Consistent: stock never below zero, money in integers, no half-saved order (Chapters {{n-13}} and {{n-11}}).
  • Clear: every error in the same Problem Details form, every input validated (Chapter {{n-14}}).
  • Observable: structured logs, metrics and health checks from the first day (Chapter {{n-4}}).
  • Tested and shippable: tests against a real database, and one command to run everything (Chapters {{n-5}} and {{n-1}}).

{{n}}.5 Products, page by page



Laravel’s cursorPaginate is the keyset pagination of Chapter {{n-14}}: the cursor holds the last row’s price and id, and the next page asks for the rows after that pair. With the index (price, id) PostgreSQL jumps straight to the right place, so page 1000 costs what page 1 costs (Chapter {{n-3}}):






The second orderBy('id') is not decoration: two products may share a price, and without a second, unique key a page boundary between them would skip one or show it twice. cursorPaginate needs the order to be unique for exactly that reason.



{{n}}.6 Orders that happen once



The order is the heart of the shop, and the place where most of the book meets. Phones lose their connection mid-request; the app retries; the customer taps twice. If each request made an order, the customer would pay twice. The client therefore sends an Idempotency-Key header, a value it chooses once per order and repeats on every retry. The whole order is one transaction (Chapter {{n-11}}), and its first statement claims the key:






insertOrIgnore becomes INSERT … ON CONFLICT DO NOTHING on PostgreSQL, and the unique constraint does the hard work. If two copies of the same request arrive together, the second insert waits for the first transaction, then inserts nothing, and the code returns that order. No lock in the code, no race: the database already guarantees it. If the key comes back with a different body, the client has a bug, and saying so is better than guessing. The distinct rule refuses the same product twice in one order, which the table’s primary key would refuse less politely.



Then each line takes its stock with the conditional update of Chapter {{n-11}}: decrement on a query with where('stock', '>=', $quantity) returns how many rows changed. If any line is short, the Problem rolls the whole transaction back, the claimed key included, so the client may fix the order and retry with the same key:






Look at where the job is dispatched: inside the transaction. In Chapter {{n-7}} that would have been a mistake, and we wrote afterCommit(): with the Redis queue, a job pushed before the commit may run before the order exists, or exist for an order that rolled back. Here the queue connection is database, and the database queue writes the job as a row in the jobs table through the same connection, in the same transaction. The job exists if and only if the order does. That is the outbox pattern, with no extra table and no extra code.



The same line of code, SendOrderEmail::dispatch(), is right with one queue driver and wrong with another. Knowing why is what lets you choose: the database queue commits with your data; Redis is faster, but needs afterCommit() and accepts a small gap between the commit and the push.



The job itself carries only the order’s id and reads the rest when it runs, as in Chapter {{n-7}}. Its $tries and $backoff give a slow email service a few chances before the job is marked as failed:






The worker takes jobs with FOR UPDATE SKIP LOCKED, so several workers never run the same job. Delivery is at least once: a worker that crashes after sending but before deleting the job leaves it for the next one, and the email goes twice. A real email provider accepts an idempotency key too, and the order id is the natural one to give it.



Quick check
  1. Why is the key claimed with insertOrIgnore rather than by first checking whether an order with that key exists?
  2. An order has two lines, and the second is out of stock. What is left in the database afterwards, including the jobs table?
  3. Why may SendOrderEmail::dispatch() be called inside the transaction here, when Chapter {{n-7}} used afterCommit()?



{{n}}.7 Logs, metrics and health



One middleware, appended to every request, writes one JSON log line and increments one counter in Redis, keyed by method, route and status. Because it wraps the whole router, it also sees the 401s of auth:sanctum and the 429s of the rate limit, which happen before any controller runs:






The counters live in Redis rather than in PHP’s memory because PHP forgets everything between requests, and because every copy of the app must add to the same numbers (Chapter {{n-4}}). Measure::metrics() prints them in Prometheus’s text format. The routes add the two health endpoints: Laravel’s own /up says the process is alive, which is what Docker’s health check asks; /api/ready says it can do its work, which is what a load balancer asks:






{{n}}.8 Tests against a real database



The tests are Pest feature tests (Chapter {{n-5}}): real requests through the real routes, middleware and database. phpunit.xml points them at PostgreSQL’s shop_test database and the database queue, so a test can count the job rows. DatabaseTruncation migrates once and empties every table before each test, so each one starts with the same five products, with the same ids:






Each test states one promise from the brief. The most important is the first, which sends the same order twice and checks that there is one order, one stock deduction and one job:









Watch out: tests and real data
Our first version used RefreshDatabase, which wraps each test in a transaction and rolls it back. That is fast, but PostgreSQL sequences are not rolled back, so the products had new ids in every test and the tests that used ids 1 and 2 failed. Truncation resets them. Whatever you choose, the tests must use a database of their own, named in phpunit.xml: never let a test runner reach credentials for production, because emptying tables is exactly what tests do.



{{n}}.9 Shipping it



The Dockerfile has two stages. The first, from the official Composer image, installs the dependencies from the lock file, without the development ones, before copying the code, so that layer is rebuilt only when composer.lock changes (Chapter {{n-1}}). The second is PHP with Apache and the PostgreSQL driver, and receives only the finished application:






One line deserves attention: SetEnvIf Authorization …. Apache does not hand the Authorization header to PHP by default. Laravel’s public/.htaccess contains the same fix, but our configuration does not read .htaccess files. Without this line every login works and every authenticated request answers 401: exactly what the first recording of this chapter printed, until we added it.



Compose runs the four parts. The app and the worker are the same image with different commands, so they can never run different versions of the code. The settings come from the environment; APP_KEY is read from the .env file beside compose.yaml, which .dockerignore keeps out of the image:

Professional habit: a production checklist
Before a service takes real traffic, walk a short written list with the team: settings from the environment and secrets outside the image; migrations as a separate step; php artisan optimize when the container starts, so configuration and routes are cached; health and readiness probes wired to the platform; logs collected and an alert on the error rate and the latency; failed jobs watched; backups taken and a restore tried; rate limits on everything that costs money or guesses secrets; and a rollback that has been practised. The list is boring on purpose: incidents rarely come from clever bugs, mostly from a forgotten line on a list like this.



{{n}}.11 What you built



In about 500 lines of our own: accounts with hashed passwords and expiring tokens; product pages that stay fast at any size; orders that are atomic, idempotent and never oversell; emails whose jobs commit with the order; Problem Details for every error; logs, metrics and two kinds of health check; tests that prove each promise against a real database; and one image, run by Compose, with its database, Redis and worker.



What a production version would add, each from a chapter you have read: secrets from the platform, not from files (Chapter {{n-1}}); HTTPS and security headers in front (Chapter {{n-8}}); tracing across the worker (Chapter {{n-4}}); a smaller image with PHP-FPM or FrankenPHP if its size matters (Chapter {{n-1}}); and a CI pipeline that runs the tests, builds the image and deploys it. None of them changes the code you wrote; each one sits around it. That is the sign of a structure that is ready to grow.

Summary



    

  • Turn a brief into user stories with a test for “done”, and write the quality goals before the code.
    • 

  • Let the database guarantee what must always be true: unique keys, stock never below zero, one order per idempotency key.
    • 

  • Make retries safe with an Idempotency-Key: claim it in the order’s transaction, replay the same answer, refuse a changed body.
    • 

  • Know what your queue driver does with transactions: the database queue is an outbox; Redis needs afterCommit().
    • 

  • Keep shared state, such as rate-limit counts and metrics, in Redis, so any number of copies behaves as one.
    • 

  • Give every error one Problem Details shape, and every service logs, metrics, health and readiness.
    • 

  • Prove each promise with Pest against a real database, ship one image for the app and its worker, and migrate as a separate step.
    • 




Quick check answers: 1. Because checking first leaves a gap: two copies of the same request can both find no order with that key, and both create one. insertOrIgnore claims the key and checks it in one statement, and the unique constraint makes the second insert wait for the first transaction, then insert nothing. 2. Nothing from this order: the Problem rolls back the transaction, so the order row, its first line, the stock taken for it and the claimed key are undone, and since the job is dispatched after the loop, no job row was ever written (and if it had been, it would have rolled back too). 3. Because the queue connection is database: the job is a row written through the same connection, so it belongs to the same transaction and disappears if the order rolls back. With the Redis queue the push happens immediately and outside the transaction, which is why Chapter {{n-7}} needed afterCommit().
