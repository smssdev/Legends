Architecture: Keeping Code Easy to Change

In this chapter you will learn to

  • recognise the signs of a Laravel app that is getting hard to change
  • separate business rules from controllers, Eloquent and facades
  • write actions that orchestrate a use case through interfaces (ports)
  • use the service container as the composition root
  • organise code by feature, and enforce the boundaries with Pest architecture tests
  • know when a monolith is the right answer, and when to split

Laravel makes the first version of everything quick: a controller, a model, a facade call, done. That speed is a strength, and for small apps it is enough. As the shop grows, the same habits produce controllers that validate, query, price, email and format in one method, and a pricing rule that appears again, slightly different, in a job. Such code works; it is just harder to change every month. Architecture is the set of decisions about where each kind of code lives, so that the shop’s rules can be understood, tested and changed without touching everything else. This chapter rebuilds the order feature as one module with clear layers, small enough to read whole.

The most expensive bug I have seen was a discount rule copied into four controllers. Marketing changed the rule; we updated three of them. For two weeks, orders through the mobile app got a discount that the website refused. No single line was wrong. The rule simply had no home.

{{n}}.1 Signs that structure is needed

  • Fat controllers and fat models. A controller method that does five jobs, or a model with forty methods mixing queries, rules and formatting.
  • Rules in several places. The same check written in a controller, a job and a console command.
  • Tests that need everything. To test a pricing rule you must migrate a database and fake three facades.
  • Afraid to change the infrastructure. Replacing the mail provider, or moving one table, means editing business code everywhere.

The cure is the same idea at several sizes: separate what the business decides from how it is delivered and stored. The decisions, the domain, change when the business changes; HTTP, the database and the mail provider change for technical reasons. Laravel does not force a structure, which leaves the choice to you.

{{n}}.3 Adapters



Adapters connect the ports to real technology; this design is often called ports and adapters, or hexagonal architecture. The store adapter implements OrderStore with Laravel’s query builder, including the transaction and the atomic stock update of Chapter {{n-9}}:






The transaction belongs here: “take the stock and save the order, all or nothing” is the port’s promise, and how the database keeps it is the adapter’s business. Facades and the query builder are welcome in adapters; they are what adapters are for. The controller is the HTTP adapter: validated input in, the action’s result or error out:






Deciding that “out of stock” means 409 is an HTTP concern, so it lives in the controller. An Artisan command or a queued job could call the same action and translate the same errors its own way.

{{n}}.5 Testing by layer



The reward for this structure shows in the tests. The action can be tested with in-memory fakes for its ports, as a plain unit test, without a database, the framework or a mail provider:






The fakes are small anonymous classes implementing the ports; each test builds the situation it needs: a store that succeeds, one that reports too little stock, one that must not be called. The adapter is tested against the real PostgreSQL test database, as in Chapter {{n-3}}, and only for what it adds.

Watch out: architecture is a cost too
Every interface and adapter is a file to read and an indirection to follow. For a page that lists products, a controller with an Eloquent query and a resource is the right amount of structure; wrapping it in an action, a port and a repository is ceremony. Introduce layers where they pay: where business rules live, where several entry points share behaviour, where tests are slow because everything is tangled. Using Eloquent directly in simple places is not a failure of architecture; it is good judgement.



{{n}}.6 Modules, monoliths and services



    

  • Organise by feature, not by kind. app/Orders, app/Catalog, app/Accounts, each with its domain, actions and adapters, rather than every controller in app/Http/Controllers and every model in app/Models. A change to ordering then touches one folder. Laravel finds classes anywhere under app/, so no configuration is needed.
    • 

  • Modules talk through their actions. Orders may call Catalog’s actions, but must not query its tables or use its models directly; Pest’s toOnlyBeUsedIn can enforce it. Events (Chapter {{n-5}}) let a module react to another without depending on it.
    • 

  • A modular monolith first. One Laravel application, well divided into modules, is the right shape for almost every team: one deployment, one database, transactions that span modules, and simple debugging.
    • 

  • Services when there is a reason. Splitting into separate services pays off when parts must scale very differently, be deployed by different teams independently, or be isolated for safety. The cost is real: network calls that fail, data spread across databases without shared transactions, and the tracing of Chapter {{n-2}} becoming a necessity. Clear modules make a later split easy; a tangle split into services is a distributed tangle.
    • 




Professional habit: write decisions down
When you make a structural decision (“orders do not use catalog models”, “actions for every use case with business rules”), write a short architecture decision record: the context, the decision, the alternatives and the consequences, one page in docs/decisions/. A year later, the next developer, often yourself, will know why, and can change the decision on purpose instead of by accident.

Summary



    

  • Architecture decides where each kind of code lives, so rules can change without touching delivery and storage.
    • 

  • The domain holds rules and words in plain PHP, using no facades; its exceptions speak the business’s language.
    • 

  • Actions orchestrate a use case through ports (interfaces); adapters implement them with Laravel’s tools.
    • 

  • The service container, configured in a provider, is the composition root: one line per port.
    • 

  • Actions are tested with fakes as unit tests; adapters against the real database; boundaries with Pest arch tests.
    • 

  • Organise by feature; prefer a modular monolith; split into services only for a concrete reason.
    • 




Quick check answers: 1. So that the shop’s rules depend on nothing that changes for technical reasons: they can be read without knowing Laravel, tested as plain PHP without booting the framework, and reused by any entry point. A facade would tie the rule to the container and to a particular database or log. 2. The controller, the HTTP adapter: a status code is part of HTTP, not of the business. An Artisan command would translate the same exception into a message and an exit code. 3. Only the binding in AppServiceProvider: write a class that implements Mailer with a Mailable or the provider’s SDK, and bind it instead of LogMailer. The domain, the action and their tests do not change.
