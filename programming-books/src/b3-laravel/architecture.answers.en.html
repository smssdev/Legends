If the process dies between the two, no email is sent; when that matters, the store writes to an outbox inside its transaction, or dispatches a queued mail job with afterCommit().
  3. The arithmetic (“members get 5% off the total”) is a plain domain rule next to total(), with unit tests for members, non-members and rounding. Whether a customer is a member is data, so the action asks a port (Customers::isMember($email)), bound in the provider to an adapter that queries the database, and passes the answer to the rule; the store saves the discounted total. Tests: domain unit tests for the arithmetic; action tests with a fake Customers returning true and false; a feature test for the adapter’s query against PostgreSQL; and one HTTP feature test that a member’s order total is discounted.

Costs: network calls that fail or time out between orders and the rest; no shared transactions, so stock and orders can disagree and need sagas or outboxes; separate deployments, monitoring, tracing and on-call; data duplicated or fetched across the network; slower development while the boundary settles. Questions first: Which concrete problem would the split solve? Does ordering need to scale differently, or be deployed by a separate team? Is the module already clean inside the monolith, using only its own tables and talking to others through actions? If the answers are vague, keep a well-divided module and revisit when there is a measured need.
  5. arch('the store adapter is wired only in the provider')->expect('App\Orders\Infrastructure\QueryBuilderOrderStore')->toOnlyBeUsedIn('App\Providers'). It matters because the adapter is a detail: if controllers, jobs or other modules use it directly, they skip the action and its rules, couple themselves to the query builder, and cannot be tested with a fake store. Keeping the concrete class visible only to the composition root keeps every other class depending on the port.
