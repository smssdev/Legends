Because they tell the client different things. 201 Created says “this request made a new order”; 200 OK with Idempotent-Replayed: true says “nothing new happened, this is the order your earlier request made”. A client normally treats both as success, but its logs, its metrics and any developer reading the traffic can see that a retry happened, and how often. Counting replays is also a good signal of network trouble between the app and the API.
  2. It decodes to {"price":9000,"id":4,"_pointsToNextItems":true}: the sort values of the last row on the page, and the direction. With the price alone, products that share a price break the page boundary. Say products 7 and 8 both cost 6000 and the page size is 1: page 1 ends at product 7; asking for price > 6000 skips product 8, and price >= 6000 shows product 7 again. With (6000, 7) the next page asks for (price, id) > (6000, 7), exactly product 8. That is why the query orders by id as well: it makes the order unique.
  3. “Exactly one email per order, only for orders that exist” can break. With Redis, dispatch() pushes the job immediately, outside the transaction. If the order then rolls back (a later line out of stock), the job still runs for an order that does not exist; and a fast worker may even run it before the commit, when Order::findOrFail cannot see the order yet. The smallest fix is SendOrderEmail::dispatch($order->id)->afterCommit(); (or public $afterCommit = true; on the job), as in Chapter {{n-7}}. That still leaves a small gap: if the process dies between the commit and the push, the email is lost, which the database queue does not allow.
  4. The second request makes a new order, and that is right. The 409 rolled back the whole transaction, including the insertOrIgnore that claimed k1, so no order with that key exists and the retry runs as if it were the first. The promise of an idempotency key is “the same key never makes two orders”, not “the same key always gives the same answer”: a request that failed and changed nothing may be retried, and the customer gets the order they wanted once the stock is back.

Move the keys to their own table in a new migration: Schema::create('idempotency_keys', …) with user_id, key, request_hash, order_id (a foreign key) and created_at, a primary key on ['user_id', 'key'] and an index on created_at; then drop the unique pair and the two columns from orders in a later migration, once the code uses the new table. The order inserts its key row with insertOrIgnore in the same transaction, as now. A scheduled command deletes old keys in batches: Schedule::call(fn () => DB::table('idempotency_keys')->where('created_at', '<', now()->subDay())->limit(1000)->delete())->everyFifteenMinutes(); in routes/console.php. The guarantee holds for any retry within 24 hours, because the row exists until then; and the API documentation must say that keys are remembered for 24 hours only.
