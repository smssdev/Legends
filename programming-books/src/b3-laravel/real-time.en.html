Chapter {{n}}

Real-time with Reverb

In this chapter you will learn to

  • choose between polling, server-sent events and WebSockets
  • broadcast Laravel events to the browser through Reverb, Laravel’s own WebSocket server
  • see the protocol on the wire, with a client written in a few lines
  • protect private channels with authorization rules
  • run Reverb in production across several servers, and handle reconnecting and missed events

HTTP is a conversation the client always starts: it asks, the server answers, and the server has no way to speak first. Yet many screens should change by themselves: an order moving from “paid” to “shipped”, a chat message arriving, the last kits in stock disappearing. Laravel’s answer is broadcasting: an ordinary event, dispatched in PHP, is pushed over WebSockets to every browser that listens. This chapter installs it with Reverb, Laravel’s free WebSocket server, and watches the messages arrive.

The first live feature I built was a counter of people viewing a product. It worked beautifully on my laptop. In production we ran three servers, and each one counted only its own visitors, so the number jumped between three different values every time the page reconnected. That week I learned why the WebSocket server should be a separate, shared service.

{{n}}.1 Three ways to be up to date

  • Polling: the client asks every few seconds, “anything new?”. Simple, works everywhere, and often good enough; but most answers are “no”, each one costs a request, and news arrives up to one interval late.
  • Server-sent events (SSE): the client makes one HTTP request, and the server keeps the response open, writing an event whenever something happens. One direction only. In PHP, each open response holds a whole worker process for as long as the page is open, which is why PHP applications rarely use it.
  • WebSockets: an HTTP request that is upgraded into a two-way connection, where either side can send a message at any time. A PHP request cannot hold thousands of these, so Laravel hands them to a separate, long-running server built for it: Reverb.

The flow is always the same. The Laravel application dispatches an event; Laravel sends it over HTTP to Reverb; Reverb pushes it to every client subscribed to the event’s channel. Because every web server and worker sends its events to the same Reverb, it does not matter which server made the change: a problem that real-time code written by hand must solve with publish/subscribe.

{{n}}.3 Broadcasting an event



An event that implements ShouldBroadcast (or ShouldBroadcastNow) is broadcast when it is dispatched. Three methods say where it goes and what it carries:






    

  • broadcastOn names the channel; here every watcher of order 1001 listens on orders.1001.
    • 

  • broadcastAs gives the event a short name for clients; without it, they see the full class name.
    • 

  • broadcastWith chooses the data. Without it, every public property is sent, and with models, every visible attribute: a common way to leak data to browsers. Send what the screen needs.
    • 

  • ShouldBroadcastNow sends at once, inside the dispatch. ShouldBroadcast puts the sending on the queue of Chapter {{n-1}}, so a slow or unreachable Reverb never slows the request; that is the right choice in an application.

{{n}}.4 On the wire



Reverb speaks the Pusher protocol, a small set of JSON messages over a WebSocket, which many client libraries understand. In a browser, Laravel Echo hides it:

{{n}}.5 Private channels



Anyone who knows the app key can subscribe to a public channel, so orders.1001 would let any visitor watch any order. Real order updates belong on a private channel: new PrivateChannel("orders.{$this->orderId}") in broadcastOn. Before subscribing to a private channel, the client asks the Laravel application for permission at /broadcasting/auth, and Laravel runs the rule written for that channel in routes/channels.php:






The rule receives the signed-in user and the parts of the channel name, and returns whether that user may listen; here, only the order’s own customer. A request without a signed-in user is refused before any rule runs:






When the rule says yes, Laravel signs the answer with the app secret, and Reverb accepts the subscription only with a valid signature, so a client cannot skip the check. Echo makes the request for you, with the session cookie on your own website or a Sanctum token from an app (Chapter {{n-3}}). Presence channels go one step further: the rule returns information about the user, and every member of the channel learns who else is there, which is how “3 people are viewing this product” is built.



Watch out: broadcasting is not storage
A broadcast reaches only the clients connected at that moment; nothing is stored. A browser that connects a second later, or reconnects after a network blip, never sees it. Broadcasts are hints that something changed; the truth stays in the database. When a page opens, or Echo reconnects, load the current state with an ordinary request, then follow the live updates.



{{n}}.6 Reverb in production



    

  • A long-running process. reverb:start runs under Supervisor, systemd or the container platform of Chapter {{n+5}}, restarted after each deploy with php artisan reverb:restart. A web server in front (nginx, Caddy) handles TLS and forwards wss:// connections to it.
    • 

  • More than one Reverb server. When one Reverb process is not enough, run several and set REVERB_SCALING_ENABLED=true: they share messages through Redis publish/subscribe (Chapter {{n-4}}), so a client connected to any of them receives every broadcast.
    • 

  • Connections and limits. Each open connection holds memory and a file descriptor for as long as the page is open. Raise the open file limit (ulimit -n) for the Reverb process, and set proxy timeouts for long-lived connections. Reverb’s pings keep connections alive and detect clients that vanished.
    • 

  • Reconnecting. Networks drop, phones sleep, Reverb restarts at every deploy. Echo reconnects by itself with growing delays; when it does, the page should reload the current state.
    • 

  • Do you need it? A status that changes twice a day does not need a socket; polling every 30 seconds, or refreshing when the user returns to the tab, may be the better engineering.
    • 




Professional habit: decide what each channel may reveal
Before adding a broadcast, write down who may listen to its channel and what its data may contain, and make the code match: public channels only for data anyone may see, a rule in routes/channels.php for every private channel, a test for the user who must be refused, and broadcastWith on every event. A broadcast is an API response pushed to a browser, and deserves the same review.

Summary



    

  • Polling asks repeatedly; SSE holds a response open; WebSockets carry messages both ways and, in Laravel, live in Reverb.
    • 

  • An event with ShouldBroadcast goes from Laravel to Reverb to every client on its channel; broadcastWith decides what they receive.
    • 

  • Reverb speaks the Pusher protocol; Laravel Echo is the browser client.
    • 

  • Private channels are authorized by rules in routes/channels.php, checked at /broadcasting/auth and signed with the app secret.
    • 

  • Broadcasts are hints, not storage: pages load the current state and then listen.
    • 

  • In production Reverb is supervised, restarted after deploys, and scaled across servers with Redis.
    • 




Quick check answers: 1. A PHP request lives for one response, and each worker handles one request at a time; holding thousands of connections open for hours would need thousands of workers. Reverb is a long-running, event-driven process built to keep many idle connections cheaply, and the application only sends it events. 2. Every public property of the event: here orderId and status, and with an Eloquent model as a property, all of the model’s visible attributes. 3. Sending to Reverb then happens in a queue worker: the request does not wait for it, a moment when Reverb is down does not fail the request, and the queue retries the broadcast.
