Chapter {{n}}

Security: Attacks and Defences

In this chapter you will learn to

  • think like an attacker, using the OWASP Top 10 as a map
  • see SQL injection steal password hashes, and make it impossible with bindings
  • stop clients from writing fields they must not touch
  • keep user input out of file paths and other dangerous places
  • protect browser users with security headers, CORS and Laravel’s own defences
  • handle limits, debug mode, secrets and dependencies like a professional

Every API on the internet is probed by scripts within hours of going online. Most of what they try is old and well known, and most successful attacks still use the same few mistakes: input treated as code, missing checks, secrets in the wrong place. Laravel prevents many of them by default, which makes it all the more important to know where its protection ends. This chapter commits the mistakes on purpose. Each attack gets two routes side by side, the obvious version under /unsafe and the safe one, and every attack is run for real with curl.

The first time I ran a security scanner against an API I had built, it found a search box that accepted SQL. I had used string interpolation because it was “just for a search”. Within a minute, the scanner had listed every table in my database. Nothing was stolen, because it was a test server. It was the most useful minute of my career.

{{n}}.1 Thinking like an attacker

An attacker reads your API differently from a user: every input is a chance to make the server do something it was not meant to do. The OWASP Top 10, a list kept by the Open Worldwide Application Security Project from data on real breaches, names the most common ways this succeeds. Its 2025 edition, and where this book deals with each:

Two principles run through all of it. Never trust input: anything from the client (body, query, headers, cookies, file names) may be written by an attacker. And defence in depth: each layer assumes the one before it might fail.

{{n}}.2 Injection

The search below puts the input into its SQL with PHP’s string interpolation. For an ordinary search it works perfectly, which is exactly why this bug survives code review:







The attacker’s input closed the quote, added a UNION that reads the users table, and commented out the rest with --. The database cannot tell which part of the text came from the programmer and which from the attacker, so it ran all of it, and the response contains every email and password hash. With a little more work the same hole reads any table, changes data, or worse.



The safe route sends the same input as a binding: the SQL text, with ?, and the value travel to PostgreSQL separately, so the value can never become code. It simply searched for a product with that strange name, and found none. Eloquent and the query builder bind every value for you, so Product::where('name', $q) is safe. The danger remains wherever text is pasted into SQL:


    

  • The Raw methods (whereRaw, selectRaw, orderByRaw, DB::raw) and DB::select take SQL text: give them bindings as their second argument, never interpolated variables.
    • 

  • Column names, such as the field to sort by, cannot be bindings. Validate them against a fixed list with Rule::in(['name', 'price']), as Chapter {{n-6}}’s requests did.
    • 

  • The same bug exists outside SQL: shell commands built from input (use Process::run with an array of arguments), and HTML built from input (section {{n}}.5).
    • 




{{n}}.3 Mass assignment



An update that writes whatever fields arrive is convenient: add a column, and the route supports it at once. It also supports columns nobody meant to expose:









Omar sent one extra field and became an admin. This is mass assignment, a form of broken access control. Laravel has two layers against it, and the unsafe route had to switch both off:


    

  • The model’s fillable list. User declares #[Fillable(['name', 'email', 'password'])], so update() and create() ignore role. forceFill() exists for trusted code, such as seeders, and skips the list. With Model::preventSilentlyDiscardingAttributes() from Chapter {{n-4}}, an attempt to fill role throws instead of being ignored.
    • 

  • Validated data only. $request->validate() returns only the fields that have rules, never $request->all(). The prohibited rule goes further and refuses a request that sends role at all, so the client learns it is not allowed rather than wondering why nothing happened. Changing a role is a different route, for admins only.
    • 




{{n}}.4 Paths and other dangerous places



Serving files from a folder by name looks harmless. But a name is input, and .. means “the folder above”:









This is path traversal, and here it handed over the .env file: the application key that signs and encrypts cookies, and the database password. The safe route reads through a disk rooted at the folder; Laravel’s storage layer (Flysystem) refuses any path that climbs out of its root, and the route turns that refusal into a 404. Better still is not to use the client’s text as a path at all: store uploads with $file->store('products'), which picks a random name, keep the original name in the database, and look up by id.



The same idea applies to every place where input reaches something powerful:


    

  • URLs the server fetches (“import a product image from this address”). An attacker gives http://localhost:5432 or the cloud provider’s internal metadata address, and your server, inside your network, fetches it for them. This is server-side request forgery (SSRF), exercise 5.
    • 

  • Redirects (?next=… after sign-in): only allow paths on your own site, or an attacker sends users to a fake copy of it. redirect()->intended() stays on your site.
    • 

  • Unserialising data from the client with unserialize() can create arbitrary objects; accept JSON instead.
    • 




Watch out: validation is not escaping
Validating input (“the name is 1 to 100 characters”) and making it safe for a destination (SQL, a path, HTML, a shell) are different jobs. A perfectly valid product name can contain a quote, .. or <script>. Validate at the edge, and make values safe where they are used, with the tool made for that destination: bindings, disks, Blade’s escaping.



{{n}}.5 Protecting browser users



An API is often called from a website, and the browser adds attacks of its own. Laravel already handles much of them for its own pages:


    

  • Cross-site scripting (XSS): an attacker gets their script into a page other people see, for example as a product review, and it runs with the visitor’s session. Blade’s {{ }} escapes everything; {!! !!} does not, and is the place to look in a review. An API protects itself by returning JSON with the right Content-Type, and the frontend by escaping, as Vue and React do except in v-html and dangerouslySetInnerHTML.
    • 

  • Cross-site request forgery (CSRF): another site makes the browser send a request to yours, and the browser attaches your cookies. Laravel’s web routes check a CSRF token on every form; its session cookie is SameSite=Lax; and tokens in the Authorization header, as in Chapter {{n-1}}, are never sent automatically at all.
    • 

  • Clickjacking: your page is loaded invisibly inside another site, and the user is tricked into clicking your buttons.
    • 




Browsers can refuse much of this if the server asks them to, with security headers. Laravel does not set them by default; a small middleware, added to every response in bootstrap/app.php, does:












    

  • Content-Security-Policy lists where scripts, styles and images may come from. An API answers with JSON and needs none of them, so default-src 'none' refuses everything; a website lists its own sources. It is the strongest defence against XSS in pages.
    • 

  • Strict-Transport-Security tells the browser to use only HTTPS for this site for a year, so nobody can downgrade a visit to plain HTTP.
    • 

  • X-Frame-Options and frame-ancestors stop other sites from framing yours; X-Content-Type-Options: nosniff stops the browser from guessing that a text file is a script.
    • 




CORS (cross-origin resource sharing) is the other half. By default a script on evil.example may send a request to your API but may not read the answer. CORS headers relax that for the origins you name. Laravel answers CORS from config/cors.php (created by php artisan config:publish cors), here limited to the shop’s website and two methods:









Both requests got Access-Control-Allow-Origin: https://shop.example: with a single allowed origin, Laravel always names it. A browser compares that value with the origin of the page that made the request; for the script on evil.example they differ, so the browser hides the response from it. Note what CORS is not: it does not stop curl, scripts or servers, which ignore it, and it does not stop the request from reaching your server. It protects users’ browsers, not your API; authentication and authorization still do that. Never allow every origin with * on an API that uses cookies.

{{n}}.6 Limits and errors



An attacker does not need to break in to hurt you; making the server too busy for real users is enough, so every input needs a size. Each string in each rule set gets a max, every list a maximum page size, expensive routes a rate limiter (Chapter {{n-7}}), and the web server a limit on request bodies (PHP’s post_max_size and upload_max_filesize, and client_max_body_size in nginx):

The error names the database, its host and port, the failing SQL, and where the code lives; the full answer also has a stack trace through the framework. On a development machine this is exactly what you want; in production it is a map for attackers. APP_DEBUG=false in production, always, and the details go to the log (Chapter {{n+4}}), where only you can read them. php artisan about shows the current setting.



{{n}}.7 Secrets and configuration



The .env file that path traversal leaked holds the most valuable things the application has. Rules for it:






    

  • Never in the repository. Laravel’s .gitignore already excludes .env (the first part of the output above); .env.example, with every name and no real value, documents what is needed. A secret pushed once is in the history forever: change it, do not just delete the file.
    • 

  • Different in every environment, set by the platform (Chapter {{n+7}}’s containers receive them as environment variables) or a secret manager. The APP_KEY signs and encrypts cookies and encrypted values: a leaked key lets an attacker forge them, so changing it is urgent, and APP_PREVIOUS_KEYS keeps old encrypted data readable while you do.
    • 

  • Read through config(). Call env() only inside config/*.php; after php artisan config:cache in production, env() elsewhere returns null. A missing setting should fail loudly at start-up, not at the first request that needs it.
    • 

  • Never logged. Laravel hides password fields from validation errors and exceptions; keep tokens and keys out of your own log messages too.
    • 




{{n}}.8 Dependencies



The shop’s code is a few hundred lines; the packages in vendor are hundreds of thousands. A known vulnerability in an old version, a malicious package a typo away from a popular one, or an honest package whose maintainer’s account was stolen can all reach your server. composer audit (the second part of the output above) checks every installed version against a database of known vulnerabilities; run it in CI, and fail the build on findings. Commit composer.lock and deploy with composer install, so every machine gets exactly the versions you tested; let a bot (Dependabot, Renovate) open small update pull requests often; and before adding a package, look at who maintains it and whether a few lines of your own would do.



Professional habit: a security checklist in every review
Keep a short checklist next to your pull request template: Is every input validated with a size? Does any input reach a Raw method, a path, a URL, a shell or {!! !!}? Is every new route behind authentication and a policy, with a test for the “no”? Are there new secrets, and are they in .env and config/? Are new packages needed and maintained? Thirty seconds per review prevents most of this chapter.

Summary



    

  • Never trust input, and defend in depth; the OWASP Top 10 is the map of what goes wrong most.
    • 

  • Injection happens when input becomes code: SQL takes bindings, column names take an allowlist.
    • 

  • Fillable lists and validated data stop mass assignment; disks stop traversal; allowlists stop SSRF and open redirects.
    • 

  • Browsers are protected by security headers, CORS for named origins, CSRF tokens and SameSite cookies.
    • 

  • Every input has a size, and APP_DEBUG is off in production.
    • 

  • Secrets live in the environment, read through config(); dependencies are audited and updated often.
    • 




Quick check answers: 1. With a binding, the SQL text and the value are sent separately, so the database never parses the value as SQL, whatever characters it contains. Escaping by hand tries to make the value harmless inside the text, and must anticipate every special character, encoding and database quirk; missing one is enough. 2. validate() would return only name, and the fillable list would ignore role anyway, so Omar would not become an admin; but the request would succeed without telling him the field is not allowed. prohibited refuses it with 422. 3. CORS is not meant to stop requests; it stops a browser from letting a script on another site read the response. The server still checks who is calling and what they may do; and the request here changed nothing.
