Chapter {{n}}

Calling AI Models from Your Apps

In this chapter you will learn to

  • put a model behind one small interface, so the app does not care which model it is
  • stream answers to users, and measure the time to the first words
  • handle rate limits and failures with retries, and slowness with deadlines
  • get structured data from a model that the app can use directly
  • protect the service: input limits and per-user rate limits

Until now the model has been a tool for you, the developer. This part of the book puts it inside your applications, where it serves users who do not read prompts, do not wait patiently and do not forgive errors. The model call itself is one line; the engineering is everything around it: what the user sees while the model thinks, what happens when the provider is busy, how long to wait, what to send and what to refuse. This chapter builds those parts, small and tested, around the book’s model and a stand-in for a hosted one.

No account or key was used in this chapter. The “hosted” model is a fake server written in thirty lines, which answers with errors on purpose, so that the retry code is tested against something real.

Two providers, one loop. The hosted one is the fake API, which refuses the first two calls with 429 Too Many Requests; the retry code waited 200 ms, then 400 ms, and the third call worked. Switching to a real provider changes two environment variables, not the app.



Look at the local answer too: “Yes, your loyalty card is valid at both branches.” That happens to be true for this café, and the model had no way of knowing it. Nothing in the prompt said so; the model gave the most likely answer to the question. An app that answers customers needs to give the model the facts, which is the next chapter.



Tip
Keep the model’s name, the system prompt and the settings in configuration, next to the provider, not scattered through the code. Then trying a new model is a change in one place, and you can run the same test questions against two models to compare them before switching.



{{n}}.2 Retries and deadlines






Retry only what can succeed later: rate limits, temporary server errors, a dropped connection. A request refused for a bad key or a bad input fails the same way every time, and retrying it wastes time and money. Wait longer each time, so a busy provider gets room to recover, and stop after a few tries, so a user is not left waiting forever.



And give every call a deadline. A user will not wait a minute for an answer; after a few seconds, a fallback (“we are busy, please try again”) is better than a spinner:








Watch out
Retries multiply cost: a request that is retried three times is paid for up to four times, and a retry loop in every one of a thousand users’ requests can turn a provider’s short outage into a long one. Retry with growing waits, cap the attempts, and never retry a request that changes something (an order, a payment) unless it carries an idempotency key.



{{n}}.3 Streaming



A model writes its answer token by token. Sending each piece to the user as it arrives makes a slow model feel fast:








The first words arrived after 0.7 seconds, the whole answer after 2.8. Without streaming, the user stares at nothing for 2.8 seconds; with it, they start reading at once. The answer is the same, and the experience is not.

  2. What does streaming change: the time to the whole answer, or the time to the first words?
  3. Why did the local model say the card works in both branches?

{{n}}.4 Structured answers



When the app, not a person, reads the answer, ask for data. The schema of Chapter 3, through the same interface:








The app parsed the answer and added up the cups: an object, not a sentence. Hosted providers offer the same with a JSON schema parameter. Validate the values anyway, as Chapter 3 showed: a schema makes the shape certain, not the content.



Professional habit
Log every model call your app makes: the provider, the model, the prompt’s size in tokens, the time to the first token and to the end, the outcome. Without those numbers you cannot tell whether a complaint is about the model, the provider or your code, and you cannot see what the feature costs.

Summary



    

  • Put every model behind one small interface; local and hosted models then look the same to the app.
    • 

  • Retry temporary failures with growing waits and a limit; give every call a deadline and a fallback.
    • 

  • Stream answers: the total time is the same, but users start reading at once.
    • 

  • Ask for structured output when the app reads the answer, and validate it.
    • 

  • Protect the service with input limits and per-user rate limits, and log every call.
    • 




Quick check answers: 1. Retry rate limits (429), temporary server errors (500, 502, 503) and dropped connections; do not retry a bad key (401), a bad request (400) or anything that would change something without an idempotency key. 2. The time to the first words: the whole answer takes as long as before. 3. Because it is the most likely answer to that question in general; nothing told the model the café’s rules. It happened to be true.
