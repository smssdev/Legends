Chapter {{n}}

Pair Programming with AI

In this chapter you will learn to

  • work with an assistant in small steps: specification, plan, tests, code
  • check that new tests fail for the right reason before any code exists
  • send real test failures back, and know when to stop
  • get code in your project’s style by showing the model your project
  • read what the assistant wrote, including its explanation, with a reviewer’s eye
  • keep the decisions, and the examples that define “correct”, for yourself

In pair programming, two developers share one task: one types, the other watches, questions and thinks ahead, and they swap. With an assistant, you are always the second developer, even while it types. This chapter builds a small feature with the book’s model in the steps a careful pair would follow, runs the real tests at every step, and shows what happened the first three times I tried: the failures taught more than the success.

The final run of this chapter went smoothly in English. It took three versions of my own loop to get there, and the Arabic edition, with the same model, struggled much longer. Section {{n}}.6 tells that story, because it is the part you will meet at work.

{{n}}.1 Start with a specification

The feature is small and real: split a café bill between friends, in whole piastres, with a tip. Before asking for anything, write down what correct means, including examples you worked out yourself:

splitBill(total, people, tipPercent) splits a café bill. total is in piastres (an integer), people is a whole number of at least 1, tipPercent is a whole number such as 10. The tip is total * tipPercent / 100, rounded to the nearest piastre. It returns an array with one integer amount per person, adding up exactly to total plus tip; when it does not divide evenly, the first people pay one piastre more. It throws a RangeError if people is less than 1. Examples: splitBill(1000, 3, 10) is [367, 367, 366]; splitBill(995, 2, 15) is [572, 572]; splitBill(1000, 4, 0) is [250, 250, 250, 250].

The examples matter most. “splitBill(1000, 3, 10) is [367, 367, 366]” settles questions that words leave open: is the tip rounded before or after the split, who pays the extra piastre, are amounts integers. An early version of this chapter had no examples, and the model’s tests expected [27, 27, 27, 27] for a bill that adds up to 110: confident, specific and wrong. The model can write tests; it cannot know what your business means by correct. That knowledge is yours, and the examples are where you put it.

{{n}}.2 Small steps

The program asks for one thing at a time, each in a fresh request with exactly what that step needs: a plan, then tests, then code.




Small steps are not ceremony. Each one is small enough to read in a minute, so you can catch a misunderstanding while it is still one line in a plan instead of forty lines in a file. And each fresh request keeps the context clean: the code step sees the specification, not the model’s earlier musings.



{{n}}.3 Tests that fail for the right reason



New tests must fail before the code exists; otherwise they test nothing. But they must fail on their assertions, not because the test file itself is broken. So, before asking for any code, the program runs the tests against an empty function:








This step exists because the first version of this chapter did not have it. The model’s tests imported assert from node:test, where it is not, so every test failed with “assert.deepEqual is not a function”. My loop then asked the model to fix the code “and not the tests”, and the model, unable to fix a problem that was not in the code, eventually replied with an explanation instead of code, which the loop wrote into bill.mjs. Two lessons came out of that, and both are in the code now: tests are checked before they are trusted, and an answer without a code block is never written over a file.



{{n}}.4 Send back the real failure



Then the code, and the loop: run the real tests; if they fail, send the failures back and ask for a fix; stop after a few rounds.








This run needed no fix: the tests failed on their assertions against the empty function, and the first version of the code passed all six. Here is the code and the tests, as the model wrote them:










Notice that the model added two tests of its own, for one person and for a one-percent tip. Read them as carefully as the code: splitBill(100, 2, 1) is [51, 50] because the tip rounds to 1 and the extra piastre goes to the first person. Correct. A test you did not check is a second opinion you did not read.



Tip
When you send failures back, send the failure itself: the test’s name, the expected and actual values, the error message. “It doesn’t work” gives the model nothing to reason from. The helper failures in lib/tests.mjs picks exactly those lines out of the test output.



Quick check
  1. Why run new tests against an empty function first?
  2. What decides whether splitBill(1000, 3, 10) is right: the model, the tests, or the specification?
  3. Why does the loop keep the old code when an answer has no code block?

{{n}}.5 Show it your project



An assistant writes in the style it saw most often, unless you show it yours. This program asks for the same small function twice, alone and with one file from the project:










Alone, the request got Python, again, with errors printed and swallowed. With the house file, it got an exported async function in the same shape: a default path, an empty result for a missing file, and every other error thrown, not hidden. That is most of what a code reviewer would ask for, obtained by pasting one file.



Most of it. The new function calls readFile and does not import it: the model copied the body’s style and dropped the line above it. It would fail the first time it ran. Matching style is not the same as being complete, which is why the tests of Section {{n}}.3 come before the style, not after it.



Professional habit
Keep a short file of conventions for your project, with one or two real examples, and give it to the assistant at the start of a task: modules or not, how errors are handled, how files are named, which libraries to use. Many tools read such a file automatically. It saves you from correcting the same habits in every answer.



{{n}}.6 When the pair struggles



The same chapter, run for the Arabic edition with the Arabic specification, went differently. The model’s test file used require, which does not work in a JavaScript module, and the run stopped before testing anything. The loop sent back the real error, “require is not defined in ES module scope, you can use import instead”; the error even said what to do. The model answered with the same mistake. Only a hint from the developer, a sentence naming the convention, moved it on.



This is the part of pair programming with AI that tutorials skip. An assistant can be stuck on something you would see in a second, and asking again in different words often produces the same answer. When the same failure comes back twice, stop the loop and do one of three things: tell it the fact it is missing, show it a correct example, or write those three lines yourself. Project {{n}}.3 builds a loop that stops on its own for exactly that reason.



{{n}}.7 Read what it explains



Asking the assistant to explain its code, and how it could fail, is a good habit: it puts a second description next to the code, and differences between the two are where bugs hide. But the explanation is also generated text:








Most of it is accurate. One note is not: it warns that rounding the tip “is not the same as calculating tip as a percentage of the total with rounding” and “can lead to inaccuracies”. That is exactly what the specification asks for, and the sentence contradicts itself. And the answer ran out of room before it reached the inputs that could make the code fail, the part we asked for. Read an explanation the way you read the code: line by line, against the specification.

Summary



    

  • You are the senior half of the pair: you write the specification and the examples that define “correct”.
    • 

  • Work in small steps, each a fresh request with what it needs: plan, tests, code.
    • 

  • New tests must fail on their assertions before the code exists; a test file that cannot run is the first bug.
    • 

  • Send back real failures, write only code into files, and stop when the same failure repeats.
    • 

  • Show the assistant your project to get your style, then check what the style hid.
    • 

  • An explanation is generated text too: read it against the specification.
    • 




Quick check answers: 1. To prove the tests can fail, and that they fail on their assertions rather than because the test file is broken; tests that pass against an empty function, or crash before running, test nothing. 2. The specification, through the examples you worked out; the tests only check what they were told, and the model only guesses. 3. Because an answer without code is usually an explanation or an excuse, and writing it into bill.mjs would replace working code with prose.
