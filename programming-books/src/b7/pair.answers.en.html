A fact about the project belongs in the request, before the first answer: the model then writes the right thing the first time, instead of being corrected, and a correction late in a conversation competes with everything the model already wrote. Chapter 3’s rule applies: what you leave out, the model guesses.

Whatever the model returns, check it the cheap way: run node --check and import the module once in a test; a missing import fails immediately. In the book’s run, the Arabic request did include the import and the English one did not, from almost the same prompt; only running the file tells you which you got.
  4. Decide with the specification only: compute the expected value by hand from its rules and examples. If the specification gives the same answer as the code, the test is wrong; if it gives the test’s answer, the code is wrong; if the specification does not decide (for example, a negative total), neither is wrong yet: the specification has a gap, and you fill it, then add an example. Never let the model’s test decide what the rule is.

To be sure the tests did not change, keep a hash of the test file before the refactor and compare it after, or make the test file read-only during that step. A refactor that needs the tests changed is not a refactor.
