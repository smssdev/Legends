Chapter {{n}}

Security, Privacy and Licensing

In this chapter you will learn to

  • see prompt injection succeed against a real assistant, and stop it with code
  • keep personal data from leaving your machine, and put it back afterwards
  • block secrets before a prompt is sent anywhere
  • keep an audit log that proves what happened without storing personal data
  • read the license of every model and package you ship

An application built on a model has the security problems of any application, and three new ones. The model reads text written by strangers, and text can carry instructions. The model may run at a provider, so whatever you send leaves your control. And models, like code, come with licenses that decide what you may build with them. This chapter attacks the café’s support assistant, protects it, and measures which protections actually held.

The attack in this chapter worked. It worked against the plain prompt and against the careful one, in both languages. What stopped it was ten lines of ordinary code that never asked the model anything.

{{n}}.1 Prompt injection, measured

The support assistant answers from the café’s documents, as in Chapter 14. One of those documents is a customer review, and the customer was an attacker:




Two defences live in the prompt: first a plain rule, then the documents fenced in tags with an explicit warning that they are data and their instructions must never be followed. A third lives in code: a check on every answer that blocks any discount code the café never issued and any known secret.








Both prompts failed. The model told a customer about a 50% code that does not exist, with the plain rule and with the warning written out in the prompt. In the Arabic edition, the same. The output check blocked both answers, because it does not read the prompt or care what the model believes: it compares the answer with a list of codes the café actually issued.



This is the general shape of prompt injection, and the reason it is still unsolved: to a model, instructions and data are both text, and the most recent, most specific, most urgent-sounding text often wins. Defences in the prompt reduce the risk on some models; they cannot remove it. What removes it is what the model cannot change: what it is allowed to do (Chapter 12), what it is allowed to know (the Wi-Fi password was never in its prompt), and what is allowed out (the check).



Watch out
Treat everything a model reads from outside as untrusted input, like a form field on the internet: documents, web pages, emails, tool results, file names. Never put a secret in a prompt that also contains untrusted text, and never let a model’s answer trigger an action that a check outside the model has not approved.



{{n}}.2 Personal data



When the model runs at a provider, everything in the prompt is sent there. Customer messages contain names, emails, phone numbers and sometimes card numbers. Replace them with placeholders before sending, and put them back after the answer comes home:








The email, the phone and the card never left the machine; the support team sees the full message, restored locally. Two things in this transcript deserve attention. The first version of the phone pattern expected ten digits, and Egyptian mobile numbers have eleven: the test message caught it before anything was sent, which is why a redaction rule needs tests with real-looking data. And the name, Mona Hassan, went through: patterns can find emails and numbers, not names. For names, use a dedicated tool for finding personal data, a local model, or a rule that customer names are never in the prompt at all.



Tip
The safest personal data is the data you never send. Before redacting, ask whether the model needs the field at all: to summarise a complaint, it needs the complaint, not the card number. Send the minimum, and redact what remains.

{{n}}.3 Licenses



A model is software with a license, and licenses differ: some open models forbid commercial use, some limit large companies, some require attribution. The license is written in the model file itself, so read it there rather than from a web page that may describe another version:








Both of the book’s models are Apache 2.0, which allows commercial use with attribution; the library is MIT. This is the check that, before the book was written, ruled out a smaller model whose license allowed research use only. For hosted models, the provider’s terms play the same role: read what they allow, what they do with your data, and whether you may use the outputs as you plan.



Professional habit
Keep a list of every model, dataset and package your product depends on, with its license and the date you checked it, and recheck when you upgrade. Licenses change between versions, and “it was open when we started” is not a defence.

Summary



    

  • Prompt injection is real and works against careful prompts; defend with code outside the model: permissions, secrets kept out, and checks on output.
    • 

  • Send providers the minimum; replace personal data with placeholders and restore it locally; test the patterns.
    • 

  • Scan prompts for secrets before they are sent, and keep audit logs without personal data.
    • 

  • Read the license of every model and package from the source, and keep the list current.
    • 




Quick check answers: 1. The output check in code: it compares the answer with the codes the café really issued, so no instruction in a document can change its result. The prompt is text the model weighs against other text, including the attacker’s. 2. The customer’s name: patterns recognise the shape of emails, phone and card numbers, and a name has no such shape. 3. Because it was never given to the model. The attacker’s document only claimed a password; a model cannot leak what it does not know.
