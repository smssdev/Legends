Chapter {{n}}

Automating Repetitive Work

In this chapter you will learn to

  • decide, by measuring, whether a repetitive task needs a model or a plain script
  • score both against an answer key a person wrote, and time them
  • use a model once to write the code, instead of once per item
  • cache answers so the same item is never asked twice
  • send the items where methods disagree to a person, and test generated code before trusting it

Every team has work that comes back every day: label the customer feedback, pull the orders out of messages, clean up dates in a spreadsheet. A language model can do all of it, and it is tempting to put one in every script. But a model is slow, costs money when it is hosted, and is never exactly predictable; a regular expression is instant, free and does the same thing every time. This chapter does three repetitive tasks both ways, scores both against answers a person wrote, and finds where each belongs.

In this chapter the five-minute keyword rules matched the model on every review, a hundred times faster. That is not a story about weak models. It is a story about easy tasks, and about knowing which kind you have.

{{n}}.1 Labelling, both ways

Twelve reviews of the café, each labelled by a person with a topic and a sentiment. That is the answer key, and both methods are scored against it:








A tie, twelve of twelve, and the rules finished in under a second against 44 seconds for the model. Be fair to the model, though: the keyword lists were written while looking at these twelve reviews, so they fit them perfectly. A thirteenth review (“the waiter forgot my sugar”) has no keyword in any list; the rules would guess “taste” and the model would most likely say “service”. Rules are fast and exact on what you foresaw, and silently wrong on what you did not. In the Arabic edition the model got ten of twelve, and the rules, written the same way, twelve.

{{n}}.2 Extraction, both ways



Order notes typed by staff, turned into drink, size and count. A regular expression with a small word list, against the model with a schema:








Both perfect. The notes are short and use a dozen words, which is exactly the situation where a regular expression shines. The first Arabic run said otherwise, and the reason was in my script: the regular expression returned “لاتيه” and the answer key said latte, so every Arabic row looked wrong until a small name map translated one to the other. When two methods disagree, check the comparison before blaming either.



Tip
Before automating with a model, write the plain script first, even a crude one, and measure it on fifty real items with an answer key. If it gets nearly all of them, you are done, and your automation is instant, free and predictable. If it does not, you now know exactly which items need the model.



{{n}}.3 Ask once, run forever



The best use of a model for repetitive work is often not inside the loop at all: ask it once to write the code, then run the code on every row. Here the model writes a function to turn six date formats into ISO dates:








Four of six right, and two return null. On a spreadsheet of ten thousand rows, that is a third of the dates silently blank. The first attempt was worse: the answer ran out of room in the middle of a comment, the code block never closed, and the file did not even load. Generated code is like code from a new colleague: often useful, sometimes incomplete, and never to be run on real data before it is tested, which is Project {{n}}.3.



Look at what the generated function is, too: a plain function with regular expressions and a month table. Once it works, it runs a million rows in a second, for free, with no model. The model’s job was to write it faster than you would; your job is to make sure it is right.



Watch out
A model in a loop multiplies everything: its cost, its time, and its mistakes. One wrong answer in a hundred is one wrong label in a review list, and a thousand wrong rows in a database. Put a model in a loop only when a plain script cannot do the job, and keep a person or a check on what comes out.

Summary



    

  • Measure both ways: a plain script and a model, against an answer key a person wrote, with timing.
    • 

  • Scripts are instant, free and exact on what you foresaw; models handle free text and the unforeseen, slowly.
    • 

  • Often the best use of a model is once: to write the script, which then runs with no model.
    • 

  • Test generated code on known rows before it touches real data.
    • 

  • Cache model answers, and send disagreements to a person.
    • 




Quick check answers: 1. They were written while looking at those twelve reviews, so every review contains one of their words; on reviews nobody looked at, they would miss. 2. Not the methods: the regular expression returned Arabic words and the answer key used English labels, so correct answers were compared as different. A name map fixed the comparison. 3. The code runs on every row instantly and identically, and can be tested once; a model per row is slow, costs per call, and can answer differently on similar rows.
