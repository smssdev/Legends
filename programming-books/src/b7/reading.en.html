Chapter {{n}}

Reading and Explaining Unfamiliar Code

In this chapter you will learn to

  • get a first map of a project you have never seen
  • turn an explanation into predictions, and check them by running the code
  • check “where is this decided?” answers with a search
  • spot the confident details an explanation adds that the code does not say
  • build small tools that summarise files and collect a project’s vocabulary, with checks

Most code a developer touches was written by someone else: a colleague who left, a library, yourself three years ago. Reading it is slow, and this is where assistants shine: they read fast, never get bored, and explain in plain words. They also explain with the same confidence whether they understood or not. This chapter reads a small legacy project with the book’s model, and checks every claim it makes against the only authority there is: the code, running.

The model’s explanation in this chapter reads well and is mostly right. Its predictions from that same understanding were right three times out of six. The gap between those two numbers is what this chapter is about.

Ask for the central function in the words of the people who use it:






It reads well, and most of it is right. Now read it against the code, line by line. “Over $20,000”: the amounts are piastres, so the limit is 200 pounds, and the currency was invented. “If the total is more than 20,000, take away 10%”: only when d is true, which the explanation never mentions. “If it’s a VIP customer”: only if c is exactly "VIP", in capitals. The quickest way to find such gaps is to turn understanding into predictions. This program shows the model the code, asks what six calls return, and then runs them:








Three of six. With the code in front of it, the model missed the 10% discount on the 25,000 order, the floor at zero for a small VIP order, and the fact that "vip" in small letters is not "VIP". The cases were chosen on purpose: the boundary (exactly 20,000), the flag off, the floor, the spelling. Those are the places where unfamiliar code hides its rules, and where explanations go soft.



Tip
When you need to understand a function, do not stop at an explanation. Write five calls that probe its edges, predict the results from the explanation, and run them. Where the prediction fails, the explanation was wrong or incomplete, and you now know exactly where to read.



Quick check
  1. Why did the explanation say “$20,000”?
  2. What did the call with "vip" reveal about the code?
  3. Why are boundary values like exactly 20,000 good test calls?

{{n}}.4 Where is it decided?



A question you will ask a hundred times in an unfamiliar code base: where does this rule live? The model can answer, and the answer can be checked in a second:








The file and the line are right, and grep confirms them. The rest of the answer is long and adds two more inventions: “$500” (it is 500 piastres, five pounds), and “only if the order total is above a certain threshold”, which the line it just quoted plainly does not say. The model quoted the right line and then described a different one.



That is the general shape of these answers: the parts you can check mechanically (a file, a line, a name) are usually right, and the prose around them is where the errors are. So take the pointer, check it, and read the code it points to yourself.



Professional habit
When you learn something about unfamiliar code, write it down where the next person will find it: a comment on the cryptic line, a test that pins the surprising behaviour (“lowercase vip gets no discount”), a line in the README. The model’s explanation disappears with the conversation; a test stays and keeps checking.

Summary



    

  • An assistant gives a fast first map of an unfamiliar project; use it to decide where to read.
    • 

  • An explanation is a set of claims. Turn them into predictions on edge cases, and run the real code.
    • 

  • Pointers (files, lines, names) are easy to check and usually right; the prose around them is where errors hide.
    • 

  • Watch for invented details: units, currencies, conditions and thresholds that the code does not contain.
    • 

  • Keep what you learn in the code base: comments and tests outlive the conversation.
    • 




Quick check answers: 1. Nothing in the code says what the unit is; “20000” and a discount look like money, and dollars are the most common currency in the text the model learned from. The data are in piastres. 2. That the comparison is case-sensitive: only "VIP" in capitals gets the 500 off, so a customer type typed in small letters silently gets nothing. 3. Because a condition such as t > 20000 behaves differently exactly there; an explanation that says “over 20,000” cannot tell you whether 20,000 itself counts.
