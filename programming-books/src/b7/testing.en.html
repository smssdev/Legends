Tests, Refactoring and Code Review

In this chapter you will learn to

  • measure tests written by a model: right on the real code, and able to catch planted bugs
  • check a refactor by comparing old and new code on hundreds of inputs
  • use a model as a reviewer, and score its review against problems you planted
  • recognise a green test run that proves nothing

Tests, refactoring and review are the work around a change, and they are where assistants are used most after writing code. They are also where a model’s output is hardest to judge by reading: a test file looks like testing whether or not it would catch anything, a refactor looks cleaner whether or not it changed behaviour, and a review sounds thorough whether or not it found the real problem. This chapter replaces judgement by reading with measurement, for all three.

My first measurement in this chapter reported “pass”, and the model’s tests had caught nothing. The test file it handed back contained no tests at all, and an empty test file passes. Section {{n}}.2 shows the guard that this needed.

{{n}}.2 Tests, measured



A test suite has two jobs: pass when the code is right, and fail when it is wrong. The first is checked by running the tests on the real code. The second is checked with mutants: copies of the code, each with one small planted bug. A good suite fails on every one of them; each mutant that passes is a bug your tests would let through.










Read it in order. The model wrote eight tests. Three of them fail on the real code, so they are wrong, and they are all wrong the same way: the model expected the discount to grow past the cap. For 10,000 × 100 it expected 95,000, as if the discount were 90%; the comment says “never more than 5,000 off”, so the answer is 995,000. Sent back once with the exact failures, the model returned a file that does not even parse: a parenthesis is missing.



So the program does what a developer would: it runs each test on its own against the real code and keeps the ones that pass, six of eight, and measures them against the mutants. They catch four of five. The survivor is Math.floor changed to Math.round: no test uses a price whose discount has a fraction above one half, so rounding up and rounding down give the same results on every test. That is a real gap, found by a mechanical check, and it is exactly the kind a review by eye would miss.



Two guards made these numbers honest, and both were added after the first runs lied. A test file that fails on the real code would “catch” every mutant, because it fails everywhere; so the score counts only tests that pass on the real code. And a file with no tests passes; the first version of this program accepted the model’s “fixed” test file, which turned out to be a copy of price.mjs, and reported success with zero tests. The fix needed two attempts. Checking the runner’s count of tests was not enough: in the Arabic run, the model’s answer contained no test file at all, the program ran an empty file, and Node reported one passing test, the file itself. Now a file without a single test( or it( is a failure before it is run.



Watch out
Green means “nothing failed”, not “everything was tested”. Before you trust a suite written by anyone, model or person, check three things: it ran tests (count them), it fails when the code is wrong (break the code on purpose), and its expected values come from the specification, not from the code it tests.

{{n}}.3 A refactor, compared



A refactor changes how code reads without changing what it does. The first part is a matter of taste; the second can be checked. Here the model refactors the legacy calc of Chapter 5, and the program compares old and new on 500 random orders, including the edges:








Not one difference in 500 orders, including the boundary at 20,000 and the customer type in small letters. The model even changed == to ===, a change that could alter behaviour in general; the comparison is what tells you it does not here, because c is always a string. As for readability, judge for yourself: options is a strange name for an order, and discount for a flag that switches a discount on. The model made it modern, not necessarily clear.



This technique, running two versions on the same inputs and comparing, is called differential testing, and it is the best friend of a refactor: it needs no expected values, only the old code, which you already have.



{{n}}.4 A review, scored



A model reviewer reads a diff and lists problems. To know how good it is, plant problems you know about and count which it finds. This diff has three: a password written to the log, a loop that runs one step too far, and a database insert that is not awaited.








Two of three. The secret and the off-by-one were found, though the second appears twice, once wrongly as an “infinite loop”. The missing await before db.insert, the one problem that would lose data silently in production, was not found; point 5 comes near it (“does not handle errors from db.insert”) without seeing that the inserts are never waited for. The rest of the list is generic advice that fits almost any function. A model reviewer is a useful first pass: it is fast, never tired, and good at the problems that look like problems. It is not a substitute for a person who knows how this database behaves.



Professional habit
Before you rely on any review tool, model or linter, run it on a change with problems you planted. It takes ten minutes and tells you what kind of problem it catches and what kind it misses. Then you know what you still have to look for yourself.

Summary



    

  • Measure a test suite twice: it passes on the real code, and it fails on mutants with planted bugs.
    • 

  • A model’s expected values can be wrong; keep only tests that pass on the real code, and take examples from the specification.
    • 

  • A green run can mean no tests ran. Count them.
    • 

  • Check a refactor by running old and new on the same inputs; it needs no expected values.
    • 

  • Score a model reviewer on planted problems before you rely on it, and review what it misses yourself.
