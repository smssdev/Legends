Chapter {{n}}

Documentation and Commit Messages

In this chapter you will learn to

  • have a model draft documentation comments, and run the examples it writes
  • draft a README, and look up every option it mentions in the code
  • draft commit messages, and check their format with a linter before committing
  • find documentation that went stale when the code changed

Documentation is the writing developers put off, and an assistant writes it in seconds. That is genuinely useful: a good first draft of a comment, a README section or a commit message saves real time. But documentation has a property that makes it dangerous to accept unread: nobody runs it. Wrong code fails a test; a wrong comment sits there for years, telling every new reader something false. This chapter treats documentation as something that can be checked, and checks everything the model writes.

In this chapter the model wrote true examples that test nothing, a README that matches the code, and a commit message that our linter refused twice. In the Arabic edition, one of its documentation examples was simply false. Running things found all of it.

{{n}}.1 Documentation comments, with examples that run

Ask for a JSDoc comment with examples in a form a program can read: a call, then // =>, then the result. Then run them:






Every example is true, and the comment is mostly good. But look at what the examples test: a unit price of 10. The discount on 20 cups is 20 piastres; the cap of 5,000, which the comment mentions twice, is never reached. These are true examples that would stay true for many wrong versions of the function. Ask for examples at the edges: just below the threshold, at it, and at the cap. In the Arabic edition, with the same function, one of the three examples was false: linePrice(100, 15) was documented as 1,400 and is really 1,350. A reader copying that example into a test would have written a failing test, or, worse, “fixed” the function to match.



Tip
Keep examples in documentation in a form that can be executed, and execute them in your test suite. Python calls this doctest; in JavaScript the twenty lines of docExamples do the same. Examples that run cannot quietly become false.

{{n}}.3 Commit messages, linted



A commit message is documentation of a change: what changed and why. Many teams use the Conventional Commits format: type(scope): subject, a blank line, then a body. A model drafts these well from a diff. Here the program creates a real repository, makes a real change (the discount cap drops from 5,000 to 3,000), asks for a message, and checks it with a linter before committing:










Refused twice, and no commit was made. The first subject was 113 characters; told so, the model shortened it to 93, still over the limit, because the request to keep the reason in the subject outweighed the rule. And there is a problem the linter does not check: the type is refactor, which promises that behaviour did not change, for a change that makes every large order more expensive. Release tools read those types to decide what goes in the changelog and which version number to bump; a wrong type hides a price change from everyone who reads the release notes.



The right message is short, and only a person who knows why the cap changed can write the body:



fix(price): cap the bulk discount at 3000

The 5000 cap let large office orders go below cost. Agreed with the
café on 2026-11-20.



That is the general pattern for commit messages with AI: the model summarises what changed, quickly and usually well; the why is in your head, your ticket or your conversation with the café, and the model cannot know it.



Professional habit
Run the commit message linter in a git hook, so it checks every message, written by you or by a model, before the commit exists. A rule that is checked by a machine stops being a matter of discipline.

Summary



    

  • Assistants draft documentation fast and mostly well; nobody runs documentation, so check it.
    • 

  • Write examples in a runnable form and run them; ask for examples at the edges.
    • 

  • Look up every option, file and name a README mentions in the code, and run its examples.
    • 

  • Lint commit messages by machine; decide the type and write the “why” yourself.
    • 

  • When code changes, its documentation examples tell you what went stale.
    • 




Quick check answers: 1. With a unit price of 10, the discount is a few piastres and never reaches the cap, so the examples would stay true for many wrong versions of the function: a wrong cap, a wrong rounding. 2. That the option is declared in the parseArgs options, as name: {; an option that is only mentioned in a comment does not count. 3. A reader trusts it: they copy it into a test, or “fix” the code to match it. No example sends them to the code; a wrong one sends them the wrong way.
