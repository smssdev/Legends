Chapter {{n}}

Prompting That Works

In this chapter you will learn to

  • turn a vague request into a specific one, and test what comes back
  • get structured output a program can rely on, with a schema
  • use examples, and know when they help
  • keep a model to the text you gave it, and let it say “not there”
  • check whether a technique such as “step by step” helps, instead of assuming it
  • treat a prompt like code: build it from parts, test it against cases, and score changes

A prompt is everything you give the model: the instructions, the context, the question. Chapter 1 showed why it matters so much: the model continues your text the way such text usually continues. Vague text is followed by a generic answer; specific text by a specific one. This chapter does not collect magic phrases. It runs each piece of advice on the book’s model and counts what happens, and twice the count says something the advice books do not.

One popular trick made the model worse in this chapter, and a prompt the model wrote for itself scored lower than one I wrote by hand. Both results are here, because the lesson is the same: measure.

A requirement that matters belongs in the prompt and in a test, and only the test proves it was met.

Tip
Before you send a prompt, ask: “if a new colleague got this message, could they do the task without asking me anything?” Every question they would ask is something the model will guess instead.



{{n}}.2 Output a program can read



When a program reads the answer, “reply with JSON only” is a request, not a guarantee. A grammar is a guarantee: node-llama-cpp can turn a JSON schema into rules that forbid every token that would break it.








Without a grammar, the model behaved well: five valid objects. But look at Hassan’s order, which gives no size: the model wrote null, a value the program never planned for. With the schema, it had to choose one of the three allowed sizes, and chose "unknown". The schema did two jobs: it made the reply valid JSON every time, and it limited each field to values your code handles. Hosted models offer the same thing, under names like structured outputs or JSON mode with a schema; Chapter 13 uses it from an application.



Watch out
A schema guarantees the shape, not the truth. The model can still put the wrong drink in a perfectly valid drink field. In the Arabic edition it did exactly that: with the schema, Sara’s small tea came back as an espresso. Validate the values that matter, as you would any input from outside your program.



{{n}}.3 Examples



Showing a few examples of input and answer, called few-shot prompting, is the most recommended technique of all. This program sorts eight messages from café customers into four labels, with instructions only and then with four examples, and counts the right answers:








Eight out of eight both times: the examples added nothing, because the task was already clear and the labels are ordinary English words. In the Arabic edition, the same messages in Arabic scored 6 of 8 with instructions alone and 7 of 8 with examples: the model called a double charge a bug, a reasonable reading, and the examples fixed one of its two mistakes. Examples earn their place when the instructions cannot say everything: a label with a house meaning (“is a refund question billing or question?”), a tone, a format that is easier to show than to describe. They also cost tokens in every request. So add them when a test shows a mistake they would fix, and pick examples that sit on the boundary between labels, not easy ones.

{{n}}.4 Answer from the text, or say so



Chapter 1 showed a model inventing a paper. The same thing happens with your own documentation: ask about something it does not contain, and the model may fill the gap. Here is a short documentation for a configuration file, and a question about an option that is not in it:








The first answer is honest, and three paragraphs long: it says the option is not mentioned, lists the ones that are, and then adds that it “does not exist in this configuration”, which the documentation does not say either. The second prompt gave the model a rule and a fixed sentence to use, and got exactly that sentence. A fixed answer for “not there” is useful twice over: the person reading knows it means “look elsewhere”, and a program can recognise it.



Professional habit
When a model answers from your documents, code or data, always include the rule “answer only from the text above” and a fixed reply for when the answer is missing. It costs one line and turns the most dangerous failure, a fluent invention, into a visible one.



{{n}}.5 Measure the tricks



“Ask the model to think step by step” is advice you will read everywhere, and for good reason: for large models on multi-step problems it often helps. Here it is measured on three small problems:








Asked for the result only, the model got all three right. Asked to work step by step, it got both clock times wrong, 18:20 and 13:55, after a page of confident working. More steps meant more places to slip, and this small model slipped. The Arabic edition measured the same thing in Arabic: three right directly, one right step by step. A larger model might gain from the same words; the only way to know is to count, on your model, with your kind of problem. And for clock arithmetic, the best prompt is no prompt: Chapter 2’s calculator tool, or a few lines of code.

Summary



    

  • A good prompt says what correct means: context, task, rules and format. What you leave out, the model guesses.
    • 

  • Specific prompts give much better answers, and still not guaranteed ones: test what comes back.
    • 

  • For output a program reads, use a schema: it guarantees the shape and limits the values.
    • 

  • Examples help when the instructions cannot say everything; add them when a test shows the need.
    • 

  • Keep the model to your text, with a fixed answer for “not there”.
    • 

  • Advice is a hypothesis. Measure it on your model, with your cases, before you rely on it.
    •
