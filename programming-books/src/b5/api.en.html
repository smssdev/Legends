Chapter {{n}}

Talking to an API

In this chapter you will learn to

  • run a small API server written in Dart, and talk to it with curl
  • send GET and POST requests from Flutter with the http package
  • turn JSON into Dart objects, and server errors into exceptions with clear messages
  • show loading, error and ready states, with a way to try again
  • test code that uses the network without any network, with MockClient

The café’s menu has lived in the code since Chapter 7. In a real app it lives on a server, and the app asks for it over the internet, through an API: a set of addresses that answer with data. In this chapter the café gets its own server, a single Dart file you can run on your computer, and the app learns to ask it for the menu, show what happens while it waits, survive when things go wrong, and send orders back.

Every request in this chapter really went over a network connection to a real server while the book was being made, and every error message came from that server. Only the tests use a pretend network, and they say so.

If you read Book 3 of this series, you have built APIs yourself. Watch out
On the Android emulator, localhost means the emulator itself, not your computer: use http://10.0.2.2:8080 to reach a server on your computer. And Android refuses plain http:// addresses in release builds; real servers use https://, and for local tests you can allow it in the manifest. On an iPhone simulator, localhost works.



{{n}}.2 The first request



Flutter apps make requests with the http package, published by the Dart team. The chapter’s app also uses Provider from Chapter {{n-1}}:











    

  • http.get takes a Uri and returns a Future<Response>, with statusCode and body.
    • 

  • jsonDecode, from dart:convert, turns the JSON text into Dart values: lists, maps, strings and numbers.
    • 

  • FutureBuilder shows each moment of a future: its builder runs again when the future completes. The snapshot says whether it is still waiting, has failed, or has data.
    • 

  • The future is created once, as a late final field of the State. Creating it inside build would send a new request every time the screen is drawn, which can be many times a second.
    • 




This works, and it is how every Flutter developer starts. It also has three weaknesses that the rest of the chapter fixes: the data stays as untyped maps, an error shows as a raw exception, and nothing can be tested without a server.



{{n}}.3 From JSON to objects



The professional shape puts everything about the server in one class, and turns every answer into typed Dart objects as soon as it arrives:






    

  • Drink.fromJson is a factory constructor: a constructor that builds the object from something else, here a map. After it, the rest of the app works with drink.price, an int, and never with json['price'].
    • 

  • CafeApi receives its http.Client instead of creating one. The app gives it a real client; tests will give it a fake one. This is called dependency injection, and it is what makes network code testable.
    • 

  • Every request goes through _send: a timeout of ten seconds (Chapter 4), so that a silent server cannot leave the screen waiting forever, the body decoded as UTF-8 so that Arabic arrives intact, and any status of 300 or more turned into an ApiException carrying the server’s own message.
    • 

  • replace(queryParameters: ...) builds /menu?q=tea safely, encoding spaces and Arabic letters correctly.
    • 




Professional habit
Parse at the edge. Convert JSON to typed objects in one place, as soon as it arrives, and let the rest of the app see only those objects. If the server changes a field’s name, one line changes, and the compiler finds every use; with maps passed around, the bug appears on a screen, much later.



{{n}}.4 Loading, error, ready



A screen that loads from a network is always in one of three states, and must show all three well. The model keeps the state:

{{n}}.5 Testing without a network



Widget tests never reach the internet: every real request returns 400. That is a feature: tests must not depend on a server that may be slow or down. Because CafeApi receives its client, a test can give it a MockClient from package:http/testing.dart, which answers every request with whatever the test decides:








The widget test goes further: the first request fails, the second succeeds, and the test taps “Try again” in between:








Watch out
An http.Response built in a test encodes its body as Latin-1 unless its headers say charset=utf-8. The Arabic edition of this test failed for exactly that reason until the header was added. Real servers send the header; fake ones must too.

Summary



    

  • An API answers requests (GET, POST…) with a status code and a JSON body. Try it with curl before writing the app.
    • 

  • The http package sends requests; jsonDecode turns the body into Dart values; FutureBuilder shows a future’s progress.
    • 

  • Put the server in one class that receives its http.Client, turns JSON into typed objects with fromJson, and errors into exceptions with the server’s message, with a timeout.
    • 

  • Show loading, error (with “Try again”) and ready; RefreshIndicator reloads by pulling.
    • 

  • Test with MockClient, never with a real network.
    • 




Quick check answers: 1. Because build can run many times, and each run would send a new request; the field is created once. 2. It throws an ApiException with the server’s error message, “No drink 9”. 3. Loading, error (with a way to try again) and ready.

Project {{n}}.3 · Challenge


Search on the server, without flooding it


Search the menu on the server as the customer types, but ask only when the typing stops for 400 milliseconds.


You will practise: Timer, cancelling, query parameters, and testing time with tester.pump(Duration).


    

  1. Keep a Timer? wait in the state. In onChanged, cancel it, and start a new Timer(Duration(milliseconds: 400), ...) that calls api.menu(query: text).
    2. 

  2. Typing “tea” quickly cancels the first two timers: only one request is sent, for “tea”. This is called debouncing.
    3. 

  3. Cancel the timer in dispose.
    4. 

  4. Test with a MockClient that records every query. Type “t”, “te”, “tea” with 100 milliseconds between them, check that nothing was asked yet, then pump 400 milliseconds and check that exactly one request, for “tea”, was sent.
    5. 



Hint: in a widget test, time does not pass by itself: tester.pump(Duration(milliseconds: 400)) moves the test’s clock forward exactly that much, which makes timing tests fast and exact.
