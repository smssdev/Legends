Chapter {{n}}

Saving Data on the Device

In this chapter you will learn to

  • choose where each kind of data belongs: preferences, a file, a database, or secure storage
  • keep settings and small lists with shared_preferences, and load them before the first frame
  • save a history as a JSON file in the app’s own folder, safely
  • keep many records in an SQLite database with sqflite, and search them
  • test every kind of storage without a phone

Close the café app and open it again, and everything is gone: the dark mode you chose, the hearts, the basket. Everything in this book so far lived in memory, and memory is emptied every time the app closes. People expect the opposite: an app remembers. This chapter writes data to the phone’s own storage, in three ways for three sizes of data, and every screenshot in it was taken after closing the app and opening it again.

To take this chapter’s screenshots, the browser really reloaded each app after the taps, which empties all its memory. Whatever you see on them came back from storage.

{{n}}.1 What to keep, and where

DataWhereExample
A few small valuesshared_preferencesdark mode, language, the last name typed
One document, read and written wholea file (JSON)an order history, a draft, an export
Many records, searched and changed one by onea database (SQLite)notes, messages, a product catalogue
Secretsflutter_secure_storagea login token, a password
A copy of what the server senta file or a database, as a cachethe menu, to show it offline

Watch out

Preferences and files are plain text on the device: anyone with access to the phone, or a backup of it, can read them. Never put a password or a login token there; flutter_secure_storage keeps them in the Keychain on iOS and an encrypted store on Android. Book 6 uses it for real logins.

{{n}}.2 Small values: shared_preferences

The shared_preferences package keeps key–value pairs, strings, numbers, booleans and lists of strings, in each platform’s own place: on Android a preferences file, on iOS NSUserDefaults, on the web the browser’s local storage. The chapter adds it with the other packages it uses:




The settings model of Chapter {{n-2}}, now with a memory:








    

  • SharedPreferencesAsync is the package’s current interface: every read and write is a Future, because it really goes to the disk. getBool returns null for a key that was never saved, hence ?? false.
    • 

  • The setters change the field and notify first, then save. The switch moves at once; the disk catches up a moment later.
    • 

  • main is now async. WidgetsFlutterBinding.ensureInitialized() prepares the engine, which plugins need to reach the platform, and await settings.load() reads everything before runApp: the very first frame is already dark, instead of flashing light and then switching.
    • 




Tip
Loading before runApp is right for a few settings, which take milliseconds. Never load large data there: the person stares at a blank screen until it finishes. Large data loads after the first frame, with a loading state, as in Chapter {{n-1}}.

{{n}}.3 Files: one document at a time



An order history grows, and has structure: a list of orders, each with a name and a total. It is one document, read when the screen opens and written when an order is added: a JSON file. Every app has its own private folder for such files, given by the path_provider package:






    

  • getApplicationDocumentsDirectory() returns the app’s documents folder: private to the app, kept until the app is uninstalled, and included in the phone’s backups. For data that can be downloaded again, getApplicationCacheDirectory() is the right place: the system may empty it when space runs low.
    • 

  • The folder function is a parameter with a default, exactly like the http.Client of Chapter {{n-1}}: the app gets the real folder, the test gets a temporary one.
    • 

  • A missing file is not an error: it is the first time.
    • 

  • Writing goes to a new file first, then rename puts it in place in one step. If the battery dies in the middle of writing, the old file is still whole. Writing directly over the file could leave half of it, and the history would be lost.
    • 




The test uses a real folder on the disk, and even checks the exact text in the file:








Did you know?
path_provider and the dart:io files do not work on the web: a web page has no folders. That is why the screenshots of this chapter come from preferences, which do work in a browser, and the file and database examples are proven by tests. If your app must also run on the web, choose preferences, or a package that supports it, from the start.



{{n}}.4 A database: sqflite



A file is read and written whole. With a thousand notes, changing one tick means rewriting all of them, and finding the notes that contain a word means reading all of them. A database does both directly. Every phone has SQLite, a small database in a single file, and the sqflite package lets Flutter use it with the SQL you may know from Book 3:






    

  • openDatabase opens the file, or creates it. onCreate runs only the first time, and creates the table.
    • 

  • version is the version of your table design. When a later version of the app needs a new column, it raises the number to 2 and adds an onUpgrade that runs ALTER TABLE: the notes already on people’s phones are kept and updated, not lost.
    • 

  • insert, query, update and delete build the SQL for you. insert returns the new row’s id.
    • 

  • The search word goes in whereArgs, and the SQL has a ? in its place. Never build SQL by joining text: a note containing a quote would break it, and in a server it would be a security hole.
    • 

  • SQLite has no booleans: toRow and fromRow translate between true and 1 at the edge, like fromJson in Chapter {{n-1}}.
    • 




On a computer, tests reach SQLite through the sqflite_common_ffi package, and a database can live only in memory:








Professional habit
Keep storage behind a small class with plain methods: load, add, search. The screens never see SQL, file paths or keys. When the data outgrows preferences, or moves to a server, one class changes, and every screen keeps working.

Summary



    

  • Memory empties when the app closes; storage on the device stays.
    • 

  • shared_preferences for a few small values; a JSON file for one document; SQLite with sqflite for many records; secure storage for secrets.
    • 

  • Load settings before runApp, after WidgetsFlutterBinding.ensureInitialized(); change the screen first, then save.
    • 

  • Files go in the app’s folder from path_provider; write a new file, then rename it.
    • 

  • A database has a version and onCreate/onUpgrade; values go in whereArgs.
    • 

  • Test with an in-memory preferences store, a temporary folder, and an in-memory database.
    •

Cups today, remembered

    2. 

  2. In initState, call load(), which reads getInt('cups') ?? 0, then, if mounted, sets it with setState.
    3. 

  3. “One more” and “Reset” call change(value), which sets the state and then saves with setInt.
    4. 

  4. While cups is null, show nothing: a wrong 0 that turns into 3 is worse than a blank moment.
    5. 



Hint: initState cannot be async, so it starts the future and does not wait for it; load calls setState when the value arrives.

Project {{n}}.2 · Medium


Recent searches


Remember the last five searches, newest first and without repeats, as chips that fill the field again.


You will practise: getStringList, list rules in a model, remove, chips, and a model test.


    

  1. A Recent model keeps words. Its add trims the word, ignores it if empty, and builds [w, ...words.where((old) => old != w)].take(5).toList().
    2. 

  2. Save with setStringList after every change; clear uses prefs.remove('recent').
    3. 

  3. The field’s onSubmitted adds the word and clears the field. Each word is an ActionChip that puts it back in the field.
    4. 

  4. Test the rules: add a, b, c, d, e, f, then b again and a blank; expect ['b', 'f', 'e', 'd', 'c'], and the same list from a new model.
    5. 



Hint: searching for a word already in the list moves it to the front instead of adding it twice: the where removes the old one before the new one is put first.

Project {{n}}.3 · Challenge


A basket that survives anything


Save the whole basket as JSON, restore it on opening, and never crash on a damaged value or one from another version of the app.


You will practise: jsonEncode of a map, a format version, try/catch, and tests of bad data.


    

  1. Keep counts, a Map<int, int> from drink id to quantity. After every change, save {'version': 1, 'items': {...}} with setString.
    2. 

  2. JSON keys are always strings: write the ids as '${e.key}', and read them back with int.parse.
    3. 

  3. In load, return without changes if the version is not 1, and skip ids that are no longer on the menu.
    4. 

  4. Wrap the reading in try; in catch, empty the basket and remove the damaged value, so that the app opens normally next time too.
    5. 

  5. Test four bad values: not json, a list, version 2, and a quantity that is a string. Each must give an empty basket.
    6. 



Hint: anything saved on a device will one day be read by a newer version of your app, or come back damaged. The version number costs one line, and saves you from guessing what an old value meant.
