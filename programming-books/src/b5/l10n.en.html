Chapter {{n}}

Arabic, English and RTL

In this chapter you will learn to

  • build layouts that are correct in both directions, with start and end instead of left and right
  • keep every text of an app in translation files, one per language, and generate Dart code from them
  • write plurals properly, including Arabic’s six forms
  • format prices and dates for each language, and choose between Western and Eastern Arabic digits
  • let people switch the language inside the app, and remember their choice

The Arabic apps in this book so far have been turned right to left by one line that the book promised to explain. That line forces a direction; it does not translate anything, does not change Material’s own buttons, and does not know how Arabic counts. This chapter builds the café app properly in two languages at once: all its texts in translation files, the direction following the language, plurals, prices and dates written as each language writes them, and a menu to switch.

This chapter’s app is the same in both editions of the book, because it speaks both languages. Only the comments in the code are in the language of the edition you are reading.

{{n}}.1 Start and end, not left and right

Arabic is written from right to left, and so is everything around it: the first item of a row is on the right, the back arrow points right, a list’s icon is on the right of its text. Flutter mirrors all of this by itself, from the text direction, as long as the code says start and end instead of left and right:






    

  • Directionality sets the direction for everything under it. Usually you never write it: MaterialApp sets it from the language.
    • 

  • The Row mirrors in both cards: the cup comes first, on the start side. The arrow Icons.arrow_forward mirrors too: Material marks the icons that have a direction.
    • 

  • EdgeInsets.only(left: 48) stays on the left in Arabic, where it is now the end of the row: the gap is on the wrong side. EdgeInsetsDirectional.only(start: 48) follows the direction.
    • 

  • The same pairs exist everywhere: Alignment.centerLeft and AlignmentDirectional.centerStart, BorderRadius and BorderRadiusDirectional, Positioned and PositionedDirectional, TextAlign.left and TextAlign.start.
    • 




Professional habit
Write start and end from the first line of every app, even one that has only one language today. It costs nothing, and the day the app gets an Arabic, Hebrew, Persian or Urdu version, the layout is already right. Reserve left and right for what really is physical: a shadow’s direction, a picture that must not be flipped.



{{n}}.2 Texts in translation files



Flutter’s own tool for translations is gen-l10n (“l10n” is short for “localization”: an l, ten letters, an n). It reads one ARB file per language, a JSON file of texts, and writes a Dart class with a method for each text. The packages: flutter_localizations, which comes with Flutter and holds the translations of its widgets, and intl, which formats numbers and dates:






Two settings switch the tool on. In pubspec.yaml, under flutter:, the line generate: true regenerates the code at every flutter run and build. And a file l10n.yaml at the project’s root says where the files are:






The English file is the template: every text is there, with a description and its placeholders, the values that change:






The Arabic file has the same keys and only the texts:









The tool wrote lib/l10n/app_localizations.dart and one file per language. Every key became a getter or a method: l.appTitle, l.price(45), l.pickUpOn(day). A missing key in Arabic, or a placeholder written wrong, is now an error when the app is built, not a blank on someone’s screen.



Tip
The generated files are not yours: never edit them, because the next build writes them again. That is also why the project’s analysis_options.yaml excludes them from the analyzer: lib/l10n/app_localizations*.dart.



{{n}}.3 Plurals: six forms in Arabic



English has two forms, one item and several items. Arabic has six: zero, one, two, a few (3 to 10), many (11 to 99) and the rest (100, 101…). A message that adds an “s” cannot be translated; a plural message in ICU form can:






=0, =1 and =2 are exact numbers; few, many and other are the language’s own categories, and intl knows which numbers belong to which in every language. The test checks the forms, and the formatted prices and dates:








Did you know?
The number in a plural is written as it is, 1500, while a placeholder with "format": "decimalPattern" is grouped, 1,500. For prices and big counts, give the number its own placeholder with a format.



{{n}}.4 The app in two languages



The app gives MaterialApp the languages it supports, the delegates that load each language’s texts, and the language to use:






Watch out
gen-l10n also generates a ready list, AppLocalizations.localizationsDelegates, and many tutorials use it. In Flutter 3.50 it still names Material’s translations from flutter_localizations, from before Material moved to material_ui. With it, our own texts were translated, but Material’s were not: the date picker could not even open in Arabic, because it found no Arabic texts for its buttons. Flutter’s own warning in the test named the fix: our delegate, then GlobalMaterialLocalizations.delegates (plural) from material_ui, which brings Material’s texts, Cupertino’s, and the direction of the text.






Inside the screens, AppLocalizations.of(context) gives the texts of the current language. Nothing in the page says “English” or “Arabic”:













Compare the two screens: the title, the welcome, the drinks and prices, the plural (3 items, 3 قطع), the date with its weekday, the direction of the whole page, the arrow, and even the position of the language button. One line in MaterialApp changed all of it. Material’s own widgets follow too:





Watch out
Look at the Arabic screen again: the price says 45 but the date says ٣ ديسمبر ٢٠٢٦. The test of Section {{n}}.3 got “3 ديسمبر 2026” from the same message. The difference is Material: when an app starts in Arabic, Material loads its own Arabic date data, which writes Eastern Arabic digits, and every date formatted after that uses it; numbers are not affected. If your app must use one kind of digits everywhere, decide it once: format with ar_EG for Eastern digits, or with a locale of Western digits for both, and test on the screen, not only with lookupAppLocalizations.



{{n}}.5 Choosing the language



By default, locale is null and Flutter takes the phone’s language, if the app supports it, or the first supported one. Many people in Arabic-speaking countries use phones in English but want an app in Arabic, or the opposite: give them a choice, and remember it, as in Chapter {{n-1}}:






The menu writes each language in its own words, “English” and “العربية”, whatever the current language: someone who cannot read the current one must still find their own. The test chooses Arabic, then checks the translation, the direction and what was saved:

Summary



    

  • Say start and end: EdgeInsetsDirectional, AlignmentDirectional, BorderRadiusDirectional; rows and directional icons mirror by themselves.
    • 

  • Texts live in one ARB file per language; gen-l10n, switched on by generate: true and l10n.yaml, turns them into AppLocalizations.
    • 

  • Placeholders carry values, with formats for numbers and dates; ICU plurals cover Arabic’s six forms.
    • 

  • MaterialApp takes supportedLocales, the delegates, and locale (null follows the phone); the direction comes from the language.
    • 

  • intl formats numbers and dates; for numbers, ar writes 0 to 9 and ar_EG writes ٠ to ٩; once Material is loaded in Arabic, dates use its Eastern digits.
    • 




Quick check answers: 1. In Arabic the row starts on the right, so a gap on the left is at its end, the wrong side; EdgeInsetsDirectional.only(start: 16) follows the direction. 2. Six; 11 is “many” (11 to 99), 3 is “few”, 100 is “other”. 3. Follow the phone’s language, if the app supports it.
