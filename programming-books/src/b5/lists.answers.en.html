1. It starts just as fast. itemCount is only a number; the builder is still called for the dozen or so rows on the screen, whether there are a thousand orders or a hundred thousand. What would be slow is creating 100,000 objects of data before showing the list, which is why real apps load long lists page by page (Chapter 11).
  2. Flutter divides the width inside the padding, 366 pixels, by the maximum plus the spacing, and rounds up: with 120, 366 ÷ 132 is about 2.8, so 3 columns of about 114 pixels each. With 400, 366 ÷ 412 is under 1, so 1 column, as wide as the screen. (With the chapter’s 200, 366 ÷ 212 gives 2 columns on the phone, and on the tablet 796 ÷ 212 gives 4.)
  3. Use itemCount: drinks.length + 1. In itemBuilder, return the header when i == 0, for example Padding(padding: EdgeInsets.all(16), child: Text('${drinks.length} items')), and otherwise the tile for drinks[i - 1]. Everything that reads the list by index must use i - 1; forgetting it is the classic bug of this pattern.
  4. Keep a ThemeMode in the state instead of a bool, starting at ThemeMode.system, which follows the phone’s own setting. A SegmentedButton<ThemeMode> with three segments (light, system, dark) sets it with setState, and MaterialApp(themeMode: mode, ...) uses it directly. Storing the enum rather than a bool means no conversion and no impossible states.
  5. The error says the vertical viewport was given unbounded height. A Column gives its children unlimited height (it is willing to grow), and a ListView wants to be as tall as it is allowed, so it has no size to be. Fix it by wrapping the list in Expanded, which gives it exactly the height left in the column; or by giving it a fixed height with SizedBox(height: 300, child: ListView(...)). (A third way, shrinkWrap: true, makes the list measure all its children, which loses the benefit of building only what is visible: avoid it for long lists.)
