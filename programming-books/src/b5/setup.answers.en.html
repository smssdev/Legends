For every line, -v adds the details behind the check: where Flutter is installed and from which Git address, the Dart and DevTools versions, where the Android SDK is, which platforms and build tools it contains, which Java Android Studio uses, the path of Chrome, and each connected device with its system version. Note the two paths, Flutter’s and the Android SDK’s: they are the first thing to check when a tool cannot find the other.
  2. Change 'Hello, hot reload!' and Colors.teal, and save; with hot reload each change appears at once. To move the title, remove centerTitle: true,. On Android the title then moves to the start of the bar; on an iPhone it stays centred, because a centred title is the iPhone’s own style, and Flutter follows each platform’s habits unless you say otherwise.
  3. Android takes the name under the icon from android/app/src/main/AndroidManifest.xml, in android:label="hello_bit". iOS takes it from ios/Runner/Info.plist, in the value after CFBundleDisplayName, which flutter create set to Hello Bit. Changing the app’s name for the stores is one of the few reasons to edit these folders; Chapter 15 does it.
  4. Change the expected text, for example to find.text('Hello, Dart!'). The failure names the test, then says what was expected (exactly one widget with that text) and what was found (none), then the file and line of the expect that failed. Read it as: “in this test, at this line, I expected this, and got that”. Every test failure has the same three parts.
  5. There is no single answer. A good checklist has one action per line, the exact command or link, what you should see when the step worked (for example “flutter doctor shows [✓] Android toolchain”), and the problems people met with their solutions. Each friend who follows it finds a step you thought was obvious: that is the point of the exercise.
