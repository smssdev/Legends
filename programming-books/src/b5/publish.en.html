Publishing to Google Play and the App Store

In this chapter you will learn to

  • give an app its identity: a unique id, a name in each language, a version and an icon
  • create an upload key and sign Android release builds without putting a secret in any file
  • build an Android App Bundle and check who signed it
  • walk through Google Play Console and App Store Connect, from account to review
  • keep a short, repeatable routine for every release after the first

Bit Notes runs on your phone. To run on everyone else’s, it needs what every published app has: a name people see in their language, an icon, a version, a signature that proves each update comes from you, and a page in a store. This chapter does all of it for the app of Chapter {{n-1}}, for real: the icon was drawn, the key was made, and the bundle was built and signed on the machine that made this book. Only the stores’ websites cannot be run in a book; for them, the chapter is a guided walk.

Everything in a terminal in this chapter really ran, including the Android release build. The iOS steps need a Mac with Xcode, which the book’s machine is not, so they are described and not shown: you will see them on your own Mac.

{{n}}.1 The app’s identity

Every app in a store has an application id (Android) or bundle id (iOS): a reversed domain that is unique in the world and can never change once published. flutter create builds it from --org and the project’s name:




Bit Notes is now online.bitcafe.bit_notes on both platforms. Use a domain you own, or at least one nobody else will use: com.example is refused by Google Play.



The version lives in pubspec.yaml, in two parts:






    

  • 1.0.0 is the version name that people see in the store: change it as you like, usually major.minor.patch.
    • 

  • +1 is the build number, which the stores use to know which build is newer. It must grow with every upload, and two uploads can never share one.
    • 




The name under the icon is set per platform. On Android, the manifest points to a text resource, so that each language can have its own:










On iOS the same is done in Xcode: CFBundleDisplayName in ios/Runner/Info.plist, and an InfoPlist.strings file for each language.



{{n}}.2 The icon



Every platform needs the icon in many sizes, and Android also wants an adaptive icon: a foreground and a background that each phone cuts into its own shape. The flutter_launcher_icons package makes them all from one large picture. Its settings go in pubspec.yaml:















Tip
Draw the icon for its smallest size, not its largest: on a phone it is about a centimetre wide. One clear shape, strong contrast, no text. Keep the important part of an adaptive foreground in the middle two thirds: phones cut the edges off in circles, squares and drops.



{{n}}.3 Signing for Android



Android only installs apps that are signed, and a store accepts an update only if it is signed by the same key as before. Google Play uses two keys: the app signing key, which Google keeps and uses to sign what people download, and your upload key, which proves to Google that an upload comes from you. If you lose the upload key, Google can replace it; nobody else can sign in your name. You make the upload key once, with keytool, which comes with Java:






    

  • -validity 10000 days: about 27 years. An app is signed with the same key for its whole life.
    • 

  • -storepass:env STORE_PASSWORD reads the password from an environment variable, so it never appears in the command, the terminal’s history, or a file. Before running it, set the variable without showing it: read -s STORE_PASSWORD && export STORE_PASSWORD.
    • 

  • keytool suggests the newer PKCS12 format; both work, and Flutter’s own guide uses JKS, as here.
    • 

  • The key goes in ~/keys, outside the project. Keep a copy somewhere safe, with its password in a password manager.
    • 




Gradle, Android’s build tool, needs to find it. A small file says where, and nothing more:






Flutter’s template already keeps it, and every key file, out of Git:






Then the app’s Gradle file signs release builds with it. Two imports go at the top of android/app/build.gradle.kts, and the template’s buildTypes block, which signed with the debug key, is replaced:






Watch out
Many guides put the passwords in key.properties. It works, but then a file on your disk holds everything needed to sign in your name, and one careless git add -f publishes it. Reading the password from the environment keeps the file harmless. On a build server, the variable comes from the server’s secret store.



{{n}}.4 The release build



Stores want an Android App Bundle (.aab): Google Play builds from it a small APK for each kind of phone. One command builds it, signed:






A release build is not the app you ran during development. It is compiled ahead of time to machine code, without the debugging tools, and only the icons the app uses are kept: the Material icon font went from 1.6 MB to about 2 KB. Before uploading anything, check that it is signed with your key and not the debug one:






Did you know?
To try the real release build on your own phone before publishing, run flutter run --release with the phone connected. It is faster than the debug build you know, and it is what people will get. Most “it worked on my phone” surprises are found this way.

{{n}}.5 Google Play



The rest happens in the Play Console, Google’s website for developers. Its screens change often, but the path has been the same for years. At the time of writing:



    

  1. Account. Register as a developer, once, with a one-time fee of 25 US dollars and an identity check. A personal account or an organisation’s, which needs its own official number.
    2. 

  2. Create the app. Its name in the store, its default language, app or game, free or paid. Free can never become paid later.
    3. 

  3. Store listing. A short and a full description in each language you support, the icon at 512 × 512, a feature picture of 1024 × 500, and at least two screenshots of the phone. Write the Arabic listing yourself, as you wrote the app’s ARB file.
    4. 

  4. App content. A link to a privacy policy, the Data safety form (what the app collects and why: Bit Notes keeps notes only on the phone, and sends nothing), a content rating questionnaire, the target age, and whether there are ads.
    5. 

  5. Testing. Upload the .aab to the internal testing track first: up to a hundred people you invite get it in minutes. New personal accounts must then run a closed test with at least twelve testers for fourteen days before they may publish to everyone.
    6. 

  6. Production. Create a release in the production track, with the same bundle or a newer build number, and notes on what changed, in each language. Google reviews it, usually within hours, sometimes days, and the app appears.
    7. 




On the first upload, Play Console turns on Play App Signing: Google creates the app signing key, and from then on checks your upload key on every upload.



{{n}}.6 The App Store



Apple’s path needs two things the Android one does not: a Mac with Xcode, because iOS apps are built and signed only there, and a paid membership of the Apple Developer Program, 99 US dollars a year. Then:



    

  1. Identity. On the developer website, register the bundle id online.bitcafe.bitNotes (iOS ids cannot contain _, so flutter create writes it in this form). In Xcode, open ios/Runner.xcworkspace, choose your team under Signing & Capabilities, and let Xcode manage the certificates.
    2. 

  2. The app record. In App Store Connect, Apple’s website for developers, create the app with the same bundle id, its name, and its primary language.
    3. 

  3. Build and upload. flutter build ipa builds a signed archive in build/ios/ipa. Upload it with Apple’s Transporter app, or open the archive in Xcode’s Organizer and choose Distribute App.
    4. 

  4. TestFlight. The build appears in TestFlight after a few minutes of processing. Your team can install it at once; outside testers, up to ten thousand, after a short review.
    5. 

  5. The listing. Screenshots for each required iPhone size, descriptions in each language, a privacy policy link, and the privacy “nutrition label”: what the app collects, as in Google’s form.
    6. 

  6. Review. Submit the version for App Review. Apple checks the app against its guidelines, usually within a day or two; a rejection says why, and you answer or upload a fixed build.
    7. 




Professional habit
Use the stores’ testing tracks for every release, not only the first: internal testing and TestFlight cost you a day, and spare your users the bug you missed. Then publish to a small percentage of people first (both stores allow a staged rollout), watch the crash reports, and only then to everyone.



{{n}}.7 Every release after the first



    

  1. Raise the version in pubspec.yaml: a new version name if people should notice, and always a higher build number.
    2. 

  2. Run flutter analyze and flutter test. Try the release build on a real phone, in both languages and both directions.
    3. 

  3. Build, check the signature, upload to the testing track, then roll out.
    4. 

  4. Write the release notes in each language: people read them.
    5. 

  5. After release, read the crash reports and the reviews in both consoles. Answer reviews: politely, in the reviewer’s language.
    6.

Summary



    

  • Choose the app’s id once, with --org; it can never change. The version is name+build, and the build number grows with every upload.
    • 

  • Give the name per language (values-ar/strings.xml, InfoPlist.strings) and generate every icon with flutter_launcher_icons.
    • 

  • Make an upload key with keytool, keep it outside the project, and give Gradle its password from the environment.
    • 

  • flutter build appbundle makes the signed .aab; keytool -printcert proves who signed it.
    • 

  • Play Console and App Store Connect: listing, privacy forms, a testing track, review, then a staged release.
    • 




Quick check answers: 1. The build number, 17; the version name may stay the same. 2. With Play App Signing, Google can register a new upload key after you prove who you are; the app’s id can never change: a new id is a new app, without its users or reviews. 3. So that the file, even if copied or committed by mistake, does not give anyone the power to sign as you: the password comes from the environment at build time.
