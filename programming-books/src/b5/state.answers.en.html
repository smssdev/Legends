  2. Add void clear() { _counts.clear(); _prices.clear(); notifyListeners(); }. The test adds two items, counts notifications with a listener as the chapter’s test does, calls clear(), and expects count to be 0, total to be 0, and exactly one more notification: a method that notifies once per item removed would make every listener rebuild many times for one action.
  3. The page already watches the basket, so in this case the result is the same. But read in a callback says exactly what the code does, “use the basket now”, and keeps working if the page is later changed to select only the part it shows; a callback that depends on a value captured from watch can silently use an old one. Make read in callbacks a habit, and you never have to think about it.

The dialog is the same as Chapter 8’s, with “Clear” and “Cancel” buttons. Disable the button when the basket is empty, with onPressed: basket.count == 0 ? null : ....
  5. With select, the button rebuilds once per change of the count: adding a drink rebuilds it, and so does removing one. With watch, it rebuilds on every notification of the basket, including changes that do not touch the count, such as a change of price if you add one. In this small app the numbers are close, because almost every change changes the count; in a real app, where a model holds many values, select keeps each widget rebuilding only for what it shows, which is how large screens stay smooth.
