Chapter {{n}}

Forms and Input

In this chapter you will learn to

  • read what people type with TextField and a controller
  • show the right keyboard for each kind of input, and hide passwords
  • check a whole form before sending it, with clear messages beside each field
  • offer choices with segmented buttons, checkboxes, switches, sliders and drop-down menus
  • test forms by typing in tests

Every app that does something useful asks people for something: a name, a phone number, a password, a size, a note. Typing on a phone is slow and error-prone, so a good form asks for little, shows the right keyboard, explains mistakes kindly and immediately, and never loses what was typed. This chapter builds forms like that, and ends Part II with the café’s order form, every choice changing the price as the customer makes it.

In this chapter the screenshots were typed for real: the book’s tools put the cursor in a field and pressed the keys one by one, as your fingers will.

{{n}}.1 Text fields











    

  • TextField is the box people type in. Its look comes from an InputDecoration: a labelText that moves up when the field has focus or text, a hintText shown while it is empty and focused, icons at either end, and a border.
    • 

  • A TextEditingController holds the text. Read it with name.text; change it with name.text = ... or name.clear(). The clear button calls setState(name.clear): clear the text, then rebuild.
    • 

  • onChanged runs after every key. Here it only calls setState, so build runs again and the greeting follows the text.
    • 

  • A controller holds resources, so the State releases it in dispose, the method Flutter calls when the State is removed for good. Every controller you create, you dispose.
    • 




{{n}}.2 The right keyboard



A phone has no physical keyboard: the app chooses which one appears. Choosing well saves people a lot of taps:










PropertyWhat it does



keyboardTypephone: a dial pad; emailAddress: a keyboard with @ and .; number: digits only; multiline: Enter makes a new line


textInputActionThe key in the corner of the keyboard: next moves to the next field, done closes the keyboard


obscureTextHides each character; the eye button flips it to let people check what they typed


autocorrect: falseStops the phone “correcting” email addresses and codes


maxLengthRefuses more characters than the limit, and shows a counter






The screenshot comes from a browser, which shows no on-screen keyboard. On your emulator or phone, tap each field and watch the keyboard change.



Tip
Add autofillHints: const [AutofillHints.email] (or .telephoneNumber, .password, .name) to a field, and the phone offers to fill it from the user’s saved details. One line, and many people never type at all.



{{n}}.3 Forms and validation



A form with several fields needs to check them all before sending, and say clearly what is wrong with each. Flutter’s Form does exactly that:








    

  • TextFormField is a TextField that belongs to the Form above it.
    • 

  • Each field has a validator: a function that takes the value and returns an error message, or null when the value is fine. The message appears under the field, in red.
    • 

  • The GlobalKey<FormState> gives the page a handle on the form. formKey.currentState!.validate() runs every validator, shows every message, and returns true only if all of them passed.
    • 

  • The form checks nothing until the first “Send”: an error before people have finished typing is rude. After a failed try, AutovalidateMode.onUserInteraction rechecks each field as it changes, so the red message disappears the moment the mistake is fixed.
    • 

  • The phone validator uses a regular expression, a pattern for text: ^[0-9]{11}$ means exactly eleven digits from start to end.
    • 




Tests type with tester.enterText:








Professional habit
Checking in the app is for people: fast, friendly messages. It is not protection. Anyone can send anything to your server without your app, so the server must check every value again. Chapter 11 talks to a server; this rule applies to every request you send.



{{n}}.4 Choices



When the answer is one of a few known values, do not make people type it. Material has a widget for each kind of choice:










WidgetChoose it for



SegmentedButtonOne of two to five options, all visible: sizes, views


CheckboxListTileIndependent yes/no items: extras, “remember me”


SwitchListTileA setting that takes effect at once: dark mode, notifications


SliderA number in a range, when the exact value matters less than the feel


DropdownMenuOne of a longer list, hidden until needed






All of them follow the same pattern as the star rating of Chapter 5: they show a value they are given (selected, value, initialSelection), and report a new one through a callback (onSelectionChanged, onChanged, onSelected). The state keeps the value; setState stores the new one. The segmented button takes a Set, because it can also allow several selections.

{{n}}.5 Project: the café order form



The last project of Part II brings it together: a name that must be given, a size, an extra shot, a number of cups and a note, with the price on the button changing at every choice.















    

  • The sizes are an enum that carries its price and its label, as in Chapter 3: adding a size is one line, and the compiler finds every switch that must change.
    • 

  • The total is a getter, computed from the state every time build runs. It is never stored, so it can never disagree with the choices. Store what people choose; compute everything that follows from it.
    • 

  • place validates first and stops if the name is missing. Only then does it show the summary, in a dialog from Chapter 8.
    • 

  • The note uses maxLines: 3 for a taller field, and alignLabelWithHint keeps its label at the top.
    • 









The test checks the arithmetic through the screen: a large (55) with an extra shot (10), twice, is 130.

Summary



    

  • TextField with an InputDecoration takes text; a TextEditingController reads and changes it, and is disposed in dispose().
    • 

  • Choose the keyboard with keyboardType, the corner key with textInputAction; hide passwords with obscureText.
    • 

  • A Form with a GlobalKey<FormState> checks every TextFormField’s validator with validate(); a validator returns a message or null.
    • 

  • Validate on submit, then as people type; check again on the server.
    • 

  • SegmentedButton, CheckboxListTile, SwitchListTile, Slider and DropdownMenu offer choices: each shows a value and reports changes.
    • 

  • Store what people choose; compute totals in getters. Tests type with tester.enterText.
    • 




Quick check answers: 1. null. 2. keyboardType: TextInputType.emailAddress. 3. Because controllers hold resources and listeners; releasing them when the State is removed avoids memory leaks.
