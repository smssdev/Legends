Project: A Complete Notes App

In this chapter you will

  • plan an app before writing it: its screens, its data and its files
  • build it in layers: the data, the store, the model, then the screens
  • use everything from the book together: forms, navigation, Provider, storage and two languages
  • delete with a swipe and undo, search as you type, and show empty and loading states
  • prove it works with a model test and a widget test that uses the app as a person would

Every chapter so far built a small app to show one idea. Real apps are not built that way: they are built in layers, each layer knowing only the one below it, so that each can be tested alone and changed without breaking the others. This chapter builds one complete app, Bit Notes, file by file, in the order a professional would, with nothing new to learn and everything to put together.

The screenshots of this chapter were taken by typing real notes into the app, letter by letter, in a browser whose language was set to the edition’s language. The app chose its own language from it.

{{n}}.1 The plan

Before any code, write down what the app does, in sentences a person would say:

  • I can write a note with a title and a text; a note without a title is refused.
  • I see my notes, newest first, with the pinned ones on top; I can pin and unpin.
  • I can open a note to change it, and swipe it away to delete it, with a way to undo.
  • I can search my notes as I type.
  • My notes are still there when I open the app again, in Arabic or English, as my phone is set.

Two screens are enough: the list, and an editor that both adds and edits. The files follow the layers:

lib/
  notes_app.dart        the app: MaterialApp, languages, the model
  delegates.dart        the translation delegates (Chapter {{n-1}})
  l10n/app_en.arb       the texts
  l10n/app_ar.arb
  notes/
    note.dart           the data: one note
    store.dart          where notes are kept
    model.dart          what the app can do with notes
    list_page.dart      the list screen
    edit_page.dart      the editor screen
test/
  model_test.dart       the rules, without any screen
  app_test.dart         the app, tapped as a person would

Professional habit

Build from the bottom up: data, then storage, then the model, and the screens last. Each layer can be tested as soon as it is written, before anything above it exists. When a screen finally appears, the rules under it already work.

{{n}}.2 The note

A note is plain data. It changes by making a new note with copyWith, never by changing a field, which keeps the old one intact for Undo. toJson and fromJson are the edge of Chapter {{n-3}}:




The time is saved as text in ISO 8601, 2026-11-05T00:00:00.000: readable, sortable, and understood by every language and database.



{{n}}.3 The store



The model needs somewhere to keep notes, but should not care where. An interface says what any store must do, and the app chooses one:






    

  • abstract interface class declares the two methods and nothing else. Any class that implements it can be given to the model.
    • 

  • PrefsNotesStore keeps all notes as one JSON value with a version, as in Project {{n-2}}.3. A few hundred notes fit easily, and it works on the web too.
    • 

  • MemoryNotesStore keeps them in a list: tests and examples get a store that starts exactly as they want, and touches no disk.
    • 




{{n}}.4 The model



The model is the only place that changes notes. Screens ask it, it changes the list, tells the screens, and saves:






    

  • visible is computed, not stored: the search and the order are applied every time it is read. There is no second list to forget to update.
    • 

  • The clock is a parameter, like the folder in Chapter {{n-2}}: the app uses the real time, the test chooses one.
    • 

  • remove returns the note’s position, and restore puts it back there: Undo needs nothing more.
    • 

  • Every change ends in _save: notify first, so the screen answers at once, then write.
    • 




The model can be tested completely before any screen exists. The test follows the plan’s sentences:

Each state has its own words, because each needs a different action from the person.

Summary



    

  • Plan in sentences, then in screens and files.
    • 

  • Build in layers, bottom up: the data, a store behind an interface, a model that alone changes the data, and screens that only watch and ask.
    • 

  • Compute what is shown; keep only one list.
    • 

  • Give every state its own screen: loading, empty, nothing found, and the notes.
    • 

  • Test the model alone, then the whole app with a memory store.
    • 




Quick check answers: 1. So that there is only one list: a kept copy would have to be updated after every add, edit, delete and search, and one forgotten update would show wrong notes. 2. Because after the await the tile has been removed from the screen, and its context is no longer valid; the model and the messenger read before it are still good. 3. Nothing: only a new class implementing NotesStore, and the one line in main that chooses it, as Project {{n}}.3 shows.

Project {{n}}.2 · Medium


Sort the notes


Let people sort by newest, oldest, or alphabetically, from a menu.


You will practise: an enum, a pure sorting function, PopupMenuButton, and a test of the function.


    

  1. An enum Sort { newest, oldest, az }.
    2. 

  2. A function sortNotes(notes, sort) that copies the list, sorts the copy with a switch, and returns it: it never changes what it was given.
    3. 

  3. A PopupMenuButton<Sort> in the bar sets the order; the list shows sortNotes(model.all, sort).
    4. 

  4. Test the three orders on the four sample notes.
    5.

Project {{n}}.3 · Challenge


Move the notes to SQLite


Write a SqliteNotesStore that implements NotesStore, and prove that the model works on it unchanged.


You will practise: implementing an interface, sqflite from Chapter {{n-2}}, transactions, and testing a layer through the one above it.


    

  1. Create a table notes with the five fields; the id is the primary key, and pinned is 0 or 1.
    2. 

  2. load reads all rows and builds notes. save runs in a transaction: delete all rows, insert the new list. If anything fails, nothing changes.
    3. 

  3. Reuse toJson for the row, replacing pinned with 1 or 0.
    4. 

  4. Test through the model: save the samples, load them in a NotesModel, unpin one, and load again in a new model.
    5. 

  5. In the app, the only change is the store given in main.
    6. 



Hint: saving the whole list on every change is simple and safe for hundreds of notes. With thousands, change the interface to add, update and remove one note, as Chapter {{n-2}}’s NotesDb does; the screens still will not notice.
