Chapter {{n}}

Everything Is a Widget

In this chapter you will learn to

  • see a screen as a tree of widgets, and read the code that builds it
  • show and style text, boxes, icons and buttons
  • write your own widgets, and reuse them
  • make a screen that changes when the user taps, with a StatefulWidget and setState
  • take colours and text sizes from the theme
  • test a widget by tapping it in a test

Part I taught you Dart. Part II uses it to build screens. In Flutter, every piece of a screen is a widget: the text, the icon, the button, the space between them, even the centring. You will spend the rest of the book combining widgets, so this chapter takes the most important ones one at a time, each in a small app you can run, and ends with a real piece of an app: a drink card for Bit’s café.

Every screenshot in this chapter is the real app, built from the code beside it. Type each one, run it, and change it with hot reload until the picture on your screen and the code in your head match.

{{n}}.1 A screen is a tree

Each example in this chapter is a complete app. Create a project for the chapter with flutter create, and put each example in lib/main.dart in turn (or keep them as separate files and run one with flutter run -t lib/tree.dart). Here is the first:






A widget is a description of part of the screen. Widgets contain other widgets, so the whole screen is a widget tree: MaterialApp holds a Scaffold, which holds an AppBar and a Center, which holds a Column, which holds an icon and two texts.





Some widgets draw something you can see: Text, Icon, the coloured bar of AppBar. Others only arrange their children: Center puts its one child in the middle of the space it has; Column puts its children one under the other; mainAxisSize: MainAxisSize.min makes the column only as tall as its content, so that Center can centre it. Arranging is the subject of Chapter {{n+1}}; this chapter is about the pieces themselves.



Look at const in front of Center. Everything under it is known before the app runs, so Dart builds it once and reuses it every time the screen is drawn. In Flutter, a screen is rebuilt very often, and const is a free way to make that cheap. The analyzer reminds you where you could add it.



{{n}}.2 Text








A Text shows a string. How it looks is all in its TextStyle: fontSize in logical pixels, fontWeight, color, height (the space between lines, as a multiple of the font size) and letterSpacing. maxLines and overflow: TextOverflow.ellipsis stop a long text after two lines with three dots: always think about what happens when a text is longer than you expected, because one day it will be.



A logical pixel is Flutter’s unit of size. A phone with a sharp screen packs two or three real pixels into each logical one, so a text of size 18 is the same physical size on every phone. The screenshots in this book are 390 logical pixels wide, the width of a typical phone.



{{n}}.3 Boxes and space








Container is the Swiss army knife of widgets. It can give its child:


    

  • a size: width and height;
    • 

  • padding: space inside the box, between its edge and its child;
    • 

  • a margin: space outside the box, between it and its neighbours;
    • 

  • a decoration: a BoxDecoration with a colour, rounded corners (borderRadius), a border and shadows.
    • 



EdgeInsets.all(24) gives the same space on all four sides; EdgeInsets.symmetric(vertical: 8) only above and below. When you only need one of these, use the smaller widget made for it: Padding for padding alone, SizedBox for a fixed size or a gap (SizedBox(height: 8) is the most common widget in Flutter), DecoratedBox for a decoration. They say exactly what they do.



{{n}}.4 Buttons and icons








Material gives buttons different weights, so that the most important action on a screen stands out:




ButtonUse it for



FilledButtonThe main action of the screen: usually one per screen


OutlinedButtonAn important action that is not the main one


TextButtonA minor action: “cancel”, “maybe later”


IconButtonAn action shown as an icon: like, share, delete





Every button has onPressed: the function to run when it is pressed, often written as an anonymous function () {} (which here does nothing). When onPressed is null, the button is disabled: Flutter draws it greyed out and ignores taps. You will use that to switch buttons off when their action makes no sense, as the café card does at the end of the chapter.


Icons come from Icons, which holds more than two thousand Material icons, each with a name: Icons.favorite_border, Icons.share, Icons.add. The spacing: 12 on the column puts 12 pixels between its children, and the Row puts the three icon buttons side by side.



Tip
To find an icon, search fonts.google.com/icons for what you mean (“coffee”, “cart”), then write the name in snake_case after Icons.. In VS Code, the editor shows a small picture of each icon next to its name as you type.



{{n}}.5 Your own widgets



When the same arrangement appears several times, make it a widget of its own. A contact page shows three rows, each with an icon and a text:










InfoRow is a StatelessWidget: a class with final fields, a const constructor with named parameters, and a build method that returns its tree. You already know every part of it from Chapter 3. Using it looks exactly like using Flutter’s own widgets: InfoRow(icon: Icons.phone, text: '...'). Change the padding or the icon colour in one place, and all three rows change.



Two details appear in every widget you will write. The constructor takes super.key: a key is an optional identity that helps Flutter tell widgets apart in lists, which Chapter 7 explains; pass it on and forget it for now. And build receives a BuildContext: the widget’s place in the tree, which Section {{n}}.7 uses.



Professional habit
Make widgets small. When a build method grows past one screen of code, or the same few widgets appear twice, cut a piece out into a widget with a clear name. Small widgets are easier to read, to test, and to rebuild quickly, because Flutter rebuilds only the widgets that changed.



{{n}}.6 Widgets that change: StatefulWidget



Every widget so far looks the same for ever. A like button must change when it is tapped: it has to remember something. That memory is called state, and a widget with state is a StatefulWidget:













A stateful widget comes in two classes:


    

  • LikePage, the widget itself, is still immutable: Flutter may throw it away and make a new one at any time. Its only job is createState.
    • 

  • _LikePageState is the State object. Flutter creates it once and keeps it while the widget is on the screen, so its fields, here likes, survive every rebuild. It is private (the underscore), because nobody outside needs it.
    • 




The key line is setState. It does two things: it runs the function you give it, which changes the state, and it tells Flutter that this widget needs to be built again. Flutter then calls build, which reads the new likes and returns a new tree: a full heart and the new number. You never change the screen directly; you change the state, and describe the screen for that state. This is the most important idea in Flutter, and Chapter 10 builds on it.



Testing a stateful widget is like using it: tap, then look. Flutter’s test tools do exactly that, without a phone:








tester.tap taps the widget that find.byIcon found, and tester.pump() lets Flutter build the next frame, as it would between two frames on a phone. Then expect checks the screen: one text saying 1, and a full heart.

  1. Which widget would you use for a gap of 16 pixels between two widgets?
  2. What happens to a FilledButton whose onPressed is null?
  3. In a stateful widget, where do the values that change live, and what must you call after changing them?

{{n}}.7 Theme and BuildContext



Choosing a colour for every widget by hand quickly becomes a mess. A theme chooses them once for the whole app:








ThemeData(colorSchemeSeed: Colors.teal) gives Flutter one colour, and Flutter builds a whole colour scheme from it: a primary colour, lighter containers, matching text colours, all chosen to work together and to be readable. Buttons and bars use the scheme automatically.



Your own widgets read the theme with Theme.of(context). This is what the BuildContext is for: it knows where the widget sits in the tree, so Theme.of(context) finds the nearest theme above it. theme.textTheme.headlineMedium is a named text style from the scheme, and copyWith (the pattern from Chapter 3’s exercises) changes only its colour. Change the seed to Colors.deepOrange and reload: the whole app follows.



Did you know?
The .of(context) pattern is everywhere in Flutter: Theme.of, MediaQuery.of for the screen size, Navigator.of for moving between screens in Chapter 8. Each one looks up the tree for the nearest widget that provides that kind of information.



{{n}}.8 Project: the café drink card



Let us build a real piece of an app: a card for one drink, with its name and description, a quantity the customer can change, the total, and a button to add it to the order.








Everything in the card is from this chapter, with four new details:


    

  • The widget takes the drink’s name, description and price, and the state reads them as widget.name: widget is the State’s way to reach the widget it belongs to. The card works for any drink.
    • 

  • The minus button is disabled at 1: onPressed: quantity > 1 ? ... : null. The rule “no fewer than one cup” lives in one line, and the screen shows it without any extra code.
    • 

  • Spacer() takes all the free space in the row, pushing the total to the far end.
    • 

  • SizedBox(width: double.infinity) makes the button as wide as the card; FilledButton.icon is a filled button with an icon and a label.
    • 




And the test checks the rule that matters, the total, after two taps on plus and one on minus:








Try it
Add a maximum of 10 cups, with the plus button turned off at 10, and extend the test to prove it. Then show the card three times in a Column, for a latte, a tea and a cake, each with its own quantity. Do the three cards share their state?



Common mistakes





MistakeWhat happensFix



Changing a state field without setStateThe value changes, but the screen does notChange it inside setState(() { ... })


Keeping changing values in the widget instead of the StateThe value is lost when Flutter rebuilds the widgetPut them in the State class


A text longer than its spaceYellow and black stripes: an overflowmaxLines and overflow, or room to wrap


A Column inside Center without mainAxisSize.minThe content sticks to the topmainAxisSize: MainAxisSize.min


Hard-coding colours everywhereChanging the app’s look means changing every fileUse the theme and Theme.of(context)


Forgetting constThe analyzer suggests it; the app does extra workAdd const where everything below is constant






Summary



    

  • A screen is a widget tree. Some widgets draw (Text, Icon), others arrange (Center, Column, Row).
    • 

  • Text looks the way its TextStyle says; plan for long texts with maxLines and overflow.
    • 

  • Container gives size, padding, margin and decoration; Padding and SizedBox do one job each.
    • 

  • Buttons have weights (filled, outlined, text, icon); onPressed: null disables one.
    • 

  • Write your own StatelessWidget for anything you repeat: fields, a const constructor, and build.
    • 

  • A StatefulWidget keeps its changing values in a State object; setState changes them and rebuilds.
    • 

  • Take colours and text styles from the theme with Theme.of(context).
    • 

  • Widget tests tap with tester.tap, rebuild with tester.pump(), and check with expect and find.
    • 




Quick check answers: 1. SizedBox(height: 16) in a column, or SizedBox(width: 16) in a row (or spacing: 16 on the column or row itself). 2. It is disabled: drawn greyed out, and taps are ignored. 3. In fields of the State class; change them inside setState, so that Flutter builds the widget again.
