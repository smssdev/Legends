Chapter {{n}}

Navigation

In this chapter you will learn to

  • open a new screen and come back from it, with Navigator.push and pop
  • give a screen the data it needs, and get an answer back when it closes
  • ask the user a question in a dialog
  • organise an app with tabs, a bottom navigation bar and a drawer
  • give every screen an address with the go_router package, including a page for addresses that do not exist

Until now every app had one screen. Real apps have many: a menu, a page for each drink, an order, an account, settings. Moving between them, and carrying data from one to the next, is called navigation. Flutter gives you a simple model for it, a stack of pages, and a few widgets that organise the top level of an app. This chapter covers both, and then adds the package most Flutter teams use for addresses.

Every screenshot in this chapter was taken after real taps on the running app, found by their labels, the way a screen reader finds them. If a label is missing, the taps cannot find the button, and neither can a blind user. Labels matter.

{{n}}.1 A stack of pages

Flutter keeps the screens of an app in a stack, like a pile of cards. The Navigator shows the top one. push puts a new page on top; pop takes the top page away and shows the one underneath again.











Navigator.push takes the context and a route: an object that knows how to show a page and how to animate it in. MaterialPageRoute uses the platform’s own animation: sliding in from the side on iOS, and Android’s own transition on Android. Its builder builds the new page, and here gives it the drink that was tapped through its constructor: the simplest and best way to pass data to a page.



The new page has a back arrow in its bar that nobody wrote: AppBar adds one whenever there is a page underneath. Tapping it, the phone’s back button or the iPhone’s swipe from the edge all call Navigator.pop for you.



{{n}}.2 Getting an answer back



Often the new page has a question to answer. The café’s drink page asks “how many?”, and the menu needs the answer. pop can carry a value back, and push returns a Future that completes with it, so the menu simply awaits:















    

  • Navigator.push<int> says what type of answer to expect. Navigator.pop(context, quantity) closes the page and sends the answer.
    • 

  • If the customer leaves with the back arrow instead, the answer is null: the code must handle that case, and here it simply does nothing.
    • 

  • After an await, the screen may have changed: the customer could even have left the menu. context.mounted checks that the widget is still on the screen before using its context. The analyzer warns you when you forget.
    • 

  • The quantity and the add button sit in the Scaffold’s bottomNavigationBar, inside a SafeArea: always at the bottom, always reachable by the thumb.
    •

{{n}}.3 Dialogs are routes too



A dialog that asks “are you sure?” is a small page on top of the stack, with the same answer mechanism:








showDialog pushes the dialog and returns a Future of its answer. Each button pops with true or false; tapping outside the dialog pops with null. Writing sure == true treats “no answer” as “no”, which is the safe choice for anything that deletes.



Professional habit
Name the buttons of a dialog after what they do (“Delete”, “Cancel”), never “Yes” and “No”: people read the buttons, not the question. And ask only before actions that cannot be undone; for everything else, act at once and offer undo, as in Chapter 7’s shopping list. A dialog for every action teaches people to tap “Yes” without reading.



{{n}}.4 Tabs



When a screen has a few sections of equal importance, tabs show them side by side under the bar, and let the user switch with a tap or a swipe:








A TabBar (the tabs) and a TabBarView (the pages) must stay in step: tapping a tab moves the pages, and swiping the pages moves the indicator. A controller keeps them in step, and DefaultTabController creates one for everything below it. The number of tabs, the number of pages and its length must all be the same.



{{n}}.5 The main sections of an app



Most apps have three to five main sections, always within reach. On phones they live in a NavigationBar at the bottom; less important places go in a Drawer that slides in from the side:













    

  • The NavigationBar is not navigation in the sense of the stack: it does not push anything. It changes a number in the state, and the body shows the page for that number.
    • 

  • IndexedStack builds all the pages and shows only one. A page you leave keeps its scroll position and its state, so coming back feels instant. (Showing pages[page] instead would rebuild each page from scratch.)
    • 

  • Giving the Scaffold a drawer adds a menu icon to the bar by itself, at the start; tapping it, or swiping from the start edge, opens the drawer.
    •

{{n}}.6 Every screen an address: go_router



Pushing pages by hand is perfect for small apps. Larger ones need every screen to have an address, a path like /drinks/1, as pages on a website do. Then a link in a notification or an e-mail can open the right screen directly (a deep link), the web version of the app has real URLs, and the browser’s back button works. Flutter’s team publishes a package for this, go_router. Add it to the project:






flutter pub add found the newest version that fits the project, downloaded it and the packages it needs, and wrote it into pubspec.yaml:






Now describe the screens as routes:








    

  • Each GoRoute joins a path to a page. Routes inside routes are below their parent: drinks/:id under / is /drinks/:id, and the menu stays underneath it, so the back arrow still leads to the menu.
    • 

  • :id is a path parameter: whatever is in that part of the address arrives in state.pathParameters['id'], always as a string.
    • 

  • context.go('/drinks/$i') changes the address; the router builds the stack of pages that matches it.
    • 

  • The app uses MaterialApp.router with routerConfig instead of home.
    • 




Watch out
An address can contain anything, because it can come from outside the app. int.parse of /drinks/abc throws, and /drinks/99 is a drink that does not exist. Always check path parameters, and give the router an errorBuilder for addresses that match nothing. Project {{n}}.3 does both.

Summary



    

  • Pages form a stack: Navigator.push with a MaterialPageRoute adds one, pop removes it; the back arrow appears by itself.
    • 

  • Pass data in through the page’s constructor, and out with pop(context, value); await push receives it, or null.
    • 

  • After an await, check context.mounted before using the context.
    • 

  • showDialog is a route with an answer; name its buttons after their actions.
    • 

  • DefaultTabController, TabBar and TabBarView make tabs; NavigationBar with an IndexedStack makes the main sections; Drawer holds the rest.
    • 

  • go_router gives every screen an address, with path parameters, nested routes and an errorBuilder; add it with flutter pub add.
    • 




Quick check answers: 1. A Future of the page’s answer; it completes when the page is popped, with the value given to pop, or null if none. 2. Because while waiting the user may have left the screen; using the context of a widget that is no longer on the screen is an error. 3. To keep every page alive, so that each keeps its scroll position and state when the user comes back.

Project {{n}}.2 · Medium


First-time pages


Welcome new customers with three pages they can swipe through, dots that show where they are, a “Next” button that becomes “Start”, and a “Skip” button; when they finish, replace the pages with the home screen so that back does not return to them.


You will practise: PageView with a controller, dispose, records in a list, AnimatedContainer, and pushReplacement.

    3. 

  3. Track the current page with onPageChanged. Draw the dots with AnimatedContainers: the current one wide, the others small; the change animates by itself.
