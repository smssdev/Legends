Chapter {{n}}

State with setState and Provider

In this chapter you will learn to

  • tell state that belongs to one widget from state that the whole app shares
  • lift state up to a parent, and pass changes back with callbacks
  • move shared state into a model class with ChangeNotifier, and test it without any screen
  • rebuild exactly what depends on a model, with ListenableBuilder
  • share a model across every screen with the provider package: watch, read and select

Part III builds real apps, and real apps share data between screens. The basket is filled on the menu, counted in the bar, listed on its own page and emptied at the checkout. Until now each widget kept its own state, which is perfect for a switch or a text field and hopeless for a basket. This chapter grows the café step by step, from setState in one widget to one basket that every screen shares, and shows the line of thought behind each step, so that you can choose for yourself.

The question of this chapter is not “which library is best?”. It is “who needs to know about this value?”. Answer that, and the right place for the state follows.

{{n}}.1 Two kinds of state

State is any data that can change while the app runs and that the screen depends on. It comes in two kinds:

Local stateApp state
Who needs itOne widgetSeveral widgets, often on different screens
ExamplesThe current tab, whether a password is shown, the text being typedThe basket, the signed-in user, the favourites, the settings
Where it livesIn the widget’s State, changed with setStateIn a model class above the widgets that use it

Everything you built in Part II used local state, correctly. Do not turn local state into app state “just in case”: a value that only one widget needs is simplest and safest inside that widget.

{{n}}.2 Lifting state up

The first step needs no new tool. When two widgets need the same value, move it to their nearest common parent, which passes the value down to one and a way to change it down to the other:








DrinkList does not know what a basket is: it receives onAdd, a function, and calls it. BasketBar receives the list and shows it. Only CafePage owns the basket, and only it calls setState, so there is exactly one place where the basket can change. This pattern, data down, events up, is the foundation of everything else in this chapter.



{{n}}.3 A model for the basket



Lifting works well for neighbours. It becomes painful when the shared value must travel through many layers that do not use it, or across screens. The next step takes the basket out of the widgets entirely, into a class of its own: a model.






Basket extends ChangeNotifier, a small class from Flutter’s foundation that keeps a list of listeners, functions to call when something changes, and calls them all when you call notifyListeners(). The model holds the data, privately; offers read-only views (counts returns an unmodifiable copy, so no screen can change the basket behind its back); and has methods for every change, each ending with notifyListeners(). The rules of the basket now live in one class, with no widgets in it, which means it can be tested in a few milliseconds:








A plain test, not testWidgets: no screen is built at all. The test also counts the notifications, four for four changes, because a change that forgets to notify is the most common bug in a model.



Professional habit
Keep your rules in models and your models free of widgets: no BuildContext, no colours, no navigation. A model like this can be tested exhaustively and quickly, reused by another screen, and kept when the design of the screens changes completely.



{{n}}.4 Listening without packages: ListenableBuilder



Flutter can listen to a model on its own. ListenableBuilder calls its builder again each time the model notifies:








There is no setState anywhere in this app, and the page is a StatelessWidget. The buttons call basket.add; the basket notifies; only the ListenableBuilder around the bar rebuilds. This is already a big improvement: the state is out of the widgets, and only what depends on it is rebuilt. What remains awkward is getting the basket to every widget that needs it: here it is passed through the constructor, which would mean passing it through every page of a large app.



{{n}}.5 Provider



The provider package solves that last problem: put the model once above the whole app, and let any widget below ask for it by its type. It is the approach Flutter’s own documentation teaches first. Add it:




















Three ways to get the model, for three different needs:




CallWhat it doesUse it



context.watch<Basket>()Gets the basket, and rebuilds this widget whenever it notifiesIn build, when the screen shows the model


context.read<Basket>()Gets the basket, without listeningIn callbacks such as onPressed, to call a method


context.select<Basket, int>((b) => b.count)Gets one value, and rebuilds only when that value changesIn build, when a widget needs one small part






The menu’s add buttons use read: they change the basket but do not show it, so they have no reason to rebuild. The badge uses select: it rebuilds when the count changes, not when anything else in the basket does. The basket page uses watch: it shows everything. The Badge widget draws the count on the bag icon, and hides when it is zero.



The widget test provides a basket exactly as main does, and walks across the two screens:








Watch out
Calling context.watch inside onPressed is an error: a callback runs once, it cannot “rebuild when the model changes”. And calling context.read in build is a quiet bug: the widget shows the model once and never updates. The rule is short: watch and select in build, read in callbacks.

  1. Is the text being typed in a search field local state or app state?
  2. What must every method that changes a ChangeNotifier do at the end?
  3. Which call would you use in an onPressed to add to the basket?

{{n}}.6 Choosing where state lives



Every approach in this chapter is right somewhere:


    

  1. Start with setState in the widget that uses the value.
    2. 

  2. When a neighbour needs it too, lift it to their parent, with callbacks.
    3. 

  3. When it holds rules worth testing, or many widgets need it, move it into a ChangeNotifier model.
    4. 

  4. When widgets on many screens need it, provide the model above the app.
    5. 




Did you know?
The Flutter world has many state management packages: Provider, Riverpod (by Provider’s own author), BLoC, and others. They differ in style, but every one of them is built on the ideas of this chapter: state outside the widgets, changes in one place, and widgets that rebuild when what they show changes. Learn these ideas well, and any of them takes an afternoon.

Summary



    

  • Local state belongs in a widget’s State; app state lives in a model above the widgets that share it.
    • 

  • Lift state up to the nearest common parent: data down, events up through callbacks.
    • 

  • A ChangeNotifier model holds the data privately, offers read-only views, and calls notifyListeners() after every change; test it with plain tests.
    • 

  • ListenableBuilder rebuilds only what listens to a model.
    • 

  • Provider puts a model above the app with ChangeNotifierProvider; widgets use watch and select in build, read in callbacks.
    • 




Quick check answers: 1. Local state: only the search field and its results need it, while the person types. 2. Call notifyListeners(). 3. context.read<Basket>().add(...).
