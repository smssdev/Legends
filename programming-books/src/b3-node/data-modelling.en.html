Chapter {{n}}

Data Modelling and Migrations

In this chapter you will learn to

  • turn a domain into tables: entities, relationships, and what to store or compute
  • change a schema with migrations that every machine runs the same way, and undo them
  • change a live schema without downtime, with expand and contract
  • generate TypeScript types from the real database, so tsc checks your queries
  • write typed queries with Kysely, a query builder close to SQL
  • see the N+1 problem in numbers, and fix it with one query

In Chapter {{n-1}} we created the shop’s tables by running a SQL file once. Real schemas are never written once: every month brings a new column, a new table, a rule that changes. The database in production is full of data that must survive every change, and the code that reads it must agree with it at every moment. This chapter is about keeping the schema, the data and the code in step, safely, and about writing queries that the compiler checks.

Early in my career I changed a column name directly on the production database on a Friday afternoon. The new code was not deployed yet; the old code kept asking for the old name. For twenty minutes every order failed. Since then, schema changes go through migrations, in small steps, and never on Fridays.

{{n}}.1 Modelling the shop

A data model starts from the entities of the domain (customers, products, orders) and the relationships between them:

  • One to many: a customer has many orders, an order has one customer. The “many” side holds a foreign key: orders.customer_id.
  • Many to many: an order has many products, a product is in many orders. A third table joins them, order_items, and it often carries its own data: the quantity and the price at the time.
  • One to one is rare: usually it means the two tables are one entity, or that some optional data is split off (a customer’s billing details).

Three questions decide most designs:

  • Store or compute? An order’s total can be computed from its items, so storing it as well creates two truths that can disagree. Store facts; compute what derives from them, until measurements say a stored copy is needed for speed. The price on order_items is not a copy: it is a different fact, the price then.
  • Which rules belong in the database? Every rule that must never be broken, whatever code writes the data: types, NOT NULL, uniqueness, foreign keys, ranges.
  • What happens on delete? Deleting a customer with orders must either be refused (the default), cascade, or be replaced by marking the row inactive. Decide per relationship, and write it in the foreign key.

{{n}}.2 Migrations

A migration is one change to the schema, written as code and kept in the repository: a function up that makes the change and a function down that undoes it. Each machine (your laptop, a colleague’s, CI, production) runs the migrations it has not run yet, in order, and records which ones ran. Nobody changes a shared database by hand.

Professional habit: never edit a migration that has run elsewhere
Once a migration is merged, other machines have run it, and changing its file changes nothing there: their database and yours now differ, silently. To fix a mistake, write a new migration. Before merging, run all migrations up, all down, and all up again on an empty database, in CI. It takes seconds and catches broken down functions and missing steps.



{{n}}.3 Changing a live schema: expand and contract



The shop needs a SKU, a stock code, for every product, required and unique. The obvious migration adds a NOT NULL UNIQUE column in one step. On a live system, that step fails or breaks things: the existing rows have no SKU, and the code running in production does not send one when it creates a product. While the new code is being deployed, old and new versions run side by side.



The safe pattern is expand and contract: change the schema in steps, each compatible with the code running at that moment.


    

  1. Expand: add the column as optional. Old code ignores it; nothing breaks.
    2. 

  2. Deploy code that writes it for every new product, and backfill the existing rows.
    3. 

  3. Contract: once every row has a value, make it required and unique.
    4. 










The same pattern renames a column (add the new one, write both, backfill, read the new one, drop the old one) or splits a table. It takes more migrations and more deployments, and it never takes the shop down. Two warnings for large tables: a backfill of millions of rows should run in batches outside the migration, and some changes lock a table while they run; Chapter {{n+9}} shows how to see those locks.

{{n}}.5 Typed queries



Kysely’s queries read like SQL, and their result types are built from what you select:









The type of order is exactly { id, status, customer, items: { name, quantity, price }[] }, with each field’s type from the schema; select another column and the type changes with it. jsonArrayFrom asks PostgreSQL to build the items as a JSON array inside the same query, so the order arrives in one round trip, already shaped.



Tip: query builder or ORM?
An ORM (Prisma, Drizzle, TypeORM) maps tables to objects and writes most SQL for you; a query builder such as Kysely keeps you close to SQL and only adds types and composition. ORMs are quicker for simple create-read-update-delete work. Query builders make the SQL you run obvious, which matters as soon as performance does. Both are good choices; what matters is that the team knows the SQL being sent. Turn on query logging in development whichever you choose.

201 queries against one, and many times slower, on a database on the same machine. Across a network, where each round trip costs a millisecond or more, the gap becomes seconds. N+1 is the most common performance bug in data-heavy code, because each query looks innocent and the loop hides the count. Watch the number of queries per request; Chapter {{n+9}} turns this into a habit.

Summary



    

  • Model entities and relationships; the many side holds the foreign key; many-to-many uses a joining table with its own facts.
    • 

  • Store facts, compute the rest; put every unbreakable rule in the schema; decide what deleting does.
    • 

  • Migrations are ordered, recorded, reversible changes in code. Never edit one that ran; test up, down, up.
    • 

  • Expand and contract changes a live schema in compatible steps.
    • 

  • kysely-codegen generates types from the real database; map bigint deliberately.
    • 

  • Kysely writes typed SQL; result types follow the selection; JSON aggregation shapes nested data in one query.
    • 

  • N+1: one query per row of a list. Count queries, and load related data together.
    • 




Quick check answers: 1. Other databases have already run it and will never run it again, so the change would exist only on some machines; fix mistakes with a new migration. 2. The existing rows have no value, so the database refuses the constraint (or, with a default, every row gets a meaningless value), and the old code still running does not send the column; add it as optional, fill it, then require it. 3. 1 + 50 = 51 queries; load the counts in the same query with a join and GROUP BY or a subquery, or in one second query with WHERE product_id IN (…).
