1. The three table rows fail and the two other tests pass. The rows are exactly the cases where VAT is charged on a positive amount; the “fixed discount never goes below zero” case has nothing left to tax (VAT of 0 at any rate), and the unknown code throws before VAT is computed. So the bug is in the VAT step, not in the discounts or the codes, and the diff (8550 instead of 7980, which is 15% instead of 14% of 57000) points at the rate. Good tests narrow a bug down by which of them fail.
  2. The branch where process.env.BUG is set: the tests never switch the bug on. It should not be covered by a test; it is not a feature of the shop but a switch put there for this exercise, and real code would not contain it. That is why coverage is a flashlight: an uncovered branch is a question (“is this tested, should it exist?”), not an order to write a test.
  3. (1) Shared data: another test file, or a previous test, inserts orders into the same table; check whether the test resets its data and whether files share a schema. (2) Order of execution: the test counts orders that a test running earlier or at the same time created; run it alone with --test-name-pattern many times, and then with the whole suite. (3) Something asynchronous still running: an order created by a request or job that was not awaited lands after the reset; look for missing awaits and jobs or timers left running. Running the test alone a hundred times and checking whether it ever fails separates (3) from (1) and (2).
  4. The second integration test, “refuses an order larger than the stock, and changes nothing”, already asserts mailer.send.mock.callCount() is 0 after a 409. It cannot catch an email sent inside a transaction that later rolls back, because the double only records that send was called; in that bug the email is sent (the double records one call) and the order disappears afterwards, so the test that would catch it is the opposite one: force the transaction to fail after the point where the email is sent (for example with a failing insert), and assert that send was not called. The better fix is in the design: send after the commit, or through an outbox.
  5. Unit level: a pure function isUnpaidTooLong(order, now) tested with a table of times on both sides of 15 minutes, without any clock. Integration level: the job or scheduled command that cancels orders, run against a real database, with orders whose created_at is set in the past by the test (rather than waiting), checking that only the unpaid old ones are cancelled and that stock is returned. The clock is controlled by passing now in (or with mock.timers for Date), never by sleeping. One end-to-end check at most, if the cancellation is visible to customers, using the same past timestamps. The queue itself needs no test of its timing: trust the library, test your code.
