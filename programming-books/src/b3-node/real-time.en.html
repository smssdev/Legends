Chapter {{n}}

Real-time Features

In this chapter you will learn to

  • choose between polling, server-sent events and WebSockets
  • push events to the browser with server-sent events, using nothing but HTTP
  • open two-way connections with WebSockets, and treat every message as untrusted input
  • make real-time work across several servers with Redis publish/subscribe
  • handle the hard parts: reconnecting, missed events, authentication and load

HTTP is a conversation the client always starts: it asks, the server answers, and the server has no way to speak first. Yet many screens should change by themselves: an order moving from “paid” to “shipped”, a chat message arriving, the last kits in stock disappearing. This chapter pushes an order’s status to the screen the moment it changes, first with server-sent events, then with WebSockets, and finally across two running copies of the server, which is where most real-time features break in production.

The first live feature I built was a counter of people viewing a product. It worked beautifully on my laptop. In production we ran three servers, and each one counted only its own visitors, so the number jumped between three different values every time the page reconnected. That week I learned what publish/subscribe is for.

{{n}}.1 Three ways to be up to date

  • Polling: the client asks every few seconds, “anything new?”. Simple, works everywhere, and often good enough; but most answers are “no”, each one costs a request, and news arrives up to one interval late.
  • Server-sent events (SSE): the client makes one ordinary HTTP request, and the server keeps the response open, writing an event whenever something happens. One direction only, server to client, but plain HTTP: it passes through proxies, works with cookies, and browsers reconnect automatically.
  • WebSockets: an HTTP request that is upgraded into a two-way connection, where either side can send a message at any time. The right tool when the client talks a lot too: chat, collaborative editing, games.

For updates that flow from the server to a screen, such as order statuses, notifications and live prices, SSE is usually the simplest choice. This chapter builds both, on one server.

{{n}}.2 Server-sent events

An SSE response has the type text/event-stream and is never finished. Each event is a few lines of text followed by an empty line: id: numbers it, event: names it, data: carries it, and a line starting with a colon is a comment, ignored by the browser:




To watch it, curl -N (no buffering) plays the browser in one terminal, while a second terminal changes the order’s status twice:









The two status changes appeared in the first terminal the moment they were made. In a browser, the receiving side is a few lines, with no library:



const events = new EventSource("/orders/1001/events");
events.addEventListener("status", (e) => show(JSON.parse(e.data)));



If the connection drops, EventSource reconnects by itself after a few seconds and sends the last id it saw in a Last-Event-ID header, so a server that keeps recent events can send what was missed (exercise 3).

{{n}}.4 Many servers: publish and subscribe



Real-time connections are long-lived and belong to one server process. With two or more servers behind a load balancer, the change may happen on server A while the customer’s screen is connected to server B. Keeping a list of connections in memory, as the first version of any live feature does, then silently fails for some users.



The fix is a message bus that every server listens to. Redis has one built in, publish/subscribe: PUBLISH order:1001 … delivers a message to every connection that ran SUBSCRIBE order:1001, on any server. The route that changes a status does not look for connections at all; it publishes, and whichever servers hold interested screens forward the message:






Two copies of the server run here, on ports 3000 and 3001. The client connects to 3001, and the changes are made on 3000:









Redis reported one subscriber to order:1001 (the connection held by server 3001), and both changes, made on server 3000, reached the client on 3001. The same happens with any number of servers. Two properties of pub/sub must be understood before relying on it:


    

  • Fire and forget. A message reaches only the subscribers connected at that moment; nothing is stored. A screen that connects a second later, or reconnects after a network blip, never sees it (exercise 4). Real-time messages are therefore hints that something changed; the truth stays in the database, and a client that reconnects loads the current state first.
    • 

  • A subscribed connection is busy. Once a Redis connection subscribes, it can only receive; publishing and other commands need another connection. Hence redis.duplicate() for each subscriber. With thousands of clients, share one subscriber connection per server and dispatch messages to sockets in memory.
    • 




Watch out: real-time does not replace the database
Never make a real-time message the only record of a change. Save the change, then publish; when a client connects or reconnects, send it the current state from the database, then the live updates. If the stream breaks for a minute, the user loses nothing but a little freshness. Redis Streams and dedicated brokers can store messages for replay, but the database remains the source of truth.

{{n}}.5 The hard parts



    

  • Authentication. SSE is an ordinary request, so cookies and headers work as in Chapter {{n-3}}, with one catch: the browser’s EventSource cannot add an Authorization header, so web clients use the session cookie. The browser’s WebSocket cannot set headers either: authenticate during the upgrade with the cookie, or have the client send a short-lived token as its first message, and close the socket if it does not arrive. And authorize every subscription: a customer may watch their own orders only, the same ownership rule as every other route.
    • 

  • Keeping connections alive. Proxies and load balancers close connections that stay quiet, often after 60 seconds. The SSE route sends a comment every 15 seconds; WebSockets have ping and pong frames for the same purpose, which also detect clients that vanished without saying goodbye.
    • 

  • Reconnecting. Networks drop, phones sleep, servers restart at every deploy. Clients must reconnect with a growing, random delay, so that ten thousand of them do not all reconnect in the same second after a deploy, and then reload the current state.
    • 

  • Capacity. Each open connection holds memory and a file descriptor for as long as the page is open. Node handles tens of thousands of idle connections per process, but limits (ulimit, proxy timeouts, load balancer settings) must be configured for long-lived connections. Graceful shutdown must close them, and clients must expect it.
    • 

  • Do you need it? A status that changes twice a day does not need a socket; polling every 30 seconds, or refreshing when the user returns to the tab, may be the better engineering.
    • 




Professional habit: test real-time with two servers from day one
Run two copies of the server locally, on two ports, from the first day you build a live feature, and connect the client to one while making changes on the other, exactly as this chapter did. Bugs that appear only with more than one server are the most common real-time bug in production, and they are invisible with one.

Summary



    

  • Polling asks repeatedly; server-sent events keep one HTTP response open for server-to-client events; WebSockets carry messages both ways.
    • 

  • SSE is plain text over HTTP: id, event, data; browsers reconnect by themselves and send Last-Event-ID.
    • 

  • WebSocket messages are untrusted input: parse safely, validate, limit size, authorize every subscription.
    • 

  • With several servers, changes go through Redis publish/subscribe, which delivers to every subscriber on every server.
    • 

  • Pub/sub is fire and forget: messages are hints; the database holds the truth, and reconnecting clients reload it.
    • 

  • Keep connections alive, reconnect with random delays, and test with two servers from the start.
    • 




Quick check answers: 1. SSE fits when updates flow only from the server to the client (statuses, notifications, live prices): it is plain HTTP, works with cookies and proxies, and reconnects by itself. When the client also sends frequent messages (chat, games, collaborative editing), a WebSocket avoids a new HTTP request per message. 2. Server 3000 published the change to the Redis channel order:1001; server 3001 had subscribed to that channel for its client, so Redis delivered the message to it, and it forwarded the message over the WebSocket. 3. Every message published during those 30 seconds: pub/sub does not store them. On reconnecting, it should load the order’s current state from the API (or receive it as the first message), and then follow the live updates.
