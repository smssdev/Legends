Chapter {{n}}

Testing

In this chapter you will learn to

  • decide what to test with unit, integration and end-to-end tests
  • write clear unit tests with Node’s own test runner, including table-driven tests
  • test routes against a real PostgreSQL database, with files running in parallel
  • replace slow or outside dependencies with test doubles, and control time
  • read a failing test, and measure what the tests cover
  • keep a test suite fast, reliable and worth trusting

Every chapter so far ended with a few tests. This one is about the craft itself. A good test suite is what lets you change code on a Friday afternoon without fear: it tells you within a minute whether the shop still takes orders, still charges the right amount and still refuses what it must refuse. A bad one is slow, fails at random, and is ignored. The difference is not the tool, which here is the test runner built into Node, but the decisions about what to test and how.

I once worked on a project with two thousand tests that took forty minutes and failed at random about once a day. Nobody believed a red build any more, so real bugs went out with the noise. We deleted a third of the tests, made the rest use a real database properly, and got the suite under three minutes. It caught more bugs with fewer tests.

{{n}}.1 What to test, and at which level

  • Unit tests call one function or class directly, with no network, database or clock. They are fast (thousands a second) and point straight at the broken line. They suit logic with many cases: prices, discounts, validation, state changes.
  • Integration tests run a real slice of the application: a route through its validation, its SQL and a real database. They are slower but test what the unit tests cannot: that the query is correct, that the transaction rolls back, that the status code is right.
  • End-to-end tests drive the whole system from the outside, often through a browser with Playwright (Book 2). They prove the main journeys work, and are the slowest and most fragile, so keep them few.

The classic advice is a pyramid: many unit tests, fewer integration tests, a handful of end-to-end tests. For a backend whose value is mostly in its queries, many teams lean towards more integration tests, because a unit test with a mocked database cannot catch a wrong WHERE. The real rule: test each behaviour at the lowest level where a bug in it would actually show.

{{n}}.3 Integration tests with a real database



The order route reads and writes PostgreSQL inside a transaction. Mocking the database would test only that the code calls the mock; the bugs worth catching are in the SQL. So the test runs the real route, through app.inject, against a real database:






    

  • Isolation between files. node --test runs each test file in its own process, in parallel. If two files shared tables, one could delete the other’s rows halfway through. Each file creates its own schema (a namespace inside the database), named after its process, and drops it at the end.
    • 

  • Isolation between tests. beforeEach resets the tables to a known state, so every test starts from the same data and tests can run in any order. A test that depends on another test’s leftovers will fail one day for no visible reason.
    • 

  • Checking the effects, not just the response. The first test checks the status, the body, the stock left in the database and the email; the second checks that a refused order left no row behind, which is the transaction of Chapter {{n-6}} doing its job.
    • 




The mailer is the one dependency replaced. Sending real email from tests would be slow and would reach real people, so the app receives a test double: mock.fn records every call, and the test asserts how it was called. This works because buildApp takes the mailer as a parameter instead of importing it, a design that makes code testable without any tricks (dependency injection).



Watch out: mock the edges, not the middle
Replace what is slow, outside your control or has effects in the world: email, payment providers, other companies’ APIs, the clock. Do not mock your own database, your own modules or the framework: tests full of mocks pass while the real thing is broken, and break whenever the code is reorganised even when nothing is wrong. If a test needs ten mocks, the code under test probably does too much.



{{n}}.4 Controlling time



A basket left alone for 30 minutes is released. Testing that by waiting 30 minutes is absurd, and testing it with the real clock is fragile. The runner can replace the clock with one the test moves by hand:






t.mock.timers makes Date.now() start at the given moment and advance only when the test calls tick, and it is restored automatically when the test ends. The two tests check both sides of the boundary, 29 and 30 minutes, which is where off-by-one bugs live. The same API controls setTimeout and setInterval, for code that schedules work.

{{n}}.6 Coverage



Coverage measures which lines and branches the tests ran:






Every line ran, and one branch in pricing.ts did not (exercise 2). Coverage is a good flashlight and a bad target. Low coverage reliably shows code nobody tests; high coverage proves only that lines were executed, not that anything was checked: a test with no assertions reaches 100% too. Use it to find untested areas, look at the uncovered lines of every change in review, and never chase a percentage for its own sake.



{{n}}.7 A suite worth trusting



    

  • Fast. A suite that runs in seconds is run before every commit; one that takes twenty minutes is run by CI and ignored until it fails. Parallel files, small datasets, and no sleeps.
    • 

  • Deterministic. The same code gives the same result every time. Flaky tests usually come from shared data, real time, random values, the order of results without ORDER BY, or waiting for something with a fixed delay. Fix them at once, or delete them: a flaky test teaches the team to ignore red.
    • 

  • Testing behaviour. Assert what the user or caller sees (responses, rows, emails sent), not how the code is arranged inside. Then the code can be improved without rewriting the tests.
    • 

  • Written with the bug. When a bug is found, first write a test that fails because of it, then fix it. The test proves the fix and keeps the bug from coming back.
    • 

  • Run on every change. In CI, on every pull request, against a real PostgreSQL started as a service, and the merge blocked while it is red.
    • 




Professional habit: a failing test first, for every bug
Before fixing a bug, reproduce it with a test and watch the test fail for the right reason. Only then fix the code and watch it pass. It takes a few minutes, it often reveals that the bug is not where you thought, and it adds to the suite exactly the case that real life proved you had missed.

Summary



    

  • Unit tests for logic with many cases, integration tests for routes and SQL against a real database, a few end-to-end tests for the main journeys.
    • 

  • Node’s node:test and node:assert are enough: describe, it, hooks, tables of cases, mock.fn, mocked timers and coverage.
    • 

  • Integration tests stay independent with a schema per file and a reset per test, and check effects as well as responses.
    • 

  • Test doubles replace the edges (email, payments, the clock), passed in through parameters; never the database or your own code.
    • 

  • A failure should explain itself: behaviour names and focused assertions.
    • 

  • Coverage finds untested code; a fast, deterministic suite run on every change is what makes it trustworthy.
    • 




Quick check answers: 1. Test files run in parallel processes; with shared tables, one file’s TRUNCATE or inserts could change another file’s data in the middle of its tests. A schema per file gives each its own tables in the same database. 2. Email has effects outside the system (real messages) and is slow, so the test only needs to know it was asked for, correctly. The database is where the bugs worth catching live (queries, constraints, transactions), so it must be the real one. 3. It moves the mocked Date.now() (and mocked timers) forward by 30 minutes instantly; it does not make real time pass, and it is undone when the test ends.
