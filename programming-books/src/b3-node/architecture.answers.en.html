Tests: domain unit tests for the arithmetic; a use-case test with a fake Customers port returning true and false; an adapter test for the membership query; and one HTTP integration test that a member’s order total is discounted.

Costs: network calls that fail or time out between orders and the rest; no shared transactions, so stock and orders can disagree and need sagas or outboxes; separate deployments, monitoring, tracing and on-call; data duplicated or fetched across the network; slower development while the boundary settles. Questions first: Which concrete problem would the split solve? Does orders need to scale differently from the rest, or be deployed by a separate team? Is the boundary already clean inside the monolith (could we split it tomorrow without rewriting)? If the answers are vague, keep a well-divided module and revisit when there is a measured need.
  5. Add a rule that walks every file under src/ and fails when a file imports kysely-store.ts unless it is src/server.ts. It matters because the store adapter is a detail: if routes, jobs or other modules import it directly, they bypass the use case and its rules, couple themselves to Kysely, and make it impossible to replace the adapter or test them with fakes. Keeping the concrete adapter visible only to the composition root keeps every other file depending on the port.
