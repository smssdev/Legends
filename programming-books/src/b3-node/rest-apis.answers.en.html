  4. One way: make cancel idempotent in its result. If the order is already cancelled, answer 200 with the order, because the client’s goal (a cancelled order) is reached. Another way: accept an Idempotency-Key on cancel too, and replay the first answer. The first is simpler and right here, because the second cancel changes nothing; keep 409 for orders that can no longer be cancelled because they were shipped. The general lesson: design actions so that repeating them is harmless, whenever the domain allows it.
  5. The class in answers/idempotency.ts keeps entries in a Map under the key client:key, so the same key from two clients is two entries. Each entry stores the time it was saved, read from a now function given to the constructor (by default Date.now); get deletes and ignores an entry older than the time to live. The tests pass a fake clock, () => now, and move now forward instead of waiting a day: a key is still there after 999 ms of a 1000 ms life and gone at 1000 ms. In production the client comes from authentication (Chapter {{n+5}}), and the store is a database table or Redis keys with an expiry time, which also clears old entries on its own.
