Chapter {{n}}

Designing REST APIs

In this chapter you will learn to

  • name resources and URLs so that an API can be guessed instead of memorised
  • build a versioned API on Fastify, with every input checked by a schema
  • page through lists with cursors that never repeat or skip a row
  • return every error in one standard format, Problem Details
  • make retries safe with idempotency keys, and stop lost updates with If-Match
  • limit request rates, and generate the API’s documentation from its code

An API is a product, and its users are developers. They judge it the way you judge a library: can I guess how it works, does it tell me clearly what I did wrong, and will it break my app next month? Chapter {{n-2}} taught you the protocol. This chapter is about the decisions on top of it, the ones that are cheap to get right at the start and very expensive to change once other teams depend on them. We rebuild Bit’s shop API properly, as version 1 of a public API.

The first public API I designed had /getProducts, /product_list and /Products/All, written by three people in three weeks. Every client needed our help to use it, and we could never remove anything. Consistency is not about taste: it is what lets strangers use your work without asking you.

{{n}}.1 Resources and URLs

REST organises an API around resources: the nouns of your domain, such as products and orders. URLs name the resources; methods say what to do with them. The rules that make an API guessable are few:

  • Nouns, plural, lower case: /products, /orders. The method is the verb: GET /products, not /getProducts.
  • One resource: the collection plus an id, /products/2.
  • Nesting for ownership, one level deep: /orders/7/items is fine; /customers/3/orders/7/items/2 is not. Once a resource has its own id, give it its own top-level URL.
  • Actions that are not create, read, update or delete become a sub-resource with POST: POST /orders/7/cancel. Do not hide them in a PATCH that sets status: cancelling has rules (restore the stock, refund the payment) that a generic update would skip.
  • A version in the path: /v1/.... We come back to versions in {{n}}.8.

Representations



The JSON an API sends is called a representation of the resource. Choose its conventions once, write them down, and never mix them:


    

  • One naming style. We use snake_case, like most public APIs; camelCase is just as good. Mixing them is not.
    • 

  • Times in ISO 8601, in UTC: 2026-11-01T09:00:00.000Z. Clients convert to the user’s time zone; the server never guesses it.
    • 

  • Money as an object: {"amount": 45000, "currency": "EGP"}, the amount in minor units. A bare number is ambiguous the day you sell in a second currency.
    • 

  • Lists in an object: {"data": [...], "next_cursor": ...}, never a bare array, so that page information can be added without breaking anyone.
    •

{{n}}.3 Lists: filtering, sorting, pages



A list endpoint needs three things: a way to filter, a way to sort, and pages, because no client wants ten thousand products at once. Everything a client may send is in the query schema:






Every value has limits: a page has between 1 and 50 items, prices are not negative, and only four sort orders exist. z.coerce.number() turns the text of the query string into a number. Anything else is refused with a list of every problem, before any code runs:






Watch out: never sort or filter by any field the client names
An API that sorts by whatever field arrives in ?sort= can be asked to sort by a field without an index, which makes a slow query that one attacker can repeat a thousand times a minute. It may also reveal fields that should stay private, through the order of results. List the allowed fields, as SORTS does, and add an index for each one when the data moves to a database.



Offset pages and cursor pages



The obvious way to page is an offset: ?page=2 means “skip the first 20”. It has two problems. A database must still walk past every skipped row, so page 5000 is slow. Worse, the pages drift when data changes between two requests. This small demo pages through a “newest first” list, three at a time, while a new product arrives between page 1 and page 2:









With an offset, product 4 appears on both pages, because everything moved down by one. (A product deleted in between would make one disappear instead.) A cursor says “continue after this row”, so new rows before it change nothing. This is also called keyset pagination, because it continues from the key of the last row. Our API builds its cursors like this:






The rows are ordered by the sort field and then by id, so that two products with the same price still have a fixed order: without that tiebreak, rows with equal values could move between pages. The cursor holds the last row’s sort value and id, encoded with base64url. Encoding is not secrecy, and the cursor can be decoded; the point is that clients treat it as an opaque token and send it back unchanged, so the server is free to change what is inside. Here is the client’s side:






The second request sent back the cursor from the first, and continued at product 4. With sort=-price and a price filter, the cursor carries the price as well, and the second page continues below 12,500. When next_cursor is null, the list is finished. Cursors cannot jump to page 37, but almost no user does that; they scroll, or press “load more”, which is exactly what cursors do well.

{{n}}.4 Errors: Problem Details



In Chapter {{n-2}} our errors had a shape we invented. Every API that invents its own shape forces every client to learn it. Problem Details (RFC 9457) is the standard shape for HTTP API errors, sent with the content type application/problem+json: a type URL that identifies the kind of problem and leads to its documentation, a short title, the status, a detail for this particular case, and the instance, the request that failed. Extra members are allowed, such as our errors list.



Every text a person reads lives in one file, so it can be reviewed and translated in one place:

{{n}}.5 Safe retries: idempotency keys



Chapter {{n-2}} warned that a retried POST can create an order twice. The standard answer, used by payment providers such as Stripe, is an idempotency key: the client creates a unique value (a UUID) for each intended operation and sends it in an Idempotency-Key header. If the same key arrives again, the server does not do the work again; it replays the answer it gave the first time.






The details matter more than the idea:


    

  • The server keeps a fingerprint of the body. The same key with a different body is a bug in the client, and gets a 422, never a silent replay of a different order.
    • 

  • The key is marked in progress before the work starts. A second request that arrives while the first is still running gets a 409 instead of starting the work twice.
    • 

  • If the work fails, the key is forgotten, so the client may try again with it.
    • 

  • The total is computed from the server’s prices. A client never tells the server what something costs.
    • 







The second request got the same order, with the same id and time, and a header that says it was replayed. The stock went down by 2, not by 4. Here the keys live in a Map; in production they are kept in the database, in the same transaction as the order (Chapter {{n+3}}), or in Redis (Chapter {{n+4}}), for about a day.

{{n}}.6 Lost updates: ETag and If-Match



Two administrators open product 2 at the same time. Sara changes the price to 65.00 and saves; a minute later Omar, whose screen still shows the old product, changes it to 70.00 and saves. Sara’s change is gone, and nobody was told. This is the lost update problem. HTTP solves it with the ETag you met in Chapter {{n-2}}: the product’s version is its ETag, and a change must send back the version it was based on in If-Match:









A change without If-Match is refused with 428 Precondition Required: requiring it is how the API makes sure no client forgets. The change based on version 1 succeeds and creates version 2. The second change, still based on version 1, gets 412 Precondition Failed, and the client knows to reload and show the user what changed. This is optimistic concurrency: nothing is locked while people look at a screen, and conflicts, which are rare, are detected when they happen. Chapter {{n+3}} does the same inside the database.



{{n}}.7 Rate limits



Every public API limits how fast one client may call it: to keep one buggy script from hurting everybody, and to make guessing passwords or scraping slow. The @fastify/rate-limit plugin counts requests per client address. Started with a limit of three a minute, the fourth request is refused:






The x-ratelimit-* headers tell well-behaved clients how much they have left on every answer, and retry-after tells them when to try again. A client that respects them never sees a 429. With several servers, the counts must be shared between them, which is another job for Redis (Chapter {{n+4}}).



{{n}}.8 Versions and change



Once other people use your API, every change is either additive or breaking. Adding an endpoint, an optional parameter or a new field to a response is additive: correct clients ignore what they do not know. Removing or renaming a field, changing its type or meaning, or adding a required parameter breaks clients. The rules:


    

  • Make every change additive if you possibly can. Most APIs live for years on version 1.
    • 

  • When a breaking change is unavoidable, publish /v2 next to /v1, and keep /v1 running for a stated period.
    • 

  • Announce the end in the answers themselves, with the Deprecation and Sunset headers, in the documentation, and by email to the clients you know. Watch your logs to see who still calls the old version before you turn it off.
    • 




{{n}}.9 Documentation from the code



Documentation written by hand drifts away from the code within weeks. Because every route here has a schema, the @fastify/swagger plugin generates an OpenAPI document from them: a standard, machine-readable description of every path, parameter, body and response. The API serves it at /openapi.json, and the routes listing in {{n}}.1 was read from it. From the same document, tools can render documentation pages, generate typed client libraries in many languages, and check in CI that a change does not remove anything clients depend on.



Professional habit: design the API before you build it
Write the request and response examples for a new endpoint first, in the pull request or in the OpenAPI document, and get a review from someone who will use the endpoint, such as a front-end or mobile developer. Changing an example takes minutes; changing a published API takes months of versions and deprecation emails.

Summary



    

  • Resources are plural nouns; methods are the verbs; special actions are sub-resources with POST. Nest one level at most.
    • 

  • Fix the representation rules once: one naming style, UTC times, money as amount and currency, lists in an object.
    • 

  • Schemas describe every input and output; the framework refuses bad input and types the good.
    • 

  • Cursors page without drift over a complete order (sort field plus id); allowed sort fields are listed.
    • 

  • Errors are Problem Details: type, title, status, detail, instance, from one factory and one handler.
    • 

  • Idempotency keys with fingerprints make retries safe; ETag and If-Match prevent lost updates.
    • 

  • Rate limits protect everybody; their headers let good clients avoid them.
    • 

  • Prefer additive changes; version and announce the rest. Generate OpenAPI documentation from the code.
    •

POST /orders/7/cancel: cancelling is an action with its own rules (stock, refunds, a check that the order can still be cancelled), and a dedicated endpoint can enforce them and be documented and permitted separately; a generic PATCH would let a client set any status. 2. Products with the same price would otherwise have no fixed order, so a row could move from one page to another between requests, and the cursor could not say exactly where to continue. 3. So that the server can change the cursor’s contents (another sort, a signature, an encryption) without breaking clients, and so that clients do not build cursors that skip the server’s rules.

Project {{n}}.2 · Medium


A client that retries correctly


Write a small TypeScript client for the orders endpoint that retries safely, with backoff, and test it against a server that fails on purpose.


You will practise: idempotency keys from the client’s side, timeouts, exponential backoff, and reading Retry-After.


    

  1. Write createOrder(items): it makes one UUID with crypto.randomUUID() and uses the same key for every attempt.
    2. 

  2. Retry on network errors, timeouts (use AbortSignal.timeout), 409 in-progress, 429 and 5xx; never on other 4xx.
    3. 

  3. Wait 200 ms, 400 ms, 800 ms between attempts, plus a random part (jitter), and use Retry-After when the server sends it. Give up after five attempts.
    4. 

  4. Add a test option to the server that drops the response of every second request after doing the work, and show with a test that the client still creates exactly one order.
    5. 



Hint: the jitter matters. Without it, a thousand clients that failed at the same moment retry at the same moment too, and knock the server over again.







Project {{n}}.3 · Challenge


Version 2, side by side


Introduce a breaking change as /v2, keep /v1 working from the same code, and announce its end.


You will practise: versioning, mapping representations, deprecation headers, and contract tests.


    

  1. In v2, prices become {"amount": "450.00", "currency": "EGP"} with a decimal string, and created_at is renamed created. Decide why each change is breaking.
    2. 

  2. Keep one internal model, and write one mapping function per version from the model to its representation.
    3. 

  3. Add Deprecation and Sunset headers to every v1 answer, with a date six months ahead, and a Link header to the migration guide.
    4. 

  4. Write tests that save today’s v1 responses as fixtures and fail if v1 ever changes, so that v2 work cannot break v1 by accident.
