Because they tell the client different things. 201 Created says “this request made a new order”; 200 OK with idempotent-replayed: true says “nothing new happened, this is the order your earlier request made”. A client normally treats both as success, but its logs, its metrics and any developer reading the traffic can see that a retry happened, and how often. Counting replays is also a good signal of network trouble between the app and the API.
  2. Because the price alone does not say where a page ended when several products share it. Say products 7 and 8 both cost 6000 and the page size is 1. Page 1 ends at product 7, and a cursor of only 6000 asks for price > 6000, which skips product 8. Asking for price >= 6000 instead would show product 7 again. With (6000, 7) the next page asks for (price, id) > (6000, 7), which is exactly product 8. The id makes the sort key unique, so every row has one place in the order.
  3. (a) Before sending: the transaction rolls back when the connection closes, the row lock is released, and the row is still unsent, so the next worker (or the same one after a restart) sends it. Nothing is lost and nothing is doubled. (b) After sending, before the commit: the email has gone, but the update to sent_at rolls back, so the row is sent again: a duplicate. Only (b) duplicates. The provider helps when it accepts an idempotency key: send the outbox row’s id with each email, and the provider recognises the second send of row 42 and drops it. Without such a key, a rare duplicate is the price of never losing an email.
  4. The second request makes a new order, and that is right. The 409 rolled back the whole transaction, including the INSERT that claimed k1, so no order with that key exists and the retry runs as if it were the first. The promise of an idempotency key is “the same key never makes two orders”, not “the same key always gives the same answer”: a request that failed and changed nothing may be retried, and the customer gets the order they wanted once the stock is back.
  5. Move the keys to their own table, CREATE TABLE idempotency_keys (user_id bigint NOT NULL, key text NOT NULL, request_hash text NOT NULL, order_id bigint NOT NULL REFERENCES orders (id), created_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (user_id, key)), and drop the key columns from orders. The order inserts its key row in the same transaction, with ON CONFLICT DO NOTHING as now. A scheduled job deletes old keys: DELETE FROM idempotency_keys WHERE created_at < now() - interval '24 hours', in batches with an index on created_at. The guarantee holds for any retry within 24 hours, because the row exists until then; tell clients (in the API documentation) that a key is only remembered for 24 hours, so they must not retry with an older one.
