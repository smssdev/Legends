1. After about 50 ms: the timer cannot run before the busy loop ends, and the loop then finds it overdue. Without the busy loop it runs after about 10 ms, never earlier, and often a millisecond or two later.
  2. Add HOST: z.string().min(1).default("127.0.0.1") to the schema and call server.listen(config.PORT, config.HOST, ...). 127.0.0.1 accepts connections from the same machine only. 0.0.0.0 means “every network interface”: you need it inside a Docker container or on a server that must be reached from outside, and it is exactly what you do not want on a laptop in a café.
  3. Promise.all rejects as soon as the first promise rejects, at about 200 ms, with that error. The stock request is not cancelled: it keeps running and finishes at about 300 ms, and its result is ignored. The program in the code repository (answers/all-fails.ts) prints “Promise.all rejected at 201 ms: price service down” and then “stock finished anyway at 301 ms”. To really stop the other calls, give them an AbortController’s signal and call abort() in the catch.
  4. Read Number(url.searchParams.get("rows") ?? 100000), answer 422 unless it is a whole number from 1 to 1,000,000, and pass it to orderRows. Memory stays flat because the generator makes one row at a time, and pipeline only asks for the next row when the response can take more: at no moment do all rows exist together. When the client disconnects, the response is destroyed, pipeline rejects, and it calls the generator’s return(), so the generator stops at its current yield (any finally block in it runs). The handler’s catch sees the error and, since the headers were already sent, destroys the response instead of writing a 500.
  5. The pool in answers/pool.ts keeps a list of idle workers and a queue of jobs. run puts a job in the queue and calls #next, which gives the first job to an idle worker; when the worker answers, it goes back to the idle list and #next runs again. A worker that crashes is replaced with a new one, because a crashed thread cannot be reused. The worker file listens with parentPort.on("message", ...) instead of reading workerData once. In the run in the code repository, 100 counts with a new thread each took about 6 seconds, and with a pool of four about 150 ms: starting a thread costs far more than these small counts.
