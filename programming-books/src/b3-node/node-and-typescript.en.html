Chapter {{n}}

Node.js and TypeScript on the Server

In this chapter you will learn to

  • set up a server project in TypeScript that Node runs directly, and that tsc checks
  • explain the event loop, and predict the order in which code runs
  • keep the event loop free, moving heavy CPU work to worker threads
  • wait for several things at once with promises, with failures and time limits
  • process big data with streams, in constant memory
  • load and check configuration, shut down gracefully, and test with Node’s own test runner

In Chapter {{n-1}} our server was one file. Real servers are projects: configuration that changes between your laptop and production, tests, code split into modules, and a process that must stay up for months. They also share one property that surprises developers who come from the browser or from PHP: a Node server runs all its JavaScript on a single thread, for every user at once. This chapter shows why that is fast, how one careless loop can freeze every user, and the tools that keep a Node server healthy.

My first Node server resized photos inside the request handler. It worked beautifully on my laptop. The day ten people uploaded at once, every page of the site stopped answering, including the ones that had nothing to do with photos. That was how I met the event loop.

{{n}}.1 What Node is

Node is three things put together. V8, the JavaScript engine from Chrome, runs your code. libuv, a library written in C, talks to the operating system: it opens files and network connections, and tells Node when something is ready. And a standard library (node:http, node:fs, node:stream, node:test and many more) wraps it all for JavaScript.

The important design choice is that your JavaScript runs on one thread, and I/O (input and output: the network, the disk, a database) never makes it wait. When a request handler asks the database for a list, Node hands the work to the operating system and moves on to the next request. When the list arrives, Node calls your code back. One process can serve thousands of connections at once this way, because most of a server’s time is spent waiting for I/O, and waiting costs Node nothing.

The cost of the design is just as important: while your JavaScript is computing, nothing else runs. We will see both sides for real in this chapter.

Node runs it, tsc checks it



Node runs a .ts file by type stripping: it removes the type annotations and runs what is left, without looking at them. That is fast, but it means Node never checks your types. Checking is the job of the TypeScript compiler, tsc, configured in tsconfig.json:






strict and noUncheckedIndexedAccess are the checks from Book 2. noEmit tells tsc to check only, because Node runs the source as it is. The other three options make the source safe for type stripping: imports name the real file (./config.ts, as Node needs), import type marks imports that disappear, and erasableSyntaxOnly forbids the few TypeScript features that are not just types. Instead of an enum, use an object with as const, or a union of strings such as "pending" | "paid": they are plain JavaScript plus types.



Professional habit: the checks run on every change
Because Node does not check types, a type error can reach production unless something stops it. Run npm run check and npm test in CI on every pull request, and make them required to merge. Locally, let your editor show tsc’s errors as you type. Fast running and strict checking are two separate jobs, done by two separate tools.



{{n}}.3 The event loop



The event loop is Node’s main loop. In each turn, it runs whatever is ready: timers whose time has come, I/O that has finished, callbacks scheduled with setImmediate. Between any two of these, it empties two smaller queues of microtasks: callbacks of promises, and callbacks given to process.nextTick. This program schedules one of each, and then keeps the thread busy:









Three rules explain the output:


    

  1. The code that is running always finishes first. Nothing interrupts it: “script ends” comes before every callback.
    2. 

  2. Microtasks run before the loop moves on. Both the promise callback and the nextTick callback run before the timer, even though the timer asked for 0 ms. (In an ES module, promise callbacks happen to run before nextTick ones; in an old CommonJS file it is the other way round. Code that depends on that order is fragile.)
    3. 

  3. A timer’s delay is a minimum, not a promise. The second timer asked for 10 ms and ran after 200, because the loop was busy and could not check its timers.
    4. 




The third rule is the one that matters on a server. Every request, every timer and every database answer waits for the same thread. If one piece of code keeps it for a second, every user waits a second.

{{n}}.4 Never block the loop



Here is a server with two routes. /primes counts the prime numbers up to a limit, which is pure computation; /hello answers at once:






We send a slow request and, a moment later, a quick one. curl’s -w prints how long each one took:






The quick request, which needs a fraction of a millisecond, waited more than a second, because the thread was counting primes for someone else. With a hundred users, each would wait behind every count in front of them. Typical culprits are image resizing, PDF generation, password hashing with a synchronous function, compressing big files, and JSON.parse on huge bodies.



The fix is to do heavy computation on another thread. Node’s worker threads run a separate JavaScript file with its own event loop, and exchange messages with the main thread:






The worker receives its input in workerData and posts its result back. In the app, a small function wraps it in a promise, so the handler simply awaits it:






The same two requests against the real server:






The quick request now answers in about a millisecond, before the count has finished, because the main thread was free. Starting a thread costs a few tens of milliseconds, which is nothing next to a one-second job but too much for many small ones. For those, keep a pool of threads started once and reused; you build one in Exercise 5, and the Piscina library is a well-tested one.



Tip: most libraries already do this
Many slow operations in Node’s standard library have an asynchronous version that runs on libuv’s own thread pool: crypto.scrypt instead of crypto.scryptSync, zlib.gzip instead of zlib.gzipSync, fs.promises.readFile instead of fs.readFileSync. On a server, any function whose name ends in Sync is a warning sign inside a request handler. At start-up, before the server listens, it is fine.



{{n}}.5 Waiting for several things at once



A product page might need the stock, the price and the reviews, each from a different service. This demo stands in for three network calls, of 300, 200 and 400 ms:









    

  • One after another, the waits add up: 300 + 200 + 400 = 900 ms. Writing await three times in a row is the most common accidental slowness in Node code.
    • 

  • Promise.all starts all three, then waits for the slowest: 400 ms. Use it when the calls do not depend on each other.
    • 

  • Promise.allSettled waits for all of them and reports each one as fulfilled or rejected. A page can still show the stock and the price when the reviews service is down. Promise.all would reject as a whole on the first failure.
    • 

  • AbortSignal.timeout(250) gives a call a time limit. Most modern APIs accept a signal, including fetch and Node’s timers, and give up when it fires. Every call to another service needs a limit; without one, a slow service makes your server slow too.
    • 




Watch out: “all at once” has limits
Promise.all over ten thousand items starts ten thousand database queries at the same moment, and the database falls over. For large lists, run a few at a time (in batches, or with a small helper such as p-limit). And remember that a rejected Promise.all does not stop the other promises: they keep running, and their results are simply ignored.

A stream delivers the data in pieces as it arrives, so the program only ever holds a small part of it. readline turns a file stream into lines, and for await reads them one by one:









The same total, with less than half the memory. More importantly, the streaming version uses the same memory for a file ten times bigger, while the first one would need ten times more and eventually crash. On a server that handles many requests at once, the difference is multiplied by the number of users.



Backpressure



Streams also work the other way. When you write faster than the destination can take (a slow disk, a slow client), data piles up in memory. A writable stream says so: write() returns false when its buffer is full. The program that made the CSV file waits for the drain event before writing more:






This is called backpressure: the slow side slows down the fast side, instead of letting memory fill up. You rarely handle it by hand, because pipeline does it for you. The shop’s export route makes its CSV rows with an async generator and pipes them into the response:






In the handler, await pipeline(Readable.from(orderRows(100_000)), res) sends the rows as the client reads them. If the client disconnects halfway, pipeline stops the generator and cleans up; with the older .pipe() method, that cleanup is your job, and it is often forgotten. {{n}}.7 Configuration



The port, the database address, the allowed origins and the API keys differ between your laptop, the test server and production. They must not be written in the code. The common rule is to read them from environment variables, which every hosting platform can set. But process.env holds only strings, any of which may be missing or mistyped. On your machine, the settings live in a .env file, which node --env-file=.env loads before your code runs:






Watch out: .env files hold secrets
Add .env to .gitignore on the first day, and commit a .env.example with the names and harmless values instead. A key pushed to a public repository is found by bots within minutes. Once it has been pushed, deleting it is not enough: change the key. In production, the platform’s secret settings fill the environment, and there is no .env file at all.



{{n}}.8 Errors and graceful shutdown



Servers stop all the time: for every deployment, when a machine is replaced, when the platform scales down. The platform sends the process a SIGTERM signal (Ctrl+C in a terminal sends SIGINT) and, after a grace period, kills it. A server that simply exits on the signal cuts off every request in progress: a payment half processed, an upload lost. A graceful shutdown stops accepting new connections, lets the running requests finish, and only then exits:






Here a long count is running when Ctrl+C arrives:









The server stopped listening at once, finished the count, answered 200, and then exited. The ten-second timer guarantees that a stuck request cannot keep the process alive forever, and .unref() stops the timer itself from keeping it alive.



The last handler is about a different kind of error. Errors you expect, such as a missing product or a timeout, are handled where they happen and become answers. An unhandled rejection means a promise failed and no code was waiting for the failure: a bug. After a bug, the process may be in a state nobody planned for, with half-updated data in memory. The safe reaction is to log it and exit, and let a supervisor (Docker, systemd or the hosting platform, Chapter {{n+14}}) start a fresh process. Never keep a damaged process running just to look available.

Summary



    

  • Node is V8, libuv and a standard library. Your JavaScript runs on one thread; I/O never makes it wait.
    • 

  • Node runs TypeScript by stripping types; tsc checks them. erasableSyntaxOnly keeps the source strippable: no enums.
    • 

  • The event loop runs current code to the end, then microtasks, then timers and I/O. Timer delays are minimums.
    • 

  • Never block the loop: CPU work goes to worker threads, slow APIs are used in their async versions.
    • 

  • Promise.all waits for independent calls at once, allSettled survives failures, and AbortSignal.timeout limits every call.
    • 

  • Streams process big data in constant memory; backpressure slows the fast side; pipeline handles both and cleans up.
    • 

  • Configuration comes from the environment, checked once with a schema; secrets never enter the repository.
    • 

  • A graceful shutdown closes, finishes, then exits. After an unhandled error, log and exit, and let a supervisor restart.
    • 

  • node:test runs tests with no extra tool; servers in tests listen on port 0.
    • 




Quick check answers: 1. Because a server mostly waits for I/O, and Node hands that waiting to the operating system and serves other connections meanwhile; the thread is only busy while JavaScript is actually computing. 2. tsc, through npm run check, in the editor while writing and in CI before the change is merged. 3. After the 300 ms of computation have finished: at about 300 ms, never at 100.
