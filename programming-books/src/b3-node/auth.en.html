Chapter {{n}}

Authentication and Authorization

In this chapter you will learn to

  • tell authentication (who are you?) from authorization (may you do this?)
  • store passwords so that a stolen database does not reveal them
  • register and sign users in, without telling attackers which emails exist
  • issue session tokens you can revoke, and understand when a JWT is the better choice
  • protect routes by role and by ownership
  • slow down password guessing, and test all of it automatically

Until now, anyone could call every route of the shop’s API. A real shop needs to know who is calling: a customer sees their own orders and no one else’s, and only staff may see the list of customers. Getting this right is not hard, but almost every mistake in it is a security incident, and the mistakes are invisible until someone exploits them. This chapter builds it step by step with Node’s own crypto module, PostgreSQL and Fastify, and runs every request against the real server.

Years ago a site I used was breached, and the attackers published its user table. My password was right there, in plain text, next to my email. It was the same password I used on two other sites. That afternoon I changed seven passwords, and I promised myself that no table I build would ever hold one.

{{n}}.1 Two questions

Every protected request answers two separate questions, in order:

  • Authentication: who is calling? The client proves an identity, with a password once and then with a token on every request. If it cannot, the answer is 401 Unauthorized (a confusing name: it means “not authenticated”).
  • Authorization: may this user do this? The identity is known; the rules decide. If they say no, the answer is 403 Forbidden, or 404 Not Found when even the existence of the thing is private.

Keeping them apart keeps the code clear: one function finds the user, and the rules about what each user may do live next to the routes they protect.

{{n}}.2 Storing passwords

A password must never be stored as it is, and never with an ordinary hash such as SHA-256 either. A fast hash is the problem: a graphics card computes billions of SHA-256 hashes a second, so an attacker with a stolen table tries every common password against every row in minutes. Password storage needs a hash that is slow on purpose and needs a lot of memory, so that each guess costs real time: scrypt, Argon2 or bcrypt. Node has scrypt built in:




    

  • The salt is 16 random bytes, different for every hash, stored next to it. Two users with the same password get different hashes, so an attacker must attack each row separately, and precomputed tables of hashes are useless.
    • 

  • The cost is stored inside the string. When computers get faster you raise COST; old hashes still verify with the cost they were made with, and can be upgraded when the user next signs in (exercise 3).
    • 

  • timingSafeEqual compares all 32 bytes every time. An ordinary comparison stops at the first different byte, and the time it takes can leak information.
    • 

  • normalize("NFKC") makes passwords typed on different keyboards compare equal when they look the same, which matters for Arabic and other non-Latin passwords.
    • 







The same password gave two different strings, both verify, and one hash took tens of milliseconds: nothing for a user signing in, a great deal for an attacker trying a billion guesses.



Watch out: never write your own crypto
This chapter uses scrypt, HMAC and random bytes from Node’s crypto module, all written and reviewed by specialists. Combining well-known pieces in the standard way is fine; inventing your own hashing scheme, your own encryption or your own random token generator is not. Math.random() is never acceptable for anything secret: it is predictable. Use randomBytes.



{{n}}.3 Registering and signing in



The users table follows Chapter {{n-3}}’s migrations. Emails are compared without their capitals, so the unique index is on lower(email), not on the column:






Registration validates the body, hashes the password and inserts the user. The unique index, not a check in code, decides whether the email is taken: ON CONFLICT DO NOTHING returns no row when it is, and two simultaneous registrations with the same email cannot both succeed (the lesson of Chapter {{n-2}}):









Signing in is where attackers probe. Two details stop the login route from telling them which emails have accounts:






    

  • The same answer for an unknown email and a wrong password: “email or password is wrong”, never “no such user”.
    • 

  • The same time. Without the DUMMY hash, an unknown email would answer at once and a known one after a slow hash, and the time alone would reveal which emails exist. Verifying against a dummy hash makes both cost one hash.
    • 







(Registration still reveals that an email is taken; that is usually accepted for usability. Sites that must hide it send an email in both cases instead of answering differently.)



{{n}}.4 Sessions and tokens



After a successful sign-in the server gives the client a session token: proof of identity for the next requests, so the password is sent once. Our tokens are 32 random bytes, and the database stores only their SHA-256 hash:






A fast hash is right here, unlike for passwords: the token is 32 random bytes, not a word a person chose, so there is nothing to guess, and the hash only ensures that someone who reads the sessions table cannot use what they read. On every request, a preHandler reads the Authorization header and finds the user:









Because sessions live in the database, signing out is a DELETE, and the token stops working at once. The database keeps only hashes, of passwords and of tokens:






What about JWTs?



A JSON Web Token takes the opposite approach: instead of a random key into a table, the token contains the data (the user id, the role, the expiry), signed with the server’s secret so that it cannot be changed. Here is one made by hand, to see what is inside:









Changing the role to admin broke the signature, so a JWT cannot be forged. But anyone can read it, and the server checks it without looking anything up, which is both its strength and its weakness: it cannot be revoked. A user who signs out, changes their password or loses their role keeps a valid token until it expires. JWTs fit messages between your own services and short-lived tokens (minutes); for users of your own apps, opaque tokens in a table, or in Redis from Chapter {{n-1}}, are simpler and safer. Never put a secret in a JWT payload.



Note: tokens in browsers
A mobile app keeps the token in the phone’s secure storage and sends it in the Authorization header, as curl does here. A website should not keep it in localStorage, where any injected script can read it. Instead the server sets it in a cookie with HttpOnly (scripts cannot read it), Secure (HTTPS only) and SameSite=Lax (not sent with most requests from other sites), and reads the cookie instead of the header. Cookies bring a risk of their own, cross-site request forgery, which Chapter {{n+1}} deals with.



{{n}}.5 Authorization: roles and ownership



Authentication found the user; now the routes decide what that user may do. Two kinds of rule cover most applications: a role (customer or admin) for whole areas, and ownership for single records:









    

  • addHook("onRequest", authenticate) protects every route of the plugin, including routes added to it later. A rule that each route must remember will one day be forgotten.
    • 

  • The list of orders is filtered in the query: WHERE user_id = …. Fetching everything and filtering in code risks returning too much the day someone changes it.
    • 

  • Omar asking for Sara’s order gets 404, exactly as for an order that does not exist. A 403 would confirm that order 1 exists, and ids that count up would let him learn how many orders the shop has.
    • 

  • The admin list returns 403: Omar knows the route exists, and he is told he lacks the role.
    •

{{n}}.6 Slowing down guessing



A slow hash protects a stolen table; the running server needs protection too, against a script that tries passwords one after another. The login route has its own rate limit (from Chapter {{n-5}}’s plugin), keyed on the client’s address and the email, so one attacker cannot try thousands of passwords on one account:






The sixth attempt was refused before its password was even checked. In production the counters belong in Redis, shared by every server. Locking the account after a few failures is tempting but lets anyone lock out any user by typing wrong passwords for them; rate limits slow the attacker without punishing the owner. Adding a second factor (a code from an app) is the strongest protection of all.



{{n}}.7 Testing it



Security rules are exactly the kind of code that breaks silently, so each rule gets a test. Fastify’s app.inject sends requests to the application without a network, so the tests run fast:









Note what is tested: not only that the right user gets in, but that the wrong ones are kept out. A test suite that checks only the happy path would pass for an API with no security at all.



Professional habit: test the “no” for every route
For every protected route, write at least two tests: one without a token (401) and one as a user who must not have access (403 or 404). Add them in the same pull request as the route. The day someone removes a hook or changes a query, these tests fail, which is far cheaper than finding out from a customer who saw someone else’s order.

Summary



    

  • Authentication finds out who is calling (401 if unknown); authorization decides what they may do (403, or 404 to hide existence).
    • 

  • Passwords are stored with a slow, salted hash (scrypt here), compared in constant time.
    • 

  • Sign-in gives the same answer and the same time for a wrong email and a wrong password.
    • 

  • Session tokens are random bytes, stored only as a hash, and revoked by deleting the row.
    • 

  • A JWT carries signed data that anyone can read and nobody can revoke: good between services and for minutes, not for user sessions.
    • 

  • Protect whole plugins with a hook, filter records by owner in the query, rate-limit login, and test every “no”.
    • 




Quick check answers: 1. A session token is 32 random bytes: there are far too many possibilities to try, so the hash only needs to stop someone who reads the table from using the values directly, and a fast hash does that. A password is chosen by a person from a small set of likely words, so an attacker can try the likely ones quickly unless each try is made deliberately slow. 2. 403 Forbidden: the server knows exactly who is calling (the token is valid), so the problem is not authentication; the user lacks the admin role. 3. So that the response takes the same time whether or not the email exists; otherwise an unknown email would be answered much faster, and the time would reveal which emails have accounts.

Change your password

You will practise: verifying the current password, hashing, and revoking sessions.

    2. 

  2. Refuse with 401 if the current password is wrong, and with 422 if the new one equals the old one.
    3. 

  3. After the change, delete every other session of the user, keeping the one making the request.
    4. 

  4. Test the three cases, and that a second device’s token stops working.
    5. 



Hint: asking for the current password stops someone who finds an unlocked, signed-in laptop from taking over the account.

Project {{n}}.3 · Challenge


Forgotten password


Build a password reset that cannot be used to take over someone else’s account.


You will practise: single-use tokens, expiry, not leaking account existence, and side effects through an outbox.


    

  1. POST /auth/forgot takes an email and always answers 202, whether or not the account exists.
    2. 

  2. For an existing account, store the hash of a random token with a 30-minute expiry, and put the reset link in the outbox from Chapter {{n-2}} instead of sending it inside the request.
    3. 

  3. POST /auth/reset takes the token and a new password, works once, and deletes all the user’s sessions.
    4. 

  4. Test an expired token, a reused token, and that the answer for an unknown email is identical.
    5. 



Hint: the reset token is a password for 30 minutes. Treat it exactly like a session token: random, hashed in the database, and deleted when used.
