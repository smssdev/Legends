Chapter {{n}}

Architecture: Keeping Code Easy to Change

In this chapter you will learn to

  • recognise the signs of code that is getting hard to change
  • separate business rules from HTTP, databases and frameworks
  • describe what a use case needs as ports, and plug adapters into them
  • wire everything in one composition root, without a framework for dependency injection
  • organise code by feature, and enforce the boundaries with a test
  • know when a monolith is the right answer, and when to split

Every chapter so far added something the shop needed: a route, a query, a lock, a job, a metric. Each was small. Together they make a codebase where one route handler validates input, reads three tables, applies pricing rules, sends an email and formats the response, and the pricing rule appears again, slightly different, in another route. Such code works; it is just harder to change every month. Architecture is the set of decisions about where each kind of code lives, so that the shop’s rules can be understood, tested and changed without touching everything else. This chapter rebuilds the order feature with clear layers, small enough to read whole.

The most expensive bug I have seen was a discount rule copied into four route handlers. Marketing changed the rule; we updated three of them. For two weeks, orders through the mobile app got a discount that the website refused. No single line was wrong. The rule simply had no home.

{{n}}.1 Signs that structure is needed

  • Fat route handlers. A handler that parses, decides, queries, sends and formats does five jobs; changing one risks the others.
  • Rules in several places. The same check (“at most 10 of one product”) written in two routes, or once in a route and once in a job.
  • Tests that need everything. To test a pricing rule you must start a server, fill a database and fake an email service.
  • Afraid to change the infrastructure. Replacing the mail provider, or moving one table, means editing business code everywhere.

The cure is the same idea at several sizes: separate what the business decides from how it is delivered and stored. The decisions, the domain, change when the business changes; HTTP, PostgreSQL and the email provider change for technical reasons. Keeping them apart lets each change without the other.

Adapters connect the ports to real technology. This design is often called ports and adapters, or hexagonal architecture. The store adapter implements OrderStore with Kysely and PostgreSQL, including the transaction and the atomic stock update of Chapter {{n-9}}:






The transaction belongs here, in the adapter: “take the stock and save the order, all or nothing” is the port’s promise, and how a database keeps that promise is the adapter’s business. The HTTP adapter works the other way round, translating a request into a call of the use case, and the use case’s result or error into a response:






Deciding that “out of stock” means 409 is an HTTP concern, so it lives in the HTTP adapter. A command-line tool or a queue worker could call the same use case and translate the same errors differently.

{{n}}.5 Testing by layer



The reward for this structure shows in the tests. The use case can be tested with in-memory fakes for its ports, without a database, a server or a mail provider:






Each test sets up exactly the situation it needs: a store that succeeds, one that reports too little stock, one that must not be called at all. The adapter is tested against a real database, as in Chapter {{n-3}}, and only for what it adds: SQL, transactions and the mapping of rows.



Boundaries that only exist in people’s heads erode under deadlines. An architecture test makes them part of the build:









When someone, in a hurry, imports the database into the domain, the build says so:






This handmade check covers one folder; tools such as dependency-cruiser and ESLint’s import rules do the same for a whole codebase.



Watch out: architecture is a cost too
Every port and adapter is a file to read and an indirection to follow. For a route that reads one row and returns it, a use case and a repository are ceremony; keep such routes simple. Introduce layers where they pay: where business rules live, where several entry points share behaviour, where tests are slow because everything is tangled. The goal is code that is easy to change, not code that looks like a diagram.



{{n}}.6 Modules, monoliths and services



    

  • Organise by feature, not by kind. orders/, catalog/, accounts/, each with its domain, use cases and adapters, rather than controllers/, services/, repositories/ holding a bit of everything. A change to ordering then touches one folder.
    • 

  • Modules talk through their public functions. orders may call catalog’s exported use cases, but must not read catalog’s tables or import its internals. The same architecture test can enforce it.
    • 

  • A modular monolith first. One deployable application, well divided into modules, is the right shape for almost every team: one build, one database, transactions that span modules, and simple debugging.
    • 

  • Services when there is a reason. Splitting into separate services pays off when parts must scale very differently, be deployed by different teams independently, or be isolated for safety. The cost is real: network calls that fail, data spread across databases without shared transactions, and the tracing of Chapter {{n-2}} becoming a necessity. Clear modules make a later split easy; a tangle split into services is a distributed tangle.
    • 




Professional habit: write decisions down
When you make a structural decision (“orders do not read catalog tables”, “we use a modular monolith”), write a short architecture decision record: the context, the decision, the alternatives and the consequences, one page in docs/decisions/. A year later, the next developer, often yourself, will know why, and can change the decision on purpose instead of by accident.

Summary



    

  • Architecture decides where each kind of code lives, so rules can change without touching delivery and storage.
    • 

  • The domain holds rules and words in plain code, importing nothing technical; errors speak the business’s language.
    • 

  • Use cases orchestrate a business action through ports; adapters implement the ports with real technology.
    • 

  • A single composition root chooses and wires the concrete pieces; dependency injection is a function argument.
    • 

  • Use cases are tested with fakes in milliseconds; adapters against real infrastructure; boundaries with an architecture test.
    • 

  • Organise by feature; prefer a modular monolith; split into services only for a concrete reason.
    •
