Chapter {{n}}

Security: Attacks and Defences

In this chapter you will learn to

  • think like an attacker, using the OWASP Top 10 as a map
  • see SQL injection steal password hashes, and make it impossible with parameters
  • stop clients from writing fields they must not touch
  • keep user input out of file paths and other dangerous places
  • protect browser users with security headers, CORS and safe cookies
  • handle limits, secrets, configuration and dependencies like a professional

Every API on the internet is probed by scripts within hours of going online. Most of what they try is old and well known, and most successful attacks still use the same few mistakes: input treated as code, missing checks, secrets in the wrong place. This chapter commits those mistakes on purpose. Each attack gets two routes side by side, the obvious version under /unsafe and the safe one, and every attack is run for real with curl. Seeing your own server hand over its password hashes is the fastest way to never write that code again.

The first time I ran a security scanner against an API I had built, it found a search box that accepted SQL. I had used string templates because they were “just for a search”. Within a minute, the scanner had listed every table in my database. Nothing was stolen, because it was a test server. It was the most useful minute of my career.

{{n}}.1 Thinking like an attacker

An attacker reads your API differently from a user: every input is a chance to make the server do something it was not meant to do. The OWASP Top 10, a list kept by the Open Worldwide Application Security Project from data on real breaches, names the most common ways this succeeds. Two principles run through all of it. Never trust input: anything from the client (body, query, headers, cookies, file names) may be written by an attacker. And defence in depth: each layer assumes the one before it might fail.

{{n}}.2 Injection

The search below builds its SQL with a template string. For an ordinary search it works perfectly, which is exactly why this bug survives code review:







The attacker’s input closed the quote, added a UNION that reads the users table, and commented out the rest with --. The database cannot tell which part of the text came from the programmer and which from the attacker, so it ran all of it, and the response contains every email and password hash. With a little more work the same hole reads any table, changes data, or worse.



The safe route sends the same input as a parameter: the SQL text, with $1, and the value travel to PostgreSQL separately, so the value can never become code. It simply searched for a product with that strange name, and found none. Kysely and every serious query builder or ORM do this for every value, which is one more reason to use them. The danger remains wherever text is pasted into SQL:


    

  • Raw SQL helpers (sql.raw in Kysely, query() with a template): use their parameter form, never string building.
    • 

  • Identifiers such as a column to sort by cannot be parameters. Check them against a fixed list: sort must be one of "name" or "price", as Chapter {{n-6}}’s schemas did.
    • 

  • The same bug exists outside SQL: shell commands built from input (use execFile with an array of arguments, not exec with a string), NoSQL filters built from JSON the client sent, and HTML built from input (section {{n}}.5).
    • 




{{n}}.3 Over-posting



A profile update that writes whatever fields arrive is convenient: add a column, and the route supports it at once. It also supports columns nobody meant to expose:









Omar sent one extra field and became an admin. This is over-posting (or mass assignment), a form of broken access control. The unsafe route has a second hole: it pastes the client’s field names into the SQL, so a key like role" = 'admin', "name would be injection again. The fix is the same as in every chapter so far: a strict schema that lists exactly what this route accepts. z.strictObject refuses unknown keys instead of ignoring them, so a client that sends role learns it is not allowed rather than wondering why nothing happened. Changing a role is a different route, for admins only.



{{n}}.4 Paths and other dangerous places



Serving files from a folder by name looks harmless. But a name is input, and .. means “the folder above”:









This is path traversal, and here it handed over the .env file with the database password. The safe route resolves the full path and checks that it is still inside the public folder before reading. Even better is not to use the client’s text as a path at all: store files under random names, keep the original name in the database, and look up by id.



The same idea applies to every place where input reaches something powerful:


    

  • URLs the server fetches (“import a product image from this address”). An attacker gives http://localhost:5432 or the cloud provider’s internal metadata address, and your server, inside your network, fetches it for them. This is server-side request forgery (SSRF), exercise 5.
    • 

  • Redirects (?next=… after sign-in): only allow paths on your own site, or an attacker sends users to a fake copy of it.
    • 

  • Regular expressions built from input, or slow ones run on long input, can freeze the event loop for seconds.
    • 




Watch out: validation is not escaping
Validating input (“the name is 1 to 100 characters”) and making it safe for a destination (SQL, a path, HTML, a shell) are different jobs. A perfectly valid product name can contain a quote, .. or <script>. Validate at the edge, and make values safe where they are used, with the tool made for that destination: parameters, path checks, the template’s escaping.



{{n}}.5 Protecting browser users



An API is often called from a website, and the browser adds attacks of its own. Three are worth knowing by name:


    

  • Cross-site scripting (XSS): an attacker gets their script into a page other people see, for example as a product review, and it runs with the visitor’s session. An API protects itself by returning JSON with the right Content-Type, never HTML built from input; the frontend protects itself by escaping, which Vue and React do by default everywhere except v-html and dangerouslySetInnerHTML.
    • 

  • Clickjacking: your page is loaded invisibly inside another site, and the user is tricked into clicking your buttons.
    • 

  • Cross-site request forgery (CSRF): another site makes the browser send a request to yours, and the browser attaches your cookies. Cookies with SameSite=Lax (or Strict) are not sent with such requests; tokens in the Authorization header, as in Chapter {{n-1}}, are never sent automatically at all.
    • 




Browsers can refuse much of this if the server asks them to, with security headers. The @fastify/helmet plugin sets a sensible set on every response:









    

  • Content-Security-Policy lists where scripts, styles and images may come from; an injected script from elsewhere, or inline, is refused. It is the strongest defence against XSS in pages.
    • 

  • Strict-Transport-Security tells the browser to use only HTTPS for this site for a year, so nobody can downgrade a visit to plain HTTP.
    • 

  • X-Frame-Options and frame-ancestors stop other sites from framing yours; X-Content-Type-Options: nosniff stops the browser from guessing that a text file is a script.
    • 




CORS (cross-origin resource sharing) is the other half. By default a script on evil.example may send a request to your API but may not read the answer. CORS headers relax that for the origins you name, and only for them:






The shop’s website got Access-Control-Allow-Origin; the other website did not, so a browser will hide the response from its script. Note what CORS is not: it does not stop curl, scripts or servers, which ignore it, and it does not stop the request from reaching your server. It protects users’ browsers, not your API; authentication and authorization still do that. Never answer every origin with * on an API that uses cookies.

{{n}}.6 Limits



An attacker does not need to break in to hurt you; making the server too busy for real users is enough. Every input needs a size:






The body limit refused 200 KB before parsing it. The same thinking applies everywhere: a maximum length on every string in every schema (the search accepts 100 characters), a maximum page size on every list, a rate limit on expensive routes (Chapter {{n-6}}), timeouts on calls to other services, and a limit on upload sizes. Errors must not help the attacker either: the error handler logs the details and sends the client only a title and a status, never a stack trace or a SQL message.



{{n}}.7 Secrets and configuration



The .env file that path traversal leaked holds the most valuable things the application has: database passwords, API keys, signing secrets. Rules for them:


    

  • Never in the repository. .env is in .gitignore from the first commit; a file .env.example with every name and no real value documents what is needed. A secret pushed once is in the history forever: change it, do not just delete the file.
    • 

  • Different in every environment, set by the platform (Chapter {{n+7}}’s containers receive them as environment variables) or by a secret manager, and changed when someone leaves the team.
    • 

  • Never logged. Log requests without their Authorization header and bodies without passwords.
    • 

  • Checked at start-up. A server that starts with a wrong setting fails later, at the worst moment and with a confusing error:
    • 










The rest of the code imports config instead of reading process.env, so every setting has a type, a check and one place where it is documented.



{{n}}.8 Dependencies



The shop’s code is a few hundred lines; the packages in node_modules are hundreds of thousands. Most attacks on a modern application could arrive through them: a known vulnerability in an old version, or a malicious package, a typo away from a popular one (expresss), or an honest package whose maintainer’s account was stolen. Habits that keep the risk small:






    

  • npm audit checks every installed version against a database of known vulnerabilities; run it in CI, and fail the build on high and critical findings.
    • 

  • Commit the lockfile and install with npm ci, so every machine gets exactly the versions you tested.
    • 

  • Let a bot (Dependabot, Renovate) open pull requests for updates, so they arrive small and often, with tests, instead of once a year in a panic.
    • 

  • Before adding a package, look at who maintains it, how many people use it, and whether a few lines of your own would do. Every dependency is code you run with your server’s full permissions.
    • 




Professional habit: a security checklist in every review
Keep a short checklist next to your pull request template: Is every input validated with a size? Does any input reach SQL, a path, a URL, a shell or HTML? Is every new route behind authentication and authorization, with a test for the “no”? Are there new secrets, and are they outside the code? Are new dependencies needed and maintained? Thirty seconds per review prevents most of this chapter.

Summary



    

  • Never trust input, and defend in depth; the OWASP Top 10 is the map of what goes wrong most.
    • 

  • Injection happens when input becomes code: SQL takes parameters, identifiers take an allowlist.
    • 

  • Strict schemas stop over-posting; checked paths stop traversal; allowlists stop SSRF and open redirects.
    • 

  • Browsers are protected by security headers (CSP, HSTS, framing), CORS for named origins, and SameSite cookies.
    • 

  • Every input has a size, and errors reveal nothing.
    • 

  • Secrets live outside the code and the logs; configuration is checked at start-up; dependencies are audited and updated often.
    • 




Quick check answers: 1. With a parameter, the SQL text and the value are sent separately, so the database never parses the value as SQL, whatever characters it contains. Escaping by hand tries to make the value harmless inside the text, and must anticipate every special character, encoding and database quirk; missing one is enough. 2. It would accept the body and silently drop role, so Omar would not become an admin, but he would also not be told that the field is not allowed, and a later change to the code might start using it. strictObject refuses the request with 422. 3. CORS is not meant to stop requests; it stops a browser from letting a script on another site read the response. The server still checks who is calling and what they may do; and the request here changed nothing.
