Capstone: A Production API

In this chapter you will

  • turn a short brief into the endpoints, tables and quality goals of a real API
  • build accounts, products and orders in one codebase, each with the techniques of its chapter
  • make an order happen exactly once, even when the client sends it twice
  • send the order’s email from an outbox, never from inside the transaction
  • prove it with tests against a real database, then run the whole system in containers
  • check the result against a production checklist, and know what is still missing

Each chapter of this book solved one problem on a small example: a route, a transaction, a lock, a token, a job, a metric. A real service needs all of them at once, and the hard part is not any single technique but how they fit together. In this last chapter we build Bit’s shop API from an empty folder to a system of four containers: about 600 lines of TypeScript, each line run, each test passed, and each answer below printed by the real server.

Every section says which chapter a decision comes from. When something feels new, that is your cue to go back and read that chapter again: you will understand it better now that you see where it fits.

{{n}}.1 The brief

The shop owner writes: “Customers should create an account, browse the products, and order. An order must never be charged twice, and they should get an email when it is placed. It has to stay up when we are busy.” As in every real project, the first job is to turn that into something testable:

As a customer, I want to…Done when…
create an account and sign inPOST /auth/register and POST /auth/login return a user and a token; a stolen database opens no account
browse the products, cheapest firstGET /products returns pages with a cursor; no product is skipped or repeated, however large the table
place an orderPOST /orders takes the stock and saves the order together, or does neither; the same request sent twice makes one order
get an email when I orderExactly one email per order, even if the email service or the worker is down for a while

And the qualities that every endpoint must also meet:

  • Safe: passwords hashed slowly, tokens stored only as hashes, login attempts limited (Chapters {{n-9}} and {{n-8}}).
  • Consistent: stock never below zero, money in integers, no half-saved order (Chapters {{n-13}} and {{n-11}}).
  • Clear: every error in the same Problem Details form, every input validated (Chapter {{n-14}}).
  • Observable: structured logs, metrics and health checks from the first day (Chapter {{n-4}}).
  • Tested and shippable: tests against a real database, and one command to run everything (Chapters {{n-5}} and {{n-1}}).

{{n}}.5 Products, page by page



The product list uses keyset pagination from Chapter {{n-14}}: the cursor is the last row’s price and id, and the next page starts after that pair. With the index (price, id) PostgreSQL jumps straight to the right place, so page 1000 costs what page 1 costs (Chapter {{n-3}}). The cursor is opaque to clients, and a cursor that does not decode is a 422, not a 500:






The id in the cursor is not decoration: two products may share a price, and without a second, unique key a page boundary between them would skip one or show it twice.



{{n}}.6 Orders that happen once



The order is the heart of the shop, and the place where most of the book meets. Phones lose their connection mid-request; the app retries; the customer taps twice. If each request made an order, the customer would pay twice. The client therefore sends an Idempotency-Key header, a value it chooses once per order and repeats on every retry. The whole order is one transaction (Chapter {{n-11}}), and its first statement claims the key:






The unique constraint does the hard work. If two copies of the same request arrive together, the second INSERT waits for the first transaction, then finds the key taken and returns that order. No lock in the code, no race: the database already guarantees it. If the key comes back with a different body, the client has a bug, and saying so is better than guessing. (The refine on the body refuses the same product twice in one order, which the table’s primary key would refuse less politely, with a 500.)



Then each line takes its stock with the conditional update of Chapter {{n-11}}. If any line is short, the error rolls the whole transaction back: the order row, the lines already taken and the claimed key all disappear, so the client may fix the order and retry with the same key:






Look at what the order does not do: it does not send the email. That one missing line is the difference between a shop that sometimes emails customers about orders that do not exist, and one that never does.



Quick check
  1. Why is the key claimed with INSERT … ON CONFLICT DO NOTHING rather than by first checking whether it exists?
  2. An order has two lines, and the second is out of stock. What is left in the database afterwards?
  3. Why does the login limit keep its counts in Redis instead of memory?



{{n}}.7 The outbox and the worker



Sending the email inside the transaction is wrong twice: the transaction may still roll back after the email has gone, and a slow email service would hold the order’s locks. Sending it after the commit is better, but if the process dies between the commit and the send, the email is lost. The outbox removes both problems: the order writes a row into the outbox table in the same transaction, so the message exists if and only if the order does. A separate worker sends what the outbox holds:






FOR UPDATE SKIP LOCKED lets you run several workers: each takes rows that no other worker holds. And the row is marked sent in the same transaction that sent it, so a worker that crashes halfway releases its rows to the next one. That makes delivery at least once: in a rare crash after sending but before the commit, the email goes twice. A real email provider accepts an idempotency key too, and the outbox row’s id is the natural one to give it. The queues of Chapter {{n-7}} work the same way; here PostgreSQL is the queue, which is enough for a few thousand messages an hour and needs nothing else to run.

{{n}}.9 Tests against a real database



The tests use app.inject from Chapter {{n-5}}: real requests through the real routes, without opening a port. They run against PostgreSQL and Redis, on a separate database named in .env.test, and each test rebuilds the schema from the same schema.sql that production uses:






Each test states one promise from the brief. The most important is the first, which sends the same order twice and checks that there is one order, one stock deduction and one outbox row:









Watch out: tests that pass against the wrong database
Rebuilding the schema in every test is fast and makes tests independent, but it drops every table. That is why the tests read their own .env.test, pointing at shop_test. Never let tests fall back to the development settings, and never give a test runner credentials that reach production: one wrong environment variable must not be able to empty a real database.

Professional habit: a production checklist
Before a service takes real traffic, walk a short written list with the team: settings checked at start-up and secrets outside the image; migrations run as a separate step, never by the app on start; health and readiness probes wired to the platform; logs collected and an alert on the error rate and the latency; backups taken and a restore tried; rate limits on everything that costs money or guesses secrets; and a rollback that has been practised. The list is boring on purpose: incidents rarely come from clever bugs, mostly from a forgotten line on a list like this.



{{n}}.12 What you built



In about 600 lines: accounts with properly hashed passwords and revocable tokens; product pages that stay fast at any size; orders that are atomic, idempotent and never oversell; emails that are sent if and only if the order exists; Problem Details for every error; logs, metrics and two kinds of health check; tests that prove each promise against a real database; and one image, run by Compose, with its database, Redis and worker.



What a production version would add, each from a chapter you have read: migrations with a tool instead of one schema.sql (Chapter {{n-12}}); secrets from the platform, not from compose.yaml (Chapter {{n-1}}); HTTPS and security headers in front (Chapter {{n-8}}); tracing across the worker (Chapter {{n-4}}); and a CI pipeline that runs the tests, builds the image and deploys it. None of them changes the code you wrote; each one sits around it. That is the sign of a structure that is ready to grow.

Summary



    

  • Turn a brief into user stories with a test for “done”, and write the quality goals before the code.
    • 

  • Let the database guarantee what must always be true: unique keys, stock never below zero, one order per idempotency key.
    • 

  • Make retries safe with an Idempotency-Key: claim it in the order’s transaction, replay the same answer, refuse a changed body.
    • 

  • Never do side effects inside a transaction: write an outbox row, and let a worker with SKIP LOCKED send it.
    • 

  • Keep shared state, such as rate-limit counts, outside the process, so any number of copies behaves as one.
    • 

  • Give every error one Problem Details shape, and every service logs, metrics, health and readiness.
    • 

  • Prove each promise with tests against a real database, and ship one image for the app and its worker.
    • 




Quick check answers: 1. Because checking first leaves a gap: two copies of the same request can both find no order with that key, and both create one. The insert claims the key and checks it in one step, and the unique constraint makes the second insert wait for the first transaction, then do nothing. 2. Nothing from this order: the error rolls back the transaction, so the order row, its first line, the stock taken for it and the claimed key are all undone, and no outbox row exists. The client may correct the order and send it again, even with the same key. 3. Because memory belongs to one process: with three copies of the app, an attacker gets three times the attempts, and every restart or deployment resets the count. Redis gives all copies one shared count that survives restarts.




Practice projects



These projects grow the API the way a real one grows. For each one, write the user story and its test first, put the rule where the database can guarantee it when possible, and run the tests and the whole system in Compose before calling it done.

Project {{n}}.2 · Medium


Cancel an order


Add POST /orders/:id/cancel: within 30 minutes of placing it, a customer may cancel, and the stock comes back.


You will practise: conditional updates, transactions, the outbox, and testing rules that depend on time.


    

  1. Add a status column (placed, cancelled) with a check constraint.
    2. 

  2. In one transaction: set the status to cancelled only if it is placed, belongs to the user and is recent enough; then return each line’s quantity to the stock; then write an order.cancelled outbox row.
    3. 

  3. Cancelling twice must be harmless: the second call changes nothing and says so.
    4. 

  4. Teach the worker to send a different email for order.cancelled.
    5. 

  5. Test the 30-minute rule by inserting an order with an older created_at, not by waiting.
    6. 



Hint: put the whole rule in the WHERE of the update and check how many rows changed; then two cancels at once cannot both return the stock.







Project {{n}}.3 · Challenge


Survive a busy day


Show, with numbers, that the API keeps its promises under load and when parts of it fail.


You will practise: load testing, concurrency, failure testing, and reading metrics.


    

  1. With autocannon (Chapter {{n-3}}), send 2000 orders for a product with a stock of 100, from many connections, each with its own key. Check that exactly 100 orders exist and the stock is 0.
    2. 

  2. Send 50 copies of one order with the same key at once, and check there is exactly one order.
    3. 

  3. Run three workers (docker compose up --scale worker=3) and check that every outbox row was sent exactly once.
    4. 

  4. Stop Redis while the app runs. What do /ready, /health and a login answer? Decide what they should answer, and make it so.
    5. 

  5. Write what you measured: requests per second, the slowest 1%, and anything that surprised you.
    6. 



Hint: for step 4, a limit that cannot be counted must still fail safely. Decide whether a login without Redis is refused (safer) or allowed (friendlier), and write the reason in a decision record.






Exercises



    

  1. Easy In the journey, the second order request answered 200 with the header idempotent-replayed: true, and the first answered 201. Why give them different status codes, when the body is the same?
    2. 

  2. Easy Why does the product cursor contain the id as well as the price? Give an example with two products where a cursor without the id goes wrong.
    3. 

  3. Medium The worker marks a row as sent in the same transaction in which it sends the email. Describe what happens if the worker crashes (a) before sending, (b) after sending but before the commit. Which of the two can cause a duplicate, and how can the email provider help?
    4. 

  4. Medium A customer sends an order with key k1; the product is out of stock and the answer is 409. Ten minutes later the stock is refilled, and the client retries with k1. What happens, and why is that the right behaviour?
    5. 

  5. Challenge Idempotency keys stay in the orders table forever. Propose how to let them expire after 24 hours without breaking the guarantee for retries within that time, and write the change to the schema and the query.
    6.
