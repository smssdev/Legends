Chapter {{n}}

Performance

In this chapter you will learn to

  • measure performance under load instead of guessing
  • read percentiles and throughput, and know which matters when
  • find the bottleneck, which is usually the database, and fix it with the right index
  • understand the concurrency model of Node’s event loopPHP’s worker processes, and its limits
  • choose between faster code, caching, background work and more servers

“Make it fast” is not a task until it has a number: how many requests a second, how slow the slowest ones may be, measured how. This chapter follows the order that works in practice. First measure, under realistic load. Then find the one thing that limits the system, the bottleneck. Fix that, and measure again. Almost every time, the bottleneck is not where intuition points, and the fix is smaller than feared. Here a single line of SQL makes the shop’s product query almost a hundred times faster.

I once spent a week rewriting a JSON serialiser to make an API faster. It became 30% quicker at serialising, and the API became 1% faster, because 95% of each request was spent waiting for one query without an index. The index took a minute to add. I have measured before optimising ever since.

{{n}}.1 Measuring

Performance has two numbers that matter, and they are different:

  • Latency: how long one request takes, as seen by the client. Report it as percentiles (Chapter {{n-1}}): the median (p50) is a typical request, the p99 is the slowest one in a hundred, which on a busy site is someone every second.
  • Throughput: how many requests per second the system completes. It matters for capacity: how many users one server can carry.

A load test measures both by sending many requests at once. autocannon, a load-testing tool written in Node, opens a number of connections and keeps them busy for a few seconds. The shop has 500,000 products in 2,000 categories:

Watch out: measure like production
A load test on a laptop with ten rows tells you nothing. Use production-like data volumes (the bottleneck here appears only because the table is big), the same database, a server configured as in production (no debug loggingOPcache on, debug off, configuration cached), and a load generator on a different machine when the numbers matter. Warm up first, run several times, and change one thing at a time.



{{n}}.2 Finding the bottleneck



The observability of Chapter {{n-1}} usually points straight at it: the histogram of the listing route is slow, and its trace shows nearly all the time inside one SQL query. PostgreSQL can explain how it runs a query, and with ANALYZE it runs the query and reports the real times:









Read a plan from the inside out. The innermost step is a Parallel Seq Scan: three processes read the whole table, checking every row against the category, and “Rows Removed by Filter” says that 166,500 rows per process were read and thrown away to find 250. Then they sort and merge the matches, and keep 20. About 20 milliseconds per query, and with twenty clients the database is busy reading the same table over and over: that is the bottleneck. (Chapter {{n-10}} introduced indexes; here is what the lack of one costs.)



{{n}}.3 The right index



An index on category alone would find the 250 rows quickly, but they would still need sorting. An index on (category, price) keeps the rows of each category already sorted by price, so the database can read the first 20 entries of one category and stop:






An Index Scan reading 20 entries, no sort, and about a quarter of a millisecond instead of 20: almost a hundred times less work. And under the same load:







From about 90 to about 7,000 requests a second, and the median from 200 milliseconds to 2. Nothing in Node changed.







From about 70 to about 540 requests a second, with four workers of PHP’s built-in server. Nothing in PHP changed.




Indexes are not free: each one takes disk space and slows down every insert and update a little, because it must be kept up to date. Add them for the queries that run often or are slow, matching their WHERE and ORDER BY columns in order, and check with EXPLAIN that they are used. The same habit finds the other database problems: the N+1 queries of Chapter {{n-9}}, SELECT * on wide tables, and offset pagination that reads thousands of rows to skip them.

{{n}}.4 The event loop



Node runs your JavaScript on a single thread, the event loop. That is why one process can serve thousands of requests: while one request waits for the database, the loop runs others. It also means that any JavaScript that runs for a long time without waiting blocks every request in the process. Two routes do the same expensive work, hashing a password with 100,000 rounds, in two ways:






While four clients call one of them, ten others call /ping, which does nothing at all:






With the synchronous version, /ping fell from about 35,000 requests a second to under 100, and its median rose to over 100 milliseconds: it waited in line behind each hash. With the asynchronous version, the hashing runs on libuv’s thread pool, outside the event loop, and /ping stayed fast. The lessons:


    

  • Never use the …Sync functions of fs, crypto and zlib in request handlers.
    • 

  • Heavy computation in JavaScript (image processing, big JSON, complex reports) belongs in a worker thread, a separate process, or a background job (Chapter {{n-4}}).
    • 

  • Watch the event loop delay (prom-client’s default metrics, Chapter {{n-1}}): when it grows, something is blocking.
    • 

  • One process uses one CPU core for JavaScript. Run one process per core (several containers, or Node’s cluster module) to use the whole machine.
    • 





{{n}}.4 PHP workers



PHP takes the opposite approach to Node: each request runs in a worker process that handles one request at a time, from start to finish, and forgets everything afterwards. PHP-FPM, the process manager used in production, keeps a pool of these workers (pm.max_children); PHP’s built-in server can do the same with PHP_CLI_SERVER_WORKERS. Concurrency is therefore the number of workers. This route waits 100 milliseconds, like a call to a slow partner service:









One worker completed about 10 requests a second, exactly 1 ÷ 0.1 seconds: each request held the only worker while it waited. More workers multiplied the throughput, because the waiting happened in parallel. The lessons:


    

  • Waiting is the enemy. A worker that waits for a slow API is a worker that serves nobody. Move slow calls to queued jobs (Chapter {{n-4}}), give every outgoing call a short timeout, and cache what you can (Chapter {{n-7}}).
    • 

  • Size the pool from memory. Each worker uses memory (often 30–60 MB for a Laravel app); pm.max_children is roughly the memory you can give PHP divided by the memory per worker. Too few, and requests queue; too many, and the server swaps.
    • 

  • Do less per request. Turn on OPcache (compiled code kept in memory), run php artisan optimize in production (cached configuration, routes and views), and avoid loading what the request does not need.
    • 

  • Or keep the application in memory. Laravel Octane runs the application in long-lived workers (FrankenPHP, Swoole or RoadRunner), so the framework boots once instead of on every request. It is faster, but state left in static properties or singletons now survives between requests, which must be designed for.
    • 





{{n}}.5 The order of fixes



When the measurements show a real problem, try the fixes in this order, cheapest first:


    

  1. Do less work. An index, a better query, fewer queries, smaller responses, no work the client did not ask for. Usually the biggest win.
    2. 

  2. Do the work later. Emails, reports and calls to partners in background jobs, so the request returns at once.
    3. 

  3. Do the work once. Cache answers that many requests share (Chapter {{n-7}}), and let HTTP caches and CDNs serve what does not change (Cache-Control, ETag).
    4. 

  4. Do the work in parallel. More processes or servers behind a load balancer. This works only for the parts that can be shared out: the database behind them does not get faster by adding web servers, which is why the database was fixed first.
    5. 

  5. Get a bigger machine. Sometimes the cheapest option of all, and always worth pricing before a month of engineering.
    6. 




Professional habit: a performance budget, checked automatically
Write down the targets (“the listing: p95 under 100 ms at 200 requests a second”), keep a load test for the main routes in the repository, and run it before releases against production-like data. A regression caught by a test costs a revert; one caught by customers costs their patience. And keep the before-and-after numbers of every optimisation: they are the proof that the work was worth it.

Summary



    

  • Measure first: latency as percentiles, throughput as requests per second, under realistic load with realistic data.
    • 

  • Find the bottleneck with metrics, traces and EXPLAIN ANALYZE; it is usually a query.
    • 

  • A composite index matching WHERE and ORDER BY turned a full scan into reading 20 entries.
    • 

  • Node’s event loop runs one thing at a time: never block it; offload heavy work.
    • 

  • PHP’s concurrency is its workers: never make them wait; size the pool from memory; OPcache, optimize, Octane.
    • 

  • Fix in order: less work, later work, work once, work in parallel, a bigger machine.
    • 

  • Keep a performance budget and a load test, and record before-and-after numbers.
    • 




Quick check answers: 1. Each user makes many requests, so most users meet the slow ones regularly; and a fast majority pulls the average down, hiding a minority that waits for seconds. The p99 describes what the unluckiest regular experiences look like. 2. That the database read 166,500 rows per process and discarded them, to find the few hundred it needed: a full table scan, the sign of a missing index. 3. An index is sorted by its first column, then the second within it. With (category, price), the rows of one category are together and already ordered by price, so the query reads the first 20. With (price, category), the rows of one category are scattered through the whole index, and the database would have to scan most of it.
