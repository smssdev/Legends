1. SELECT name, email FROM customers WHERE city = 'Cairo' AND id <= 7 ORDER BY name; returns Lina, Sara and Youssef. Both conditions must be true, so AND; the ORDER BY makes the order part of the answer instead of an accident of storage.
  2. Karim’s city is NULL, and NULL != 'Cairo' is NULL, not true, so his row is dropped. Write WHERE city IS DISTINCT FROM 'Cairo', which treats NULL as a value that is simply different, or WHERE city <> 'Cairo' OR city IS NULL. For the named customers, the result is Omar, Karim, Mona and Hana. Whether Karim belongs in the answer is a business question; the query must answer it on purpose, not by accident.
  3. SELECT p.name FROM products p LEFT JOIN order_items i ON i.product_id = p.id AND i.order_id > 100000 GROUP BY p.id, p.name HAVING count(i.order_id) = 0; gives Battery pack, Sensor set, Remote control and Gear box. The condition on order_id belongs in the ON clause: in the WHERE clause, it would remove the rows with NULL and turn the left join back into an inner join. WHERE NOT EXISTS (SELECT 1 FROM order_items i WHERE i.product_id = p.id AND i.order_id > 100000) says the same more directly.
  4. A partial index contains only the rows that match its WHERE: CREATE INDEX orders_pending_recent_idx ON orders (created_at) WHERE status = 'pending';. Since few orders are pending at any time, the index stays tiny however large orders grows, and EXPLAIN shows Index Scan using orders_pending_recent_idx. The query must include status = 'pending' for PostgreSQL to use it.
  5. Group by month in a CTE, then use two window functions over the months in order: sum(revenue) OVER (ORDER BY month) for the running total, and revenue - lag(revenue) OVER (ORDER BY month) for the change. lag reads the previous row, so the first month’s change is NULL. The query in the code repository shows the first months of the generated data; the first is small because the data starts on 19 November, part of the way through the month.
