Chapter {{n}}

Transactions, Locks and Consistency

In this chapter you will learn to

  • group changes into transactions that happen completely or not at all
  • see a race condition sell one item ten times, and fix it three different ways
  • choose an isolation level, knowing what each lets a transaction see
  • recognise deadlocks, and prevent them with a consistent lock order
  • retry the transactions the database refuses, safely
  • keep side effects such as emails and messages out of transactions that might roll back

Everything in Part 1 quietly assumed one request at a time. A real shop serves many customers at once, and the database runs their requests side by side. Most of the time they touch different rows and nothing interesting happens. Then two customers buy the last robot kit at the same moment, and the shop sells it twice. These bugs never show in development, where you are the only user; they appear under load, rarely, and they cost money. This chapter makes them happen on purpose, so you can see them, and then makes them impossible.

A bug report said: “we sold 103 tickets for a room of 100”. I could not reproduce it. Every test passed, every read of the code looked right. It only happened when three people pressed “buy” in the same tenth of a second. It took me a week to understand that my code was correct for one user and wrong for two.

{{n}}.1 Transactions: all or nothing

A transaction groups statements so that they act as one. It has four guarantees, known as ACID:

  • Atomicity: either every change is kept, or none is.
  • Consistency: every rule of the schema holds at the end.
  • Isolation: transactions running at the same time do not see each other’s unfinished work (exactly how much they see is the isolation level, {{n}}.3).
  • Durability: once committed, a change survives a crash.

BEGIN starts a transaction, COMMIT keeps its changes, ROLLBACK throws them away. Inside the transaction, the change is visible; after the rollback, it never happened:






When one step fails, the transaction is aborted: PostgreSQL ignores every later statement, and even COMMIT turns into a ROLLBACK. The first update, which succeeded, is undone with the rest:






That is exactly what an order with several items needs: if the third item is out of stock, the stock of the first two must not be taken. Every statement you run outside BEGIN is a transaction of its own, committed at once.



{{n}}.2 A race: one kit, ten buyers



Here is the obvious way to sell a product: read the stock, check it in code, write the new stock, record the order. To see what happens under load, the program starts ten buyers at the same moment, each with its own database connection, for a product with one unit left. A short pause between reading and writing stands for what a real application does there, such as calling a payment service:














The ten buyers are ten processes made with pcntl_fork, each with its own connection, like ten PHP workers serving ten requests:










The naive version sold one kit ten times. Every buyer read “1 in stock” before anyone had written, every buyer decided to sell, and every buyer wrote “0”. The transaction did not help: it makes changes all-or-nothing, but it does not stop two transactions from reading the same value. This is a race condition, a check-then-act bug: the check was true when it ran and false by the time the action happened.



The other three versions each sold it once. They are the three standard fixes:


    

  • An atomic update. UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock > 0 checks and changes in one statement. PostgreSQL locks the row while it updates, so the second buyer’s update waits, then re-checks stock > 0 against the new value and changes nothing. The number of changed rows tells the code whether it sold. When the rule fits in a WHERE, this is the simplest and fastest fix.
    • 

  • A row lock. SELECT … FOR UPDATE reads the row and locks it until the transaction ends. Every other buyer waits at that line, then reads the stock after the first one committed. Use it when the decision needs code between the read and the write (a price calculation, a call to another service), and keep such transactions short, because everyone waits.
    • 

  • Serializable isolation. The code stays naive, and the database guarantees that the result equals running the transactions one after another. When it detects that this is impossible, it refuses a transaction with error 40001, and the code runs it again from the start: here, nine of the ten buyers were refused once and found the stock empty on their retry.
    • 




Watch out: the check in code is never enough
Any rule of the form “only if …” (enough stock, a seat still free, a balance high enough, a username not taken) is a race when it is checked in code and then written. Put the rule where the database can enforce it at the moment of the write: in a conditional update, a unique constraint, a CHECK, or a lock. Chapter {{n-2}}’s CHECK (stock >= 0) would also have stopped the oversale, with an error instead of a quiet second order.



{{n}}.3 Isolation levels



The isolation level decides what a transaction sees of other transactions that commit while it is running. Two connections show the difference: A reads a price, B changes it and commits, A reads again and then tries to change it:


















    

  • READ COMMITTED, PostgreSQL’s default: every statement sees everything committed before it started. A’s second read saw B’s new price, so two reads in one transaction disagreed, and A’s update built on B’s value.
    • 

  • REPEATABLE READ: the transaction sees a snapshot taken at its first statement. A’s second read still saw 45000, so its reads are consistent with each other. And when A tried to update a row that B had changed since that snapshot, PostgreSQL refused: A was working from an old picture. The application must retry.
    • 

  • SERIALIZABLE adds detection of every pattern that could not happen if the transactions ran one after another, as in the race above. It is the safest level and needs retries the most.
    • 




A practical rule: keep the default, use atomic statements and constraints for the rules they can express, take row locks when code must decide between a read and a write, and use SERIALIZABLE (with retries) for complicated multi-row rules where it is hard to see every race. Reports that read many tables at once benefit from REPEATABLE READ, so their numbers come from one moment.

{{n}}.4 Deadlocks



Locks have their own trap. Transaction A locks product 1 and then wants product 2; transaction B has locked product 2 and wants product 1. Each waits for the other, forever:


















PostgreSQL checks for such cycles after a second of waiting (deadlock_timeout), picks one transaction, and aborts it with error 40P01, so the other can finish. Which one loses depends on timing. Two habits keep deadlocks rare: lock rows in a consistent order (for an order with several products, lock or update them sorted by id), and keep transactions short, with no network calls or user waits inside them. Like serialization failures, a deadlock victim can simply be retried.



{{n}}.5 Transactions in the framework




With Kysely from Chapter {{n-1}}, a transaction is a callback; it commits when the callback returns and rolls back when it throws. Row locks and isolation levels are methods:


    

  • await db.transaction().setIsolationLevel("serializable").execute(async (trx) => { … }), using trx, not db, for every query inside.
    • 

  • trx.selectFrom("products").selectAll().where("id", "=", id).forUpdate().executeTakeFirst() for a row lock.
    • 



Kysely does not retry for you: wrap the call in a small loop that retries on codes 40001 and 40P01, a few times, with a short random pause between attempts. The race program above has exactly that loop.




Laravel wraps a transaction in a closure: DB::transaction(function () { … }) commits when the closure returns and rolls back when it throws. Its second argument is a number of attempts: DB::transaction($work, attempts: 5) runs the closure again when the database reports a deadlock or a serialization failure, which is the retry loop of the race program, built in. Row locks are query builder methods: Product::whereKey($id)->lockForUpdate()->first(), or sharedLock() to stop others from changing the row while still letting them read it. Chapter {{n-3}}’s order controller used the atomic update inside DB::transaction.




{{n}}.6 Side effects and the outbox



A transaction can be rolled back; an email cannot be unsent. If the code sends “your order is confirmed” inside the transaction and the commit then fails (a deadlock, a constraint, a crash), the customer has an email for an order that does not exist. Sending after the commit has the opposite problem: if the process crashes between the commit and the send, the order exists and the email never goes.



The reliable pattern is the outbox: inside the same transaction as the order, insert a row into an outbox table describing the message to send. The order and its message commit together or not at all. A separate worker reads the outbox, sends each message, and marks it sent; if it crashes, it sends again later, so the receiver must tolerate duplicates (idempotency again). Chapter {{n+4}} builds the worker with a queue, and Laravel’s afterCommit option for jobs covers the simpler half of the problem.



Professional habit: test races on purpose
A race does not appear in a test that runs one request at a time. For every “only if” rule (stock, seats, balances, unique names), write one test that starts many requests at the same moment, as this chapter’s race program does, and asserts on the final state: one sale, one booking, a balance never below zero. Such a test fails reliably on the naive code, which is the proof that it tests the right thing.

Summary



    

  • A transaction makes several statements atomic: one failure, and COMMIT becomes ROLLBACK.
    • 

  • Transactions do not stop races: “read, check in code, write” sells one item many times under load.
    • 

  • Three fixes: an atomic conditional update, a row lock with FOR UPDATE, or SERIALIZABLE with retries.
    • 

  • READ COMMITTED sees each statement’s latest commits; REPEATABLE READ sees one snapshot and refuses updates to rows changed since.
    • 

  • Deadlocks are cycles of locks; PostgreSQL breaks them with 40P01. Lock in a consistent order, keep transactions short, retry.
    • 

  • Side effects belong after the commit, reliably through an outbox.
    • 




Quick check answers: 1. A transaction makes its own changes all-or-nothing, but under the default isolation level it does not stop other transactions from reading the same row at the same time, so all ten read “1” before any of them wrote. 2. Other SELECT … FOR UPDATE statements, and updates, on that row wait until the locking transaction commits or rolls back; plain SELECTs still read the last committed version without waiting. 3. Roll back and run the whole transaction again from the beginning, reading the data afresh, a limited number of times, ideally after a short random pause.

Project {{n}}.1 · Easy


A safe stock reservation


Turn the race program into a reusable function that reserves several products for one order, safely, and prove it under load.


You will practise: atomic updates, transactions with several statements, consistent lock order, and concurrency tests.


    

  1. Write reserve(items): inside one transaction, take each product’s quantity with an atomic conditional update, and roll back the whole order if any item is short.
    2. 

  2. Sort the items by product id before updating, and explain why.
    3. 

  3. Start 50 concurrent orders for random baskets on a few products with small stocks, and check afterwards that no stock is negative and that the stock taken equals the quantities in the successful orders.
    4. 

  4. Remove the sorting, run it again, and count the deadlocks.
    5. 



Hint: the final check is the real test: the sum of quantities in successful orders, plus the remaining stock, must equal the starting stock, for every product.







Project {{n}}.2 · Medium


Money between wallets


Build customer wallets with transfers that never lose or create money, whatever the concurrency.


You will practise: double-entry thinking, row locks in order, CHECK constraints, and invariants.


    

  1. Create wallets (customer, balance in piastres, CHECK (balance >= 0)) and transfers (from, to, amount, time).
    2. 

  2. Write transfer(from, to, amount): lock both wallets with FOR UPDATE in id order, check the balance, move the money, and record the transfer, in one transaction.
    3. 

  3. Run 1,000 random transfers concurrently between 20 wallets, and check that the total of all balances never changed.
    4. 

  4. Rewrite it with SERIALIZABLE and no explicit locks, with retries, and compare the number of retries and the time taken.
    5. 



Hint: real systems rarely store a balance alone; they keep a ledger of entries and compute or cache the balance from it. Your transfers table is the start of that ledger.







Project {{n}}.3 · Challenge


An outbox that never loses a message


Send an order confirmation exactly when the order is committed, even if processes crash at the worst moments.


You will practise: the outbox pattern, FOR UPDATE SKIP LOCKED, idempotent consumers, and crash testing.


    

  1. Create an outbox table (id, type, payload as JSON, created, sent). Insert a message in the same transaction as each order.
    2. 

  2. Write a worker that, in a transaction, takes up to 10 unsent messages with FOR UPDATE SKIP LOCKED, “sends” them (write them to a file), and marks them sent.
    3. 

  3. Run three workers at once and check that no message is sent twice by different workers in normal operation.
    4. 

  4. Kill a worker in the middle of a batch (after writing to the file, before committing) and show that the message is sent again: make the receiver ignore duplicates by message id.
    5. 



Hint: SKIP LOCKED lets each worker skip the rows another worker has locked, so several workers share the queue without waiting for each other. It is how PostgreSQL can serve as a simple job queue.
