SQL and PostgreSQL

In this chapter you will learn to

  • design tables with the right types, and let the database enforce your rules
  • read data with SELECT, filters, sorting, and the strange logic of NULL
  • combine tables with joins, and summarise them with GROUP BY
  • write CTEs and window functions for questions that plain queries cannot answer
  • change data with RETURNING and upserts
  • read a query plan, and add the index that turns a scan into a lookup
  • send values to SQL safely from your code, so that SQL injection cannot happen

Until now the shop kept its data in memory, in a file, or in a database we did not look inside. Part 2 opens the database. Almost every backend you will work on keeps its important data in a relational database, and almost every serious performance problem you will meet ends in a query. SQL is fifty years old and will outlive the frameworks in this book; learning it well is one of the best investments a backend developer can make. We use PostgreSQL, the most capable free database, and run every query for real on a shop with a hundred thousand orders.

For years I treated the database as a place to put things, and wrote everything else in code: loops over rows, checks before every insert, totals summed in JavaScript. Then a colleague replaced two hundred lines of my code with one query that ran fifty times faster. That was the day I started learning SQL properly.

{{n}}.1 Tables, types and rules

A relational database stores data in tables. Each table has fixed columns, each with a type, and any number of rows. Tables refer to each other through ids. Here is the shop:




Read it slowly, because every word is a decision:


    

  • Types. bigint for ids, because integer stops at about two billion. text for strings, with no arbitrary length limit (PostgreSQL stores text and varchar the same way). integer for money in piastres. timestamptz for moments in time: it stores an exact instant, in UTC, and never confuses time zones. Never use timestamp without a time zone for events.
    • 

  • GENERATED ALWAYS AS IDENTITY numbers rows automatically. It is the standard way; the older serial works too.
    • 

  • PRIMARY KEY identifies each row: unique, never null, and indexed.
    • 

  • NOT NULL, UNIQUE and CHECK are rules the database enforces on every write.
    • 

  • REFERENCES is a foreign key: an order cannot point to a customer who does not exist. ON DELETE CASCADE deletes an order’s items with the order.
    • 

  • order_items has a composite primary key: one row per product per order. It also copies the price, because product prices change and an order must not.

Let the database say no



Every rule in the schema is enforced, whichever program writes the data: your API, a script someone runs at midnight, or a colleague in psql:






A price of zero, an order for a customer who does not exist, a second account with the same email, stock below zero: each is refused, with a message that names the rule. Validation in the application gives users friendly messages; constraints in the database guarantee the data stays correct when the application has a bug. You want both.



{{n}}.2 Reading: SELECT



A query names the columns it wants, the table, the rows (WHERE), the order, and how many:






Write SQL keywords in capitals and names in lower case, one clause per line. SQL does not care, but readers do. The second query uses aggregate functions, which turn many rows into one: count, sum, min, max and avg.



NULL: the missing value



NULL means “unknown” or “missing”. Karim has no city. That sounds simple, until you compare:






Is an unknown city equal to an unknown city? SQL’s answer is “unknown”: NULL = NULL is NULL, not true. A WHERE keeps only rows where the condition is true, so city = NULL keeps nothing, ever. Use IS NULL and IS NOT NULL. Arithmetic with NULL gives NULL too, and aggregates such as sum skip NULL values. The best defence is NOT NULL on every column that has no good reason to be empty.



{{n}}.3 Joins: combining tables



A join puts together rows from several tables that belong together. To list each named customer’s orders with their totals, the query joins customers to their orders and orders to their items, then groups the items of each order:






JOIN … ON (an inner join) keeps only the combinations that match. That is why Karim and Hana, who have no orders, are missing. To keep every customer, use a left join: every row of the left table, with NULL where the right table has nothing:






Notice count(o.id), not count(*). count(*) counts rows, and Karim’s row exists (with NULL for the order), so it would say 1. count(o.id) counts the values that are not NULL, so it says 0. This small difference hides in many reports.



{{n}}.4 Grouping and summarising



GROUP BY makes one result row per group, and aggregates summarise each group. HAVING filters the groups, as WHERE filters rows:






Read the order in which the database works, which is not the order in which the query is written: FROM and the joins first, then WHERE (cancelled orders go), then GROUP BY, then HAVING (products that sold 26,600 units or fewer go), then SELECT, then ORDER BY. That is why WHERE cannot use sum(...): when it runs, there are no groups yet.



Money is still in piastres in the sums, and divided by 100 only at the end, for display. Integer division would be wrong for an amount like 12,550 piastres; here every revenue happens to be whole pounds. In an API, send piastres and let the client format them.



{{n}}.5 CTEs and window functions



Some questions need a result to build on. “Rank the named customers by what they spent, and show each one’s share” needs the totals first, then a ranking over them:






    

  • WITH spent AS (…) is a common table expression (CTE): a named query used by the next one. It reads like a variable, and keeps long queries understandable.
    • 

  • rank() OVER (ORDER BY …) is a window function: it computes over a set of rows without collapsing them, unlike GROUP BY. Each customer keeps their row and gets a rank.
    • 

  • sum(s.total) OVER () is an aggregate used as a window over all rows: the grand total, next to every row, so each row can compute its share.
    • 




Window functions answer the questions reports always ask: rankings, running totals, the previous month for comparison (lag), the top three per category. Without them, you would write loops in code over thousands of rows.

{{n}}.6 Writing: INSERT, UPDATE, DELETE



Writes can answer too. RETURNING gives back columns of the rows that were written, so the application gets the new id and the defaults without a second query. ON CONFLICT turns an insert that would break a unique rule into an update, an upsert:






The upsert is one statement, so two requests that register the same email at the same moment cannot both insert: the database decides. Doing the same in code (“check whether it exists, then insert”) leaves a gap between the check and the insert in which another request can slip through. Chapter {{n+2}} is about exactly these gaps.



Watch out: UPDATE and DELETE without WHERE
DELETE FROM orders; deletes every order, instantly, without asking. Before running an UPDATE or a DELETE by hand, run the same WHERE as a SELECT and check the rows. Better still, start a transaction with BEGIN;, run the change, look at the result, and only then COMMIT; (or ROLLBACK;). Chapter {{n+2}} explains transactions.



{{n}}.7 Indexes and query plans



The orders table has a hundred thousand rows. How does PostgreSQL find the orders of customer 1234? EXPLAIN shows the plan the database chose; with ANALYZE, it also runs the query and reports what really happened:






A sequential scan: PostgreSQL read all 100,006 rows and threw away 99,962 to find 44. Five milliseconds sounds small, but it grows with the table, and the API does it on every request for every user. An index is a separate, sorted structure (a B-tree) that maps values to rows, like the index at the back of this book:






Now the database goes straight to the 44 rows through the index: several times faster here, and the gap widens as the table grows, because a B-tree lookup takes about the same time for a million rows as for a thousand. Three rules about indexes:


    

  • PostgreSQL does not index foreign keys for you. orders.customer_id had no index until we added one. Index the foreign keys you search or join by.
    • 

  • An index serves the queries that match it. A query that wraps the column in a function cannot use a plain index on the column. You can index the expression itself:
    • 







    

  • Indexes are not free. Each one takes space and slows every insert and update, which must update the index too. Add them for the queries you actually run, as shown by EXPLAIN and by the slow query log, not “just in case”.
    • 




For a column pair such as (price, id), the order matters: the index is sorted by price first, so it serves WHERE price = … and ORDER BY price, id, but not a search by id alone. Chapter {{n+10}} goes deeper into plans and tuning.



Professional habit: EXPLAIN before you ship
For every new query that will run on a large or growing table, run EXPLAIN ANALYZE on realistic data before the code is merged, and paste the plan in the pull request. A Seq Scan on a big table in a request path is a bug waiting for traffic. Testing on a table with twelve rows proves nothing: generate data, as seed.sql does with generate_series.



{{n}}.8 SQL from code, safely



Applications send SQL to the database through a driver. The single most important rule: never build SQL by joining strings with input. Here is why, with an input that a form could send as an email address:










Glued into the SQL, the input closed the quote and added OR '1'='1', which is always true: the query returned every customer, 2008 rows, instead of none. This is SQL injection, still one of the most common and most damaging attacks on the web: with a slightly different input, an attacker can read any table, or delete them. With a parameter, $1, the SQL and the value are sent to the database separately; the value can never become SQL, whatever it contains, and the same query found no customer with that strange email.



Notice the last line: orders arrived as the string '2'. count(*) returns a bigint, and a JavaScript number cannot hold every bigint exactly, so the pg driver plays safe and returns a string. Convert it when you know the value is small (Number(row.orders)), or cast in SQL (count(*)::int). Chapter {{n+1}} adds a typed layer that does this once.

PDO is PHP’s database layer, and it is what Laravel uses underneath: DB::select('… where email = ?', [$email]), the query builder and Eloquent all send parameters this way. They are only unsafe when you put input into the SQL text yourself, for example in DB::raw() or whereRaw() with string concatenation. Notice also that count arrived as a PHP int: PDO for PostgreSQL converts integer columns to PHP integers. Chapter {{n+1}} puts Eloquent on top of this.

Summary



    

  • Tables have typed columns: bigint ids, text, integer money, timestamptz times. Constraints (PRIMARY KEY, NOT NULL, UNIQUE, CHECK, REFERENCES) keep data correct whatever writes it.
    • 

  • SELECT … FROM … WHERE … ORDER BY … LIMIT reads rows; aggregates summarise them.
    • 

  • NULL is unknown: compare it with IS NULL; it spreads through arithmetic.
    • 

  • Inner joins keep matches; left joins keep every left row. Count a right-table column, not *.
    • 

  • GROUP BY makes groups, HAVING filters them; the database runs FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY in that order.
    • 

  • CTEs name intermediate results; window functions compute across rows without collapsing them.
    • 

  • RETURNING and ON CONFLICT make writes answer and upserts atomic.
    • 

  • EXPLAIN ANALYZE shows the plan; indexes turn scans into lookups. Index foreign keys and real query patterns, including expressions.
    • 

  • Parameters, never string concatenation, between code and SQL.
    • 




Quick check answers: 1. Comparing anything with NULL gives NULL (unknown), never true, and WHERE keeps only rows where the condition is true; use IS NULL. 2. count(*) counts rows, and a customer with no orders still has one row in a left join (with NULLs), so they get 1 instead of 0; count a column from the orders table, such as count(o.id). 3. WHERE runs before the rows are grouped, so there is no sum yet; filter groups with HAVING sum(quantity) > 100.
