Docker: Shipping the Same Thing Everywhere

In this chapter you will learn to

  • explain images, containers and layers, and why they end “it works on my machine”
  • write a production Dockerfile for the NodePHP service, small and safe
  • run the service and its database together with Docker Compose, with health checks
  • run one-off commands such as migrations in the same image
  • prepare containers for production: configuration, secrets, logs, workers and releases

The shop now needs a precise list of things to run: a particular version of NodePHP with particular extensions, its dependencies, PostgreSQL, Redis, environment variables, a worker. On a developer’s laptop that list lives in someone’s memory; on a server, in a setup document that is always slightly out of date. Docker turns the list into a file that a machine follows exactly. The result, an image, runs the same on a laptop, in CI and in production. Every example in this book has quietly used it: PostgreSQL and Redis ran in containers from the first chapter. Now the shop itself goes into one.

My first deployment checklist had 41 steps, and a new server took a day. One step was “install the image library, version 2.x (not 3!)”. When we moved to Docker, the checklist became one command, and the “not 3” lived in a file that CI checked on every change. I have not missed the checklist once.

{{n}}.1 Images and containers

  • An image is a read-only package: a minimal operating system, the runtime, your code and its dependencies, and the command to start it. It is built once and copied anywhere.
  • A container is a running instance of an image, isolated from the host and from other containers: its own files, processes and network address, sharing the host’s kernel. Containers start in a second and are thrown away freely; nothing written inside one survives its removal unless it is in a volume.
  • An image is a stack of layers, one per instruction of its Dockerfile. Docker caches each layer and rebuilds only from the first instruction whose inputs changed, which is why the order of instructions matters.

{{n}}.2 A production Dockerfile

The service is a small Fastify app that reads the products from PostgreSQL. Its Dockerfile has two stages: the first installs the production dependencies, the second copies only what is needed to run:




    

  • Dependencies before code. package.json and the lock file are copied first and npm ci runs on them alone; editing the code then rebuilds only the last layers, in seconds. npm ci installs exactly the lock file’s versions, and --omit=dev leaves out TypeScript, test tools and the rest.
    • 

  • No build step. Node 22 runs TypeScript files directly by stripping their types (Chapter {{n-14}}), so the image runs src/server.ts as it is. Projects that compile add a build stage whose output is copied in the same way.
    • 

  • Not as root. The official image provides a node user; if an attacker found a hole in the app, they would not be root inside the container.
    • 

  • A health check. Docker asks the app’s own /health route (Chapter {{n-3}}) every five seconds, and reports the container as healthy or not.
    • 

  • A .dockerignore keeps node_modules, .env and .git out of the build, so local files and secrets never end up in the image.
    • 








The service is a small PHP app that reads the products from PostgreSQL through PDO. Its Dockerfile starts from the official image with Apache and PHP, and adds the PostgreSQL driver:






    

  • Extensions are compiled in. docker-php-ext-install builds pdo_pgsql into PHP; the system library it needs comes from the operating system’s packages, and the package lists are deleted in the same layer so they do not bloat the image.
    • 

  • Production settings. The official image ships php.ini-production (no errors shown to visitors, sensible limits); the Dockerfile makes it the active configuration.
    • 

  • Only public/ is served. Apache’s document root points at public/, so files such as bin/count.php or a .env can never be downloaded, and every address falls back to index.php.
    • 

  • A health check. Docker asks the app’s own /health route (Chapter {{n-3}}) every five seconds.
    • 

  • A .dockerignore keeps vendor, .env and .git out of the build, so local files and secrets never end up in the image.
    • 








Size matters: every image is downloaded by every server that runs it, and every package inside is something that may need a security update. Slim base images, multi-stage builds and deleting build tools in the layer that used them all keep it down (exercise 3).



{{n}}.3 Compose: the whole stack



An app is rarely alone. Docker Compose describes several containers, their configuration and their network in one file, and starts them together:












    

  • Services find each other by name. Compose puts them on one private network, where the database’s address is simply db. Only the app’s port is published to the host; the database is reachable from the app, not from outside.
    • 

  • A named volume keeps the database’s files when its container is replaced. The first time the database starts, it runs the SQL files mounted in /docker-entrypoint-initdb.d.
    • 

  • Health checks drive the start order. condition: service_healthy starts the app only once PostgreSQL answers, and --wait returns only when every container is healthy.
    • 













One command started the database, waited for it, started the app and waited for it too. The products came from PostgreSQL inside the stack. docker compose run started a new container from the same image for a one-off command, the way migrations and maintenance scripts run in production. The logs went to standard output, where Docker collects them (Chapter {{n-3}}). And down -v removed everything, the volume included, leaving the machine as it was.

{{n}}.4 Containers in production



A container platform (a server with Compose, Kubernetes, or a cloud service that runs containers) takes the image and runs it. A few rules make that safe:


    

  • Configuration from the environment. The same image goes to staging and production; only environment variables differ (Chapter {{n-7}}). Secrets come from the platform’s secret store, never from the image or a committed file.
    • 

  • One concern per container. The web app, the queue worker (Chapter {{n-6}}) and the scheduler run as separate containers from the same image with different commands, so each can be scaled and restarted on its own.
    • 

  • Stateless containers. Anything that must survive goes to the database, Redis, object storage or a volume. A container can then be replaced at any moment, which is what deployments and autoscaling do.
    • 

  • Graceful shutdown. The platform sends SIGTERM and waits a little before killing; the app finishes its requests and the worker its jobs, as earlier chapters prepared.
    • 

  • Releases in steps. Build the image in CI, tag it with the commit (never only latest), scan it for known vulnerabilities, push it to a registry, run the migrations as a one-off container, then replace the running containers gradually while health checks confirm each new one.
    • 





A Laravel image



For a full Laravel application the same ideas apply, with a few more stages. A Composer stage runs composer install --no-dev --optimize-autoloader; a Node stage builds the front-end assets with npm run build; the final image copies both, and at start runs php artisan optimize to cache configuration, routes and views. Web servers commonly used are Apache as here, nginx with PHP-FPM in two containers, or FrankenPHP, a single server that can also run Octane. The queue worker (php artisan queue:work), the scheduler (php artisan schedule:work) and Reverb (php artisan reverb:start) are further services of the same image, and php artisan migrate --force runs as a one-off container during each release. Laravel Sail provides a ready-made Compose setup for development.




Professional habit: the same image from CI to production
Build the image once, in CI, from a clean checkout, and promote that exact image through staging to production by its tag. Never build on the production server, and never change a running container by hand: the next deployment would silently undo it. If something must change, change the Dockerfile or the configuration, and ship a new image.

Summary



    

  • An image packages the runtime, code and dependencies; a container runs it, isolated and disposable; volumes keep data.
    • 

  • A good Dockerfile orders layers for the cache, installs production dependencies only, runs as non-root, and has a health check and a .dockerignore.
    • 

  • Compose starts the app and its services on a private network, in order, with health checks; run executes one-off commands in the same image.
    • 

  • In production: configuration and secrets from the environment, one concern per container, stateless containers, graceful shutdown.
    • 

  • Release by building once in CI, tagging, scanning, migrating, and replacing containers gradually.
    • 




Quick check answers: 1. Docker rebuilds from the first instruction whose inputs changed. Copying only the dependency files first means the expensive install layer is reused as long as dependencies do not change, so an ordinary code change rebuilds in seconds instead of reinstalling everything. 2. Only the app needs to reach it, through the private network; publishing it would expose the database to anything that can reach the host, and nothing outside the stack has a reason to connect. 3. They are still there: down removes the containers and the network, but keeps the named volume, so the new database container finds the same files (and does not run the initialisation scripts again, since the database already exists). -v removes the volume too.
