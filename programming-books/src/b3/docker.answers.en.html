1. Set the working directory; copy the dependency files; install the dependencies; copy the source code. The working directory comes first because every later path is relative to it. The dependency files and the install come before the code so that their layers are reused whenever only code changes; copying the code last means an ordinary change rebuilds only that final, cheap layer.
  2. Everything in a Dockerfile ends up in the image, and anyone who can pull the image (CI, other teams, a leaked registry token) can read it with docker history or by running the image; the password is also committed to the repository with the Dockerfile, and the same image cannot be used with a different password in another environment. Pass it at run time instead, from the platform’s secret store: environment entries filled from secrets in Compose or Kubernetes, or an .env file that is never committed.
  3. (1) A smaller base image, such as an Alpine variant or a “distroless” one: often half the size, but Alpine uses a different C library that some native modules or extensions do not support, and distroless images have no shell for debugging. (2) Remove build tools in the same layer that used them (install native build tools only in the dependency stagepurge libpq-dev and keep only the runtime libpq5, or build the extension in a separate stage): smaller and fewer packages to patch, but a slightly more complex Dockerfile. (3) Fewer dependencies: check what node_modules holds with npm ls --omit=dev and remove packages the app does not needuse a lighter web server image (for example FrankenPHP or PHP-FPM without Apache) and install only the extensions the app uses; the trade-off is time spent, and sometimes features of the bigger option.
  4. Compose starts the containers in dependency order but, with a plain depends_on, it waits only until the database container has started, not until PostgreSQL accepts connections, which takes a few seconds; the app starts, fails to connect, and crashes (it works later after a restart or a retry). Give the database a health check (pg_isready) and make the app wait for it with depends_on: db: condition: service_healthy, as this chapter’s Compose file does; the app should also retry its connection at start-up, since databases restart in production too.
  5. Expand and contract (Chapter {{n-11}}). Release 1: a migration adds the column as nullable (or with a default), and the code writes it for new rows while still working without it; CI builds, tests and scans the image; the migration runs as a one-off container (old code is unaffected by a new nullable column); the new containers replace the old ones gradually behind health checks. Then a backfill fills the column for existing rows, in batches. Release 2: a migration makes the column required (now safe, since every row has a value), and the code starts relying on it; deployed the same way. At every moment, the running code and the database schema are compatible, so no request fails.
