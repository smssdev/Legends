Chapter {{n}}

Observability: Logs, Metrics and Traces

In this chapter you will learn to

  • write structured logs that machines can search and people can read
  • follow one request across services with a trace id
  • count requests, errors and durations as metrics, and read them like Prometheus
  • answer health and readiness checks so platforms know what to do with each server
  • turn signals into alerts that wake people only when users are affected

Tests prove the code worked on the day it shipped. In production, things go wrong that no test imagined: a partner’s API slows down, a disk fills, one query becomes slow when a table grows. Observability is the ability to answer “what is happening, and why?” from the outside, without adding code and redeploying first. It rests on three kinds of signal: logs (what happened, event by event), metrics (how much and how fast, as numbers over time) and traces (where the time of one request went, across services). This chapter adds all three to a small shop service, written with Fastify, written in plain PHP so that every moving part is visible, with the Laravel equivalents at the end.

The worst night of my first job began with a customer email: “checkout has been broken for three hours”. Our logs were lines like Error occurred, with no order, no user and no time zone. We spent two hours finding which server, and one minute fixing the bug. Since then I log as if I will be reading it at three in the morning, tired, in a hurry. Because I will.

{{n}}.1 Structured logs

A log line like Order failed for sara is easy to write and hard to use: you cannot count them, filter them by order or join them to other lines. A structured log writes each event as one JSON object per line, with named fields. Tools such as Loki, Elasticsearch or a cloud provider’s log service can then answer questions like “all errors for this order in the last hour”, and people can still read it.

PHP applications log with Monolog, the library under Laravel’s Log facade. A formatter decides how each record is written; this one writes a short JSON object per line:







Three requests, one of which brings its own trace id from a caller:


















Every line carries the same fields: the time, the level (debug, info, warn, error), the service that wrote it, and the request’s trace id. The start and the end of each request are logged with its method, address, status and response time. Good habits for what goes into logs:


    

  • Log events, with context. “order placed” with the order id and total, not “done”. Every line of a request carries its id, so one search shows the whole story.
    • 

  • Choose levels honestly. error for something that needs a person; warn for something odd that the code handled; info for normal events. Production usually keeps info and above.
    • 

  • Never log secrets or personal data. No passwords, tokens, card numbers or whole request bodies. The serializers above log the method and address only, not the headers with their Authorization.
    • 

  • Write to standard output, and let the platform collect, store and search. The application should not manage log files.
    • 




{{n}}.2 Errors



When something fails, two audiences need different things. The client needs a short answer that reveals nothing (Chapter {{n-4}}); the team needs every detail. The trace id connects them:


















The customer sees “Server error” and a trace id they can quote to support; the log has the message, the type and the line, under the same id. With an error tracker (Sentry, or the free GlitchTip), errors are also grouped, counted and sent to the team with the full stack, which is better than reading logs for them.



{{n}}.3 Traces across services



Once a request crosses from one service to another, a request id is no longer enough: each service would make up its own. The W3C Trace Context standard defines a header, traceparent, that carries a trace id from service to service: 00-, 32 hex characters of trace id, 16 of the caller’s span id, and flags. Each service takes the trace id from the incoming header (or starts a new trace), logs with it, and passes it on:


















The two services wrote to different terminals; merged by time, their lines form one story under one trace id: the checkout started, called the stock service, which answered in a few milliseconds, and the checkout finished. This is the core idea of distributed tracing. Full tracing systems go further: each step becomes a span with a start, a duration and a parent, sent to a tracing backend (Jaeger, Tempo, or a cloud service) that draws the whole request as a timeline. OpenTelemetry, the open standard for this, provides libraries for every language that create spans for HTTP calls, database queries and queue jobs automatically, using the same traceparent header.

{{n}}.4 Metrics



Logs tell you about individual events; metrics are numbers about all of them, cheap to store for months and fast to chart: requests per second, errors per minute, how slow the slowest requests are. For a web service, three numbers per route cover most needs, often called RED: the Rate of requests, the Errors among them, and their Duration. Prometheus, the most common open-source metrics system, collects them by reading a /metrics page from each server every few seconds.




The prom-client library keeps the numbers in the process’s memory and writes the page:










A Node process keeps counters in memory, but a PHP process forgets everything when its request ends, so the counters live in Redis (Chapter {{n-6}}), updated after the response has been sent:










    

  • A counter only goes up: http_requests_total by method, route and status. Prometheus computes rates from it (“errors per minute”) by comparing readings over time.
    • 

  • A histogram counts durations into buckets: how many requests took at most 10 ms, 50 ms, and so on. From it, Prometheus estimates percentiles: the 95th percentile (p95) is the time under which 95% of requests finish. Percentiles matter more than averages, because an average hides the customers who waited ten seconds.
    • 

  • Labels use the route pattern, never the real address or a user id: /products/:id is one series, while one series per product would multiply without end (high cardinality) and overload the metrics system.
    • 




{{n}}.5 Health and readiness



Load balancers and container platforms keep asking each server whether it is well, and act on the answer. Two different questions deserve two endpoints:


















    

  • Liveness (/health): is the process alive and answering? If not, the platform restarts it. It must not check the database: when the database is down, restarting every web server makes things worse, not better.
    • 

  • Readiness (/ready): can this server do useful work right now? If not, the load balancer stops sending it traffic until it can. Here it checks the database with a short timeout, and answered 503 as soon as the database stopped, while liveness stayed 200.
    •

{{n}}.6 From signals to alerts



Dashboards are for looking; alerts are for being told. The art is alerting on what users feel, not on every cause:


    

  • Service level objectives. Decide what “working” means, in numbers: “99.5% of checkout requests succeed, and 95% finish within 500 ms, over 30 days”. That is an SLO; the 0.5% of allowed failures is the error budget. Alert when the budget is burning fast, not at every error.
    • 

  • Symptoms over causes. “Checkout errors above 2% for 5 minutes” wakes someone; “CPU at 80%” goes to a dashboard. High CPU with happy users is not an emergency; a broken checkout at 20% CPU is.
    • 

  • Every alert is actionable. It says what is wrong, links to the dashboard and to a short guide (a runbook) for what to check first. An alert that people learn to ignore is worse than none.
    • 

  • Watch the background too. Queue length and failed jobs (Chapter {{n-3}}), disk space, certificate expiry, and the time since the last successful backup.
    • 





{{n}}.7 In Laravel



Everything above exists in Laravel, ready to switch on:


    

  • Structured logs. In config/logging.php, give the stderr channel Monolog’s JsonFormatter and set LOG_CHANNEL=stderr. Log::withContext(['trace' => $id]) in a middleware adds the trace id to every line of the request; the Context facade does the same and also passes it on to queued jobs.
    • 

  • Errors. APP_DEBUG=false, and ->withExceptions() in bootstrap/app.php to report to an error tracker; Sentry has an official Laravel package.
    • 

  • Health. Laravel already answers /up (the health route in bootstrap/app.php); add a readiness route that checks the database and Redis with short timeouts.
    • 

  • Insight. Pulse, Laravel’s free dashboard, shows slow requests, slow queries, failed jobs and busy users from inside the application; Telescope records every request, query and job in development. For Prometheus, community exporters publish the same counters and histograms as this chapter, and OpenTelemetry’s PHP libraries add tracing.
    • 





{{n}}.7 Going further in Node



    

  • Logs. pino writes to standard output; in development, pipe it through pino-pretty for colours. Use request.log in routes so that every line carries the request id, and pino’s redact option to remove fields such as password wherever they appear.
    • 

  • Errors. Sentry and GlitchTip have Node SDKs that hook into Fastify.
    • 

  • Tracing. OpenTelemetry’s Node SDK, with its automatic instrumentation, creates spans for incoming requests, fetch calls, PostgreSQL queries and Redis commands without changing the routes, and propagates traceparent for you.
    • 

  • Metrics. prom-client’s collectDefaultMetrics() adds the process’s memory, CPU and event loop delay, which is the first sign of blocking code (Chapter {{n+1}}).
    • 





Professional habit: debug production from the signals first
When something goes wrong, resist adding console.log or dd() and redeploying. Start from the alert, open the dashboard, find the trace id of a failing request, and read its logs. Each time the signals were not enough to answer the question, add the missing field, metric or span, so that next time they are. Observability is built one incident at a time.

Summary



    

  • Logs say what happened, metrics how much and how fast, traces where one request’s time went.
    • 

  • Structured logs are one JSON object per line, with a level, the service and a trace id, and no secrets.
    • 

  • Errors give the client a title and the trace id; the details go to the log or an error tracker.
    • 

  • The traceparent header carries the trace id between services; OpenTelemetry turns it into full traces.
    • 

  • RED metrics per route: rate, errors and duration as a histogram, read by Prometheus; labels stay low-cardinality.
    • 

  • Liveness and readiness are different checks; alerts follow SLOs and symptoms, each with a runbook.
    • 




Quick check answers: 1. Its fields can be searched and counted by tools (“all errors for order 1001”, “errors per minute by route”), it carries the request’s trace id so it can be joined with the other lines of the same request, and it can leave out personal data such as the email, which the free-text line puts in every copy of the logs. 2. It is the key to the logs: when the customer or the support team quotes it, the team can find every line about that request, across services, without guessing from times and addresses, while the client learns nothing about the code. 3. So that all the lines written about one checkout, in both services, share one id and can be shown together; with separate ids nobody could tell which stock request belonged to which checkout.
