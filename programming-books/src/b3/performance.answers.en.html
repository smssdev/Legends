1. Most requests are fast, so the route itself is not slow in general; one request in a hundred takes nearly a second. Something affects only some requests: a slow query for certain parameters (a big customer, a category without an index), a lock that some requests wait for, a cache miss that recomputes, an occasional call to a slow service, or garbage collection pauses. Start from the traces of the slow requests (Chapter {{n-1}}) and compare them with fast ones: the difference shows where the time goes.
  2. CREATE INDEX ON orders (customer_id, status, created_at). The two equality conditions come first, so that the index narrows straight to one customer’s paid orders; within them the entries are sorted by created_at, so the database reads the last 10 entries (an index can be read backwards for DESC) and stops, without sorting. With created_at first, the index would be ordered by time across all customers, and the conditions would have to be checked entry by entry.
  3. Both readFileSync and JSON.parse run on the event loop: while each of the ten requests reads and parses 50 MB, which takes hundreds of milliseconds, no other request in the process can run, so every route becomes slow at once, and memory spikes as ten copies are held. Fixes: do not parse it per request (parse once at start-up, or keep the data in a database and query what is needed); or move the work off the loop, reading with the asynchronous fs.promises.readFile and parsing in a worker thread, or in a background job that stores the result.About 4096 ÷ 80 ≈ 50 workers, minus a margin for the operating system and the PHP-FPM master: set pm.max_children to about 45. When all 45 are busy, new requests wait in the listen queue of PHP-FPM (and in nginx) until a worker frees up; if the wait is long, they time out with a 502 or 504. More workers than memory allows would be worse: the server would swap and every request would slow down. The real fix for a long queue is to make requests shorter (no waiting on slow calls) or to add servers.
  4. The bottleneck is the database, not the web servers: every web server sends the same expensive queries to the same database, so adding servers only sends it more work at the same time (and more connections). Find the expensive queries (the slow query log, pg_stat_statements, EXPLAIN ANALYZE), fix them with indexes and better queries, remove N+1 patterns, cache what is shared, and only then consider read replicas or a bigger database server.
  5. Measure first: a load test of the page with realistic data, p50/p95/p99, and a trace of one request showing the 12 queries and their times. (1) Do less: combine the queries with eager loading or joins, add indexes for the slow ones, select only the columns shown; measure again. (2) Do later: anything not needed to render the page (view counts, recommendations computed per visit) goes to a background job or is loaded separately. (3) Do once: cache the product data shared by all visitors in Redis with invalidation on change, and set Cache-Control so a CDN can serve the page or its API for a few seconds; measure the hit rate and the latency. (4) Only if the page is still too slow under the target load, add servers, checking the database stays healthy. Each step is kept only if the numbers improved.
