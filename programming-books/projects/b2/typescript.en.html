Practice projects

In each project, write the types first, before any function. Then let the compiler guide you: when it complains, read the message before changing anything. Run npx tsc --noEmit often, and run the file with node file.ts to see the output.

Project {{n}}.1 · Easy

A typed shopping cart

Rewrite a shopping cart in TypeScript, with immutable updates and a coupon, so that the compiler protects every function.

You will practise: object types, readonly, optional properties, default parameters, Record, and ?? with an indexed lookup.

  1. Write three types: Product (with a read-only id), CartLine (a product and a quantity), and Cart (a read-only array of lines and an optional coupon).
  2. Write add(cart, product, quantity = 1): Cart. If the product is already in the cart, return a new cart with that line’s quantity increased; otherwise append a new line.
  3. Keep the coupons in const DISCOUNTS: Record<string, number>.
  4. Write total(cart): number. Because of noUncheckedIndexedAccess, DISCOUNTS[code] may be undefined, so write ?? 0.
  5. Try to break it on purpose: change a product’s id, push into cart.lines, pass a price as a string. Read each error.

Hint: round money to two decimal places only at the end, in total. Rounding at every step adds small errors together.

Project {{n}}.2 · Medium


The life of an order


Model every status an online order goes through as a discriminated union, and write functions that cannot forget a status.


You will practise: discriminated unions, narrowing in a switch, assertNever, and functions that answer questions about a state.


    

  1. Write type OrderStatus with five variants on a kind field: placed, paid (with an amount), shipped (with a tracking number), delivered and cancelled (with a reason). Every variant has an at time.
    2. 

  2. Write describe(status): string with a switch. Use the extra fields only in their own case, and finish with default: return assertNever(status).
    3. 

  3. Write canCancel(status): boolean: only orders that are placed or paid may be cancelled.
    4. 

  4. Print a short history of three statuses, marking the ones that can still be cancelled.
    5. 

  5. Add a sixth variant, returned, and let the compiler show you every place that must change.
    6. 



Hint: step 5 is the point of the whole project. In a real codebase the switch statements may be spread across twenty files; the compiler finds all of them in a second.

Project {{n}}.3 · Challenge


A type-safe event emitter


Take the event emitter from the last chapter and give it types, so that the names of events and the arguments of each one are checked everywhere.


You will practise: generic classes, keyof, indexed access types (Events[E]), mapped types, and labelled tuples.


    

  1. Describe your events as one type, where each key is an event name and each value is a tuple of its arguments: { order: [id: number, total: number]; logout: [] }.
    2. 

  2. Write class Emitter<Events extends Record<string, unknown[]>>.
    3. 

  3. Store listeners in a mapped type: { [E in keyof Events]?: Set<(...args: Events[E]) => void> }. Each event gets a set of functions with exactly its own arguments.
    4. 

  4. Type on and emit with a type parameter E extends keyof Events, so the event name decides the argument types.
    5. 

  5. Check the result with a file of deliberate mistakes: the wrong arguments, a misspelled event, and a listener that expects a string.
    6. 



Hint: notice that the listener (id, total) => … needs no annotations at all: TypeScript infers both types from the event name. Well-typed libraries feel like this: you write less, and the editor knows more.
