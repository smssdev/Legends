Project {{n}}.1 · Easy

Images that fit every screen

Give the hero image two sizes and let the browser choose, and stop the browser from downloading a picture nobody has scrolled to yet. Then prove both with a script.

You will practise: srcset with width descriptors, sizes, loading="lazy", and checking downloads with the Resource Timing API.

  1. List both files in srcset with their real widths: hero-small.png 640w, hero-big.png 1000w.
  2. Tell the browser how wide the image will be shown with sizes: the full screen on phones, 640 px on wider screens.
  3. Keep width, height and alt on the image, as always.
  4. Add a second picture far down the page with loading="lazy".
  5. Write a Playwright script that opens the page as a phone, as a high-density phone and as a desktop, and prints which hero file was used and whether the lower picture was downloaded.

Hint: look at the second line of the result. A phone with a high-density screen needs twice the pixels to look sharp, so the browser correctly picks the bigger file. You describe the facts; the browser makes the choice.










Project {{n}}.2 · Medium


A filter that never freezes


Filter thousands of slow rows while the text field stays perfectly responsive, and show that the list is catching up.


You will practise: finding a long task in the Performance panel, deferring an update, memoising a component, and showing a pending state.


    

  1. Build the slow version first: filter and render directly from the input’s value. Type quickly and feel the input lag.
    2. 

  2. Record it in the Performance panel of DevTools with the CPU slowed 4×. Find the long tasks after each key press.
    3. 


  3. Use useDeferredValue(text) for the list, and wrap the list in memo so it only re-renders when its items change.
    4. 



  4. Keep a second, delayed copy of the text for the list (debounced, as in the state chapter), and compute the filtered items from it.
    5. 


  5. While the list is behind the input, fade it and say “Updating…” in a polite live region.
    6. 

  6. Record again and compare: typing should no longer wait for the list.
    7. 



Hint: deferring does not make the work smaller; it changes its priority. If the list is still too slow when it finally renders, the next step is virtualisation: render only the 20 rows that fit on the screen.








Project {{n}}.3 · Challenge


A bundle budget that fails the build


Measure how much compressed JavaScript and CSS the app sends to users, compare it with a budget, and stop the build when it is over.


You will practise: walking a folder recursively, compressing with node:zlib, and exit codes.


    

  1. Collect every file under the built folder (dist in a real project; here, the book’s shared vendor folder), recursively.
    2. 

  2. For each .js and .css file, add its gzip size: that is what travels over the network.
    3. 

  3. Compare the totals with a budget, and print each line with ✓ or ✗.
    4. 

  4. Set the exit code to 1 when any budget is exceeded, and add the script after vite build in npm run check.
    5. 

  5. Read the result honestly: the shared React bundle alone is far over a 60 KB budget. Decide whether to raise the budget on purpose, or to load less.
    6. 



Hint: a budget that fails is a conversation, not a disaster. The point is that growth becomes a decision someone makes knowingly, instead of something that happens by accident.
