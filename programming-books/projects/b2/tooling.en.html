Practice projects

These projects set up habits rather than features. You will use all three in every project for the rest of this book, so take the time to do them properly in your own Vite project.

Project {{n}}.1 · Easy

A small utility library with a public face

Organise helper functions into modules, and decide which of them the rest of the app may use.

You will practise: named exports, re-exports, a barrel file, and keeping some code internal.

  1. Create a folder modules with text.mjs (slugify and truncate) and numbers.mjs (clamp and percent).
  2. slugify turns a title into a web address: lower case, no spaces at the ends, and every run of other characters becomes one -. The pattern \p{L} means “any letter in any language”, so it works for Arabic too.
  3. Add internal.mjs with a helper used only inside the folder.
  4. Write index.mjs that re-exports the four public functions, and not the internal one.
  5. In app.mjs, import only from ./index.mjs and try each function.

Hint: the barrel is a promise to the rest of the team: “these functions are stable; everything else may change”. Keep it small.

Project {{n}}.2 · Medium


One command to check everything


Give your project a check script that runs the type checker, the linter and the formatter in order, and stops at the first problem.


You will practise: npm scripts, && to chain commands, ESLint rules, and reading which tool failed.


    

  1. Install ESLint, typescript-eslint and Prettier as in section {{n}}.4, resolving the TypeScript version if needed.
    2. 

  2. Add the scripts with npm pkg set: lint, format and check, where check is tsc && eslint src && prettier --check src.
    3. 

  3. Add a file that uses var, and run npm run check. Notice that tsc passed silently and ESLint stopped the chain.
    4. 

  4. Fix the problem and run the check again until it passes.
    5. 

  5. Make it a habit: run npm run check before every git commit.
    6. 



Hint: && runs the next command only if the previous one succeeded. Put the fastest checks first, so you hear about problems sooner. Many teams also run this script automatically with a Git hook.

Project {{n}}.3 · Challenge


Settings for every environment


Use one API address while you develop and another in production, read them in one typed module, and prove which one the build used.


You will practise: .env files, import.meta.env, failing early on missing settings, and inspecting build output.


    

  1. Create .env.development and .env.production, each with a different VITE_API_URL.
    2. 

  2. Write src/config.ts, the only file that reads import.meta.env. If the address is missing, throw an error with a helpful message straight away.
    3. 

  3. Export one read-only config object, and import it wherever the address is needed.
    4. 

  4. Run npm run dev and check the development address in the console. Then build.
    5. 

  5. Search the built JavaScript with grep to confirm that the production address, and only that one, went in.
    6. 



Hint: step 5 is how you prove what is really inside your build. Use the same trick to check that no secret slipped in: if you can find it with grep, so can anyone.
