Practice projects

These projects are about habits more than code. Do each one with another person if you can: a classmate, a colleague, or a friend from an online community. Review and mentoring are learned with someone on the other side.

Project {{n}}.1 · Easy

Review your own old code

Take a project you wrote a few months ago, open a pull request that improves one thing, and review it as if a colleague had written it.

You will practise: small focused pull requests, the review order, labelled comments, and answering every comment.

  1. Choose one improvement only: a function without tests, a confusing name, a missing error state. Make it on a branch, under 100 changed lines.
  2. Fill in the pull request template from this chapter, including how to test it.
  3. Wait a day. Then review the pull request on GitHub in the order purpose, design, correctness, tests, readability, and leave at least five labelled comments, including one praise.
  4. Answer every comment as the author: fix it, open an issue for it, or disagree with a reason.

Hint: reviewing your own code after a day is surprisingly effective, because you have forgotten what you meant and can only read what you wrote. That is exactly the position of every reviewer.

Project {{n}}.2 · Medium

A robot reviewer in CI

Run the chapter’s review robot on every pull request in GitHub Actions, and make it fail the check when it finds a problem.

You will practise: reading diffs, exit codes, GitHub Actions workflows, and required checks.

  1. Copy review-bot.ts into a repository of yours, and make it end with process.exitCode = findings.length ? 1 : 0.
  2. Write .github/workflows/review.yml: on pull_request, check out the code with fetch-depth: 0, run git diff origin/${{ github.base_ref }}...HEAD > pr.diff, then run the robot.
  3. Open a pull request with a console.log in it and check that the robot fails. Remove it and check that it passes.
  4. In the repository settings, make the check required for merging into the main branch.
  5. Add one rule that your own team (or you) keeps forgetting.

Hint: the three dots in main...HEAD matter. They compare against the point where your branch started, so changes merged into main since then are not counted as yours.

Project {{n}}.3 · Challenge

A decision you can defend

Choose between two real libraries for your project with a time-boxed spike and a weighted matrix, write the decision record, and present it in ten minutes.

You will practise: one-way doors, criteria and weights, spikes, sensitivity, and decision records.

  1. Pick a real choice, for example dates (date-fns or the built-in Intl and Temporal), or charts (two chart libraries). Decide whether it is a one-way or two-way door.
  2. Write the criteria and their weights before you try anything. Include bundle size, measured as in Chapter {{n-5}}.
  3. Spend at most half a day per option building the same small screen. Write down surprises as you go.
  4. Score the options in a copy of decide.ts and run the sensitivity check. Find the criterion that would change the winner.
  5. Write the decision record, including the bad consequences of your choice, and present it to someone in ten minutes. Note their questions: each one is something the record should have answered.

Hint: if no weight change can flip the winner, the decision was easy and the matrix was not needed. If many can, the scores are probably guesses: that is the moment for a spike, not a longer meeting.
