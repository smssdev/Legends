Project {{n}}.1 · Easy

A catalogue with real Arabic plurals

Build a small message catalogue and a translate function that picks the right plural form and formats numbers for each language.

You will practise: keys, placeholders, Intl.PluralRules, Intl.NumberFormat, and types derived from the catalogue.

  1. Write the catalogue as one object per language. Plural messages are objects with one text per category.
  2. Give Arabic all six categories (zero, one, two, few, many, other), and English two.
  3. In translate, pick the category with new Intl.PluralRules(locale).select(count), falling back to other.
  4. Replace {name} placeholders with values, formatting numbers with Intl.NumberFormat(locale).
  5. Derive the type of the keys from the English catalogue, so a misspelled key is a compile error.

Hint: “zero” and “one” in Arabic are often whole phrases without a number at all (“لا عناصر”, “عنصر واحد”), which is why each category gets its own full text.








Project {{n}}.2 · Medium


One app, two directions


A cart that switches between English and Arabic at runtime, mirrors its layout, and formats money and plurals correctly in both.


You will practise: a language context, setting lang and dir, logical CSS, flipping directional icons, and <bdi>.


    

  1. Write a provider that keeps the locale, sets document.documentElement.lang and dir in an effect, and provides t and a money formatter.
    2. 

  2. Write all spacing and borders with logical properties, and check that nothing needs a special RTL rule.
    3. 

  3. Flip the arrow icon only, with [dir="rtl"] .next::after { transform: scaleX(-1); }.
    4. 

  4. Wrap product names, which may be in either language, in <bdi>.
    5. 

  5. Switch languages back and forth, and check every line: text, plural, prices, alignment, arrow.
    6. 



Hint: save the chosen language (in localStorage or the address, such as /ar/cart) and start from navigator.languages on the first visit. An address per language is also what search engines need.








Project {{n}}.3 · Challenge


A translation checker


Compare two message catalogues and report keys that are missing, keys that are extra, and messages whose placeholders do not match, so broken translations cannot reach users.


You will practise: reading JSON, regular expressions with matchAll, set-like comparisons, and failing the build.


    

  1. Load en.json (the source of truth) and ar.json.
    2. 

  2. For each English key, report it if Arabic lacks it.
    3. 

  3. Extract the placeholders of both texts with /\{(\w+)\}/g, sort them, and compare. A translator who renamed {total} to {sum} would show an empty value to users.
    4. 

  4. Report Arabic keys that English no longer has: old texts that should be deleted.
    5. 

  5. Set a failing exit code when there is any problem, and add the script to npm run check.
    6. 



Hint: real projects also check plural messages (every category the language needs is present) and keys used in the code but missing from the catalogue. Libraries such as i18next have tools for both.
