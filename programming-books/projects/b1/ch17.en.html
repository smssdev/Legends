Practice projects: upgrade your app

The app is finished, and this is where real development begins: improving something that already works without breaking it. Copy the whole app folder for each project, make a branch in Git, and commit as you go. Each project touches all three files, just like a real feature.

Project 17.1 · Easy

A progress bar

Show how much of the list is done, as a bar and in words, and keep it in step with every change.

You will practise: the <progress> element, adding to render(), and accent-color.

  1. In the HTML, above the list, add <progress id="progress" max="1" value="0"> and a <span id="progress-text">. Link them with aria-labelledby so the bar has a name.
  2. In the CSS, let the bar fill the row with flex: 1, and colour it with accent-color: var(--brand).
  3. In render(), work out done = tasks.length - count, then set the bar’s max and value.
  4. Use tasks.length || 1 for max, so an empty list does not divide by zero.
  5. Write “1 of 3 done” into the span. Tick, untick, add and delete tasks, and check that the bar is always right.

Hint: you did not touch addTask, toggleTask or deleteTask. Because every change ends in render(), one new block there is enough. That is the reward for the structure you built in this chapter.

Project 17.2 · Medium

Edit a task

Typos happen. Let the user fix a task’s text in place: Enter saves, Escape cancels.

You will practise: a new change function, replaceWith, keyboard events, focus() and select().

  1. Add renameTask(id, text) next to the other change functions: find the task, change its text, and call update().
  2. In taskItem, add an “Edit” button with an aria-label that names the task, like the delete button.
  3. Write startEditing(li, task): create an input holding the current text, and swap it in with label.replaceWith(input). Then call focus() and select().
  4. Listen for keydown on the input. On "Enter", save the trimmed text if it is not empty. On "Escape", just call render().
  5. When the input loses focus (blur), call render() too, so a half-edited task never stays on screen.

Hint: section 17.7 suggested double-clicking. A button is better: double-click cannot be done with a keyboard or easily on a phone, and you learned in chapter 16 why that matters.

Project 17.3 · Challenge

English and Arabic in one app

Add a button that switches every text in the app between English and Arabic, flips the layout from left-to-right to right-to-left, and remembers the choice.

You will practise: keeping texts as data, data-* attributes, functions stored in objects, lang and dir, and a second localStorage key.

  1. Create a TEXTS object with an en and an ar part, holding every word the app shows. left is a function, because the Arabic plural changes with the number.
  2. Write a tiny helper, t(key), that returns the text for the current language.
  3. In the HTML, mark each text with its key: <h1 data-text="title">. Add a language button in the header.
  4. Write applyLanguage(): set document.documentElement.lang and dir, fill every [data-text] element, set the placeholder and the labels, then render().
  5. Replace every fixed word in app.js with t(…), then delete the old leftText.
  6. The button switches language, saves it under its own key, and calls applyLanguage(). Reload the page: it should open in the last language you chose.

Hint: because the CSS uses flex and gap, and no fixed “left” or “right”, the whole layout mirrors itself when dir changes. Real apps keep their texts this way, which is how they are translated into many languages without touching the code.
