Graduation projects

These last three projects turn everything you built in this book into something you can show the world. They are not about new code; they are about presenting your work the way professionals do. When you finish them, you will have a portfolio, not just a folder of exercises.

Project 18.1 · Easy

A README that sells your project

Write the page a visitor sees first on GitHub, so that in thirty seconds they know what your app does, can try it, and can see what you learned.

You will practise: Markdown headings, lists, links and images, and writing for a busy reader.

  1. In your tasks app folder, create README.md. GitHub shows it automatically under your files.
  2. Start with the name and one sentence that says what it is and who it is for.
  3. Add the live link from GitHub Pages and a screenshot, saved in the same folder.
  4. List the features in short lines. Mention accessibility and both languages: they make you stand out.
  5. End with “What I learned”, in two or three honest sentences. Recruiters read this part.
  6. Commit, push, and look at your repository page on GitHub.

Hint: write it for someone who will never run your code. Most visitors only read the first screen, so put the link and the screenshot near the top.

Project 18.3 · Challenge


Your own app, from idea to launch


Choose a small problem from your own life, plan an app that solves it, and publish version 1 in about a week, alone.


You will practise: the whole method from chapter 17, deciding what to leave out, and finishing.


    

  1. Write one sentence for the problem and one for who has it. If you cannot, choose another idea.
    2. 

  2. Split the features into “must have” and “nice to have”. Version 1 gets only the first list, three or four items at most.
    3. 

  3. Sketch the screens on paper, and write the data as one JavaScript object.
    4. 

  4. Break the work into daily milestones, each one ending with something that works and a commit.
    5. 

  5. Build it in the order from chapter 17: HTML, then CSS, then JavaScript, then the tests.
    6. 

  6. Publish it, write its README, add it to your portfolio, and send the link to one person who will use it. Their first question is your next feature.
    7. 



Hint: the hardest part of a real project is not the code; it is saying “not now” to good ideas so that you finish. Every professional product you use started as a small version 1.
