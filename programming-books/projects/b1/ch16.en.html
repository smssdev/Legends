Practice projects

For each project, do the keyboard test from section 16.3 before you call it finished: put the mouse away and use only Tab, Shift+Tab, Enter and Space. If you can do everything, and always see where you are, you are on the right track.

Project 16.1 · Easy

Rescue a recipe card

This card looks fine, but a screen reader user, a keyboard user and someone in bright sunlight would all struggle with it. Find five problems and fix them.

You will practise: real buttons, headings and landmarks, alt text, labels, contrast, and the visible focus outline.



    

  1. The title is a div. Make it an h1, so it appears in the screen reader’s list of headings.
    2. 

  2. The image has no alt. Describe what a sighted reader sees, in one short sentence.
    3. 

  3. The search box has only a placeholder, which disappears as soon as you type. Give it a real <label>, and put it in a <form role="search">.
    4. 

  4. “Search” and “Save recipe” are divs: Tab skips them. Turn them into <button> elements.
    5. 

  5. The grey time text (#c4c4c4 on white) has a contrast of about 1.7. Darken it to #4b5563 and check the ratio with the script from section 16.6.
    6. 

  6. Wrap the page in header, main and article, then do the keyboard test.
    7. 



Hint: most accessibility fixes are not extra work. They are simply the right HTML element for the job, which you would have used anyway with a little more care.








Project 16.2 · Medium


A form that explains its errors


When the visitor makes a mistake, tell them what went wrong, where, and how to fix it, in a way that both eyes and screen readers notice.


You will practise: label, autocomplete, aria-describedby, aria-invalid, role="alert", and moving the focus with JavaScript.


    

  1. Build the form with a label for every field, and add novalidate so your script, not the browser, shows the messages.
    2. 

  2. Under each input, add an empty <p class="error">, and link it to the input with aria-describedby. The screen reader will read it with the field.
    3. 

  3. Keep the rules as data: an array of { id, message, ok }, where ok is a small function that tests the value.
    4. 

  4. On submit, check every rule. Write the message, and set aria-invalid="true" on each field that fails.
    5. 

  5. Fill a summary box at the top with a link to each problem, show it, and call summary.focus(). Because it has role="alert", it is announced at once.
    6. 

  6. When everything is correct, hide the summary and show a success message in a role="status" element.
    7. 



Hint: never use colour alone for errors. Here the message has words, the border changes, and the summary repeats it, so people who cannot see red still know what to do.








Project 16.3 · Challenge


An accessible FAQ


Build questions that open and close their answers, and that tell assistive technology whether each one is open.


You will practise: buttons inside headings, aria-expanded, aria-controls, the hidden attribute, and querySelectorAll.


    

  1. For each question write an h2 containing a <button type="button" aria-expanded="false" aria-controls="answer-1">.
    2. 

  2. Below it, put the answer in <div id="answer-1" hidden>. hidden hides it from everyone, screen readers included.
    3. 

  3. Find all the buttons with querySelectorAll and give each a click listener.
    4. 

  4. On click, read aria-expanded, flip it, and set the answer’s hidden to match.
    5. 

  5. Draw the + and − with CSS from the attribute itself: button[aria-expanded="true"]::after. Now the look can never disagree with what the screen reader says.
    6. 

  6. Test it with only the keyboard: Tab to a question, press Enter or Space, and Tab into the open answer.
    7. 



Hint: because you used real buttons, Enter and Space work with no extra code. A div with a click listener would need a dozen lines to copy what <button> gives you free.
