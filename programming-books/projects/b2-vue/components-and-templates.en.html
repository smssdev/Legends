Practice projects

Build each project in a Vite project created with the vue-ts template: npm create vite@latest my-vue -- --template vue-ts. Before writing code, draw the screen on paper and circle the components. Then build from the smallest component upwards.

Project {{n}}.1 · Easy

A profile card

Build a profile card with a slot for the biography, and a follow button that changes the number of followers.

You will practise: typed props, a default slot, exporting a type from a component, ref and computed.

  1. Write a type Person with a name, role, city, number of projects and number of followers. Export it from ProfileCard.vue, so pages can import it with the component.
  2. Show the first letter of the name in a circle, marked aria-hidden="true": the name is already written next to it.
  3. Put a <slot /> under the role and city, so each page can put its own text inside the card.
  4. Add const following = ref(false), and a computed number of followers that adds one while following. Do not change the prop.
  5. Give the button :aria-pressed="following", so screen readers announce whether it is on.

Hint: in the template, @click="following = !following" is enough: Vue unwraps the ref when you assign to it there too. In the script you would write following.value = !following.value.

A catalogue with filters


Show a grid of products with filter buttons for each category and a line that says how many products are visible.


You will practise: lists and keys, a ref typed with a union, a computed filtered list, and buttons with aria-pressed.


    

  1. Reuse products.ts. Create the type Filter = "all" | Product["category"]: it updates itself if a category is added.

  2. Keep the filter buttons as data, an array of { value, label }, and render them with v-for.
    3. 

  3. Store only the chosen filter in a ref. Make visible a computed.
    4. 

  4. Show “Showing 3 of 4 products” using visible.length and products.length.
    5. 

  5. Group the buttons with role="group" and a label, and mark the active one with :aria-pressed.

Hint: a common mistake is to keep visible in a ref too, and then forget to update it when the products change. If a value can be calculated from other state, compute it.








Project {{n}}.3 · Challenge


Accessible tabs


Build a reusable tabs component that works with the mouse, the keyboard and screen readers, in both left-to-right and right-to-left pages.


You will practise: named and dynamic slots, ARIA roles, useId for unique ids, template refs to move the focus, and keyboard events.


    

  1. Make TabList take labels: string[] and a label for the group. The content of each tab comes from a named slot: #tab-0, #tab-1…
    2. 

  2. Render a role="tablist" with one role="tab" button per tab, and one role="tabpanel" per tab, hidden unless active.
    3. 

  3. Link each tab and panel with aria-controls and aria-labelledby. Make the ids with useId(), so two tab lists on one page never clash.
    4. 

  4. Only the active tab is in the Tab order (:tabindex="0"); the others get -1. The arrow keys move between tabs, and Home and End jump to the ends.
    5. 

  5. Collect the buttons with ref="tab" inside the v-for and useTemplateRef("tab"), which gives an array, and call focus() on the new tab. In a right-to-left page, the right arrow moves to the previous tab.
    6. 



Hint: this is the keyboard pattern described in the WAI-ARIA Authoring Practices, the reference for accessible widgets. When you build any widget, look it up there first: the keyboard behaviour users expect is already decided.
