Practice projects

These projects grow the dashboard the way a real one grows: one feature at a time, each meeting the same quality goals. For every project, write the user story first, put the logic in lib/ with a test, keep the screen thin, and run the three checks (unit tests, end-to-end tests, size) before you call it done.

Project {{n}}.1 · Easy

A customers page

A page listing every customer with their number of orders, their total spent and their last order date, sorted by total, with a link to their orders.

You will practise: deriving data with pure functions, a new route and a nav link, Intl formats, and URL state.

  1. Write customers(orders) in lib/: group by customer, ignore cancelled orders in the total, and sort. Test it with four orders from two customers.
  2. Add /customers to the routes and to the side navigation, with texts in both languages in messages.ts.
  3. Make each customer’s name a link to /orders?q=<name>, so the existing search does the rest.
  4. Add the page to the axe test in e2e/admin.spec.ts.

Hint: there is no new request here. The orders are already in the query cache, so useOrders() returns them at once, and the new page costs the server nothing.

Project {{n}}.2 · Medium

Date ranges and a CSV export

Filter the orders by a date range kept in the address, and download exactly the filtered orders as a CSV file that opens correctly in Excel, in Arabic too.

You will practise: extending readFilters safely, date inputs, building files in the browser, and testing pure output.

  1. Add from and to (as YYYY-MM-DD) to Filters. Ignore values that are not valid dates, and test that.
  2. Add two <input type="date"> fields with labels, updating the address with replace.
  3. Write toCsv(orders) in lib/: a header row, one row per order, values with commas or quotes wrapped in quotes and inner quotes doubled. Test it with a customer name that contains a comma.
  4. Download it with a Blob and a temporary link. Start the file with the byte order mark "﻿", or Excel will show Arabic names as nonsense.

Hint: export what the user is looking at, all pages of it, not only the current page. Users expect “export” to mean “these results”.

Project {{n}}.3 · Challenge

From laptop to production

Turn the dashboard into a Vite project with a real CI pipeline, and serve it from a container, ready for a real /api.

You will practise: Vite, GitHub Actions, required checks, Docker, Nginx, and single-page app routing on a server.

  1. Create a Vite Vue project (Chapter 3) and move src/ into it. In development, run the pretend server only when import.meta.env.DEV is true.
  2. Write a workflow that, on every pull request, installs with npm ci, then runs the type checker, the unit tests, the end-to-end tests and the size script, and make all four required.
  3. Write a two-stage Dockerfile: the first stage builds with Node, the second copies dist/ into an Nginx image.
  4. Configure Nginx to send every unknown path to index.html, so /orders/1036 works after a reload, and to forward /api/ to the real server.
  5. Add long cache headers for the hashed files in assets/, and none for index.html.

Hint: the cache rule in the last step is what makes releases safe. Hashed files never change, so they can be cached for a year; index.html must always be fresh, because it is the file that points to the new hashes.
