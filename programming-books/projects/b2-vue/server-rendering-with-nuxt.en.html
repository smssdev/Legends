Practice projects

Run npm run build at the end of every project and read the prerendering lines. Before you build, write down how you expect each address to be made; every surprise is something you can learn from.

Project {{n}}.1 · Easy

A shop that fails gracefully

Give Bit’s shop friendly errors, a loading bar, and a slow part that does not hold the whole page back.

You will practise: error.vue, createError, clearError, <NuxtLoadingIndicator>, and useFetch with lazy.

  1. Make error.vue show a different message for 404 and for everything else, and offer a way home with clearError({ redirect: "/" }).
  2. Make the product API throw a 500 for one id, and check what users see, and which status code curl -I reports.
  3. Add a slow “Reviews” API (1.5 s) and load it on the product page with useFetch(…, { lazy: true }), so the page does not wait for it. Show a small skeleton while status is "pending".
  4. Check with a slow network in the DevTools that the loading bar of <NuxtLoadingIndicator> appears between pages.

Hint: a lazy fetch renders the page on the server without that data, and loads it in the browser. Use it for parts below the fold or that matter less; never for the main content, which search engines need in the HTML.

Project {{n}}.2 · Medium

A static blog that search engines love

A blog whose articles are Markdown files in the project, prerendered at build time, with a title and description per article and a sitemap.

You will practise: reading files in server routes, dynamic pages, useSeoMeta, prerendering, and a server route that returns XML.

  1. Put three articles in server/content/, each starting with a title and a date. Write server/utils/posts.ts that reads them with node:fs/promises.
  2. Add server/api/posts.get.ts and server/api/posts/[slug].get.ts, turning Markdown into HTML on the server with a library such as marked.
  3. Write pages/blog/index.vue and pages/blog/[slug].vue with useFetch, useSeoMeta, and a 404 for unknown slugs.
  4. Add the rule "/blog/**": { prerender: true }. Nitro follows the links from the list and prerenders every article it finds.
  5. Add server/routes/sitemap.xml.ts, which returns the address of every article with the right content-type.

Hint: the Markdown library runs only on the server, so it adds nothing to the browser’s JavaScript. Heavy work belongs in server/; the browser should receive results, not tools.

Project {{n}}.3 · Challenge

Prices an admin can change

A protected admin page where the shop owner changes a product’s price. The cached product pages show the new price soon after, and nobody else can change anything.

You will practise: cookies on the server, route middleware, server routes with permission checks, runtimeConfig, and route rules.

  1. Keep the prices in a server-side Map that a updatePrice(id, price) function can change.
  2. Write server/api/admin/sign-in.post.ts, which compares a password with useRuntimeConfig().adminPassword and, on success, sets an httpOnly, secure, sameSite cookie with setCookie.
  3. Protect the page with a route middleware in app/middleware/admin.ts that redirects to the sign-in page when the cookie is missing, and give the admin pages ssr: false in the route rules.
  4. Write server/api/admin/price.post.ts. It checks the cookie again (the page middleware does not protect the route), validates the price with zod as a positive whole number, and calls updatePrice.
  5. Change a price, then open the product page. Explain why the old price can appear for up to the swr time, and how a shorter time, or no cache for this page, changes that.

Hint: the permission check lives inside every server route, never only in the page that shows the form. A middleware decides what the screen shows; only the server decides what happens.
