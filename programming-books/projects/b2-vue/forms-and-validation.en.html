Practice projects

For each form, write the schema first, with every error message, and test it with safeParse in Node before you build any screen. When the rules are right, the form is mostly wiring.

Project {{n}}.1 · Easy

An accessible contact form

Finish the contact form from this chapter, and make sure every field is labelled, linked to its error, and receives the focus when it is wrong.

You will practise: useForm, a field component with a scoped slot, @blur, and accessibility attributes.

  1. Write the schema and infer the type. Give every rule a message that explains the fix.
  2. Write FormField: a label, a scoped slot for the input, and the error paragraph with an id. Pass id, aria-invalid and aria-describedby through the slot.
  3. Bind each input with v-model and v-bind="attrs", and call blur("name") on @blur.
  4. Try every mistake: leave fields empty, type a short name, a broken email, an age of 9. Check that errors appear only after leaving a field, and disappear as soon as the value is fixed.
  5. Test with a screen reader (VoiceOver, NVDA or TalkBack): submit an empty form and listen. The focus should land on the first field, and its error should be read with its label.

Hint: the focus moves to the first [aria-invalid='true'] element after nextTick, because the attribute only appears once Vue has updated the page. Without the await nextTick(), there would be nothing to focus yet.

Project {{n}}.2 · Medium

Sign up, with an answer from the server

A sign-up form with a password, its confirmation and a terms box, which also shows the server’s “email already used” message on the email field.

You will practise: rules that compare two fields with refine, z.literal(true) for a required checkbox, server errors returned from the submit function, and the submitting state.

  1. Write the schema: an email, a password of at least 8 characters with a digit, a confirmation, and terms: z.literal(true, "…").
  2. Compare the passwords with .refine(…, { path: ["confirm"] }), so the error appears under the confirmation field.
  3. In the submit function, check the full schema, then call a pretend server that answers { email: "…" } for one particular email. Return that object, and useForm shows it under the email field.
  4. Disable the button while submitting is true, so a double click cannot create two accounts.
  5. Give each password input autocomplete="new-password", so password managers offer to create a strong one.

Hint: design your API so that its errors name the field they belong to, as the pretend server does here. Then the frontend can put every server error in the right place with one line of code.
