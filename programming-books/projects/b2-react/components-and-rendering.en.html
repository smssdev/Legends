Practice projects

Build each project in a Vite project created with the react-ts template: npm create vite@latest my-react -- --template react-ts. Before writing code, draw the screen on paper and circle the components. Then build from the smallest component upwards.

Project {{n}}.1 · Easy

A profile card

Build a profile card from four small components, with a follow button that changes the number of followers.

You will practise: typed props, children, splitting a design into components, and one piece of state.

  1. Write a type Person with a name, role, city, number of projects and number of followers.
  2. Build the small parts first: Avatar (the first letter of the name in a circle) and Stat (a number with a label).
  3. Build ProfileCard, which takes a person and children, so each page can put its own text inside the card.
  4. Add const [following, setFollowing] = useState(false). Show one more follower while following; do not change person.
  5. Give the button aria-pressed={following}, so screen readers announce whether it is on.

Hint: the number of followers shown is calculated from the props and the state on every render. You never store it separately, so it can never be wrong. The next chapter calls this “derived state”.

Project {{n}}.2 · Medium

A catalogue with filters

Show a grid of products with filter buttons for each category and a line that says how many products are visible.

You will practise: lists and keys, state typed with a union, deriving a filtered list, and buttons with aria-pressed.

  1. Reuse products.ts. Create the type Filter = "all" | Product["category"]: it updates itself if a category is added.
  2. Keep the filter buttons as data, an array of { value, label }, and render them with map.
  3. Store only the chosen filter in state. Calculate visible from it on every render with filter.
  4. Show “Showing 3 of 4 products” using visible.length and products.length.
  5. Group the buttons with role="group" and a label, and mark the active one with aria-pressed.

Hint: a common mistake is to keep visible in state too, and then forget to update it when the products change. If a value can be calculated from other state, calculate it.

Project {{n}}.3 · Challenge

Accessible tabs

Build a reusable Tabs component that works with the mouse, the keyboard and screen readers, in both left-to-right and right-to-left pages.

You will practise: passing content as data, ARIA roles, useId for unique ids, useRef to move the focus, and keyboard events.

  1. Make Tabs take tabs: { label: string; content: ReactNode }[] and a label for the group.
  2. Render a role="tablist" with one role="tab" button per tab, and one role="tabpanel" per tab, hidden unless active.
  3. Link each tab and panel with aria-controls and aria-labelledby. Make the ids with useId(), so two Tabs on one page never clash.
  4. Only the active tab is in the Tab order (tabIndex={0}); the others get -1. The arrow keys move between tabs, and Home and End jump to the ends.
  5. Keep the buttons in a useRef array, and call focus() on the new tab after the arrow keys. In a right-to-left page, the right arrow moves to the previous tab.

Hint: this is the keyboard pattern described in the WAI-ARIA Authoring Practices, the reference for accessible widgets. When you build any widget, look it up there first: the keyboard behaviour users expect is already decided.
