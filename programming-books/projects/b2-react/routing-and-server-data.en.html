Practice projects

Start each project from the routes, written as data, before any component. If you can read the whole app from the routes array, the design is right.

Project {{n}}.1 · Easy

A small blog with pretty addresses

A list of posts and a page for each post, at addresses like /posts/rules-for-state, with a kind message for posts that do not exist.

You will practise: nested routes, an index route, a route parameter, Link and NavLink, and not-found handling.

  1. Give each post a slug: a short, readable id made from the title, such as keys-explained. Readable addresses are better for users and for search engines.
  2. Write a Layout with the blog’s name, a NavLink to the list, and an Outlet.
  3. The index route shows the list; posts/:slug shows one post.
  4. In PostPage, find the post by useParams().slug. If it does not exist, say so and link back home.
  5. Try a wrong address by hand, such as /posts/nothing, and check the message.

Hint: the data here is a constant, so no query is needed. Not every page needs TanStack Query; use it when the data comes from a server.









Project {{n}}.2 · Medium


A product list you can share


Extend the shop from this chapter so that the category and a search text live in the address, and every combination can be shared as a link.


You will practise: useSearchParams for reading and writing, query keys with several parts, and keeping the address in step with an input.


    

  1. Read category and q from the search parameters. Both may be missing.
    2. 

  2. Put both in the query key: ["products", category, q], and pass both to the API function.
    3. 

  3. Make the search input controlled by the address: its value is q ?? "", and onChange calls setParams with the new text, keeping the category.
    4. 

  4. Pass { replace: true } to setParams while typing, so every letter does not become a new entry in the back button’s history.
    5. 

  5. Open the same address in a new tab and check that you see exactly the same list.
    6. 



Hint: to change one parameter and keep the others, copy them first: const next = new URLSearchParams(params); next.set("q", text); setParams(next, { replace: true });.







Project {{n}}.3 · Challenge


An optimistic favourite button


A heart that fills the moment it is pressed, saves in the background, and quietly puts things back if the server refuses.


You will practise: useMutation, reading and writing the query cache, rolling back with a context value, and invalidating.


    

  1. Load the product with useQuery under the key ["product", id].
    2. 

  2. Create a mutation whose mutationFn calls setFavourite(id, value).
    3. 

  3. In onMutate, cancel queries for the key (so an old answer cannot overwrite you), save the current value with getQueryData, write the new value with setQueryData, and return { previous }.
    4. 

  4. In onError, write context.previous back. In onSettled, invalidate the key, so the screen ends with the server’s truth.
    5. 

  5. Test the failure: the fake API has a server.failNextSave switch. Watch the heart fill, then empty, with a message.
    6. 



Hint: use optimistic updates for small, frequent, reversible actions, such as likes, ticks and reordering. For payments and anything hard to undo, show a clear “Saving…” state and wait for the server instead.
