Practice projects

Run npm run build at the end of every project and read the route table. Before you build, write down the symbol you expect for each address; every surprise in the table is something you can learn from.

Project {{n}}.1 · Easy

A shop that fails gracefully

Give Bit’s shop a page for errors, a better 404 for missing products, and a loading state for each slow part, so that nothing ever shows the user a blank screen or a stack trace.

You will practise: error.tsx, not-found.tsx at different levels, loading.tsx, and <Suspense> around one slow part.

  1. Write app/error.tsx as a Client Component that receives { error, reset }, shows a friendly message, and offers a “Try again” button that calls reset().
  2. Make getProduct throw for one id, and check that only the content area is replaced, while the nav stays.
  3. Add app/products/[id]/not-found.tsx, which says that the product was not found and links back to the list. Unknown addresses elsewhere still use the general 404.
  4. Add a slow “Reviews” part to the product page (await a 1.5 s delay), and wrap it alone in <Suspense> with a small skeleton, so the rest of the page appears at once.

Hint: error.tsx catches errors from the pages below it, not from the layout in the same folder. To catch errors in the root layout too, Next.js has a special global-error.tsx, which must write its own <html> and <body>.

Project {{n}}.2 · Medium

A static blog that search engines love

A blog whose articles are Markdown files in the project, built entirely at build time, with a title and description per article, a sitemap and a robots file.

You will practise: reading files in a Server Component, generateStaticParams, generateMetadata, sitemap.ts and robots.ts.

  1. Put three articles in content/, each starting with a title and a date on its first lines. Write lib/posts.ts with getPosts() and getPost(slug), using node:fs/promises.
  2. Make app/blog/page.tsx list the articles, newest first, and app/blog/[slug]/page.tsx show one. Turn Markdown into HTML with a library such as marked, on the server.
  3. Add generateStaticParams and generateMetadata, and call notFound() for unknown slugs.
  4. Add app/sitemap.ts, which returns the address of every article, and app/robots.ts, which points to the sitemap. Open /sitemap.xml to check.
  5. Build, and check that every article is ○ or ◐ in the route table. Then use curl to check that an article’s title is in the HTML.

Hint: the Markdown library runs only on the server, so it adds nothing to the browser’s JavaScript. That is a quiet advantage of Server Components: heavy libraries for formatting, dates or syntax highlighting are free for your users.

Project {{n}}.3 · Challenge

Prices an admin can change

A protected admin page where the shop owner changes a product’s price. The cached product pages show the new price at once, and nobody else can change anything.

You will practise: cookies, redirect, Server Actions with permission checks, cacheTag and updateTag.

  1. Mark getProducts and getProduct with "use cache" and cacheTag("products"), and keep the prices in a module-level Map that an updatePrice(id, price) function can change.
  2. Write a sign-in Server Action that compares a password with process.env.ADMIN_PASSWORD, and on success sets an httpOnly, secure, sameSite cookie with cookies() from next/headers.
  3. Make app/admin/page.tsx read the cookie and call redirect("/admin/sign-in") if it is missing.
  4. Write the changePrice action. It checks the cookie again (the page check does not protect the action), validates the price with zod as a positive whole number, calls updatePrice, then updateTag("products").
  5. Change a price, open the product page, and check that the new price is there without a new build.

Hint: a real app would keep prices in a database and signed sessions in a library, but the shape is the same: the permission check lives inside every action, never only in the page that shows the form.
