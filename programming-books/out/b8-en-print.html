Before you begin

How to Use This Book

Claude is one family of AI models that reaches you through several doors: a chat app on the web, desktop and phone; Claude Code, an agent that works in your terminal and your repository; and an API that puts the same models inside your own programs. This book teaches all three the way a professional uses them: what each is good at, how to give it the right context, how to check its work, and what it costs. It is written for developers and teams, and it builds on Book 7, AI for Developers, whose habits (give the model what it needs, check what it gives you, measure before you believe) apply here to one family of tools in depth.

What you need

  • Node.js 22 and a code editor, as in the earlier books.
  • For Part I, a Claude account; the free plan is enough for most of it, and the chapters say where a paid plan adds something.
  • For Part II, Claude Code, installed as Chapter 6 shows, with a Claude subscription or an API key.
  • For Part III, nothing more: every example runs against the book’s practice server, described below. A key from the Claude Console is needed only when you want real answers from Claude.

The practice server

Every program in this book calls Claude through the official SDK, @anthropic-ai/sdk, exactly as it would in production. To let you run all of them for free, offline and with no account, the book’s code repository includes a practice server: a small local program that speaks the API’s format (requests, responses, streaming events, tool calls, errors, token usage) and answers from a file in each chapter, practice.json.

Read this before any example

The practice server is not Claude. Its answers were written for this book, to show what each part of a response looks like and how a program should handle it. When a transcript in this book shows an answer, it is the practice server’s, and the chapter says so. The field names, the streaming events, the kinds of error and their status codes, and the code are real; the words of the answers, and of the error messages, are the practice server’s, and its token counts are an approximation (about four characters per token). To see what Claude really answers, run the same code against the real API with your own key: Claude’s words will differ, and you should check them the way Book 7 taught.

Switching between the two is a matter of two environment variables, which the SDK reads by itself:

node practice/server.mjs &                       # the practice server, on port 4141
export ANTHROPIC_BASE_URL=http://127.0.0.1:4141    # talk to it
export ANTHROPIC_API_KEY=test-key                  # its only key

unset ANTHROPIC_BASE_URL                           # the real API instead
export ANTHROPIC_API_KEY=sk-ant-...                # your own key, never in code

Chapter 1

Meet Claude: Models, Strengths and Limits

In this chapter you will learn to

  • tell apart the ways Claude reaches you: the apps, Claude Code and the API
  • choose between the Claude models by task, speed and price
  • send a first message from code and read everything that comes back
  • work out what a request costs before you send a thousand of them
  • name Claude’s limits, and recognise the errors a first program meets

Claude is a family of AI models made by Anthropic. The same models answer you in the chat app, edit your repository through Claude Code, and run inside your programs through the API. This chapter introduces the family: which models exist and how they differ, what a request and a response look like, what they cost, and what Claude cannot do however well you ask. Everything after this chapter builds on it.

Bit

Every answer from “Claude” in this chapter comes from the book’s practice server, not from Claude: the preface explains why. The prices, the limits, the errors and the code are real, and the arithmetic in this chapter is exact.

1.1 One family, three doors

DoorWhat it isBest forPart
Claude appsChat on the web (claude.ai), on the desktop and on phones, with files, projects, artifacts, research and connectorsThinking, writing, analysis and one-off tasks, alone or as a teamI
Claude CodeAn agent that reads, edits and runs code in your terminal, your editor or the cloudWork inside a repository: features, fixes, refactors, reviewsII
The Claude APIAn HTTP API and official SDKs, also offered through Amazon Bedrock, Google Cloud and Microsoft FoundryPutting Claude inside your own productIII

The doors share the models but not the setup around them. The apps add a system prompt, tools and memory features that Anthropic maintains; Claude Code adds tools for files and commands, and permissions; the API adds nothing: you get the model, and every instruction, tool and check is yours to write. That is why the same question can get a different answer in each place, and why Part III spends so much time on what the apps do for you.

1.2 The models

Claude models come in tiers, named for size and speed, and each tier gets new versions. In November 2026 the current ones are:

ModelIdUse it forInput / output, $ per million tokens
Claude Fable 5.2claude-fable-5-2The hardest reasoning and long-running agent work8 / 40
Claude Opus 5.5claude-opus-5-5Complex coding and knowledge work; the default choice4 / 20

for await (const model of client.models.list()) {
  const input = (model.max_input_tokens / 1000).toLocaleString("en-US");
  console.log(`${model.id.padEnd(18)} ${model.display_name.padEnd(18)} input ${input}K, output ${model.max_tokens / 1000}K`);
}

Did you know?

A token is the unit models read and write: a short word, part of a longer word, a punctuation mark. In English a token is about four characters on average; Arabic and code usually take more tokens for the same length. Prices and limits are counted in tokens, and the API counts them exactly for you (Chapter 15).

1.3 A first message

Install the SDK in a new project, start the practice server from the book’s repository, and point the SDK at it with the two variables from the preface:

npm install @anthropic-ai/sdk@1.8.0
node practice/server.mjs &
export ANTHROPIC_BASE_URL=http://127.0.0.1:4141 ANTHROPIC_API_KEY=test-key

Then a program of a few lines:

hello.mjs (part)
const question = process.argv[2] ?? "Introduce yourself in three sentences.";
const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 1000,
  messages: [{role: "user", content: question}],
});
for (const block of response.content) {
  if (block.type === "text") console.log(block.text);
}
const {input_tokens, output_tokens} = response.usage;
const dollars = cost(response.model, response.usage).toFixed(6);
console.log(`--- stop: ${response.stop_reason}; ` +
  `tokens: ${input_tokens} in, ${output_tokens} out; cost: $${dollars}`);
Terminal
$ node hello.mjs
I'm Claude, an AI model made by Anthropic. I can read and write text and code, look at images and documents, and use tools that you give me. I don't remember earlier conversations unless you send them again, and I can be wrong, so check what matters.
--- stop: end_turn; tokens: 19 in, 70 out; cost: $0.001476

The answer is the practice server’s, written to sound like Claude introducing itself; Claude’s own words will differ. What matters is the shape, which is the API’s. A request names the model, the max_tokens the answer may use, and the messages so far, starting with the user’s. The response’s content is a list of blocks, not a string: here a single text block, but later chapters meet thinking blocks, tool calls and citations, so code always looks at each block’s type. stop_reason says why the answer ended: end_turn means Claude finished, max_tokens means it was cut off, and other values (a tool call, a refusal) mean the program has work to do. And usage counts the tokens, from which the program works out the cost.

Watch out

Never write an API key in code, and never commit one. The SDK reads ANTHROPIC_API_KEY from the environment, so the code above works with the practice server and with the real API without a change. A key in a repository is a key anyone can spend on.

1.4 What it costs

Every request is priced by its tokens: input at one rate, output at a higher one (five times higher for every current model), and two more rates for prompt caching, which Chapter 15 covers. The calculation is short enough to keep next to your code:

lib/prices.mjs (part)
export function cost(model, usage) {
  const p = PRICES[model];
  const written = usage.cache_creation_input_tokens ?? 0;
  const read = usage.cache_read_input_tokens ?? 0;
  const dollars = usage.input_tokens * p.input + usage.output_tokens * p.output +
    written * p.input * 1.25 + read * p.cacheRead;
  return dollars / 1_000_000;
}
Terminal
$ node prices.mjs
claude-fable-5-2   $0.03600 each, $36.00 per thousand
claude-opus-5-5    $0.01800 each, $18.00 per thousand
claude-sonnet-5-5  $0.00900 each, $9.00 per thousand
claude-haiku-5-5   $0.00045 each, $0.45 per thousand
claude-opus-5-5, cached prompt: $0.01116 each

The same request, 2,000 tokens in and 500 out, costs eighty times more on the most capable model than on the fastest. A thousand of them costs $36 on Claude Fable 5.2 and 45 cents on Claude Haiku 5.5. And caching most of the prompt, as in the last line, cuts the Opus request by more than a third, because input read from the cache costs a twentieth of its usual price on Claude Opus 5.5. Neither number says which model to use: a cheap model that gets a task wrong costs more than an expensive one that gets it right, which is why Chapter 16 measures before it chooses.

Tip

Start with Claude Opus 5.5, the default, until the feature works and you have a way to measure it; then try the smaller models on the same measurement. Moving down to Sonnet or Haiku is often possible for a well-defined task; you only know when you measure.

Quick check

  1. Why should a program ask the API for its models instead of keeping a list?
  2. Why is a response’s content a list of blocks rather than a string?
  3. The same request costs $0.018 on Opus 5.5. What does it cost on Sonnet 5.5, and why exactly half?

The answers are at the end of the chapter, after the summary.

1.5 Strengths and limits

Claude reads quickly and widely: a long contract, a codebase, a spreadsheet, a screenshot. It writes clearly in many languages, Arabic and English included. It reasons through problems in steps, thinking before it answers when the task needs it. It writes and reviews code well enough that Part II is a whole part. And it uses tools: given a function to call, it decides when to call it and what to pass, which is how it searches, runs code and acts in your systems (Chapter 12).

Its limits are the same in kind as every model of Book 7, and they decide how you design around it:

  • Its knowledge stops at a date. Ask about today’s news and the honest answer is the one below: it does not know. Recent facts must come from you, from a search tool, or from your documents.
  • The API remembers nothing. Each request is complete in itself: to continue a conversation, you send it all again. The apps keep history and memory for you; your programs must do it themselves (Chapter 11).
  • It can be wrong, fluently. Better models are wrong less often, not never. Everything Book 7 taught about checking applies here.
  • It may decline. Some requests are refused for safety, with stop_reason set to refusal. A program handles that like any other outcome (Chapter 16).
  • Its context is large but finite, and what you put in it costs money and attention: a million tokens is a capacity, not a target.
Terminal
$ node hello.mjs "What happened in the news today?"
I can't know that: I have no access to the news, and my knowledge stops at my training cutoff. Give me the articles, or use a tool such as web search, and I can summarise them.
--- stop: end_turn; tokens: 17 in, 51 out; cost: $0.001088

The practice server’s answer here was written to show the right behaviour: say what cannot be known, and say what would help. Check that the real model behaves like this for the questions your users ask; when it does not, that is what search tools and your own documents are for.

1.6 Thinking and effort

Current Claude models think before they answer when a problem needs it, and decide for themselves how much: this is adaptive thinking. You control the depth with effort, from low to max, set in output_config. Low effort is faster and cheaper, for simple tasks and chat; high effort is for hard problems, where thinking longer pays off. On Claude Opus 5.5 the default is medium, and thinking cannot be turned off: effort is the only control. A first program discovers this, and two other rules, the way everyone does:

errors.mjs (part)
const attempts = [
  ["a misspelled model", {...ask, model: "claude-opus-55"}],
  ["no max_tokens", {model: "claude-opus-5-5", messages: ask.messages}],
  ["thinking turned off", {...ask, model: "claude-opus-5-5", thinking: {type: "disabled"}}],
];
Terminal
$ node errors.mjs
a misspelled model: 404 NotFoundError
  model: claude-opus-55
no max_tokens: 400 BadRequestError
  max_tokens: Field required
thinking turned off: 400 BadRequestError
  thinking: type "disabled" is not supported for this model; use "adaptive" or omit it

Three different errors, each with a status and a message that names the problem. A model id with a typo is a 404, not found; a request without max_tokens is a 400, invalid; and asking Claude Opus 5.5 to stop thinking is a 400 too. Read the message before changing the code: the API almost always says which field is wrong.

Professional habit

Keep the model id, the effort and max_tokens in one place in your configuration, not scattered through the code. Models change every few months, and the team that can switch, measure and switch back in an afternoon will always use the best model for the price.

Summary

  • One family of models reaches you through the apps, Claude Code and the API; each door adds different things around the same models.
  • Fable, Opus, Sonnet and Haiku trade capability for speed and price; ask the API which models exist and their limits.
  • A response is a list of typed blocks, with a stop_reason and a usage that every program should read.
  • Cost is tokens times price, with output dearer than input and cached input much cheaper; calculate it before you scale.
  • Claude’s knowledge ends at a date, the API remembers nothing, and answers can be wrong or refused: design for all four.

Quick check answers: 1. Because the list changes with every release and differs between accounts and platforms; the API always knows what your key can use and each model’s limits. 2. Because a response can contain more than text: thinking, tool calls, and text split around citations; a list of typed blocks holds them all, in order. 3. $0.009, because both Sonnet prices ($2 in, $10 out) are exactly half of Opus’s ($4 and $20), so any mix of tokens costs half.

Practice projects

The projects are three small tools every team that uses the API ends up writing: a first choice of model, a budget, and error messages that say what to do.

Project 1.1 · Easy

A first choice of model

Suggest a model from three questions about a task: is it hard, is it long-running, is it high-volume?

You will practise: turning a rule of thumb into code you can argue with.

  1. Write the three questions as booleans.
  2. Map them to a model, from Haiku for volume to Fable for long, hard work.
  3. Print the suggestion for four tasks.
choose.mjs (part)
export function chooseModel({hard, longRunning, highVolume}) {
  if (highVolume && !hard) return "claude-haiku-5-5";
  if (hard && longRunning) return "claude-fable-5-2";
  if (hard) return "claude-opus-5-5";
  return "claude-sonnet-5-5";
}

Your result should look like this:

Terminal
$ node choose.mjs
classify support tickets               claude-haiku-5-5
answer customers in a chat             claude-sonnet-5-5
refactor a large codebase              claude-opus-5-5
plan a migration with many unknowns    claude-fable-5-2

Hint: this is a starting point, not a decision. The decision comes from measuring the suggested model and the one below it on real examples of the task, as Chapter 16 does.

Project 1.2 · Medium

A monthly budget

Estimate what a feature costs a month on three models, with and without caching.

You will practise: cost as a design input, before the first line of the feature.

  1. Describe the feature: requests a day, tokens in and out.
  2. Price a month on each model with cost.
  3. Price it again with 80% of the input read from the cache.
budget.mjs (part)
function monthly({model, perDay, input, output, cachedShare = 0}) {
  const cached = Math.round(input * cachedShare);
  const usage = {input_tokens: input - cached, cache_read_input_tokens: cached, output_tokens: output};
  return cost(model, usage) * perDay * 30;
}

Your result should look like this:

Terminal
$ node budget.mjs
ticket summaries: 5,000 a day, 3,000 tokens in, 300 out
  claude-opus-5-5    $ 2700.00 a month; with 80% cached $ 1332.00
  claude-sonnet-5-5  $ 1350.00 a month; with 80% cached $  666.00
  claude-haiku-5-5   $   67.50 a month; with 80% cached $   35.10

Hint: the range is wide: $35 to $2,700 for the same feature. Caching halves every model’s bill here, because most of the cost is the long input. Run this before the meeting where someone asks what the feature will cost.

Project 1.3 · Challenge

Errors that say what to do

Turn every kind of API error into one sentence that tells a developer what to fix.

You will practise: the SDK’s typed errors, checked from the most specific to the most general.

  1. Write one sentence for each error class.
  2. Check instanceof from specific to general, and rethrow what you do not know.
  3. Provoke three errors: a wrong model, a wrong key, and no server.
handle.mjs (part)
export function advice(error) {
  if (error instanceof Anthropic.APIConnectionError) return "No connection: check the network and ANTHROPIC_BASE_URL.";
  if (error instanceof Anthropic.AuthenticationError) return "Check ANTHROPIC_API_KEY: missing, mistyped or revoked.";
  if (error instanceof Anthropic.NotFoundError) return "Check the model name against GET /v1/models.";
  if (error instanceof Anthropic.RateLimitError) return "Too many requests: wait as long as retry-after says, then retry.";
  if (error instanceof Anthropic.BadRequestError) return "Fix the request: read the message, it names the field.";
  if (error instanceof Anthropic.InternalServerError) return "A problem on the API's side: retry with backoff.";
  throw error;
}

Your result should look like this:

Terminal
$ node handle.mjs
NotFoundError        Check the model name against GET /v1/models.
AuthenticationError  Check ANTHROPIC_API_KEY: missing, mistyped or revoked.
APIConnectionError   No connection: check the network and ANTHROPIC_BASE_URL.

Hint: order matters because the classes form a hierarchy: NotFoundError and RateLimitError are both APIErrors, so a broad check first would hide them. And never match on the message text: the classes and the status are the stable contract.

Chapter 2

Conversations, Files and Images

In this chapter you will learn to

  • open a conversation with what Claude needs, and steer it when the answer is off
  • know when to continue, when to edit, and when to start a new chat
  • see what “the conversation” really is underneath, and why long ones cost more
  • give Claude PDFs, documents and images, and check what it reads from them
  • keep private data out of places it should not go

Most people meet Claude in a chat window, and most of what they get from it depends on how they talk to it. This chapter is about using that window well: how to start, how to steer, how to bring in your files and screenshots, and how to know when a conversation has run its course. It also opens the window to look inside, with a few lines of code, because knowing what the app does for you explains most of its behaviour.

Bit

The answers in this chapter’s transcripts are the practice server’s. The images and the PDFs are real files, made by the chapter’s script; the shapes of the requests, the token accounting and the error are the API’s.

2.1 A good first message

A chat with Claude is a conversation with a capable colleague who has just walked in: well read, quick, and knowing nothing about your situation. The first message decides most of what follows. A good one carries four things:

PartWeakStrong
Context“Write a menu description.”“I run a small café in Cairo; most customers are students.”
The task“Make it good.”“Describe our new rose latte in two sentences for the menu board.”
The form(nothing)“Warm, simple English; no more than 30 words; no exclamation marks.”
An example(nothing)“Here is how we describe our honey cappuccino: …”

None of this is new: it is Book 7’s Chapter 3, applied to a chat. What is new is the window itself, which gives you three ways to steer when an answer misses:

  • Continue when the answer is on the right track: “shorter”, “more formal”, “now the Arabic version”. Each reply builds on everything above it.
  • Edit your message when the answer went wrong because of how you asked. The conversation branches from there, and the wrong turn no longer sits in the history, pulling later answers toward it.
  • Start a new chat when the topic changes. An old conversation about last month’s budget is not context for today’s job advert; it is noise, and, as Section 2.2 shows, it is paid for on every turn.

Tip

When a long chat has produced something you want to keep (a plan, a set of decisions), ask Claude to summarise it in a few lines, and start the next chat with that summary. You keep the conclusions and drop the hundred messages that led to them.

2.2 What the conversation really is

Claude does not remember the chat between your messages. Each time you press send, the app sends the whole conversation again, every message from the first, and the model reads it from the top before writing the next reply. Three lines of code show it, using the API of Chapter 1:

chat.mjs (part)
for (const question of turns) {
  messages.push({role: "user", content: question});
  const response = await client.messages.create({
    model: "claude-opus-5-5",
    max_tokens: 1000,
    messages,
  });
  messages.push({role: "assistant", content: response.content});
  const used = response.usage.input_tokens;
  console.log(`> ${question}\n${text(response)}`);
  console.log(`  (turn ${messages.length / 2}: ${used} tokens in)`);
}
Terminal
$ node chat.mjs
> My name is Mona and I run a café.
Nice to meet you, Mona! A café is a lovely thing to run. How can I help?
  (turn 1: 18 tokens in)
> Suggest a name for a new drink.
Since it's for your café: "Bit Bloom" (a rose latte), "Nile Breeze" (iced mint tea) or "Mona's Morning" (a honey cappuccino).
  (turn 2: 66 tokens in)
> What is my name?
Your name is Mona, and you run a café.
  (turn 3: 125 tokens in)

Claude knew the name in the third turn because the program sent the first turn again with it. Look at the token counts: 18, then 66, then 125. Every turn pays for everything before it, so a conversation’s cost grows faster than its length. Send the same question without the history, and the knowledge is gone:

Terminal
$ node forget.mjs
I don't know your name: this is the start of our conversation, and you haven't told me yet.

The apps add features on top of this: in some plans and settings Claude can search or remember earlier chats, and a project (Chapter 3) gives every chat in it the same documents and instructions. But the core is always the same: the model sees what is sent, and only that. When Claude “forgets” something from early in a very long chat, or contradicts it, it is usually because that part is far back in a long text, competing with everything after it.

Watch out

Long conversations get slower, cost more, and can drift: an early mistake that was never corrected keeps being read on every turn. If a chat has gone wrong for several turns, do not argue with it; start again with a better first message.

2.3 Files

You can attach documents to a message: PDFs, Word files, spreadsheets, text and code. For a PDF, Claude receives both the text and an image of each page, so it can read tables, charts and layout as well as words. Underneath, a PDF is a document block placed before the question:

lib/files.mjs (part)
export function block(file, title) {
  const data = fs.readFileSync(file).toString("base64");
  if (file.endsWith(".pdf")) {
    const source = {type: "base64", media_type: "application/pdf", data};
    return {type: "document", source, title};
  }
  const source = {type: "base64", media_type: TYPES[path.extname(file)], data};
  return {type: "image", source};
}
pdf.mjs (part)
const question = "What are the obligations of the Buyer? Name the clause and page of each.";

// A PDF is a document block: Claude reads its text and its pages.
const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 1000,
  messages: [{role: "user", content: [
    block("files/contract.pdf"),
    {type: "text", text: question},
  ]}],
});
Terminal
$ node pdf.mjs
The Buyer must pay within 30 days of each delivery (clause 2, page 1); late payment costs 2% a month (clause 3, page 1); and ending the agreement needs 60 days' written notice (clause 4, page 2).
--- 3034 tokens in

The contract is two short pages, made by the chapter’s script, and the question asks for the clause and page of every obligation. That one instruction is what makes the answer checkable: you can open page 2 and read clause 4 yourself. Notice the tokens too: about three thousand for two short pages, because each page is also read as an image. A hundred-page report is a large request, and it is sent again on every turn of the conversation.

Tip

Ask for references whenever an answer comes from a document: the clause, the page, the row, the exact quotation. An answer you can check in ten seconds is worth more than a fluent one you have to take on trust. Chapter 12 shows the API’s citations, which return the exact passage with each claim.

2.4 Images

Claude reads images: screenshots of an error, a photo of a whiteboard, a chart, a receipt, a hand-drawn sketch of a screen. An image is a content block, like a document:

image.mjs (part)
const question = "What does this chart show? Give the numbers.";

// An image is a content block, sent next to the question.
const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 1000,
  messages: [{role: "user", content: [
    block("files/sales.png"),
    {type: "text", text: question},
  ]}],
});
Terminal
$ node image.mjs
Cups sold per month at Bit Cafe in the first half of 2026: 410 in January, 380 in February, 455 in March, 520 in April, 610 in May and 590 in June. Sales dipped in February, then grew for three months to a peak in May, with a small fall in June.
--- 369 tokens in

The chart is real: six bars with their values printed above them, made by the chapter’s script from the numbers 410, 380, 455, 520, 610 and 590. The practice server’s answer reads them all correctly; a real model usually does too when the numbers are printed, and is less reliable when it must estimate a bar’s height against an axis, read small print, or count many similar objects. Treat numbers read from an image as a draft: when they matter, compare them with the source, or ask for the data itself.

An image block must say what it is, and be it. Send a PNG labelled as a JPEG and the request fails before any model sees it:

Terminal
$ node mime.mjs
400 BadRequestError: messages.0.content.0.source: the image data is image/png, but media_type says image/jpeg

2.5 What you share

Everything you attach is sent to Anthropic to be processed, like everything you type. Before you upload a contract, a customer list or a screenshot of a dashboard, ask the same question you would before emailing it to an outside consultant: am I allowed to share this, and with whom? Your company may have a policy, and a business or enterprise plan may be the only approved way to use Claude with company data. Check your plan’s privacy settings, including whether your chats may be used to improve the models, and choose deliberately. And remove what the task does not need: Claude can summarise a complaint without the customer’s phone number (Book 7, Chapter 15).

Professional habit

Before you attach a file, look at it the way a stranger would. Screenshots in particular carry more than you mean to share: an open tab, a name in a corner, a token in a URL. Crop first.

Common mistakes

MistakeWhat happensFix
A first message with no contextGeneric answers that fit anyoneSay who, what for, in what form, with an example

One endless chat for everythingSlower, dearer, more confused answersA new chat per topic; carry a summary

Summary

  • A good first message gives context, the task, the form and an example; steer by continuing, editing or starting fresh.
  • The conversation is resent in full on every turn: that is how Claude “remembers”, and why long chats cost more and drift.
  • Documents and images are content blocks; PDFs are read as text and as page images.
  • Ask for references with every answer from a document, and check numbers read from images.
  • Share only what you are allowed to share, and only what the task needs.

Quick check answers: 1. Because chat.mjs sent the earlier turns again, including “My name is Mona”, while forget.mjs sent only the question; the model knows only what is in the request. 2. Because each turn resends all the earlier turns: the third request contains the first two questions and both answers as well as its own. 3. Checking: with the clause and page named, a person can verify each obligation in seconds instead of trusting the summary.

Project 2.2 · Medium

Keep a conversation within a budget

Drop the oldest turns of a history until it fits a token budget, measured with the token-counting endpoint.

You will practise: countTokens, and the cost of forgetting.

  1. Count the tokens of the whole history.
  2. While it is over budget, drop the oldest question and its answer.
  3. Try three budgets, and see what is left.
trim.mjs (part)
export async function trim(messages, budget) {
  let kept = [...messages];
  for (;;) {
    const counted = await client.messages.countTokens({model, messages: kept});
    const size = counted.input_tokens;
    if (size <= budget || kept.length <= 1) return {kept, size};
    kept = kept.slice(2); // one user turn and its answer
  }
}

Your result should look like this:

Terminal
$ node trim.mjs
budget 1000: kept 13 of 13 messages, 952 tokens
budget  400: kept 5 of 13 messages, 327 tokens
budget  150: kept 1 of 13 messages, 15 tokens

Hint: at the smallest budget only the last question survives: whatever the user said first, their name, their café, is gone. Trimming is cheap and forgetful. The better tool for long conversations keeps a summary of what was dropped, or uses the API’s compaction, which does that for you (Chapter 14).

Appendix

Answers to the Exercises

Try every exercise yourself before you look here. When your answer differs from this one, that is not necessarily wrong: most problems have several good solutions. If yours handles normal and unusual cases, and you can explain your choices, it is a good answer. The full, tested code for every answer is in the book’s code repository.

Chapter 1

  1. Print response.model, response.id and the cost from cost(response.model, response.usage). A reply in practice.json is an object with a when (words the question must contain) and a text; put it before any reply that would also match, because the first match wins. The id is worth logging in real programs: it is what Anthropic’s support asks for when you report a problem.
  2. The stop_reason is max_tokens, and the text stops in the middle of a sentence. A program must not treat it as a complete answer: show it as cut off, ask again with a larger max_tokens, or ask for a shorter answer in the prompt. Silent truncation is one of the most common bugs in programs that call a model.
  3. Nothing changes with the practice server: it does not think, and it ignores effort. With the real API, low effort usually means less thinking, fewer tokens, a faster and cheaper answer, and for a simple question the same answer. The difference shows on hard questions, which is why effort is chosen per task and measured, not set once for everything.
  4. Add a batch option that halves the cost, and print a fourth column. Good candidates are work nobody waits for: nightly summaries of tickets, tagging a backlog, translating documentation, running an evaluation set. A chat with a customer is not one: the customer is waiting.
  5. List the models with client.models.list(), send the same request to each in turn, and print the text, usage and cost for each, catching errors so that one model that fails does not stop the others. Against the practice server, every model gives the same scripted answer and the token counts are approximations, so only the costs differ. The comparison means something only with real answers, and even then a single question is an anecdote: compare models on a set of questions with known good answers, as Book 7 did.

Chapter 2

  1. The rewritten message usually gets an answer that needs fewer follow-ups: it fits your audience, your length and your tone the first time. If both answers are equally good, the task was simple enough that context did not matter; the habit pays off on the tasks where it does.
  2. Add the input_tokens and output_tokens of each turn to a running total. A conversation of 30 turns of the same size does not cost ten times one of three, because turn 30 resends turns 1 to 29: the input grows with each turn, so the total grows roughly with the square of the number of turns. Ten times the turns is nearly eighty times the input tokens (1 + 2 + … + 30 = 465 turns’ worth, against 1 + 2 + 3 = 6).
  3. Anthropic’s guidance is to put images and documents before the question, so that the model reads the material first and then what to do with it. Placed after, the model reads the question without the thing it asks about; it usually still answers well, but the habit costs nothing and is followed in every example of this book.
  4. Keep messages[0] and drop two messages at a time from index 1: kept = [kept[0], ...kept.slice(3)]. The pair dropped is an answer and the question after it, so what remains still starts with the user’s first message and still alternates: user, assistant, user. Whatever you drop, keep that rule true: the first message is the user’s, and roles alternate.
  5. Keep messages; after each turn, print the cost from usage; when countTokens passes the budget, send the oldest half to Claude with “summarise this conversation in five lines, keeping names, numbers and decisions”, and replace that half with one user message containing the summary and one assistant message acknowledging it. With the practice server, add a reply for the summary request so the logic can be tested end to end; the quality of real summaries is something to check against the real API.
