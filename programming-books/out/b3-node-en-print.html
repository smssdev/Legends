Chapter 1

How Servers Work: HTTP in Depth

In this chapter you will learn to

  • follow a request from a URL to a response: name lookup, connection, request, answer
  • read and write HTTP by hand, because it is plain text
  • choose the right method and status code, and know which requests are safe to repeat
  • use the headers that matter: content type and length, caching with ETags, CORS
  • inspect any API with curl, the backend developer’s most used tool
  • build a small JSON API with no framework, so that you know what every framework does for you

Every backend you will ever build, whatever the language or framework, does the same job: it waits for a message, works out what was asked, and sends a message back. The messages follow a protocol called HTTP. Frameworks hide it behind routes and controllers, which is useful until something goes wrong: a request that works in curl but not in the browser, a cache that never updates, a client that retries and charges a customer twice. Then you need to know what is really on the wire. This chapter shows it to you, byte by byte, with a small server we write ourselves.

Bit

The first API I wrote worked perfectly, as long as I was the only one calling it. Then a browser called it from another address, and nothing worked. I lost a day to a problem that two headers solved. Since then I read the raw request first, and guess second.

1.1 From a URL to an answer

When a web app in Bit’s shop asks for http://localhost:3000/products/2, four things happen, in this order:

  1. Name lookup. Computers talk to addresses, not names. The client asks the Domain Name System (DNS) for the address of the host (here localhost, which always means “this same computer”, at 127.0.0.1). For a real site such as shop.example, a DNS server somewhere on the internet answers.
  2. Connection. The client opens a TCP connection to that address and a port, a number that picks one program on the machine. Our server listens on port 3000. TCP makes sure that bytes arrive complete and in order.
  3. Security, for HTTPS. With https://, the two sides first agree on encryption keys (the TLS handshake), and the server proves who it is with a certificate. Everything after that is encrypted. The HTTP inside is the same.
  4. Request and response. The client sends an HTTP request as text; the server sends back a response. The connection may then stay open for the next request.

Everything in this chapter happens on your own computer, so you can see every step without a network in the way. We need a server to talk to. The book’s code folder has one for this chapter, a small API for Bit’s shop, with no framework at all. Start it in a terminal and leave that terminal open:

Terminal 1
# Start the server (and leave it running in this terminal)
$ node server.ts
Listening on http://localhost:3000

Node 22.18 and later run TypeScript files directly: they remove the types and run what is left. We will read the whole server in Section 1.9. First, we look at it from the outside, the way every client does.

1.2 HTTP is text

HTTP/1.1, the version every server understands, is plain text sent over the TCP connection. You can type a request yourself. The nc (netcat) tool opens a TCP connection and passes through whatever you give it; printf writes the request, with \r\n at the end of each line, as the protocol requires. Open a second terminal:

Terminal 2
# Type a request by hand: HTTP/1.1 is plain text over a TCP connection
$ printf 'GET /products/1 HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc localhost 3000
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 41
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: close

{"id":1,"name":"Robot kit","price":45000}

That is all an HTTP exchange is. Both messages have the same shape:

  1. A first line. In the request, the request line: the method (GET), the target (/products/1) and the version. In the response, the status line: the version, a status code (200) and a short reason (OK).
  2. Headers, one per line, Name: value. Names are not case sensitive: content-type and Content-Type are the same header.
  3. An empty line. It says “the headers end here”. Forget it, and the server waits for more headers forever.
  4. The body, if there is one. The receiver knows where it ends from Content-Length: here, 41 bytes.

Our request had two headers. Host is required in HTTP/1.1, because one machine with one address often serves many sites, and the server needs to know which one you mean. Connection: close asks the server to close the connection after answering, so that nc stops; we will come back to connections in Section 1.7.

Typing requests by hand teaches the format, but every day you will use curl. It comes with macOS, Linux and Windows 10 and later. With -v (verbose) it shows everything it does; -s (silent) hides its progress bar:

In the browser’s developer tools, the Network panel shows the same thing for every request a page makes: method, address, status, request and response headers, and body. When a front end and a back end disagree, open it, find the request, and read it as you just read curl’s output. Most bugs are visible right there.

1.3 Addresses: path and query string

The target of a request has two parts. The path, such as /products, names a resource: a thing the API knows about. The query string, after a ?, holds name=value pairs joined with &, usually to filter, sort or page through a list. Our server understands one, max_price:

Terminal 2
# A list, filtered by a query string
$ curl -s 'localhost:3000/products?max_price=15000'
[{"id":2,"name":"Spare wheels","price":6000},{"id":3,"name":"Battery pack","price":12500}]
# Only the headers (HEAD): the same answer without the body
$ curl -sI localhost:3000/products
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 132
ETag: "8f38510311e374f1"
Cache-Control: no-cache
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5

The quotes around the first address matter: without them, the shell would treat ? and & as its own special characters. The second command uses -I, which sends HEAD: the same request as GET, but the server answers with the headers only. A client can learn the size or the version of a big resource without downloading it.

Prices are whole numbers of piastres (45000 is 450.00), never fractions. Floating-point numbers cannot hold most decimal fractions exactly, and money that is off by a fraction of a piastre is still wrong money. This rule follows us through the whole book.

1.4 Methods, and which requests can be repeated

The method says what the client wants to do with the resource. Two of its properties matter more than its name:

  • A method is safe if it only reads: it changes nothing on the server. Anyone can send it, any number of times: browsers prefetch links, search engines crawl them.
  • A method is idempotent if sending it twice has the same effect as sending it once. This matters because networks fail. When a request times out, the client cannot know whether the server received it. It can safely send an idempotent request again; a non-idempotent one might do the work twice.
MethodMeaningSafeIdempotent
GETRead a resourceYesYes
HEADLike GET, headers onlyYesYes
OPTIONSAsk what is allowed (used by CORS, 1.8)YesYes
POSTCreate something, or run an actionNoNo
PUTReplace a resource with the one sentNoYes
PATCHChange part of a resourceNoNot guaranteed
DELETERemove a resourceNoYes

PUT is idempotent because it says “make it this”: doing it twice leaves the same result. POST says “add one”: doing it twice adds two. Here is a POST that creates a product. With -d, curl sends a body (and switches to POST by itself); -H adds a header, and -i shows the response headers:

Terminal 2

$ curl -si -X POST localhost:3000/products -H 'Content-Type: application/json' -d '{"name": "USB cable", "price": 2500}'

Content-Length: 40

Date: Thu, 19 Nov 2026 18:42:39 GMT

{"id":4,"name":"USB cable","price":2500}
# It is there now
$ curl -s localhost:3000/products/4
{"id":4,"name":"USB cable","price":2500}

The answer is 201 Created, not just 200 OK, and the Location header gives the address of the new product. A client does not need to guess how addresses are built: the server tells it.

Watch out: a retried POST can charge twice

A phone on a weak network sends “pay 450.00”, the answer is lost, and the app tries again. With a plain POST, the customer pays twice. Serious APIs make such requests safe to repeat with an idempotency key: the client sends a unique value in a header, and the server remembers which keys it has already handled. We build this with a database in Chapter 6.

1.5 Status codes: the first thing a client reads

The status code is a three-digit number, and its first digit is its class:

  • 2xx: it worked.
  • 3xx: look somewhere else, or use what you already have.
  • 4xx: the client made a mistake. Sending the same request again will fail again.
  • 5xx: the server failed. The same request might work later.

That difference between 4xx and 5xx is what clients, retry logic and monitoring tools rely on: a spike of 5xx wakes someone up at night, a spike of 4xx usually means a broken client. So each mistake gets the code that describes it. Here are the ones our server returns, with curl’s -w option printing the status after the body:

1.6 Headers that do real work

Dozens of headers exist; a handful do most of the work in an API.

Content-Type and Content-Length

Content-Type says what the body is: application/json; charset=utf-8 for our answers. The client must send it too: our server answered 415 to -d 'name=Cable', because curl labels such a body application/x-www-form-urlencoded, the format of an HTML form. Content-Length is the size of the body in bytes, not in characters. In UTF-8, an English letter takes one byte, but an Arabic letter takes two, and many emoji take four. A server that counts characters cuts Arabic text short.

Caching: ETag and 304

Most requests ask for something the client has already seen. The server can label each version of a resource with an ETag, a short fingerprint of its content. Our server makes one from a hash of the list. The client sends it back in If-None-Match, and if the list has not changed the server answers 304 Not Modified with no body:

Terminal 2
# The first visit: the server sends the list and its ETag
$ curl -si localhost:3000/products
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 173
ETag: "c25b00ae213de631"
Cache-Control: no-cache
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5

[{"id":1,"name":"Robot kit","price":45000},{"id":2,"name":"Spare wheels","price":6000},{"id":3,"name":"Battery pack","price":12500},{"id":4,"name":"USB cable","price":2500}]
# The next visit sends the ETag back: nothing changed, so 304 and no body
$ curl -si localhost:3000/products -H 'If-None-Match: "c25b00ae213de631"'
HTTP/1.1 304 Not Modified
Content-Length: 0
ETag: "c25b00ae213de631"
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5

Browsers do this by themselves: they store the ETag and send it back on the next visit. Cache-Control: no-cache tells them to always ask first (it does not mean “do not store”; that is no-store). Other values let a client reuse a copy without asking at all, for a time: max-age=60 means one minute, which is right for a product list that may change, and max-age=31536000, immutable means one year, which is right for files whose name changes with their content, such as the bundles from Book 2.

Authorization and cookies

A client proves who it is in one of two ways. Programs and mobile apps usually send a token in Authorization: Bearer <token>. Browsers usually rely on a cookie: the server sends Set-Cookie: session=…; HttpOnly; Secure; SameSite=Lax, and the browser sends Cookie: session=… with every later request to that site. HttpOnly hides the cookie from JavaScript, so an injected script cannot steal it; Secure sends it over HTTPS only; SameSite limits when other sites can make the browser send it. Chapter 8 builds both, properly.

1.7 Connections, and the versions of HTTP

Opening a TCP connection costs a round trip to the server, and the TLS handshake costs one or two more. To a server on another continent, that is a few hundred milliseconds before the first byte of the answer. So HTTP/1.1 keeps connections open by default, and sends the next request on the same one. curl can show whether it was reused:

Terminal 2
# Two requests in one curl command: is the connection reused?
$ curl -sv localhost:3000/products/1 localhost:3000/products/2 -o /dev/null -o /dev/null 2>&1 | grep -E 'Connected|Re-using|left intact|Closing|^< HTTP'
* Connected to localhost (127.0.0.1) port 3000
< HTTP/1.1 200 OK
* Connection #0 to host localhost left intact
* Re-using existing connection with host localhost
< HTTP/1.1 200 OK
* Connection #0 to host localhost left intact

For the second request, curl says Re-using existing connection. Node keeps an idle connection for five seconds (the Keep-Alive: timeout=5 header you saw in every answer), and one Node process can hold thousands of them at once, because it never waits: while one request waits for a file or a database, the same thread works on the others. Chapter 2 looks at this event loop closely.

HTTP/2 and HTTP/3 change how the messages travel, not what they mean. HTTP/2 sends them in a compact binary form and runs many requests at the same time over one connection. HTTP/3 does the same over QUIC, a newer transport that recovers faster from lost packets, which helps on mobile networks. Methods, headers, status codes and bodies are exactly what you have learned. In practice, the web server or load balancer in front of your application speaks HTTP/2 and HTTP/3 to browsers, and plain HTTP/1.1 to your application.

Good to know: HTTPS everywhere

Without TLS, anyone on the path (the café’s Wi-Fi, a provider) can read and change every request, passwords and tokens included. Every public API must use HTTPS, and certificates are free from Let’s Encrypt. You rarely write TLS code yourself: the web server or the hosting platform does it, which is how we set it up in Chapter 16.

1.8 CORS: when a browser calls your API

A browser protects its users with the same-origin policy. An origin is a scheme, a host and a port together: http://localhost:5173, where a Vite app runs, and http://localhost:3000, where our API runs, are different origins. By default, JavaScript on one origin may send a request to another, but may not read the answer. Otherwise any site you visit could read your bank’s pages with your cookies.

CORS (Cross-Origin Resource Sharing) lets a server say which other origins may read its answers. For a request that could change something, such as a POST with a JSON body, the browser first sends a preflight: an OPTIONS request asking whether the real one is allowed. We can play the browser with curl:

Terminal 2
# A browser asks first (a preflight) before a POST from another site
$ curl -si -X OPTIONS localhost:3000/products -H 'Origin: http://localhost:5173' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: content-type'
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://localhost:5173
Vary: Origin
Content-Length: 0
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type
Access-Control-Max-Age: 600
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5
# Another site is not on the list: no Access-Control header, so the browser blocks it
$ curl -si localhost:3000/products/1 -H 'Origin: https://evil.example'
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 41
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5

{"id":1,"name":"Robot kit","price":45000}

For the web app’s origin, the server answers the preflight with what is allowed, and the browser remembers it for ten minutes (Max-Age: 600). For any other origin there is no Access-Control-Allow-Origin header, and the browser refuses to give the answer to the page’s JavaScript. The Vary: Origin header tells caches that the answer depends on the Origin header, so that one site is never served a copy made for another.

Watch out: CORS is not access control

Look again at the second command: the server still answered 200 with the product. CORS is enforced by the browser, to protect the browser’s user. curl, a script or an attacker’s server ignores it completely. Anything that must be private needs authentication and authorisation on the server. And never answer Access-Control-Allow-Origin: * together with cookies: list the origins you trust, as our server does.

1.9 Inside the server

Now that you know what goes over the wire, the server holds no surprises. We read it in five parts, from the top of the file.

The data and the settings. The products live in an array, with prices in piastres. ORIGINS lists the only web app allowed to read our answers from a browser (1.8), and MAX_BODY is the largest body we accept:

server.ts (1 of 5)
import { createServer } from "node:http";
import type { IncomingMessage, ServerResponse } from "node:http";
import { createHash } from "node:crypto";

type Product = { id: number; name: string; price: number };
type Headers = Record<string, string>;

const products: Product[] = [
  { id: 1, name: "Robot kit", price: 45000 },
  { id: 2, name: "Spare wheels", price: 6000 },
  { id: 3, name: "Battery pack", price: 12500 },
];
// the web app that may call this API from a browser
const ORIGINS = ["http://localhost:5173"];
const MAX_BODY = 1024; // bytes

One place sends answers. Every response in the file goes through send, which sets the type and the length, counted in bytes with Buffer.byteLength. An empty body gets no type at all. fail gives every error the same shape. Because of these two functions, no route can forget a header or invent its own error format:

server.ts (2 of 5)
function send(res: ServerResponse, status: number, body?: unknown,
              headers: Headers = {}) {
  const text = body === undefined ? "" : JSON.stringify(body);
  res.writeHead(status, {
    ...(text && { "Content-Type": "application/json; charset=utf-8" }),
    "Content-Length": String(Buffer.byteLength(text)), // bytes, not characters
    ...headers,
  });
  res.end(text);
}

function fail(res: ServerResponse, status: number, code: string,
              message: string, extra = {}, headers: Headers = {}) {
  send(res, status, { error: { code, message, ...extra } }, headers);
}

Routing. handle looks at the method and the path and decides what to do: the CORS headers first, for any request, then the preflight, then the list, then one product. Everything else is a 404. Notice that the 405 answer names the allowed methods, and that a HEAD is answered like a GET: Node itself drops the body of an answer to HEAD.

server.ts (3 of 5)
async function handle(req: IncomingMessage, res: ServerResponse) {
  const url = new URL(req.url ?? "/", "http://localhost");
  const origin = req.headers.origin;
  if (origin && ORIGINS.includes(origin)) {
    res.setHeader("Access-Control-Allow-Origin", origin);
    res.setHeader("Vary", "Origin");
  }

  if (req.method === "OPTIONS") {
    return send(res, 204, undefined, {
      "Access-Control-Allow-Methods": "GET, POST",
      "Access-Control-Allow-Headers": "Content-Type",
      "Access-Control-Max-Age": "600",
    });
  }

  if (url.pathname === "/products") {
    if (req.method === "GET" || req.method === "HEAD") {
      const max = Number(url.searchParams.get("max_price") ?? Infinity);
      const list = products.filter((p) => p.price <= max);
      const hash = createHash("md5").update(JSON.stringify(list)).digest("hex");
      const etag = `"${hash.slice(0, 16)}"`;
      if (req.headers["if-none-match"] === etag) {
        return send(res, 304, undefined, { ETag: etag });
      }
      return send(res, 200, list, { ETag: etag, "Cache-Control": "no-cache" });
    }
    if (req.method === "POST") return create(req, res);
    return fail(res, 405, "method_not_allowed", "Use GET or POST here", {},
                { Allow: "GET, HEAD, POST" });
  }

  const one = url.pathname.match(/^\/products\/(\d+)$/);
  if (one && req.method === "GET") {
    const product = products.find((p) => p.id === Number(one[1]));
    if (!product) return fail(res, 404, "not_found", "No product with this id");
    return send(res, 200, product);
  }
  return fail(res, 404, "not_found", "Nothing here");
}

Distrust the body. Creating a product checks everything a client could get wrong, in order: the type before reading, the size while reading (readBody stops at 1 KB, so a huge body never reaches memory), the JSON in a try, and then each field for its type and range, collecting every error before answering. Real APIs allow more than 1 KB, but they always have a limit; without one, a single client can fill the server’s memory.

server.ts (4 of 5)
async function readBody(req: IncomingMessage): Promise<string> {
  let size = 0;
  const parts: Buffer[] = [];
  for await (const chunk of req) {
    size += chunk.length;
    if (size > MAX_BODY) throw new Error("too_large");
    parts.push(chunk);
  }
  return Buffer.concat(parts).toString("utf8");
}

async function create(req: IncomingMessage, res: ServerResponse) {
  if (!req.headers["content-type"]?.startsWith("application/json")) {
    return fail(res, 415, "unsupported_media_type", "Send JSON");
  }
  let data: { name?: unknown; price?: unknown };
  try {
    data = JSON.parse(await readBody(req));
  } catch (e) {
    if (e instanceof Error && e.message === "too_large") {
      return fail(res, 413, "too_large", "At most 1 KB");
    }
    return fail(res, 400, "bad_json", "The body is not valid JSON");
  }

  const { name, price } = data;
  const errors: Record<string, string> = {};
  if (typeof name !== "string" || !name.trim()) errors.name = "Required";
  if (typeof price !== "number" || !Number.isInteger(price) || price <= 0) {
    errors.price = "A whole number of piastres above 0";
  }
  if (Object.keys(errors).length) {
    return fail(res, 422, "invalid", "Check the fields", { fields: errors });
  }

  const product = {
    id: products.length + 1,
    name: (name as string).trim(),
    price: price as number,
  };
  products.push(product);
  send(res, 201, product, { Location: `/products/${product.id}` });
}

The server itself. createServer calls our function for every request. When the response is finished, one line goes to the log with the method, the address, the status and the time it took. Any unexpected error is caught here, once: the real error goes to the log, and the client gets a plain 500 without stack traces or file paths that would help an attacker. requestTimeout cuts off a client that sends too slowly, so a few slow clients cannot hold every connection:

server.ts (5 of 5)
const server = createServer((req, res) => {
  const start = performance.now();
  res.on("finish", () => {
    const ms = Math.round(performance.now() - start);
    console.log(`${req.method} ${req.url} ${res.statusCode} ${ms}ms`);
  });
  handle(req, res).catch((error) => {
    console.error(error); // the details stay in the server's log
    if (!res.headersSent) {
      fail(res, 500, "server_error", "Something went wrong on our side");
    }
  });

Professional habit: look at the wire first

When an API “does not work”, do not change code at random. Reproduce the request with curl -v, or copy it from the browser’s Network panel (“Copy as cURL”), and read the request and the answer line by line: the method, the address, the Content-Type, the status, the error body. Summary

  • A request goes through a name lookup, a TCP connection, TLS for HTTPS, and then the HTTP request and response.
  • HTTP/1.1 is text: a first line, headers, an empty line, and a body whose size is in Content-Length, in bytes.
  • The path names a resource; the query string filters and pages.
  • Safe methods only read; idempotent ones can be repeated. POST is neither, so retries need idempotency keys.
  • 2xx worked, 3xx look elsewhere, 4xx the client’s mistake, 5xx the server’s. Errors have one shape, with a stable code and a readable message.
  • ETag and If-None-Match turn repeated reads into empty 304 answers; Cache-Control says how long a copy may be reused.
  • Connections are kept alive and reused; HTTP/2 and HTTP/3 change the transport, not the meaning.
  • CORS lets a browser page read answers from another origin. It protects browser users; it does not protect your server.
  • Every server, with or without a framework, needs: one way to answer, distrust of input, limits, caught errors and a log line per request.

Quick check answers: 1. At the first empty line; the body is exactly Content-Length bytes long. 2. My first Node server resized photos inside the request handler. It worked beautifully on my laptop. The day ten people uploaded at once, every page of the site stopped answering, including the ones that had nothing to do with photos. That was how I met the event loop.

2.1 What Node is

Node is three things put together. V8, the JavaScript engine from Chrome, runs your code. libuv, a library written in C, talks to the operating system: it opens files and network connections, and tells Node when something is ready. And a standard library (node:http, node:fs, node:stream, node:test and many more) wraps it all for JavaScript.

The important design choice is that your JavaScript runs on one thread, and I/O (input and output: the network, the disk, a database) never makes it wait. When a request handler asks the database for a list, Node hands the work to the operating system and moves on to the next request. When the list arrives, Node calls your code back. One process can serve thousands of connections at once this way, because most of a server’s time is spent waiting for I/O, and waiting costs Node nothing.

The cost of the design is just as important: while your JavaScript is computing, nothing else runs. We will see both sides for real in this chapter.

2.3 The event loop

The event loop is Node’s main loop. In each turn, it runs whatever is ready: timers whose time has come, I/O that has finished, callbacks scheduled with setImmediate. Between any two of these, it empties two smaller queues of microtasks: callbacks of promises, and callbacks given to process.nextTick. This program schedules one of each, and then keeps the thread busy:

demos/event-loop.ts
import { readFile } from "node:fs/promises";

console.log("script starts");
setTimeout(() => console.log("timer (0 ms)"), 0);
Promise.resolve().then(() => console.log("promise callback"));
process.nextTick(() => console.log("process.nextTick"));
console.log("script ends");

// wait for some I/O, then a second experiment
await readFile(import.meta.filename);
const asked = performance.now();
setTimeout(() => {
  const late = Math.round(performance.now() - asked);
  console.log(`timer asked for 10 ms, ran after ${late} ms`);
}, 10);
const until = performance.now() + 200;
while (performance.now() < until); // busy for 200 ms
Terminal
# The order things run in
$ node demos/event-loop.ts
script starts
script ends
promise callback
process.nextTick
timer (0 ms)
timer asked for 10 ms, ran after 200 ms

Three rules explain the output:

  1. The code that is running always finishes first. Nothing interrupts it: “script ends” comes before every callback.
  2. Microtasks run before the loop moves on. Both the promise callback and the nextTick callback run before the timer, even though the timer asked for 0 ms. (In an ES module, promise callbacks happen to run before nextTick ones; in an old CommonJS file it is the other way round. Code that depends on that order is fragile.)
  3. A timer’s delay is a minimum, not a promise. The second timer asked for 10 ms and ran after 200, because the loop was busy and could not check its timers.

The third rule is the one that matters on a server. Every request, every timer and every database answer waits for the same thread. If one piece of code keeps it for a second, every user waits a second.

2.4 Never block the loop

Here is a server with two routes. /primes counts the prime numbers up to a limit, which is pure computation; /hello answers at once:

demos/blocking.ts
import { createServer } from "node:http";
import { countPrimes } from "../src/primes.ts";

createServer((req, res) => {
  const url = new URL(req.url ?? "/", "http://localhost");
  if (url.pathname === "/primes") {
    const primes = countPrimes(Number(url.searchParams.get("limit"))); // blocks!
    return res.end(JSON.stringify({ primes }));
  }
  res.end(JSON.stringify({ message: "hello" }));
}).listen(3001);

We send a slow request and, a moment later, a quick one. curl’s -w prints how long each one took:

Terminal
# One slow request (a CPU count) and one quick one, sent at the same moment
$ curl -s 'localhost:3001/primes?limit=5000000' -w ' %{time_total}s\n' & sleep 0.05; curl -s localhost:3001/hello -w ' %{time_total}s\n'; wait
{"primes":348513} 1.394915s
{"message":"hello"} 1.343057s

The quick request, which needs a fraction of a millisecond, waited more than a second, because the thread was counting primes for someone else. With a hundred users, each would wait behind every count in front of them. Typical culprits are image resizing, PDF generation, password hashing with a synchronous function, compressing big files, and JSON.parse on huge bodies.

The fix is to do heavy computation on another thread. Node’s worker threads run a separate JavaScript file with its own event loop, and exchange messages with the main thread:

src/primes-worker.ts
// Runs in its own thread, so a long count never blocks the event loop.
import { parentPort, workerData } from "node:worker_threads";
import { countPrimes } from "./primes.ts";

parentPort?.postMessage(countPrimes(workerData as number));

The worker receives its input in workerData and posts its result back. In the app, a small function wraps it in a promise, so the handler simply awaits it:

src/app.ts
function countInWorker(limit: number): Promise<number> {
  return new Promise((resolve, reject) => {
    const worker = new Worker(new URL("./primes-worker.ts", import.meta.url), {
      workerData: limit,
    });
    worker.once("message", resolve);
    worker.once("error", reject);
  });
}

The same two requests against the real server:

Terminal
# The same two requests, with the count in a worker thread
$ curl -s 'localhost:3000/primes?limit=5000000' -w ' %{time_total}s\n' & sleep 0.05; curl -s localhost:3000/hello -w ' %{time_total}s\n'; wait
{"message":"Hello from Bit's shop"} 0.001101s
{"limit":5000000,"primes":348513,"ms":1347} 1.348983s

The quick request now answers in about a millisecond, before the count has finished, because the main thread was free. Starting a thread costs a few tens of milliseconds, which is nothing next to a one-second job but too much for many small ones. For those, keep a pool of threads started once and reused; you build one in Exercise 5, and the Piscina library is a well-tested one.

Tip: most libraries already do this

Many slow operations in Node’s standard library have an asynchronous version that runs on libuv’s own thread pool: crypto.scrypt instead of crypto.scryptSync, zlib.gzip instead of zlib.gzipSync, fs.promises.readFile instead of fs.readFileSync. On a server, any function whose name ends in Sync is a warning sign inside a request handler. At start-up, before the server listens, it is fine.

2.5 Waiting for several things at once

A product page might need the stock, the price and the reviews, each from a different service. This demo stands in for three network calls, of 300, 200 and 400 ms:

demos/concurrency.ts
import { setTimeout as sleep } from "node:timers/promises";

// Three slow services, as a real API would call over the network.
const stock = (signal?: AbortSignal) => sleep(300, 7, { signal });
const price = (signal?: AbortSignal) => sleep(200, 45000, { signal });
const reviews = (signal?: AbortSignal) => sleep(400, 4.5, { signal });

async function timed(label: string, work: () => Promise<unknown>) {
  const start = performance.now();
  const result = await work();
  console.log(`${label}: ${Math.round(performance.now() - start)} ms`, result);
}

await timed("one after another", async () => {
  return [await stock(), await price(), await reviews()];
});

await timed("all at once", () => Promise.all([stock(), price(), reviews()]));

const down = () => Promise.reject(new Error("the reviews service is down"));
await timed("one fails, the others still count", async () => {
  const results = await Promise.allSettled([stock(), price(), down()]);
  return results.map((r) => (r.status === "fulfilled" ? r.value : "failed"));
});

await timed("with a time limit of 250 ms", async () => {
  const limit = AbortSignal.timeout(250);
  const results = await Promise.allSettled([stock(), price(), reviews(limit)]);
  return results.map((r) =>
    r.status === "fulfilled" ? r.value : "skipped (too slow)",
  );
});
Terminal
# Waiting for three services
$ node demos/concurrency.ts
one after another: 903 ms [ 7, 45000, 4.5 ]
all at once: 401 ms [ 7, 45000, 4.5 ]
one fails, the others still count: 301 ms [ 7, 45000, 'failed' ]
with a time limit of 250 ms: 301 ms [ 7, 45000, 'skipped (too slow)' ]
  • One after another, the waits add up: 300 + 200 + 400 = 900 ms. Writing await three times in a row is the most common accidental slowness in Node code.
  • Promise.all starts all three, then waits for the slowest: 400 ms. Use it when the calls do not depend on each other.
  • Promise.allSettled waits for all of them and reports each one as fulfilled or rejected. A page can still show the stock and the price when the reviews service is down. Promise.all would reject as a whole on the first failure.
  • AbortSignal.timeout(250) gives a call a time limit. Most modern APIs accept a signal, including fetch and Node’s timers, and give up when it fires. Every call to another service needs a limit; without one, a slow service makes your server slow too.

Watch out: “all at once” has limits

Promise.all over ten thousand items starts ten thousand database queries at the same moment, and the database falls over. For large lists, run a few at a time (in batches, or with a small helper such as p-limit). And remember that a rejected Promise.all does not stop the other promises: they keep running, and their results are simply ignored.

2.6 Streams: big data in small memory

Suppose Bit’s shop must add up a million orders from a CSV file. The direct way reads the whole file into memory first:

demos/total-read.ts
import { readFile } from "node:fs/promises";

const text = await readFile("orders.csv", "utf8"); // the whole file in memory
let total = 0;
for (const line of text.split("\n").slice(1)) {
  if (line) total += Number(line.split(",")[2]);
}
const peak = Math.round(process.resourceUsage().maxRSS / 1024);
console.log(`total: ${total}, peak memory: ${peak} MB`);

A stream delivers the data in pieces as it arrives, so the program only ever holds a small part of it. readline turns a file stream into lines, and for await reads them one by one:

demos/total-stream.ts
import { createReadStream } from "node:fs";
import { createInterface } from "node:readline";

const lines = createInterface({ input: createReadStream("orders.csv") });
let total = 0;
let first = true;
for await (const line of lines) {
  if (first) {
    first = false; // the header
    continue;
  }
  total += Number(line.split(",")[2]);
}
const peak = Math.round(process.resourceUsage().maxRSS / 1024);
console.log(`total: ${total}, peak memory: ${peak} MB`);

On a server that handles many requests at once, the difference is multiplied by the number of users.

Backpressure

Streams also work the other way. When you write faster than the destination can take (a slow disk, a slow client), data piles up in memory. A writable stream says so: write() returns false when its buffer is full. The program that made the CSV file waits for the drain event before writing more:

demos/make-orders.ts
import { createWriteStream } from "node:fs";
import { once } from "node:events";

const file = createWriteStream("orders.csv");
file.write("id,customer,total\n");
for (let id = 1; id <= 1_000_000; id++) {
  const line = `${id},customer-${id % 97},${(id * 7919) % 100000}\n`;
  // write() returns false when the buffer is full: wait until it drains
  if (!file.write(line)) await once(file, "drain");
}
file.end();
await once(file, "finish");
console.log("1000000 orders written to orders.csv");

This is called backpressure: the slow side slows down the fast side, instead of letting memory fill up. You rarely handle it by hand, because pipeline does it for you. The shop’s export route makes its CSV rows with an async generator and pipes them into the response:

src/app.ts
async function* orderRows(count: number) {
  yield "id,customer,total\n";
  for (let id = 1; id <= count; id++) {
    yield `${id},customer-${id % 97},${(id * 7919) % 100000}\n`;
  }
}

In the handler, await pipeline(Readable.from(orderRows(100_000)), res) sends the rows as the client reads them. If the client disconnects halfway, pipeline stops the generator and cleans up; with the older .pipe() method, that cleanup is your job, and it is often forgotten. 2.7 Configuration

The port, the database address, the allowed origins and the API keys differ between your laptop, the test server and production. They must not be written in the code. The common rule is to read them from environment variables, which every hosting platform can set. But process.env holds only strings, any of which may be missing or mistyped. So the project reads them in one place, once, and checks them with zod:

src/config.ts
import { z } from "zod";

// process.env holds strings only: coerce and check them once, at start-up
const Env = z.object({
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  ALLOWED_ORIGINS: z
    .string()
    .transform((list) => list.split(",").map((origin) => origin.trim()))
    .pipe(z.array(z.url())),
});

const parsed = Env.safeParse(process.env);
if (!parsed.success) {
  console.error("Invalid configuration:\n" + z.prettifyError(parsed.error));
  process.exit(1);
}

// read-only: nothing can change the configuration later
export const config = Object.freeze(parsed.data);
export type Config = typeof config;

Everywhere else, the code imports config and gets real types: config.PORT is a number, config.ALLOWED_ORIGINS an array of URLs. And a wrong setting stops the server at once, with a clear message, instead of failing an hour later in the middle of a request:

2.8 Errors and graceful shutdown

Servers stop all the time: for every deployment, when a machine is replaced, when the platform scales down. The platform sends the process a SIGTERM signal (Ctrl+C in a terminal sends SIGINT) and, after a grace period, kills it. A server that simply exits on the signal cuts off every request in progress: a payment half processed, an upload lost. A graceful shutdown stops accepting new connections, lets the running requests finish, and only then exits:

src/server.ts
import { config } from "./config.ts";
import { createApp } from "./app.ts";
import { log } from "./log.ts";

const server = createApp();
server.requestTimeout = 30_000;
server.listen(config.PORT, () => {
  log("info", `Listening on http://localhost:${config.PORT}`);
});

function shutdown(signal: string): void {
  log("info", `${signal}: no new connections, finishing requests in progress`);
  server.close(() => {
    // stop accepting, let running requests finish
    log("info", "all requests finished, bye");
    process.exit(0);
  });
  // close kept-alive connections that are doing nothing
  server.closeIdleConnections();
  setTimeout(() => {
    log("error", "requests still running after 10 s, stopping anyway");
    process.exit(1);
  }, 10_000).unref(); // never hang forever
}
process.once("SIGTERM", () => shutdown("SIGTERM"));
process.once("SIGINT", () => shutdown("SIGINT"));

// the process is in an unknown state: log and stop; the supervisor restarts it
process.on("unhandledRejection", (error) => {
  log("error", `unexpected error, stopping: ${String(error)}`);
  process.exit(1);
});

The last handler is about a different kind of error. Errors you expect, such as a missing product or a timeout, are handled where they happen and become answers. An unhandled rejection means a promise failed and no code was waiting for the failure: a bug. After a bug, the process may be in a state nobody planned for, with half-updated data in memory. The safe reaction is to log it and exit, and let a supervisor (Docker, systemd or the hosting platform, Chapter 16) start a fresh process. Never keep a damaged process running just to look available.

Summary

  • Node is V8, libuv and a standard library. Your JavaScript runs on one thread; I/O never makes it wait.
  • Node runs TypeScript by stripping types; tsc checks them. erasableSyntaxOnly keeps the source strippable: no enums.
  • The event loop runs current code to the end, then microtasks, then timers and I/O. Timer delays are minimums.
  • Never block the loop: CPU work goes to worker threads, slow APIs are used in their async versions.
  • Promise.all waits for independent calls at once, allSettled survives failures, and AbortSignal.timeout limits every call.
  • Streams process big data in constant memory; backpressure slows the fast side; pipeline handles both and cleans up.
  • Configuration comes from the environment, checked once with a schema; secrets never enter the repository.
  • A graceful shutdown closes, finishes, then exits. After an unhandled error, log and exit, and let a supervisor restart.
  • node:test runs tests with no extra tool; servers in tests listen on port 0.

3.1 Resources and URLs

REST organises an API around resources: the nouns of your domain, such as products and orders. URLs name the resources; methods say what to do with them. The rules that make an API guessable are few:

  • Nouns, plural, lower case: /products, /orders. The method is the verb: GET /products, not /getProducts.
  • One resource: the collection plus an id, /products/2.
  • Nesting for ownership, one level deep: /orders/7/items is fine; /customers/3/orders/7/items/2 is not. Once a resource has its own id, give it its own top-level URL.
  • Actions that are not create, read, update or delete become a sub-resource with POST: POST /orders/7/cancel. Do not hide them in a PATCH that sets status: cancelling has rules (restore the stock, refund the payment) that a generic update would skip.
  • A version in the path: /v1/.... We come back to versions in 3.8.

Representations

The JSON an API sends is called a representation of the resource. Choose its conventions once, write them down, and never mix them:

  • One naming style. We use snake_case, like most public APIs; camelCase is just as good. Mixing them is not.
  • Times in ISO 8601, in UTC: 2026-11-01T09:00:00.000Z. Clients convert to the user’s time zone; the server never guesses it.
  • Money as an object: {"amount": 45000, "currency": "EGP"}, the amount in minor units. A bare number is ambiguous the day you sell in a second currency.
  • Lists in an object: {"data": [...], "next_cursor": ...}, never a bare array, so that page information can be added without breaking anyone.

3.3 Lists: filtering, sorting, pages

A list endpoint needs three things: a way to filter, a way to sort, and pages, because no client wants ten thousand products at once. Everything a client may send is in the query schema:

  id: "id",
  price: "price",
  "-price": "price",
  name: "name",
} as const;
type Sort = keyof typeof SORTS;

const ListQuery = z.object({

An API that sorts by whatever field arrives in ?sort= can be asked to sort by a field without an index, which makes a slow query that one attacker can repeat a thousand times a minute. It may also reveal fields that should stay private, through the order of results. List the allowed fields, as SORTS does, and add an index for each one when the data moves to a database.

Offset pages and cursor pages

The obvious way to page is an offset: ?page=2 means “skip the first 20”. It has two problems. A database must still walk past every skipped row, so page 5000 is slow. Worse, the pages drift when data changes between two requests. This small demo pages through a “newest first” list, three at a time, while a new product arrives between page 1 and page 2:

A cursor says “continue after this row”, so new rows before it change nothing. This is also called keyset pagination, because it continues from the key of the last row. Our API builds its cursors like this:

src/routes/products.ts
function compare(row: Product, [value, id]: Position, sort: Sort): number {
  const own = row[SORTS[sort]];
  const diff = own < value ? -1 : own > value ? 1 : row.id - id;
  return sort === "-price" ? -diff : diff;
}

// opaque to clients: base64url, so nobody builds cursors by hand
const encode = (position: Position) =>
  Buffer.from(JSON.stringify(position)).toString("base64url");

function decode(cursor: string): Position {
  try {
    const position = JSON.parse(Buffer.from(cursor, "base64url").toString());
    if (Array.isArray(position) && position.length === 2)
      return position as Position;
  } catch {}
  const error = { field: "querystring.cursor", message: "invalid cursor" };
  throw problems.invalidRequest([error]);
}

The rows are ordered by the sort field and then by id, so that two products with the same price still have a fixed order: without that tiebreak, rows with equal values could move between pages. The cursor holds the last row’s sort value and id, encoded with base64url. Encoding is not secrecy, and the cursor can be decoded; the point is that clients treat it as an opaque token and send it back unchanged, so the server is free to change what is inside. 3.4 Errors: Problem Details

In Chapter 1 our errors had a shape we invented. Every API that invents its own shape forces every client to learn it. Problem Details (RFC 9457) is the standard shape for HTTP API errors, sent with the content type application/problem+json: a type URL that identifies the kind of problem and leads to its documentation, a short title, the status, a detail for this particular case, and the instance, the request that failed. Extra members are allowed, such as our errors list.

Every text a person reads lives in one file, so it can be reviewed and translated in one place:

  stale: () => new Problem(412, "stale", m.stale, m.staleDetail),
  keyReused: () =>
    new Problem(422, "idempotency-key-reused", m.keyReused, m.keyReusedDetail),
  inProgress: () =>
    new Problem(409, "in-progress", m.inProgress, m.inProgressDetail),
  outOfStock: (id: number, stock: number) =>
    new Problem(
      409,
      "out-of-stock",
      m.outOfStock,
      say(m.outOfStockDetail, { id, stock }),
    ),
  unknownProduct: (id: number) =>
    new Problem(422, "unknown-product", m.unknownProduct, say(m.noProduct, { id })),
  cannotCancel: (id: number, status: string) =>
    new Problem(
      409,
      "invalid-state",
      m.cannotCancel,
      say(m.cannotCancelDetail, { id, status }),
    ),
  tooManyRequests: (seconds: number) =>
    new Problem(
      429,
      "too-many-requests",

      say(m.tooManyRequestsDetail, { seconds }),
    ),
  server: () => new Problem(500, "server-error", m.serverError),
};

One error handler turns everything into a problem: our own problems as they are, validation errors as 422 for a body and 400 for the rest of the request, the rate limiter’s errors as 429, and anything unexpected as a plain 500, with the details in the log:

src/app.ts
  app.setErrorHandler((error: FastifyError, request, reply) => {
    let problem: Problem;
    if (error instanceof Problem) {
      problem = error;
    } else if (hasZodFastifySchemaValidationErrors(error)) {
      const where = error.validationContext ?? "body";
      const errors = error.validation.map((issue) => ({
        field: [
          where,
          ...String(issue.instancePath).split("/").filter(Boolean),
        ].join("."),
        message: issue.message ?? "",
      }));
      // 422: a well-formed body with wrong values
      // 400: a bad query, path or header: the request itself is malformed
      problem =
        where === "body"
          ? problems.invalidBody(errors)
          : problems.invalidRequest(errors);
    } else if (error.statusCode === 429) {
      problem = problems.tooManyRequests(
        Number(reply.getHeader("retry-after") ?? 60),
      );
    } else {
      request.log.error(error); // the details stay in the log
      problem = problems.server();
    }
    reply.code(problem.status).type("application/problem+json");
    return reply.send(problem.body(request.url));
  });

3.5 Safe retries: idempotency keys

Chapter 1 warned that a retried POST can create an order twice. The standard answer, used by payment providers such as Stripe, is an idempotency key: the client creates a unique value (a UUID) for each intended operation and sends it in an Idempotency-Key header. If the same key arrives again, the server does not do the work again; it replays the answer it gave the first time.

src/routes/orders.ts
    app.post(
      "/orders",
      {
        schema: {
          headers: z.object({ "idempotency-key": z.string().min(8).max(100) }),
          body: NewOrder,
          response: { 201: OrderOut },
        },
      },
      async (request, reply) => {
        const key = request.headers["idempotency-key"];
        const body = JSON.stringify(request.body);
        const fingerprint = createHash("sha256").update(body).digest("hex");
        const saved = keys.get(key);
        if (saved) {
          if (saved.fingerprint !== fingerprint) throw problems.keyReused();
          if (!saved.order) throw problems.inProgress();
          reply.header("Idempotent-Replayed", "true");
          reply.header("Location", `/v1/orders/${saved.order.id}`);
          return reply.code(201).send(saved.order);
        }
        // mark the key as in progress before doing the work
        keys.set(key, { fingerprint });

        try {
          const items = request.body.items.map(({ product_id, quantity }) => {
            const product = store.products.find((p) => p.id === product_id);
            if (!product) throw problems.unknownProduct(product_id);
            if (product.stock < quantity) {
              throw problems.outOfStock(product.id, product.stock);
            }
            return { product, quantity };
          });
          for (const { product, quantity } of items) {
            product.stock -= quantity;
            product.version += 1;
          }
          const order: Order = {
            id: store.nextOrderId++,
            status: "pending",
            // the price comes from the server, never from the client
            items: items.map(({ product, quantity }) => ({
              product_id: product.id,
              quantity,
              price: product.price,
            })),
            total: items.reduce(
              (sum, { product, quantity }) => sum + product.price * quantity,
              0,
            ),
            created_at: new Date().toISOString(),
          };
          store.orders.push(order);
          keys.set(key, { fingerprint, order: show(order) });
          reply.header("Location", `/v1/orders/${order.id}`);
          return reply.code(201).send(show(order));
        } catch (error) {
          keys.delete(key); // a failed attempt may be tried again with the same key
          throw error;
        }
      },
    );

The details matter more than the idea:

  • The server keeps a fingerprint of the body. The same key with a different body is a bug in the client, and gets a 422, never a silent replay of a different order.
  • The key is marked in progress before the work starts. A second request that arrives while the first is still running gets a 409 instead of starting the work twice.
  • If the work fails, the key is forgotten, so the client may try again with it.
  • The total is computed from the server’s prices. A client never tells the server what something costs.

3.6 Lost updates: ETag and If-Match

Two administrators open product 2 at the same time. Sara changes the price to 65.00 and saves; a minute later Omar, whose screen still shows the old product, changes it to 70.00 and saves. Sara’s change is gone, and nobody was told. This is the lost update problem. HTTP solves it with the ETag you met in Chapter 1: the product’s version is its ETag, and a change must send back the version it was based on in If-Match:

src/routes/products.ts
    app.patch(
      "/products/:id",
      {
        schema: {
          params: IdParams,
          body: ProductPatch,
          response: { 200: ProductOut },
        },
      },
      async (request, reply) => {
        const product = find(request.params.id);
        const ifMatch = request.headers["if-match"];
        if (!ifMatch) throw problems.needIfMatch();
        if (ifMatch !== `"${product.version}"`) throw problems.stale();
        Object.assign(product, request.body, { version: product.version + 1 });
        reply.header("ETag", `"${product.version}"`);
        return show(product);
      },
    );

A change without If-Match is refused with 428 Precondition Required: requiring it is how the API makes sure no client forgets. The change based on version 1 succeeds and creates version 2. The second change, still based on version 1, gets 412 Precondition Failed, and the client knows to reload and show the user what changed. This is optimistic concurrency: nothing is locked while people look at a screen, and conflicts, which are rare, are detected when they happen. Chapter 6 does the same inside the database.

3.7 Rate limits

Every public API limits how fast one client may call it: to keep one buggy script from hurting everybody, and to make guessing passwords or scraping slow. The @fastify/rate-limit plugin counts requests per client address. Started with a limit of three a minute, the fourth request is refused:

3.8 Versions and change

Once other people use your API, every change is either additive or breaking. Adding an endpoint, an optional parameter or a new field to a response is additive: correct clients ignore what they do not know. Removing or renaming a field, changing its type or meaning, or adding a required parameter breaks clients. The rules:

  • Make every change additive if you possibly can. Most APIs live for years on version 1.
  • When a breaking change is unavoidable, publish /v2 next to /v1, and keep /v1 running for a stated period.
  • Announce the end in the answers themselves, with the Deprecation and Sunset headers, in the documentation, and by email to the clients you know. Watch your logs to see who still calls the old version before you turn it off.

3.9 Documentation from the code

Documentation written by hand drifts away from the code within weeks. Because every route here has a schema, the @fastify/swagger plugin generates an OpenAPI document from them: a standard, machine-readable description of every path, parameter, body and response. The API serves it at /openapi.json, and the routes listing in 3.1 was read from it. From the same document, tools can render documentation pages, generate typed client libraries in many languages, and check in CI that a change does not remove anything clients depend on.

Professional habit: design the API before you build it

Write the request and response examples for a new endpoint first, in the pull request or in the OpenAPI document, and get a review from someone who will use the endpoint, such as a front-end or mobile developer. Changing an example takes minutes; changing a published API takes months of versions and deprecation emails.

Summary

  • Resources are plural nouns; methods are the verbs; special actions are sub-resources with POST. Nest one level at most.
  • Fix the representation rules once: one naming style, UTC times, money as amount and currency, lists in an object.
  • Schemas describe every input and output; the framework refuses bad input and types the good.
  • Cursors page without drift over a complete order (sort field plus id); allowed sort fields are listed.
  • Errors are Problem Details: type, title, status, detail, instance, from one factory and one handler.
  • Idempotency keys with fingerprints make retries safe; ETag and If-Match prevent lost updates.
  • Rate limits protect everybody; their headers let good clients avoid them.
  • Prefer additive changes; version and announce the rest. Generate OpenAPI documentation from the code.

Chapter 1

  1. The status line is HTTP/1.1 200 OK; the headers are Content-Type, Content-Length, Date and Connection; then comes the empty line, and the body is the JSON object of 41 bytes. Without Host, Node answers 400 Bad Request by itself, before our code runs, so not even our log line appears: HTTP/1.1 requires the header, and Node enforces it.
  2. GET /products?max_price=100: safe and idempotent. PUT /products/2 with a full product: not safe, idempotent (the product ends up the same however many times it is sent). POST /products/2/reviews: neither; two requests make two reviews. DELETE /cart/items/7: not safe, idempotent. PATCH /products/2 with {"stock_change": -1}: neither, because each request takes one more item from the stock; a PATCH that sets a value ({"stock": 4}) would be idempotent.
  3. In handle, after the line that matches /products/:id, add: if the method is DELETE, find the product’s index with findIndex; answer 404 if it is -1, otherwise remove it with splice and answer send(res, 204). The first delete answers 204 and the second 404; that is still idempotent, because the server is in the same state after both. The new product, though, gets id 3 again, because the id is “number of products + 1”. A client holding an old link to product 3 now gets a different product, and if you had deleted product 1 instead, the new product would get the id of product 3, which still exists. Ids must never be reused: keep a counter, let nextId = products.length + 1, and use nextId++. With that change, the run in the code repository creates product 4. A database does this for you, with a sequence.
  4. The product list is public: anyone can read it with curl, so a page on another site reading it in a visitor’s browser learns nothing secret. CORS only stops other sites’ JavaScript from reading answers with the visitor’s browser. The danger is an endpoint that answers with private data because of the visitor’s cookies, such as GET /me/orders: there, letting any origin read the answer would let any site read the visitor’s orders. What protects it is not CORS alone, but the server checking who is asking (authentication), what they may see (authorisation), and cookies with SameSite, together with a short list of trusted origins.
  5. The answer must carry Content-Encoding: gzip, so the client knows to decompress; Content-Length with the size of the compressed bytes; and Vary: Accept-Encoding, so a cache never gives a compressed copy to a client that cannot read it. In send, check res.req.headers["accept-encoding"], compress with gzipSync from node:zlib, and send the buffer. With the three products of the run, the list is 128 bytes plain and 105 bytes compressed. That is a small saving, because gzip needs repetition to work with; on a list of a hundred products, the same JSON shrinks to a fraction of its size. That is also why servers do not compress tiny bodies: below about 1 KB, the work costs more than it saves. curl --compressed sends the header and decompresses the answer for you.

Chapter 2

  1. After about 50 ms: the timer cannot run before the busy loop ends, and the loop then finds it overdue. Without the busy loop it runs after about 10 ms, never earlier, and often a millisecond or two later.
  2. Add HOST: z.string().min(1).default("127.0.0.1") to the schema and call server.listen(config.PORT, config.HOST, ...). 127.0.0.1 accepts connections from the same machine only. 0.0.0.0 means “every network interface”: you need it inside a Docker container or on a server that must be reached from outside, and it is exactly what you do not want on a laptop in a café.
  3. Promise.all rejects as soon as the first promise rejects, at about 200 ms, with that error. The stock request is not cancelled: it keeps running and finishes at about 300 ms, and its result is ignored. The program in the code repository (answers/all-fails.ts) prints “Promise.all rejected at 201 ms: price service down” and then “stock finished anyway at 301 ms”. To really stop the other calls, give them an AbortController’s signal and call abort() in the catch.
  4. Read Number(url.searchParams.get("rows") ?? 100000), answer 422 unless it is a whole number from 1 to 1,000,000, and pass it to orderRows. Memory stays flat because the generator makes one row at a time, and pipeline only asks for the next row when the response can take more: at no moment do all rows exist together. When the client disconnects, the response is destroyed, pipeline rejects, and it calls the generator’s return(), so the generator stops at its current yield (any finally block in it runs). The handler’s catch sees the error and, since the headers were already sent, destroys the response instead of writing a 500.
  5. The pool in answers/pool.ts keeps a list of idle workers and a queue of jobs. run puts a job in the queue and calls #next, which gives the first job to an idle worker; when the worker answers, it goes back to the idle list and #next runs again. A worker that crashes is replaced with a new one, because a crashed thread cannot be reused. The worker file listens with parentPort.on("message", ...) instead of reading workerData once. In the run in the code repository, 100 counts with a new thread each took about 6 seconds, and with a pool of four about 150 ms: starting a thread costs far more than these small counts.

  2. 409 Conflict for the email, since the request is valid but clashes with existing data (some APIs use 422 to avoid revealing which emails exist; for a sign-up form, the security chapter discusses this choice); 428 Precondition Required; 412 Precondition Failed; 400 Bad Request, because the body cannot even be read; 422, because the body is readable and one value breaks a rule.
  3. Add q: z.string().trim().min(2).max(50).optional() to the query schema, read it with the other values, and add one filter: .filter((p) => !q || p.name.toLowerCase().includes(q.toLowerCase())). The cursor still works, because it records a position in the sorted order, not in the filtered list: the client sends the same q with the cursor, and the next page continues after that position among the matching products. In the run in the code repository, q=se with limit=1 returns “Servo motor”, then “Sensor set” with the cursor, and q=x is refused with a 400 problem. In a database, a search like this needs a suitable index, which Chapter 4 covers.
  4. One way: make cancel idempotent in its result. If the order is already cancelled, answer 200 with the order, because the client’s goal (a cancelled order) is reached. Another way: accept an Idempotency-Key on cancel too, and replay the first answer. The first is simpler and right here, because the second cancel changes nothing; keep 409 for orders that can no longer be cancelled because they were shipped. The general lesson: design actions so that repeating them is harmless, whenever the domain allows it.
  5. The class in answers/idempotency.ts keeps entries in a Map under the key client:key, so the same key from two clients is two entries. Each entry stores the time it was saved, read from a now function given to the constructor (by default Date.now); get deletes and ignores an entry older than the time to live. The tests pass a fake clock, () => now, and move now forward instead of waiting a day: a key is still there after 999 ms of a 1000 ms life and gone at 1000 ms. In production the client comes from authentication (Chapter 8), and the store is a database table or Redis keys with an expiry time, which also clears old entries on its own.
