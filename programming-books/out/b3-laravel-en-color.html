Chapter 1

How Servers Work: HTTP in Depth

In this chapter you will learn to

  • follow a request from a URL to a response: name lookup, connection, request, answer
  • read and write HTTP by hand, because it is plain text
  • choose the right method and status code, and know which requests are safe to repeat
  • use the headers that matter: content type and length, caching with ETags, CORS
  • inspect any API with curl, the backend developer’s most used tool
  • build a small JSON API with no framework, so that you know what every framework does for you

Every backend you will ever build, whatever the language or framework, does the same job: it waits for a message, works out what was asked, and sends a message back. The messages follow a protocol called HTTP. Frameworks hide it behind routes and controllers, which is useful until something goes wrong: a request that works in curl but not in the browser, a cache that never updates, a client that retries and charges a customer twice. Then you need to know what is really on the wire. This chapter shows it to you, byte by byte, with a small server we write ourselves.

Bit

The first API I wrote worked perfectly, as long as I was the only one calling it. Then a browser called it from another address, and nothing worked. I lost a day to a problem that two headers solved. Since then I read the raw request first, and guess second.

1.1 From a URL to an answer

When a web app in Bit’s shop asks for http://localhost:3000/products/2, four things happen, in this order:

  1. Name lookup. Computers talk to addresses, not names. The client asks the Domain Name System (DNS) for the address of the host (here localhost, which always means “this same computer”, at 127.0.0.1). For a real site such as shop.example, a DNS server somewhere on the internet answers.
  2. Connection. The client opens a TCP connection to that address and a port, a number that picks one program on the machine. Our server listens on port 3000. TCP makes sure that bytes arrive complete and in order.
  3. Security, for HTTPS. With https://, the two sides first agree on encryption keys (the TLS handshake), and the server proves who it is with a certificate. Everything after that is encrypted. The HTTP inside is the same.
  4. Request and response. The client sends an HTTP request as text; the server sends back a response. The connection may then stay open for the next request.

Everything in this chapter happens on your own computer, so you can see every step without a network in the way. We need a server to talk to. The book’s code folder has one for this chapter, a small API for Bit’s shop, with no framework at all. Start it in a terminal and leave that terminal open:

Terminal 1
# Start the server (and leave it running in this terminal)
$ php -S localhost:8000 server.php
[Thu Nov 19 18:42:39 2026] PHP 8.5.13 Development Server (http://localhost:8000) started

PHP comes with a small web server for development: php -S listens on an address and sends every request to the script you name. The script is plain PHP; it reads like JavaScript with a $ before every variable, and Chapter 2 explains the language properly. We will read the whole script in Section 1.9. First, we look at the server from the outside, the way every client does.

1.2 HTTP is text

HTTP/1.1, the version every server understands, is plain text sent over the TCP connection. You can type a request yourself. The nc (netcat) tool opens a TCP connection and passes through whatever you give it; printf writes the request, with \r\n at the end of each line, as the protocol requires. Open a second terminal:

Terminal 2
# Type a request by hand: HTTP/1.1 is plain text over a TCP connection
$ printf 'GET /products/1 HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc localhost 8000
HTTP/1.1 200 OK
Host: localhost
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: close
Content-Type: application/json; charset=utf-8
Content-Length: 41

{"id":1,"name":"Robot kit","price":45000}

That is all an HTTP exchange is. Both messages have the same shape:

  1. A first line. In the request, the request line: the method (GET), the target (/products/1) and the version. In the response, the status line: the version, a status code (200) and a short reason (OK).
  2. Headers, one per line, Name: value. Names are not case sensitive: content-type and Content-Type are the same header.
  3. An empty line. It says “the headers end here”. Forget it, and the server waits for more headers forever.
  4. The body, if there is one. The receiver knows where it ends from Content-Length: here, 41 bytes.

Our request had two headers. Host is required in HTTP/1.1, because one machine with one address often serves many sites, and the server needs to know which one you mean. Connection: close asks the server to close the connection after answering, so that nc stops; we will come back to connections in Section 1.7.

The PHP development server adds a header you would not expect, Host, to its responses. It is a quirk of this tool, not part of HTTP, and one of several reasons it is for development only. In production, PHP runs behind a real web server, as you will see in Chapter 17.

1.3 Addresses: path and query string

The target of a request has two parts. The path, such as /products, names a resource: a thing the API knows about. The query string, after a ?, holds name=value pairs joined with &, usually to filter, sort or page through a list. Our server understands one, max_price:

Terminal 2
# A list, filtered by a query string
$ curl -s 'localhost:8000/products?max_price=15000'
[{"id":2,"name":"Spare wheels","price":6000},{"id":3,"name":"Battery pack","price":12500}]
# Only the headers (HEAD): the same answer without the body
$ curl -sI localhost:8000/products
HTTP/1.1 200 OK
Host: localhost:8000
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: close
Content-Type: application/json; charset=utf-8
Content-Length: 132
ETag: "8f38510311e374f1"
Cache-Control: no-cache

The quotes around the first address matter: without them, the shell would treat ? and & as its own special characters. The second command uses -I, which sends HEAD: the same request as GET, but the server answers with the headers only. A client can learn the size or the version of a big resource without downloading it.

Prices are whole numbers of piastres (45000 is 450.00), never fractions. Floating-point numbers cannot hold most decimal fractions exactly, and money that is off by a fraction of a piastre is still wrong money. This rule follows us through the whole book.

1.4 Methods, and which requests can be repeated

The method says what the client wants to do with the resource. Two of its properties matter more than its name:

  • A method is safe if it only reads: it changes nothing on the server. Anyone can send it, any number of times: browsers prefetch links, search engines crawl them.
  • A method is idempotent if sending it twice has the same effect as sending it once. This matters because networks fail. When a request times out, the client cannot know whether the server received it. It can safely send an idempotent request again; a non-idempotent one might do the work twice.

1.5 Status codes: the first thing a client reads

The status code is a three-digit number, and its first digit is its class:

  • 2xx: it worked.
  • 3xx: look somewhere else, or use what you already have.
  • 4xx: the client made a mistake. Sending the same request again will fail again.
  • 5xx: the server failed. The same request might work later.

That difference between 4xx and 5xx is what clients, retry logic and monitoring tools rely on: a spike of 5xx wakes someone up at night, a spike of 4xx usually means a broken client. So each mistake gets the code that describes it. Here are the ones our server returns, with curl’s -w option printing the status after the body:

1.6 Headers that do real work

Dozens of headers exist; a handful do most of the work in an API.

Content-Type and Content-Length

Content-Type says what the body is: application/json; charset=utf-8 for our answers. The client must send it too: our server answered 415 to -d 'name=Cable', because curl labels such a body application/x-www-form-urlencoded, the format of an HTML form. Content-Length is the size of the body in bytes, not in characters. In UTF-8, an English letter takes one byte, but an Arabic letter takes two, and many emoji take four. A server that counts characters cuts Arabic text short.

Caching: ETag and 304

Most requests ask for something the client has already seen. The server can label each version of a resource with an ETag, a short fingerprint of its content. Our server makes one from a hash of the list. The client sends it back in If-None-Match, and if the list has not changed the server answers 304 Not Modified with no body:

Terminal 2
# The first visit: the server sends the list and its ETag
$ curl -si localhost:8000/products

Host: localhost:8000
Date: Thu, 19 Nov 2026 18:42:40 GMT
Connection: close
Content-Type: application/json; charset=utf-8
Content-Length: 173
ETag: "c25b00ae213de631"
Cache-Control: no-cache

[{"id":1,"name":"Robot kit","price":45000},{"id":2,"name":"Spare wheels","price":6000},{"id":3,"name":"Battery pack","price":12500},{"id":4,"name":"USB cable","price":2500}]
# The next visit sends the ETag back: nothing changed, so 304 and no body
$ curl -si localhost:8000/products -H 'If-None-Match: "c25b00ae213de631"'

Host: localhost:8000
Date: Thu, 19 Nov 2026 18:42:40 GMT

Browsers do this by themselves: they store the ETag and send it back on the next visit. Cache-Control: no-cache tells them to always ask first (it does not mean “do not store”; that is no-store). Other values let a client reuse a copy without asking at all, for a time: max-age=60 means one minute, which is right for a product list that may change, and max-age=31536000, immutable means one year, which is right for files whose name changes with their content, such as the bundles from Book 2.

Authorization and cookies

A client proves who it is in one of two ways. Programs and mobile apps usually send a token in Authorization: Bearer <token>. Browsers usually rely on a cookie: the server sends Set-Cookie: session=…; HttpOnly; Secure; SameSite=Lax, and the browser sends Cookie: session=… with every later request to that site. HttpOnly hides the cookie from JavaScript, so an injected script cannot steal it; Secure sends it over HTTPS only; SameSite limits when other sites can make the browser send it. Chapter 9 builds both, properly.

1.7 Connections, and the versions of HTTP

Opening a TCP connection costs a round trip to the server, and the TLS handshake costs one or two more. To a server on another continent, that is a few hundred milliseconds before the first byte of the answer. So HTTP/1.1 keeps connections open by default, and sends the next request on the same one. curl can show whether it was reused:

Terminal 2
# Two requests in one curl command: is the connection reused?
$ curl -sv localhost:8000/products/1 localhost:8000/products/2 -o /dev/null -o /dev/null 2>&1 | grep -E 'Connected|Re-using|left intact|Closing|^< HTTP'
* Connected to localhost (127.0.0.1) port 8000
< HTTP/1.1 200 OK
* Closing connection
* Connected to localhost (127.0.0.1) port 8000
< HTTP/1.1 200 OK
* Closing connection

The PHP development server closes the connection after every answer (the Connection: close you saw in each response), and it handles one request at a time. That is fine on your laptop and far too slow for real users. In production, a web server such as Nginx or Caddy holds the connections, keeps them open, and hands each request to one of many PHP worker processes. PHP itself works the same way in both cases: each request starts with nothing in memory and ends by forgetting everything. This model is called shared-nothing, and it is why our script keeps its products in a file, as you will see in 1.9.

HTTP/2 and HTTP/3 change how the messages travel, not what they mean. HTTP/2 sends them in a compact binary form and runs many requests at the same time over one connection. HTTP/3 does the same over QUIC, a newer transport that recovers faster from lost packets, which helps on mobile networks. Methods, headers, status codes and bodies are exactly what you have learned. In practice, the web server or load balancer in front of your application speaks HTTP/2 and HTTP/3 to browsers, and plain HTTP/1.1 to your application.

Good to know: HTTPS everywhere

Without TLS, anyone on the path (the café’s Wi-Fi, a provider) can read and change every request, passwords and tokens included. Every public API must use HTTPS, and certificates are free from Let’s Encrypt. You rarely write TLS code yourself: the web server or the hosting platform does it, which is how we set it up in Chapter 17.

1.8 CORS: when a browser calls your API

A browser protects its users with the same-origin policy. An origin is a scheme, a host and a port together: http://localhost:5173, where a Vite app runs, and http://localhost:8000, where our API runs, are different origins. By default, JavaScript on one origin may send a request to another, but may not read the answer. Otherwise any site you visit could read your bank’s pages with your cookies.

CORS (Cross-Origin Resource Sharing) lets a server say which other origins may read its answers. For a request that could change something, such as a POST with a JSON body, the browser first sends a preflight: an OPTIONS request asking whether the real one is allowed. We can play the browser with curl:

Terminal 2
# A browser asks first (a preflight) before a POST from another site
$ curl -si -X OPTIONS localhost:8000/products -H 'Origin: http://localhost:5173' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: content-type'
HTTP/1.1 204 No Content
Host: localhost:8000
Date: Thu, 19 Nov 2026 18:42:40 GMT
Connection: close
Access-Control-Allow-Origin: http://localhost:5173
Vary: Origin
Content-Type:
Content-Length: 0
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type
Access-Control-Max-Age: 600
# Another site is not on the list: no Access-Control header, so the browser blocks it
$ curl -si localhost:8000/products/1 -H 'Origin: https://evil.example'
HTTP/1.1 200 OK
Host: localhost:8000
Date: Thu, 19 Nov 2026 18:42:40 GMT
Connection: close
Content-Type: application/json; charset=utf-8
Content-Length: 41

{"id":1,"name":"Robot kit","price":45000}

For the web app’s origin, the server answers the preflight with what is allowed, and the browser remembers it for ten minutes (Max-Age: 600). For any other origin there is no Access-Control-Allow-Origin header, and the browser refuses to give the answer to the page’s JavaScript. The Vary: Origin header tells caches that the answer depends on the Origin header, so that one site is never served a copy made for another.

Watch out: CORS is not access control

Look again at the second command: the server still answered 200 with the product. CORS is enforced by the browser, to protect the browser’s user. curl, a script or an attacker’s server ignores it completely. Anything that must be private needs authentication and authorisation on the server. And never answer Access-Control-Allow-Origin: * together with cookies: list the origins you trust, as our server does.

1.9 Inside the server

Now that you know what goes over the wire, the server holds no surprises. We read it in five parts, from the top of the file.

The settings, and a log line for every request. ORIGINS lists the only web app allowed to read our answers from a browser (1.8), MAX_BODY is the largest body we accept, and the products live in a file next to the script. header_remove('X-Powered-By') stops PHP from announcing its exact version to anyone who asks, which saves attackers a step. register_shutdown_function runs a function when the request ends, however it ends; ours writes one line to the server’s log with the method, the address, the status and the time it took:

server.php (1 of 5)
<?php
// Bit's shop API in plain PHP.
// Run: php -S localhost:8000 server.php

// the web app that may call this API from a browser
const ORIGINS = ['http://localhost:5173'];
const MAX_BODY = 1024; // bytes
const DATA = __DIR__ . '/products.json';

// do not tell attackers which PHP version runs here
header_remove('X-Powered-By');
$start = hrtime(true);
register_shutdown_function(function () use ($start) {
    $ms = intdiv(hrtime(true) - $start, 1_000_000);
    $status = http_response_code();
    $request = "{$_SERVER['REQUEST_METHOD']} {$_SERVER['REQUEST_URI']}";
    error_log("$request $status {$ms}ms");
});

One place sends answers. Every response in the file goes through send, which sets the type and the length. strlen counts bytes, which is what Content-Length needs, and JSON_UNESCAPED_UNICODE keeps Arabic text readable instead of turning every letter into \u0639. An empty body gets no type at all. fail gives every error the same shape. Because of these two functions, no route can forget a header or invent its own error format:

server.php (2 of 5)
function send(int $status, mixed $body = null, array $headers = []): void
{
    $text = $body === null ? '' : json_encode($body, JSON_UNESCAPED_UNICODE);
    http_response_code($status);
    if ($text === '') {
        header('Content-Type:'); // no body, so no type
    } else {
        header('Content-Type: application/json; charset=utf-8');
    }
    // strlen counts bytes, not characters
    header('Content-Length: ' . strlen($text));
    foreach ($headers as $name => $value) {
        header("$name: $value");
    }
    echo $text;
}

function fail(int $status, string $code, string $message,
              array $extra = [], array $headers = []): void
{
    $error = ['code' => $code, 'message' => $message] + $extra;
    send($status, ['error' => $error], $headers);
}

Routing. handle looks at the method and the path and decides what to do: the CORS headers first, for any request, then the preflight, then the list, then one product. Everything else is a 404. Notice that the 405 answer names the allowed methods, and that a HEAD is answered like a GET: PHP itself drops the body of an answer to HEAD. products() reads the file again for every request, because PHP keeps nothing in memory between requests.

server.php (3 of 5)
function products(): array
{
    // PHP forgets everything after each request: the products live in a file.
    return json_decode(file_get_contents(DATA), true);
}

function handle(): void
{
    $method = $_SERVER['REQUEST_METHOD'];
    $path = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH);
    $origin = $_SERVER['HTTP_ORIGIN'] ?? null;
    if ($origin && in_array($origin, ORIGINS, true)) {
        header("Access-Control-Allow-Origin: $origin");
        header('Vary: Origin');
    }

    if ($method === 'OPTIONS') {
        send(204, null, [
            'Access-Control-Allow-Methods' => 'GET, POST',
            'Access-Control-Allow-Headers' => 'Content-Type',
            'Access-Control-Max-Age' => '600',
        ]);
        return;
    }

    if ($path === '/products') {
        if ($method === 'GET' || $method === 'HEAD') {
            $max = (int) ($_GET['max_price'] ?? PHP_INT_MAX);
            $cheap = array_filter(products(), fn ($p) => $p['price'] <= $max);
            $list = array_values($cheap);
            $hash = md5(json_encode($list, JSON_UNESCAPED_UNICODE));
            $etag = '"' . substr($hash, 0, 16) . '"';
            if (($_SERVER['HTTP_IF_NONE_MATCH'] ?? null) === $etag) {
                send(304, null, ['ETag' => $etag]);
                return;
            }
            send(200, $list, ['ETag' => $etag, 'Cache-Control' => 'no-cache']);
            return;
        }
        if ($method === 'POST') {
            create();
            return;
        }
        fail(405, 'method_not_allowed', 'Use GET or POST here', [],
             ['Allow' => 'GET, HEAD, POST']);
        return;
    }

    if (preg_match('#^/products/(\d+)$#', $path, $m) && $method === 'GET') {
        foreach (products() as $product) {
            if ($product['id'] === (int) $m[1]) {
                send(200, $product);
                return;
            }
        }
        fail(404, 'not_found', 'No product with this id');
        return;
    }
    fail(404, 'not_found', 'Nothing here');
}

Distrust the body. Creating a product checks everything a client could get wrong, in order: the type, the size (before reading a single byte of the body), the JSON, and then each field for its type and range, collecting every error before answering. Real APIs allow more than 1 KB, but they always have a limit. Then the new product is written to the file under a lock: flock makes a second request wait until the first has finished writing, so that two new products cannot overwrite each other. This is exactly the problem databases solve properly, with transactions, in Part 2.

        return;

    $price = $data['price'] ?? null;

    }
    if (!is_int($price) || $price <= 0) {
        $errors['price'] = 'A whole number of piastres above 0';
    }
    if ($errors) {

        return;
    }

    flock($file, LOCK_EX); // two requests at once must not both write the file
    $list = json_decode(stream_get_contents($file), true);

        'id' => count($list) + 1,
        'name' => trim($name),
        'price' => $price,

    rewind($file);
    fwrite($file, json_encode($list, JSON_UNESCAPED_UNICODE));
    flock($file, LOCK_UN);
    fclose($file);

}

Professional habit: look at the wire first

When an API “does not work”, do not change code at random. Reproduce the request with curl -v, or copy it from the browser’s Network panel (“Copy as cURL”), and read the request and the answer line by line: the method, the address, the Content-Type, the status, the error body. Nine times out of ten the problem is in plain sight there. Keep the working curl command in the bug report or the pull request, so the next person can check it in one line.

Summary

  • A request goes through a name lookup, a TCP connection, TLS for HTTPS, and then the HTTP request and response.
  • HTTP/1.1 is text: a first line, headers, an empty line, and a body whose size is in Content-Length, in bytes.
  • The path names a resource; the query string filters and pages.
  • Safe methods only read; idempotent ones can be repeated. POST is neither, so retries need idempotency keys.
  • 2xx worked, 3xx look elsewhere, 4xx the client’s mistake, 5xx the server’s. Errors have one shape, with a stable code and a readable message.
  • ETag and If-None-Match turn repeated reads into empty 304 answers; Cache-Control says how long a copy may be reused.
  • Connections are kept alive and reused; HTTP/2 and HTTP/3 change the transport, not the meaning.
  • CORS lets a browser page read answers from another origin. It protects browser users; it does not protect your server.
  • Every server, with or without a framework, needs: one way to answer, distrust of input, limits, caught errors and a log line per request.

HTTP over a bare socket

2.2 Types, and the strict mode

PHP checks types when the code runs. A function declares the types of its parameters and of its result, much as in TypeScript. But by default, PHP tries to convert a value of the wrong type before it gives up:

demos/loose.php

    return $price * $quantity;

2.4 Arrays: lists and maps in one

PHP has one array type for what JavaScript splits into arrays and plain objects. Its keys are integers or strings, and it keeps them in the order you add them:

demos/arrays.php
<?php

declare(strict_types=1);

// One type, two uses: a list (keys 0, 1, 2...) and a map (keys you choose).
$prices = [45000, 6000, 12500];
$product = ['id' => 1, 'name' => 'Robot kit', 'price' => 45000];

$prices[] = 2500; // push
echo count($prices), ' ', $product['name'], ' ', $product['stock'] ?? 0, "\n";

// Unlike JavaScript, assigning an array copies it
$copy = $prices;
$copy[] = 99;
echo count($prices), ' ', count($copy), "\n";

// Destructuring, like JavaScript
[$first, $second] = $prices;
['name' => $name, 'price' => $price] = $product;
echo "$first $second $name $price\n";

// map, filter, reduce: careful, the order of the arguments differs
$cheap = array_filter($prices, fn (int $p) => $p < 10000);
$doubled = array_map(fn (int $p) => $p * 2, $prices);
$sum = array_reduce($prices, fn (int $carry, int $p) => $carry + $p, 0);
print_r($cheap); // the keys are kept: 1 and 3, not 0 and 1
echo json_encode(array_values($cheap)), ' ', json_encode($doubled), " $sum\n";

// PHP 8.4: find, any, all
$big = array_find($prices, fn (int $p) => $p > 10000);
$any = array_any($prices, fn (int $p) => $p > 40000);
$all = array_all($prices, fn (int $p) => $p > 0);
var_dump($big, $any, $all);

// PHP 8.5: the pipe operator passes the value on the left to the callable on the right
$label = '  Robot kit  ' |> trim(...) |> mb_strtoupper(...) |> (fn (string $s) => "[$s]");
echo $label, "\n";

Line by line, the points that catch JavaScript developers:

  • $prices[] = 2500 appends, like push. ?? gives a default when a key is missing (or null), exactly as in JavaScript.
  • Arrays are values. $copy = $prices makes a copy; adding to the copy left the original with 4 items. In JavaScript, both names would point to the same array. Objects, on the other hand, are shared in PHP as in JavaScript.
  • Destructuring uses square brackets for both kinds: [$first, $second] by position, ['name' => $name] by key.
  • The array functions take their arguments in different orders: array_map(callback, array) but array_filter(array, callback). Your editor will remind you; there is no logic to remember.
  • array_filter keeps the keys: the cheap prices are at keys 1 and 3. Encoded as JSON, an array with gaps in its keys becomes an object, not a list. Pass the result through array_values, as the next line does, whenever you need a list again.

  • PHP 8.5 added the pipe operator |>: it passes the value on its left to the function on its right, so a chain of steps reads from left to right instead of from the inside out. trim(...) with three dots is a first-class callable: the function itself, like writing trim without calling it in JavaScript.

2.5 Functions and closures

A function written inside another piece of code can use the variables around it. JavaScript simply shares them. PHP is more careful, and this is the rule from Bit’s story:

demos/closures.php
<?php

declare(strict_types=1);

$discount = 10;
// fn captures by value, automatically
$apply = fn (int $price): int => $price - intdiv($price * $discount, 100);
$discount = 50; // too late: fn already copied 10
echo $apply(45000), "\n";

$count = 0;
// function () needs use to capture, also by value
$increment = function () use ($count): int {
    return ++$count;
};
$increment();
$increment();
echo $count, "\n"; // still 0: the closure changed its own copy

// &$count: by reference, the JavaScript way
$counter = function () use (&$count): void {
    $count++;
};
$counter();
$counter();
echo $count, "\n";

// Named arguments: skip to the one you need, in any order
echo str_pad(string: '7', length: 3, pad_string: '0', pad_type: STR_PAD_LEFT), "\n";
echo json_encode(['name' => 'Robot kit'], flags: JSON_UNESCAPED_UNICODE), "\n";
Terminal

  • An arrow function, fn (...) => expression, captures the variables it uses automatically, by value, when it is created. Changing $discount afterwards changes nothing: the price is 40500, 10% off.
  • A full function () { ... } captures nothing unless you list the variables in use, again by value. That is why $count stayed 0: each call increased the closure’s own copy.
  • To share a variable the JavaScript way, capture it by reference with &. Use this rarely; a function that returns a new value is easier to follow.
  • Named arguments let you pass arguments by name, in any order, skipping the optional ones you do not need. Laravel uses them often, and they make long calls readable.

Now the classes. Bit’s shop needs money that never loses a piastre, and currencies that cannot be mistyped. A currency is a fixed set of values, which is exactly what an enum is:

src/Currency.php
<?php

declare(strict_types=1);

namespace Shop;

enum Currency: string
{
    case EGP = 'EGP';
    case SAR = 'SAR';
    case USD = 'USD';

    public function symbol(): string
    {
        return match ($this) {
            self::EGP => 'E£',
            self::SAR => 'SR',
            self::USD => '$',
        };
    }
}

A backed enum has a value for each case (here the ISO code), so it can be stored in a database and read back. Enums can have methods. match is a stricter switch: it compares with ===, returns a value, has no fall-through, and throws an error if no case matches, so a new currency cannot be forgotten silently.

src/Money.php
<?php

declare(strict_types=1);

namespace Shop;

use InvalidArgumentException;

// readonly: set once, in the constructor, never again
final readonly class Money
{
    // constructor promotion: the parameters are the properties
    public function __construct(
        public int $amount, // minor units: piastres, halalas, cents
        public Currency $currency,
    ) {
        if ($amount < 0) {
            throw new InvalidArgumentException('An amount cannot be negative');
        }
    }

    public function plus(Money $other): Money
    {
        if ($other->currency !== $this->currency) {
            throw new CurrencyMismatch($this->currency, $other->currency);
        }
        return new Money($this->amount + $other->amount, $this->currency);
    }

    public function times(int $quantity): Money
    {
        return new Money($this->amount * $quantity, $this->currency);
    }

    public function format(): string
    {
        $whole = intdiv($this->amount, 100);
        $cents = str_pad((string) ($this->amount % 100), 2, '0', STR_PAD_LEFT);
        return "{$this->currency->symbol()} " . number_format($whole) . ".$cents";
    }
}
  • Constructor promotion: parameters marked public in the constructor become properties. Six lines of boilerplate disappear.
  • readonly class: every property can be set once, in the constructor, and never again. A Money value never changes: plus and times return new objects. This is the same immutability you used in React and Vue state, and it removes a whole family of bugs.
  • final: nobody can extend the class. Make classes final unless they are designed to be extended.
  • The constructor refuses a negative amount, and plus refuses to add different currencies. An object that checks its own rules can never exist in a broken state.

The currency error is a class of its own, so that code can catch exactly this error and nothing else:

src/CurrencyMismatch.php
<?php

declare(strict_types=1);

namespace Shop;

use DomainException;

final class CurrencyMismatch extends DomainException
{
    public function __construct(
        public readonly Currency $left,
        public readonly Currency $right,
    ) {
        $message = strtr('Cannot add {a} to {b}', [
            '{a}' => $right->value,
            '{b}' => $left->value,
        ]);
        parent::__construct($message);
    }
}

The cart uses two features from PHP 8.4:

src/Cart.php
<?php

declare(strict_types=1);

namespace Shop;

use InvalidArgumentException;

final class Cart
{
    // anyone can read it; only the class can change it
    /** @var array<int, array{product: Product, quantity: int}> */
    public private(set) array $lines = [];

    // a property hook: read like a property, computed like a method
    public Money $total {
        get => array_reduce(
            $this->lines,
            fn (Money $sum, array $line) => $sum->plus(
                $line['product']->price->times($line['quantity']),
            ),
            new Money(0, $this->currency),
        );
    }

    public int $count {
        get => array_sum(array_column($this->lines, 'quantity'));
    }

    public function __construct(public readonly Currency $currency) {}

    public function add(Product $product, int $quantity = 1): static
    {
        if ($quantity < 1) {
            throw new InvalidArgumentException('Quantity must be at least 1');
        }
        $current = $this->lines[$product->id]['quantity'] ?? 0;
        $this->lines[$product->id] = [
            'product' => $product,
            'quantity' => $current + $quantity,
        ];
        return $this;
    }
}
  • public private(set) is asymmetric visibility: anyone may read $lines, only the class may change it. Before PHP 8.4 this needed a private property and a getter method.
  • $total and $count have property hooks: they are read like properties ($cart->total) but computed by the get code every time, like a getter in a JavaScript class. The total is always correct, because it is never stored.
  • add returns static, the cart itself, so calls can be chained.

Finally, a product, with one more PHP 8.5 feature:

src/Product.php
<?php

declare(strict_types=1);

namespace Shop;

final readonly class Product
{
    public function __construct(
        public int $id,
        public string $name,
        public Money $price,
    ) {}

    // PHP 8.5: clone with new values. Nothing changes: you get a changed copy.
    public function onSale(int $percent): static
    {
        $amount = intdiv($this->price->amount * (100 - $percent), 100);
        return clone($this, [
            'name' => "{$this->name} (-{$percent}%)",
            'price' => new Money($amount, $this->price->currency),
        ]);
    }
}

Tip: Exception and Error

Everything that can be thrown implements Throwable. Exception and its subclasses are for problems your program expects and can handle: an invalid argument, a missing record, a currency mismatch. Error and its subclasses (TypeError, ValueError, and the visibility errors above) mean the code itself is wrong. Catch exceptions where you can do something useful about them; let errors reach the framework, which logs them and answers 500, as our server did in Chapter 1.

2.8 How PHP runs on a server

You saw in Chapter 1 that PHP starts each request with an empty memory and forgets everything when it ends. Two details complete the picture. First, PHP does not parse your files again for every request: OPcache keeps the compiled code in shared memory, so only your code’s work is repeated, not the parsing. Second, servers such as FrankenPHP (with Laravel Octane) can run in worker mode, keeping the application in memory between requests for speed, like a Node server. Then static properties and singletons survive from one request to the next, and code that was safe under shared-nothing may leak one user’s data into another’s request. We return to this when we measure performance in Chapter 15.

The controller holds one method per route. It stays thin: it reads the request, asks someone else to do the work, and builds the response.

app/Http/Controllers/ProductController.php
<?php

declare(strict_types=1);

namespace App\Http\Controllers;

use App\Catalog\ProductCatalog;
use App\Http\Requests\StoreProductRequest;
use App\Http\Requests\UpdateProductRequest;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Illuminate\Http\Response;

final class ProductController extends Controller
{
    // the container builds the controller and passes it a catalog
    public function __construct(private readonly ProductCatalog $catalog) {}

    public function index(Request $request): JsonResponse
    {
        $max = $request->integer('max_price', PHP_INT_MAX);
        $products = array_filter(
            $this->catalog->all(),
            fn (array $p) => $p['price'] <= $max,
        );

        return $this->json(['data' => array_values($products)]);
    }

    public function show(int $product): JsonResponse
    {
        return $this->json(['data' => $this->findOrFail($product)]);
    }

    public function store(StoreProductRequest $request): JsonResponse
    {
        // only the checked fields, nothing else the client sent
        $product = $this->catalog->create($request->validated());

        return $this
            ->json(['data' => $product], 201)
            ->header('Location', route('products.show', $product['id']));
    }

    public function update(UpdateProductRequest $request, int $product): JsonResponse
    {
        $this->findOrFail($product);
        $changed = $this->catalog->update($product, $request->validated());

        return $this->json(['data' => $changed]);
    }

    public function destroy(int $product): Response
    {
        $this->findOrFail($product);
        $this->catalog->delete($product);

        return response()->noContent();
    }

    // Without the flag, Laravel writes every non-English letter as \u0643 and so on.
    private function json(array $data, int $status = 200): JsonResponse
    {
        return response()->json($data, $status, [], JSON_UNESCAPED_UNICODE);
    }

    private function findOrFail(int $id): array
    {
        $product = $this->catalog->find($id);
        if ($product === null) {
            abort(404, __('There is no product :id.', ['id' => $id]));
        }

        return $product;
    }
}
  • The route parameter {product} arrives as the argument $product, by name.
  • $request->integer('max_price', PHP_INT_MAX) reads a query value as an int, with a default: no $_GET, no casting by hand.
  • abort(404, …) stops the request with that status from anywhere, and the exception handler turns it into a JSON answer.
  • route('products.show', 4) builds the URL from the route’s name, so URLs are never written twice.
  • $this->json is a small helper of ours. By default, Laravel writes JSON with every non-English letter escaped as ك: valid, but unreadable for people. The flag JSON_UNESCAPED_UNICODE keeps Arabic as Arabic, as in Chapter 1.

3.4 The service container

The controller’s constructor asks for a ProductCatalog, and nobody calls new ProductController. Laravel’s service container builds the controller: it reads the constructor’s types, builds what each parameter needs (and what those need, all the way down), and passes them in. This is dependency injection: a class says what it needs, and does not go looking for it.

ProductCatalog is an interface, a contract that says what a catalog can do, not how:

app/Catalog/ProductCatalog.php
<?php

declare(strict_types=1);

namespace App\Catalog;

// What the controllers need from a catalog, not how it stores products.
interface ProductCatalog
{
    /** @return list<array{id: int, name: string, price: int, stock: int}> */
    public function all(): array;

    /** @return array{id: int, name: string, price: int, stock: int}|null */
    public function find(int $id): ?array;

    /** @param array{name: string, price: int, stock?: int} $data */
    public function create(array $data): array;

    public function update(int $id, array $data): ?array;

    public function delete(int $id): bool;
}

The container cannot build an interface, so we tell it which class to use, in a service provider, a class Laravel runs at start-up to register things:

app/Providers/AppServiceProvider.php
<?php

namespace App\Providers;

use App\Catalog\JsonProductCatalog;
use App\Catalog\ProductCatalog;
use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Ask for a ProductCatalog, get this one: built once per request cycle.
        $this->app->singleton(
            ProductCatalog::class,
            fn () => new JsonProductCatalog(config('shop.catalog_file')),
        );
    }

    public function boot(): void
    {
        // At most N requests a minute per address; N comes from config/shop.php.
        RateLimiter::for('api', function (Request $request) {
            $perMinute = config('shop.requests_per_minute');

            return Limit::perMinute($perMinute)->by($request->ip());
        });
    }
}

The real catalog keeps products in a JSON file, under a lock, exactly like Chapter 1’s server. Because PHP forgets everything between requests, storage must live outside the process:

app/Catalog/JsonProductCatalog.php
    private function change(callable $edit): mixed
    {
        $file = fopen($this->path, 'c+');
        // the lock makes a second request wait while the first one writes
        flock($file, LOCK_EX);
        $text = stream_get_contents($file);
        [$store, $result] = $edit($text ? json_decode($text, true) : self::seed());
        ftruncate($file, 0);
        rewind($file);
        fwrite($file, json_encode($store, JSON_UNESCAPED_UNICODE));
        flock($file, LOCK_UN);
        fclose($file);

        return $result;
    }

Every change goes through this one method: it opens the file, waits for the lock, lets the caller edit the data, and writes it back. create, update and delete only describe the edit.

Why the interface? Because the controller does not care where products are kept. In Chapter 6 we write a catalog backed by the database and change one line in the provider; no controller changes. And in tests, we can give the controller a different catalog, as you will see in 3.8.

3.6 Middleware and rate limits

A middleware wraps every request in a group. It can look at the request, refuse it, change it, and look at the response on the way back. Ours measures how long the application took and reports it in a Server-Timing header, which browsers’ developer tools display:

app/Http/Middleware/AddServerTiming.php
<?php

declare(strict_types=1);

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

// Adds the time the app spent on the request, which browsers' developer tools show.
final class AddServerTiming
{
    public function handle(Request $request, Closure $next): Response
    {
        $start = hrtime(true);
        $response = $next($request); // everything after this middleware runs here
        $ms = (hrtime(true) - $start) / 1_000_000;
        $response->headers->set('Server-Timing', sprintf('app;dur=%.1f', $ms));

        return $response;
    }
}

Everything before $next($request) runs on the way in; everything after it runs on the way out. bootstrap/app.php appends it to the API group, and throttleApi() adds Laravel’s rate limiter, using the api limiter defined in the service provider:

4.1 Resources and URLs

REST organises an API around resources: the nouns of your domain, such as products and orders. URLs name the resources; methods say what to do with them. The rules that make an API guessable are few:

  • Nouns, plural, lower case: /products, /orders. The method is the verb: GET /products, not /getProducts.
  • One resource: the collection plus an id, /products/2.
  • Nesting for ownership, one level deep: /orders/7/items is fine; /customers/3/orders/7/items/2 is not.
  • Actions that are not create, read, update or delete become a sub-resource with POST: POST /orders/7/cancel. Do not hide them in a PATCH that sets status: cancelling has rules (restore the stock, refund the payment) that a generic update would skip.
  • A version in the path: /api/v1/.... Make every change additive if you can; when a breaking change cannot be avoided, publish /v2 beside /v1 and announce the end of /v1 with the Deprecation and Sunset headers.
routes/api.php
<?php

use App\Http\Controllers\OrderController;
use App\Http\Controllers\ProductController;
use App\Http\Middleware\Idempotent;
use Illuminate\Support\Facades\Route;

Route::prefix('v1')->group(function () {
    Route::apiResource('products', ProductController::class)
        ->only(['index', 'show', 'update']);

    Route::controller(OrderController::class)->group(function () {
        Route::post('orders', 'store')->middleware(Idempotent::class)->name('orders.store');
        Route::get('orders/{order}', 'show')->name('orders.show');
        Route::post('orders/{order}/cancel', 'cancel')->name('orders.cancel');
    });
});

Products are read and updated through a resource controller. Orders have their own controller; Route::controller groups its routes, and the cancel action is a sub-resource. Creating an order goes through an extra middleware, Idempotent, which we write in 4.5.

4.3 API Resources: the representation

A database row and the JSON a client receives are two different things, and they should change for different reasons. The table may gain internal columns; the JSON is a promise to other developers. An API Resource is the class that turns one into the other:

app/Http/Resources/ProductResource.php
<?php

namespace App\Http\Resources;

use App\Models\Product;
use Illuminate\Http\Request;
use Illuminate\Http\Resources\Json\JsonResource;

/** @mixin Product */
class ProductResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        // version is internal: the client sees it only as the ETag
        return [
            'id' => $this->id,
            'name' => $this->name,
            'price' => Money::of($this->price),
            'stock' => $this->stock,
            'created_at' => $this->created_at->toIso8601ZuluString(),
        ];
    }
}

Fix the conventions of the representation once, and keep them everywhere:

  • One naming style. We use snake_case, as Laravel does.
  • Times in ISO 8601, in UTC: 2026-11-01T09:00:00Z. Clients convert to the user’s time zone.
  • Money as an object, the amount in minor units with its currency. One helper makes it the same in every resource:
app/Http/Resources/Money.php
<?php

namespace App\Http\Resources;

final class Money
{
    /** @return array{amount: int, currency: string} */
    public static function of(int $amount): array
    {
        return ['amount' => $amount, 'currency' => config('shop.currency')];
    }
}
  • Internal columns stay inside. version and updated_at are not in the resource; adding a column to the table changes nothing for clients.
  • Lists in an object, never a bare array, so that page information has a place: Laravel adds data, links and meta for you.

One more convention needs a line of code: by default Laravel writes every non-English letter as ك. A small middleware adds JSON_UNESCAPED_UNICODE to every JSON answer of the API, once, instead of in every controller:

app/Http/Middleware/UnescapedJson.php
final class UnescapedJson
{
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);
        if ($response instanceof JsonResponse) {
            $options = $response->getEncodingOptions();
            $options |= JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES;
            $response->setEncodingOptions($options);
        }

        return $response;
    }
}

4.4 Lists: filters, sorting and cursor pages

Everything a client may send to the list is in a form request, with limits on every value:

app/Http/Requests/ListProductsRequest.php
    public function rules(): array
    {
        return [
            'limit' => ['sometimes', 'integer', 'between:1,50'],
            'sort' => ['sometimes', 'in:id,price,-price,name'],
            'min_price' => ['sometimes', 'integer', 'min:0'],
            'max_price' => ['sometimes', 'integer', 'min:0'],
            'cursor' => ['sometimes', 'string'],
        ];
    }

Only four sort orders exist. An API that sorts by any field the client names can be asked to sort by a column without an index, which makes a slow query one attacker can repeat a thousand times a minute.

The obvious way to page is an offset, ?page=2, meaning “skip the first 20”. It has two problems: the database must still walk past every skipped row, so deep pages are slow; and the pages drift when rows are added or removed between two requests, so a user sees one product twice, or never. A cursor says “continue after this row” instead, so new rows before it change nothing. Laravel builds cursors with cursorPaginate:

app/Http/Controllers/ProductController.php
    public function index(ListProductsRequest $request): AnonymousResourceCollection
    {
        $sort = $request->validated('sort', 'id');
        $direction = str_starts_with($sort, '-') ? 'desc' : 'asc';
        $min = $request->validated('min_price');
        $max = $request->validated('max_price');

        $products = Product::query()
            ->when($min !== null, fn ($query) => $query->where('price', '>=', $min))
            ->when($max !== null, fn ($query) => $query->where('price', '<=', $max))
            ->orderBy(ltrim($sort, '-'), $direction)
            // a complete order: the same price is decided by id
            ->orderBy('id', $direction)
            ->cursorPaginate((int) $request->validated('limit', 5))
            ->withQueryString();

        return ProductResource::collection($products);
    }

The second orderBy matters. A cursor needs a complete order: two products with the same price must still have a fixed place, or a row could move from one page to the next between requests. Ordering by price and then by id makes every position unique, and the migration’s index on (price, id) lets the database find it directly. Here is the client’s side:

4.5 Errors: Problem Details

Laravel’s default error answers, which you saw in Chapter 3, have a shape of their own. Every API with its own shape forces every client to learn it. Problem Details (RFC 9457) is the standard shape for HTTP API errors, sent with the content type application/problem+json: a type URL that identifies the kind of problem and leads to its documentation, a short title, the status, a detail for this case, and the instance, the request that failed. Extra members are allowed, such as a list of errors.

A problem is an exception that knows how to render itself:

app/Http/Problem.php
final class Problem extends HttpException
{
    public function __construct(
        int $status,
        public readonly string $slug,
        public readonly string $title,
        public readonly ?string $detail = null,
        public readonly array $extra = [],
        array $headers = [],
    ) {
        parent::__construct($status, $detail ?? $title, null, $headers);
    }

    public function render(Request $request): JsonResponse
    {
        $body = [
            'type' => "https://bit-shop.example/problems/{$this->slug}",
            'title' => $this->title,
            'status' => $this->getStatusCode(),
            'detail' => $this->detail,
            'instance' => $request->getRequestUri(),
            ...$this->extra,
        ];
        $body = array_filter($body, fn ($value) => $value !== null);
        $headers = ['Content-Type' => 'application/problem+json', ...$this->getHeaders()];
        $flags = JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES;

        return response()->json($body, $this->getStatusCode(), $headers, $flags);
    }
}

One class decides how every other exception becomes a problem: validation errors, models that were not found, rate limits, other HTTP errors, and anything unexpected as a plain 500. It also makes the problems the API throws on purpose, so no controller invents a new status code or a new shape:

app/Http/Problems.php
    public static function from(Throwable $e): Problem
    {
        return match (true) {
            $e instanceof Problem => $e,
            $e instanceof ValidationException => new Problem(422, 'invalid-request',
                __('problems.invalid'), null, ['errors' => self::errors($e)]),
            $e instanceof NotFoundHttpException => self::notFound($e->getPrevious()),
            $e instanceof ThrottleRequestsException => new Problem(
                429, 'too-many-requests', __('problems.limit'), null, [], $e->getHeaders()),
            $e instanceof HttpExceptionInterface => new Problem(
                $e->getStatusCode(), 'http-error', $e->getMessage() ?: __('problems.server')),
            default => new Problem(500, 'server-error', __('problems.server')),
        };
    }

match (true) takes the first arm whose condition holds, a common PHP idiom for a list of type checks. The texts come from a language file, lang/en/problems.php, read by __('problems.stale') in the app’s language. And one line in bootstrap/app.php sends every exception in the API through it:

bootstrap/app.php
    ->withExceptions(function (Exceptions $exceptions): void {
        // Every error in the API becomes Problem Details;
        // the web pages keep Laravel's usual error pages.
        $exceptions->render(function (Throwable $e, Request $request) {
            if ($request->is('api/*')) {
                return Problems::from($e)->render($request);
            }
        });
    })->create();

4.6 Safe retries: idempotency keys

Chapter 1 warned that a retried POST can create an order twice. The standard answer, used by payment providers such as Stripe, is an idempotency key: the client creates a unique value (a UUID) for each intended operation and sends it in an Idempotency-Key header. If the same key arrives again, the server does not do the work again; it replays the answer it gave the first time. This is a job for middleware, because it wraps the controller without the controller knowing:

app/Http/Middleware/Idempotent.php
final class Idempotent
{
    public function handle(Request $request, Closure $next): Response
    {
        $key = (string) $request->header('Idempotency-Key');
        if (strlen($key) < 8 || strlen($key) > 100) {
            throw new Problem(400, 'invalid-request', __('problems.invalid'),
                __('problems.key'));
        }
        $id = 'idempotency:'.$key;
        $fingerprint = hash('sha256', $request->getContent());

        $lock = Cache::lock($id.':lock', 30); // one request per key at a time
        if (! $lock->get()) {
            throw new Problem(409, 'in-progress', __('problems.in_progress'),
                __('problems.in_progress_detail'));
        }
        try {
            $saved = Cache::get($id);
            if ($saved !== null) {
                if ($saved['fingerprint'] !== $fingerprint) {
                    throw new Problem(422, 'idempotency-key-reused',
                        __('problems.reused'), __('problems.reused_detail'));
                }
                $headers = array_filter($saved['headers']);
                $headers['Idempotent-Replayed'] = 'true';

                return response($saved['body'], $saved['status'], $headers);
            }
            $response = $next($request);
            if ($response->isSuccessful()) {
                // kept a day; a failed request is not kept, so it may be retried
                Cache::put($id, [
                    'fingerprint' => $fingerprint,
                    'status' => $response->getStatusCode(),
                    'body' => $response->getContent(),
                    'headers' => [
                        'Content-Type' => $response->headers->get('Content-Type'),
                        'Location' => $response->headers->get('Location'),
                    ],
                ], now()->addDay());
            }

            return $response;
        } finally {
            $lock->release();
        }
    }
}
  • A lock on the key makes a second request that arrives while the first is still running get a 409, instead of doing the work twice. Cache::lock works across all the PHP processes of a server, because the lock lives in the cache store (here the database; Redis in Chapter 8).
  • A fingerprint of the body is kept with the answer. The same key with a different body is a bug in the client, and gets a 422, never a silent replay of a different order.
  • Only successful answers are kept, for a day. A request that failed may be tried again with the same key.

The controller creates the order inside a database transaction: either every change happens, or none does:

app/Http/Controllers/OrderController.php
    public function store(StoreOrderRequest $request): JsonResponse
    {
        // anything thrown here undoes the whole transaction, stock included
        $order = DB::transaction(function () use ($request) {
            $items = [];
            foreach ($request->validated('items') as $line) {
                ['product_id' => $id, 'quantity' => $quantity] = $line;
                // take stock only if there is enough: two orders never get the last one
                $taken = Product::whereKey($id)
                    ->where('stock', '>=', $quantity)
                    ->decrement('stock', $quantity, [
                        'version' => DB::raw('version + 1'),
                    ]);
                $product = Product::findOrFail($id);
                if ($taken === 0) {
                    throw Problems::outOfStock($id, $product->stock);
                }
                // the price comes from the database, never from the client
                $items[] = [
                    'product_id' => $id,
                    'quantity' => $quantity,
                    'price' => $product->price,
                ];
            }
            $total = array_sum(array_map(
                fn ($item) => $item['price'] * $item['quantity'],
                $items,
            ));
            $order = Order::create(['status' => 'pending', 'total' => $total]);
            $order->items()->createMany($items);

            return $order;
        });

        return OrderResource::make($order->load('items'))
            ->response()
            ->setStatusCode(201)
            ->header('Location', route('orders.show', $order));
    }

The stock is taken with one conditional statement, “decrease the stock by 2 where the stock is at least 2”, and the number of changed rows says whether it worked. Reading the stock first and writing it afterwards would let two orders both see the last kit and both take it; Chapter 7 explains why, and the other tools for it. If anything throws, the transaction is rolled back, so an order that fails on its third item gives back the stock of the first two. And the prices come from the database: a client never tells the server what something costs.

4.7 Lost updates: ETag and If-Match

Two administrators open product 2 at the same time. Sara changes the price to 65.00 and saves; a minute later Omar, whose screen still shows the old product, changes it to 70.00 and saves. Sara’s change is gone, and nobody was told. This is the lost update problem. HTTP solves it with the ETag from Chapter 1: the product’s version is its ETag, and a change must send back, in If-Match, the version it was based on:

app/Http/Controllers/ProductController.php
    public function show(Request $request, Product $product): JsonResponse
    {
        $response = ProductResource::make($product)->response();
        $response->setEtag((string) $product->version);
        // 304 and no body when If-None-Match matches
        $response->isNotModified($request);

        return $response;
    }

    public function update(
        UpdateProductRequest $request,
        Product $product,
    ): JsonResponse {
        $ifMatch = $request->header('If-Match');
        if ($ifMatch === null) {
            throw Problems::needIfMatch();
        }
        // one statement: change it only if the version is the one the client read
        $changed = Product::whereKey($product->id)
            ->where('version', (int) trim($ifMatch, '"'))
            ->update([...$request->validated(), 'version' => DB::raw('version + 1')]);
        if ($changed === 0) {
            throw Problems::stale();
        }

        return $this->show($request, $product->refresh());
    }

show sets the ETag, and Symfony’s isNotModified turns the answer into an empty 304 when the client already has this version. update refuses a request without If-Match, and then changes the row only if its version is still the one the client read, raising it by one in the same statement. If no row changed, someone else got there first:

5.1 Tables, types and rules

A relational database stores data in tables. Each table has fixed columns, each with a type, and any number of rows. Tables refer to each other through ids. Here is the shop:

schema.sql
CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- the database numbers the rows itself; nobody sends an id
  name       text NOT NULL,
  email      text NOT NULL UNIQUE,
  city       text,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  price integer NOT NULL CHECK (price > 0), -- piastres: whole numbers, never fractions
  stock integer NOT NULL DEFAULT 0 CHECK (stock >= 0) -- the database refuses negative stock, whatever the application does
);

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers (id),
  status      text NOT NULL DEFAULT 'pending'
              CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')), -- only these four values can ever be stored
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_id   bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
  product_id bigint NOT NULL REFERENCES products (id),
  quantity   integer NOT NULL CHECK (quantity BETWEEN 1 AND 99),
  price      integer NOT NULL, -- the price when the order was made: prices change, orders must not
  PRIMARY KEY (order_id, product_id) -- a product appears once per order
);

Read it slowly, because every word is a decision:

  • Types. bigint for ids, because integer stops at about two billion. text for strings, with no arbitrary length limit (PostgreSQL stores text and varchar the same way). integer for money in piastres. timestamptz for moments in time: it stores an exact instant, in UTC, and never confuses time zones. Never use timestamp without a time zone for events.
  • GENERATED ALWAYS AS IDENTITY numbers rows automatically. It is the standard way; the older serial works too.
  • PRIMARY KEY identifies each row: unique, never null, and indexed.
  • NOT NULL, UNIQUE and CHECK are rules the database enforces on every write.
  • REFERENCES is a foreign key: an order cannot point to a customer who does not exist. ON DELETE CASCADE deletes an order’s items with the order.
  • order_items has a composite primary key: one row per product per order. It also copies the price, because product prices change and an order must not.

5.3 Joins: combining tables

A join puts together rows from several tables that belong together. To list each named customer’s orders with their totals, the query joins customers to their orders and orders to their items, then groups the items of each order:

psql
# Join the tables: each named customer's orders with their totals
shop=# SELECT c.name, o.id, o.status, sum(i.quantity * i.price) AS total
shop-# FROM customers c
shop-# JOIN orders o ON o.customer_id = c.id
shop-# JOIN order_items i ON i.order_id = o.id
shop-# WHERE c.id <= 7
shop-# GROUP BY c.name, o.id, o.status
shop-# ORDER BY o.id;

shop=# SELECT c.name, count(o.id) AS orders

shop-# LEFT JOIN orders o ON o.customer_id = c.id

5.4 Grouping and summarising

GROUP BY makes one result row per group, and aggregates summarise each group. HAVING filters the groups, as WHERE filters rows:

psql
# The products that bring in the most money
shop=# SELECT p.name, sum(i.quantity) AS units, sum(i.quantity * i.price) / 100 AS revenue
shop-# FROM order_items i
shop-# JOIN orders o ON o.id = i.order_id
shop-# JOIN products p ON p.id = i.product_id
shop-# WHERE o.status <> 'cancelled'
shop-# GROUP BY p.name
shop-# HAVING sum(i.quantity) > 26600
shop-# ORDER BY revenue DESC;
      name      | units | revenue 
----------------+-------+---------
 Battery pack   | 26878 | 3359750
 Gear box       | 26694 | 2936340
 Remote control | 26673 | 2133840
 Speaker        | 26676 | 2000700
 LED strip      | 27350 | 1094000
 USB cable      | 26699 |  667475
(6 rows)

Read the order in which the database works, which is not the order in which the query is written: FROM and the joins first, then WHERE (cancelled orders go), then GROUP BY, then HAVING (products that sold 26,600 units or fewer go), then SELECT, then ORDER BY. That is why WHERE cannot use sum(...): when it runs, there are no groups yet.

Money is still in piastres in the sums, and divided by 100 only at the end, for display. Integer division would be wrong for an amount like 12,550 piastres; here every revenue happens to be whole pounds. In an API, send piastres and let the client format them.

5.5 CTEs and window functions

Some questions need a result to build on. “Rank the named customers by what they spent, and show each one’s share” needs the totals first, then a ranking over them:

psql
# A CTE and a window function: rank the named customers by what they spent
shop=# WITH spent AS (
shop-#   SELECT o.customer_id, sum(i.quantity * i.price) AS total
shop-#   FROM orders o
shop-#   JOIN order_items i ON i.order_id = o.id
shop-#   WHERE o.status <> 'cancelled'
shop-#   GROUP BY o.customer_id
shop-# )
shop-# SELECT c.name, s.total,
shop-#        rank() OVER (ORDER BY s.total DESC) AS place,
shop-#        round(s.total * 100.0 / sum(s.total) OVER (), 1) AS percent
shop-# FROM spent s
shop-# JOIN customers c ON c.id = s.customer_id
shop-# WHERE c.id <= 7
shop-# ORDER BY place;
  name   | total | place | percent 
---------+-------+-------+---------
 Youssef | 97500 |     1 |    41.6
 Sara    | 74000 |     2 |    31.6
 Omar    | 42000 |     3 |    17.9
 Mona    | 21000 |     4 |     9.0
(4 rows)
  • WITH spent AS (…) is a common table expression (CTE): a named query used by the next one. It reads like a variable, and keeps long queries understandable.
  • rank() OVER (ORDER BY …) is a window function: it computes over a set of rows without collapsing them, unlike GROUP BY. Each customer keeps their row and gets a rank.
  • sum(s.total) OVER () is an aggregate used as a window over all rows: the grand total, next to every row, so each row can compute its share.

Window functions answer the questions reports always ask: rankings, running totals, the previous month for comparison (lag), the top three per category. Without them, you would write loops in code over thousands of rows.

The upsert is one statement, so two requests that register the same email at the same moment cannot both insert: the database decides. Watch out: UPDATE and DELETE without WHERE

DELETE FROM orders; deletes every order, instantly, without asking. Before running an UPDATE or a DELETE by hand, run the same WHERE as a SELECT and check the rows. Better still, start a transaction with BEGIN;, run the change, look at the result, and only then COMMIT; (or ROLLBACK;). Chapter 7 explains transactions.

5.7 Indexes and query plans

The orders table has a hundred thousand rows. How does PostgreSQL find the orders of customer 1234? EXPLAIN shows the plan the database chose; with ANALYZE, it also runs the query and reports what really happened:

psql
# How does PostgreSQL find one customer's orders?
shop=# EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF)
shop-# SELECT count(*) FROM orders WHERE customer_id = 1234;
                               QUERY PLAN                               
------------------------------------------------------------------------
 Aggregate (actual time=5.177..5.178 rows=1.00 loops=1)
   ->  Seq Scan on orders (actual time=0.067..5.166 rows=44.00 loops=1)
         Filter: (customer_id = 1234)

         Heap Blocks: exact=44

Now the database goes straight to the 44 rows through the index: several times faster here, and the gap widens as the table grows, because a B-tree lookup takes about the same time for a million rows as for a thousand. Three rules about indexes:

  • PostgreSQL does not index foreign keys for you. orders.customer_id had no index until we added one. Index the foreign keys you search or join by.
  • An index serves the queries that match it. A query that wraps the column in a function cannot use a plain index on the column. You can index the expression itself:
psql
# An index on an expression, for case-insensitive email lookups
shop=# EXPLAIN (COSTS OFF)
shop-# SELECT id FROM customers WHERE lower(email) = 'sara@example.com';
                     QUERY PLAN                      
-----------------------------------------------------
 Seq Scan on customers
   Filter: (lower(email) = 'sara@example.com'::text)
(2 rows)
shop=# CREATE INDEX customers_lower_email_idx ON customers (lower(email));
CREATE INDEX
shop=# EXPLAIN (COSTS OFF)
shop-# SELECT id FROM customers WHERE lower(email) = 'sara@example.com';
                          QUERY PLAN                           
---------------------------------------------------------------
 Bitmap Heap Scan on customers
   Recheck Cond: (lower(email) = 'sara@example.com'::text)
   ->  Bitmap Index Scan on customers_lower_email_idx
         Index Cond: (lower(email) = 'sara@example.com'::text)
(4 rows)
  • Indexes are not free. Each one takes space and slows every insert and update, which must update the index too. Add them for the queries you actually run, as shown by EXPLAIN and by the slow query log, not “just in case”.

For a column pair such as (price, id), the order matters: the index is sorted by price first, so it serves WHERE price = … and ORDER BY price, id, but not a search by id alone. Chapter 15 goes deeper into plans and tuning.

Professional habit: EXPLAIN before you ship

For every new query that will run on a large or growing table, run EXPLAIN ANALYZE on realistic data before the code is merged, and paste the plan in the pull request. A Seq Scan on a big table in a request path is a bug waiting for traffic. Testing on a table with twelve rows proves nothing: generate data, as seed.sql does with generate_series.

5.8 SQL from code, safely

Applications send SQL to the database through a driver. The single most important rule: never build SQL by joining strings with input. Here is why, with an input that a form could send as an email address:

php/query.php
<?php

declare(strict_types=1);

$db = new PDO('pgsql:host=localhost;dbname=shop', 'bit', 'secret', [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION, // errors become exceptions, not silent false
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
]);

// What a form might send as an email: it closes the quote and adds a condition.
$input = "x' OR '1'='1";

// WRONG: the input becomes part of the SQL
$unsafe = $db->query("SELECT id, email FROM customers WHERE email = '$input'");
echo 'string concatenation: ', count($unsafe->fetchAll()), " rows\n";

// Right: the SQL and the value travel separately; ? is only ever a value
$safe = $db->prepare('SELECT id, email FROM customers WHERE email = ?');
$safe->execute([$input]);
echo 'parameter: ', count($safe->fetchAll()), " rows\n";

$sara = $db->prepare('SELECT c.name, count(o.id) AS orders FROM customers c
    LEFT JOIN orders o ON o.customer_id = c.id WHERE c.email = ? GROUP BY c.name');
$sara->execute(['sara@example.com']);
var_dump($sara->fetch());
Terminal
# From PHP, with PDO
$ php php/query.php
string concatenation: 2008 rows
parameter: 0 rows
array(2) {
  ["name"]=>
  string(4) "Sara"
  ["orders"]=>
  int(2)
}

Glued into the SQL, the input closed the quote and added OR '1'='1', which is always true: the query returned every customer, 2008 rows, instead of none. This is SQL injection, still one of the most common and most damaging attacks on the web: with a slightly different input, an attacker can read any table, or delete them. With a prepared statement and a ? placeholder, the SQL and the value are sent to the database separately; the value can never become SQL, whatever it contains, and the same query found no customer with that strange email.

PDO is PHP’s database layer, and it is what Laravel uses underneath: DB::select('… where email = ?', [$email]), the query builder and Eloquent all send parameters this way. They are only unsafe when you put input into the SQL text yourself, for example in DB::raw() or whereRaw() with string concatenation. Notice also that count arrived as a PHP int: PDO for PostgreSQL converts integer columns to PHP integers. Chapter 6 puts Eloquent on top of this.

Summary

  • Tables have typed columns: bigint ids, text, integer money, timestamptz times. Constraints (PRIMARY KEY, NOT NULL, UNIQUE, CHECK, REFERENCES) keep data correct whatever writes it.
  • SELECT … FROM … WHERE … ORDER BY … LIMIT reads rows; aggregates summarise them.
  • NULL is unknown: compare it with IS NULL; it spreads through arithmetic.
  • Inner joins keep matches; left joins keep every left row. Count a right-table column, not *.
  • GROUP BY makes groups, HAVING filters them; the database runs FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY in that order.
  • CTEs name intermediate results; window functions compute across rows without collapsing them.
  • RETURNING and ON CONFLICT make writes answer and upserts atomic.
  • EXPLAIN ANALYZE shows the plan; indexes turn scans into lookups. Index foreign keys and real query patterns, including expressions.
  • Parameters, never string concatenation, between code and SQL.

Quick check answers: 1. Comparing anything with NULL gives NULL (unknown), never true, and WHERE keeps only rows where the condition is true; use IS NULL. 2. count(*) counts rows, and a customer with no orders still has one row in a left join (with NULLs), so they get 1 instead of 0; count a column from the orders table, such as count(o.id). 3. WHERE runs before the rows are grouped, so there is no sum yet; filter groups with HAVING sum(quantity) > 100.

6.2 Changing a live schema: expand and contract

Every product needs a SKU, a stock code, required and unique. Adding a required column in one step fails on a live system: existing rows have no value, and the code still running in production does not send one. The safe pattern is expand and contract:

  1. Expand: add the column as nullable. The running code ignores it.
  2. Deploy code that writes it, and fill it for the existing rows.
  3. Contract: make it required and unique.
database/migrations/…_add_sku_to_products.php
return new class extends Migration
{
    public function up(): void
    {
        Schema::table('products', function (Blueprint $table) {
            $table->string('sku')->nullable();
        });
    }

    public function down(): void
    {
        Schema::table('products', function (Blueprint $table) {
            $table->dropColumn('sku');
        });
    }
};
database/migrations/…_require_product_sku.php
    public function up(): void
    {
        // Step 2: fill it for the existing rows, in chunks.
        DB::table('products')->whereNull('sku')->chunkById(500, function ($products) {
            foreach ($products as $product) {
                DB::table('products')->where('id', $product->id)
                    ->update(['sku' => sprintf('BIT-%04d', $product->id)]);
            }
        });

        // Step 3, contract: every row has a SKU now; make it required and unique.
        Schema::table('products', function (Blueprint $table) {
            $table->string('sku')->nullable(false)->unique()->change();
        });
    }

chunkById fills the rows 500 at a time, so a large table is never loaded into memory at once. On a table of millions of rows, run the backfill as a separate command or job rather than inside a migration. The same pattern renames a column (add the new one, write both, backfill, read the new one, drop the old one) without the shop ever stopping.

6.3 Models and relationships

Each table gets a model. Relationships are methods that return relationship objects:

app/Models/Order.php
class Order extends Model
{
    protected $fillable = ['customer_id', 'status'];

    protected function casts(): array
    {
        return ['status' => OrderStatus::class]; // the column holds text; the model gives you the enum
    }

    public function customer(): BelongsTo
    {
        return $this->belongsTo(Customer::class);
    }

    public function products(): BelongsToMany
    {
        return $this->belongsToMany(Product::class, 'order_items')->withPivot('quantity', 'price');
    }

    // a reusable condition: Order::query()->shipped()
    #[Scope]
    protected function shipped(Builder $query): void
    {
        $query->where('status', OrderStatus::Shipped);
    }

    // The total, computed from the items: piastres, as stored.
    protected function total(): Attribute
    {
        return Attribute::get(fn () => $this->products->sum(
            fn (Product $p) => $p->pivot->quantity * $p->pivot->price,
        ));
    }
}
  • belongsTo on the side with the foreign key (an order belongs to a customer), and hasMany on the other (a customer has many orders).
  • belongsToMany for many-to-many, through order_items. withPivot brings the joining table’s own facts, the quantity and the price at the time, onto each product as $product->pivot.
  • A cast converts a column when it is read and written. The status column holds text; the model gives you the OrderStatus enum from Chapter 2, with its labels.
  • A scope is a named, reusable condition, marked with #[Scope]: Order::shipped().
  • An attribute such as total is computed from the items when read: $order->total. It is not stored, so it cannot disagree with them.

6.4 Seeing the SQL

Every query Laravel sends passes through the database layer, and DB::listen can watch them. The book’s Artisan commands collect the SQL of each piece of work:

routes/console.php
function countQueries(callable $work): array
{
    $queries = [];
    DB::listen(function ($query) use (&$queries) {
        $queries[] = $query->sql;
    });
    $result = $work();
    DB::flushQueryLog();

    return [$result, $queries];
}

6.5 The N+1 problem

A report lists every shipped order with its products. Written the natural way, it loads the orders, then touches $order->products for each one, and Eloquent loads them lazily, one order at a time:

routes/console.php
Artisan::command('shop:report {mode}', function (string $mode) {
    $start = hrtime(true);
    [$orders, $queries] = countQueries(function () use ($mode) {
        $orders = $mode === 'eager'
            ? Order::shipped()->with('products')->get() // two queries: the orders, then all their products at once
            : Order::shipped()->get();
        // each ->products loads that order's products: one more query per order
        $orders->each(fn (Order $order) => $order->products->count());

        return $orders;
    });
    $ms = intdiv(hrtime(true) - $start, 1_000_000);
    $this->line(sprintf('%-5s %d orders, %d queries, %d ms', $mode, $orders->count(),
        count($queries), $ms));
});
Terminal
# The same report two ways: count the queries
$ SHOP_STRICT=false php artisan shop:report lazy
lazy  200 orders, 201 queries, 166 ms
$ SHOP_STRICT=false php artisan shop:report eager
eager 200 orders, 2 queries, 55 ms

Lazy: one query for the orders and one more for each of the 200 orders, 201 queries. Eager, with with('products'): two queries, the orders and then all their products with WHERE order_id IN (…). Several times faster on a database on the same machine; across a network, the difference grows to seconds. This is the N+1 problem, the most common performance bug in Laravel applications, because every line looks innocent.

Laravel can turn it into an error. In the service provider:

app/Providers/AppServiceProvider.php
    public function boot(): void
    {
        // in development: no lazy loading, no silently ignored attributes
        Model::preventLazyLoading(config('shop.strict'));
        Model::preventSilentlyDiscardingAttributes(config('shop.strict'));
    }

6.6 Mass assignment

Product::create($request->all()) would let a client set any column it names, including ones it must never touch. $fillable lists the attributes that may be set from an array; everything else is ignored, or, with preventSilentlyDiscardingAttributes, refused loudly:

Terminal

7.1 Transactions: all or nothing

A transaction groups statements so that they act as one. It has four guarantees, known as ACID:

  • Atomicity: either every change is kept, or none is.
  • Consistency: every rule of the schema holds at the end.
  • Isolation: transactions running at the same time do not see each other’s unfinished work (exactly how much they see is the isolation level, 7.3).
  • Durability: once committed, a change survives a crash.

This chapter uses two small tables:

schema.sql
CREATE TABLE products (
  id    bigint PRIMARY KEY,
  name  text NOT NULL,
  price integer NOT NULL CHECK (price > 0),
  stock integer NOT NULL CHECK (stock >= 0)
);
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  product_id bigint NOT NULL REFERENCES products (id),
  buyer      integer NOT NULL
);
INSERT INTO products VALUES (1, 'Robot kit', 45000, 1), (2, 'Spare wheels', 6000, 10);

7.2 A race: one kit, ten buyers

Here is the obvious way to sell a product: read the stock, check it in code, write the new stock, record the order. To see what happens under load, the program starts ten buyers at the same moment, each with its own database connection, for a product with one unit left. A short pause between reading and writing stands for what a real application does there, such as calling a payment service:

php/race.php
function buy(PDO $db, string $mode, int $buyer): int
{
    $retries = 0;
    while (true) {
        try {
            $db->exec($mode === 'serializable' ? 'BEGIN ISOLATION LEVEL SERIALIZABLE' : 'BEGIN');
            if ($mode === 'atomic') {
                // one statement: the database checks and changes the stock together
                $taken = $db->exec('UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock > 0');
                if ($taken === 1) {
                    $db->prepare('INSERT INTO orders (product_id, buyer) VALUES (1, ?)')->execute([$buyer]);
                }
            } else {
                // read, decide in code, write: the classic race
                // FOR UPDATE locks the row: other buyers wait here until this transaction ends
                $lock = $mode === 'lock' ? ' FOR UPDATE' : '';
                $stock = (int) $db->query("SELECT stock FROM products WHERE id = 1$lock")->fetchColumn();
                // the time a real app spends between reading and writing: a call to a payment service, say
                $db->query('SELECT pg_sleep(0.1)');
                if ($stock > 0) {
                    $db->prepare('UPDATE products SET stock = ? WHERE id = 1')->execute([$stock - 1]);
                    $db->prepare('INSERT INTO orders (product_id, buyer) VALUES (1, ?)')->execute([$buyer]);
                }
            }
            $db->exec('COMMIT');
            return $retries;
        } catch (PDOException $e) {
            $db->exec('ROLLBACK');
            // serialization failure: start the whole transaction again
            if ($e->getCode() !== '40001') {
                throw $e;
            }
            $retries++;
        }
    }
}

The ten buyers are ten processes made with pcntl_fork, each with its own connection, like ten PHP workers serving ten requests:

php/race.php
$setup = $connect();
$setup->exec('TRUNCATE orders; UPDATE products SET stock = 1 WHERE id = 1');
$setup = null; // closed before forking: a child must never share its parent's connection

    $pid = pcntl_fork();
    if ($pid === 0) {
        exit(buy($connect(), $mode, $buyer));
    }
    $children[] = $pid;
}
$retries = 0;
foreach ($children as $pid) {
    pcntl_waitpid($pid, $status);
    $retries += pcntl_wexitstatus($status);
}

The naive version sold one kit ten times. Every buyer read “1 in stock” before anyone had written, every buyer decided to sell, and every buyer wrote “0”. The transaction did not help: it makes changes all-or-nothing, but it does not stop two transactions from reading the same value. This is a race condition, a check-then-act bug: the check was true when it ran and false by the time the action happened.

The other three versions each sold it once. They are the three standard fixes:

  • An atomic update. UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock > 0 checks and changes in one statement. PostgreSQL locks the row while it updates, so the second buyer’s update waits, then re-checks stock > 0 against the new value and changes nothing. The number of changed rows tells the code whether it sold. When the rule fits in a WHERE, this is the simplest and fastest fix.
  • A row lock. SELECT … FOR UPDATE reads the row and locks it until the transaction ends. Every other buyer waits at that line, then reads the stock after the first one committed. Use it when the decision needs code between the read and the write (a price calculation, a call to another service), and keep such transactions short, because everyone waits.
  • Serializable isolation. The code stays naive, and the database guarantees that the result equals running the transactions one after another. When it detects that this is impossible, it refuses a transaction with error 40001, and the code runs it again from the start: here, nine of the ten buyers were refused once and found the stock empty on their retry.

Watch out: the check in code is never enough

Any rule of the form “only if …” (enough stock, a seat still free, a balance high enough, a username not taken) is a race when it is checked in code and then written. Put the rule where the database can enforce it at the moment of the write: in a conditional update, a unique constraint, a CHECK, or a lock. Chapter 5’s CHECK (stock >= 0) would also have stopped the oversale, with an error instead of a quiet second order.

7.3 Isolation levels

The isolation level decides what a transaction sees of other transactions that commit while it is running. Two connections show the difference: A reads a price, B changes it and commits, A reads again and then tries to change it:

php/isolation.php
// A reads, B changes and commits, A reads again, then A tries to change it
$a->exec("BEGIN ISOLATION LEVEL $level");
echo 'A reads the price: ', $price(), "\n";
$b->exec('UPDATE products SET price = 50000 WHERE id = 1');
echo "B sets the price to 50000 and commits\n";
echo 'A reads it again: ', $price(), "\n";
try {
    $a->exec('UPDATE products SET price = price + 1000 WHERE id = 1');
    $a->exec('COMMIT');
    echo 'A adds 1000 to the price: ', $price(), "\n";
} catch (PDOException $e) {
    $a->exec('ROLLBACK');
    echo 'A adds 1000 to the price: ERROR ', preg_replace('/^ERROR:\s+/', '', $e->errorInfo[2]), "\n";
}
Terminal
# READ COMMITTED (PostgreSQL's default)
$ php php/isolation.php

B sets the price to 50000 and commits
A reads it again: 50000
A adds 1000 to the price: 51000
# REPEATABLE READ
$ php php/isolation.php 'REPEATABLE READ'
A reads the price: 45000
B sets the price to 50000 and commits
A reads it again: 45000
A adds 1000 to the price: ERROR could not serialize access due to concurrent update
  • READ COMMITTED, PostgreSQL’s default: every statement sees everything committed before it started. A’s second read saw B’s new price, so two reads in one transaction disagreed, and A’s update built on B’s value.
  • REPEATABLE READ: the transaction sees a snapshot taken at its first statement. A’s second read still saw 45000, so its reads are consistent with each other. And when A tried to update a row that B had changed since that snapshot, PostgreSQL refused: A was working from an old picture. The application must retry.
  • SERIALIZABLE adds detection of every pattern that could not happen if the transactions ran one after another, as in the race above. It is the safest level and needs retries the most.

A practical rule: keep the default, use atomic statements and constraints for the rules they can express, take row locks when code must decide between a read and a write, and use SERIALIZABLE (with retries) for complicated multi-row rules where it is hard to see every race. Reports that read many tables at once benefit from REPEATABLE READ, so their numbers come from one moment.

7.4 Deadlocks

Locks have their own trap. Transaction A locks product 1 and then wants product 2; transaction B has locked product 2 and wants product 1. Each waits for the other, forever:

php/deadlock.php
// A locks product 1 then 2; B locks 2 then 1
function run(string $name, int $first, int $second): void
{
    $db = new PDO('pgsql:host=localhost;dbname=shop', 'bit', 'secret',
        [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]);
    $take = $db->prepare('UPDATE products SET stock = stock + 1 WHERE id = ?');
    try {
        $db->exec('BEGIN');
        $take->execute([$first]);
        usleep(200_000);
        $take->execute([$second]);
        $db->exec('COMMIT');
        echo "$name: done\n";
    } catch (PDOException $e) {
        $db->exec('ROLLBACK');
        $message = preg_replace('/^ERROR:\s+/', '', strtok($e->errorInfo[2], "\n"));
        echo "$name: failed, {$e->getCode()}, $message\n"; // one echo: two processes print at once
    }
}
Terminal
# Two transactions, the same two rows, in opposite orders
$ php php/deadlock.php

A: done

PostgreSQL checks for such cycles after a second of waiting (deadlock_timeout), picks one transaction, and aborts it with error 40P01, so the other can finish. Which one loses depends on timing. Two habits keep deadlocks rare: lock rows in a consistent order (for an order with several products, lock or update them sorted by id), and keep transactions short, with no network calls or user waits inside them. Like serialization failures, a deadlock victim can simply be retried.

7.5 Transactions in the framework

Laravel wraps a transaction in a closure: DB::transaction(function () { … }) commits when the closure returns and rolls back when it throws. Its second argument is a number of attempts: DB::transaction($work, attempts: 5) runs the closure again when the database reports a deadlock or a serialization failure, which is the retry loop of the race program, built in. Row locks are query builder methods: Product::whereKey($id)->lockForUpdate()->first(), or sharedLock() to stop others from changing the row while still letting them read it. Chapter 4’s order controller used the atomic update inside DB::transaction.

7.6 Side effects and the outbox

A transaction can be rolled back; an email cannot be unsent. If the code sends “your order is confirmed” inside the transaction and the commit then fails (a deadlock, a constraint, a crash), the customer has an email for an order that does not exist. Sending after the commit has the opposite problem: if the process crashes between the commit and the send, the order exists and the email never goes.

The reliable pattern is the outbox: inside the same transaction as the order, insert a row into an outbox table describing the message to send. The order and its message commit together or not at all. A separate worker reads the outbox, sends each message, and marks it sent; if it crashes, it sends again later, so the receiver must tolerate duplicates (idempotency again). Chapter 11 builds the worker with a queue, and Laravel’s afterCommit option for jobs covers the simpler half of the problem.

Professional habit: test races on purpose

A race does not appear in a test that runs one request at a time. For every “only if” rule (stock, seats, balances, unique names), write one test that starts many requests at the same moment, as this chapter’s race program does, and asserts on the final state: one sale, one booking, a balance never below zero. Such a test fails reliably on the naive code, which is the proof that it tests the right thing.

Summary

  • A transaction makes several statements atomic: one failure, and COMMIT becomes ROLLBACK.
  • Transactions do not stop races: “read, check in code, write” sells one item many times under load.
  • Three fixes: an atomic conditional update, a row lock with FOR UPDATE, or SERIALIZABLE with retries.
  • READ COMMITTED sees each statement’s latest commits; REPEATABLE READ sees one snapshot and refuses updates to rows changed since.
  • Deadlocks are cycles of locks; PostgreSQL breaks them with 40P01. Lock in a consistent order, keep transactions short, retry.
  • Side effects belong after the commit, reliably through an outbox.

Quick check answers: 1. A transaction makes its own changes all-or-nothing, but under the default isolation level it does not stop other transactions from reading the same row at the same time, so all ten read “1” before any of them wrote. 2. Other SELECT … FOR UPDATE statements, and updates, on that row wait until the locking transaction commits or rolls back; plain SELECTs still read the last committed version without waiting. 3. Roll back and run the whole transaction again from the beginning, reading the data afresh, a limited number of times, ideally after a short random pause.

8.2 A cache in front of a slow query

The most common pattern is cache-aside: the application looks in Redis first; on a cache miss it asks the database and keeps a copy in Redis for next time; on a cache hit the database is not touched. Here a pg_sleep(0.2) makes the query take 200 milliseconds, like a heavy report:

php/cache.php
// the slow query: pg_sleep stands for a heavy report or a join over big tables
function productFromDb(PDO $db, int $id): array
{
    $query = $db->prepare('SELECT id, name, price FROM products, pg_sleep(0.2) WHERE id = ?');
    $query->execute([$id]);

    return $query->fetch();
}

// cache-aside: look in Redis first; on a miss, ask the database and keep the answer
function product(PDO $db, Predis\Client $redis, int $id): array
{
    $key = "product:$id";
    $cached = $redis->get($key);
    if ($cached !== null) {
        return [json_decode($cached, true), 'Redis'];
    }
    $fresh = productFromDb($db, $id);
    // forgotten after 60 seconds, even if nobody deletes it
    $redis->set($key, json_encode($fresh), 'EX', 60);

    return [$fresh, 'PostgreSQL'];
}

// changing the data: update the database first, then delete the cached copy
function setPrice(PDO $db, Predis\Client $redis, int $id, int $price): void
{
    $db->prepare('UPDATE products SET price = ? WHERE id = ?')->execute([$price, $id]);
    $redis->del("product:$id");
}

The PHP programs reach Redis with Predis, a client written in PHP and installed with Composer (composer require predis/predis), so no extension is needed.

third request    Robot kit, 45000, from Redis in 0 ms

The first request paid the full 200 milliseconds; the next two came from memory in about one. That is the reward. The cost is that there are now two copies of the data, and the copy can be wrong. Two rules keep it right:

  • Invalidate on change. Whatever changes the data deletes the cached copy, after the database write has succeeded. The next read misses and fetches the new value: the price 47000 appeared at once. Deleting is safer than writing the new value into the cache, because two concurrent writers could otherwise leave the older value there.
  • Always set an expiry. Some change will one day forget to invalidate: a direct SQL fix, a new code path, a bug. A TTL limits how long a wrong copy can live. Choose it from the question “how stale may this be?”: seconds for stock levels, minutes for a product page, hours for a list of countries.

Watch out: cache what is shared, not what is private

A cache key must contain everything the answer depends on. A product page in two languages needs product:2:ar and product:2:en, and anything that depends on the user (their basket, their prices, their permissions) needs the user in the key, or no cache at all. Serving one customer’s cached data to another is a security incident, not a performance bug.

8.3 Stampedes and locks

A cache has a dangerous moment: when a popular key expires. Every request that arrives in the next 200 milliseconds misses, and every one of them asks the database the same heavy question. This is a cache stampede. The program sends twenty requests at once for a product that is not cached, first without protection, then with a lock that lets only one request rebuild the cache while the others wait and look again:

php/stampede.php
// delete the lock only if it is still ours, in one step on the server
const RELEASE = <<<'LUA'
    if redis.call("GET", KEYS[1]) == ARGV[1]
      then return redis.call("DEL", KEYS[1]) else return 0 end
    LUA;

function product(Predis\Client $redis, string $mode, int $id): array
{
    $key = "product:$id";
    while (true) {
        $cached = $redis->get($key);
        if ($cached !== null) {
            return json_decode($cached, true);
        }
        if ($mode === 'naive') {
            break;
        }
        // only the request that gets the lock asks the database; the others wait and look again
        $token = bin2hex(random_bytes(16)); // a random token: only the owner of the lock may release it
        if ($redis->set("lock:$key", $token, 'PX', 5000, 'NX')) {
            try {
                $fresh = productFromDb($redis, $id);
                $redis->set($key, json_encode($fresh), 'EX', 60);

                return $fresh;
            } finally {
                $redis->eval(RELEASE, 1, "lock:$key", $token);
            }
        }
        usleep(50_000);
    }
    $fresh = productFromDb($redis, $id);
    $redis->set($key, json_encode($fresh), 'EX', 60);

    return $fresh;
}

As in the previous chapter, the twenty requests are twenty processes made with pcntl_fork, each with its own connections.

Terminal
# Twenty requests on a cold cache
$ php php/stampede.php naive
naive   20 requests, database queries: 20, 260 ms
$ php php/stampede.php locked
locked  20 requests, database queries: 1, 284 ms

Without the lock, twenty requests made twenty identical queries; with it, one. With a real report that takes two seconds and a page that a thousand visitors open in that time, this is the difference between a slow page and a database that falls over. The lock is three ideas:

  • Take it with SET key token NX PX 5000. NX means only one client can create the key; the others get null and know someone else is working. PX 5000 makes the lock expire after 5 seconds, so a process that crashes while holding it cannot block everyone forever.
  • A random token as the value. If the work took longer than 5 seconds, the lock expired and another process may hold it now. Deleting the key blindly would release their lock.
  • Release with a script. “Read the value, compare it, delete the key” must happen in one step, or the lock could change hands between the read and the delete. Redis runs a Lua script atomically, like a single command, so the release checks the token and deletes in one step.

A Redis lock is good for efficiency: avoiding duplicate work, as here. It is not a guarantee of correctness, because a lock that expires while its owner is still working (a long pause, a slow network) lets two processes in. When two processes doing the work at once would corrupt data, the last line of defence stays in the database: a constraint, a conditional update or a row lock, from Chapter 7.

8.4 A rate limit that servers share

Chapter 3 limited requests with Laravel’s rate limiter, which counts in whatever cache store the application uses.

With counters in each server’s memory, a client who spreads requests across two servers gets twice the limit, and a restart resets everyone. The counter belongs in Redis, where every server sees the same number:

php/ratelimit.php
<?php

declare(strict_types=1);

require __DIR__.'/vendor/autoload.php';

const LIMIT = 5;
const WINDOW = 10; // seconds

// one counter per client; the first request starts a 10-second window
function allow(Predis\Client $redis, string $client): array
{
    $key = "rate:$client";
    // MULTI/EXEC: both commands run together, nothing in between
    [$count] = $redis->transaction(function ($tx) use ($key) {
        $tx->incr($key);
        $tx->expire($key, WINDOW, 'NX');
    });

    return [$count <= LIMIT, $count, $key];
}

// two servers, two connections, one Redis: the limit is shared
$servers = [
    'A' => new Predis\Client('tcp://localhost:6379'),
    'B' => new Predis\Client('tcp://localhost:6379'),
];
$servers['A']->del('rate:203.0.113.7');
foreach (range(1, 8) as $i) {
    $name = $i % 2 === 1 ? 'A' : 'B';
    $redis = $servers[$name];
    [$allowed, $count, $key] = allow($redis, '203.0.113.7');
    $answer = $allowed
        ? "allowed ($count of ".LIMIT.')'
        : 'refused, 429, try again in '.$redis->ttl($key).' s';
    echo "request $i via server $name: $answer\n";
}

The requests alternated between servers A and B, and the sixth was refused whichever server received it. Two details make it right:

  • EXPIRE … NX sets the expiry only if the key has none, so the first request starts the 10-second window and later requests do not extend it.
  • MULTI and EXEC send both commands as one transaction: Redis runs them together, with no other client’s command in between. With two separate commands, a process that crashed after INCR and before EXPIRE would leave a counter that never expires, and that client blocked forever.

This is a fixed window: simple and cheap, but a client can send 5 requests at the end of one window and 5 more at the start of the next. A sliding window counts the requests of the last 10 seconds at every moment, with a sorted set of timestamps; it is exercise 5.

8.5 Redis in the framework

Laravel has Redis built in. Set REDIS_CLIENT=predis (or install the phpredis extension, which is faster), point REDIS_HOST at the server, and choose CACHE_STORE=redis. Then everything in this chapter is one line:

  • Cache::remember("product:$id", 60, fn () => Product::findOrFail($id)) is cache-aside, and Cache::forget("product:$id") invalidates.
  • Cache::lock("report", 5)->get(fn () => …) takes a lock with a token and releases it safely, with the same SET NX and Lua script as above; Cache::flexible() serves the old value while one request rebuilds it, which also prevents stampedes.
  • The rate limiter (RateLimiter::for and the throttle middleware) counts in the cache store, so with Redis it is shared by every server.
  • Redis::incr(), Redis::zadd() and the other commands are available directly for anything else; Chapter 11 runs the queue on Redis.

8.6 What belongs in Redis

Redis keeps everything in memory, and memory is small and expensive compared with disk. Three settings decide how it behaves when things go wrong:

  • maxmemory limits the memory Redis may use, and maxmemory-policy decides what happens at the limit. For a pure cache, allkeys-lru evicts the least recently used keys, which is exactly what a cache should forget. The default, noeviction, refuses new writes instead.
  • Persistence (RDB snapshots and the AOF log) can save the data to disk, so a restart does not empty it. A cache can do without; sessions and queues need it.
  • One Redis for a cache that may forget, and another (or another configuration) for data that must not: a queue whose jobs vanish under memory pressure loses orders.

The rule that follows: Redis holds copies and short-lived state; the database holds the truth. If Redis were emptied right now, the application should get slower, log users out at worst, but lose nothing that matters.

Professional habit: measure before you cache

A cache adds a second copy of the data, invalidation code, and a new way to be wrong. Before adding one, measure: which query is slow, how often it runs, and whether an index (Chapter 5) or a better query would fix it with no copy at all. Then cache the few hot, expensive, shared answers, and watch the hit rate: a cache that is hit 20% of the time is mostly overhead.

Summary

  • Redis keeps keys in memory and answers in under a millisecond; every single command is atomic.
  • Cache-aside: read Redis, on a miss read the database and keep a copy with a TTL; on change, delete the copy.
  • A stampede sends every request to the database when a hot key expires; a lock lets one rebuild it.
  • A safe lock: SET key token NX PX, and release with a Lua script that checks the token. Redis locks save work; correctness stays in the database.
  • Rate limits belong in Redis so that servers share them; MULTI/EXEC keeps counter and expiry together.
  • Redis holds copies and short-lived state; the database holds the truth.

Quick check answers: 1. Two updates can happen at nearly the same time; if each writes its value into the cache, the slower one can overwrite the newer value with the older, and the cache stays wrong until the TTL. Deleting is the same whatever the order, and the next read loads the current value from the database. 2. If the process holding the lock crashed or hung, the key would never disappear, and every later request would wait forever for a cache that nobody rebuilds. 3. When the lock expires while its owner is still working, another process can take it; a fixed value would let the first process, when it finishes, delete the second one’s lock. The token lets each process delete only the lock it took.

Years ago a site I used was breached, and the attackers published its user table. My password was right there, in plain text, next to my email. It was the same password I used on two other sites. 9.1 Two questions

Every protected request answers two separate questions, in order:

  • Authentication: who is calling? The client proves an identity, with a password once and then with a token on every request. If it cannot, the answer is 401 Unauthorized (a confusing name: it means “not authenticated”).
  • Authorization: may this user do this? The identity is known; the rules decide. If they say no, the answer is 403 Forbidden, or 404 Not Found when even the existence of the thing is private.

Laravel keeps them apart too: guards and the auth middleware answer the first question; gates and policies answer the second.

9.2 Storing passwords

A password must never be stored as it is, and never with an ordinary hash such as SHA-256 either. A fast hash is the problem: a graphics card computes billions of SHA-256 hashes a second, so an attacker with a stolen table tries every common password against every row in minutes. Password storage needs a hash that is slow on purpose: bcrypt, Argon2 or scrypt. Laravel’s Hash facade uses bcrypt by default, and the User model hashes automatically, because its password attribute has the hashed cast. A small Artisan command shows what it produces:

routes/console.php

    $b = Hash::make($password);

    $this->line("hash 2 $b");

    $this->line('wrong password: '.json_encode(Hash::check($password.'r', $a)));

    Hash::make($password);
    $this->line('one hash took '.round((hrtime(true) - $start) / 1e6).' ms');

Watch out: never write your own crypto

Hash, Str::random() and hash_hmac are written and reviewed by specialists. Combining well-known pieces in the standard way is fine; inventing your own hashing scheme, your own encryption or your own token generator is not. rand() and mt_rand() are never acceptable for anything secret: they are predictable. Use random_bytes() or Str::random().

9.4 Registering and signing in

Registration validates the body, and User::create hashes the password through the cast. Emails are stored in lower case so that Lina@Example.com and lina@example.com are one account. The unique rule gives a friendly message, but it checks and then inserts, a race from Chapter 7: the unique index on the column is what really decides, and the exception it throws becomes a 409:

app/Http/Controllers/AuthController.php
    public function register(Request $request): JsonResponse
    {
        // emails in lower case: Lina@Example.com is lina@example.com
        $request->merge(['email' => Str::lower((string) $request->input('email'))]);
        $data = $request->validate([
            'email' => ['required', 'email', 'max:254', 'unique:users'],
            'name' => ['required', 'string', 'max:100'],
            'password' => ['required', 'string', Password::min(12), 'max:128'],

        try {
            $user = User::create($data)->refresh();

            // two registrations at once: the unique index decides, not the rule
            abort(409, __('Email already registered.'));
        }

        return response()->json($user->only('id', 'email', 'name', 'role'), 201);
    }

What about JWTs?

A JSON Web Token takes the opposite approach: instead of a random key into a table, the token contains the data (the user id, the role, the expiry), signed with the server’s secret so that it cannot be changed. Here is one made by hand, to see what is inside:

routes/console.php
Artisan::command('shop:jwt', function () {
    $secret = 'a secret only the server knows';
    $url = fn (string $bytes) => rtrim(strtr(base64_encode($bytes), '+/', '-_'), '=');
    $b64 = fn (array $value) => $url(json_encode($value));
    $sign = fn (string $data) => $url(hash_hmac('sha256', $data, $secret, true));

    // a JWT: header and payload in base64url, then their HMAC
    $header = $b64(['alg' => 'HS256', 'typ' => 'JWT']);
    $payload = $b64(['sub' => 2, 'role' => 'customer', 'exp' => 1795000000]);
    $token = "$header.$payload.".$sign("$header.$payload");
    $this->line("token: $token");

    // anyone can read the payload: it is encoded, not encrypted
    $read = fn (string $part) => base64_decode(strtr($part, '-_', '+/'));
    $this->line('payload, read without the key: '.$read(explode('.', $token)[1]));

    $valid = function (string $jwt) use ($sign) {
        [$h, $p, $signature] = explode('.', $jwt);

        return hash_equals($sign("$h.$p"), $signature);
    };
    $this->line('signature valid: '.json_encode($valid($token)));
    // change the payload, keep the signature
    $forged = $b64(['sub' => 2, 'role' => 'admin', 'exp' => 1795000000]);
    $signature = explode('.', $token)[2];
    $this->line('tampered token valid: '.json_encode($valid("$header.$forged.$signature")));
});

A mobile app keeps the token in the phone’s secure storage and sends it in the Authorization header, as curl does here. A website should not keep a token where scripts can read it. For a single-page app on your own domain, Sanctum has a second mode: the app signs in through Laravel’s ordinary session, held in an HttpOnly, Secure, SameSite=Lax cookie, and auth:sanctum accepts either the cookie or a token. You list the website’s domain in SANCTUM_STATEFUL_DOMAINS. Cookies bring a risk of their own, cross-site request forgery, which Chapter 10 deals with.

9.5 Authorization: gates and policies

Authentication found the user; now the rules decide what that user may do. A gate is one named yes-or-no rule, good for whole areas such as an admin section; it is defined once, in a service provider, and the can:admin middleware in the routes applies it:

    public function boot(): void

        // a gate: one yes-or-no rule with a name

9.6 Slowing down guessing

A slow hash protects a stolen table; the running server needs protection too, against a script that tries passwords one after another. The login rate limiter (Chapter 3 introduced rate limiters) is keyed on the client’s address and the email, so one attacker cannot try thousands of passwords on one account:

app/Providers/AppServiceProvider.php
        RateLimiter::for('login', function (Request $request) {
            $key = $request->ip().'|'.Str::lower((string) $request->input('email'));

            return Limit::perMinute(5)->by($key)->response(function ($request, $headers) {
                $seconds = $headers['Retry-After'];

                return response()->json([
                    'message' => __('Too many attempts. Try again in :seconds seconds.', ['seconds' => $seconds]),
                ], 429, $headers);
            });
        });

Professional habit: test the “no” for every route

For every protected route, write at least two tests: one without a token (401) and one as a user who must not have access (403 or 404). Add them in the same pull request as the route. The day someone removes a middleware or changes a query, these tests fail, which is far cheaper than finding out from a customer who saw someone else’s order.

Summary

  • Authentication finds out who is calling (401 if unknown); authorization decides what they may do (403, or 404 to hide existence).
  • Passwords are stored with a slow, salted hash: bcrypt through Hash and the hashed cast.
  • Sign-in gives the same answer and the same time for a wrong email and a wrong password.
  • Sanctum tokens are random, stored only as a SHA-256 hash, given an expiry, and revoked by deleting the row.
  • A JWT carries signed data that anyone can read and nobody can revoke: good between services and for minutes, not for user sessions.
  • Gates for areas, policies for records; rate-limit login, and test every “no”.

Quick check answers: 1. A token’s random part is 40 random characters: there are far too many possibilities to try, so the hash only needs to stop someone who reads the table from using the values directly, and a fast hash does that. A password is chosen by a person from a small set of likely words, so an attacker can try the likely ones quickly unless each try is made deliberately slow. 2. 403 Forbidden: the server knows exactly who is calling (the token is valid), so the problem is not authentication; the user lacks the admin role. 3. So that the response takes the same time whether or not the email exists; otherwise an unknown email would be answered much faster, and the time would reveal which emails have accounts.

10.2 Injection

The search below puts the input into its SQL with PHP’s string interpolation. For an ordinary search it works perfectly, which is exactly why this bug survives code review:

routes/api.php
Route::get('unsafe/products', function (Request $request) {
    $q = $request->query('q');

    // DANGER: the input becomes part of the SQL text
    return DB::select("SELECT name, price FROM products WHERE name = '$q'");
});

Route::get('products', function (Request $request) {
    $q = $request->validate(['q' => ['required', 'string', 'max:100']])['q'];

    // the input travels separately, as a binding: it is only ever a value
    // the same query with Eloquent: Product::where('name', $q)->get()
    return DB::select('SELECT name, price FROM products WHERE name = ?', [$q]);
});

$ curl -s -G localhost:8000/api/unsafe/products -H 'Accept: application/json' --data-urlencode "q=x' UNION SELECT email || ' ' || password, 0 FROM users --" | jq -c '.[]'

The attacker’s input closed the quote, added a UNION that reads the users table, and commented out the rest with --. The database cannot tell which part of the text came from the programmer and which from the attacker, so it ran all of it, and the response contains every email and password hash. With a little more work the same hole reads any table, changes data, or worse.

The safe route sends the same input as a binding: the SQL text, with ?, and the value travel to PostgreSQL separately, so the value can never become code. It simply searched for a product with that strange name, and found none. Eloquent and the query builder bind every value for you, so Product::where('name', $q) is safe. The danger remains wherever text is pasted into SQL:

  • The Raw methods (whereRaw, selectRaw, orderByRaw, DB::raw) and DB::select take SQL text: give them bindings as their second argument, never interpolated variables.
  • Column names, such as the field to sort by, cannot be bindings. Validate them against a fixed list with Rule::in(['name', 'price']), as Chapter 4’s requests did.
  • The same bug exists outside SQL: shell commands built from input (use Process::run with an array of arguments), and HTML built from input (section 10.5).

10.3 Mass assignment

An update that writes whatever fields arrive is convenient: add a column, and the route supports it at once. It also supports columns nobody meant to expose:

routes/api.php
Route::patch('unsafe/users/{user}', function (Request $request, User $user) {
    // DANGER: every field the client sends is written, role included
    $user->forceFill($request->all())->save();

    return $user->only('id', 'name', 'role');
});

Route::patch('users/{user}', function (Request $request, User $user) {
    // only the fields a customer may change; role is refused outright
    $user->update($request->validate([
        'name' => ['required', 'string', 'max:100'],
        'role' => ['prohibited'],
    ]));

    return $user->only('id', 'name', 'role');
});
Terminal
# Omar changes his name, and his role
$ curl -s -X PATCH localhost:8000/api/unsafe/users/2 -H 'Accept: application/json' -H 'Content-Type: application/json' -d '{"name":"Omar","role":"admin"}' | jq -c
{"id":2,"name":"Omar","role":"admin"}
# The same request, on the safe route
$ curl -s -X PATCH localhost:8000/api/users/2 -H 'Accept: application/json' -H 'Content-Type: application/json' -d '{"name":"Omar","role":"admin"}' | jq -c

Omar sent one extra field and became an admin. This is mass assignment, a form of broken access control. Laravel has two layers against it, and the unsafe route had to switch both off:

  • The model’s fillable list. User declares #[Fillable(['name', 'email', 'password'])], so update() and create() ignore role. forceFill() exists for trusted code, such as seeders, and skips the list. With Model::preventSilentlyDiscardingAttributes() from Chapter 6, an attempt to fill role throws instead of being ignored.
  • Validated data only. $request->validate() returns only the fields that have rules, never $request->all(). The prohibited rule goes further and refuses a request that sends role at all, so the client learns it is not allowed rather than wondering why nothing happened. Changing a role is a different route, for admins only.

10.4 Paths and other dangerous places

Serving files from a folder by name looks harmless. But a name is input, and .. means “the folder above”:

routes/api.php
Route::get('unsafe/files/{path}', function (string $path) {
    // DANGER: '../' climbs out of the folder
    $text = file_get_contents(storage_path("app/files/$path"));

    return response($text)->header('Content-Type', 'text/plain');
})->where('path', '.*');

Route::get('files/{path}', function (string $path) {
    // a disk rooted at the folder: Flysystem refuses paths that climb out
    $files = Storage::build(['driver' => 'local', 'root' => storage_path('app/files')]);
    try {
        $text = $files->get($path) ?? abort(404, 'Not Found');
    } catch (PathTraversalDetected) {
        abort(404, 'Not Found');
    }

    return response($text)->header('Content-Type', 'text/plain');
})->where('path', '.*');

Better still is not to use the client’s text as a path at all: store uploads with $file->store('products'), which picks a random name, keep the original name in the database, and look up by id.

The same idea applies to every place where input reaches something powerful:

  • URLs the server fetches (“import a product image from this address”). An attacker gives http://localhost:5432 or the cloud provider’s internal metadata address, and your server, inside your network, fetches it for them. This is server-side request forgery (SSRF), exercise 5.
  • Redirects (?next=… after sign-in): only allow paths on your own site, or an attacker sends users to a fake copy of it. redirect()->intended() stays on your site.
  • Unserialising data from the client with unserialize() can create arbitrary objects; accept JSON instead.

Watch out: validation is not escaping

Validating input (“the name is 1 to 100 characters”) and making it safe for a destination (SQL, a path, HTML, a shell) are different jobs. A perfectly valid product name can contain a quote, .. or <script>. Validate at the edge, and make values safe where they are used, with the tool made for that destination: bindings, disks, Blade’s escaping.

10.5 Protecting browser users

An API is often called from a website, and the browser adds attacks of its own. Laravel already handles much of them for its own pages:

  • Cross-site scripting (XSS): an attacker gets their script into a page other people see, for example as a product review, and it runs with the visitor’s session. Blade’s {{ }} escapes everything; {!! !!} does not, and is the place to look in a review. An API protects itself by returning JSON with the right Content-Type, and the frontend by escaping, as Vue and React do except in v-html and dangerouslySetInnerHTML.
  • Cross-site request forgery (CSRF): another site makes the browser send a request to yours, and the browser attaches your cookies. Laravel’s web routes check a CSRF token on every form; its session cookie is SameSite=Lax; and tokens in the Authorization header, as in Chapter 9, are never sent automatically at all.
  • Clickjacking: your page is loaded invisibly inside another site, and the user is tricked into clicking your buttons.

Browsers can refuse much of this if the server asks them to, with security headers. Laravel does not set them by default; a small middleware, added to every response in bootstrap/app.php, does:

app/Http/Middleware/SecurityHeaders.php
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);
        // security headers on every response; an API needs no scripts or frames at all
        $response->headers->add([
            'Content-Security-Policy' => "default-src 'none'; frame-ancestors 'none'",
            'Strict-Transport-Security' => 'max-age=31536000; includeSubDomains',
            'X-Content-Type-Options' => 'nosniff',
            'X-Frame-Options' => 'DENY',
            'Referrer-Policy' => 'no-referrer',
        ]);

        return $response;
    }
bootstrap/app.php
    ->withMiddleware(function (Middleware $middleware): void {
        $middleware->append(SecurityHeaders::class);
    })

  • Content-Security-Policy lists where scripts, styles and images may come from. An API answers with JSON and needs none of them, so default-src 'none' refuses everything; a website lists its own sources. It is the strongest defence against XSS in pages.
  • Strict-Transport-Security tells the browser to use only HTTPS for this site for a year, so nobody can downgrade a visit to plain HTTP.
  • X-Frame-Options and frame-ancestors stop other sites from framing yours; X-Content-Type-Options: nosniff stops the browser from guessing that a text file is a script.

CORS (cross-origin resource sharing) is the other half. By default a script on evil.example may send a request to your API but may not read the answer. Note what CORS is not: it does not stop curl, scripts or servers, which ignore it, and it does not stop the request from reaching your server. It protects users’ browsers, not your API; authentication and authorization still do that. Never allow every origin with * on an API that uses cookies.

The .env file that path traversal leaked holds the most valuable things the application has. Rules for it:

  • Different in every environment, set by the platform (Chapter 17’s containers receive them as environment variables) or a secret manager.   • Read through config(). Call env() only inside config/*.php; after php artisan config:cache in production, env() elsewhere returns null. A missing setting should fail loudly at start-up, not at the first request that needs it.
  • Never logged. Laravel hides password fields from validation errors and exceptions; keep tokens and keys out of your own log messages too.

10.8 Dependencies

The shop’s code is a few hundred lines; the packages in vendor are hundreds of thousands. A known vulnerability in an old version, a malicious package a typo away from a popular one, or an honest package whose maintainer’s account was stolen can all reach your server. composer audit (the second part of the output above) checks every installed version against a database of known vulnerabilities; run it in CI, and fail the build on findings. Commit composer.lock and deploy with composer install, so every machine gets exactly the versions you tested; let a bot (Dependabot, Renovate) open small update pull requests often; and before adding a package, look at who maintains it and whether a few lines of your own would do.

Professional habit: a security checklist in every review

Keep a short checklist next to your pull request template: Is every input validated with a size? Does any input reach a Raw method, a path, a URL, a shell or {!! !!}? Is every new route behind authentication and a policy, with a test for the “no”? Are there new secrets, and are they in .env and config/? Are new packages needed and maintained? Thirty seconds per review prevents most of this chapter.

Chapter 1

  1. The status line is HTTP/1.1 200 OK; the headers are Content-Type, Content-Length, Date and Connection (and the development server’s extra Host); then comes the empty line, and the body is the JSON object of 41 bytes. Without Host, the PHP development server answers 200 as if nothing were wrong: it is lenient because it is a development tool. Production web servers such as Nginx answer 400 Bad Request, because HTTP/1.1 requires the header.
  2. GET /products?max_price=100: safe and idempotent. PUT /products/2 with a full product: not safe, idempotent (the product ends up the same however many times it is sent). POST /products/2/reviews: neither; two requests make two reviews. DELETE /cart/items/7: not safe, idempotent. PATCH /products/2 with {"stock_change": -1}: neither, because each request takes one more item from the stock; a PATCH that sets a value ({"stock": 4}) would be idempotent.
  3. In handle, before the GET route for one product, add the same pattern for DELETE: open the file and lock it, as create does, keep every product whose id is not the one asked for, write the list back if it got shorter, and answer 204, or 404 if nothing was removed. The first delete answers 204 and the second 404; that is still idempotent, because the server is in the same state after both. The new product, though, gets id 3 again, because the id is “number of products + 1”. A client holding an old link to product 3 now gets a different product, and if you had deleted product 1 instead, the new product would get the id of product 3, which still exists. Ids must never be reused: keep a counter in a file, next-id.txt, and read and increase it while holding the lock. With that change, the run in the code repository creates product 4. A database does this for you, with a sequence.
  4. The product list is public: anyone can read it with curl, so a page on another site reading it in a visitor’s browser learns nothing secret. CORS only stops other sites’ JavaScript from reading answers with the visitor’s browser. The danger is an endpoint that answers with private data because of the visitor’s cookies, such as GET /me/orders: there, letting any origin read the answer would let any site read the visitor’s orders. What protects it is not CORS alone, but the server checking who is asking (authentication), what they may see (authorisation), and cookies with SameSite, together with a short list of trusted origins.
  5. The answer must carry Content-Encoding: gzip, so the client knows to decompress; Content-Length with the size of the compressed bytes; and Vary: Accept-Encoding, so a cache never gives a compressed copy to a client that cannot read it. In send, check $_SERVER['HTTP_ACCEPT_ENCODING'], and compress with gzencode. With the three products of the run, the list is 128 bytes plain and 103 bytes compressed. That is a small saving, because gzip needs repetition to work with; on a list of a hundred products, the same JSON shrinks to a fraction of its size. That is also why servers do not compress tiny bodies: below about 1 KB, the work costs more than it saves. curl --compressed sends the header and decompresses the answer for you.

  1. Nothing of the three changes is kept.   5. function retrying(Closure $work, int $attempts = 5): mixed
{
    for ($attempt = 1; ; $attempt++) {
        try {
            return DB::transaction($work);
        } catch (QueryException $e) {
            $code = $e->getCode();
            if ($attempt === $attempts || ! in_array($code, ['40001', '40P01'], true)) {
                throw $e;
            }
            usleep(random_int(0, 20_000 * 2 ** $attempt)); // grows with each attempt
        }
    }
}

    In a real Laravel project DB::transaction($work, attempts: 5) already retries deadlocks and serialization failures; this helper adds the growing random pause.

    The pause is random so that two transactions that collided do not retry at the same instant and collide again; it grows so that a busy moment gets time to pass. Only the whole transaction is retried, never a single statement, because everything it read may have changed.

  5. Sign-in returns two tokens: an access token, a JWT valid for 10 minutes carrying the user id and role, and a refresh token, random bytes stored as a hash in the database with a long expiry. Every API request checks only the JWT’s signature and expiry, without a database query. When the access token expires, the client sends the refresh token to POST /api/auth/refresh, which checks it in the database, replaces it with a new one (so a stolen refresh token works only once), and returns a new JWT. Sign-out deletes the refresh token; the access token stays valid for up to 10 minutes, which is the price. The gain is no database lookup on most requests, which matters when many services check tokens; for a single API with a database already involved in every request, Sanctum’s tokens are simpler.

Chapter 10

  1. A binding can only stand for a value; ORDER BY ? would sort by a constant string, the same for every row, and column names are part of the SQL itself. Validate the input against a fixed list, 'sort' => ['nullable', Rule::in(['name', 'price'])], and pass only the validated value to orderBy() (not orderByRaw), which also quotes it as an identifier. Anything else is refused with 422.
  2. CORS is enforced by browsers, and only for reading responses. Anyone can call the route with curl, a script or another server, none of which care about CORS; and even a browser on another site can still send many requests. Protection of data and actions comes from authentication and authorization on the server. CORS only decides which websites’ scripts may read the answers in a user’s browser.
