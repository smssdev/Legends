Claude is one family of AI models that reaches you through several doors: a chat app on the web, desktop and phone; Claude Code, an agent that works in your terminal and your repository; and an API that puts the same models inside your own programs. This book teaches all three the way a professional uses them: what each is good at, how to give it the right context, how to check its work, and what it costs. It is written for developers and teams, and it builds on Book 7, AI for Developers, whose habits (give the model what it needs, check what it gives you, measure before you believe) apply here to one family of tools in depth.

The practice server

Read this before any example

The practice server is not Claude. Its answers were written for this book, to show what each part of a response looks like and how a program should handle it. When a transcript in this book shows an answer, it is the practice server’s, and the chapter says so. The errors, the field names, the streaming events and the code are real; the words of the answers are not Claude’s, and the token counts are an approximation (about four characters per token). Meet Claude: Models, Strengths and Limits

In this chapter you will learn to

Claude is a family of AI models made by Anthropic. The same models answer you in the chat app, edit your repository through Claude Code, and run inside your programs through the API. This chapter introduces the family: which models exist and how they differ, what a request and a response look like, what they cost, and what Claude cannot do however well you ask. Did you know?

A token is the unit models read and write: a short word, part of a longer word, a punctuation mark. In English a token is about four characters on average; Arabic and code usually take more tokens for the same length. Prices and limits are counted in tokens, and the API counts them exactly for you (Chapter 15).

1.3 A first message

Install the SDK in a new project, start the practice server from the book’s repository, and point the SDK at it with the two variables from the preface:

npm install @anthropic-ai/sdk@1.8.0
node practice/server.mjs &
export ANTHROPIC_BASE_URL=http://127.0.0.1:4141 ANTHROPIC_API_KEY=test-key

Then a program of a few lines:

hello.mjs (part)
const question = process.argv[2] ?? "Introduce yourself in three sentences.";
const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 1000,
  messages: [{role: "user", content: question}],
});
for (const block of response.content) {
  if (block.type === "text") console.log(block.text);
}
const {input_tokens, output_tokens} = response.usage;
const dollars = cost(response.model, response.usage).toFixed(6);
console.log(`--- stop: ${response.stop_reason}; ` +
  `tokens: ${input_tokens} in, ${output_tokens} out; cost: $${dollars}`);
Terminal
$ node hello.mjs

--- stop: end_turn; tokens: 19 in, 70 out; cost: $0.001476

The answer is the practice server’s, written to sound like Claude introducing itself; Claude’s own words will differ. What matters is the shape, which is the API’s. A request names the model, the max_tokens the answer may use, and the messages so far, starting with the user’s. The response’s content is a list of blocks, not a string: here a single text block, but later chapters meet thinking blocks, tool calls and citations, so code always looks at each block’s type. stop_reason says why the answer ended: end_turn means Claude finished, max_tokens means it was cut off, and other values (a tool call, a refusal) mean the program has work to do. And usage counts the tokens, from which the program works out the cost.

Watch out

Never write an API key in code, and never commit one. The SDK reads ANTHROPIC_API_KEY from the environment, so the code above works with the practice server and with the real API without a change. A key in a repository is a key anyone can spend on.

1.4 What it costs

Every request is priced by its tokens: input at one rate, output at a higher one (five times higher for every current model), and two more rates for prompt caching, which Chapter 15 covers. The calculation is short enough to keep next to your code:

lib/prices.mjs (part)
export function cost(model, usage) {
  const p = PRICES[model];
  const written = usage.cache_creation_input_tokens ?? 0;
  const read = usage.cache_read_input_tokens ?? 0;
  const dollars = usage.input_tokens * p.input + usage.output_tokens * p.output +
    written * p.input * 1.25 + read * p.cacheRead;
  return dollars / 1_000_000;
}
Terminal
$ node prices.mjs
claude-fable-5-2   $0.03600 each, $36.00 per thousand
claude-opus-5-5    $0.01800 each, $18.00 per thousand
claude-sonnet-5-5  $0.00900 each, $9.00 per thousand
claude-haiku-5-5   $0.00045 each, $0.45 per thousand
claude-opus-5-5, cached prompt: $0.01116 each

The same request, 2,000 tokens in and 500 out, costs eighty times more on the most capable model than on the fastest. A thousand of them costs $36 on Claude Fable 5.2 and 45 cents on Claude Haiku 5.5. And caching most of the prompt, as in the last line, cuts the Opus request by more than a third, because input read from the cache costs a twentieth of its usual price on Claude Opus 5.5. Neither number says which model to use: a cheap model that gets a task wrong costs more than an expensive one that gets it right, which is why Chapter 16 measures before it chooses.

Tip

Start with Claude Opus 5.5, the default, until the feature works and you have a way to measure it; then try the smaller models on the same measurement. Moving down to Sonnet or Haiku is often possible for a well-defined task; you only know when you measure.

Quick check

  1. Why should a program ask the API for its models instead of keeping a list?
  2. Why is a response’s content a list of blocks rather than a string?
  3. The same request costs $0.018 on Opus 5.5. What does it cost on Sonnet 5.5, and why exactly half?

The answers are at the end of the chapter, after the summary.

1.5 Strengths and limits

Claude reads quickly and widely: a long contract, a codebase, a spreadsheet, a screenshot. It writes clearly in many languages, Arabic and English included. It reasons through problems in steps, thinking before it answers when the task needs it. It writes and reviews code well enough that Part II is a whole part. And it uses tools: given a function to call, it decides when to call it and what to pass, which is how it searches, runs code and acts in your systems (Chapter 12).

Its limits are the same in kind as every model of Book 7, and they decide how you design around it:

  • Its knowledge stops at a date. Ask about today’s news and the honest answer is the one below: it does not know. Recent facts must come from you, from a search tool, or from your documents.
  • The API remembers nothing. Each request is complete in itself: to continue a conversation, you send it all again. The apps keep history and memory for you; your programs must do it themselves (Chapter 11).
  • It can be wrong, fluently. Better models are wrong less often, not never. Everything Book 7 taught about checking applies here.
  • It may decline. Some requests are refused for safety, with stop_reason set to refusal. A program handles that like any other outcome (Chapter 16).
  • Its context is large but finite, and what you put in it costs money and attention: a million tokens is a capacity, not a target.
Terminal
$ node hello.mjs "What happened in the news today?"
I can't know that: I have no access to the news, and my knowledge stops at my training cutoff. Give me the articles, or use a tool such as web search, and I can summarise them.
--- stop: end_turn; tokens: 17 in, 51 out; cost: $0.001088

The practice server’s answer here was written to show the right behaviour: say what cannot be known, and say what would help. Check that the real model behaves like this for the questions your users ask; when it does not, that is what search tools and your own documents are for.

1.6 Thinking and effort

Current Claude models think before they answer when a problem needs it, and decide for themselves how much: this is adaptive thinking. You control the depth with effort, from low to max, set in output_config. Low effort is faster and cheaper, for simple tasks and chat; high effort is for hard problems, where thinking longer pays off. On Claude Opus 5.5 the default is medium, and thinking cannot be turned off: effort is the only control. A first program discovers this, and two other rules, the way everyone does:

errors.mjs (part)
const attempts = [
  ["a misspelled model", {...ask, model: "claude-opus-55"}],
  ["no max_tokens", {model: "claude-opus-5-5", messages: ask.messages}],
  ["thinking turned off", {...ask, model: "claude-opus-5-5", thinking: {type: "disabled"}}],
];
Terminal
$ node errors.mjs
a misspelled model: 404 NotFoundError
  model: claude-opus-55
no max_tokens: 400 BadRequestError
  max_tokens: Field required
thinking turned off: 400 BadRequestError
  thinking: type "disabled" is not supported for this model; use "adaptive" or omit it

Three different errors, each with a status and a message that names the problem. A model id with a typo is a 404, not found; a request without max_tokens is a 400, invalid; and asking Claude Opus 5.5 to stop thinking is a 400 too. Read the message before changing the code: the API almost always says which field is wrong.

Professional habit

Keep the model id, the effort and max_tokens in one place in your configuration, not scattered through the code. Models change every few months, and the team that can switch, measure and switch back in an afternoon will always use the best model for the price.

Summary

  • One family of models reaches you through the apps, Claude Code and the API; each door adds different things around the same models.
  • Fable, Opus, Sonnet and Haiku trade capability for speed and price; ask the API which models exist and their limits.
  • A response is a list of typed blocks, with a stop_reason and a usage that every program should read.
  • Cost is tokens times price, with output dearer than input and cached input much cheaper; calculate it before you scale.
  • Claude’s knowledge ends at a date, the API remembers nothing, and answers can be wrong or refused: design for all four.

Quick check answers: 1. Because the list changes with every release and differs between accounts and platforms; the API always knows what your key can use and each model’s limits. 2. Because a response can contain more than text: thinking, tool calls, and text split around citations; a list of typed blocks holds them all, in order. 3. $0.009, because both Sonnet prices ($2 in, $10 out) are exactly half of Opus’s ($4 and $20), so any mix of tokens costs half.

A first choice of model

export function chooseModel({hard, longRunning, highVolume}) {

Project 1.2 · Medium

A monthly budget

Estimate what a feature costs a month on three models, with and without caching.

You will practise: cost as a design input, before the first line of the feature.

  1. Describe the feature: requests a day, tokens in and out.
  2. Price a month on each model with cost.
  3. Price it again with 80% of the input read from the cache.
budget.mjs (part)
function monthly({model, perDay, input, output, cachedShare = 0}) {
  const cached = Math.round(input * cachedShare);
  const usage = {input_tokens: input - cached, cache_read_input_tokens: cached, output_tokens: output};
  return cost(model, usage) * perDay * 30;
}

Terminal
$ node budget.mjs

Project 1.3 · Challenge

Errors that say what to do

Turn every kind of API error into one sentence that tells a developer what to fix.

You will practise: the SDK’s typed errors, checked from the most specific to the most general.

  1. Write one sentence for each error class.
  2. Check instanceof from specific to general, and rethrow what you do not know.
  3. Provoke three errors: a wrong model, a wrong key, and no server.
handle.mjs (part)
export function advice(error) {
  if (error instanceof Anthropic.APIConnectionError) return "No connection: check the network and ANTHROPIC_BASE_URL.";
  if (error instanceof Anthropic.AuthenticationError) return "Check ANTHROPIC_API_KEY: missing, mistyped or revoked.";
  if (error instanceof Anthropic.NotFoundError) return "Check the model name against GET /v1/models.";
  if (error instanceof Anthropic.RateLimitError) return "Too many requests: wait as long as retry-after says, then retry.";
  if (error instanceof Anthropic.BadRequestError) return "Fix the request: read the message, it names the field.";
  if (error instanceof Anthropic.InternalServerError) return "A problem on the API's side: retry with backoff.";
  throw error;
}

Your result should look like this:

Terminal
$ node handle.mjs
NotFoundError        Check the model name against GET /v1/models.
AuthenticationError  Check ANTHROPIC_API_KEY: missing, mistyped or revoked.
APIConnectionError   No connection: check the network and ANTHROPIC_BASE_URL.

Hint: order matters because the classes form a hierarchy: NotFoundError and RateLimitError are both APIErrors, so a broad check first would hide them. And never match on the message text: the classes and the status are the stable contract.

Appendix

Answers to the Exercises

Try every exercise yourself before you look here. When your answer differs from this one, that is not necessarily wrong: most problems have several good solutions. If yours handles normal and unusual cases, and you can explain your choices, it is a good answer. The full, tested code for every answer is in the book’s code repository.

Chapter 1

  1. Print response.model, response.id and the cost from cost(response.model, response.usage). A reply in practice.json is an object with a when (words the question must contain) and a text; put it before any reply that would also match, because the first match wins. The id is worth logging in real programs: it is what Anthropic’s support asks for when you report a problem.
  2. The stop_reason is max_tokens, and the text stops in the middle of a sentence. A program must not treat it as a complete answer: show it as cut off, ask again with a larger max_tokens, or ask for a shorter answer in the prompt. Silent truncation is one of the most common bugs in programs that call a model.
  3. Nothing changes with the practice server: it does not think, and it ignores effort. With the real API, low effort usually means less thinking, fewer tokens, a faster and cheaper answer, and for a simple question the same answer. The difference shows on hard questions, which is why effort is chosen per task and measured, not set once for everything.
  4. Add a batch option that halves the cost, and print a fourth column. Good candidates are work nobody waits for: nightly summaries of tickets, tagging a backlog, translating documentation, running an evaluation set. A chat with a customer is not one: the customer is waiting.
  5. List the models with client.models.list(), send the same request to each in turn, and print the text, usage and cost for each, catching errors so that one model that fails does not stop the others. Against the practice server, every model gives the same scripted answer and the token counts are approximations, so only the costs differ. The comparison means something only with real answers, and even then a single question is an anecdote: compare models on a set of questions with known good answers, as Book 7 did.
