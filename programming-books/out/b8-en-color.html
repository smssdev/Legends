A token is the unit models read and write: a short word, part of a longer word, a punctuation mark. The answer is the practice server’s, written to sound like Claude introducing itself; Claude’s own words will differ. What matters is the shape, which is the API’s. A request names the model, the max_tokens the answer may use, and the messages so far, starting with the user’s. The response’s content is a list of blocks, not a string: here a single text block, but later chapters meet thinking blocks, tool calls and citations, so code always looks at each block’s type. stop_reason says why the answer ended: end_turn means Claude finished, max_tokens means it was cut off, and other values (a tool call, a refusal) mean the program has work to do. 1.4 What it costs

Every request is priced by its tokens: input at one rate, output at a higher one (five times higher for every current model), and two more rates for prompt caching, which Chapter 15 covers. The calculation is short enough to keep next to your code:

lib/prices.mjs (part)
export function cost(model, usage) {
  const p = PRICES[model];
  const written = usage.cache_creation_input_tokens ?? 0;
  const read = usage.cache_read_input_tokens ?? 0;
  const dollars = usage.input_tokens * p.input + usage.output_tokens * p.output +
    written * p.input * 1.25 + read * p.cacheRead;
  return dollars / 1_000_000;
}
Terminal
$ node prices.mjs

claude-opus-5-5    $0.01800 each, $18.00 per thousand
claude-sonnet-5-5  $0.00900 each, $9.00 per thousand
claude-haiku-5-5   $0.00045 each, $0.45 per thousand

The same request, 2,000 tokens in and 500 out, costs eighty times more on the most capable model than on the fastest. A thousand of them costs $36 on Claude Fable 5.2 and 45 cents on Claude Haiku 5.5. And caching most of the prompt, as in the last line, cuts the Opus request by more than a third, because input read from the cache costs a twentieth of its usual price on Claude Opus 5.5. Neither number says which model to use: a cheap model that gets a task wrong costs more than an expensive one that gets it right, which is why Chapter 16 measures before it chooses.

1.5 Strengths and limits

Claude reads quickly and widely: a long contract, a codebase, a spreadsheet, a screenshot. It writes clearly in many languages, Arabic and English included. It reasons through problems in steps, thinking before it answers when the task needs it. It writes and reviews code well enough that Part II is a whole part. And it uses tools: given a function to call, it decides when to call it and what to pass, which is how it searches, runs code and acts in your systems (Chapter 12).

Its limits are the same in kind as every model of Book 7, and they decide how you design around it:

  • Its knowledge stops at a date. Ask about today’s news and the honest answer is the one below: it does not know. Recent facts must come from you, from a search tool, or from your documents.
  • The API remembers nothing. Each request is complete in itself: to continue a conversation, you send it all again. The apps keep history and memory for you; your programs must do it themselves (Chapter 11).
  • It can be wrong, fluently. Better models are wrong less often, not never. Everything Book 7 taught about checking applies here.
  • It may decline. Some requests are refused for safety, with stop_reason set to refusal. A program handles that like any other outcome (Chapter 16).
  • Its context is large but finite, and what you put in it costs money and attention: a million tokens is a capacity, not a target.

$ node hello.mjs "What happened in the news today?"

1.6 Thinking and effort

Current Claude models think before they answer when a problem needs it, and decide for themselves how much: this is adaptive thinking. You control the depth with effort, from low to max, set in output_config. Low effort is faster and cheaper, for simple tasks and chat; high effort is for hard problems, where thinking longer pays off. On Claude Opus 5.5 the default is medium, and thinking cannot be turned off: effort is the only control. A first program discovers this, and two other rules, the way everyone does:

Professional habit

Keep the model id, the effort and max_tokens in one place in your configuration, not scattered through the code. Models change every few months, and the team that can switch, measure and switch back in an afternoon will always use the best model for the price.

2.1 A good first message

A chat with Claude is a conversation with a capable colleague who has just walked in: well read, quick, and knowing nothing about your situation. The first message decides most of what follows. A good one carries four things:

PartWeakStrong
Context“Write a menu description.”“I run a small café in Cairo; most customers are students.”
The task“Make it good.”“Describe our new rose latte in two sentences for the menu board.”

  • Continue when the answer is on the right track: “shorter”, “more formal”, “now the Arabic version”. Each reply builds on everything above it.
  • Edit your message when the answer went wrong because of how you asked. The conversation branches from there, and the wrong turn no longer sits in the history, pulling later answers toward it.
  • Start a new chat when the topic changes. An old conversation about last month’s budget is not context for today’s job advert; it is noise, and, as Section 2.2 shows, it is paid for on every turn.

Tip

When a long chat has produced something you want to keep (a plan, a set of decisions), ask Claude to summarise it in a few lines, and start the next chat with that summary. You keep the conclusions and drop the hundred messages that led to them.

2.2 What the conversation really is

Claude does not remember the chat between your messages. Each time you press send, the app sends the whole conversation again, every message from the first, and the model reads it from the top before writing the next reply. Three lines of code show it, using the API of Chapter 1:

chat.mjs (part)
for (const question of turns) {
  messages.push({role: "user", content: question});
  const response = await client.messages.create({
    model: "claude-opus-5-5",
    max_tokens: 1000,
    messages,
  });
  messages.push({role: "assistant", content: response.content});
  const used = response.usage.input_tokens;
  console.log(`> ${question}\n${text(response)}`);
  console.log(`  (turn ${messages.length / 2}: ${used} tokens in)`);
}

The apps add features on top of this: in some plans and settings Claude can search or remember earlier chats, and a project (Chapter 3) gives every chat in it the same documents and instructions. But the core is always the same: the model sees what is sent, and only that. When Claude “forgets” something from early in a very long chat, or contradicts it, it is usually because that part is far back in a long text, competing with everything after it.

Watch out

Long conversations get slower, cost more, and can drift: an early mistake that was never corrected keeps being read on every turn. If a chat has gone wrong for several turns, do not argue with it; start again with a better first message.

2.3 Files

    return {type: "document", source, title};
  }
  const source = {type: "base64", media_type: TYPES[path.extname(file)], data};

2.5 What you share

Everything you attach is sent to Anthropic to be processed, like everything you type. Before you upload a contract, a customer list or a screenshot of a dashboard, ask the same question you would before emailing it to an outside consultant: am I allowed to share this, and with whom? Your company may have a policy, and a business or enterprise plan may be the only approved way to use Claude with company data. Check your plan’s privacy settings, including whether your chats may be used to improve the models, and choose deliberately. And remove what the task does not need: Claude can summarise a complaint without the customer’s phone number (Book 7, Chapter 15).

Professional habit

Before you attach a file, look at it the way a stranger would. Screenshots in particular carry more than you mean to share: an open tab, a name in a corner, a token in a URL. Crop first.

export async function trim(messages, budget) {
  let kept = [...messages];
  for (;;) {
    const counted = await client.messages.countTokens({model, messages: kept});
    const size = counted.input_tokens;
    if (size <= budget || kept.length <= 1) return {kept, size};
    kept = kept.slice(2); // one user turn and its answer
  }
}

3.1 What a project is

In the Claude apps, a project has three parts:

  • Instructions, written once, that apply to every chat in the project: who Claude is helping, which sources to use, how to answer.
  • Knowledge: files you add (documents, PDFs, code, data) that Claude can read in every chat.
  • Chats, each a normal conversation that starts with the instructions and the knowledge already in place.

On team plans, a project can be shared with colleagues, who then chat with the same instructions and knowledge. When the knowledge grows larger than Claude can read at once, the app searches it for the passages that matter to each question, instead of reading everything: the retrieval that Book 7’s Chapter 14 built by hand.

The book’s example is two projects for Bit Cafe: one for answering customers, with the menu, the policies, the barista recipes and a guide to the café’s voice; and one for writing social media posts, with just the menu:

3.2 Instructions that hold up

Project instructions are read at the start of every chat, by every member of the team, for months. They deserve the care of code:

support/instructions.md
You answer customers of Bit Cafe. Use only the project's documents. Follow voice.md. If the documents do not answer, say you will ask a colleague.

Three sentences, and each one earns its place. The first says who Claude is helping, which decides the tone and the level of detail. The second limits the sources, so the answer about prices comes from the menu and not from what cafés usually charge. The third says what to do when the documents are silent, which is the case instructions most often forget, and the one that produces confident inventions when they do.

Tip

Keep instructions short and about behaviour; put facts in the knowledge. “Our latte costs 45” in the instructions goes out of date unseen; in menu.md it sits with the other prices, where the person who changes prices will find it.

3.3 Knowledge you can keep current

A project is only as good as its documents, and documents rot. A few rules keep them useful:

  • One topic per file, named for the topic: menu.md, policies.md. Clear names help Claude and the people who maintain them.
  • The current version only. Two menus, one from last year, give Claude two prices to choose from. Replace files; do not add new versions next to old ones.
  • Text over scans. A Markdown or text file is read exactly; a scanned PDF must be read from page images, which is slower and less reliable.
  • An owner and a date. Somebody updates the menu when prices change, and the file says when it was last checked.

3.4 A project underneath

Built with the API, a project is a few lines: the instructions become the system prompt, the part of the request that sets Claude’s role before any message, and the knowledge follows as documents in it. The last document carries a cache_control marker, which asks the API to keep everything up to that point in the prompt cache, so the next request that starts with the same text reads it back for a fraction of the price:

lib/project.mjs (part)
export function loadProject(folder) {
  const instructions = read(folder, "instructions.md");
  const dir = path.join(folder, "knowledge");
  const knowledge = fs.readdirSync(dir).sort().map((name) => ({
    type: "text",
    text: `<document name="${name}">\n${read(dir, name)}</document>`,
  }));
  knowledge.at(-1).cache_control = {type: "ephemeral"};
  return {instructions, knowledge};
}
lib/project.mjs (part)
export async function chat(project, question) {
  return client.messages.create({
    model: "claude-opus-5-5",
    max_tokens: 1000,
    system: [{type: "text", text: project.instructions}, ...project.knowledge],
    messages: [{role: "user", content: question}],
  });
}

The reason is a rule of prompt caching that the API applies without an error or a warning: a prefix shorter than a minimum is not cached. The minimum depends on the model, from 512 to 4,096 tokens; the practice server uses 1,024, and the English knowledge is 913 tokens long.

In the Arabic edition, the same four documents take 1,379 tokens, because Arabic text uses more tokens for the same content, and there the cache works as intended: the first chat writes 1,379 tokens to the cache, and the next two read them back. Watch out

Caching fails silently: a request that misses the cache still works, it just costs the full price. Check cache_read_input_tokens in the usage of the second request. If it is zero, either the prefix is too short, or something in it changed between requests: a date in the instructions, documents in a different order, a tool list that varies. 3.5 Projects for a team

A shared project gives a team one place for its working knowledge: the support team’s answers, the engineering team’s conventions, the sales team’s product sheets. Before sharing, settle three things. Who can change the instructions and the knowledge: a project anyone can edit drifts. What is in the knowledge: everyone with access can ask Claude about every document in it, so a salary sheet does not belong in a project the whole company uses. And how chats are shared: check what your plan shows to other members, and tell the team, so nobody types into a shared space what they meant to keep private.

Professional habit

Give every shared project an owner and a monthly check: are the documents current, are the instructions still right, and what did people ask that the documents could not answer? Those questions are the next documents to write.

This chapter is about getting artifacts that work, and knowing that they do.

Bit

The artifact in this chapter has a real bug, and a real browser found it: a bill of 85.50 came out as 85. The artifact was written for the book and returned by the practice server; the test, the failure and the fix that passed are all real.

4.1 What an artifact is

When an answer is substantial and stands on its own, Claude puts it in an artifact rather than in the flow of the chat. The common kinds are:

KindExamplesCheck it by
DocumentsA plan, a policy, a report in MarkdownReading it against its sources
CodeA script, a function, a configuration fileRunning its tests
Web pages and appsA calculator, a form, a dashboard in one HTML file or a React componentUsing it in a browser, with a test
Diagrams and imagesA flowchart in Mermaid, an SVG logoRendering it and reading every arrow

An artifact keeps its versions: each change you ask for makes a new one, and you can go back. It can be published with a link, and others can open it, use it, or make their own copy. Some apps let an artifact itself call Claude, so a page you made can answer questions or generate text for whoever uses it. All of this makes artifacts feel finished. They are drafts, made by a model, and the rest of this chapter treats them that way.

4.2 Asking for one

An artifact request is a small specification (Book 7, Chapter 9): what it is for, what goes in and comes out, and the constraints that matter. The chapter’s request:

Make me a tip calculator as one HTML page: a field for the bill in EGP,
a field for the tip percentage, and the tip and the total, updated as I type.

It says the form (one HTML page), the inputs, the outputs and the behaviour. A better request would also say how it will be checked (“a bill of 85.50 at 10% gives 8.55”) and the constraints a team cares about: works offline, no external libraries, labelled fields, Arabic and English. Every constraint you leave out is one the artifact may quietly break.

4.3 A demo is not a test

Open the page, type 100, see 10.00 and 110.00, and it looks finished. Type a bill a real café prints, with piastres, and it is not. A test in a real browser, with Playwright, types what a customer would and reads what the page shows:

check.mjs (part)
export async function check(file) {
  const browser = await chromium.launch();
  const page = await browser.newPage();
  await page.goto(`file://${path.resolve(file)}`);
  await page.fill("#bill", "85.50");
  await page.fill("#tip", "10");
  const tip = await page.textContent("#tip-amount");
  const total = await page.textContent("#total");
  await browser.close();
  const ok = tip === "8.55" && total === "94.05";
  const failure = "bill 85.50 at 10% gave tip $tip and total $total; expected 8.55 and 94.05".replace("$tip", tip).replace("$total", total);
  return {ok, failure: ok ? "" : failure};
}
Terminal
$ node check.mjs artifacts/tip-v1.html
FAIL artifacts/tip-v1.html: bill 85.50 at 10% gave tip 8.50 and total 93.50; expected 8.55 and 94.05

A tip of 8.50 instead of 8.55. The cause is one word in the artifact:

artifacts/tip-v1.html (part)
    function update() {
      const amount = parseInt(bill.value);
      const share = (amount * Number(tip.value)) / 100;
      document.getElementById("tip-amount").textContent = share.toFixed(2);
      const total = amount + share;
      document.getElementById("total").textContent = total.toFixed(2);
    }

parseInt reads digits until the first character that is not one, so "85.50" becomes 85 and the piastres disappear. The page looked right for every round number anyone would try in a demo. This is the most common way artifacts fail: not by crashing, but by being right in the cases you thought of and wrong in the ones your users bring.

Watch out

Money, dates, time zones, rounding, empty fields and very long inputs are where generated code fails most often. Before anyone relies on an artifact that touches them, test exactly those cases, with values from real life.

4.4 Fixing it in the conversation

“It doesn’t work” gives Claude nothing to work with. The failing test does: what was typed, what came out, what was expected. Send it back into the same conversation, so the reply builds on the page it made:

fix.mjs (part)
const messages = [{role: "user", content: REQUEST}];
messages.push({role: "assistant", content: await ask(messages)});
const {failure} = await check("artifacts/tip-v1.html");
messages.push({role: "user", content: failed(failure)});
const reply = await ask(messages);
const [html] = codeBlocks(reply).filter((b) => b.lang === "html");

The practice server’s reply names the cause and replaces parseInt with Number; a real model would usually find it the same way, from the same evidence. The same test, run again, passes: that, not the reply’s explanation, is what tells you the fix works. In the app the loop is the same: describe the failure precisely, ask for the change, and check the new version before you share it.

Tip

Ask for the test along with the artifact: “and a list of five inputs with the results you expect”. You still check that the expected results are right, but you get a test plan for free, and the artifact is written with those cases in mind.

4.5 Diagrams and documents

Ask for a diagram and you usually get it as Mermaid, a text format for flowcharts and sequences that the app draws for you (Project 4.1 saves one). Because it is text, it can live in your repository next to the code it explains, and change in the same pull request. Check a diagram by reading every arrow against what really happens: a diagram that is wrong teaches the wrong thing to everyone who reads it.

Document artifacts (plans, policies, guides) are checked like any text from Claude: against their sources, with names, numbers and dates verified. A long document drafted by Claude and edited by you is a good way to work; a long document drafted by Claude and sent unread is not.

4.6 Sharing

A published artifact can be opened by anyone with the link. Before you publish, read it for what it contains: an internal price list, a customer’s name in sample data, a URL with a token. If the artifact calls Claude for whoever uses it, think about what they could ask it, and who pays. And decide who maintains it: a useful artifact spreads, and an unmaintained one keeps giving last quarter’s answers long after the quarter has changed.

Professional habit

Treat any artifact that others will rely on as code: put it in the repository, give it a test, and change it through review. The app is a fine place to draft it; it is not a place to maintain it.

Summary

  • Artifacts are standalone outputs (documents, code, pages, diagrams) with versions and sharing.
  • Ask for one like a small specification: purpose, inputs, outputs, constraints, and how it will be checked.
  • Test artifacts like code, in a real browser, with the values real users bring; the calculator was right for 100 and wrong for 85.50.
  • Fix by sending the failing test back into the conversation, and believe the test, not the explanation.
  • Read before you publish, and move what others rely on into the repository.

Quick check answers: 1. Because a demo uses round numbers, and parseInt only loses digits after a decimal point; the test used a real bill, 85.50. 2. The exact input, what came out, and what was expected: it points at the cause, so the fix can be precise. 3. The test: the explanation is what the model says it did; the test is what the page does.

async function lint(file) {
  const browser = await chromium.launch();

  const requests = [];

    "every input has a label": await page.$$eval("input", (inputs) =>

    "makes no network requests": requests.length === 0,
  };
  await browser.close();
  return results;
}

5.2 Web search from the API

Turning search on is one entry in tools. Claude decides whether to search, and what for; max_uses limits how many searches one request may run:

export async function research(question, search = {}) {
  return client.messages.create({
    model: "claude-opus-5-5",
    max_tokens: 4000,
    tools: [
      {type: "web_search_20260209", name: "web_search", max_uses: 3, ...search},
    ],
    messages: [{role: "user", content: question}],

}

5.3 Reading a cited answer

A program shows the answer the way the app does: a number after each cited claim, and the sources at the end:

lib/research.mjs (part)
export function render(response) {
  const sources = [];
  let text = "";
  for (const block of response.content) {
    if (block.type !== "text") continue;
    text += block.text;
    for (const c of block.citations ?? []) {
      if (!sources.includes(c.url)) sources.push(c.url);
      text += `[${sources.indexOf(c.url) + 1}]`;
    }
  }
  return {text, sources};
}

$ node ask.mjs

Sources (searches: 1):
[1] https://coffee-association.example/2026/11/bean-prices
[2] https://news.example/business/coffee-prices-rise
[3] https://beanblog.example/prices-will-double

Every sentence but the last has a source, and that is exactly where the reading starts, not where it ends. Look at what each claim rests on. The 8% comes from the association that set the prices, three days ago: the best source there is. The cause comes from a news report, two days old, which is reasonable. The doubling comes from a blog post five weeks old, whose title states a prediction as a fact: a citation, but not evidence. And the last sentence has no source because it is Claude’s own reasoning, which may be right but should be read as an opinion.

A citation answers one question: where did this sentence come from? It does not answer whether the source is right, current, or relevant to you. Each citation carries the cited_text from the page, so you can check that the source says what the sentence claims; the source itself, you judge as you would any web page.

Watch out

Search results are text written by strangers, and Claude reads them. A page can contain instructions aimed at AI models, as Book 7’s Chapter 15 showed with a café review. Never give a model with web search access to secrets or to tools that act, without checks outside the model on what it does.

5.4 When a search fails

A search can fail while the request succeeds. The response is a normal 200 with a normal stop reason, and the failure sits inside a result block, where the list of results would be:

errors.mjs (part)
for (const block of response.content) {
  if (block.type === "server_tool_use") console.log(`search: ${block.input.query}`);
  if (block.type !== "web_search_tool_result") continue;
  if (Array.isArray(block.content)) {
    console.log(`  ${block.content.length} results`);
  } else {
    console.log(`  search failed: ${block.content.error_code}`);
  }
}
Terminal
$ node errors.mjs
search: coffee prices Africa
  0 results
search: bean prices Kenya
  0 results
search: bean prices Ethiopia
  search failed: max_uses_exceeded
stop: end_turn

The question asked for more than two searches could cover, and the third search came back as max_uses_exceeded. A program that assumed content is always a list would crash here, or worse, report zero results as if the web had nothing. Check the type of content before reading it, and treat an answer built on failed searches as incomplete, whether or not the answer says so.

5.5 Research in the apps

For a broad question (“what are our options for accepting payments in Egypt?”), the apps can run a research process: Claude plans, searches many times, reads the pages it finds, and writes a report with sources. It takes minutes rather than seconds, and it is good at covering ground you would not have thought of. Read its report the way Section 5.3 read the short answer: by its sources. Open the three or four citations that carry the conclusions, check their dates and their authors, and treat the report as a well-organised first draft of your own research, not as the research.

5.6 Connectors

A connector lets Claude reach into a tool your team uses: shared documents, email, a calendar, a code repository, an issue tracker. Most are built on MCP, the open protocol of Chapter 13, and you can add your own. Once connected, Claude can search your documents to answer a question, summarise a thread, or, if the connector allows it, create a ticket or draft a reply.

Three questions decide whether a connector is safe to turn on:

  • What can it read? Everything Claude reads through it becomes part of the conversation. Connect the folder the task needs, not the whole drive.
  • What can it do? Reading is one level of trust; sending, deleting and paying are another. Prefer connectors that ask you before each action, and read the action before you approve it.
  • Who wrote what it reads? An email from outside your company is untrusted text, like a web page. A connector that reads email and can also send it is exactly the combination an attacker would want.

Professional habit

For every connector your team enables, write one line: what it can read, what it can do, and who approved it. Review the list when people change roles, and remove what nobody uses: an idle connector is access nobody is watching.

Part I used Claude in a window, and you carried the code to and from it. Claude Code works where the code is: in your terminal, inside your repository. That makes it the most powerful way to use Claude for software, and the one where permissions matter most.

6.3 The agent loop, visible

With --output-format stream-json, Claude Code prints every event as a line of JSON: each message, each tool call, each result, and a summary at the end. A few lines of JavaScript turn the stream into something a person can read:

watch.mjs (part)
for await (const line of readline.createInterface({input: process.stdin})) {
  const event = JSON.parse(line);
  for (const block of event.message?.content ?? []) {
    if (block.type === "text") console.log(`  says   ${block.text}`);
    if (block.type === "tool_use") console.log(`  calls  ${block.name}: ${JSON.stringify(block.input)}`);
    if (block.type === "tool_result") {
      const content = typeof block.content === "string" ? block.content : JSON.stringify(block.content);
      console.log(`  gets   ${block.is_error ? "(error) " : ""}${short(content)}`);
    }
  }
  if (event.type === "result") {
    const denied = event.permission_denials.length;
    console.log(`  turns: ${event.num_turns}, denied: ${denied}, ` +
      `cost: $${event.total_cost_usd.toFixed(4)}, ${event.subtype}`);
  }
}

6.4 Permissions

Claude Code’s tools fall into two groups. Reading (files, searches, the list of files) is allowed by default. Anything that changes something or runs something (editing files, running commands, fetching from the web) needs permission, given once, for a session, or by rule. A rule names a tool and, for commands, the command:

Terminal
$ claude -p "Run the tests and tell me what fails." --model claude-opus-5-5 --no-session-persistence --allowedTools "Bash(node --test)" --output-format stream-json --verbose | node watch.mjs
  says   I'll run the tests.
  calls  Bash: {"command":"node --test","description":"Run the tests"}
  gets   (error) ok 1 - a round bill | not ok 2 - a bill with piastres
  says   One test fails: "a bill with piastres". total("85.50", 10) returns 93.50 instead of 94.05, because parseInt drops the .50 before the tip is added.
  turns: 2, denied: 0, cost: $0.0669, success

--allowedTools "Bash(node --test)" allows exactly that command, and nothing else: not node --test --watch, not rm. This time the tests ran, for real, and their real result went back to the model: the round bill passes, the bill with piastres fails, the same parseInt bug as Chapter 4. The same rules can live in a settings file, for you or for the whole team (Chapter 8).

Permission modes change the default for a whole session: default asks for each action; acceptEdits lets Claude edit files without asking but still asks before commands; plan lets it read and plan but not change anything, which is the right start for a large task. And there is a mode that skips all permission checks: it exists for throwaway sandboxes, and has no place on a machine with your keys, your email and your company’s code.

Watch out

Allow commands by name, not by pattern you have not thought through. Bash(npm test) is a decision; Bash(*) is giving away the decision. A repository can contain instructions in a README or an issue, written for AI agents to find, and the commands you allowed are what such instructions can reach.

6.5 What a run costs

With --output-format json, print mode returns one JSON object at the end: the result, the number of turns, the token usage and the cost. A script keeps what it needs:

fields.mjs (part)
const result = JSON.parse(fs.readFileSync(0, "utf8"));
const {usage} = result;
console.log({
  subtype: result.subtype,
  result: result.result,
  num_turns: result.num_turns,
  total_cost_usd: result.total_cost_usd,
  tokens: {
    input: usage.input_tokens,
    cache_written: usage.cache_creation_input_tokens,
    cache_read: usage.cache_read_input_tokens,
    output: usage.output_tokens,
  },
});
Terminal
$ claude -p "Explain price.mjs in two sentences." --model claude-opus-5-5 --no-session-persistence --output-format json | node fields.mjs
{
  subtype: 'success',
  result: 'price.mjs exports total(bill, tip), which adds the tip percentage to the bill. It reads the bill with parseInt, so the piastres of a bill like 85.50 are dropped.',
  num_turns: 2,
  total_cost_usd: 0.06547180000000001,
  tokens: { input: 0, cache_written: 12267, cache_read: 12184, output: 85 }
}

Two turns (reading the file, then answering), about seven cents. Look at the tokens: twelve thousand written to the cache, twelve thousand read from it, and almost nothing else. Before your prompt says a word, Claude Code sends its own instructions and the descriptions of its tools, and that is most of every request. Caching makes the second turn cheap; the first still pays to write the cache. The practice server counts tokens approximately, so the real figures will differ, but the shape does not: an agent’s fixed context is a large part of its cost, and the cost is per turn.

Tip

On a subscription, Claude Code’s usage counts against your plan’s limits rather than a bill; with an API key, every turn is billed. Either way, /cost in an interactive session and the JSON output in print mode tell you what a task used. Look after a few tasks, and you will know what your work costs.

7.4 Habits for real repositories

  • Small tasks. “Add VAT to receipts” is a task; “clean up the billing code” is a week. Small tasks give small diffs, and small diffs get real reviews.
  • Questions before changes. In an unfamiliar codebase, ask first (“where is the total computed?”, Project 7.1), or start in plan mode, and correct the plan before any file changes.
  • Tests as the contract. If the tests are weak, the agent’s “they pass” means little. Ask for the tests first, read them, then ask for the change.
  • Undo without fear. git checkout -- . throws away a change you do not like; a fresh attempt with a better prompt is often faster than repairing a bad one.
  • You commit. Read every line, run the tests yourself, and make the commit with your name on it. The agent wrote the change; you are the one who says it is right.

Professional habit

Hold changes made with Claude Code to the same review as changes from a colleague: the same tests, the same reviewer, the same standards. A team that reviews agent changes more lightly will soon have a codebase nobody understands.

8.3 Hooks: rules that hold

CLAUDE.md says “never push”. That is advice: the model reads it and usually follows it. Usually is not enough for some rules. A hook is a command Claude Code runs itself at a moment in the loop (before a tool runs, after it runs, when a prompt is submitted, when the session stops), whatever the model thinks. The project’s hook runs before every shell command:

.claude/hooks/no-push.sh (part)
input=$(cat)
case "$input" in
  *"git push"*) echo "Pushing is done by a person, after review." >&2; exit 2 ;;
esac
exit 0
Terminal

A model can ignore advice; it cannot ignore a hook.

Hooks are ordinary programs, so they can do far more than block: format a file after every edit, run the tests when the session ends, add today’s on-call name to every prompt, write an audit log. Keep them fast, since they run on every matching event, and remember that they run with your permissions.

8.4 Skills

A skill is a folder with a SKILL.md: a name, a one-line description, and instructions, plus any scripts or templates the task needs. Claude Code sees only the descriptions until a task calls for a skill; then it loads the instructions. Unlike CLAUDE.md, which is sent with every request, a skill costs nothing until it is used, so a team can keep dozens.

.claude/skills/release-notes/SKILL.md
---
name: release-notes
description: Write release notes for the café app from the commits since the last release.
---
List the changes under Added, Changed and Fixed, one line each, in words a customer understands. Leave out changes customers cannot see.

Project 8.2 runs it. The description matters more than it looks: it is what Claude reads to decide whether the skill fits the task, so write it as the situation it is for (“write release notes for the café app”), not as a title (“release helper”).

Professional habit

Review changes to CLAUDE.md, settings, hooks and skills like code, in pull requests, with someone who understands what they allow. They decide what an agent knows, may do and must not do, for everyone on the team.

9.3 Rules that hold for everyone

The first commit message was “fixed stuff”. The repository has a commit-msg hook, a script git itself runs before accepting a commit:

githooks/commit-msg (part)
if ! head -n 1 "$1" | grep -qE '^(feat|fix|docs|refactor|test|chore)(\([a-z-]+\))?: .+'; then
  echo "Commit messages follow Conventional Commits: type(scope): subject" >&2
  exit 1
fi

The message did not match, the hook exited with 1, and git refused the commit; its message went back to the model, which committed again with a message that follows the convention, naming the issue. This is a different kind of hook from Chapter 8’s: it belongs to git, not to Claude Code, so it applies to every commit in the repository, by a person, by Claude Code, or by any other tool. Rules that matter to the team belong where they hold for everyone: git hooks locally, and on the server, branch protection and required checks (Chapter 10).

Tip

Keep git hooks in the repository (here in githooks/) and point git at them with git config core.hooksPath githooks, as the chapter’s setup does. Hooks in .git/hooks are not versioned, so each developer, and each agent’s machine, would have a different set.

9.4 The pull request

The description came from the repository’s template, section by section: what changed and why, how it was tested, and the issue it closes. Project 9.3 gathers it with the branch’s commits and the size of the change, which is what a reviewer reads first. On a hosting service such as GitHub, “Closes #42” in a pull request closes the issue when the pull request is merged, and Claude Code can open the pull request itself through the service’s command-line tool, if you allow it.

Twelve turns and about seventy cents, by the practice server’s count: a real task of this size usually costs less than an hour of anyone’s time, and the review it needs still costs a person’s attention. That attention is better spent on a small, well-described pull request than on a large one.

Watch out

Do not let an agent merge its own pull request, or push to the main branch. Opening a pull request is a proposal; merging is a decision. Keep decisions with people, and make the server enforce it with branch protection, so that no permission set by mistake can bypass it.

Chapter 10

Claude Code for Teams and CI

In this chapter you will learn to

A team using Claude Code needs two things that a single developer does not. The first is shared rules that a person cannot loosen by accident: what every session may do, and what none may. The second is automation: Claude Code running on every pull request, in the same pipeline as the tests, without anyone typing. This chapter builds both, and shows what each one costs.

Bit

The settings, the denial, the CI script, its exit codes and its costs are real Claude Code behaviour. The verdicts come from the practice server, scripted to depend on the diff it received: blocking the unrounded total, passing the rounded one.

10.2 A review in CI

In continuous integration nobody can approve a tool call, so the safest run has no tools at all: Claude Code reads the diff from standard input, answers, and stops. Three flags make it fit for a pipeline: --tools "" so it can only read what it is given, --max-budget-usd so a run cannot overspend, and --json-schema so the verdict comes back as data:

ci/review.sh (part)
claude -p "Review this diff for the café app. Report blockers only: bugs, missing tests for changed behaviour, or money handled wrongly." < /tmp/branch.diff \
  --model claude-opus-5-5 --tools "" --max-budget-usd 0.50 --no-session-persistence \
  --output-format json --json-schema "$(cat review/schema.json)" > review.json
node -e '
  const r = JSON.parse(require("fs").readFileSync("review.json", "utf8"));
  const v = r.structured_output;
  console.log(JSON.stringify(v), `($${r.total_cost_usd.toFixed(4)})`);
  process.exit(r.subtype === "success" && v.ok ? 0 : 1);
'
review/schema.json
{
  "type": "object",
  "properties": {
    "ok": {
      "type": "boolean"
    },
    "blockers": {
      "type": "array",
      "items": {
        "type": "string"
      }

  },

    "ok",

  ]

The branch adds VAT to receipts, the change of Chapter 7, with the rounding problem its review found. The CI step:

Terminal

The verdict is an object, not a paragraph: ok is false and the blocker names the file and the problem, so the script exits with 1 and the pipeline fails. With --json-schema, Claude Code gives the model a tool to report its answer in that shape and returns it in structured_output; a script never has to parse prose.

Look at the cost, too: a cent and a half. The runs of the earlier chapters cost about twelve cents a turn, mostly for Claude Code’s own instructions and tool descriptions; with no tools, there is little to send but the diff and the request. In a pipeline that runs on every push, that difference is the budget.

The developer rounds the total, commits, and the same step runs again:

Terminal
$ cp changes/receipt-rounded.mjs src/receipt.mjs && git commit -qam "fix(receipt): round the total" && sh ci/review.sh; echo "exit $?"
{"ok":true,"blockers":[]} ($0.0143)
exit 0

Watch out

The diff is input from whoever opened the pull request, and a pull request from outside the team can contain text written to steer a reviewer. A review with no tools can only answer; it cannot run anything. Never give a CI run tools that write, or secrets it does not need, on code nobody on the team has looked at.

10.3 In the pipeline

The workflow runs the same script on every pull request, with the API key from the repository’s secrets, read-only access to its contents and a time limit (Project 10.3 checks the file). Anthropic also publishes a GitHub Action for Claude Code, which can review pull requests and answer comments that mention it; the principles are the same: the fewest tools that do the job, a limit on spending, and output a script can read.

What the automatic review produces is information for a person, not a decision. A failing review should block a merge the way a failing test does; a passing one should not approve anything. The pull request still needs a human reviewer, who now starts with the mechanical problems already found.

Chapter 11

The Claude API

In this chapter you will learn to

Chapter 1 sent one message and read one answer. A product sends thousands, from users who are waiting, through networks that fail, to a service that sometimes says “not now”. This chapter covers what every production program needs around the call itself: streaming, retries, timeouts, answers that do not fit, and what to do when the model you wanted is busy.

Bit

The errors, retries, timeouts and streaming events in this chapter are real behaviours of the SDK against the practice server, which can be made slow, busy or overloaded on purpose. The words of the answers are the practice server’s.

11.1 Streaming

A long answer can take many seconds to write. Without streaming, the user stares at nothing until it is complete; with it, the first words appear almost at once. The SDK’s stream gives you the text as it arrives, and the complete message at the end:

stream.mjs (part)
const stream = client.messages.stream({
  model: "claude-opus-5-5",
  max_tokens: 1000,
  messages: [{role: "user", content: "Describe our rose latte for the menu board in two sentences."}],
});
let pieces = 0;
stream.on("text", (piece) => {
  process.stdout.write(pieces++ % 4 === 0 ? `|${piece}` : piece);
});
const message = await stream.finalMessage();
console.log(`\n--- ${pieces} pieces; stop: ${message.stop_reason}; ${message.usage.output_tokens} tokens out`);
Terminal
$ node stream.mjs
|A latte made with |our Ethiopian espresso, steamed |milk and a touch |of rose syrup. Floral, |gentle and only here |for the spring.
--- 23 pieces; stop: end_turn; 39 tokens out

Each bar marks where every fourth piece began: the answer arrived in 23 pieces, and the program printed each one immediately. finalMessage() then gives the same message a non-streaming call would have returned, with its stop reason and usage, so the rest of the program does not care how it arrived. Stream whenever a person is waiting, and whenever max_tokens is large: long requests that do not stream can hit HTTP timeouts before the answer is finished.

11.2 Retries

Some failures are worth trying again: 429 (too many requests), 529 (overloaded), other 5xx errors, and broken connections. Others are not: a 400 will fail the same way every time. The SDK knows the difference, and retries the first kind by itself, twice by default, waiting longer each time and respecting the retry-after header when the API sends one. A wrapper around fetch makes it visible:

retry.mjs (part)
const statuses = [];
const counting = async (url, init) => {
  const response = await fetch(url, init);
  statuses.push(response.status);
  return response;
};
Terminal
$ node retry.mjs
"Nile Frost": cold, clear, and from here.
  maxRetries 2, attempts: 429 → 429 → 200
RateLimitError: 429
  maxRetries 0, attempts: 429

With the default, the request failed twice with 429, waited as the server asked, and succeeded on the third attempt; the program saw only the answer. With maxRetries: 0, the first 429 became a RateLimitError. Leave the retries on for interactive requests, set them higher for background jobs that can wait, and never write a second retry loop around the SDK’s own: the waits multiply.

Watch out

Retries make failures slower, not rarer. If your requests are rate-limited regularly, the fix is fewer or smaller requests (caching, batching, a smaller model for simple tasks, Chapter 15) or a higher limit, not more retries.

11.3 Timeouts

The SDK waits up to ten minutes by default, which suits long answers and not much else. Set the timeout for the request in front of you:

timeout.mjs (part)
for (const timeout of [1000, 10000]) {
  const start = Date.now();
  try {
    const r = await client.messages.create(request, {timeout, maxRetries: 0});
    console.log(`timeout ${timeout} ms: ${r.content[0].text}`);
  } catch (error) {
    console.log(`timeout ${timeout} ms: ${error.constructor.name}`);
  }
  console.log(`  after ${Math.round((Date.now() - start) / 1000)} s`);
}
Terminal
$ node timeout.mjs
timeout 1000 ms: APIConnectionTimeoutError
  after 1 s
timeout 10000 ms: Customers like the coffee and the staff; they complain about the queue at lunch and the noise in the evening.
  after 3 s

The practice server took three seconds on purpose. With a one-second timeout, the SDK gave up and raised APIConnectionTimeoutError; with ten seconds, the answer arrived. In the JavaScript SDK the timeout is in milliseconds; other SDKs use their own units (seconds in Python, for example). Timeouts are retried like other connection errors, so the longest wait is the timeout times the number of attempts: set both with that sum in mind.

11.4 Answers that do not fit

When an answer reaches max_tokens, it stops, mid-sentence if need be, and stop_reason says max_tokens. A program must not show it as complete. To continue, keep the cut answer in the history and ask for the rest in a new user message:

truncate.mjs (part)
const messages = [{role: "user", content: "Write the welcome text for our new website."}];
const first = await client.messages.create({model: "claude-opus-5-5", max_tokens: 40, messages});
console.log(`[${first.stop_reason}] ${text(first)}`);

messages.push({role: "assistant", content: first.content});
messages.push({role: "user", content: "Continue exactly where you stopped."});
const rest = await client.messages.create({model: "claude-opus-5-5", max_tokens: 1000, messages});
console.log(`[${rest.stop_reason}] ${text(rest)}`);
Terminal
$ node truncate.mjs
[max_tokens] Welcome to Bit Cafe, where every cup starts with beans we roast ourselves in small batches. We opened in Zamalek in 2019 with one machine and a long table, and
[end_turn] today we serve three neighbourhoods, but the table is still the heart of every branch: a place to work, to meet, or to read slowly. Come for the coffee; stay for the company.

The first answer stopped at “and”; the second began with “today”, because the model could read exactly where its first answer ended. The simpler fix is often the better one: a larger max_tokens, or a request for a shorter answer.

An older trick no longer works here: writing the start of Claude’s answer yourself, as a last assistant message, for Claude to continue. Current models refuse it:

Terminal
$ node prefill.mjs
400 BadRequestError
  messages: this model does not support assistant message prefill; the last message must be a user message

To control the form of an answer, say it in the instructions, or ask for structured output (Chapter 12); to continue an answer, use a user message as above.

11.5 When a model is busy

An overloaded model returns 529, and after the SDK’s retries the error reaches your code. For a feature that must answer, fall back to another model that can do the job, and say so in your logs (Project 11.3). Every response also carries a request id, on success and on error: log it with your own request, and when something goes wrong, it is the first thing Anthropic’s support asks for (Project 11.2).

Professional habit

For every call to the API, log the model, the request id, the stop reason, the tokens and the time taken. When a user reports a strange answer, those five fields are the difference between finding the cause in a minute and guessing for a day.
