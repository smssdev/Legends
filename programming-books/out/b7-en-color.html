1.1 A model on your computer

Create a folder, and install one package:

npm install node-llama-cpp@3.22.3

node-llama-cpp runs open models with llama.cpp, a fast engine written in C++, and gives them a JavaScript interface. Every example in the book loads its model through the same small file:

lib/model.mjs
// The book's model: Qwen3 4B Instruct (2507), an open model under the
// Apache 2.0 license, quantized to 4 bits by Unsloth (2.5 GB). It is
// downloaded once, the first time an example runs, into
// ~/.node-llama-cpp/models; then everything runs on your computer, offline.
import {getLlama, LlamaLogLevel, resolveModelFile} from "node-llama-cpp";

export const MODEL = "hf:unsloth/Qwen3-4B-Instruct-2507-GGUF:Q4_K_M";

export async function loadModel() {
  const llama = await getLlama({gpu: false, logLevel: LlamaLogLevel.error});
  return llama.loadModel({modelPath: await resolveModelFile(MODEL)});
}

resolveModelFile downloads the model from Hugging Face, a public library of open models, the first time, and finds it on disk after that. gpu: false runs on the processor, so the book’s numbers do not depend on a graphics card; if you have one, removing that option makes everything faster and changes nothing else.

Did you know?

“Open model” means the trained numbers are published and you may run them yourself. Each one comes with a license, and they are not all alike: some forbid commercial use, some limit large companies, and some, like Apache 2.0, allow nearly anything. The book’s model was chosen for that license. Read it before you put any model in a product.

1.2 The only thing a model does

Give a model some text and it returns one thing: for every token it knows, the probability that it comes next. This program asks for those probabilities after an unfinished sentence and prints the eight highest:

next.mjs
import {loadModel} from "./lib/model.mjs";

const model = await loadModel();
const context = await model.createContext({contextSize: 512});
const sequence = context.getSequence();

// Everything a model does is this: given the tokens so far, a probability
// for every possible next token.
const prompt = "The café sells coffee and";
const tokens = model.tokenize(prompt);
const options = {probabilities: true};
for await (const output of sequence.evaluateWithMetadata(tokens, options)) {
  const {probabilities} = output;
  console.log(`"${prompt}" ... 8 likely tokens, of ${probabilities.size}:`);
  for (const [token, probability] of [...probabilities].slice(0, 8)) {
    const piece = JSON.stringify(model.detokenize([token])).padEnd(14);
    const percent = (probability * 100).toFixed(1).padStart(5);
    const bar = "#".repeat(Math.round(probability * 40));
    console.log(`  ${piece} ${percent}%  ${bar}`);
  }
  break;
}

A chat assistant is this, in a loop. It picks a token, appends it, asks for the probabilities again, and stops when it picks a special token that means “end”. A ten-line answer is a few hundred of these steps. The fluency comes from being very good at this one step; the mistakes come from the same place, because a fluent continuation and a true one are not the same thing.

Tip

When an assistant gives an answer you did not expect, ask yourself: “what text usually follows a question like mine?” A vague question is followed, in the world’s text, by a generic answer. A question that contains your actual code, error and constraints is followed by something specific. Chapter 3 is built on that idea.

1.3 Tokens

A model does not read letters or words. Its tokenizer cuts text into tokens from a fixed vocabulary: common words become one token, rare words several, and anything can always be spelled out piece by piece. This program cuts the same sentence in English and in Arabic:

tokens.mjs
import {loadModel} from "./lib/model.mjs";

const model = await loadModel();

// The same sentence in two languages, and how the model cuts each into
// tokens.
const sentences = [
  "The café opens at 8:30 and closes at 22:00.",
  "يفتح المقهى في 8:30 ويغلق في 22:00.",
];
for (const sentence of sentences) {
  const tokens = model.tokenize(sentence);
  const pieces = tokens.map((token) => model.detokenize([token]));
  const words = sentence.split(" ").length;
  const size = `${sentence.length} characters, ${tokens.length} tokens`;
  console.log(`${words} words, ${size}`);
  console.log("  " + pieces.map((piece) => `[${piece}]`).join(""));
}

Three things are worth seeing. Most English words are one token with their leading space. Numbers are cut into single digits: to this model, 22:00 is five tokens. And the Arabic sentence, two words shorter, takes more tokens: “يفتح” is two pieces and “المقهى” three. The vocabulary was built from text that is mostly English and Chinese, so Arabic words are less often whole entries.

That matters because tokens are the unit of everything. Hosted models are priced per token; the context window, how much text a model can consider at once, is measured in tokens; and speed is tokens per second. Project 1.1 measures the difference on a full sentence: 1.18 tokens per English word, 2.63 per Arabic word. The same conversation in Arabic costs more, fills the window sooner and takes longer, with this model. Other models have other vocabularies, so measure the ones you use.

Watch out

Counting letters, reversing words and doing arithmetic on long numbers are hard for models for the reason you just saw: the model never sees the letters, only the pieces. When you need an exact count, a sort or a sum, ask the model to write code that does it, and run the code.

Quick check

  1. Why does “ past” appear in a list of things a café sells?
  2. A text has 1,000 English words. Roughly how many tokens is it for this model, and how many if it were 1,000 Arabic words?
  3. Why is “how many letters are in this word?” harder for a model than “what does this word mean?”

The answers are at the end of the chapter, after the summary.

1.4 Temperature

The probabilities are fixed; how the next token is chosen from them is up to you. At temperature 0 the most likely token always wins. Higher temperatures flatten the probabilities and then draw at random, so less likely tokens get a chance. The seed fixes the random draw, so the same seed repeats the same choices:

temperature.mjs
import {LlamaCompletion} from "node-llama-cpp";
import {loadModel} from "./lib/model.mjs";

const model = await loadModel();
const context = await model.createContext({contextSize: 512});
const completion = new LlamaCompletion({
  contextSequence: context.getSequence(),
});

// Temperature 0 always takes the most likely token; higher temperatures
// sample, so the answer changes with the seed.
const request = "A short, friendly name for a new café:";
for (const temperature of [0, 1.2]) {
  console.log(`temperature ${temperature}:`);
  for (const seed of [1, 2, 3]) {
    const text = await completion.generateCompletion(request, {
      temperature,
      seed,
      maxTokens: 12,
    });
    console.log(`  seed ${seed}: ${text.trim().split("\n")[0]}`);
  }
}

Professional habit

When an AI feature is part of your product, record the model, its version, the temperature and the prompt with every result you keep. When a user reports a strange answer, those four things are the difference between reproducing it in a minute and guessing for a day.

  • Parameters are the numbers learned in training: here about four billion. Training showed the model trillions of tokens of text and adjusted those numbers, again and again, so that its predictions of the next token got better. Everything the model “knows” is in them, as patterns, not as a list of facts it can look up.
  • 4-bit quantized means each number is stored in about four bits instead of sixteen. The file is four times smaller and much faster, and a little less precise. That is why a 4-billion-parameter model fits in 2.5 GB.
  • The vocabulary is the tokenizer’s list: 151,936 pieces, the same number you saw in Section 1.2.
  • The context window is the most tokens the model can consider at once: the instructions, the conversation, any documents you paste and the answer, together. Anything outside it does not exist for the model. Our examples use small windows (512 or 2,048 tokens) because memory grows with the window.

Two more facts follow from the training. A model’s knowledge stops at the date its training text was collected: it can be fluent about a library’s old version and know nothing of the current one. And a model has no memory between conversations: a chat assistant seems to remember because the application sends the earlier messages again, inside the context window, every time.

1.6 Confident and wrong

The paper “Brewing Tokens” by Layla Hassan does not exist; it was made up for this section. This program asks the model to summarize it, once plainly and once with permission to say it is not sure:

In English, the model did well: it said, both times, that it knows no such paper. Then the same question was asked in Arabic, for the Arabic edition of this book, with the same model at the same temperature. This is what people call a hallucination, and Section 1.2 already explained it. The model is not looking anything up. It is producing the most likely continuation of the text, and the most likely continuation of “summarize this paper” is a summary. Whether it refuses depends on whether refusing was common, in its training, after text like yours: in English, where it was trained on more examples of “there is no such paper”, it refused; in Arabic it did not. The model gave no sign of which answer was true. It never does: a wrong answer comes out as fluently as a right one.

Watch out

The most dangerous inventions are the plausible ones: a function that sounds like it belongs to a library, a configuration option with the right naming style, a reference to a real-looking source. Before you rely on any name, number, quotation or link from a model, check it where it is defined: the documentation, the code, the source itself.

Larger hosted models invent less often, and many can now search the web or read your files, which helps a great deal. None of that changes the mechanism. Throughout this book, you will use three defences, and this section has already shown two of them: give the model the facts instead of asking it to remember them (Chapter 14), allow and ask for “I don’t know” (Chapter 3), and check what matters (every chapter).

Summary

  • A language model does one thing: given the tokens so far, it gives a probability to every possible next token. Generation repeats that, one token at a time.
  • Tokens are pieces of words from a fixed vocabulary. They are the unit of price, context and speed, and the same text can need very different numbers of them in different languages.
  • Temperature decides how the next token is chosen: 0 for the most likely, higher for variety. A seed makes random choices repeatable.
  • Parameters hold what the model learned, as patterns. Its knowledge stops at its training date, and it remembers nothing between conversations.
  • Models invent fluent answers when the likely continuation is not the true one. Give them facts, let them say “I don’t know”, and check what matters.

The model never sees letters, only tokens that may hold several letters each; meaning, on the other hand, is exactly what it learned from seeing words in context.

2.2 Chat: the whole conversation, every time

A chat session in node-llama-cpp keeps the conversation for you. This program asks two questions in one session, prints how many tokens the context holds after each answer, and then asks the second question again, in a new session:

chat.mjs
import {LlamaChatSession} from "node-llama-cpp";
import {loadModel} from "./lib/model.mjs";

const model = await loadModel();
const context = await model.createContext({contextSize: 2048});
const options = {temperature: 0, maxTokens: 120};
const systemPrompt = "You are a concise assistant for JavaScript developers. Answer in at most two lines.";

// The model remembers nothing: every turn, the whole conversation is sent
// again.
const sequence = context.getSequence();
const session = new LlamaChatSession({contextSequence: sequence, systemPrompt});
for (const question of ["How do I read a JSON file in Node?", "And how do I write one?"]) {
  const answer = await session.prompt(question, options);
  // How many tokens the conversation now takes in the context.
  console.log(`> ${question}\n${answer}\n[${sequence.nextTokenIndex} tokens]\n`);
}

sequence.dispose();
console.log("A new conversation, asked only the second question:");

  contextSequence: context.getSequence(),

“And how do I write one?” only makes sense after the first question, and in the first session the model understood it: write a JSON file. The context had grown from 75 to 120 tokens, because the system prompt, the first question, the first answer and the second question were all in it. In the new session, the same five words meant nothing in particular, and the model answered a different question with confidence: how to write a variable.

Every chat product works this way. The model remembers nothing; the application sends the conversation again with each message. Three practical rules follow:

  • A long conversation gets slower and, with hosted models, more expensive with every message, because every message resends all the earlier ones.
  • When the conversation outgrows the context window, the application must drop or summarise the oldest messages, and the model then forgets what you said at the start.
  • When an assistant starts to confuse an old task with a new one, start a new conversation. It is not rude; it is a clean context.

Tip

The system prompt is the instruction placed before the conversation: here, “a concise assistant for JavaScript developers, at most two lines”. Chat products let you set one, often called custom instructions or a project prompt. Put there what is true for every question: your language, your framework and versions, how long answers should be. Then you do not repeat it in every message.

2.3 Completion: the code around your cursor

An editor assistant does not chat. As you type, it sends the code before the cursor and the code after it, and asks the model for the piece in between. This is called fill in the middle, and some models, like the book’s, were trained for it:

complete.mjs
import {LlamaCompletion} from "node-llama-cpp";
import {loadModel} from "./lib/model.mjs";

const model = await loadModel();
const context = await model.createContext({contextSize: 1024});
const completion = new LlamaCompletion({
  contextSequence: context.getSequence(),
});

// An editor sends the code before and after the cursor, and asks for the
// middle.
const before = `// Total price of an order, with tax.
export function total(items, taxRate) {
`;
const after = `
}

export const TAX_RATE = 0.14;
`;

// Raw, the model keeps writing past the function; an editor stops at the
// end of the block.
for (const stop of [[], ["\n}"]]) {
  const middle = await completion.generateInfillCompletion(before, after, {
    temperature: 0,
    maxTokens: 60,
    customStopTriggers: stop,
  });
  console.log(stop.length ? "--- stopped at the block's end:" : "--- raw:");
  console.log(middle.replace(/^\n/, ""));
}

The middle is reasonable code, but look at the end of the raw answer: a closing brace. The code after the cursor already has one, so accepting the raw text would leave two and break the file. The second run stops when the model writes a newline and a brace at the start of a line, which is what an editor does in its own way: it trims, checks the brackets, and shows only what fits.

Notice also what the model assumed. The comment says “total price of an order” and nothing more, so it invented the shape of an item: item.price and item.quantity. If your items have count, the suggestion is wrong, and it looks exactly like right code. A completion knows only what is near the cursor, plus whatever other files the editor chose to send. Open the files it should know about, and name things clearly: the clearer the code around the cursor, the better the suggestion.

Watch out

Completions arrive one Tab away, many times an hour. That is what makes them useful, and what makes them easy to accept without reading. Read each one as you would read a colleague’s code in review: the names, the edge cases, the units. A wrong field name accepted at 4 p.m. is a bug report at 9 a.m.

2.4 Agents: a model that uses tools

An agent is a model that can ask your program to do things. You describe some functions; the model may answer with a call instead of text; your program runs the call and gives the result back; and the model continues, until it answers. Here the agent may list and read the files of a small project, and every call is printed:

agent.mjs (part)
const functions = {
  listFiles: defineChatSessionFunction({
    description: "List the files of the project",
    handler() {
      return show("listFiles", {}, fs.readdirSync("cafe", {recursive: true}));
    },
  }),
  readFile: defineChatSessionFunction({
    description: "Read one file of the project",
    params: {type: "object", properties: {path: {type: "string"}}},
    handler({path}) {
      return show("readFile", {path}, fs.readFileSync(`cafe/${path}`, "utf8"));
    },
  }),
};

// Show every call, so we can see what the agent did, not only what it
// said.
function show(name, params, result) {
  console.log(`[tool] ${name}(${JSON.stringify(params)})`);
  return result;
}

  • An agent can only be as good as its instructions and tools. The same model failed and succeeded with the same tools; only the words changed. Chapter 3 is about those words.
  • Tools are permissions. This agent can only read, inside one folder. An agent that can write files, run commands or call services can do damage when it is wrong. Give it the least it needs, and review what it did. Chapter 12 goes further.
  • Show the calls. The [tool] lines are how you know the answer came from the file, not from the model’s imagination. Good agent products show every step for the same reason.

2.6 What the tool can see

An assistant can only use what is in its context. How much is that, against a real code base? This program counts the tokens in one library, node-llama-cpp itself:

context.mjs (part)
// How much text a real library is, against the size of a context window.
const folder = "node_modules/node-llama-cpp/dist";
let files = 0;
let tokens = 0;
for (const name of fs.readdirSync(folder, {recursive: true})) {
  if (name.endsWith(".js")) {
    const text = fs.readFileSync(path.join(folder, name), "utf8");
    files++;
    tokens += model.tokenize(text).length;
  }
}
console.log(`node-llama-cpp: ${files} JavaScript files, ${tokens} tokens`);
for (const window of [8_192, 128_000, 1_000_000]) {
  const share = Math.min(100, (100 * window) / tokens).toFixed(0);
  console.log(`a ${window}-token window holds ${share}% of it`);
}

One mid-sized library is about 410,000 tokens. An 8,000-token window holds 2% of it; even a 128,000-token window, common in hosted models, holds less than a third. Your application, with its dependencies, is far larger. So every tool that works with code must choose what to send: the open files, files with similar names, the results of a search, the files an agent decided to read. When an assistant gets your code wrong, the first question is not “is the model clever enough?” but “did it see the right files?”

And whatever a hosted tool sends leaves your computer. Before you use one at work, find out three things: what it sends (the current file, open files, the whole repository), where it goes and whether it is kept, and whether your company allows it. Chapter 15 covers this in detail; the short rule is that a secret in a file is a secret sent to the tool.

Professional habit

Keep secrets out of the files an assistant can see: in environment variables or a secret manager, never in the code, and never in a file you paste into a chat. Most tools also let you exclude files or folders; exclude anything that holds keys, customer data or configuration for production.

Summary

  • Every AI tool is a model in one of three shapes: a chat, a completion, or an agent with tools.
  • A chat resends the whole conversation each time; the model remembers nothing, so a new conversation starts from zero.
  • An editor completion fills the middle between the code before and after the cursor, and must be trimmed and read.
  • An agent calls functions your program runs, and its results go back into the context. Its instructions decide whether it uses its tools; its tools decide what it can break.
  • Speed is time to the first token and tokens per second. Context is limited, so every tool chooses what to send, and what it sends to a hosted model leaves your computer.

4.1 Start with a specification

The feature is small and real: split a café bill between friends, in whole piastres, with a tip. Before asking for anything, write down what correct means, including examples you worked out yourself:

splitBill(total, people, tipPercent) splits a café bill. total is in piastres (an integer), people is a whole number of at least 1, tipPercent is a whole number such as 10. The tip is total * tipPercent / 100, rounded to the nearest piastre. It returns an array with one integer amount per person, adding up exactly to total plus tip; when it does not divide evenly, the first people pay one piastre more. It throws a RangeError if people is less than 1. Examples: splitBill(1000, 3, 10) is [367, 367, 366]; splitBill(995, 2, 15) is [572, 572]; splitBill(1000, 4, 0) is [250, 250, 250, 250].

The examples matter most. “splitBill(1000, 3, 10) is [367, 367, 366]” settles questions that words leave open: is the tip rounded before or after the split, who pays the extra piastre, are amounts integers. An early version of this chapter had no examples, and the model’s tests expected [27, 27, 27, 27] for a bill that adds up to 110: confident, specific and wrong. The model can write tests; it cannot know what your business means by correct. That knowledge is yours, and the examples are where you put it.

    const result = runTests(testFile);

  }
}

6.2 A wrong answer, without a crash

Bugs that crash are the easy ones. This function should list the three most expensive drinks, and it lists the wrong three:

shop/top.mjs
import {MENU} from "./menu.mjs";

export function topThree(menu) {
  return menu
    .map((drink) => drink.price)
    .sort()
    .reverse()
    .slice(0, 3)
    .map((price) => menu.find((drink) => drink.price === price).name);
}

console.log(topThree(MENU));
Terminal
$ node shop/top.mjs
[ 'cold brew', 'latte', 'espresso' ]

The mocha, at 1,050, is missing. Ask for the cause and a fix, then run the fix:

Terminal
$ node wrong.mjs
**Most likely cause:** The function incorrectly assumes that each price appears only once, and `find()` may return the wrong drink if multiple drinks share the same price, or it fails to properly match the drink by price due to the order of iteration.

**Fixed function:**
```javascript
export function topThree(menu) {
  return menu
    .sort((a, b) => b.price - a.price)
    .slice(0, 3)
    .map(drink => drink.name);
}
```

--- run:
before: [ 'cold brew', 'latte', 'espresso' ]
fixed:  ["mocha","cold brew","latte"]
right:  ["mocha","cold brew","latte"]

The fix works: the three right drinks, in order. The diagnosis is wrong. Repeated prices and find are not the problem; there are no repeated prices. The real cause is .sort() with no compare function, which sorts numbers as text: “1050” comes before “250” because “1” comes before “2”, so after reverse() the mocha is last. The model’s new code happens to avoid that by sorting with b.price - a.price, for a reason it never states.

Does a wrong reason matter, if the fix works? Yes, for two reasons. The next time someone sorts numbers with .sort(), nobody will know it is a bug, because the lesson was never learned. And the fix has a side effect the explanation does not mention: menu.sort sorts the array in place, so calling topThree(MENU) now reorders the café’s menu for every other part of the program. A fix you do not understand is a change you cannot review.

The Arabic edition got no fix at all. Asked the same question in Arabic, the model settled on the same wrong cause, then repeated nearly the same sentence until the answer ran out of room, 800 tokens, before any code. When a model starts going in circles, a longer answer will not help; a narrower question will (Exercise 3).

Watch out

“It works now” is the most dangerous sentence in debugging with AI. Before you accept a fix, say in one sentence why the old code was wrong and the new code is right. If you cannot, you have not found the bug yet; you have found a change that hides it, for now.

  3. What does the model’s fix do to MENU?

6.3 A reproduction that reproduces

A failure that happens at night, on a server, in the middle of a long job, is hard to study. A minimal reproduction, a few lines that fail the same way, makes it easy: you can run it, change it, and share it. Assistants are good at writing them, and here is the check that matters: run it and compare the error.

lib/run.mjs (part)
export function errorLine(output) {
  const found = output.match(/\b(\w*Error): (.*)$/m);
  return found ? `${found[1]}: ${found[2]}` : "(no error)";
}
repro.mjs (part)
// A reproduction is only useful if it fails the same way: run it and
// compare the error.

const got = errorLine(run("repro/attempt.mjs").output);
console.log(`wanted: ${wanted}`);
console.log(`got:    ${got}`);
console.log(got === wanted ? "same error: a reproduction" : "different: not a reproduction yet");
Terminal
$ node repro.mjs

const orders = [];

  return order.price;
}

  return orders.reduce((sum, order) => sum + priceOf(order), 0);
}

total();

wanted: TypeError: Cannot read properties of undefined (reading 'price')
got:    (no error)
different: not a reproduction yet

The script looks like the failing code, with priceOf and total and a reduce, and it does not fail: it adds up an empty list, which is zero. A reproduction that does not reproduce is worse than none, because it looks like evidence that the problem is somewhere else.

The first version of this check was wrong too, and it is worth seeing why. It looked for the error only at the start of a line. In the log, each line starts with a time, so it found no error in the log, found no error in the script, and announced “same error: a reproduction”. Two absences compared equal. A check that can pass when nothing happened is not a check; this one now finds the error anywhere on the line, and would say “wanted” something before it says “same”.

Professional habit

When you fix a bug, keep the reproduction as a test. It already fails the right way; after the fix it passes; and from then on it guards that exact failure. Debugging with an assistant produces many small scripts; the ones that reproduce a real failure are worth keeping.

Summary

  • Give the assistant the full error, the trace, and the files the trace names.
  • The crash site and the cause are often different places; the model tends to name the crash site.
  • A suggested cause is a hypothesis; a suggested fix is code to run, read and explain before you accept it.
  • A reproduction is only a reproduction if it fails the same way, and that is checked by running it.
  • Your checking code can be wrong too; make sure it cannot pass when nothing happened.
