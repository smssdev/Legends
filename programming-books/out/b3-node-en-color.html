Chapter 1

How Servers Work: HTTP in Depth

In this chapter you will learn to

  • follow a request from a URL to a response: name lookup, connection, request, answer
  • read and write HTTP by hand, because it is plain text
  • choose the right method and status code, and know which requests are safe to repeat
  • use the headers that matter: content type and length, caching with ETags, CORS
  • inspect any API with curl, the backend developer’s most used tool
  • build a small JSON API with no framework, so that you know what every framework does for you

Every backend you will ever build, whatever the language or framework, does the same job: it waits for a message, works out what was asked, and sends a message back. The messages follow a protocol called HTTP. Frameworks hide it behind routes and controllers, which is useful until something goes wrong: a request that works in curl but not in the browser, a cache that never updates, a client that retries and charges a customer twice. Then you need to know what is really on the wire. This chapter shows it to you, byte by byte, with a small server we write ourselves.

Bit

The first API I wrote worked perfectly, as long as I was the only one calling it. Then a browser called it from another address, and nothing worked. I lost a day to a problem that two headers solved. Since then I read the raw request first, and guess second.

1.1 From a URL to an answer

When a web app in Bit’s shop asks for http://localhost:3000/products/2, four things happen, in this order:

  1. Name lookup. Computers talk to addresses, not names. The client asks the Domain Name System (DNS) for the address of the host (here localhost, which always means “this same computer”, at 127.0.0.1). For a real site such as shop.example, a DNS server somewhere on the internet answers.
  2. Connection. The client opens a TCP connection to that address and a port, a number that picks one program on the machine. Our server listens on port 3000. TCP makes sure that bytes arrive complete and in order.
  3. Security, for HTTPS. With https://, the two sides first agree on encryption keys (the TLS handshake), and the server proves who it is with a certificate. Everything after that is encrypted. The HTTP inside is the same.
  4. Request and response. The client sends an HTTP request as text; the server sends back a response. The connection may then stay open for the next request.

Everything in this chapter happens on your own computer, so you can see every step without a network in the way. We need a server to talk to. The book’s code folder has one for this chapter, a small API for Bit’s shop, with no framework at all. Start it in a terminal and leave that terminal open:

Terminal 1
# Start the server (and leave it running in this terminal)
$ node server.ts
Listening on http://localhost:3000

Node 22.18 and later run TypeScript files directly: they remove the types and run what is left. We will read the whole server in Section 1.9. First, we look at it from the outside, the way every client does.

1.2 HTTP is text

HTTP/1.1, the version every server understands, is plain text sent over the TCP connection. You can type a request yourself. The nc (netcat) tool opens a TCP connection and passes through whatever you give it; printf writes the request, with \r\n at the end of each line, as the protocol requires. Open a second terminal:

Terminal 2
# Type a request by hand: HTTP/1.1 is plain text over a TCP connection
$ printf 'GET /products/1 HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc localhost 3000
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 41
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: close

{"id":1,"name":"Robot kit","price":45000}

That is all an HTTP exchange is. Both messages have the same shape:

  1. A first line. In the request, the request line: the method (GET), the target (/products/1) and the version. In the response, the status line: the version, a status code (200) and a short reason (OK).
  2. Headers, one per line, Name: value. Names are not case sensitive: content-type and Content-Type are the same header.
  3. An empty line. It says “the headers end here”. Forget it, and the server waits for more headers forever.
  4. The body, if there is one. The receiver knows where it ends from Content-Length: here, 41 bytes.

Our request had two headers. Host is required in HTTP/1.1, because one machine with one address often serves many sites, and the server needs to know which one you mean. Connection: close asks the server to close the connection after answering, so that nc stops; we will come back to connections in Section 1.7.

1.3 Addresses: path and query string

The target of a request has two parts. The path, such as /products, names a resource: a thing the API knows about. The query string, after a ?, holds name=value pairs joined with &, usually to filter, sort or page through a list. Our server understands one, max_price:

Terminal 2

$ curl -s 'localhost:3000/products?max_price=15000'

# Only the headers (HEAD): the same answer without the body
$ curl -sI localhost:3000/products
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 132

Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5

The quotes around the first address matter: without them, the shell would treat ? and & as its own special characters. The second command uses -I, which sends HEAD: the same request as GET, but the server answers with the headers only. A client can learn the size or the version of a big resource without downloading it.

Prices are whole numbers of piastres (45000 is 450.00), never fractions. Floating-point numbers cannot hold most decimal fractions exactly, and money that is off by a fraction of a piastre is still wrong money. This rule follows us through the whole book.

1.4 Methods, and which requests can be repeated

The method says what the client wants to do with the resource. Two of its properties matter more than its name:

  • A method is safe if it only reads: it changes nothing on the server. Anyone can send it, any number of times: browsers prefetch links, search engines crawl them.
  • A method is idempotent if sending it twice has the same effect as sending it once. This matters because networks fail. When a request times out, the client cannot know whether the server received it. It can safely send an idempotent request again; a non-idempotent one might do the work twice.

We build this with a database in Chapter 6.

1.5 Status codes: the first thing a client reads

The status code is a three-digit number, and its first digit is its class:

  • 2xx: it worked.
  • 3xx: look somewhere else, or use what you already have.
  • 4xx: the client made a mistake. Sending the same request again will fail again.
  • 5xx: the server failed. The same request might work later.

That difference between 4xx and 5xx is what clients, retry logic and monitoring tools rely on: a spike of 5xx wakes someone up at night, a spike of 4xx usually means a broken client. So each mistake gets the code that describes it. Here are the ones our server returns, with curl’s -w option printing the status after the body:

1.6 Headers that do real work

Dozens of headers exist; a handful do most of the work in an API.

Content-Type and Content-Length

Content-Type says what the body is: application/json; charset=utf-8 for our answers. The client must send it too: our server answered 415 to -d 'name=Cable', because curl labels such a body application/x-www-form-urlencoded, the format of an HTML form. Content-Length is the size of the body in bytes, not in characters. In UTF-8, an English letter takes one byte, but an Arabic letter takes two, and many emoji take four. A server that counts characters cuts Arabic text short.

Caching: ETag and 304

Most requests ask for something the client has already seen. The server can label each version of a resource with an ETag, a short fingerprint of its content. Our server makes one from a hash of the list. The client sends it back in If-None-Match, and if the list has not changed the server answers 304 Not Modified with no body:

$ curl -si localhost:3000/products

Cache-Control: no-cache
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5

# The next visit sends the ETag back: nothing changed, so 304 and no body
$ curl -si localhost:3000/products -H 'If-None-Match: "c25b00ae213de631"'

Browsers do this by themselves: they store the ETag and send it back on the next visit. Cache-Control: no-cache tells them to always ask first (it does not mean “do not store”; that is no-store). Other values let a client reuse a copy without asking at all, for a time: max-age=60 means one minute, which is right for a product list that may change, and max-age=31536000, immutable means one year, which is right for files whose name changes with their content, such as the bundles from Book 2.

Authorization and cookies

A client proves who it is in one of two ways. Programs and mobile apps usually send a token in Authorization: Bearer <token>. Browsers usually rely on a cookie: the server sends Set-Cookie: session=…; HttpOnly; Secure; SameSite=Lax, and the browser sends Cookie: session=… with every later request to that site. HttpOnly hides the cookie from JavaScript, so an injected script cannot steal it; Secure sends it over HTTPS only; SameSite limits when other sites can make the browser send it. Chapter 8 builds both, properly.

1.7 Connections, and the versions of HTTP

Opening a TCP connection costs a round trip to the server, and the TLS handshake costs one or two more. To a server on another continent, that is a few hundred milliseconds before the first byte of the answer. So HTTP/1.1 keeps connections open by default, and sends the next request on the same one. curl can show whether it was reused:

Terminal 2
# Two requests in one curl command: is the connection reused?
$ curl -sv localhost:3000/products/1 localhost:3000/products/2 -o /dev/null -o /dev/null 2>&1 | grep -E 'Connected|Re-using|left intact|Closing|^< HTTP'
* Connected to localhost (127.0.0.1) port 3000
< HTTP/1.1 200 OK
* Connection #0 to host localhost left intact
* Re-using existing connection with host localhost
< HTTP/1.1 200 OK
* Connection #0 to host localhost left intact

For the second request, curl says Re-using existing connection. Node keeps an idle connection for five seconds (the Keep-Alive: timeout=5 header you saw in every answer), and one Node process can hold thousands of them at once, because it never waits: while one request waits for a file or a database, the same thread works on the others. Chapter 2 looks at this event loop closely.

HTTP/2 and HTTP/3 change how the messages travel, not what they mean. HTTP/2 sends them in a compact binary form and runs many requests at the same time over one connection. HTTP/3 does the same over QUIC, a newer transport that recovers faster from lost packets, which helps on mobile networks. Methods, headers, status codes and bodies are exactly what you have learned. In practice, the web server or load balancer in front of your application speaks HTTP/2 and HTTP/3 to browsers, and plain HTTP/1.1 to your application.

Good to know: HTTPS everywhere

Without TLS, anyone on the path (the café’s Wi-Fi, a provider) can read and change every request, passwords and tokens included. Every public API must use HTTPS, and certificates are free from Let’s Encrypt. You rarely write TLS code yourself: the web server or the hosting platform does it, which is how we set it up in Chapter 16.

1.8 CORS: when a browser calls your API

A browser protects its users with the same-origin policy. An origin is a scheme, a host and a port together: http://localhost:5173, where a Vite app runs, and http://localhost:3000, where our API runs, are different origins. By default, JavaScript on one origin may send a request to another, but may not read the answer. Otherwise any site you visit could read your bank’s pages with your cookies.

CORS (Cross-Origin Resource Sharing) lets a server say which other origins may read its answers. For a request that could change something, such as a POST with a JSON body, the browser first sends a preflight: an OPTIONS request asking whether the real one is allowed. We can play the browser with curl:

Terminal 2
# A browser asks first (a preflight) before a POST from another site
$ curl -si -X OPTIONS localhost:3000/products -H 'Origin: http://localhost:5173' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: content-type'
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://localhost:5173
Vary: Origin
Content-Length: 0
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type
Access-Control-Max-Age: 600
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5
# Another site is not on the list: no Access-Control header, so the browser blocks it
$ curl -si localhost:3000/products/1 -H 'Origin: https://evil.example'
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 41
Date: Thu, 19 Nov 2026 18:42:39 GMT
Connection: keep-alive
Keep-Alive: timeout=5

{"id":1,"name":"Robot kit","price":45000}

For the web app’s origin, the server answers the preflight with what is allowed, and the browser remembers it for ten minutes (Max-Age: 600). For any other origin there is no Access-Control-Allow-Origin header, and the browser refuses to give the answer to the page’s JavaScript. The Vary: Origin header tells caches that the answer depends on the Origin header, so that one site is never served a copy made for another.

Watch out: CORS is not access control

Look again at the second command: the server still answered 200 with the product. CORS is enforced by the browser, to protect the browser’s user. curl, a script or an attacker’s server ignores it completely. Anything that must be private needs authentication and authorisation on the server. And never answer Access-Control-Allow-Origin: * together with cookies: list the origins you trust, as our server does.

1.9 Inside the server

Now that you know what goes over the wire, the server holds no surprises. We read it in five parts, from the top of the file.

The data and the settings. The products live in an array, with prices in piastres. ORIGINS lists the only web app allowed to read our answers from a browser (1.8), and MAX_BODY is the largest body we accept:

server.ts (1 of 5)

import { createHash } from "node:crypto";

type Product = { id: number; name: string; price: number };

const products: Product[] = [
  { id: 1, name: "Robot kit", price: 45000 },
  { id: 2, name: "Spare wheels", price: 6000 },

One place sends answers. Every response in the file goes through send, which sets the type and the length, counted in bytes with Buffer.byteLength. An empty body gets no type at all. fail gives every error the same shape. Because of these two functions, no route can forget a header or invent its own error format:

server.ts (2 of 5)
function send(res: ServerResponse, status: number, body?: unknown,
              headers: Headers = {}) {
  const text = body === undefined ? "" : JSON.stringify(body);
  res.writeHead(status, {
    ...(text && { "Content-Type": "application/json; charset=utf-8" }),
    "Content-Length": String(Buffer.byteLength(text)), // bytes, not characters
    ...headers,
  });
  res.end(text);
}

function fail(res: ServerResponse, status: number, code: string,
              message: string, extra = {}, headers: Headers = {}) {
  send(res, status, { error: { code, message, ...extra } }, headers);
}

Routing. handle looks at the method and the path and decides what to do: the CORS headers first, for any request, then the preflight, then the list, then one product. Everything else is a 404. Notice that the 405 answer names the allowed methods, and that a HEAD is answered like a GET: Node itself drops the body of an answer to HEAD.

server.ts (3 of 5)
async function handle(req: IncomingMessage, res: ServerResponse) {
  const url = new URL(req.url ?? "/", "http://localhost");
  const origin = req.headers.origin;
  if (origin && ORIGINS.includes(origin)) {
    res.setHeader("Access-Control-Allow-Origin", origin);
    res.setHeader("Vary", "Origin");
  }

  if (req.method === "OPTIONS") {
    return send(res, 204, undefined, {
      "Access-Control-Allow-Methods": "GET, POST",
      "Access-Control-Allow-Headers": "Content-Type",
      "Access-Control-Max-Age": "600",
    });
  }

  if (url.pathname === "/products") {
    if (req.method === "GET" || req.method === "HEAD") {
      const max = Number(url.searchParams.get("max_price") ?? Infinity);
      const list = products.filter((p) => p.price <= max);
      const hash = createHash("md5").update(JSON.stringify(list)).digest("hex");
      const etag = `"${hash.slice(0, 16)}"`;
      if (req.headers["if-none-match"] === etag) {
        return send(res, 304, undefined, { ETag: etag });
      }
      return send(res, 200, list, { ETag: etag, "Cache-Control": "no-cache" });
    }
    if (req.method === "POST") return create(req, res);
    return fail(res, 405, "method_not_allowed", "Use GET or POST here", {},
                { Allow: "GET, HEAD, POST" });
  }

  const one = url.pathname.match(/^\/products\/(\d+)$/);
  if (one && req.method === "GET") {
    const product = products.find((p) => p.id === Number(one[1]));
    if (!product) return fail(res, 404, "not_found", "No product with this id");
    return send(res, 200, product);
  }
  return fail(res, 404, "not_found", "Nothing here");
}

Distrust the body. Creating a product checks everything a client could get wrong, in order: the type before reading, the size while reading (readBody stops at 1 KB, so a huge body never reaches memory), the JSON in a try, and then each field for its type and range, collecting every error before answering. Real APIs allow more than 1 KB, but they always have a limit; without one, a single client can fill the server’s memory.

server.ts (4 of 5)
async function readBody(req: IncomingMessage): Promise<string> {
  let size = 0;
  const parts: Buffer[] = [];
  for await (const chunk of req) {
    size += chunk.length;
    if (size > MAX_BODY) throw new Error("too_large");
    parts.push(chunk);
  }
  return Buffer.concat(parts).toString("utf8");
}

async function create(req: IncomingMessage, res: ServerResponse) {
  if (!req.headers["content-type"]?.startsWith("application/json")) {
    return fail(res, 415, "unsupported_media_type", "Send JSON");
  }
  let data: { name?: unknown; price?: unknown };
  try {
    data = JSON.parse(await readBody(req));
  } catch (e) {
    if (e instanceof Error && e.message === "too_large") {
      return fail(res, 413, "too_large", "At most 1 KB");
    }
    return fail(res, 400, "bad_json", "The body is not valid JSON");
  }

  const { name, price } = data;
  const errors: Record<string, string> = {};
  if (typeof name !== "string" || !name.trim()) errors.name = "Required";
  if (typeof price !== "number" || !Number.isInteger(price) || price <= 0) {
    errors.price = "A whole number of piastres above 0";
  }
  if (Object.keys(errors).length) {
    return fail(res, 422, "invalid", "Check the fields", { fields: errors });
  }

  const product = {
    id: products.length + 1,
    name: (name as string).trim(),
    price: price as number,
  };
  products.push(product);
  send(res, 201, product, { Location: `/products/${product.id}` });
}

The server itself. createServer calls our function for every request. When the response is finished, one line goes to the log with the method, the address, the status and the time it took. Any unexpected error is caught here, once: the real error goes to the log, and the client gets a plain 500 without stack traces or file paths that would help an attacker. requestTimeout cuts off a client that sends too slowly, so a few slow clients cannot hold every connection:

When an API “does not work”, do not change code at random. Summary

  • A request goes through a name lookup, a TCP connection, TLS for HTTPS, and then the HTTP request and response.
  • HTTP/1.1 is text: a first line, headers, an empty line, and a body whose size is in Content-Length, in bytes.
  • The path names a resource; the query string filters and pages.
  • Safe methods only read; idempotent ones can be repeated. POST is neither, so retries need idempotency keys.
  • 2xx worked, 3xx look elsewhere, 4xx the client’s mistake, 5xx the server’s. Errors have one shape, with a stable code and a readable message.
  • ETag and If-None-Match turn repeated reads into empty 304 answers; Cache-Control says how long a copy may be reused.
  • Connections are kept alive and reused; HTTP/2 and HTTP/3 change the transport, not the meaning.
  • CORS lets a browser page read answers from another origin. It protects browser users; it does not protect your server.
  • Every server, with or without a framework, needs: one way to answer, distrust of input, limits, caught errors and a log line per request.

Quick check answers: 1. At the first empty line; the body is exactly Content-Length bytes long. 2. Yes for DELETE: it is idempotent, so a second one leaves the same state (even though its answer may be 404). No for POST /orders: it might create a second order, unless the API supports an idempotency key. 3. 422: the request was well-formed JSON that the server could read; its content failed validation.

Bit

My first Node server resized photos inside the request handler. It worked beautifully on my laptop. The day ten people uploaded at once, every page of the site stopped answering, including the ones that had nothing to do with photos. That was how I met the event loop.

2.1 What Node is

Node is three things put together. V8, the JavaScript engine from Chrome, runs your code. libuv, a library written in C, talks to the operating system: it opens files and network connections, and tells Node when something is ready. And a standard library (node:http, node:fs, node:stream, node:test and many more) wraps it all for JavaScript.

The important design choice is that your JavaScript runs on one thread, and I/O (input and output: the network, the disk, a database) never makes it wait. When a request handler asks the database for a list, Node hands the work to the operating system and moves on to the next request. When the list arrives, Node calls your code back. One process can serve thousands of connections at once this way, because most of a server’s time is spent waiting for I/O, and waiting costs Node nothing.

The cost of the design is just as important: while your JavaScript is computing, nothing else runs. We will see both sides for real in this chapter.

2.3 The event loop

The event loop is Node’s main loop. In each turn, it runs whatever is ready: timers whose time has come, I/O that has finished, callbacks scheduled with setImmediate. Between any two of these, it empties two smaller queues of microtasks: callbacks of promises, and callbacks given to process.nextTick. This program schedules one of each, and then keeps the thread busy:

demos/event-loop.ts
import { readFile } from "node:fs/promises";

console.log("script starts");
setTimeout(() => console.log("timer (0 ms)"), 0);
Promise.resolve().then(() => console.log("promise callback"));
process.nextTick(() => console.log("process.nextTick"));
console.log("script ends");

// wait for some I/O, then a second experiment
await readFile(import.meta.filename);
const asked = performance.now();
setTimeout(() => {
  const late = Math.round(performance.now() - asked);
  console.log(`timer asked for 10 ms, ran after ${late} ms`);
}, 10);
const until = performance.now() + 200;
while (performance.now() < until); // busy for 200 ms
Terminal
# The order things run in
$ node demos/event-loop.ts
script starts
script ends
promise callback
process.nextTick
timer (0 ms)
timer asked for 10 ms, ran after 200 ms

Three rules explain the output:

  1. The code that is running always finishes first. Nothing interrupts it: “script ends” comes before every callback.
  2. Microtasks run before the loop moves on. Both the promise callback and the nextTick callback run before the timer, even though the timer asked for 0 ms. (In an ES module, promise callbacks happen to run before nextTick ones; in an old CommonJS file it is the other way round. Code that depends on that order is fragile.)
  3. A timer’s delay is a minimum, not a promise. The second timer asked for 10 ms and ran after 200, because the loop was busy and could not check its timers.

The third rule is the one that matters on a server. Every request, every timer and every database answer waits for the same thread. If one piece of code keeps it for a second, every user waits a second.

2.4 Never block the loop

Here is a server with two routes. /primes counts the prime numbers up to a limit, which is pure computation; /hello answers at once:

demos/blocking.ts
import { createServer } from "node:http";
import { countPrimes } from "../src/primes.ts";

createServer((req, res) => {
  const url = new URL(req.url ?? "/", "http://localhost");
  if (url.pathname === "/primes") {
    const primes = countPrimes(Number(url.searchParams.get("limit"))); // blocks!
    return res.end(JSON.stringify({ primes }));
  }
  res.end(JSON.stringify({ message: "hello" }));
}).listen(3001);

We send a slow request and, a moment later, a quick one. curl’s -w prints how long each one took:

Terminal
# One slow request (a CPU count) and one quick one, sent at the same moment
$ curl -s 'localhost:3001/primes?limit=5000000' -w ' %{time_total}s\n' & sleep 0.05; curl -s localhost:3001/hello -w ' %{time_total}s\n'; wait
{"primes":348513} 1.394915s
{"message":"hello"} 1.343057s

The quick request, which needs a fraction of a millisecond, waited more than a second, because the thread was counting primes for someone else. With a hundred users, each would wait behind every count in front of them. Typical culprits are image resizing, PDF generation, password hashing with a synchronous function, compressing big files, and JSON.parse on huge bodies.

The fix is to do heavy computation on another thread. Node’s worker threads run a separate JavaScript file with its own event loop, and exchange messages with the main thread:

src/primes-worker.ts
// Runs in its own thread, so a long count never blocks the event loop.
import { parentPort, workerData } from "node:worker_threads";
import { countPrimes } from "./primes.ts";

parentPort?.postMessage(countPrimes(workerData as number));

The worker receives its input in workerData and posts its result back. In the app, a small function wraps it in a promise, so the handler simply awaits it:

src/app.ts
function countInWorker(limit: number): Promise<number> {
  return new Promise((resolve, reject) => {
    const worker = new Worker(new URL("./primes-worker.ts", import.meta.url), {
      workerData: limit,
    });
    worker.once("message", resolve);
    worker.once("error", reject);
  });
}

The same two requests against the real server:

Terminal
# The same two requests, with the count in a worker thread
$ curl -s 'localhost:3000/primes?limit=5000000' -w ' %{time_total}s\n' & sleep 0.05; curl -s localhost:3000/hello -w ' %{time_total}s\n'; wait
{"message":"Hello from Bit's shop"} 0.001101s
{"limit":5000000,"primes":348513,"ms":1347} 1.348983s

The quick request now answers in about a millisecond, before the count has finished, because the main thread was free. Starting a thread costs a few tens of milliseconds, which is nothing next to a one-second job but too much for many small ones. For those, keep a pool of threads started once and reused; you build one in Exercise 5, and the Piscina library is a well-tested one.

Tip: most libraries already do this

Many slow operations in Node’s standard library have an asynchronous version that runs on libuv’s own thread pool: crypto.scrypt instead of crypto.scryptSync, zlib.gzip instead of zlib.gzipSync, fs.promises.readFile instead of fs.readFileSync. On a server, any function whose name ends in Sync is a warning sign inside a request handler. At start-up, before the server listens, it is fine.

2.5 Waiting for several things at once

A product page might need the stock, the price and the reviews, each from a different service. This demo stands in for three network calls, of 300, 200 and 400 ms:

demos/concurrency.ts
import { setTimeout as sleep } from "node:timers/promises";

// Three slow services, as a real API would call over the network.
const stock = (signal?: AbortSignal) => sleep(300, 7, { signal });
const price = (signal?: AbortSignal) => sleep(200, 45000, { signal });
const reviews = (signal?: AbortSignal) => sleep(400, 4.5, { signal });

async function timed(label: string, work: () => Promise<unknown>) {
  const start = performance.now();
  const result = await work();
  console.log(`${label}: ${Math.round(performance.now() - start)} ms`, result);
}

await timed("one after another", async () => {
  return [await stock(), await price(), await reviews()];
});

await timed("all at once", () => Promise.all([stock(), price(), reviews()]));

const down = () => Promise.reject(new Error("the reviews service is down"));
await timed("one fails, the others still count", async () => {
  const results = await Promise.allSettled([stock(), price(), down()]);
  return results.map((r) => (r.status === "fulfilled" ? r.value : "failed"));
});

await timed("with a time limit of 250 ms", async () => {
  const limit = AbortSignal.timeout(250);
  const results = await Promise.allSettled([stock(), price(), reviews(limit)]);
  return results.map((r) =>
    r.status === "fulfilled" ? r.value : "skipped (too slow)",
  );
});
Terminal
# Waiting for three services
$ node demos/concurrency.ts
one after another: 903 ms [ 7, 45000, 4.5 ]
all at once: 401 ms [ 7, 45000, 4.5 ]
one fails, the others still count: 301 ms [ 7, 45000, 'failed' ]
with a time limit of 250 ms: 301 ms [ 7, 45000, 'skipped (too slow)' ]
  • One after another, the waits add up: 300 + 200 + 400 = 900 ms. Writing await three times in a row is the most common accidental slowness in Node code.
  • Promise.all starts all three, then waits for the slowest: 400 ms. Use it when the calls do not depend on each other.
  • Promise.allSettled waits for all of them and reports each one as fulfilled or rejected. A page can still show the stock and the price when the reviews service is down. Promise.all would reject as a whole on the first failure.
  • AbortSignal.timeout(250) gives a call a time limit. Most modern APIs accept a signal, including fetch and Node’s timers, and give up when it fires. Every call to another service needs a limit; without one, a slow service makes your server slow too.

Watch out: “all at once” has limits

Promise.all over ten thousand items starts ten thousand database queries at the same moment, and the database falls over. For large lists, run a few at a time (in batches, or with a small helper such as p-limit). And remember that a rejected Promise.all does not stop the other promises: they keep running, and their results are simply ignored.

2.6 Streams: big data in small memory

Suppose Bit’s shop must add up a million orders from a CSV file. The direct way reads the whole file into memory first:

demos/total-read.ts
import { readFile } from "node:fs/promises";

const text = await readFile("orders.csv", "utf8"); // the whole file in memory
let total = 0;
for (const line of text.split("\n").slice(1)) {
  if (line) total += Number(line.split(",")[2]);
}
const peak = Math.round(process.resourceUsage().maxRSS / 1024);
console.log(`total: ${total}, peak memory: ${peak} MB`);

A stream delivers the data in pieces as it arrives, so the program only ever holds a small part of it. readline turns a file stream into lines, and for await reads them one by one:

demos/total-stream.ts
import { createReadStream } from "node:fs";
import { createInterface } from "node:readline";

const lines = createInterface({ input: createReadStream("orders.csv") });
let total = 0;
let first = true;
for await (const line of lines) {
  if (first) {
    first = false; // the header
    continue;
  }
  total += Number(line.split(",")[2]);
}
const peak = Math.round(process.resourceUsage().maxRSS / 1024);
console.log(`total: ${total}, peak memory: ${peak} MB`);

More importantly, the streaming version uses the same memory for a file ten times bigger, while the first one would need ten times more and eventually crash. On a server that handles many requests at once, the difference is multiplied by the number of users.

Backpressure

Streams also work the other way. When you write faster than the destination can take (a slow disk, a slow client), data piles up in memory. A writable stream says so: write() returns false when its buffer is full. The program that made the CSV file waits for the drain event before writing more:

demos/make-orders.ts
import { createWriteStream } from "node:fs";
import { once } from "node:events";

const file = createWriteStream("orders.csv");
file.write("id,customer,total\n");
for (let id = 1; id <= 1_000_000; id++) {
  const line = `${id},customer-${id % 97},${(id * 7919) % 100000}\n`;
  // write() returns false when the buffer is full: wait until it drains
  if (!file.write(line)) await once(file, "drain");
}
file.end();
await once(file, "finish");
console.log("1000000 orders written to orders.csv");

This is called backpressure: the slow side slows down the fast side, instead of letting memory fill up. You rarely handle it by hand, because pipeline does it for you. The shop’s export route makes its CSV rows with an async generator and pipes them into the response:

src/app.ts
async function* orderRows(count: number) {
  yield "id,customer,total\n";
  for (let id = 1; id <= count; id++) {
    yield `${id},customer-${id % 97},${(id * 7919) % 100000}\n`;
  }
}

In the handler, await pipeline(Readable.from(orderRows(100_000)), res) sends the rows as the client reads them. 2.7 Configuration

The port, the database address, the allowed origins and the API keys differ between your laptop, the test server and production. They must not be written in the code. The common rule is to read them from environment variables, which every hosting platform can set. But process.env holds only strings, any of which may be missing or mistyped. So the project reads them in one place, once, and checks them with zod:

src/config.ts
import { z } from "zod";

// process.env holds strings only: coerce and check them once, at start-up
const Env = z.object({
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  ALLOWED_ORIGINS: z
    .string()
    .transform((list) => list.split(",").map((origin) => origin.trim()))
    .pipe(z.array(z.url())),
});

const parsed = Env.safeParse(process.env);
if (!parsed.success) {
  console.error("Invalid configuration:\n" + z.prettifyError(parsed.error));
  process.exit(1);
}

// read-only: nothing can change the configuration later
export const config = Object.freeze(parsed.data);
export type Config = typeof config;

2.8 Errors and graceful shutdown

Servers stop all the time: for every deployment, when a machine is replaced, when the platform scales down. The platform sends the process a SIGTERM signal (Ctrl+C in a terminal sends SIGINT) and, after a grace period, kills it. A server that simply exits on the signal cuts off every request in progress: a payment half processed, an upload lost. A graceful shutdown stops accepting new connections, lets the running requests finish, and only then exits:

src/server.ts
import { config } from "./config.ts";
import { createApp } from "./app.ts";
import { log } from "./log.ts";

const server = createApp();
server.requestTimeout = 30_000;
server.listen(config.PORT, () => {
  log("info", `Listening on http://localhost:${config.PORT}`);
});

function shutdown(signal: string): void {
  log("info", `${signal}: no new connections, finishing requests in progress`);
  server.close(() => {
    // stop accepting, let running requests finish
    log("info", "all requests finished, bye");
    process.exit(0);
  });
  // close kept-alive connections that are doing nothing
  server.closeIdleConnections();
  setTimeout(() => {
    log("error", "requests still running after 10 s, stopping anyway");
    process.exit(1);
  }, 10_000).unref(); // never hang forever
}
process.once("SIGTERM", () => shutdown("SIGTERM"));
process.once("SIGINT", () => shutdown("SIGINT"));

// the process is in an unknown state: log and stop; the supervisor restarts it
process.on("unhandledRejection", (error) => {
  log("error", `unexpected error, stopping: ${String(error)}`);
  process.exit(1);
});

The last handler is about a different kind of error. Errors you expect, such as a missing product or a timeout, are handled where they happen and become answers. An unhandled rejection means a promise failed and no code was waiting for the failure: a bug. After a bug, the process may be in a state nobody planned for, with half-updated data in memory. The safe reaction is to log it and exit, and let a supervisor (Docker, systemd or the hosting platform, Chapter 16) start a fresh process. Never keep a damaged process running just to look available.

Summary

  • Node is V8, libuv and a standard library. Your JavaScript runs on one thread; I/O never makes it wait.
  • Node runs TypeScript by stripping types; tsc checks them. erasableSyntaxOnly keeps the source strippable: no enums.
  • The event loop runs current code to the end, then microtasks, then timers and I/O. Timer delays are minimums.
  • Never block the loop: CPU work goes to worker threads, slow APIs are used in their async versions.
  • Promise.all waits for independent calls at once, allSettled survives failures, and AbortSignal.timeout limits every call.
  • Streams process big data in constant memory; backpressure slows the fast side; pipeline handles both and cleans up.
  • Configuration comes from the environment, checked once with a schema; secrets never enter the repository.
  • A graceful shutdown closes, finishes, then exits. After an unhandled error, log and exit, and let a supervisor restart.
  • node:test runs tests with no extra tool; servers in tests listen on port 0.

3.1 Resources and URLs

REST organises an API around resources: the nouns of your domain, such as products and orders. URLs name the resources; methods say what to do with them. The rules that make an API guessable are few:

  • Nouns, plural, lower case: /products, /orders. The method is the verb: GET /products, not /getProducts.
  • One resource: the collection plus an id, /products/2.
  • Nesting for ownership, one level deep: /orders/7/items is fine; /customers/3/orders/7/items/2 is not. Once a resource has its own id, give it its own top-level URL.
  • Actions that are not create, read, update or delete become a sub-resource with POST: POST /orders/7/cancel. Do not hide them in a PATCH that sets status: cancelling has rules (restore the stock, refund the payment) that a generic update would skip.
  • A version in the path: /v1/.... We come back to versions in 3.8.

Representations

The JSON an API sends is called a representation of the resource. Choose its conventions once, write them down, and never mix them:

  • One naming style. We use snake_case, like most public APIs; camelCase is just as good. Mixing them is not.
  • Times in ISO 8601, in UTC: 2026-11-01T09:00:00.000Z. Clients convert to the user’s time zone; the server never guesses it.
  • Money as an object: {"amount": 45000, "currency": "EGP"}, the amount in minor units. A bare number is ambiguous the day you sell in a second currency.
  • Lists in an object: {"data": [...], "next_cursor": ...}, never a bare array, so that page information can be added without breaking anyone.

3.3 Lists: filtering, sorting, pages

A list endpoint needs three things: a way to filter, a way to sort, and pages, because no client wants ten thousand products at once. Everything a client may send is in the query schema:

  id: "id",
  price: "price",
  "-price": "price",
  name: "name",

const ListQuery = z.object({

Offset pages and cursor pages

The obvious way to page is an offset: ?page=2 means “skip the first 20”. It has two problems. A database must still walk past every skipped row, so page 5000 is slow. Worse, the pages drift when data changes between two requests. This small demo pages through a “newest first” list, three at a time, while a new product arrives between page 1 and page 2:

A cursor says “continue after this row”, so new rows before it change nothing. This is also called keyset pagination, because it continues from the key of the last row. Our API builds its cursors like this:

src/routes/products.ts
function compare(row: Product, [value, id]: Position, sort: Sort): number {
  const own = row[SORTS[sort]];
  const diff = own < value ? -1 : own > value ? 1 : row.id - id;
  return sort === "-price" ? -diff : diff;
}

// opaque to clients: base64url, so nobody builds cursors by hand
const encode = (position: Position) =>
  Buffer.from(JSON.stringify(position)).toString("base64url");

function decode(cursor: string): Position {
  try {
    const position = JSON.parse(Buffer.from(cursor, "base64url").toString());
    if (Array.isArray(position) && position.length === 2)
      return position as Position;
  } catch {}
  const error = { field: "querystring.cursor", message: "invalid cursor" };
  throw problems.invalidRequest([error]);
}

The rows are ordered by the sort field and then by id, so that two products with the same price still have a fixed order: without that tiebreak, rows with equal values could move between pages. The cursor holds the last row’s sort value and id, encoded with base64url. Encoding is not secrecy, and the cursor can be decoded; the point is that clients treat it as an opaque token and send it back unchanged, so the server is free to change what is inside. 3.4 Errors: Problem Details

In Chapter 1 our errors had a shape we invented. Every API that invents its own shape forces every client to learn it. Problem Details (RFC 9457) is the standard shape for HTTP API errors, sent with the content type application/problem+json: a type URL that identifies the kind of problem and leads to its documentation, a short title, the status, a detail for this particular case, and the instance, the request that failed. Extra members are allowed, such as our errors list.

Every text a person reads lives in one file, so it can be reviewed and translated in one place:

One error handler turns everything into a problem: our own problems as they are, validation errors as 422 for a body and 400 for the rest of the request, the rate limiter’s errors as 429, and anything unexpected as a plain 500, with the details in the log:

src/app.ts
  app.setErrorHandler((error: FastifyError, request, reply) => {
    let problem: Problem;
    if (error instanceof Problem) {
      problem = error;
    } else if (hasZodFastifySchemaValidationErrors(error)) {
      const where = error.validationContext ?? "body";
      const errors = error.validation.map((issue) => ({
        field: [
          where,
          ...String(issue.instancePath).split("/").filter(Boolean),
        ].join("."),
        message: issue.message ?? "",
      }));
      // 422: a well-formed body with wrong values
      // 400: a bad query, path or header: the request itself is malformed
      problem =
        where === "body"
          ? problems.invalidBody(errors)
          : problems.invalidRequest(errors);
    } else if (error.statusCode === 429) {
      problem = problems.tooManyRequests(
        Number(reply.getHeader("retry-after") ?? 60),
      );
    } else {
      request.log.error(error); // the details stay in the log
      problem = problems.server();
    }
    reply.code(problem.status).type("application/problem+json");
    return reply.send(problem.body(request.url));
  });

3.5 Safe retries: idempotency keys

Chapter 1 warned that a retried POST can create an order twice. The standard answer, used by payment providers such as Stripe, is an idempotency key: the client creates a unique value (a UUID) for each intended operation and sends it in an Idempotency-Key header. If the same key arrives again, the server does not do the work again; it replays the answer it gave the first time.

src/routes/orders.ts
    app.post(
      "/orders",
      {
        schema: {
          headers: z.object({ "idempotency-key": z.string().min(8).max(100) }),
          body: NewOrder,
          response: { 201: OrderOut },
        },
      },
      async (request, reply) => {
        const key = request.headers["idempotency-key"];
        const body = JSON.stringify(request.body);
        const fingerprint = createHash("sha256").update(body).digest("hex");
        const saved = keys.get(key);
        if (saved) {
          if (saved.fingerprint !== fingerprint) throw problems.keyReused();
          if (!saved.order) throw problems.inProgress();
          reply.header("Idempotent-Replayed", "true");
          reply.header("Location", `/v1/orders/${saved.order.id}`);
          return reply.code(201).send(saved.order);
        }
        // mark the key as in progress before doing the work
        keys.set(key, { fingerprint });

        try {
          const items = request.body.items.map(({ product_id, quantity }) => {
            const product = store.products.find((p) => p.id === product_id);
            if (!product) throw problems.unknownProduct(product_id);
            if (product.stock < quantity) {
              throw problems.outOfStock(product.id, product.stock);
            }
            return { product, quantity };
          });
          for (const { product, quantity } of items) {
            product.stock -= quantity;
            product.version += 1;
          }
          const order: Order = {
            id: store.nextOrderId++,
            status: "pending",
            // the price comes from the server, never from the client
            items: items.map(({ product, quantity }) => ({
              product_id: product.id,
              quantity,
              price: product.price,
            })),
            total: items.reduce(
              (sum, { product, quantity }) => sum + product.price * quantity,
              0,
            ),
            created_at: new Date().toISOString(),
          };
          store.orders.push(order);
          keys.set(key, { fingerprint, order: show(order) });
          reply.header("Location", `/v1/orders/${order.id}`);
          return reply.code(201).send(show(order));
        } catch (error) {
          keys.delete(key); // a failed attempt may be tried again with the same key
          throw error;
        }
      },
    );

The details matter more than the idea:

  • The server keeps a fingerprint of the body. The same key with a different body is a bug in the client, and gets a 422, never a silent replay of a different order.
  • The key is marked in progress before the work starts. A second request that arrives while the first is still running gets a 409 instead of starting the work twice.
  • If the work fails, the key is forgotten, so the client may try again with it.
  • The total is computed from the server’s prices. A client never tells the server what something costs.

3.6 Lost updates: ETag and If-Match

Two administrators open product 2 at the same time. Sara changes the price to 65.00 and saves; a minute later Omar, whose screen still shows the old product, changes it to 70.00 and saves. Sara’s change is gone, and nobody was told. This is the lost update problem. HTTP solves it with the ETag you met in Chapter 1: the product’s version is its ETag, and a change must send back the version it was based on in If-Match:

src/routes/products.ts
    app.patch(
      "/products/:id",
      {
        schema: {
          params: IdParams,
          body: ProductPatch,
          response: { 200: ProductOut },
        },
      },
      async (request, reply) => {
        const product = find(request.params.id);
        const ifMatch = request.headers["if-match"];
        if (!ifMatch) throw problems.needIfMatch();
        if (ifMatch !== `"${product.version}"`) throw problems.stale();
        Object.assign(product, request.body, { version: product.version + 1 });
        reply.header("ETag", `"${product.version}"`);
        return show(product);
      },
    );

A change without If-Match is refused with 428 Precondition Required: requiring it is how the API makes sure no client forgets. The change based on version 1 succeeds and creates version 2. The second change, still based on version 1, gets 412 Precondition Failed, and the client knows to reload and show the user what changed. This is optimistic concurrency: nothing is locked while people look at a screen, and conflicts, which are rare, are detected when they happen. Chapter 6 does the same inside the database.

3.8 Versions and change

Once other people use your API, every change is either additive or breaking. Adding an endpoint, an optional parameter or a new field to a response is additive: correct clients ignore what they do not know. Removing or renaming a field, changing its type or meaning, or adding a required parameter breaks clients. The rules:

  • Make every change additive if you possibly can. Most APIs live for years on version 1.
  • When a breaking change is unavoidable, publish /v2 next to /v1, and keep /v1 running for a stated period.
  • Announce the end in the answers themselves, with the Deprecation and Sunset headers, in the documentation, and by email to the clients you know. Watch your logs to see who still calls the old version before you turn it off.

3.9 Documentation from the code

Documentation written by hand drifts away from the code within weeks. Because every route here has a schema, the @fastify/swagger plugin generates an OpenAPI document from them: a standard, machine-readable description of every path, parameter, body and response. The API serves it at /openapi.json, and the routes listing in 3.1 was read from it. From the same document, tools can render documentation pages, generate typed client libraries in many languages, and check in CI that a change does not remove anything clients depend on.

Professional habit: design the API before you build it

Write the request and response examples for a new endpoint first, in the pull request or in the OpenAPI document, and get a review from someone who will use the endpoint, such as a front-end or mobile developer. Changing an example takes minutes; changing a published API takes months of versions and deprecation emails.

4.1 Tables, types and rules

A relational database stores data in tables. Each table has fixed columns, each with a type, and any number of rows. Tables refer to each other through ids. Here is the shop:

schema.sql
CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- the database numbers the rows itself; nobody sends an id
  name       text NOT NULL,
  email      text NOT NULL UNIQUE,
  city       text,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  price integer NOT NULL CHECK (price > 0), -- piastres: whole numbers, never fractions
  stock integer NOT NULL DEFAULT 0 CHECK (stock >= 0) -- the database refuses negative stock, whatever the application does
);

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers (id),
  status      text NOT NULL DEFAULT 'pending'
              CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')), -- only these four values can ever be stored
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_id   bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
  product_id bigint NOT NULL REFERENCES products (id),
  quantity   integer NOT NULL CHECK (quantity BETWEEN 1 AND 99),
  price      integer NOT NULL, -- the price when the order was made: prices change, orders must not
  PRIMARY KEY (order_id, product_id) -- a product appears once per order
);

Read it slowly, because every word is a decision:

  • Types. bigint for ids, because integer stops at about two billion. text for strings, with no arbitrary length limit (PostgreSQL stores text and varchar the same way). integer for money in piastres. timestamptz for moments in time: it stores an exact instant, in UTC, and never confuses time zones. Never use timestamp without a time zone for events.
  • GENERATED ALWAYS AS IDENTITY numbers rows automatically. It is the standard way; the older serial works too.
  • PRIMARY KEY identifies each row: unique, never null, and indexed.
  • NOT NULL, UNIQUE and CHECK are rules the database enforces on every write.
  • REFERENCES is a foreign key: an order cannot point to a customer who does not exist. ON DELETE CASCADE deletes an order’s items with the order.
  • order_items has a composite primary key: one row per product per order. It also copies the price, because product prices change and an order must not.

4.3 Joins: combining tables

A join puts together rows from several tables that belong together. To list each named customer’s orders with their totals, the query joins customers to their orders and orders to their items, then groups the items of each order:

psql
# Join the tables: each named customer's orders with their totals
shop=# SELECT c.name, o.id, o.status, sum(i.quantity * i.price) AS total
shop-# FROM customers c
shop-# JOIN orders o ON o.customer_id = c.id
shop-# JOIN order_items i ON i.order_id = o.id
shop-# WHERE c.id <= 7
shop-# GROUP BY c.name, o.id, o.status
shop-# ORDER BY o.id;

shop=# SELECT c.name, count(o.id) AS orders

shop-# LEFT JOIN orders o ON o.customer_id = c.id

4.4 Grouping and summarising

GROUP BY makes one result row per group, and aggregates summarise each group. HAVING filters the groups, as WHERE filters rows:

psql
# The products that bring in the most money
shop=# SELECT p.name, sum(i.quantity) AS units, sum(i.quantity * i.price) / 100 AS revenue
shop-# FROM order_items i
shop-# JOIN orders o ON o.id = i.order_id
shop-# JOIN products p ON p.id = i.product_id
shop-# WHERE o.status <> 'cancelled'
shop-# GROUP BY p.name
shop-# HAVING sum(i.quantity) > 26600
shop-# ORDER BY revenue DESC;
      name      | units | revenue 
----------------+-------+---------
 Battery pack   | 26878 | 3359750
 Gear box       | 26694 | 2936340
 Remote control | 26673 | 2133840
 Speaker        | 26676 | 2000700
 LED strip      | 27350 | 1094000
 USB cable      | 26699 |  667475
(6 rows)

Read the order in which the database works, which is not the order in which the query is written: FROM and the joins first, then WHERE (cancelled orders go), then GROUP BY, then HAVING (products that sold 26,600 units or fewer go), then SELECT, then ORDER BY. That is why WHERE cannot use sum(...): when it runs, there are no groups yet.

Money is still in piastres in the sums, and divided by 100 only at the end, for display. Integer division would be wrong for an amount like 12,550 piastres; here every revenue happens to be whole pounds. In an API, send piastres and let the client format them.

4.5 CTEs and window functions

Some questions need a result to build on. “Rank the named customers by what they spent, and show each one’s share” needs the totals first, then a ranking over them:

psql
# A CTE and a window function: rank the named customers by what they spent
shop=# WITH spent AS (
shop-#   SELECT o.customer_id, sum(i.quantity * i.price) AS total
shop-#   FROM orders o
shop-#   JOIN order_items i ON i.order_id = o.id
shop-#   WHERE o.status <> 'cancelled'
shop-#   GROUP BY o.customer_id
shop-# )
shop-# SELECT c.name, s.total,
shop-#        rank() OVER (ORDER BY s.total DESC) AS place,
shop-#        round(s.total * 100.0 / sum(s.total) OVER (), 1) AS percent
shop-# FROM spent s
shop-# JOIN customers c ON c.id = s.customer_id
shop-# WHERE c.id <= 7
shop-# ORDER BY place;
  name   | total | place | percent 
---------+-------+-------+---------
 Youssef | 97500 |     1 |    41.6
 Sara    | 74000 |     2 |    31.6
 Omar    | 42000 |     3 |    17.9
 Mona    | 21000 |     4 |     9.0
(4 rows)
  • WITH spent AS (…) is a common table expression (CTE): a named query used by the next one. It reads like a variable, and keeps long queries understandable.
  • rank() OVER (ORDER BY …) is a window function: it computes over a set of rows without collapsing them, unlike GROUP BY. Each customer keeps their row and gets a rank.
  • sum(s.total) OVER () is an aggregate used as a window over all rows: the grand total, next to every row, so each row can compute its share.

Window functions answer the questions reports always ask: rankings, running totals, the previous month for comparison (lag), the top three per category. Without them, you would write loops in code over thousands of rows.

4.6 Writing: INSERT, UPDATE, DELETE

Writes can answer too. RETURNING gives back columns of the rows that were written, so the application gets the new id and the defaults without a second query. ON CONFLICT turns an insert that would break a unique rule into an update, an upsert:

psql
# Writes that answer: RETURNING, and an upsert with ON CONFLICT
shop=# INSERT INTO customers (name, email, city)
shop-# VALUES ('Nour', 'nour@example.com', 'Giza')
shop-# RETURNING id, created_at;
  id  |          created_at           
------+-------------------------------
 2009 | 2026-11-19 20:42:29.499252+00
(1 row)

INSERT 0 1
shop=# INSERT INTO customers (name, email, city)
shop-# VALUES ('Nour', 'nour@example.com', 'Aswan')
shop-# ON CONFLICT (email) DO UPDATE SET city = excluded.city
shop-# RETURNING id, name, city;
  id  | name | city  
------+------+-------
 2009 | Nour | Aswan
(1 row)

INSERT 0 1
shop=# UPDATE products SET stock = stock + 5
shop-# WHERE id = 3
shop-# RETURNING name, stock;
     name     | stock 
--------------+-------
 Battery pack |     5
(1 row)

UPDATE 1

The upsert is one statement, so two requests that register the same email at the same moment cannot both insert: the database decides. Doing the same in code (“check whether it exists, then insert”) leaves a gap between the check and the insert in which another request can slip through. Chapter 6 is about exactly these gaps.

Watch out: UPDATE and DELETE without WHERE

DELETE FROM orders; deletes every order, instantly, without asking. Before running an UPDATE or a DELETE by hand, run the same WHERE as a SELECT and check the rows. Better still, start a transaction with BEGIN;, run the change, look at the result, and only then COMMIT; (or ROLLBACK;). Chapter 6 explains transactions.

4.7 Indexes and query plans

The orders table has a hundred thousand rows. How does PostgreSQL find the orders of customer 1234? EXPLAIN shows the plan the database chose; with ANALYZE, it also runs the query and reports what really happened:

psql
# How does PostgreSQL find one customer's orders?
shop=# EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF)
shop-# SELECT count(*) FROM orders WHERE customer_id = 1234;
                               QUERY PLAN                               
------------------------------------------------------------------------
 Aggregate (actual time=5.177..5.178 rows=1.00 loops=1)
   ->  Seq Scan on orders (actual time=0.067..5.166 rows=44.00 loops=1)
         Filter: (customer_id = 1234)
         Rows Removed by Filter: 99962
 Planning Time: 0.293 ms
 Execution Time: 5.231 ms
(6 rows)

A sequential scan: PostgreSQL read all 100,006 rows and threw away 99,962 to find 44. Five milliseconds sounds small, but it grows with the table, and the API does it on every request for every user. An index is a separate, sorted structure (a B-tree) that maps values to rows, like the index at the back of this book:

psql
# Add an index on the foreign key, and ask again
shop=# CREATE INDEX orders_customer_id_idx ON orders (customer_id);
CREATE INDEX
shop=# EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF)
shop-# SELECT count(*) FROM orders WHERE customer_id = 1234;
                                              QUERY PLAN                                               
-------------------------------------------------------------------------------------------------------
 Aggregate (actual time=0.240..0.241 rows=1.00 loops=1)
   ->  Bitmap Heap Scan on orders (actual time=0.057..0.232 rows=44.00 loops=1)
         Recheck Cond: (customer_id = 1234)
         Heap Blocks: exact=44
         ->  Bitmap Index Scan on orders_customer_id_idx (actual time=0.042..0.042 rows=44.00 loops=1)
               Index Cond: (customer_id = 1234)
               Index Searches: 1
 Planning Time: 0.474 ms
 Execution Time: 0.307 ms
(9 rows)

Now the database goes straight to the 44 rows through the index: several times faster here, and the gap widens as the table grows, because a B-tree lookup takes about the same time for a million rows as for a thousand. Three rules about indexes:

  • PostgreSQL does not index foreign keys for you. orders.customer_id had no index until we added one. Index the foreign keys you search or join by.
  • An index serves the queries that match it. A query that wraps the column in a function cannot use a plain index on the column. You can index the expression itself:
psql
# An index on an expression, for case-insensitive email lookups
shop=# EXPLAIN (COSTS OFF)
shop-# SELECT id FROM customers WHERE lower(email) = 'sara@example.com';
                     QUERY PLAN                      
-----------------------------------------------------
 Seq Scan on customers
   Filter: (lower(email) = 'sara@example.com'::text)
(2 rows)
shop=# CREATE INDEX customers_lower_email_idx ON customers (lower(email));
CREATE INDEX
shop=# EXPLAIN (COSTS OFF)
shop-# SELECT id FROM customers WHERE lower(email) = 'sara@example.com';
                          QUERY PLAN                           
---------------------------------------------------------------
 Bitmap Heap Scan on customers
   Recheck Cond: (lower(email) = 'sara@example.com'::text)
   ->  Bitmap Index Scan on customers_lower_email_idx
         Index Cond: (lower(email) = 'sara@example.com'::text)
(4 rows)
  • Indexes are not free. Each one takes space and slows every insert and update, which must update the index too. Add them for the queries you actually run, as shown by EXPLAIN and by the slow query log, not “just in case”.

For a column pair such as (price, id), the order matters: the index is sorted by price first, so it serves WHERE price = … and ORDER BY price, id, but not a search by id alone. Chapter 14 goes deeper into plans and tuning.

Professional habit: EXPLAIN before you ship

For every new query that will run on a large or growing table, run EXPLAIN ANALYZE on realistic data before the code is merged, and paste the plan in the pull request. A Seq Scan on a big table in a request path is a bug waiting for traffic. Testing on a table with twelve rows proves nothing: generate data, as seed.sql does with generate_series.

4.8 SQL from code, safely

Applications send SQL to the database through a driver. The single most important rule: never build SQL by joining strings with input. Here is why, with an input that a form could send as an email address:

node/query.ts
import pg from "pg";

const pool = new pg.Pool({ connectionString: "postgres://bit:secret@localhost:5432/shop" });

// What a form might send as an email: it closes the quote and adds a condition.
const input = "x' OR '1'='1";

// WRONG: the input becomes part of the SQL
const unsafe = await pool.query(`SELECT id, email FROM customers WHERE email = '${input}'`);
console.log("string concatenation:", unsafe.rowCount, "rows");

// Right: the SQL and the value travel separately; $1 is only ever a value
const safe = await pool.query("SELECT id, email FROM customers WHERE email = $1", [input]);
console.log("parameter:", safe.rowCount, "rows");

const sara = await pool.query(
  "SELECT c.name, count(o.id) AS orders FROM customers c " +
    "LEFT JOIN orders o ON o.customer_id = c.id WHERE c.email = $1 GROUP BY c.name",
  ["sara@example.com"],
);
// count(*) is a bigint; pg returns it as a string, because JavaScript numbers cannot hold every bigint
console.log(sara.rows[0], typeof sara.rows[0].orders);

await pool.end();
Terminal
# From Node, with the pg driver
$ node node/query.ts
string concatenation: 2008 rows
parameter: 0 rows
{ name: 'Sara', orders: '2' } string

Glued into the SQL, the input closed the quote and added OR '1'='1', which is always true: the query returned every customer, 2008 rows, instead of none. This is SQL injection, still one of the most common and most damaging attacks on the web: with a slightly different input, an attacker can read any table, or delete them. With a parameter, $1, the SQL and the value are sent to the database separately; the value can never become SQL, whatever it contains, and the same query found no customer with that strange email.

Notice the last line: orders arrived as the string '2'. count(*) returns a bigint, and a JavaScript number cannot hold every bigint exactly, so the pg driver plays safe and returns a string. Convert it when you know the value is small (Number(row.orders)), or cast in SQL (count(*)::int). Chapter 5 adds a typed layer that does this once.

Summary

  • Tables have typed columns: bigint ids, text, integer money, timestamptz times. Constraints (PRIMARY KEY, NOT NULL, UNIQUE, CHECK, REFERENCES) keep data correct whatever writes it.
  • SELECT … FROM … WHERE … ORDER BY … LIMIT reads rows; aggregates summarise them.
  • NULL is unknown: compare it with IS NULL; it spreads through arithmetic.
  • Inner joins keep matches; left joins keep every left row. Count a right-table column, not *.
  • GROUP BY makes groups, HAVING filters them; the database runs FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY in that order.
  • CTEs name intermediate results; window functions compute across rows without collapsing them.
  • RETURNING and ON CONFLICT make writes answer and upserts atomic.
  • EXPLAIN ANALYZE shows the plan; indexes turn scans into lookups. Index foreign keys and real query patterns, including expressions.
  • Parameters, never string concatenation, between code and SQL.

Quick check answers: 1. Comparing anything with NULL gives NULL (unknown), never true, and WHERE keeps only rows where the condition is true; use IS NULL. 2. count(*) counts rows, and a customer with no orders still has one row in a left join (with NULLs), so they get 1 instead of 0; count a column from the orders table, such as count(o.id). 3. WHERE runs before the rows are grouped, so there is no sum yet; filter groups with HAVING sum(quantity) > 100.

Early in my career I changed a column name directly on the production database on a Friday afternoon. The new code was not deployed yet; the old code kept asking for the old name. For twenty minutes every order failed. Since then, schema changes go through migrations, in small steps, and never on Fridays.

5.1 Modelling the shop

A data model starts from the entities of the domain (customers, products, orders) and the relationships between them:

  • One to many: a customer has many orders, an order has one customer. The “many” side holds a foreign key: orders.customer_id.
  • Many to many: an order has many products, a product is in many orders. A third table joins them, order_items, and it often carries its own data: the quantity and the price at the time.
  • One to one is rare: usually it means the two tables are one entity, or that some optional data is split off (a customer’s billing details).

Three questions decide most designs:

  • Store or compute? An order’s total can be computed from its items, so storing it as well creates two truths that can disagree. Store facts; compute what derives from them, until measurements say a stored copy is needed for speed. The price on order_items is not a copy: it is a different fact, the price then.
  • Which rules belong in the database? Every rule that must never be broken, whatever code writes the data: types, NOT NULL, uniqueness, foreign keys, ranges.
  • What happens on delete? Deleting a customer with orders must either be refused (the default), cascade, or be replaced by marking the row inactive. Decide per relationship, and write it in the foreign key.

5.2 Migrations

A migration is one change to the schema, written as code and kept in the repository: a function up that makes the change and a function down that undoes it. Each machine (your laptop, a colleague’s, CI, production) runs the migrations it has not run yet, in order, and records which ones ran. Nobody changes a shared database by hand.

We use Kysely, a type-safe SQL query builder for TypeScript that includes a migration runner. The first migration creates the tables of Chapter 4:

migrations/2026_11_01_001_initial.ts
import { type Kysely, sql } from "kysely";

// up: what this migration adds
export async function up(db: Kysely<unknown>): Promise<void> {
  await db.schema
    .createTable("customers")
    .addColumn("id", "bigint", (c) => c.primaryKey().generatedAlwaysAsIdentity())
    .addColumn("name", "text", (c) => c.notNull())
    .addColumn("email", "text", (c) => c.notNull().unique())
    .addColumn("created_at", "timestamptz", (c) =>
      c.notNull().defaultTo(sql`now()`),
    )
    .execute();

  await db.schema
    .createTable("products")
    .addColumn("id", "bigint", (c) => c.primaryKey().generatedAlwaysAsIdentity())
    .addColumn("name", "text", (c) => c.notNull())
    .addColumn("price", "integer", (c) => c.notNull().check(sql`price > 0`))
    .addColumn("stock", "integer", (c) =>
      c
        .notNull()
        .defaultTo(0)
        .check(sql`stock >= 0`),
    )
    .execute();

  await db.schema
    .createTable("orders")
    .addColumn("id", "bigint", (c) => c.primaryKey().generatedAlwaysAsIdentity())
    .addColumn("customer_id", "bigint", (c) =>
      c.notNull().references("customers.id"),
    )
    .addColumn("status", "text", (c) =>
      c
        .notNull()
        .defaultTo("pending")
        .check(sql`status IN ('pending', 'paid', 'shipped', 'cancelled')`),
    )
    .addColumn("created_at", "timestamptz", (c) =>
      c.notNull().defaultTo(sql`now()`),
    )
    .execute();
  await db.schema
    .createIndex("orders_customer_id_idx")
    .on("orders")
    .column("customer_id")
    .execute();

  await db.schema
    .createTable("order_items")
    .addColumn("order_id", "bigint", (c) =>
      c.notNull().references("orders.id").onDelete("cascade"),
    )
    .addColumn("product_id", "bigint", (c) => c.notNull().references("products.id"))
    .addColumn("quantity", "integer", (c) =>
      c.notNull().check(sql`quantity BETWEEN 1 AND 99`),
    )
    .addColumn("price", "integer", (c) => c.notNull())
    .addPrimaryKeyConstraint("order_items_pkey", ["order_id", "product_id"])
    .execute();
}

// down: how to undo it exactly
export async function down(db: Kysely<unknown>): Promise<void> {
  for (const table of ["order_items", "orders", "products", "customers"]) {
    await db.schema.dropTable(table).execute();
  }
}

5.3 Changing a live schema: expand and contract

The shop needs a SKU, a stock code, for every product, required and unique. The obvious migration adds a NOT NULL UNIQUE column in one step. On a live system, that step fails or breaks things: the existing rows have no SKU, and the code running in production does not send one when it creates a product. While the new code is being deployed, old and new versions run side by side.

The safe pattern is expand and contract: change the schema in steps, each compatible with the code running at that moment.

  1. Expand: add the column as optional. Old code ignores it; nothing breaks.
  2. Deploy code that writes it for every new product, and backfill the existing rows.
  3. Contract: once every row has a value, make it required and unique.
migrations/2026_11_02_001_product_sku_expand.ts
import type { Kysely } from "kysely";

// Step 1, expand: a new column that may be empty, so old code keeps working.
export async function up(db: Kysely<unknown>): Promise<void> {
  await db.schema.alterTable("products").addColumn("sku", "text").execute();
}

export async function down(db: Kysely<unknown>): Promise<void> {
  await db.schema.alterTable("products").dropColumn("sku").execute();
}
migrations/2026_11_03_001_product_sku_contract.ts
import { type Kysely, sql } from "kysely";

export async function up(db: Kysely<unknown>): Promise<void> {
  // Step 2: fill the column for every existing row.
  await sql`UPDATE products SET sku = 'BIT-' || lpad(id::text, 4, '0') WHERE sku IS NULL`.execute(
    db,
  );
  // Step 3, contract: now every row has a SKU, make it required and unique.
  await db.schema
    .alterTable("products")
    .alterColumn("sku", (c) => c.setNotNull())
    .execute();
  await db.schema
    .createIndex("products_sku_key")
    .on("products")
    .column("sku")
    .unique()
    .execute();
}

export async function down(db: Kysely<unknown>): Promise<void> {
  await db.schema.dropIndex("products_sku_key").execute();
  await db.schema
    .alterTable("products")
    .alterColumn("sku", (c) => c.dropNotNull())
    .execute();
}

The same pattern renames a column (add the new one, write both, backfill, read the new one, drop the old one) or splits a table. It takes more migrations and more deployments, and it never takes the shop down. Two warnings for large tables: a backfill of millions of rows should run in batches outside the migration, and some changes lock a table while they run; Chapter 14 shows how to see those locks.

5.5 Typed queries

Kysely’s queries read like SQL, and their result types are built from what you select:

export async function findOrder(id: number) {

  return db

    .innerJoin("customers as c", "c.id", "o.customer_id")

          .whereRef("i.order_id", "=", "o.id"),

    ])
    .where("o.id", "=", id)
    .executeTakeFirst();

Tip: query builder or ORM?

An ORM (Prisma, Drizzle, TypeORM) maps tables to objects and writes most SQL for you; a query builder such as Kysely keeps you close to SQL and only adds types and composition. ORMs are quicker for simple create-read-update-delete work. Query builders make the SQL you run obvious, which matters as soon as performance does. Both are good choices; what matters is that the team knows the SQL being sent. Turn on query logging in development whichever you choose.

5.6 The N+1 problem

A page lists a customer’s orders with their items. The natural first version loads the orders, then loops over them and loads each order’s items:

src/orders.ts
export async function customerOrdersOneByOne(customerId: number) {
  const orders = await db
    .selectFrom("orders")
    .select(["id", "status"])
    .where("customer_id", "=", customerId)
    .execute();
  const result = [];
  for (const order of orders) {
    const items = await db
      .selectFrom("order_items")
      .select(["product_id", "quantity", "price"])
      .where("order_id", "=", order.id)
      .execute();
    result.push({ ...order, items });
  }
  return result;
}

That is one query for the orders and one more for each order: 1 + N queries. The second version asks for everything at once:

src/orders.ts
export async function customerOrdersAtOnce(customerId: number) {
  return db
    .selectFrom("orders as o")
    .select((eb) => [
      "o.id",
      "o.status",
      jsonArrayFrom(
        eb
          .selectFrom("order_items as i")
          .select(["i.product_id", "i.quantity", "i.price"])
          .whereRef("i.order_id", "=", "o.id"),
      ).as("items"),
    ])
    .where("o.customer_id", "=", customerId)
    .execute();
}

6.1 Transactions: all or nothing

A transaction groups statements so that they act as one. It has four guarantees, known as ACID:

  • Atomicity: either every change is kept, or none is.
  • Consistency: every rule of the schema holds at the end.
  • Isolation: transactions running at the same time do not see each other’s unfinished work (exactly how much they see is the isolation level, 6.3).
  • Durability: once committed, a change survives a crash.

This chapter uses two small tables:

schema.sql
CREATE TABLE products (
  id    bigint PRIMARY KEY,
  name  text NOT NULL,
  price integer NOT NULL CHECK (price > 0),
  stock integer NOT NULL CHECK (stock >= 0)
);
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  product_id bigint NOT NULL REFERENCES products (id),
  buyer      integer NOT NULL
);
INSERT INTO products VALUES (1, 'Robot kit', 45000, 1), (2, 'Spare wheels', 6000, 10);

6.2 A race: one kit, ten buyers

Here is the obvious way to sell a product: read the stock, check it in code, write the new stock, record the order. To see what happens under load, the program starts ten buyers at the same moment, each with its own database connection, for a product with one unit left. A short pause between reading and writing stands for what a real application does there, such as calling a payment service:

node/race.ts
async function buy(buyer: number) {
  const db = new pg.Client(url);
  await db.connect();
  try {
    for (;;) {
      try {
        await db.query(mode === "serializable" ? "BEGIN ISOLATION LEVEL SERIALIZABLE" : "BEGIN");
        if (mode === "atomic") {
          // one statement: the database checks and changes the stock together
          const taken = await db.query(
            "UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock > 0",
          );
          if (taken.rowCount === 1) {
            await db.query("INSERT INTO orders (product_id, buyer) VALUES (1, $1)", [buyer]);
          }
        } else {
          // read, decide in code, write: the classic race
          // FOR UPDATE locks the row: other buyers wait here until this transaction ends
          const lock = mode === "lock" ? " FOR UPDATE" : "";
          const { rows } = await db.query(`SELECT stock FROM products WHERE id = 1${lock}`);
          // the time a real app spends between reading and writing: a call to a payment service, say
          await db.query("SELECT pg_sleep(0.1)");
          if (rows[0].stock > 0) {
            await db.query("UPDATE products SET stock = $1 WHERE id = 1", [rows[0].stock - 1]);
            await db.query("INSERT INTO orders (product_id, buyer) VALUES (1, $1)", [buyer]);
          }
        }
        await db.query("COMMIT");
        return;
      } catch (error) {
        await db.query("ROLLBACK");
        // serialization failure: start the whole transaction again
        if ((error as { code?: string }).code !== "40001") throw error;
        retries++;
      }
    }
  } finally {
    await db.end();
  }
}

The naive version sold one kit ten times. Every buyer read “1 in stock” before anyone had written, every buyer decided to sell, and every buyer wrote “0”. The transaction did not help: it makes changes all-or-nothing, but it does not stop two transactions from reading the same value. This is a race condition, a check-then-act bug: the check was true when it ran and false by the time the action happened.

The other three versions each sold it once. They are the three standard fixes:

  • An atomic update. UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock > 0 checks and changes in one statement. PostgreSQL locks the row while it updates, so the second buyer’s update waits, then re-checks stock > 0 against the new value and changes nothing. The number of changed rows tells the code whether it sold. When the rule fits in a WHERE, this is the simplest and fastest fix.
  • A row lock. SELECT … FOR UPDATE reads the row and locks it until the transaction ends. Every other buyer waits at that line, then reads the stock after the first one committed. Use it when the decision needs code between the read and the write (a price calculation, a call to another service), and keep such transactions short, because everyone waits.
  • Serializable isolation. The code stays naive, and the database guarantees that the result equals running the transactions one after another. When it detects that this is impossible, it refuses a transaction with error 40001, and the code runs it again from the start: here, nine of the ten buyers were refused once and found the stock empty on their retry.

Watch out: the check in code is never enough

Any rule of the form “only if …” (enough stock, a seat still free, a balance high enough, a username not taken) is a race when it is checked in code and then written. Put the rule where the database can enforce it at the moment of the write: in a conditional update, a unique constraint, a CHECK, or a lock. Chapter 4’s CHECK (stock >= 0) would also have stopped the oversale, with an error instead of a quiet second order.

6.3 Isolation levels

The isolation level decides what a transaction sees of other transactions that commit while it is running. Two connections show the difference: A reads a price, B changes it and commits, A reads again and then tries to change it:

node/isolation.ts
// A reads, B changes and commits, A reads again, then A tries to change it
await a.query(`BEGIN ISOLATION LEVEL ${level}`);
console.log("A reads the price:", await price());
await b.query("UPDATE products SET price = 50000 WHERE id = 1");
console.log("B sets the price to 50000 and commits");
console.log("A reads it again:", await price());
try {
  await a.query("UPDATE products SET price = price + 1000 WHERE id = 1");
  await a.query("COMMIT");
  console.log("A adds 1000 to the price:", (await a.query("SELECT price FROM products WHERE id = 1")).rows[0].price);
} catch (error) {
  await a.query("ROLLBACK");
  console.log("A adds 1000 to the price: ERROR", (error as Error).message);
}

  • READ COMMITTED, PostgreSQL’s default: every statement sees everything committed before it started. A’s second read saw B’s new price, so two reads in one transaction disagreed, and A’s update built on B’s value.
  • REPEATABLE READ: the transaction sees a snapshot taken at its first statement. A’s second read still saw 45000, so its reads are consistent with each other. And when A tried to update a row that B had changed since that snapshot, PostgreSQL refused: A was working from an old picture. The application must retry.
  • SERIALIZABLE adds detection of every pattern that could not happen if the transactions ran one after another, as in the race above. It is the safest level and needs retries the most.

A practical rule: keep the default, use atomic statements and constraints for the rules they can express, take row locks when code must decide between a read and a write, and use SERIALIZABLE (with retries) for complicated multi-row rules where it is hard to see every race. Reports that read many tables at once benefit from REPEATABLE READ, so their numbers come from one moment.

6.4 Deadlocks

Locks have their own trap. Transaction A locks product 1 and then wants product 2; transaction B has locked product 2 and wants product 1. Each waits for the other, forever:

node/deadlock.ts
// A locks product 1 then 2; B locks 2 then 1
async function run(name: string, first: number, second: number) {
  const db = new pg.Client(url);
  await db.connect();
  try {
    await db.query("BEGIN");
    await take(db, first);
    await sleep(200);
    await take(db, second);
    await db.query("COMMIT");
    console.log(`${name}: done`);
  } catch (error) {
    await db.query("ROLLBACK");
    console.log(`${name}: failed, ${(error as { code?: string }).code}, ${(error as Error).message}`);
  } finally {
    await db.end();
  }
}
Terminal
# Two transactions, the same two rows, in opposite orders
$ node node/deadlock.ts
B: failed, 40P01, deadlock detected
A: done

PostgreSQL checks for such cycles after a second of waiting (deadlock_timeout), picks one transaction, and aborts it with error 40P01, so the other can finish. Which one loses depends on timing. Two habits keep deadlocks rare: lock rows in a consistent order (for an order with several products, lock or update them sorted by id), and keep transactions short, with no network calls or user waits inside them. Like serialization failures, a deadlock victim can simply be retried.

6.5 Transactions in the framework

With Kysely from Chapter 5, a transaction is a callback; it commits when the callback returns and rolls back when it throws. Row locks and isolation levels are methods:

  • await db.transaction().setIsolationLevel("serializable").execute(async (trx) => { … }), using trx, not db, for every query inside.
  • trx.selectFrom("products").selectAll().where("id", "=", id).forUpdate().executeTakeFirst() for a row lock.

Kysely does not retry for you: wrap the call in a small loop that retries on codes 40001 and 40P01, a few times, with a short random pause between attempts. The race program above has exactly that loop.

6.6 Side effects and the outbox

A transaction can be rolled back; an email cannot be unsent. If the code sends “your order is confirmed” inside the transaction and the commit then fails (a deadlock, a constraint, a crash), the customer has an email for an order that does not exist. Sending after the commit has the opposite problem: if the process crashes between the commit and the send, the order exists and the email never goes.

The reliable pattern is the outbox: inside the same transaction as the order, insert a row into an outbox table describing the message to send. The order and its message commit together or not at all. A separate worker reads the outbox, sends each message, and marks it sent; if it crashes, it sends again later, so the receiver must tolerate duplicates (idempotency again). Chapter 10 builds the worker with a queue.

Professional habit: test races on purpose

A race does not appear in a test that runs one request at a time. For every “only if” rule (stock, seats, balances, unique names), write one test that starts many requests at the same moment, as this chapter’s race program does, and asserts on the final state: one sale, one booking, a balance never below zero. Such a test fails reliably on the naive code, which is the proof that it tests the right thing.

Summary

  • A transaction makes several statements atomic: one failure, and COMMIT becomes ROLLBACK.
  • Transactions do not stop races: “read, check in code, write” sells one item many times under load.
  • Three fixes: an atomic conditional update, a row lock with FOR UPDATE, or SERIALIZABLE with retries.
  • READ COMMITTED sees each statement’s latest commits; REPEATABLE READ sees one snapshot and refuses updates to rows changed since.
  • Deadlocks are cycles of locks; PostgreSQL breaks them with 40P01. Lock in a consistent order, keep transactions short, retry.
  • Side effects belong after the commit, reliably through an outbox.

7.1 Redis in five minutes

Redis is a server that stores keys and their values in memory. Clients talk to it over the network, like a database, and redis-cli is its command-line client. The simplest values are strings, and a key can carry an expiry time:

7.2 A cache in front of a slow query

The most common pattern is cache-aside: the application looks in Redis first; on a cache miss it asks the database and keeps a copy in Redis for next time; on a cache hit the database is not touched. Here a pg_sleep(0.2) makes the query take 200 milliseconds, like a heavy report:

node/cache.ts
// the slow query: pg_sleep stands for a heavy report or a join over big tables
async function productFromDb(id: number): Promise<Product> {
  const sql = "SELECT id, name, price FROM products, pg_sleep(0.2) WHERE id = $1";
  return (await db.query(sql, [id])).rows[0];
}

// cache-aside: look in Redis first; on a miss, ask the database and keep the answer
async function product(id: number) {
  const key = `product:${id}`;
  const cached = await redis.get(key);
  if (cached !== null) return { product: JSON.parse(cached) as Product, from: "Redis" };
  const fresh = await productFromDb(id);
  // forgotten after 60 seconds, even if nobody deletes it
  await redis.set(key, JSON.stringify(fresh), { EX: 60 });
  return { product: fresh, from: "PostgreSQL" };
}

// changing the data: update the database first, then delete the cached copy
async function setPrice(id: number, price: number) {
  await db.query("UPDATE products SET price = $1 WHERE id = $2", [price, id]);
  await redis.del(`product:${id}`);
}
Terminal
# A cache in front of a slow query
$ node node/cache.ts

second request   Robot kit, 45000, from Redis in 1 ms
third request    Robot kit, 45000, from Redis in 1 ms

The first request paid the full 200 milliseconds; the next two came from memory in about one. That is the reward. The cost is that there are now two copies of the data, and the copy can be wrong. Two rules keep it right:

  • Invalidate on change. Whatever changes the data deletes the cached copy, after the database write has succeeded. The next read misses and fetches the new value: the price 47000 appeared at once. Deleting is safer than writing the new value into the cache, because two concurrent writers could otherwise leave the older value there.
  • Always set an expiry. Some change will one day forget to invalidate: a direct SQL fix, a new code path, a bug. A TTL limits how long a wrong copy can live. Choose it from the question “how stale may this be?”: seconds for stock levels, minutes for a product page, hours for a list of countries.

Watch out: cache what is shared, not what is private

A cache key must contain everything the answer depends on. A product page in two languages needs product:2:ar and product:2:en, and anything that depends on the user (their basket, their prices, their permissions) needs the user in the key, or no cache at all. Serving one customer’s cached data to another is a security incident, not a performance bug.

7.3 Stampedes and locks

A cache has a dangerous moment: when a popular key expires. Every request that arrives in the next 200 milliseconds misses, and every one of them asks the database the same heavy question. This is a cache stampede. The program sends twenty requests at once for a product that is not cached, first without protection, then with a lock that lets only one request rebuild the cache while the others wait and look again:

node/stampede.ts
// delete the lock only if it is still ours, in one step on the server
const RELEASE = `if redis.call("GET", KEYS[1]) == ARGV[1]
  then return redis.call("DEL", KEYS[1]) else return 0 end`;

async function product(id: number) {
  const key = `product:${id}`;
  for (;;) {
    const cached = await redis.get(key);
    if (cached !== null) return JSON.parse(cached);
    if (mode === "naive") break;
    // only the request that gets the lock asks the database; the others wait and look again
    const token = randomUUID(); // a random token: only the owner of the lock may release it
    if (await redis.set(`lock:${key}`, token, { NX: true, PX: 5000 })) {
      try {
        const fresh = await productFromDb(id);
        await redis.set(key, JSON.stringify(fresh), { EX: 60 });
        return fresh;
      } finally {
        await redis.eval(RELEASE, { keys: [`lock:${key}`], arguments: [token] });
      }
    }
    await sleep(50);
  }
  const fresh = await productFromDb(id);
  await redis.set(key, JSON.stringify(fresh), { EX: 60 });
  return fresh;
}
Terminal
# Twenty requests on a cold cache
$ node node/stampede.ts naive
naive   20 requests, database queries: 20, 440 ms
$ node node/stampede.ts locked
locked  20 requests, database queries: 1, 259 ms

Without the lock, twenty requests made twenty identical queries; with it, one. With a real report that takes two seconds and a page that a thousand visitors open in that time, this is the difference between a slow page and a database that falls over. The lock is three ideas:

  • Take it with SET key token NX PX 5000. NX means only one client can create the key; the others get null and know someone else is working. PX 5000 makes the lock expire after 5 seconds, so a process that crashes while holding it cannot block everyone forever.
  • A random token as the value. If the work took longer than 5 seconds, the lock expired and another process may hold it now. Deleting the key blindly would release their lock.
  • Release with a script. “Read the value, compare it, delete the key” must happen in one step, or the lock could change hands between the read and the delete. Redis runs a Lua script atomically, like a single command, so the release checks the token and deletes in one step.

A Redis lock is good for efficiency: avoiding duplicate work, as here. It is not a guarantee of correctness, because a lock that expires while its owner is still working (a long pause, a slow network) lets two processes in. When two processes doing the work at once would corrupt data, the last line of defence stays in the database: a constraint, a conditional update or a row lock, from Chapter 6.

7.4 A rate limit that servers share

Chapter 3 limited requests with @fastify/rate-limit, which counts in the server’s own memory.

With counters in each server’s memory, a client who spreads requests across two servers gets twice the limit, and a restart resets everyone. The counter belongs in Redis, where every server sees the same number:

node/ratelimit.ts
import { createClient } from "redis";

const LIMIT = 5;
const WINDOW = 10; // seconds

// one counter per client; the first request starts a 10-second window
async function allow(redis: ReturnType<typeof createClient>, client: string) {
  const key = `rate:${client}`;
  // MULTI/EXEC: both commands run together, nothing in between
  const [count] = await redis.multi().incr(key).expire(key, WINDOW, "NX").exec();
  return { allowed: Number(count) <= LIMIT, count: Number(count), key };
}

// two servers, two connections, one Redis: the limit is shared
const servers = {
  A: await createClient({ url: "redis://localhost:6379" }).connect(),
  B: await createClient({ url: "redis://localhost:6379" }).connect(),
};
await servers.A.del("rate:203.0.113.7");
for (let i = 1; i <= 8; i++) {
  const name = i % 2 === 1 ? "A" : "B";
  const redis = servers[name];
  const { allowed, count, key } = await allow(redis, "203.0.113.7");
  const answer = allowed
    ? `allowed (${count} of ${LIMIT})`
    : `refused, 429, try again in ${await redis.ttl(key)} s`;
  console.log(`request ${i} via server ${name}: ${answer}`);
}
await servers.A.close();
await servers.B.close();
Terminal
# Five requests per 10 seconds, shared by two servers
$ node node/ratelimit.ts
request 1 via server A: allowed (1 of 5)
request 2 via server B: allowed (2 of 5)
request 3 via server A: allowed (3 of 5)
request 4 via server B: allowed (4 of 5)

The requests alternated between servers A and B, and the sixth was refused whichever server received it. Two details make it right:

  • EXPIRE … NX sets the expiry only if the key has none, so the first request starts the 10-second window and later requests do not extend it.
  • MULTI and EXEC send both commands as one transaction: Redis runs them together, with no other client’s command in between. With two separate commands, a process that crashed after INCR and before EXPIRE would leave a counter that never expires, and that client blocked forever.

This is a fixed window: simple and cheap, but a client can send 5 requests at the end of one window and 5 more at the start of the next. A sliding window counts the requests of the last 10 seconds at every moment, with a sorted set of timestamps; it is exercise 5.

7.5 Redis in the framework

In a Fastify application, create one Redis client when the server starts, share it with app.decorate("redis", client), and close it in an onClose hook, exactly like the database pool. The ready-made pieces accept it:

  • @fastify/rate-limit takes a redis option, and then keeps its counters there instead of in memory, shared by every server.
  • Caching stays a few lines of your own code, like product() above, often wrapped in a small helper cached(key, ttl, load).
  • For locks with automatic renewal and for queues, there are packages built on these same commands; Chapter 10 uses Redis for a job queue.

7.6 What belongs in Redis

Redis keeps everything in memory, and memory is small and expensive compared with disk. Three settings decide how it behaves when things go wrong:

  • maxmemory limits the memory Redis may use, and maxmemory-policy decides what happens at the limit. For a pure cache, allkeys-lru evicts the least recently used keys, which is exactly what a cache should forget. The default, noeviction, refuses new writes instead.
  • Persistence (RDB snapshots and the AOF log) can save the data to disk, so a restart does not empty it. A cache can do without; sessions and queues need it.
  • One Redis for a cache that may forget, and another (or another configuration) for data that must not: a queue whose jobs vanish under memory pressure loses orders.

The rule that follows: Redis holds copies and short-lived state; the database holds the truth. If Redis were emptied right now, the application should get slower, log users out at worst, but lose nothing that matters.

Professional habit: measure before you cache

A cache adds a second copy of the data, invalidation code, and a new way to be wrong. Before adding one, measure: which query is slow, how often it runs, and whether an index (Chapter 4) or a better query would fix it with no copy at all. Then cache the few hot, expensive, shared answers, and watch the hit rate: a cache that is hit 20% of the time is mostly overhead.

Quick check answers: 1. Authentication and Authorization

In this chapter you will learn to

  • tell authentication (who are you?) from authorization (may you do this?)
  • store passwords so that a stolen database does not reveal them
  • register and sign users in, without telling attackers which emails exist
  • issue session tokens you can revoke, and understand when a JWT is the better choice

Until now, anyone could call every route of the shop’s API. A real shop needs to know who is calling: a customer sees their own orders and no one else’s, and only staff may see the list of customers. Getting this right is not hard, but almost every mistake in it is a security incident, and the mistakes are invisible until someone exploits them. This chapter builds it step by step with Node’s own crypto module, PostgreSQL and Fastify, and runs every request against the real server.

Bit

Years ago a site I used was breached, and the attackers published its user table. My password was right there, in plain text, next to my email. It was the same password I used on two other sites. That afternoon I changed seven passwords, and I promised myself that no table I build would ever hold one.

8.1 Two questions

Every protected request answers two separate questions, in order:

  • Authentication: who is calling? The client proves an identity, with a password once and then with a token on every request. If it cannot, the answer is 401 Unauthorized (a confusing name: it means “not authenticated”).
  • Authorization: may this user do this? The identity is known; the rules decide. If they say no, the answer is 403 Forbidden, or 404 Not Found when even the existence of the thing is private.

Keeping them apart keeps the code clear: one function finds the user, and the rules about what each user may do live next to the routes they protect.

8.2 Storing passwords

A password must never be stored as it is, and never with an ordinary hash such as SHA-256 either. A fast hash is the problem: a graphics card computes billions of SHA-256 hashes a second, so an attacker with a stolen table tries every common password against every row in minutes. Password storage needs a hash that is slow on purpose and needs a lot of memory, so that each guess costs real time: scrypt, Argon2 or bcrypt. Node has scrypt built in:

src/password.ts
import { randomBytes, scrypt, timingSafeEqual } from "node:crypto";

// N = 2^15: tens of milliseconds and 32 MB per hash, slow on purpose; raise it as computers get faster
const COST = 2 ** 15;

function derive(password: string, salt: Buffer, cost: number) {
  return new Promise<Buffer>((resolve, reject) => {
    const options = { N: cost, r: 8, p: 1, maxmem: 64 * 1024 * 1024 };
    scrypt(password.normalize("NFKC"), salt, 32, options, (error, key) =>
      error ? reject(error) : resolve(key),
    );
  });
}

export async function hashPassword(password: string) {
  // a new random salt for every hash: the same password never gives the same hash
  const salt = randomBytes(16);
  const key = await derive(password, salt, COST);
  // algorithm, cost, salt and key in one string: old hashes still verify after the cost changes
  return [
    "scrypt",
    COST,
    salt.toString("base64url"),
    key.toString("base64url"),
  ].join("$");
}

export async function verifyPassword(password: string, stored: string) {
  const [, cost, salt, key] = stored.split("$");
  const expected = Buffer.from(key ?? "", "base64url");
  const actual = await derive(
    password,
    Buffer.from(salt ?? "", "base64url"),
    Number(cost),
  );
  // compares every byte, so the time taken does not reveal where the first difference is
  return timingSafeEqual(actual, expected);
}
  • The salt is 16 random bytes, different for every hash, stored next to it. Two users with the same password get different hashes, so an attacker must attack each row separately, and precomputed tables of hashes are useless.
  • The cost is stored inside the string. When computers get faster you raise COST; old hashes still verify with the cost they were made with, and can be upgraded when the user next signs in (exercise 3).
  • timingSafeEqual compares all 32 bytes every time. An ordinary comparison stops at the first different byte, and the time it takes can leak information.
  • normalize("NFKC") makes passwords typed on different keyboards compare equal when they look the same, which matters for Arabic and other non-Latin passwords.

8.4 Sessions and tokens

After a successful sign-in the server gives the client a session token: proof of identity for the next requests, so the password is sent once. Our tokens are 32 random bytes, and the database stores only their SHA-256 hash:

src/sessions.ts
const digest = (token: string) => createHash("sha256").update(token).digest("hex");

export async function startSession(userId: number) {
  // 32 random bytes: impossible to guess, and meaningless without the database
  const token = randomBytes(32).toString("base64url");
  await db
    .insertInto("sessions")
    // only the hash is stored: a leaked sessions table opens no account
    .values({
      token_hash: digest(token),
      user_id: userId,
      expires_at: sql`now() + interval '30 days'`,
    })
    .execute();
  return token;
}

export async function userForToken(token: string) {
  return db
    .selectFrom("sessions")
    .innerJoin("users", "users.id", "sessions.user_id")
    .select(["users.id", "users.email", "users.name", "users.role"])
    .where("sessions.token_hash", "=", digest(token))
    .where("sessions.expires_at", ">", sql<Date>`now()`)
    .executeTakeFirst();
}

export async function endSession(token: string) {
  await db.deleteFrom("sessions").where("token_hash", "=", digest(token)).execute();
}

A fast hash is right here, unlike for passwords: the token is 32 random bytes, not a word a person chose, so there is nothing to guess, and the hash only ensures that someone who reads the sessions table cannot use what they read. On every request, a preHandler reads the Authorization header and finds the user:

src/auth.ts
// Authentication: who is calling? (Authorization: Bearer <token>)
export async function authenticate(request: FastifyRequest) {
  const [scheme, token] = (request.headers.authorization ?? "").split(" ");
  const user = scheme === "Bearer" && token ? await userForToken(token) : undefined;
  if (!user) throw problems.unauthenticated();
  request.user = user;
  request.token = token;
}

// authorization: the user is known; may they do this?
export function requireRole(role: Role) {
  return async (request: FastifyRequest) => {
    if (request.user?.role !== role) throw problems.forbidden(role);
  };
}

export function currentUser(request: FastifyRequest): User {
  if (!request.user) throw problems.unauthenticated();
  return request.user;
}

What about JWTs?

A JSON Web Token takes the opposite approach: instead of a random key into a table, the token contains the data (the user id, the role, the expiry), signed with the server’s secret so that it cannot be changed. Here is one made by hand, to see what is inside:

demos/jwt.ts
// a JWT: header and payload in base64url, then an HMAC of both with the server's secret
const header = b64({ alg: "HS256", typ: "JWT" });
const payload = b64({ sub: 2, role: "customer", exp: 1795000000 });
const token = `${header}.${payload}.${sign(`${header}.${payload}`)}`;
console.log("token:", token);

// anyone can read the payload: it is encoded, not encrypted
const read = (part: string) =>
  JSON.parse(Buffer.from(part, "base64url").toString());
console.log("payload, read without the key:", read(token.split(".")[1] ?? ""));

const valid = (jwt: string) => {
  const [h, p, signature = ""] = jwt.split(".");
  const expected = Buffer.from(sign(`${h}.${p}`));
  const given = Buffer.from(signature);
  return given.length === expected.length && timingSafeEqual(given, expected);
};

Note: tokens in browsers

A mobile app keeps the token in the phone’s secure storage and sends it in the Authorization header, as curl does here. A website should not keep it in localStorage, where any injected script can read it. Instead the server sets it in a cookie with HttpOnly (scripts cannot read it), Secure (HTTPS only) and SameSite=Lax (not sent with most requests from other sites), and reads the cookie instead of the header. Cookies bring a risk of their own, cross-site request forgery, which Chapter 9 deals with.

Professional habit: test the “no” for every route

For every protected route, write at least two tests: one without a token (401) and one as a user who must not have access (403 or 404). Add them in the same pull request as the route. The day someone removes a hook or changes a query, these tests fail, which is far cheaper than finding out from a customer who saw someone else’s order.

Summary

  • Authentication finds out who is calling (401 if unknown); authorization decides what they may do (403, or 404 to hide existence).
  • Passwords are stored with a slow, salted hash (scrypt here), compared in constant time.
  • Sign-in gives the same answer and the same time for a wrong email and a wrong password.
  • Session tokens are random bytes, stored only as a hash, and revoked by deleting the row.
  • A JWT carries signed data that anyone can read and nobody can revoke: good between services and for minutes, not for user sessions.
  • Protect whole plugins with a hook, filter records by owner in the query, rate-limit login, and test every “no”.

Quick check answers: 1. A session token is 32 random bytes: there are far too many possibilities to try, so the hash only needs to stop someone who reads the table from using the values directly, and a fast hash does that. A password is chosen by a person from a small set of likely words, so an attacker can try the likely ones quickly unless each try is made deliberately slow. 2. 403 Forbidden: the server knows exactly who is calling (the token is valid), so the problem is not authentication; the user lacks the admin role. 3. So that the response takes the same time whether or not the email exists; otherwise an unknown email would be answered much faster, and the time would reveal which emails have accounts.

Chapter 1

  1. The status line is HTTP/1.1 200 OK; the headers are Content-Type, Content-Length, Date and Connection; then comes the empty line, and the body is the JSON object of 41 bytes. Without Host, Node answers 400 Bad Request by itself, before our code runs, so not even our log line appears: HTTP/1.1 requires the header, and Node enforces it.
  2. GET /products?max_price=100: safe and idempotent. PUT /products/2 with a full product: not safe, idempotent (the product ends up the same however many times it is sent). POST /products/2/reviews: neither; two requests make two reviews. DELETE /cart/items/7: not safe, idempotent. PATCH /products/2 with {"stock_change": -1}: neither, because each request takes one more item from the stock; a PATCH that sets a value ({"stock": 4}) would be idempotent.
  3. In handle, after the line that matches /products/:id, add: if the method is DELETE, find the product’s index with findIndex; answer 404 if it is -1, otherwise remove it with splice and answer send(res, 204). The first delete answers 204 and the second 404; that is still idempotent, because the server is in the same state after both. The new product, though, gets id 3 again, because the id is “number of products + 1”. A client holding an old link to product 3 now gets a different product, and if you had deleted product 1 instead, the new product would get the id of product 3, which still exists. Ids must never be reused: keep a counter, let nextId = products.length + 1, and use nextId++. With that change, the run in the code repository creates product 4. A database does this for you, with a sequence.
  4. The product list is public: anyone can read it with curl, so a page on another site reading it in a visitor’s browser learns nothing secret. CORS only stops other sites’ JavaScript from reading answers with the visitor’s browser. The danger is an endpoint that answers with private data because of the visitor’s cookies, such as GET /me/orders: there, letting any origin read the answer would let any site read the visitor’s orders. What protects it is not CORS alone, but the server checking who is asking (authentication), what they may see (authorisation), and cookies with SameSite, together with a short list of trusted origins.
  5. The answer must carry Content-Encoding: gzip, so the client knows to decompress; Content-Length with the size of the compressed bytes; and Vary: Accept-Encoding, so a cache never gives a compressed copy to a client that cannot read it. In send, check res.req.headers["accept-encoding"], compress with gzipSync from node:zlib, and send the buffer. With the three products of the run, the list is 128 bytes plain and 105 bytes compressed. That is a small saving, because gzip needs repetition to work with; on a list of a hundred products, the same JSON shrinks to a fraction of its size. That is also why servers do not compress tiny bodies: below about 1 KB, the work costs more than it saves. curl --compressed sends the header and decompresses the answer for you.

Chapter 6

  1. Nothing of the three changes is kept. The connection drops, PostgreSQL sees the session end without a COMMIT, and rolls the transaction back; its row locks are released at the same moment, so the transactions waiting for those rows continue. A crash of the database server itself has the same result: on restart, an uncommitted transaction never happened.
  2. Page views: an atomic update, UPDATE pages SET views = views + 1 WHERE id = $1, with no read in code; nothing to check, so nothing can race. A numbered seat: an atomic conditional update (UPDATE seats SET booked_by = $1 WHERE id = $2 AND booked_by IS NULL, and look at the number of changed rows) or a unique constraint on the seat in a bookings table. A unique username: a unique constraint (or unique index), and turn its error into a 409; checking first in code is only for a friendly message, never the guarantee.
  3. Make both transactions take the rows in the same order, lowest id first: B runs run("B", 1, 2) like A. Then B waits at product 1 until A commits, and continues; no cycle is possible. The programs take an ordered argument for this, and the run in the code repository prints “A: done” and “B: done” in both editions. With several products, sort them by id before locking or updating.
  4. The lock is held for the whole duration of the network call, which can take seconds or time out, and every other buyer of that product waits in the meantime; a slow payment service becomes a slow shop. Worse, if the charge succeeds and the commit then fails, money is taken for an order that does not exist. A better order: (1) a short transaction that reserves the stock with an atomic update and creates the order as “pending”; (2) the charge, outside any transaction, with an idempotency key made from the order id; (3) a short transaction that marks the order “paid”, or releases the stock if the charge failed. A worker cancels pending orders that stay pending too long.
  5. async function retrying<T>(work: () => Promise<T>, attempts = 5): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await work();
    } catch (error) {
      const code = (error as { code?: string }).code;
      if (attempt === attempts || (code !== "40001" && code !== "40P01")) throw error;
      const pause = Math.random() * 20 * 2 ** attempt; // grows with each attempt
      await new Promise((resolve) => setTimeout(resolve, pause));
    }
  }
}

    The pause is random so that two transactions that collided do not retry at the same instant and collide again; it grows so that a busy moment gets time to pass. Only the whole transaction is retried, never a single statement, because everything it read may have changed.

Chapter 7

  1. The product price: a few minutes, with invalidation on every change, because a wrong price shown for minutes is tolerable only if changes also delete the key at once. The exchange rate: as long as its source updates it, often an hour, since every page reads it and it changes on a schedule. The list of countries: a day or more; it almost never changes, and a deploy can clear it. It is never deleted, the count only grows, and that client is refused forever. Send both in one MULTI/EXEC transaction, or use EXPIRE key 60 NX in the same transaction, as the chapter’s program does, or a Lua script that does both.
  3. Every cached product page that shows the category must be invalidated.   4. Process A took the lock and paused for 7 seconds (a long query, a garbage-collection pause, a slow network). At 5 seconds the lock expired; process B took it and started the same work. For 2 seconds both worked at once, and when A finished, its release script saw B’s token and correctly left B’s lock alone. Protections: (1) make the work safe to run twice, with database constraints, conditional updates or idempotency keys, so a duplicate does no harm; (2) a TTL with a wide margin, and a watchdog that renews the lock (only if the token is still ours) while the work continues; (3) a fencing token: an increasing number given with the lock and stored with every write, so the database refuses a write carrying an older number than one it has already seen.

Chapter 8

  1. The salt makes every user’s hash different, so identical passwords do not show as identical hashes, one computation cannot attack every row at once, and precomputed tables are useless. It does not make each guess slower: SHA-256 is still billions of guesses a second, so a weak password in any single row falls in seconds. The fix is a slow, memory-hard function (scrypt, Argon2, bcrypt), with a salt.
  2. No header: 401. An expired token: 401, since the server can no longer tell who is calling; the client should sign in again.   5. Sign-in returns two tokens: an access token, a JWT valid for 10 minutes carrying the user id and role, and a refresh token, random bytes stored as a hash in the database with a long expiry. Every API request checks only the JWT’s signature and expiry, without a database query. The gain is no database lookup on most requests, which matters when many services check tokens; for a single API with a database already involved in every request, this chapter’s sessions are simpler.
